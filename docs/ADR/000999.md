# ADR-000999: 所有者で絞るベクトル検索の候補選定を EXISTS 半結合に切り替え、HNSW 候補を実体化して distance + 0 で並べ直す

## Status

Accepted

## Date

2026-11-07

## Affected Services

- rag-orchestrator (Go): `Search` / `HybridSearch` / `SearchNeighbors` の SQL と、その形を固定する repository テスト
- rag-db (PostgreSQL + pgvector): スキーマ・設定の変更なし。plan の形だけが変わる
- alt-backend (Go): 一回限りの `cmd/rag_owner_backfill` が pgbouncer 越しに simple protocol で接続する

## Context

rag-orchestrator のベクトル検索は、テナント分離以降 `rag_documents.user_id` で所有者を絞っている。分離より前に索引した文書の大半は `user_id` が NULL のままで、検索から見えていなかった。これを埋める一回限りの owner backfill (`cmd/rag_owner_backfill`) を本番で実行した。

backfill の直後から、Augur の 1 ターンに約 3 分かかり、ブラウザ側でエラーになった。1 ターンの中でベクトル検索は 3 回走る。元クエリ、展開クエリの並列検索、回答のあとの related citations である。ログではそれぞれ 51 s・56 s・53 s かかっていた。

旧 SQL は候補選定の段階で 3 テーブルを結合していた。

```sql
SELECT ...
FROM rag_chunks c
JOIN rag_document_versions v ON c.version_id = v.id
JOIN rag_documents d ON v.document_id = d.id
WHERE d.current_version_id = v.id
  AND d.user_id = $owner
ORDER BY c.embedding <=> $query
LIMIT $n
```

プランナは `v.document_id = d.id` と `d.current_version_id = v.id` の 2 キー結合の行数を 1 行と見積もった。その結果、HNSW index (`rag_chunks_embedding_idx`) を使わず、全 chunk との距離を計算してから並べる plan を選んでいた。backfill 前は所有者付きの文書がほとんどなく、絞り込みの段階で候補が尽きていたので表に出なかった。SQL は変えておらず、データ分布の変化で顕在化した plan の退行である。

並べ直しにも制約があった。[[000987]] は `hnsw.iterative_scan = relaxed_order` を rag-db の既定にしている。relaxed_order の index scan は、距離順を厳密には保証しない。さらに PostgreSQL 17 以降は、インライン化された CTE や subquery のソート順を外側でも使い回す。そのため外側の `ORDER BY` が plan から消えうる。最初に EXISTS だけへ書き換えた版では、実際に外側の Sort が消えた。

## Decision

所有者で絞るベクトル検索の候補選定を EXISTS 半結合に切り替え、候補を `AS MATERIALIZED` で実体化したうえで、外側で `distance + 0` によって並べ直すことを採用する。

### 1. 候補選定は EXISTS 半結合にする

```sql
WITH candidates AS MATERIALIZED (
  SELECT c.id, (c.embedding <=> $query) AS distance
  FROM rag_chunks c
  WHERE EXISTS (
    SELECT 1 FROM rag_documents d
    WHERE d.current_version_id = c.version_id
      AND d.user_id = $owner
  )
  ORDER BY c.embedding <=> $query
  LIMIT $candidate_limit
)
SELECT ...
FROM candidates cand
JOIN rag_chunks c ON c.id = cand.id
JOIN rag_document_versions v ON c.version_id = v.id
JOIN rag_documents d ON v.document_id = d.id
WHERE d.current_version_id = v.id AND d.user_id = $owner
ORDER BY cand.distance + 0 ASC
LIMIT $limit
```

- 候補を選ぶ段階では `rag_document_versions` を結合しない。所有者条件は EXISTS の中、つまり LIMIT の前に置く。
- `version_number` / `title` / `url` / `article_id` は、候補を絞ったあとに外側で結合して取る。
- この形だとプランナは HNSW の index scan と Nested Loop Semi Join を選ぶ。

### 2. 候補を実体化し、`distance + 0` で並べ直す

- pgvector が relaxed_order と組み合わせて推奨している書き方に従う。
- `+ 0` は式を index の順序とは別物にする。これでプランナが外側の Sort を省けなくなる。
- `HybridSearch` と `SearchNeighbors` の vector arm は、`vector_candidates AS MATERIALIZED` に対して `rank() OVER (ORDER BY distance + 0)` で順位を付ける。

### 3. 3 経路を同じ形にそろえる

- 対象は `Search`、`HybridSearch`、`SearchNeighbors` の 3 つ。`SearchNeighbors` は回答のあとの related citations が使う。
- `HybridSearch` / `SearchNeighbors` の text arm も、所有者の絞り込みを EXISTS にする。

### 4. SQL の形を単体テストで固定する

repository テストが生成された SQL を捕捉し、候補段ごとに次を確かめる。

- `rag_document_versions` が現れない。
- EXISTS が `d.current_version_id = c.version_id` で結合している。
- 所有者条件が EXISTS の中、LIMIT より前にある。
- `MATERIALIZED` と `distance + 0` がある。
- HNSW の `ORDER BY` が LIMIT より前にある。
- 外側の結合し直しの内容。

### 5. backfill は pgbouncer 越しに simple protocol で接続する

`cmd/rag_owner_backfill` は pgbouncer を経由して接続する。pgx 既定のキャッシュ付き prepared statement では、`42P05`(prepared statement already exists)で衝突した。そこで `QueryExecModeSimpleProtocol` を使う。

### 検証

修正前の値は障害時のログ上の所要時間、修正後の値は本番 rag-db で読み取り専用に実行した `EXPLAIN ANALYZE` である。

| クエリ | 修正前 | 修正後 |
|---|---|---|
| `Search`(元クエリ) | 51 s | 37 ms |
| `HybridSearch`(展開クエリの並列検索) | 56 s | vector arm 4 ms |
| `SearchNeighbors`(related citations) | 53 s | 16 ms |

`force_generic_plan` で generic plan を強制すると、新 SQL でも HNSW を使わず、十数秒から 30 秒弱かかる。一方、rag-orchestrator は pgx 既定のキャッシュ付き prepared statement で rag-db に直接つなぐ。既定の `plan_cache_mode = auto` では、custom plan の推定コストが generic plan の約 60 分の 1 なので、custom plan が選ばれ続ける。

### 検討して却下した代替案

- **`CREATE STATISTICS` で行数推定を直す**: PostgreSQL の拡張統計は 1 テーブル内の列相関しか扱わない。テーブルをまたぐ 2 キー結合の誤推定は直らない。
- **`rag_chunks` に `user_id` を非正規化し、1 テーブルで絞る**: `current_version_id` の切り替えと同期させる書き込み経路と migration が必要になる。応答停止の修正としては重い。所有者が増えて走査量が問題になったときの選択肢として残す。
- **`hnsw.iterative_scan = strict_order` にする**: 外側の並べ直しは不要になる。ただし rag-db 全体の既定を変えることになり、[[000987]] の判断をこの修正の範囲で覆す。pgvector が relaxed_order 向けに示す書き方で足りる。
- **`SET LOCAL` や plan hint の拡張でプランナを誘導する**: トランザクションごとの設定、または拡張の導入が要る。データ分布が変わると追従しない。

## Consequences

### Pros

- 1 ターンのベクトル検索 3 回が、それぞれ約 50 s から数十 ms 以下になった。Augur の 1 ターンが検索待ちで数分かかる状態がなくなる。
- 所有者付き文書の比率が変わっても、HNSW の index scan と半結合の plan が保たれる。
- relaxed_order の下でも、返す順序が距離順で厳密になる。
- 候補段を 3 テーブル結合に戻す変更は、単体テストで落ちる。

### Cons / Tradeoffs

- 単体テストが見るのは SQL の形だけで、plan は検証しない。plan の退行はデータ分布しだいで起き、CI では検出できない。所有者フィルタ付きベクトル検索の SQL を変えるときは、本番相当のデータで `EXPLAIN` を取り、`rag_chunks_embedding_idx` が plan に残ることを確かめる必要がある。
- generic plan では HNSW を使わない。`plan_cache_mode` を `force_generic_plan` にしたり、pgx の実行モードを変えたりすると再発しうる。
- 候補段の所有者フィルタは index scan の出力に対して効く。所有者が増えて 1 人あたりの文書が全体のごく一部になると、iterative scan が `hnsw.max_scan_tuples` に達し、LIMIT より少ない件数で返りうる。そうなったら、上で残した非正規化案を検討する。
- `SearchWithinArticles`(記事 ID で絞る検索)は今回の対象外で、外側の厳密な並べ直しがない。現在の plan は HNSW を使わないので順序は正しい。ただし plan が変わると、relaxed_order による順序のずれが出うる。
