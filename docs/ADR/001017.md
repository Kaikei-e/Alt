# ADR-001017: rag-orchestrator の peer 許可リストに alt-harvester を加え、止まっていた RAG 索引登録を復旧する

## Status

Accepted

## Date

2026-11-18

## Affected Services

- rag-orchestrator — `PEER_IDENTITY_ALLOWED_PEERS` の既定値更新（`alt-harvester` を追加）
- alt-harvester — `compose/core.yaml` の古いコメント更新、再投入に伴う索引登録の再開
- compose — `compose/rag.yaml` の既定許可リスト更新、`compose/core.yaml` のコメント更新
- deploy — `deploy/desired-env.lkal` と `deploy/host-prereqs.yaml` の許可リスト宣言更新
- observability — outbox の `FAILED` 件数と最終登録文書時刻の検知指標・アラート検討（実装時に具体化）

## Context

[[001015]] の R0 として、読書と後続のつながり機能（[[001023]]）の前提となる RAG 索引登録の停止を復旧する必要がある。2026-11-17 時点の本番データを読み取り専用で計測した結果は次のとおりである。

- `alt-db` の `outbox_events` に `FAILED` が 968 件ある。うち 958 件は 2026-11-03 以降の `RAG UpsertIndex returned non-OK status: 403` であり、残り 10 件は 2026-10-31 の status 500 である。
- `rag-db` の `rag_documents` の最後の行は 2026-11-03 である。開いた記事 523 本のうち、埋め込みがあるのは 268 本にとどまる。

設定・コード・起動ログから原因を特定した（コンテナ再起動後に新規の登録試行がなく、`caller not in allowlist` のログ行自体は取得できていない）。

- `rag-orchestrator` は 2026-10-31 のコミット `b240295f0` で mTLS の peer 検証を fail-closed にした。`rag-orchestrator/cmd/server/main.go`（158〜160 行目）は REST サーバに `peerMW.Require` を掛けており、`rag-orchestrator/internal/middleware/peer_identity.go`（61〜67 行目）が証明書の CN が許可リストにない場合に HTTP 403 を返す。このサービスで 403 を返す箇所はここだけである。起動ログは `peer_identity_enabled`、`mode: mtls`、`allowed_peers: ["alt-backend"]` を出している。
- 一方、`outbox-worker` は [[000954]] の 3 プロセス分割により `alt-harvester` で動いている（`alt-backend/app/di/container_harvester.go:169-180`、`alt-backend/app/orchestrator/job/registry.go:35`）。`alt-harvester` の証明書の CN は `alt-harvester` である（`compose/core.yaml:566` の `CERT_SUBJECT`）。
- `compose/core.yaml:578-581` のコメントは、`outbox-worker` が `alt-harvester` で動くなら許可リストに `alt-harvester` が必要だと書いていた。しかし許可リストの宣言 3 箇所はすべて `alt-backend` のまま残っていた。
  - `compose/rag.yaml:206`: `PEER_IDENTITY_ALLOWED_PEERS=${RAG_ORCHESTRATOR_ALLOWED_PEERS:-alt-backend}`
  - `deploy/desired-env.lkal:47`: `RAG_ORCHESTRATOR_ALLOWED_PEERS = ["alt-backend"]`
  - `deploy/host-prereqs.yaml:440-441`: `required: [alt-backend]`
- `alt-backend/app/adapter/augur_adapter/augur_adapter.go:105-116` と `alt-backend/app/orchestrator/job/outbox_worker.go:191-222` では、5xx を一時障害として再試行する一方、4xx は終端の `FAILED` として再試行しない。このため 403 になった全イベントが再試行されずに止まった。

既存の検証と監視でこの停止を検知できなかった理由も確かめた。

- `altctl mtls validate` と `altctl mtls observe`（`altctl/cmd/mtls.go:20-23`、`altctl/internal/mtlsedge/types.go:14-16`、`altctl/internal/mtlsedge/semantic.go:74-118`）は `pre-processor -> news-creator` の単一エッジ専用に固定されており（[[000998]]）、`alt-harvester -> rag-orchestrator` は検査しない。
- `scripts/kisage-env.py` の `verify`（655〜675 行目）は、`deploy/desired-env.lkal`・`deploy/host-prereqs.yaml`・`compose/` 既定値の 3 箇所が互いに一致しているかを見るため、3 箇所が揃って `alt-backend` のみを書いていれば通る。
- `alt-backend/app/orchestrator/job/outbox_metrics.go:24-36` には `alt_harvester_outbox_events_failed_total` などの OTel カウンタがあるが、`observability/` 配下の Prometheus / Grafana ルールにはこのカウンタや `outbox_events` の `FAILED` 件数を見る規則がない。`observability/prometheus/rules/augur-answer-alerts.yml:200-301` には埋め込み世代と所有者の網羅率ルールはあるが、`rag_documents` の最終登録時刻を見る指標やアラート規則はない。

## Decision

1. **`RAG_ORCHESTRATOR_ALLOWED_PEERS` を `alt-backend` と `alt-harvester` の 2 つにする。** `compose/rag.yaml`、`deploy/desired-env.lkal`、`deploy/host-prereqs.yaml` の 3 箇所の宣言を同じ変更で更新し、`compose/core.yaml` の古いコメントも実態に合わせて改める。理由は、`outbox-worker` を動かす `alt-harvester` の証明書 CN（`alt-harvester`）を受信側が許可するためである。
2. **反映後、`FAILED` になった索引登録イベントを `PENDING` に戻して再投入する。** 索引登録は冪等である。本番データベースへの書き込みになるため、運用者が持ち主の確認を得てから実行し、2026-11-03 以降に索引されていない記事を埋める。理由は、403 で終端になった 958 件を含む未登録記事を自動復旧させるためである。
3. **4xx を終端の `FAILED` とする outbox の扱いは変えない。** `augur_adapter` と `outbox_worker` が 4xx を再試行しない現行仕様は維持する。理由は、本来 4xx は再試行しても成功しない拒否であり、再試行対象にすると別の恒久エラーでキューが詰まり続けるためである。
4. **索引登録が止まったことを検知できるようにする。** 監視対象は `outbox_events` の `FAILED` 件数と、最後に登録された文書の時刻とする。具体的な指標やアラート規則の手段は、既存の `alt_harvester_outbox_events_failed_total` などの有無を踏まえて実装時に決める。理由は、今回は 2 週間以上停止に気づけなかったためである。
5. **プロセスを分けて呼び出し元の CN が変わるときは、受信側の許可リストを同じ変更で更新する。** [[000954]] の分割でこの 1 本が漏れた教訓を運用規律として固定する。理由は、設定宣言の一致検査だけでは実行時の呼び出し元の移動を検出できないためである。

### 検討した代替案

- **(a) `outbox-worker` を `alt-backend` に戻す**: 退けた。[[000954]] で決めたユーザ向け API と定期ジョブのプロセス・障害境界の分離に反するためである。
- **(b) `alt-harvester` の証明書の CN を `alt-backend` にする**: 退けた。別プロセスに同じ CN を与えると呼び出し元の識別を偽ることになり、mTLS のピア単位の認可が崩れるためである。
- **(c) `rag-orchestrator` の peer 検査を無効にする**: 退けた。[[000741]] とコミット `b240295f0` の fail-closed 方針に反するためである。

## Consequences

### Pros

- `alt-harvester` からの索引登録（`UpsertIndex`）が通り、2026-11-03 から止まっていた記事の埋め込み作成が再開する。
- `alt-harvester` 固有の CN を使うため、[[000741]] のピア識別と [[000954]] の責務分割をどちらも維持できる。
- `outbox_events` の `FAILED` 件数と最終登録時刻の監視方針を置くことで、同種の無言の停止を早期に検知できるようになる。

### Cons / Tradeoffs

- `compose/rag.yaml`、`deploy/desired-env.lkal`、`deploy/host-prereqs.yaml` の更新だけでは過去の `FAILED` 968 件は復旧しない。反映後に持ち主の確認を得て `PENDING` へ戻す運用作業が必要である。
- 10 月 31 日の status 500 による 10 件の `FAILED` を合わせて戻すか、11 月 3 日以降の 403 分（958 件）だけを対象にするかの判断は再投入手順の実行時に決める。
- 検知指標の具体的な集計方法（`outbox_events` の SQL / exporter 化か既存 OTel カウンタへのアラート追加か、`rag_documents` の最終時刻の取得先）と閾値は本 ADR では決めていない。
- `altctl mtls validate` を他エッジへ広げるかどうか（[[000998]]）は本 ADR の対象外とする。

## Deploy-model 整合性セルフチェック

この ADR は compose の環境変数既定値（`RAG_ORCHESTRATOR_ALLOWED_PEERS`）とコメントを変えるが、新しい compose サービスの追加や `depends_on` の変更はない。既存の `rag-orchestrator` を rolling で再作成するだけで反映でき、rolling 互換である。
