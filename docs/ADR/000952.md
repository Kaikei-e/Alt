# ADR-000952: 3-day Recap 多層障害の恒久対策として ML アーティファクト整合ゲート・実面 CDC・BFF CSRF double-submit・キュー 429 backpressure・admin retry no-op 禁止を導入する

## Status

Accepted

## Date

2026-07-26

## Affected Services

- recap-subworker (Python)
- recap-worker (Rust)
- news-creator (Python)
- alt-frontend-sv (TypeScript / SvelteKit)
- recap-migration-atlas

## Context

2026-07 の 3-day Recap 多層障害の詳細調査結果は [[PM-2026-052]]
（`docs/postmortems/PM-2026-052-recap-3days-multilayer-outage.md`）を参照。
本 ADR は同インシデントの修正で確定した、単一サービスに閉じない横断的な
設計決定 5 件のみを記録する。個々のバグ再現手順・タイムライン・影響範囲は
postmortem 側の正本とし、ここでは重複させない。

主な事象（決定の背景として必要な範囲のみ）:

- recap-subworker: `pyproject.toml` の `scikit-learn>=1.5.0`（unbounded
  floor）が定期依存更新で 1.8.0 → 1.9.0 に上がり、`data/genre_classifier_ja.meta.json`
  に記録された学習時 sklearn バージョンと起動時ランタイムバージョンが
  minor 精度で一致しなくなった。`recap_subworker.services.classifier._guard_metadata_against_runtime`
  （[[000835]] stage 3 の fail-closed ガード）は仕様通り起動時に
  `ConfigValidationError` で拒否したが、検知が本番デプロイ後になり
  classification worker pool が初期化不能になった。
- recap-worker ↔ recap-subworker の clustering pact
  (`pacts/recap-worker-recap-subworker.json`) が `POST /v1/clustering/{run_id}`
  という、実装にも本番トラフィックにも存在しないエンドポイントをスタブ実装
  して「緑」を維持していた（fabricated route）。
- alt-frontend-sv の CSRF ガードは、guard 時に auth-hub の `/session` を
  再取得してリクエストのトークンと比較していたが、auth-hub の CSRF トークンは
  リプレイ耐性強化で毎秒変化する HMAC（unix 秒タイムスタンプ埋め込み）に
  なっており、再取得比較は原理的に一致しない。
- news-creator の `HybridPrioritySemaphore` が `QueueFullError` を送出しても
  `/api/generate` 等のハンドラはそれを捕捉せず 500/502 として返しており、
  呼び出し元（recap-worker）は backpressure と障害を区別できなかった。
  recap-worker 側も `classify_coarse` がクライアント全体の 1h タイムアウトを
  継承し、チャンク/タグ生成の失敗にリトライが無かった。
- recap-worker `/admin/jobs/retry` は常に空 `genres` の新規 `JobContext` を
  作って `run_job` を呼び、成功すれば無条件に `202 Accepted` を返していた。
  再実行対象の failed job が無くても "成功" に見える silent no-op だった
  （Rule 8 違反）。

## Decision

### D1. ML アーティファクト/ランタイム整合を CI ゲートで検証する

学習済み分類器アーティファクト（joblib）が前提とする scikit-learn バージョンを
`pyproject.toml` で学習時 minor に上限ピンする
（`scikit-learn>=1.8.0,<1.9.0`）。加えて `uv.lock` の実解決バージョンと
アーティファクトの学習時バージョンの一致を CI unit test
（`recap-subworker/tests/unit/test_classifier_sklearn_lock_drift.py`）で検証する。
アーティファクト本体はホストマウントの gitignored ファイルのため、テストは
`uv.lock` を「ビルド時に何が入るか」の正本として扱い、`.meta.json` の
学習時バージョンをテスト内定数として固定し比較する。

**代替案として却下**:
- 依存更新のたびにアーティファクトを再学習する — GPU ビルドが必須で
  定期依存更新フロー（自動 PR）に乗らず、非現実的。
- ランタイムガードのみに依存する — [[000835]] の fail-closed 自体は正しい
  設計だが、検知タイミングが本番デプロイ後になるため、CI 側で同じ不整合を
  事前に検知するゲートが別途必要。

### D2. CDC は実在するエンドポイントのみを対象にする

recap-worker ↔ recap-subworker の clustering pact を、実際に存在する面
（`POST /v1/runs` + `GET /v1/runs/{run_id}`）に置き換える。provider 検証は
`recap_subworker.app.routers.runs` の実 router に DI override（usecase
依存をインメモリ fake に差し替え）を通した実面検証とし、存在しない
エンドポイントをハンドフェイクのスタブで「緑」にすることを禁止する。

デプロイ済みの旧 consumer（recap-worker の frozen pact）に対しては
expand-then-contract で段階移行する: `test_provider_verification.py` の
`_create_provider_app` に `POST /v1/clustering/{run_id}` のレガシー互換スタブを
撤去条件コメント付きで一時併存させ、対象の recap-worker バージョンが
Pact Broker の deployed 記録から外れた時点で削除する。この撤去条件は
テストファイル側のコメントを正本とし、恒久的な互換レイヤーとしては扱わない。

**代替案として却下**:
- 旧 consumer pact を無視して provider 検証をスキップする — `can-i-deploy`
  が deployed な旧 consumer pact も検証対象にする設計（[[000752]] の
  `deployedOrReleased` selector）と矛盾し、デプロイゲートを壊す。

### D3. BFF の CSRF ガードは double-submit cookie 方式にする

auth-hub が発行する CSRF トークンはリプレイ耐性強化のため呼び出しごとに
値が変わる。「guard 時に auth-hub から再取得して比較する」方式は原理的に
成立しない。そこで、トークン発行時（`POST /csrf`）に httpOnly /
`SameSite=Strict` cookie（`csrf_token`、TTL は auth-hub の
`DefaultCSRFTTL` に合わせる）へミラーし、guard 時は cookie の値と
`X-CSRF-Token` ヘッダーを直接比較する（`verifyCsrfToken`）。guard 時に
auth-hub への追加往復は発生しない。auth-hub 側のトークン発行・検証ロジックは
無変更。

**代替案として却下**:
- auth-hub の Validate API を新たに HTTP 公開する — サービス間結合と
  リクエストごとの往復が増える。
- BFF と auth-hub で HMAC secret を共有し BFF 側で単独検証する — secret の
  露出面が広がり、auth-hub を CSRF トークンの唯一の発行者に保つ方針に反する。

### D4. キュー飽和は 429 backpressure として表面化させる

news-creator の `QueueFullError`（`HybridPrioritySemaphore` 由来）を、
`/api/generate` / `/api/expand_query` / `/api/recap_summary` の各ハンドラで
捕捉し、`500`/`502` ではなく `429` + `Retry-After` として返す。これは
2026-02 の queue-saturation 対策（[[000185]]、429 + hold_slot + 指数
バックオフの 3 層）のうち、HTTP 層での明示的な 429 化が漏れていた箇所を
補完するものであり、既存の 3 層設計を置き換えない。

あわせて recap-worker 側にも有界化を入れる: `classify_coarse`
（coarse genre classification, `POST /v1/classify/coarse`）はクライアント
全体の 1h タイムアウトを継承していたのを
`RECAP_SUBWORKER_COARSE_CLASSIFY_TIMEOUT_SECS`（デフォルト 30s）による
per-call タイムアウトに変更し、タイムアウト/失敗時は有界リトライの上で
ジャンル未確定記事を "other" にフォールバックする。チャンク要約・タグ生成の
失敗にも同様にリトライを追加した。

### D5. admin retry の no-op 成功を禁止する

`/admin/jobs/retry` を、最新の failed recap job を実際に再実行する処理に
変更する（`retry_most_recent_failed_job` → `RetryOutcome::{Started,
NoFailedJob, AlreadyRunning}`）。空 `genres` の新規ジョブを作って
`run_job` が成功したことをもって "成功" とみなす silent no-op は
CLAUDE.md Rule 8（no silent fallback）違反として排除する。HTTP status は
outcome ごとに明示的に分岐する: `Started` → `202 Accepted`、
`NoFailedJob` → `404`、`AlreadyRunning` → `409`。

## Consequences

### Pros

- scikit-learn の定期依存更新が、学習済みアーティファクトを黙って壊す前に
  CI で検知される（本番起動失敗として発覚することがなくなる）。
- recap-worker ↔ recap-subworker の CDC が実装と乖離しなくなり、
  存在しないエンドポイントを前提にした「グリーンだが嘘の」契約が排除される。
- CSRF 検証が auth-hub のトークンローテーション仕様と整合し、guard 時の
  追加往復も発生しない。
- キュー飽和が呼び出し元から区別可能なシグナル（429 + Retry-After）として
  見えるようになり、genre 分類/チャンク/タグ生成の一過性失敗が有界リトライで
  自己回復するようになった。
- admin retry の応答が実際の状態と一致し、運用者が「再実行が効いたのか」を
  誤認しなくなる。

### Cons / Tradeoffs

- news-creator は依然として単一ワーカーの event-loop blocking と
  `MAX_QUEUE_DEPTH=10` を前提にしており、~30 ジャンル規模の fan-out には
  対応できていない（[[PM-2026-052]] L5 として指摘済み、別 ADR で扱う）。
  D4 の 429 化はこの構造的上限を可視化しただけで、上限自体は引き上げていない。
- recap-subworker 側のレガシー clustering pact 互換スタブ（D2）は、
  Pact Broker の deployed 記録が新しい recap-worker バージョンに更新されるまで
  コードベースに残る。撤去は手動確認を要する。
- scikit-learn のピン（`>=1.8.0,<1.9.0`）は現状凍結であり前進ではない。
  1.9 系への再学習・再検証は未実施（このスコープ外）。
- `recap_jobs.status` への CHECK 制約追加、`window_days` デフォルト削除
  （`recap-migration-atlas/migrations/20260725000000_*.sql`,
  `20260725000100_*.sql`）は本 ADR の decision 群を支える防御的スキーマ変更
  であり、既存データに対して読み取り専用で確認済みだが、将来 D5 と別軸で
  拡張する場合はこの CHECK セットを合わせて見直す必要がある。
