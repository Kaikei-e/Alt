# ADR-001010: Clean Architecture の層ルールから例外を無くし check_layers を agent のフィードバックループに組み込む

## Status

Accepted

## Date

2026-11-14

## Affected Services

- alt-backend (Go) — JWT の context キーを `shared/domain/authcontext` から `utils/authcontext` へ移動。`archtest` の Driver → Domain 検査を `alt/shared/domain` まで拡張
- リポジトリ共通の開発ハーネス — `.claude/skills/clean-architecture/`（`check_layers.sh`、`known_violations.tsv`、`SKILL.md`）、`AGENTS.md`、`CLAUDE.md`

## Context

[[000001]] が定めた層構成（Handler → Usecase → Port → Gateway → Driver）は、コーディングエージェント向けには `clean-architecture` skill と `check_layers.sh`（ripgrep による Go / Python の import 検査）で伝えていた。運用してみると 3 つの問題があった。

**1. 検査が「0 件になるまで直す」という完了条件として使えなかった。**
`check_layers.sh` は文書化済みの負債も違反として報告していた。`alt-backend/app` で 58 件、`knowledge-sovereign/app` で 28 件の `VIOLATION` が出る一方、他の 14 サービスは 0 件だった。58 件のうち 54 件は `alt-backend/app/archtest` の `knownViolations` が CI で免除している `shared/driver/alt_db` と `shared/driver/sovereign_client`、28 件は `knowledge-sovereign/app/CLAUDE.md` が明記している縮退構成（handler / usecase が `driver/sovereign_db` を直接 import）と Pact provider ハーネスである。スクリプトは skill の手順書から手動で呼ぶだけで、編集時にも CI でも実行されていなかった。

**2. Handler が Port を import してよいかが文書間で食い違っていた。**
`clean-architecture` skill の import 表は「REST → Usecase, Domain」、`alt-backend/CLAUDE.md` と `tdd-workflow` skill は「Handler は Usecase と Port を import」としていた。実装は後者の形で、`alt-backend/app` の handler 層 107 ファイル（テスト除く）のうち 17 ファイルが port パッケージを import している。`dataplane/connect/datahubapi` は alt-db への薄いデータ API で、handler 27 ファイルに対して usecase は 5 個であり、Port を直接呼ぶ構成が [[000241]] 以来の設計になっている。

**3. Driver が Domain 配下のパッケージを import していた。**
`alt/shared/domain/authcontext` を 4 つの Driver が import していた。CI の `archtest` は `alt/domain` しか見ないため通っていたが、「Driver は Domain を import しない」という skill のルールには反する。このパッケージは 1 ファイル 16 行で、非公開の context キーと `WithJWT` / `JWTFromContext` だけを持ち、エンティティもドメインエラーも含まない。Driver はこれを Connect / HTTP クライアントの中で読み、外向きリクエストの認証ヘッダに載せている。

一次情報も確認した。Clean Architecture の原典が定めるのは「source code dependencies can only point inwards」であり、外側の層が 1 層飛ばして内側を呼ぶことの可否は書かれていない。Hexagonal Architecture の原典も同じである。Go の `context` パッケージのドキュメントは、キーを所有するパッケージが非公開キーと型安全なアクセサを提供する形を示し、Go 公式ブログの例では外向きリクエストを出すパッケージ自身がそのアクセサで値を読んで送信リクエストに載せている。

## Decision

層ルールを「例外なしで成り立つ形」に揃え、その検査を agent の編集ループに組み込む。

### 1. Handler は Usecase・Port・Domain を import してよい

`clean-architecture` skill の import 表を「REST → Usecase, Port, Domain」に統一する。Handler が Port を直接呼んでよいのは、業務判断を伴わない素通しの 1 呼び出し（単純な読み書き、ストリームの中継）に限る。複数 Port の調整、業務規則による分岐、トランザクション境界が要る処理は Usecase に置く。Port パッケージが定義する入出力型・エラー型を Handler が参照することも許す。Handler → Gateway / Driver の禁止は変えず、`check_layers.sh` が引き続き強制する。

個別サービスがこれより厳しい検査を持つことは妨げない（`auth-token-manager` のアーキテクチャテストは handler → port を禁じている）。

**却下した代替案: Handler → Port を禁止に統一する。** 原典の読みとしてはより純粋で、すべての入口が Usecase を通る保証が得られる。しかし `alt-backend` の 17 ファイルと `datahubapi` の構成を変える必要があり、Port を 1 回呼ぶだけの素通し Usecase を大量に足すことになる。それをしない場合は台帳に例外を積むことになり、「例外を無くす」という目的に反する。Port は Handler より内側にあるので、許可しても依存の向きは保たれる。

### 2. JWT の context キーを Domain の外へ移す

`alt/shared/domain/authcontext` を `alt/utils/authcontext` へ移動する。内容は変えず、import パスだけを 13 ファイル（テスト 6 を含む）で書き換える。`alt/utils/` は層に属さない横断ヘルパの置き場で、Driver はすでに `alt/utils/safeconv` を import している。あわせて `archtest` の `TestDriverDoesNotImportDomain` を `alt/shared/domain` 配下も対象にし、同じ置き方の再発を CI で止める。

**却下した代替案: Gateway が context から値を取り出して Driver に引数で渡す。** Driver は外向きリクエストを組み立てる箇所（Connect の interceptor と HTTP リクエストの生成）で context を読んでおり、呼び出し元の Gateway は JWT を保持していない。4 つの Driver のうち 2 つ（`preprocessor_connect`、`sovereign_client`）には包む Gateway 自体がない。引数で渡すには interceptor をやめ、Driver の全メソッドのシグネチャを変える必要があり、Go 公式が示す context 値の使い方からも離れる。

**却下した代替案: `authcontext` を例外として台帳に登録する。** ドメイン語彙を持たないパッケージが Domain 配下にあること自体が誤りで、例外として残す理由がない。

### 3. check_layers を閉じられるフィードバックループにする

- **台帳**: `scripts/known_violations.tsv` に、CI のアーキテクチャテストかサービスの `CLAUDE.md` がすでに免除しているものだけを記録する（ルール名、リポジトリ相対パスの接頭辞、行の部分文字列、根拠）。一致した行は `KNOWN` として集計し、終了コードに影響させない。列の欠けた行はエラーで止める。台帳は元の免除より広くしない（`alt_db` と `sovereign_client` の Driver → Domain は `"alt/domain` の import だけを対象にする）。
- **修正指示**: 違反したルールごとに `FIX <rule>: …` を 1 行出し、何をどの層へ移すかを示す。
- **対象を絞るモード**: `--file <path>`、`--changed`（`git status` の変更ファイル）、`--hook`（エディタフックのペイロードを標準入力で受け、違反があれば標準エラーにレポートを出して終了コード 2）。
- **ルール本体は変えない**: ルール名・glob・正規表現は従来のまま。

`AGENTS.md` には skill の場所と `check_layers.sh --changed` の実行を指示する節を置き、`.agents/skills/clean-architecture`（`.claude/skills/clean-architecture` への symlink）を通じて複数のエージェントが同じ検査を使う。`CLAUDE.md` の層の記述は、矢印が呼び出しの流れであって import の向きではないことを明記する。

**却下した代替案: 言語別の専用リンタ（depguard、import-linter、dependency-cruiser など）を導入する。** 既存のサービス別アーキテクチャテストと `check_layers.sh` で必要な検査は足りており、依存ツールとそのライセンス確認を増やす理由がない。

## Consequences

### Pros

- `alt-backend/app` の `check_layers.sh` は 58 件の `VIOLATION` から 0 件になり（`KNOWN` 54 件）、`knowledge-sovereign/app` も 0 件（`KNOWN` 28 件）になった。16 サービスすべてで終了コード 0 となり、「`VIOLATION` が 0 件」を完了条件として使える。
- Handler → Port の扱いが skill・`alt-backend/CLAUDE.md`・`tdd-workflow` skill で一致した。
- `alt-backend` の Driver は Domain 配下のパッケージを 1 つも import しなくなり（`knownViolations` の 2 ディレクトリを除く）、`archtest` が `alt/shared/domain` への依存の再発を検出する。
- 違反は編集直後に、直し方つきで返る。台帳にない新しい違反だけが報告されるので、既存負債のあるディレクトリでも検査がノイズにならない。
- 検証: `check_layers_test.sh` 20 ケース通過、`alt-backend` の `go build ./...`・`go vet ./...`・`go test ./...` 通過。拡張した `archtest` は移動前のツリーで 3 ファイルを検出して失敗することを確認した。

### Cons / Tradeoffs

- Handler に業務ロジックが溜まる余地が残る。「素通しの 1 呼び出しまで」という線は機械的に検査できず、レビューと skill の記述に依存する。
- `shared/driver/alt_db` と `shared/driver/sovereign_client` の Driver → Domain（計 54 行）は台帳に残ったままで、解消していない。`knowledge-sovereign` の縮退構成 28 行も同じである。
- `KNOWN` と `WARN` は `<service-dir>` モードでしか表示されない。台帳の対象ディレクトリ内で既存と同じ形の import を増やしても `--changed` では報告されないので、該当ディレクトリを変更したときはサービス全体の走査で件数を確認する必要がある。
- `check_layers.sh` とそのテストは CI から実行されていない。編集時のフックと path-scoped ルール、検査用サブエージェントの定義はリポジトリ管理外の開発者ローカル設定であり、クローンしただけでは有効にならない。
- 検査は正規表現によるヒューリスティックで、Go と Python にしか対応していない。Rust / TypeScript のサービスと、`connect/` や `internal/adapter/` のように標準と異なるディレクトリ名は対象外である。
- `alt/domain` の `user_context.go` と `tenant.go` にも context キーが残っている。今回の範囲には含めていない。
