# ADR-001018: 読書イベントを専用の ReadingService で追記し、「読んだ」を末尾到達か本文に見合う滞在で定義する

## Status

Accepted

## Date

2026-11-18

## Affected Services

- proto — `proto/alt/reading/v1/reading.proto` を新設する
- alt-frontend-sv — 読書イベントの生成・バッチ送信と `visibilitychange` / `pagehide` での確定送信を実装する
- alt-butterfly-facade — `ReadingService` を公開サービス許可リストと telemetry 依存区分へ登録する
- alt-backend — `ReadingService` の Connect-RPC ハンドラと `knowledge-sovereign` へのイベント追記経路を新設する
- knowledge-sovereign — `reading_projector` と event-auth ポリシーへの新イベント・新メソッド登録を行う
- knowledge-sovereign-db — `reading_sources` read model テーブルのマイグレーションを新設する

## Context

持ち主が 2026-11-18 に、製品の目的を「読むこと、読ませること、読んだ情報が血肉になること」と定めた（[[001015]]）。主端末は Android の Chrome であり、日常的に使われている面は Gallery（`/feeds/visual-preview`）と Swipe（`/feeds/swipe/visual-preview`）である。

2026-11-17 時点の本番データを読み取り専用で計測したところ、既読操作の間隔は中央値 1.31 秒だった。現状の既読は「読んだ」を表していない。Gallery で記事を開くとその時点でサーバ側が既読にし、Swipe で払うと既読になるため、既読数には「払った数」と「開いた数」が混ざっている。

現状は、滞在時間、記事の末尾まで読んだかどうか、どの面を見たかを記録する仕組みがない。既存の `TrackHomeAction`（`proto/alt/knowledge_home/v1/knowledge_home.proto`）は `action_type` が自由文字列であり、`alt-backend` 側の `validActionTypes` で許可した種別を受けている。また `open` には `openMarkReadAllowedSources` による既読同期の副作用が付いており、Pact の interaction も存在しない。

`knowledge-sovereign` の `knowledge_events` は `occurred_at` による月次パーティションテーブルである。現状の `RetentionHandler`（`/admin/retention/run`）は 30 日経過後のパーティションを `.jsonl.gz` へエクスポートする仕組みを持つが、パーティションの `DETACH` や `DROP` は実装されていない。

## Decision

1. **専用の Connect-RPC サービス `alt.reading.v1.ReadingService` を新設する。** `proto/alt/reading/v1/reading.proto` を新設し、`(alt.api.v1.visibility) = VISIBILITY_PUBLIC` を付けて BFF の公開サービス許可リスト（`alt-butterfly-facade/internal/server/allowlist_gen.go`）へ登録する。最初のメソッドは複数イベントをまとめて受ける `RecordReadingEvents` とし、経路は `alt-frontend-sv` → `alt-butterfly-facade` → `alt-backend` → `knowledge-sovereign` とし、`knowledge_events` に追記する。あわせて `alt-butterfly-facade/internal/resilience/dependency_class.go` の `telemetryEndpoints` に登録し、送信失敗で読み取り系のサーキットブレーカーを開かせない。理由は、型付きの契約で複数イベントを安全に送り、既存の読み取り導線の障害予算と分離するためである。
2. **既存の `TrackHomeAction` には足さない。** 理由は 3 つある。第 1 に、`action_type` が自由文字列であり、滞在時間やスクロール率を `metadata_json` に型のないまま運ぶことになる。第 2 に、`open` には既読同期の副作用が付いている。第 3 に、BFF と `alt-backend` の間にも、`alt-backend` と `knowledge-sovereign` の間にも `TrackHomeAction` の Pact interaction がない。理由は、既存 RPC の副作用や型なし文字列を引きずらずに契約を始められるためである。
3. **イベントの語彙を段階ごとに定める。** R0 では `reading.surface_viewed.v1`、`reading.reached_end.v1`、`reading.session_ended.v1` を新設する。R1 では `reading.opened.v1` を新設する（[[001019]]）。R2 以降は `reading.queued.v1` / `reading.unqueued.v1`（[[001021]]）およびつながりとテーマのイベント（[[001023]]・[[001024]]）を追加する。理由は、段階ごとにイベントの意味を固定して安全に出荷するためである。
4. **重複排除はクライアント生成の `client_event_id`（UUIDv7）で行い、発生時刻はペイロードの `occurred_at` を使う。** サーバ側の受信時刻は別フィールドで記録し、業務上の時刻には使わない。理由は、クライアントの再送でも結果が変わらないようにし、業務上の時刻をサーバの時計や通信遅延に依存させないためである。`knowledge-sovereign` にまとめて追記する RPC はないので、`alt-backend` は 1 件ずつ追記する。重複排除キーはイベント種別と `client_event_id` から作る。途中で失敗したらエラーを返し、クライアントはまとめて再送する。追記済みの分は重複排除で無視される。ただし、`occurred_at` が受信時刻から 24 時間を超えてずれているイベントは、受信時刻を発生時刻として記録し、元の値をペイロードに残す。理由は、`knowledge_events` が `occurred_at` の月で分割されており、時計の狂った端末のイベントが既定のパーティションに入ると、その月のパーティション作成を妨げるためである。
5. **`reading.session_ended.v1` のペイロードと送信契機を定める。** ペイロードには、記事 ID、面、前面にあった時間（ミリ秒。画面が隠れている間は数えない）、最大スクロール率、本文の文字数、末尾に到達したかどうかを含める。送信は `visibilitychange` と `pagehide` で確定させ、ページを閉じても届く送り方（`fetch` の `keepalive` または `sendBeacon`）を使う。理由は、Android の Chrome でタブを閉じたり切り替えたりしても読書セッションの計測を落とさないためである。ペイロードに入れるのは ID、面の種別、数値、真偽値、時刻だけとし、記事の題、URL、本文の断片は入れない（[[000755]] が記録した上流の WAF による遮断を避ける）。Gallery と Swipe では、本文の取得が終わるまで記事 ID が決まらないことがある。読書セッションは本文が表示されて記事 ID が決まった時点から数え、記事 ID が決まらなかった閲覧は記録しない。イベントはスクロールのたびには送らず、面を離れる時点でまとめて送る。
6. **「読んだ」を末尾到達か本文に見合う滞在のどちらかで成立と定義する。** 滞在時間の基準値は、R0 で 7 日以上ためた分布から決めるため、この ADR では具体的な数値を決めない。判定規則には `read_rule_version` を付け、read model に記録する。規則を変えた場合はイベントから再射影する。理由は、実測データに基づいて閾値を決め、後から規則を改訂しても過去イベントから再計算できるようにするためである。
7. **`knowledge-sovereign` に `reading_projector` と read model `reading_sources` を新設する。** [[000944]] の `knowledge_home_projector` と同じプロセス内ループの形で実装し、projector はイベントのペイロードだけを使って `reading_sources`（読んだ記事の一覧）を作る。`reading_sources` は捨てて作り直せる read model とし、マイグレーションは `knowledge-sovereign/migrations/` の最新（`00034`）に続いて新設する。過去に開いただけの記事は、既存の `HomeItemOpened` イベントから旧規則の原典として区別して扱う（使い方は [[001023]]）。理由は、DB 単独所有原則と再射影可能な設計を保つためである。
8. **event-auth ポリシー登録と Pact の失敗テストを producer 配線より先に置く。** 新しいイベント型と RPC を `knowledge-sovereign/config/event-auth-policy.json` および `policyAuthInterceptor` に登録する。`alt-butterfly-facade` と `alt-backend` の間、および `alt-backend` と `knowledge-sovereign` の間の Pact 失敗テスト（RED）を、producer の配線より先に置く。テストは E2E から書く。理由は、認可の既定拒否による遮断と、無言の配線漏れ（[[000928]]）を事前に防ぐためである。
9. **既読（`read_status`）の扱いはこの ADR では変えない。** 既読にするきっかけを「開いた」から「読んだ」に変える判断は、R1（[[001019]]）で決める。理由は、R0 の計測導入と R1 の挙動変更を切り分けて検証するためである。

### 検討した代替案

- **(a) `TrackHomeAction` を拡張する**: 退けた。理由は決定項目 2 のとおりである。
- **(b) 外部の解析サービスやクライアントの解析 SDK を使う**: 退けた。読書の事実が外部へ出てしまい、自前のイベントログと別系統になるためである。
- **(c) サーバのアクセスログから推定する**: 退けた。前面での滞在時間とスクロールによる末尾到達はサーバのアクセスログからは取れないためである。
- **(d) 既読を「読んだ」とみなす**: 退けた。2026-11-17 時点の本番データ計測で既読操作の間隔が中央値 1.31 秒であり、実態として「読んだ」を表していないためである。

## Consequences

### Pros

- 記事を末尾まで読んだかと前面滞在時間を型付きイベントとして記録でき、R1 以降の効果を R0 の基準値と比較できる。
- 既存の `TrackHomeAction` と `read_status` に手を入れずに計測基盤を先行導入できる。
- ペイロード完結の `reading_projector` により、後から `read_rule_version` を改訂しても `reading_sources` を再射影できる。

### Cons / Tradeoffs

- 「読んだ」を成立させる具体的な滞在時間やスクロール率の数値は、この ADR では決めていない。R0 で 7 日以上データを収集した後に決める。
- `knowledge_events` の既存リテンション方針（`SystemEventsHot = 30日`）は月次パーティション単位でエクスポート対象を決める。将来パーティションの `DETACH` や `DROP` を実装する際は、`reading.*` イベントを 30 日を超えて残すかどうかを別途設計する必要がある。
- `fetch` の `keepalive` または `sendBeacon` を使う際の認証ヘッダやボディ上限との整合は、R0 の E2E 実装時に確かめる必要がある。
- 既存の `HomeItemOpened` との重複整理および既読更新タイミングの変更は、この ADR では未解決であり [[001019]] に委ねる。
