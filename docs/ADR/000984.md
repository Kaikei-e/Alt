# ADR-000984: viewport 判定を関数 API に置き換え ResponsiveLayout を `<main>` 1 本に統合する

## Status

Accepted

## Date

2026-08-28

## Affected Services

- alt-frontend-sv (SvelteKit / Svelte 5 Runes)
  - `src/lib/stores/viewport.svelte.ts` — API 置換と breakpoint の rem 化
  - `src/lib/components/layout/ResponsiveLayout.svelte` — レイアウト骨格の 1 本化
  - `src/routes/(app)/` 配下の呼び出し側 30 箇所と、`onMount` 分岐を持つ 6 ページ
  - `viewport.svelte.test.ts` / `viewport.test.ts` / `ResponsiveLayout.svelte.test.ts` ほかページ単位テスト
  - `alt-frontend-sv/docs/DESIGN_LANGUAGE.md`

## Context

### 1. リアクティビティが「受け取り方」で捨てられていた

`useViewport()` は getter を持つオブジェクトを返し、その docstring が

```ts
// Usage: `const { isDesktop } = useViewport();`
```

を推奨していた。この分割代入は getter を **1 回だけ**評価してプレーンな boolean に束縛する。
`MediaQuery` 自体はリアクティブなのに、受け取り方でリアクティビティが捨てられていた。
src/ の 30 箇所中 **28 箇所**がこの形で、`ResponsiveLayout.svelte` を含んでいた。

この欠陥の性質は、書き手の不注意ではなく **API 自身のドキュメントが壊れた使い方を教えていた**
ことにある。全呼び出し側が指示どおりに書いた結果、全呼び出し側が凍結していた。

実測（Playwright / Pixel 5、セッションを 393 で開始して広げ、戻す）:

| viewport | `matchMedia(768)` | gallery-tile | desktop card |
|---|---|---|---|
| 393 | false | 6 | 0 |
| 851 | **true** | **6** | **0** |
| 393 に戻す | false | 6 | 0 |

メディアクエリは正しく切り替わっているのに DOM が一切動かない。凍結は方向を問わないので、
読者から見た症状は逆向きに出る — 電話を**横向きで開く**と（Pixel 5 landscape = 851 CSS px、
iPhone 13 landscape = 844）デスクトップ版が出て、縦に戻してもモバイルに戻らない。リロードする
まで直らない。

### 2. 既存テストがこれを捕まえなかった理由

`viewport.test.ts` は node 環境で回っており、`matchMedia` が無いため `MediaQuery` が fallback の
false に固定されていた。そのうえ `state.isDesktop` とプロパティアクセスで読んでおり、
**docstring が教える分割代入を一度も実行していなかった**。テストが正しい使い方をして、
ドキュメントが間違った使い方を教えていた、という取り合わせである。

### 3. 分岐を直すと今度は全ページが破棄される

凍結を直すと第 2 の欠陥が連鎖して露出する。`ResponsiveLayout` の `{#if isDesktop}` が実際に
切り替わるようになるが、**両ブランチが別々の `<main>` を持ち、それぞれ `{@render children()}`
している**。`{#if}` が反転すると中身は破棄される仕様なので、回転のたびに全ページのコンポーネント
ツリーが破棄・再生成される。`useViewport` を参照していないページも巻き込まれる
（`/knowledge/trail` の `<main>` ノード identity で `DESTROYED` を計測）。

### 4. `onMount` は二度と助けに来ない

`onMount` は tracking context ではないので再実行されない。裏を返すと、これまでは
`ResponsiveLayout` の remount が `onMount` を毎回走らせ直すことで、viewport で分岐する
`onMount` のバグを覆い隠していた。第 3 の欠陥は、その隠れ蓑が外れた瞬間に表に出る:

- `menu` — desktop ブランチが空の `<div>` で、redirect 頼み → 真っ白
- `dashboard` — `{:else}` が "Redirecting…" と表示するだけ → その文が嘘のまま停止
- `stats` — 画面に出た側と違う側だけ fetch 済み → チャートが空
- `feeds/favorites` — `mobileIsLoading` が `true` 初期値のまま → 永久ローディング

### 5. 768px と 48rem は同じ問いではない

`isDesktop()` は `min-width: 768px` を見ていたが、Tailwind v4 の `md` は `48rem` である。両者が
一致するのはルートフォントが 16px のときだけで、`app.css` はルートフォントを指定していない
＝ このアプリは読者のブラウザ設定を尊重している。既定フォントを 20px にした読者は、
768px〜960px の間で「サイドバーは出る（JS 判定）が padding はモバイル（CSS 判定）」という状態に
なっていた。旧定数の docstring は "matching TailwindCSS v4 `md` (768px)" と書いており、その記述
自体がこの取り違えだった。

## Decision

**viewport 判定を getter オブジェクトから素の関数 `isDesktop()` / `isMobile()` に置き換え、
`ResponsiveLayout` のレイアウト骨格から viewport 分岐を外して `<main>` を 1 本にし、
breakpoint を Tailwind と同じ `48rem` に揃える。**

### 4.1 API を関数にする

決め手は「壊れた使い方が検出できるか」を実測したことである。

| 壊れた書き方 | getter オブジェクト | 関数（採用） |
|---|---|---|
| `const { isDesktop } = …` | 無言で凍結 | 構文的に不可能 |
| `{#if isDesktop}` | — | ts2774 で `bun run check` が落ちる |
| `{#if !isDesktop}` | — | 検出されない → だから `isMobile()` を同時に出荷した |

**却下: getter オブジェクトを維持し、呼び出し側を `$derived` に統一する。** 書き方の規約としては
成立するが、分割代入の落とし穴がそのまま残る。この repo は eslint を使っておらず、biome にも
svelte-check にもこの形は見えないので、**規約を守らせる検出手段が存在しない**。同じバグが同じ
経路で戻ってくることが確実なので採らない。

`{#if !isDesktop}`（呼び出し忘れ）は TypeScript が黙って always-false にする唯一の穴なので、
`isMobile()` を同時に出荷して `!isDesktop` を書く理由自体を消した（該当 3 箇所を変換済み、
現在 production コードに `!isDesktop` は 1 箇所も無い）。`useViewport` / `createViewportState`
は削除したので、取り残された呼び出し側があればビルドが落ちる。

### 4.2 `<main>` を 1 本にする

`<div>` / `<main>` / `{@render children()}` を各 1 本にし、`{#if}` は `Sidebar` と
`MobileBottomNav` にだけ残す。両 viewport の差は presentation でしかないので、構造分岐ではなく
Tailwind の responsive modifier（`md:` / `max-md:`）に置く。

属性が失われていないことは、旧 2 つの `<main>` を属性単位で突き合わせて確認した。
`id="main"` / `tabindex="-1"` / `bind:this` は両ブランチで同一で、差は class 式だけだった。
`cn()` を直接実行して merge 後の出力が旧 desktop / 旧 mobile と各幅で一致すること、
`className` を渡した場合の上書き挙動、ビルド後の CSS で `max-md` が
`@media not all and (width>=48rem)`（`md` の正確な補集合で境界に隙間が無い）に落ちることを
確認済み。

**却下: `Sidebar` / `MobileBottomNav` も両方 DOM に置いて CSS で切る。** 骨格と同じ理屈で
統一できて見た目は美しいが、スクリーンリーダーがナビゲーションを二重に読み上げる。a11y 上の
不利を、対称性のために払う理由がない。

### 4.3 `onMount` の扱いを原則で決める

採用した原則:

> **redirect は到着時の判断なので `onMount` に置いたままリアクティブにしない。ただしどのブランチも
> 使える画面を描かなければならない — `onMount` は二度と助けに来ないから。**

**却下: redirect を `$effect` に移す。** 分岐がリアクティブになった以上、redirect もそうすべきに
見えるが、それは回転のたびに `goto()` が走ることを意味する。デスクトップの窓を 768px across に
ドラッグしただけでも読者の居場所を捨てる。回転は「到着」ではない。

原則の後半（どのブランチも使える画面を描く）の適用:

- `menu` — redirect は据え置き。`{#if}` を削除。`MobileMenuPage` はリンクタイルの grid で
  どの幅でも読めるので、空の `<div>` が存在しなくなる
- `dashboard` — redirect は据え置き。`{:else}` が「Redirecting…」と嘘をつくのをやめ、広い画面
  向けに組んである旨と `/home` へのリンクを出す。回転で来ても行き止まりにならない
- `feeds/tag-verse` — 既存の "desktop only" 表示に `/home` リンクを足し、自分で出口を持たせる
- `stats` / `feeds/favorites` — 画面に出た側を**初回だけ**取る `$effect`。記憶は素の `let`
  （`$state` にすると effect 自身の依存になり再トリガーする）。初回コストは不変で、回転時に
  反対側が 1 度だけ埋まる
- `augur` — `augur-page` クラスは mount の性質ではなく viewport の性質なので `$effect` + cleanup

### 4.4 breakpoint を rem に揃える

`BREAKPOINT` (768) を `BREAKPOINT_REM` (48) に改名し、クエリを Tailwind の `md` と文字通り同じ形
にする。ビルド後の CSS が `width>=48rem` を出力していることを確認済み。

**却下: `@theme` に `--breakpoint-md: 768px` を置いて CSS 側を px に固定する。** 数字は見た目に
揃うが、**アプリ全体の `md:` からアクセシビリティ上の適応を奪う**。Tailwind v4 が既定を rem に
しているのは意図的で、メディアクエリの `rem` はページが適用する font-size ではなく**初期値
（ブラウザの既定）**に解決される。したがって既定フォントを上げた読者はより広いピクセル幅まで
1 カラムを保てる — 文字が大きいぶん 1 カラムに必要な幅も広いので、それが正しい。px に固定すると
「文字だけ拡大してレイアウトは追従しない」という一番悪い組み合わせになる。

### 4.5 テストを失敗の形に合わせる

リアクティビティの主張は browser project（`viewport.svelte.test.ts`）に移し、`page.viewport()` で
393 ↔ 851 を実際に往復させて `$effect` が観測した値の列を検証する。node 側（`viewport.test.ts`）は
`window` が無いときの SSR fallback の主張だけに絞る。`ResponsiveLayout.svelte.test.ts` は回転
往復をまたいで `<main>` のノード identity が保たれることと、skip-link ターゲットがどちらの幅でも
ちょうど 1 つであることを主張する。

## Consequences

### Pros

- 回転・リサイズにレイアウトが追従する。実ブラウザで 851→393→851 の往復 7/7 を確認
- 壊れた書き方がツールチェーンに見えるようになった。分割代入は構文的に不可能、`{#if isDesktop}`
  は ts2774 で `bun run check` が落ち、`useViewport` の削除で取り残しはビルドエラーになる
- 回転がページ状態を破壊しなくなった（`acolyte/new` のフォーム入力が回転をまたいで残ることで
  実証）。visual-preview のカード数リセット・scrollY リセット・既読の復活・Augur の再質問といった
  二次被害の温床が骨格レベルで消えた
- JS と CSS が同じ問いに答えるようになり、既定フォントを上げた読者の 768px〜960px の不整合が
  解消した。アプリ全体の `md:` はアクセシビリティ適応を保ったまま
- `onMount` 分岐に隠れていた 4 ページの初期化バグが、原則つきで一斉に是正された
- テストが実際の失敗の形（実ブラウザでの回転）を実行するようになった

### Cons / Tradeoffs

- **`{#if !isDesktop}` は依然として検出されない。** `isMobile()` を出荷して書く理由を消した
  だけで、穴そのものは開いている。lint で塞げないことは §4.1 のとおり
- **「初回だけ取る `$effect` + 素の `let`」は手作りのイディオム**で、`stats` と
  `feeds/favorites` に重複している。フラグを `$state` にすると effect の依存になって再トリガー
  する、という説明なしには読めない罠を残した
- **viewport ごとに別 UI を出すページは、両ブランチとも行き止まりでない画面を自前で持つ必要が
  ある。** `dashboard` / `tag-verse` の narrow 向け文面は手書きで、同種のページが増えるたびに
  同じ手作業が要る
- **`feeds/visual-preview` の回転時のカード数・スクロール・mark-as-read は本 ADR の範囲では
  未解決。** `<main>` は保たれるが、同ページが自前の `{#if isDesktop()}` で `FeedGrid` を 2 つ
  持っており、`feeds` / `removedUrls` / cursor はその `FeedGrid` のローカル `$state` なので、
  回転で grid だけが remount される。同根の派生（`FeedGrid` の 1 本化、Augur チャットの二重実装）
  は [[000985]] で扱う。本 ADR はその前提条件である
- `ResponsiveLayout` のレイアウト差分が Tailwind の class 式に寄ったため、padding の意図
  （`FULL_BLEED_PATHS` / 没入ルートの予約 padding 撤去）が `cn()` の中の条件式として読みにくく
  なった。コメントで補っているが、構造分岐より grep しづらい

## Deploy-model 整合性セルフチェック

本 ADR はフロントエンドのアプリケーションコードとテストのみを変更する。compose service の新設も、
`depends_on` の追加も、名前付き volume の追加も無い。

- [x] 新設 compose service が `depends_on` で他 service を gate するか？ — **N/A**（新設なし）
- [x] 新設 compose service に `restart: "no"` の one-shot init container を含むか？ — **N/A**（新設なし）
- [x] 新設名前付き volume を populate する責務はどこにあるか？ — **N/A**（新設なし）
- [x] いずれも該当しない → **rolling 互換**

ただし alt-frontend-sv は Svelte のコンパイル成果物を image に焼くため、`--build` 無しの
再起動では旧バンドルが動き続ける（CLAUDE.md rule 3）。回転追従は「デプロイしたのに直らない」の
典型的な形をしているので、確認時は必ず再ビルド済みであることを先に確かめること。
