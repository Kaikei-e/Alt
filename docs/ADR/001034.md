# ADR-001034: TLS ハンドシェイクで提示される証明書の期限を blackbox_exporter で外形 probe し、サービスが報告する期限との差で発報する

## Status

Proposed

本 ADR は実装に先立つ決定の提案である。隔離した検証環境での計測とコードの読解を根拠にしており、本番の証明書チェーンに対する計測と、本番 Prometheus へのルール読み込みは行っていない。

## Date

2026-11-27

## Affected Services

- observability stack（Prometheus のスクレイプ設定とアラートルール、新設 `blackbox-exporter`）
- compose（`compose/observability.yaml` に long-running サービスを 1 つ追加）
- scripts（operational-surface の台帳と、probe 対象の網羅を強制する契約テスト）

## Context

証明書の更新は成功しているのに、プロセスが古い証明書を使い続けた障害が 2 件ある。

- [[PM-2026-029]]: TLS 終端がメモリに保持した古い証明書を返し続けた。このポストモーテムは、外部から TLS ハンドシェイクして提示証明書の期限を観測する blackbox exporter の追加をアクションアイテムに挙げており、未完了のままである。
- [[PM-2026-032]]: クライアント側が起動時に読み込んだ証明書を使い続け、ローテーションから 3 時間 25 分のあいだ気づかれなかった。

どちらも、ディスク上の証明書を監視するだけでは検知できなかった。

[[000978]] でサイドカーは廃止され、east-west の leaf は各サービスが in-process で取得している。各プロセスは `pki_enrollment_cert_not_after_seconds{subject}` を出すが、この値は自分のディスク上の証明書の期限であり、ハンドシェイクで実際に提示している証明書の期限ではない。提示証明書を外から測る手段は、compose にも Prometheus 設定にも無い。

### 現行コードで「報告は新しいのに提示が古い」状態になる経路

Go と Python の実装では、報告値が更新されるのは、発行処理が証明書と鍵を読み込み、ペアの一致を確認できたときだけである。listener 側の再読み込みは同じファイルを同じ方法で読む。したがって「再読み込みに失敗して最後の正常な証明書に戻る」動作は、報告値が新しい期限を示している間は続かない。現行コードで残る経路は次の 4 つである。

1. **設定のずれ。** 報告側が読む証明書のパスと、listener が読む証明書のパスは、別々の環境変数で設定されている。両者がずれると、報告は新しく提示は古い状態がそのまま続く。
2. **時計の後退。** 再読み込みの判定は、ファイルの更新時刻が前に進んだかどうかだけを見る。ホストの時計が戻ると再読み込みしない。これは全 listener に同時に効く。
3. **再読み込みの停止。** 一部の Python listener は 30 秒ごとのポーリングだけで再読み込みする。ポーリングが止まると古いままになる。
4. **将来の回帰。** 再読み込みを通らない listener や、前段の TLS 終端が入った場合。[[PM-2026-029]] と同じ型である。Python の listener は 4 サービスで同じ生成コードを共有しているので、回帰は複数の listener に同時に起きやすい。

つまりこの probe の主目的は、いま起きている故障の検知というより、設定のずれと回帰に対するガードである。

### 計測と確認

**クライアント証明書なしでサーバ証明書を観測できるか。** 本番と無関係な隔離ネットワーク上で、サービスと同じ TLS 設定の使い捨てサーバに blackbox_exporter v0.28.0 を当てた。

| サーバ設定 | 結果 |
|---|---|
| TLS 1.3 のみ + クライアント証明書必須（Go / Python listener と同じ設定） | `probe_success=1`、期限を取得できた |
| TLS 1.2 / 1.3 両対応 | 1.3 を交渉して成功 |
| TLS 1.2 のみ | `probe_success=0`、期限の系列は出ない |
| SAN が宛先名と一致しない | `probe_success=0` |

TLS 1.3 では、サーバ証明書はクライアントが自分の証明書を送る前に届く。クライアントは自分の（空の）証明書と Finished を送った時点でハンドシェイクを完了とみなし、サーバの拒否を待たない。このため prober に秘密鍵を持たせなくても提示証明書を読める。

**どの指標が leaf の期限を表すか。** 提示されるチェーンは leaf と中間 CA である。検証環境では `probe_ssl_earliest_cert_expiry` が leaf の NotAfter と一致し（どちらも 1795798655）、中間 CA は別の値（1953392255）だった。

**正常なローテーションで両者がどれだけずれるか。** leaf の有効期間は 24 時間、更新は有効期間の 66% 経過時点（既定値）で、1 回の更新で NotAfter は約 15 時間 50 分進む。listener が新しい証明書を読むまでの時間は実装で異なる。Go はハンドシェイクごと、Rust は 5 秒間隔、Python はハンドシェイク時または 30 秒ごとのポーリングである。どの実装でも、probe 間隔 60 秒とスクレイプ間隔を合わせて約 2 分でずれは解消する。古い証明書を持ち続けるプロセスでは、ずれは旧 leaf が切れるまでの約 8 時間続く。

**読み込み失敗時の報告値は実装で異なる。** Go と Python は、ディスク上の証明書が壊れているとき報告値を更新しない。Rust は残り時間 0 として報告するので、報告値が現在時刻になる。この状態では提示側はまだ有効な旧証明書のままなので、単純に差を取ると「提示が古い」と誤って判定される。実際にはディスク側が壊れており、プロセスを再作成すると起動時の発行に失敗して停止しうる。

**既存のアラートが何を拾い、何を拾わないか。** promtool で既存ルールと合わせて評価した。

- サービスがプロセスごと落ちた場合は、各サービスの発行状態を出すエンドポイントへのスクレイプ監視（既存）が page する。
- プロセスは生きていて listener だけがハンドシェイクできない場合は、既存のどのアラートも page しない。発行状態のエンドポイントは別の listener で、発行状態の指標はディスク上の証明書しか見ない。ユーザ旅程の SLO はエッジの 3 旅程だけを数えるので、バックエンド間の経路は対象外である。実際に、mTLS の listener がエラーで終了してもプロセスが動き続けるサービスがある。

**prober 自身の故障をどう見分けるか。** trust bundle の欠落や prober の設定不良では、全 listener の probe が同時に失敗する。これを「失敗した本数が多ければ prober 側」と推定する案を下書きで試したところ、次の穴があった。

- プロセスが生きたまま listener が 3 本以上壊れると、page が 0 本になった。Context の経路 2 と 4 は複数の listener に同時に効くので、これは本来の検知対象そのものである。
- 1 本が失敗し続けている間に別のサービスが落ちたり戻ったりすると、失敗本数が閾値をまたぐたびに継続時間が数え直され、38 分間どのアラートも鳴らなかった。

一方、全サービスは証明書の発行時に、同じ trust bundle で step-ca の TLS を検証している。prober が同じ bundle で step-ca に接続できるかを見れば、prober 側の故障を本数に頼らず直接判定できる。

**条件を瞬時値で組むと、点滅で継続時間が数え直される。** canary を入れた下書きを、既存ルールと合わせて promtool で評価した。スクレイプが 1 回失敗すると、その系列は次の成功まで消える。条件のどれかが 1 回でも欠けると、アラートの継続時間は最初から数え直しになる。

- listener が壊れている間に canary が 4 分ごとに 1 回失敗すると、44 分間 page も ticket も出なかった。
- 起動と終了を繰り返すサービス（発行状態のエンドポイントは毎回 30 秒ほど応答するが、TLS の listener は開かない）では、30 分間、この probe も既存のアラートも鳴らなかった。依存先に接続できないと終了し、再起動を繰り返すサービスが実際にある。
- page が鳴っている間に canary が 1 回失敗すると、page が解消扱いになり、約 6 分後に再び鳴った。
- ディスク側も提示側も残り 4 時間未満のサービスを止めると、ディスク側の系列が消え、「提示だけが古い」という誤った診断の page が最長 1 時間鳴った。

**期限切れの証明書を提示する listener で何が見えるか。** 隔離環境で、期限切れの leaf を提示するサーバを probe した。`probe_success=0` になり、期限を表す系列は 1 本も出なかった。過去の値として出るのではなく、消える。

**受信側への影響。** クライアント認証を要求する Go の listener 6 本は、probe のたびにハンドシェイクエラーを 1 行ログに出す。合計で 1 日あたり約 8,600 行である。Python と Rust の listener は出さない見込みである。ハンドシェイク失敗を数える既存のアラートルールは無く、HTTP 系のメトリクスも増えない。

**運用面の予算。** [[000979]] は本番 include チェーンの long-running サービス数を CI で凍結している。新しい long-running サービスは、撤去した別サービスとの相殺か、期限付きの例外が無ければマージできない。予算の運用手順は、プロセスを足す前に「既存のどのユニットがモジュールとして持てるか」を検討することを求めている。

## Decision

**observability stack に `blackbox-exporter` を 1 つ追加し、east-west の全 TLS listener をクライアント証明書なしで probe する。提示された証明書の期限と、サービスが報告する期限との差を Prometheus のルールで評価する。**

### D1. prober は秘密鍵もクライアント ID も持たない

- blackbox_exporter の tcp/tls モジュールで接続し、公開 trust bundle だけを読み取り専用でマウントしてサーバ証明書を検証する。`insecure_skip_verify` は使わない。CA 違いや名前違いの証明書は probe 失敗として現れる。
- prober 用の leaf は発行しない。受信側の peer 許可リストに監視用の項目を足さない。
- コンテナは非 root、読み取り専用ルート、全 capability 削除、`no-new-privileges`、ポート非公開とする。
- `depends_on` は付けない。trust bundle が無ければ healthcheck が失敗し、canary（D4）の失敗として現れる。
- このプロセスに TLS の期限確認以外のモジュール（HTTP や synthetic）を足さない。ユーザ旅程の外形監視（[[000980]]）とは目的も配置も別である。

### D2. probe 対象は 12 listener とし、網羅を CI で強制する

対象は alt-data-hub、auth-hub（2 ポート）、search-indexer、pre-processor、tag-generator、recap-worker、acolyte-orchestrator、recap-subworker、news-creator、rag-orchestrator（2 ポート）の計 12 である。

除外は理由を明記して管理する。既定スタックに含まれない profile 付きサービス、既定で listener を閉じているサービス、クライアント専用で listener を持たないサービス、TLS 以外で保護されているサービスが該当する。

契約テストは次を検査する。

- compose 上で証明書の subject を持つ全サービスが、「probe 対象」か「理由付きの除外」のどちらかに入っている。
- probe 対象の各サービスで、listener が読む証明書のパスと、報告側が読む証明書のパスが、compose の `environment:` 上で一致している。
- listener が読む環境変数の名前が、そのサービスの listener のソースで環境変数として読まれている。この検査は、listener のソースが変わったときにも CI で走る。
- 「既定で listener を閉じている」という理由で除外したサービスは、その既定値が実際に閉じている。

### D3. 指標と結合

- 提示側は `probe_ssl_earliest_cert_expiry` を使う。
- 報告側は `pki_enrollment_cert_not_after_seconds` を `subject` ごとに最大値で畳む。
- probe の target に `subject` ラベルを付け、`subject` で結合する。1 つの subject が複数ポートを持つ場合も 1 対多で比較できる。

### D4. アラートと重大度

利用者に影響が出る故障、または数時間以内に出る故障は `page`、それ以外は `ticket` とする。どちらも Alertmanager から配送される（[[000969]]）。

prober 側の故障は canary で見分ける。prober は 12 listener とは別に、step-ca の TLS を同じ trust bundle で probe する。全サービスが発行時に通っている経路なので、これが失敗するなら prober（trust bundle、設定、ネットワーク）か step-ca のどちらかが壊れている。

| アラート | 条件 | 重大度 |
|---|---|---|
| 提示証明書の期限切れ間近 | 提示側の残りが 4 時間未満（直近 1 時間の最後の値）、2 分継続。ディスク側が残り 4 時間以上と報告しているときに限る | page |
| listener がハンドシェイクできない | 発行状態が健全と報告しているサービスの listener が 1 本以上失敗、5 分継続。canary が直近 3 分のあいだ失敗し続けているときは出さない。1 本に集約する | page |
| 提示と報告の乖離 | 差の絶対値が 300 秒超、10 分継続。報告側の発行状態が健全なとき | ticket |
| canary の失敗 | 直近 5 分に 1 回でも失敗した状態が 10 分継続。prober は動いているのに canary の系列が無い場合を含む | ticket |
| prober の停止 | 5 分継続 | ticket |
| probe のスクレイプ失敗 | 5 分継続。prober 停止中は出さない。1 本に集約する | ticket |
| probe 対象の本数が 12 と一致しない | 10 分継続 | ticket |
| probe は成功したが期限の系列が無い | 10 分継続 | ticket |
| 提示側に対応する報告側の系列が無い | 10 分継続 | ticket |

- **page の条件を直近の窓で評価する理由。** Context の計測のとおり、瞬時値で組むと、スクレイプの 1 回の失敗で継続時間が数え直され、点滅する故障で黙る。そこで probe の成否、発行状態、ディスク側の残り時間は直近 2 分の最後の値で評価する。窓は継続時間（5 分）より短くする。プロセスごと落ちたサービスは 2 分で「報告していない」扱いになり、listener の page は鳴らない。
- **listener の失敗を「発行状態が健全と報告しているサービス」に限る理由。** この probe が page するのは、既存のどのアラートも拾わない「プロセスは生きているのに listener がハンドシェイクできない」場合である。プロセスごと落ちたサービスは既存のスクレイプ監視が、ディスク上の証明書が期限切れのサービスは既存の発行系アラートが page する。同じ原因で page を重ねない。起動と終了を繰り返すサービスは、応答するたびに健全と報告するので page の対象になる。
- **listener の失敗を 1 本に集約する理由。** 運用者は 1 人であり、同時に壊れた listener の数だけ page を出しても対応は変わらない。失敗している listener は通知の本文に列挙する。集約したアラートは失敗本数が変わっても継続時間を数え直さない。
- **本数ではなく canary で分ける理由。** Context の計測のとおり、本数による推定は本来の検知対象で page を消す。canary が成功している限り、失敗が 1 本でも 12 本でも page する。
- **canary が失敗し続けているときだけ page を止める理由。** canary の 1 回の失敗で止めると、step-ca や prober の一時的な不調のたびに page が解消扱いになり、点滅している間は page が出ない。直近 3 分のあいだ 1 回も成功していないときに限って止める。prober 全体が壊れた場合は、最初の失敗から 3 分で止まるので、継続時間の 5 分には届かない。
- **canary の失敗を「直近 5 分に 1 回でも」で数える理由。** 時々だけ成功する canary（step-ca が再起動を繰り返す場合など）でも ticket を出すためである。1 回だけの失敗では鳴らないよう、継続時間を 10 分にする。
- **期限切れ間近を直近 1 時間の最後の値で評価する理由。** Context の計測のとおり、提示証明書が実際に期限切れになると期限の系列が消える。現在値だけで評価すると、故障が起きた瞬間に page が解消扱いになる。期限到達の約 5 分後に「listener がハンドシェイクできない」が加わり、2 本が並んで鳴る。期限切れ間近のほうは、最後に成功した probe から約 1 時間後に解消扱いになる。その時点でも listener の page は鳴り続けている。
- **期限切れ間近を、ディスク側が残り 4 時間以上と報告しているときに限る理由。** 提示側のアラートは、提示だけが古い場合に限って鳴らす。更新そのものが失敗して両方が古い場合は、既存のディスク側アラートが page する。ディスク側の系列が無い（サービスが止まっている）ときも鳴らさない。古い提示値だけが残って誤った診断の page になるのを防ぐためで、その場合は既存のスクレイプ監視が page する。
- **乖離を ticket にする理由。** 鳴るのは旧 leaf が切れる約 8 時間前で、その時点ではまだ何も壊れていない。原因は設定のずれか回帰であり、夜間に起こして対応する種類のものではない。放置された場合は、残り 4 時間で「提示証明書の期限切れ間近」が page する。
- **乖離に「報告側が健全」の条件を付ける理由。** ディスク上の証明書が壊れた Rust の listener で、誤った診断の乖離が出るのを防ぐ。その状態は既存の発行失敗アラートが page する。
- 乖離の閾値 300 秒は、正常時の差（数秒）と更新 1 回分の移動量（約 15 時間 50 分）の間に十分な余裕を取った値である。継続時間 10 分は、正常なローテーションのずれ（約 2 分）で鳴らない値である。
- 期限切れ間近の 4 時間は、既存のディスク側アラートと同じ閾値である。
- 乖離と canary 以外の ticket 5 本は、page する 2 本が「結合相手が無くて黙る」「prober が止まって黙る」状態を作らないために置く。prober が停止すると「prober の停止」と「本数不一致」の 2 本が鳴る。

### D5. 運用面の予算は期限付き例外で扱う

`blackbox-exporter` を台帳に `platform` として登録し、既定の例外コード `X-PLATFORM-SHARED` と期限 2027-06-30 を付ける。凍結した上限値は上げない。期限を過ぎると CI が落ちるので、相殺できる撤去対象を見つけるか、例外を継続する根拠を計測値で示すかの再判断が強制される。

### D6. 有効化の順序

望ましい順序は次のとおりである。

1. `blackbox-exporter` を起動する（他サービスを巻き込まない単独起動）。
2. 12 本の probe と canary が成功していることを確認する。
3. その後で Prometheus に設定とルールを再読み込みさせる。

ただしこの順序は保証できない。設定の変更を検知して自動で再読み込みする仕組みを入れているホストでは、ファイルが配置されてから数分以内に Prometheus が新しい設定を読む。prober が居ない状態でスクレイプが始まると、「prober の停止」と「本数不一致」の ticket 2 本が、prober を起動するまで鳴る。D4 の重大度により、この場合も page にはならない。

### 検討した代替案

| 案 | 却下理由 |
|---|---|
| 各サービスが自分の listener に接続して提示証明書の期限を自己報告する | プロセスは増えないが、3 言語 12 listener に実装が要る。固まったプロセスが自分を測る形になり、外形 probe にならない |
| 既存の platform ユニットに持たせる | Prometheus、Alertmanager、Grafana、cAdvisor は上流の配布イメージで TLS の prober を持たない。`otel-relay` は用途を限定した自前の中継であり、監視の責務を足すとその境界が崩れる |
| 既存の業務サービスに prober をモジュールとして載せる | 無関係な監視責務を足すことになり、そのサービスの停止で監視も止まる。自前の prober 実装の保守も発生する |
| 既存の read-only mTLS エッジ検査（[[000998]]）を定期実行する | 1 回ごとの検査で時系列にならず、差分や継続時間で評価できない。ホスト側のタイマーに依存する |
| prober にクライアント証明書を配り mTLS を完結させる | 新しい ID と秘密鍵、全受信側の許可リスト変更が要る。計測の結果、提示証明書の観測には不要だった |
| サーバ証明書を検証せずに期限だけ読む | CA 違い・名前違いを見逃す |
| 検証済みチェーンの期限（`probe_ssl_last_chain_expiry_timestamp_seconds`）を使う | 検証に成功したときしか意味のある値にならない。提示チェーンの最短期限で足りる |
| すべてのアラートを `page` にする | prober が 1 つ止まるだけで十数本の page が同時に出る。運用者は 1 人であり、page は即時対応が要るものに限る |
| listener ごとに個別の page を出し、同時に 3 本以上失敗したら prober 側の故障とみなして ticket 1 本に落とす | Context の計測のとおり、プロセスが生きたまま複数の listener が壊れる故障で page が 0 本になり、点滅する別の故障で継続時間が数え直される |
| Rust の発行処理を Go / Python に揃え、読み込み失敗時に報告値を更新しないようにする | 筋は良いが、recap-worker の本番コードの変更であり本 ADR の範囲を超える。ルール側の条件で誤判定を防ぐ |

## Consequences

### Pros

- 報告は新しいのに提示が古い listener を、旧 leaf が切れる約 8 時間前に知ることができる。提示だけが古いまま期限が近づいた場合は、残り 4 時間で page し、期限到達後も解消扱いにならない。
- プロセスは生きているのに listener がハンドシェイクできない状態を page できる。これは既存のどのアラートも拾っていなかった。起動と終了を繰り返して listener が開かないサービスも、同じアラートで page できる。
- スクレイプの 1 回の失敗や、canary の一時的な失敗では、page の継続時間が数え直されない。
- [[PM-2026-029]] の未完了のアクションアイテム（外部からのハンドシェイクによる期限観測）を満たす手段になる。
- prober に資格情報が無いので、監視の追加で許可リストや発行対象が増えない。
- prober の停止、canary の失敗、対象の欠落、結合相手の欠落がそれぞれ別のアラートになり、監視が黙って機能しなくなる状態を作らない。
- 証明書の subject を持つサービスを足したとき、probe 対象への追加漏れが CI で止まる。compose の `environment:` 上での listener と報告側の証明書パスのずれも CI で止まる。
- prober 側の不具合や有効化の順序の前後では page が出ない。

### Cons / Tradeoffs

- 観測できるのはサーバが提示する証明書だけである。クライアント側が古い証明書を持ち続ける障害（[[PM-2026-032]] の型）はこの probe では見えない。クライアント側は [[000773]] の再読み込みと、別途のローテーション E2E に依存する。
- `probe_success=1` は「サーバ証明書が提示され、検証できた」ことしか意味しない。listener が正規の peer を受け入れることは確かめていない。
- 報告側の値はディスク由来なので、検知できるのは「ディスクと提示の不一致」である。更新そのものが失敗して両方が古い場合は、既存のディスク側アラートが担う。
- step-ca が止まっている間は canary が失敗するので、listener の失敗は page されず、canary の ticket だけになる。その間に listener が壊れても、この probe からは page が出ない。page が出るのは、step-ca が復旧してから約 5 分後である。step-ca の停止そのものを直接 page するルールは無く、既存の更新失敗アラートに現れるのを待つことになる。
- サービスがプロセスごと落ちた場合、この probe は page しない。その page は既存のスクレイプ監視に依存する。ディスク上の証明書が期限切れになった場合も同じで、既存の発行系アラートに依存する。
- 窓で評価するのは page の 2 本と canary だけである。乖離、期限の系列なし、報告側の系列なしの ticket は瞬時値で評価する。スクレイプが数分おきに失敗し続けている間は、継続時間が数え直されてこれらの ticket は出ない（promtool で確認した）。その場合も page の 2 本は鳴る。
- 集約した page は、失敗する listener が後から増えても通知を出し直さない。通知が出るのは最初の 1 回と、その後の定期的な再通知だけである。増えた listener は通知の本文か Prometheus で確認する必要がある。
- probe 対象の listener を運用者が環境変数で閉じると、probe が失敗し続けて page が鳴り続ける。listener を閉じるときは、probe 対象からも外す必要がある。
- 既存の抑止規則は、stack・SLI・サービス・旅程のラベルがすべて一致する page と ticket の間で働く。この ADR の集約アラート（サービスのラベルを持たない）どうしでは、page が鳴っている間 ticket が抑止される。サービスのラベルを持つアラートとの間では抑止されない。抑止規則は変更しない。
- Rust の listener だけ、読み込み失敗時の報告値の意味が他と異なる。ルール側の条件で誤判定は防ぐが、実装の不揃いは残る。
- 契約テストが保証するのは subject の網羅である。既存サービスに TLS ポートを足した場合の追加漏れは検出しない。証明書パスの一致は compose の `environment:` に書かれた値しか見ない。`env_file` から注入された値でずれた場合は検出できず、乖離アラートが担う。
- listener と環境変数名、listener とソースファイルの対応表は、契約テストの中で手で保守している。同じファイルの別の箇所が同じ名前の変数を読んでいる場合や、listener を別のファイルに移した場合の取り違えは検出できない。
- 既定で listener を閉じているサービスを運用者が有効にした場合、そのサービスは probe されない。
- Go の listener 6 本のログに、probe 由来のハンドシェイクエラーが 1 日あたり約 8,600 行増える。運用者はこれを正常なものとして読み分ける必要がある。
- 対象本数 12 はルールに直書きされる。listener の増減のたびにスクレイプ設定、ルール、契約テストを同時に直す必要がある（片方だけの変更は CI で落ちる）。
- long-running サービスが 1 つ増える。例外の期限（2027-06-30）に再判断が必要になる。
- image はタグで固定しており、digest では固定していない（リポジトリの他の監視系と同じ扱い）。
- prober の `/probe` は、内部ネットワーク上の他コンテナから任意の宛先を指定して呼べる。このネットワークは外部への到達を遮断していないので、prober を踏み台にした TCP/TLS の到達確認ができる。同じネットワークには認証の無い Prometheus が既にあり、増えるリスクは小さい。ホストへはポートを公開しない。
- prober の設定ファイルの変更は、Prometheus の設定差分の検査の対象外である。変更時は prober を再作成する必要がある。
- デプロイの仕組みによっては、新サービスは自動では起動されない。その場合は運用者が起動する必要がある（`docs/runbooks/observability-config-reload.md`）。
- 本番では計測していない。運用者は、有効化から 24 時間以内に次を確認する。確認が取れた時点で、[[PM-2026-029]] の該当アクションアイテムを根拠付きで完了にする。
  - 12 本の probe と canary がすべて成功していること。
  - 9 本のルールが Prometheus に読み込まれていること。
  - 各 subject で、提示側の期限と報告側の期限の差が数秒以内であること（本番のチェーンでも最短期限が leaf であることの確認）。
  - TLS 1.2 にも対応する Rust の listener で、交渉された TLS のバージョンが 1.3 であること。
  - probe 由来のログ行数が見積もり（1 日あたり約 8,600 行）と合うこと。

## Deploy-model 整合性セルフチェック

- [x] 新設 compose service が `depends_on` で他 service を gate するか？ — しない。`blackbox-exporter` は `depends_on` を持たず、他サービスからも依存されない。
- [x] 新設 compose service に `restart: "no"` の one-shot init container を含むか？ — 含まない。
