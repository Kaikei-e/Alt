# ADR-000989: gemma4 のライセンス分類を HF model card の Apache-2.0 表記に合わせて訂正し、許可リスト内のベースラインとして扱う

## Status

Accepted

## Date

2026-09-21

## Affected Services

- news-creator（生成モデル gemma4-e4b の選定根拠）
- recap-worker（3-day recap カード化計画が gemma4 継続を前提にする）

## Context

[[000988]] はライセンス許可リストを MIT / Apache-2.0 / PostgreSQL License に確定した際、
Context で「現行の生成モデル gemma4 系は **Gemma Terms**（独自規約）で配布されており、
上記の許可リストの分類には入らない」と記述し、Decision で「許可リストは新規採用の選定基準で
既存採用分に遡及しない」という遡及なし条項によって gemma4 の継続を正当化した。

2026-09-21 に 3-day recap の品質改善計画（[[recap-topic-cards-redesign-plan]]）で生成モデルの
継続可否を再確認したところ、Hugging Face の公式 model card `google/gemma-4-E4B-it` の
frontmatter は `license: apache-2.0` であり、`license_link` が指す Gemma 4 ライセンスページも
Apache License 2.0 の本文であることを、raw README を取得して確認した（同カードの記載:
4.5B effective / 8B with embeddings、context 128K、「Out-of-the-box support for 35+ languages,
pre-trained on 140+ languages」）。Gemma Terms が適用されるのは Gemma 3 以前であり、
[[000988]] の gemma4 に関する事実記述は誤りだった。

この記述を放置すると、次のモデル選定で「gemma4 は許可リスト外の例外」という前提から
不要な交代圧力が生まれる、あるいは逆に Gemma 系一般を許可リスト内と誤読して Gemma 3 以前の
重みまで採用される、という 2 方向の誤りが起きうる。ADR 本文は改変しない規則（docs/CLAUDE.md）
のため、訂正を本 ADR として記録する。

## Decision

**gemma4 系（Gemma 4 ファミリの重み）を Apache-2.0 として許可リスト内に分類し、
news-creator の生成モデル gemma4-e4b を「遡及なし条項による例外」ではなく
「許可リスト準拠のベースライン」として扱う。**

- [[000988]] の許可リスト（MIT / Apache-2.0 / PostgreSQL License）と除外リストはそのまま
  維持する。除外リストの「Gemma Terms」は **Gemma 3 以前**の重みに適用されるものとして読む。
- [[000988]] の「eval で勝る準拠候補が出た時点で交代する」という運用は、ライセンス起因の
  交代圧力ではなく **品質のみ**を理由とする通常のモデル選定に戻る（[[000987]] の eval ゲート方式）。
- 新しい Gemma 4 系チェックポイントを採用するときは、チェックポイントごとに model card の
  `license` フィールドを確認する（ファミリ内で表記が異なる可能性を否定できないため）。
- Gemma 4 の model card は対応言語を個別に列挙しておらず、日本語のベンチマークも載せていない。
  日本語生成の品質は許可リストとは独立に、自前の golden set で計測して判断する。

**検討した代替案**:
- *[[000988]] を完全に supersede する*: 許可リストの確定そのものは正しく、変更が必要なのは
  gemma4 の事実記述だけなので、全置換は過剰。不採用。
- *訂正せず遡及なし条項で運用を続ける*: 実務上は継続できるが、誤った事実記述が次の選定判断の
  前提として参照され続ける。不採用。
- *Gemma 系全体を許可リスト内に読み替える*: Gemma 3 以前は Gemma Terms のままであり、
  ファミリ単位の読み替えは除外リストの意味を壊す。不採用。

## Consequences

### Pros

- news-creator の現行モデルが許可リスト準拠であることが事実として記録され、recap カード化計画
  ([[recap-topic-cards-redesign-plan]]) を含む後続の設計が「例外扱い」を前提にしなくてよくなる
- Gemma ファミリ内でライセンスが世代によって異なることが明文化され、Gemma 3 以前の重みを
  誤って採用する経路が塞がる

### Cons / Tradeoffs

- ライセンスの根拠が外部の model card 表記に依存する。表記が変わった場合は再確認が必要で、
  その手順（チェックポイントごとの `license` 確認）は運用者の注意に依存する
- 日本語品質の裏付けは model card からは得られないため、gemma4-e4b の継続可否は結局 golden set
  の計測結果で決まる。ライセンス訂正は品質の保証ではない
