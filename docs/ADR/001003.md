# ADR-001003: Recap 系サーフェスの出力に鮮度と劣化理由を持たせ、古い成果物を黙って表示しない

## Status

Proposed

## Date

2026-11-09

## Affected Services

- recap-worker (Rust): 最新成果物の読み出しに許容鮮度を導入、Morning Letter の版を追記型に変更、Evening Pulse 生成をイベントとして発行
- alt-backend (Go): 3 日 Recap / Topic Cards / Morning Letter / Evening Pulse の RPC に鮮度・劣化情報を載せる
- alt-frontend-sv (SvelteKit): 各画面で古い・劣化した成果物を明示表示する
- knowledge-sovereign (Go): Evening Pulse の可用性をイベントから投影する

## Context

Recap 系の 3 画面（3 日 Recap、Morning Letter、Evening Pulse）は、上流の日次バッチが失敗しても、最後に成功した成果物を「今日の内容」として表示し続ける作りだった。2026-11-04 から 6 日間、サービス間認証の取りこぼし（[[001001]]）で日次バッチが全滅した間も、3 画面とも 11-03 の成果物を出し続け、利用者の報告まで誰も気づかなかった。

### 鮮度が表現されていない箇所

- 3 日 Recap と Morning Letter の入力は、`get_latest_completed_job(3)` で取る最新の完了ジョブである。経過時間の上限がない。Morning Letter は 6 日前の recap を入力にしても `is_degraded=false` で保存していた。同じ形の再利用は 2026-07（14 日間と 6 日間）、2026-09〜10（6 日間）にも起きている
- Evening Pulse の取得 API は日付を指定せず、最新の成功行を返す。画面の見出しは "Today's key topics" のままだった
- Topic Cards の画面だけは `latest_run` を使い、「最新の更新が完了しなかったため前回の結果を表示している」と出していた。これが既にある良い先例である
- Morning Letter は 30 分ごとの再生成を同じ行への UPSERT で上書きしており、`created_at` は最初の生成時刻のままだった。そのため、実際には古くない午後に毎日 "Stale" が表示される一方、本当に古い入力は検知されなかった。上書きで 1 日最大 48 版が失われ、版付き成果物（versioned artifacts）の不変条件からも外れていた
- Knowledge Home の Evening Pulse 導線は、可用性フラグが 2026-07 以降ずっと false で、常に無効になっていた。フラグを更新していた `DigestAvailabilityReconcileJob`（[[000464]]）が、Knowledge Home の投影を knowledge-sovereign へ移した際（2026-07-15）に撤去され、代わりがなかった

### 劣化が表現されていない箇所

- 3 日 Recap は、健全に動いた日でも約半数のジャンルが LLM を通らない抽出（1 文の切り出し）だった。直近の成功ジョブでは 19 ジャンル中 9 ジャンル。英語原文のままの 1 行が要約として並んでいたが、画面からは区別できない
- Evening Pulse は、スコア・エンティティ・埋め込みが空のまま選定されていた。全 269 回の生成で品質判定 "ok" は 0 件、全件が fallback_level 1 以上だった。それでも画面には通常の結果として表示されていた
- Morning Letter のプレースホルダ出力（[[001002]]）も成功として扱われていた

日次ジョブの失敗に対するアラートは [[PM-2026-052]] のアクションアイテムに挙がっていたが、未実装のままだった。recap 関連のアラートは 2 つある。subworker の死活監視（`RecapSubworkerDown`）と、recap のトピックスナップショットイベントが 48 時間途絶えたときに発火する `KnowledgeLoopRecapTopicSnapshotProducerDead` である。今回の 6 日間の停止では、どちらも通知に至らなかった（後者が通知しなかった理由は未調査）。日次ジョブの成否そのものを監視するアラートはない。

## Decision

Recap 系サーフェスの成果物に「いつのデータか」「どう劣化しているか」をデータ契約として持たせ、古い成果物や劣化した成果物を、そうと分かる形でしか表示しないことを採用する。

1. **鮮度をデータ契約に入れる**: 3 日 Recap / Topic Cards / Morning Letter / Evening Pulse の各 RPC レスポンスに、次の 3 点を含める
   - サーバが付与した生成時刻
   - 入力ウィンドウ
   - 最新ジョブの状態（成功 / 失敗 / 実行中と、その時刻）

   Topic Cards の `latest_run` を全画面の共通形にする
2. **許容鮮度を設定で持つ**: サーフェスごとに許容鮮度（日次ジョブ由来なら 1 周期と余裕分）を必須設定として持ち、未設定なら起動時に失敗する。読み出し側は許容鮮度を超えた成果物を「古い」と判定してレスポンスに載せる。Morning Letter は、許容鮮度を超えた recap を入力にしたとき `is_degraded=true` と `degradation_reason=stale_recap_input` を記録する
3. **劣化理由を表示する**: 既存の劣化信号を `degradation_reasons` としてレスポンスに載せ、画面に表示する
   - 3 日 Recap の抽出ジャンル数
   - Evening Pulse の fallback_level
   - Morning Letter の `degradation_reason`
4. **画面での扱い**: 古い成果物は、最後に成功した時刻と最新ジョブの失敗状態を添えたバナー付きで表示する。「Today」など当日を示す文言は、鮮度が許容内のときだけ使う
5. **Morning Letter の版を追記型にする**: [[000633]] の「同じ行への UPSERT + `generation_revision`」を改める。再生成ごとに新しい版の行を追加し、最新版は版番号の最大値で引く。鮮度は版の生成時刻で判定する
6. **Evening Pulse の可用性をイベントで投影する**: recap-worker は Pulse の生成成功をイベントとして発行し、knowledge-sovereign の projector がそのイベントだけから `today_digest_view`（[[000448]]）の可用性を導く。定期 reconcile job で可変フラグを上書きする方式（[[000464]]）は採らない。[[000464]] が扱っていたもう一方の `weekly_recap_available` は、7 日 Recap の停止（[[000184]]）以降、画面からも参照されていないため対象外とする。これをもって [[000464]] の決定を全面的に置き換える
7. **ジョブの成否を監視する**: 3 日 Recap・Topic Cards・Evening Pulse の日次ジョブについて、連続失敗と最終成功からの経過時間にアラートを付ける
8. **契約を先に固める**: recap-worker → alt-backend → alt-frontend-sv のレスポンス形が変わる。また、recap-worker → knowledge-sovereign の Pulse 生成イベントを新設する。どちらも Pact の RED テストを先に入れる

### 検討した代替案

- **古い成果物を表示しない（空にする）**: 前回の結果にも価値はあり、空画面では障害の有無も伝わらない。却下
- **FE だけで生成時刻から古さを判定する**: 失敗理由や劣化理由はサーバしか知らない。また、Morning Letter の `created_at` のようにサーバ側の時刻が正しくなければ、判定自体が誤る（今回の "Stale" 誤表示）。却下
- **reconcile job を knowledge-sovereign 側で復活させる**: 可変フラグを定期的に上書きする方式で、reproject すると再現できない。append-first の不変条件に合わない。却下

## Consequences

### Pros

- 上流が止まったとき、利用者は画面上で「古い」「失敗している」と分かる。アラートと合わせて、無検知の長期停止を防ぐ
- Morning Letter の全版が残り、品質の推移や劣化の発生時刻を後から追える
- Knowledge Home の Evening Pulse 導線が、イベントから再投影できる形で復活する

### Cons / Tradeoffs

- 4 サーフェス分の RPC・Pact・FE を同時に変える必要があり、変更範囲が広い
- Morning Letter の版を追記型にすると、行数が 1 日最大約 48 倍に増える。保持期間の方針が別途必要になる
- `today_digest_view` の可用性の導出元を変えるため、knowledge-sovereign の reproject 手順の確認が要る
- 次の 2 点はこの ADR では決めない。障害記録（[[PM-2026-062]]）のアクションアイテムとして別途判断する
  - **3 日 Recap 画面の既定表示**: 現在は旧ジャンル別経路の結果を出している。入力は数十記事しかなく、健全時でも約半数のジャンルが抽出スタブになる。Topic Cards（数千件のフィード項目が入力）に切り替えるかどうか
  - **Evening Pulse の存続**: LLM を使わない 3 件選定で、入力信号を直しても「上位クラスタのラベル」以上の情報を出しにくい。作り直すか、Topic Cards に統合するか、廃止するか
