# ADR-000990: release-deploy の pre-deploy E2E を影響範囲に絞り、デプロイ経路の詰まりどころを外す

## Status

Accepted

## Date

2026-09-25

## Affected Services

- alt-deploy（release-deploy ワークフローと付随スクリプト）
- アプリ側サービスのコード変更はなし

## Context

マイクロサービス化と CI/CD が揃っているのに、こまめなデプロイに心理的な抵抗がある状態になっていた。
alt-deploy の release-deploy 直近 35 run（2026-09-01〜09-24）の job / step 時間と失敗ログを集計すると、
原因は「遅い」と「決定的に落ちる」の 2 系統に分かれた。

**遅い**

- 1 サービスだけの変更でも総所要が約 25 分。内訳は build（1 本で最大約 10 分）→ pact → gate →
  e2e → deploy の直列。
- e2e は [[000931]] の方針で、変更範囲に関係なく常に 19 サービス分のマトリクスが走る。builder
  プールは 10 スロットなので 9 本が待ち行列に入り、e2e 段だけで約 6〜8 分かかる。
- 本番側の deploy job で `docker compose pull` が最大 1932 秒かかった run がある。builder が
  GHCR に push し、本番ランナーが細い回線で pull する構成で、この pull が deploy の直前、
  つまり本番ロック保持中の直列区間に置かれていた。

**決定的に落ちる**

- 直近の失敗 3 件中 2 件が Wave 4 TLS smoke の `auth-hub:9110 ... Name or service not known`。
  `docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}'` が、複数
  ネットワークに属するコンテナ（auth-hub は alt-network と kratos-admin）の IP を区切りなしで
  連結し、urllib がそれをホスト名として DNS 解決していた。pki-agent サイドカー廃止で auth-hub が
  in-process enrollment の検査対象に入ったことで顕在化した。flaky ではなく全面ロールのたびに再現する。
- 切り替え開始後に失敗した run は `.c2quay/partial-rollout` マーカーを残す。次の run は build /
  pact / e2e を約 25 分走らせたあと `Mark rollout in progress` で foreign lock を検出して止まり、
  人手の `acknowledge_foreign_lock` を要求していた。1 回の失敗が 2 run 分の停止に連鎖する。

## Decision

以下 4 点を採用する。

1. **pre-deploy E2E を影響範囲に絞る。** `services_all` を「変更サービス ∪ その pact pairs ∪
   forced provider」とする。次のときは全サービスに戻す:
   - `proto/` または `compose/` 配下の変更（共有配線の変更）
   - workflow_dispatch の `full_e2e` 入力、または repository_dispatch の `client_payload.full_e2e`
   - サービス指定なしの manual dispatch

   選択ロジックは `scripts/resolve-affected.js` の純関数に切り出す。`SERVICE_PATHS` などの
   テーブルはワークフロー内の定義を渡し、スクリプト側には持たない（二重管理を作らない）。
   テーブルが渡されなければ例外で止める。
2. **partial-rollout ロックを resolve ジョブで先行判定する。** foreign lock があれば開始 1 分以内に
   同じメッセージで止める。自動 ack は「マーカーの SHA が今回の SHA と一致」かつ「その run が
   completed」の両方を満たすときだけ行い、`::warning::` で明示する。run 状態の API 照会に
   失敗したら ack しない（fail-closed）。deploy job 側の既存チェックは race 対策の最終防衛線として残す。
3. **本番ランナーで image を先行 pull する。** build 完了直後に prefetch job を本番ランナーで起動し、
   pact / gate / e2e と並行して変更サービスの image を `docker pull` する。本番の concurrency
   group は取らず、`continue-on-error` でリリースを止めない。deploy job の pull は正のまま残す
   （通常はキャッシュヒットになる）。
4. **TLS smoke の IP 解決を直す。** `docker inspect` をネットワーク名つきの `name=ip` 形式で出し、
   alt-network（Compose の project 接頭辞つき名も含む）を選ぶ。判別できないときは空を返して
   probe を明示的に失敗させ、別ネットワークの IP で推測しない。

### 検討した代替案

- **e2e 全件を維持し、builder スロットを増やす**: 待ち行列は減るが、19 本分の計算資源と総所要は
  残る。単一マシン前提の運用で builder を増やす余地は小さいため却下。
- **近傍を Pact Broker の matrix から動的に引く**: provider 変更時に全 consumer を網羅できるが、
  resolve が Broker 到達性に依存し、Broker 障害で e2e 選択まで壊れる。まずは既存の pact pairs
  テーブルで運用し、取りこぼしが観測されたら再検討する。
- **二重 pull（ワークフローの pull と Ansible 内の pull）の片方を削る**: 2 回目はキャッシュに
  当たるため効果が小さい。効くのは pull を直列区間から外すことなので prefetch を選んだ。
- **foreign lock を常に自動 ack する**: 別 SHA の途中ロールを黙って上書きするとロックの意味がなくなる。
  同一 SHA かつ完了済みに限定した。

## Consequences

### Pros

- 1 サービス変更での e2e が 19 本から数本になる（例: recap-evaluator だけの変更なら recap-evaluator と
  recap-worker の 2 本、alt-backend だけの変更なら同一モジュールの 4 バイナリと
  knowledge-sovereign の 5 本）。builder プールの待ち行列も解消する。
- GHCR pull が本番ロック保持区間の外に出る。回線が遅い日でも deploy job の所要が安定する。
- 全面ロールのたびに決定的に落ちていた TLS smoke が通るようになる。
- 同一 SHA の再実行は人手の ack なしで通る。別 SHA の foreign lock は 25 分後ではなく開始直後に止まる。

### Cons / Tradeoffs

- [[000931]] が pre-deploy 層でも常時全件としていた方針を部分的に緩める。pre-merge 層（Alt 側 PR
  CI）の常時全件は維持しているので回帰網は二重のままだが、pre-deploy 層の保証は影響範囲に限られる。
- 近傍は pact pairs と forced provider に基づくため、provider 変更時に全 consumer の e2e を必ずしも
  網羅しない。この取りこぼしは provider verification（契約テスト）で補う前提。不安があるリリースは
  `full_e2e` で全件に戻す。
- `compose/` 配下の変更は全件扱いにしたので、サービス個別の compose ファイルだけを触る変更でも
  全件 e2e になる。短縮効果は減るが、共有配線の回帰を拾う側に倒した。
- 本番ランナーは 1 スロットなので、prefetch は別 run の deploy job 実行中は待たされる。
  workflow 単位の concurrency で run 自体が直列化されているため、実害は小さい見込み。
- 自動 ack は GitHub API への照会に依存する。照会失敗時は従来どおり人手の ack が必要になる。
