# ADR-001024: 読んだ記事だけを原典に、テーマページを recap-worker で版を重ねて作り、文ごとに出典と照合する

## Status

Accepted

## Date

2026-11-18

## Affected Services

- recap-worker (Rust): `src/pipeline/themes/` を新設し、テーマごとのページ生成、版管理、`story_id` 継続の共用切り出し、日次バッチとイベント発行を実装する
- recap-subworker (Python): 既存の `/v1/embed`、`/v1/cluster-stories`、`/v1/verify` をテーマ生成パイプラインから再利用する
- recap-migration-atlas: `recap-db` に `read_themes`、`read_theme_versions`、`read_theme_runs` テーブルを新設する
- knowledge-sovereign (Go): `reading.theme_version_created.v1` と `reading.theme_opened.v1` を fold し、一覧用 read model `reading_themes` と `reading_theme_members` を新設する
- alt-backend (Go): テーマ表示用の RPC を提供する
- alt-data-hub (Go): 記事 ID の集合で本文を返す
- alt-frontend-sv (TypeScript / SvelteKit): `/knowledge` および `/knowledge/themes/[themeId]` 画面を新設する
- proto: テーマ版作成・閲覧イベントおよび関連 RPC 契約を追加する

## Context

持ち主は 2026-11-18 に製品の目的を「読むこと、読ませること、読んだ情報が血肉になること」と定め、その形として「読んだ記事だけを原典にした wiki」を選んだ ([[001015]])。[[001023]] が担う記事末の 1 対 1 の接続に対し、本 ADR では段階 R3 のもう一方の部品である「テーマごとに版を重ねるページ」の生成・検証・保存・表示方針を決める。

2026-11-17 時点の本番データを読み取り専用で計測した結果と、既存サービスの構造から次の事実を確認した。

- **既読規模と Topic Cards の基盤**: 開いた記事は 523〜667 本 (本文長の中央値は 6,424 文字) である。Topic Cards は 42 日で 643 枚生成され、374 個の `story_id` のうち 97 個が複数日にまたがっている。`recap-worker` には埋め込み (`SubworkerEmbedCluster` 経由で `recap-subworker` の `POST /v1/embed` を呼び `bge-m3` 1024 次元ベクトルを生成し `recap-db` にキャッシュする経路)、クラスタリング (`/v1/cluster-stories`)、トピック継続判定 (`src/pipeline/cards/rank.rs:147-214` の `determine_novelty_and_continuation`、`theta_novelty` 既定 `0.80` で `story_id` と `continues_card_id` を引き継ぐ)、文単位の検証器 (`CardVerifier` 経由で `/v1/verify` を呼び G3 帰属類似度 `tau_a` 既定 `0.55` と G4 推測語句検査を行い、不合格文を落とす `pipeline.rs:1404-1619`) が既にそろっている。
- **Topic Cards の埋め込み経路は `rag-db` に非依存である**: `rag-db` の索引登録は 2026-11-03 から止まっているが ([[001017]])、Topic Cards の埋め込みは `recap-subworker` と `recap-db` のキャッシュで完結しており、`rag-db` に依存しない。
- **Acolyte は既読記事限定のまとめに向かない**: 本番の Acolyte レポートは 11 本・62 版で、1 本の生成に約 8 分かかる。`acolyte-orchestrator/acolyte/domain/brief.py:11` の `KNOWN_SCOPE_KEYS` は `{"topic", "report_type", "time_range", "entities", "exclude"}` であり、記事 ID の集合を明示して根拠にする経路がない。
- **引用付き生成の裏づけと幻覚の知見**: ALCE (Gao ら、arXiv 2305.14627) では ELI5 において最良のモデルでも回答の 50% で引用による裏づけが不完全であった。また Hagar, Agustianto, Diakopoulos (2025、arXiv 2509.25498、査読前) では 300 文書のコーパスで出力の 30% に幻覚が含まれ、汎用チャット型の約 40% に対し出典に閉じたノート型は 13% で、誤りの多くは出典が支えていない解釈を断定する型であった。出典照合と未裏づけ文の除去が不可欠である。
- **サービス間の呼び出し関係の現状**: [[000789]] 時点では `recap-worker` が `alt-backend` の旧内部 RPC を呼んでいたが、現状は [[000954]] の 3 バイナリ分割により `recap-worker` (`compose/recap.yaml:154`、`src/clients/alt_backend.rs:128-160`) は `alt-data-hub` の `services.datahub.v1.DataHubService` へ mTLS 接続し、`DATAHUB_ALLOWED_PEERS` (`compose/core.yaml:818`) に `recap-worker` が登録されている。ほかに `recap-worker` は `knowledge-sovereign` (`AppendKnowledgeEvent`)、`recap-subworker`、`news-creator` を呼んでいる。

## Decision

1. **原典を「読んだ記事」に閉じ、ページを追記型で版管理する**: テーマページは [[001018]] の `reading_sources` にある読んだ記事だけを原典とし、テーマごとのまとめとして作る。原典の記事データは書き換えない。ページは版を重ね、既存の版を上書きしない。理由: 読んだ知識の蓄積を不変の原典と追記型の版として残すためである。
2. **生成パイプラインを `recap-worker` に新設する**: `recap-worker/recap-worker/src/pipeline/themes/` を新設する。クラスタリング (`/v1/cluster-stories`)、トピック継続 (`story_id` 引き継ぎ)、文単位の出典照合 (`CardVerifier` / `/v1/verify`) を流用し、`rank.rs` のトピック継続処理は共用できる形に切り出す。理由: テーマ生成に必要な部品がすべて `recap-worker` 側にそろっているためである。
3. **保存先を `recap-db` に新設する**: `recap-migration-atlas/migrations/` に `read_themes`、`read_theme_versions`、`read_theme_runs` テーブルを新設し、所有者は `recap-worker` とする。理由: 生成パイプライン・埋め込みキャッシュ・ジョブ実行履歴と同じ DB に閉じてデータ所有権を保つためである。
4. **埋め込みは Topic Cards と同じ経路で作り、`rag-db` に依存しない**: `SubworkerEmbedCluster` と `recap-db` の埋め込みキャッシュを使う。理由: `rag-db` の索引障害の影響を受けず、[[001023]] とは独立して開発・リリースできるためである。
5. **ページの構成を 4 要素に定める**: 各版は、要点 (各文に出典記事へのリンク)、時系列、前の版から変わったこと、まだ分かっていないことの 4 節で構成する。理由: 新たに読んだ記事による知識の更新と未解決の問いを版ごとに可視化するためである。
6. **出典で裏づけられない文を載せない**: `CardVerifier` (`/v1/verify`) の検証を通らない文は掲載せず落とす。理由: ALCE の知見どおり引用付き生成でも裏づけ漏れが起こりやすく、Hagar ら (査読前) が示すとおり出典外の断定が主な誤り型であるためである。
7. **不変の原典と保守される wiki を分ける構造に合わせる**: 不変の原典、LLM が保守する wiki、スキーマの 3 層と ingest / query / lint の操作を採る Karpathy の「LLM Wiki」(GitHub gist、2026-04-04) の型に合わせる。本リポジトリの文書 wiki と同じ規則 (原子的、概念指向、密にリンク、原典不変) で運用する。理由: 原典と解釈を分離して再構築可能性と検証可能性を保つためである。
8. **日次バッチで新しい版を作る**: 生成は日次バッチで行い、新しく読んだ記事が既存テーマに入ったときと、新しいテーマができたときにのみ新しい版を作る。テーマとして成立させる最小記事数は実装時に決める。理由: 変化のないテーマを毎回再生成する計算費用と無意味な版増加を避けるためである。
9. **イベント 2 種・read model 2 表・画面 2 面を新設する**: イベント `reading.theme_version_created.v1` と `reading.theme_opened.v1` を新設し、`knowledge-sovereign` に一覧用 read model `reading_themes` と `reading_theme_members` を新設する。`alt-frontend-sv` には `/knowledge` と `/knowledge/themes/[themeId]` を新設する。理由: 一覧や既読導線の読み取りをイベント駆動の投影に統一するためである。
10. **原典の取得は、`recap-worker` が既に接続している相手から行う**: 原典の一覧（`reading_sources`）は `knowledge-sovereign` から取り、記事の本文は `alt-data-hub` の `DataHubService` から取る。どちらも `recap-worker` が現状で接続している相手であり、サービス間の辺は増やさない。メソッドを足すときは、受信側の peer 許可リストと `knowledge-sovereign` の event-auth ポリシーを同じ変更で更新する。ページ本文の読み出しは、Topic Cards と同じく `alt-backend` が `recap-worker` の API を呼ぶ経路に合わせる。理由: 辺を増やすと許可リストの更新漏れが起きうる（[[001017]]）ためである。
11. **Acolyte は使わない**: テーマページ生成に `acolyte-orchestrator` は使わない。理由: `KNOWN_SCOPE_KEYS` に記事 ID 集合を明示指定する経路がなく、さらに 1 本あたり約 8 分を要するためである。

### 検討した代替案

- **Acolyte のレポートを使う**: 記事 ID 集合を指定する契約が無く、生成に約 8 分かかるため却下した。
- **`rag-orchestrator` に置く**: クラスタリングと `CardVerifier` が `recap-worker` / `recap-subworker` 側にあり、`rag-db` の索引障害と運命を共にしてしまうため却下した。
- **Recap や Morning Letter を流用する**: 入力が全フィードであり、読んだ記事だけに閉じる前提を満たさないため却下した。
- **エンティティのグラフとコミュニティ要約 (GraphRAG, Edge ら arXiv 2404.16130)**: 数百本の規模ではテーマ単位のクラスタリングで足り、エンティティグラフ構築の費用が見合わないため却下した。

## Consequences

### Pros

- `rag-db` の索引状態に左右されず、既存のクラスタリング・継続判定・検証器の資産を活かしてテーマページを立ち上げられる。
- 文単位の検証器で未裏づけ文を落とすため、出典から飛躍した断定の混入を構造的に抑えられる。
- 版の追記型保存と不変の原典により、後から版の差分や根拠をたどれる。

### Cons / Tradeoffs

- テーマとして成立させる最小記事数、`theta_novelty` やクラスタリング閾値をテーマ用に調整するか否かは本 ADR では決めず、実装時に決める。
- 要約が生成失敗の定型文である記事を原典入力からどう除外・フォールバックするかは本 ADR では決めない。
- `knowledge-sovereign` から原典の一覧を読むメソッドと、`alt-data-hub` から記事 ID の集合で本文を引くメソッドの具体的な形は、実装時に決める。
- 自分で構造を作る場合と機械が与えるテーマページを読む場合の学習効果の差は一次資料で確認できていない。
