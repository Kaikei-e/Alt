# ADR-000991: 日本語音声合成エンジンに Irodori-TTS v4.1-Small を採用し tts-speaker を GPU 推論の前段として再導入する

## Status

Accepted（2026-10-01）

受け入れ条件 G1〜G8 を満たしたので Accepted とした。採用構成は C3（v4.1-Small の INT8 重み・RF 40 ステップ）で、60 文字チャンク、`expandable_segments`、既定速度 1.25x を組み合わせる。実測値と判定は「計測経過」に記す。

## Date

2026-10-01

## Affected Services

- tts-speaker (Python) — 新設
- irodori-tts (third-party / CUDA) — 新設
- compose（`compose/tts.yaml`、`compose/base.yaml` の secrets）
- pki-agent scripts（provisioner の bootstrap と CN allowlist）

## Context

### 現状

- 日本語の読み上げ機能は 2026-08-08 に撤去済みである。`tts-speaker`、`proto/alt/tts/v1`、BFF からの配線、compose 定義がまとめて削除された。
- 撤去直前のエンジンは [[000900]] で選んだ Qwen3-TTS-12Hz-0.6B-CustomVoice だった。その前は Kokoro-82M だった。
- サービス間認証は [[000743]] で mTLS に一本化されている。`X-Service-Token` はもう存在しない。証明書は [[000978]] の in-process enrollment で各サービスが取得する。
- compose のスタックは `include:` で束ねている。既定の `docker compose up` で起動しない opt-in のサービスには、`perf` と `backup` の profile という前例がある。
- 想定する用途は、Evening Pulse のような日本語要約文の読み上げである。リアルタイム応答より、事前生成（バッチ）での品質を重視する。オンデマンドでの再生成も想定する。

### 課題

- **日本語品質。** 第三者による日本語ローカル TTS 12 モデルの比較では、Kokoro は速度 1 位だが日本語評価は C だった（評価者 1 名の主観を含む）。Artificial Analysis の Speech Arena など英語中心のリーダーボードの順位は、日本語品質を反映しない。選定には日本語での評価材料が要る。
- **VRAM の制約。** 稼働機の GPU は LLM（news-creator）と共有しており、LLM が常駐した状態で TTS に割ける VRAM は限られている。以下、この上限を「VRAM 予算 B」と呼ぶ。B の値は運用者が稼働機の状況から決め、本 ADR には記載しない。Irodori-TTS v4.1-Small の重みは F32 で約 3.06GB あり、サーバーの既定設定（F32）のままでは B に収まる保証がない。
  - 第三者が L4 で v4-Small（BF16 計算）を測ったところ、GPU メモリ最大使用率は 26.68%（24GB 基準で約 6.4GB）だった。
  - この値はキャッシュアロケータの挙動を含むので、実際の必要量より多めに出ている可能性がある。それでも、既定設定のままで B に収まる保証はない。

### 制約

- ライセンスは [[000988]] の許可リスト（MIT / Apache-2.0 / PostgreSQL License）に収める。対象はコード・重み・依存の全部。
- 単一マシン・単一ユーザーで運用する。GPU は LLM と共有し、TTS は VRAM 予算 B を超えないこと。使用量はプロセス単位の GPU テレメトリで測り、CUDA コンテキストを含める。
- 日本語のみを対象とする。英語テキストの読み上げは本 ADR の対象外で、別 ADR で扱う。

### 根拠（2026-09-30 調査。一次情報は公式リポジトリとモデルカード）

**日本語の読み精度**（公式の自動評価）

- 常用漢字読みベンチマーク（オリジナル版）での v4.1-Small の成績は、文単位 Kana-CER 2.36%、標準 CER 4.69% である。JSUT BASIC5000 では文単位 Kana-CER 3.43% である。いずれのデータも学習には含まれていない。
- 人手による MOS・自然性・話者類似度の大規模評価は、未実施とモデルカードに明記されている。自動指標は聴感品質を保証しない。

**VRAM と量子化**

- 公式パラメータガイドは、CUDA で `bf16`（モデル・コーデックとも）を使うとメモリが減り高速になるとしている。低 VRAM 向けには、sequential デコード、`num_candidates=1`、長い `seconds` を避けることを挙げている。
- CFG の `independent` モードでは、条件ごとに非条件ブランチが同じバッチに加わり、VRAM と計算量が増える。
- 公式の量子化版（torchao）のサイズは、INT8 重みのみが約 914MB、INT4 が約 852MB、FP8 が約 916MB である。汎用には INT8 weight-only が推奨されている。
- 第三者の L4 測定（v4-Small、短い参照音声、8 ステップ）では、INT8 と FP8 は最大使用率を約 5.4 ポイント下げたが、生成は遅くなった（INT8 は中央値で約 15%、FP8 は約 33%）。同じ記事では、参照音声を 3.8 秒から約 32 秒に延ばすと、最大使用率が 21.3% から 26.2% に上がった。量子化後の音質は評価されていない。
- 以上から、bf16 と短い参照音声の構成でも B に収まる保証はなく、稼働機での実測が要ると判断した。

**MeanFlow 版**

- v4.1-Small-MF は MIT で、4 ステップで生成する。CFG は蒸留時に取り込み済みなので、推論は 1 ステップあたり条件付き DiT を 1 回評価するだけで済む。
- JSUT の文単位 Kana-CER は、MF 4 ステップで 3.78%、通常版 40 ステップで 3.43% である。読み精度・話者類似度ともに、40 ステップの通常版の方が優れる。

**配備性**（Irodori-TTS-Server、commit `61012c760f22f7b4a6c21c5c5f8f9e148120b6f9`）

- OpenAI 互換の `POST /v1/audio/speech` を提供する。
- 設定は `IRODORI_*` 環境変数で行う。既定チェックポイントは v4-Small で、精度の既定は fp32 である。
- 同時合成数の既定は 1 で、待機が 300 秒を超えると 503 を返す。
- 長文の自動分割（既定 80 文字）は、リクエスト単位でもサーバー全体でも無効にできる。
- `/health` は認証不要で、モデル未ロードでも `status: ok` を返す。ロード済みかどうかは `runtime.loaded` で判断する。
- 公開イメージは無い。上流の Dockerfile は root で動き、`uv:latest` を使っている。
- ピーク GPU メモリを外部に出す口は無い。
- MeanFlow のチェックポイントはメタデータから自動判定され、既定ステップ数が 4 になる。

## Decision

Irodori-TTS v4.1-Small を日本語 TTS エンジンとして採用する。前段に Irodori 専用の薄い `tts-speaker` を新設して再導入する。受け入れ条件を満たすまでは opt-in のスタックとして扱い、BFF とフロントエンドにはまだ接続しない。

1. **サーバー。** Irodori-TTS-Server（commit `61012c76…`。その `uv.lock` は Irodori-TTS を `89f9d8fb…` に固定している）を、Alt 所有の `irodori-tts/Dockerfile` でビルドする。
   - 上流のソースは git の commit で固定して取得する。
   - uv のバージョンと base イメージの digest を固定する。
   - multi-stage にして venv を 1 回だけ作り、非 root で実行する。
   - イメージは CI でビルドせず、稼働機でローカルにビルドする（`pull_policy: build`）。約 9GB あるため。
2. **起動制御。** `compose/tts.yaml` の `irodori-tts` と `tts-speaker` を `profiles: [tts]` に置く。既定の `docker compose up` とデプロイでは起動せず、運用者が `--profile tts` で明示的に起動する。
   - GPU の予約は news-creator-backend と同じ書き方にする。
   - `irodori-tts` の公開はループバックだけにする。
   - Bearer キーは docker secret から渡す。
   - `HF_HUB_OFFLINE=1` とし、重みはすべて事前に配置する。
3. **VRAM 予算。** TTS コンテナの使用量を予算 B の 90% 以内に収める。B は運用者が計測時に `--budget-mib` で与える。
   - ピークは 2 つの値で測る。1 つはプロセス単位の GPU テレメトリで、CUDA コンテキストを含む。もう 1 つは `torch.cuda` の最大確保量である。
   - 後者は上流に出口が無いので、Alt 側の起動ラッパー（`alt_irodori`）が認証付きのプローブ（`/internal/cuda-memory` と `reset-peak`）を足して出す。
   - ゲートに使う値は、テレメトリのピークと「最大確保量＋CUDA コンテキスト分」のうち大きい方とする。
4. **運用構成は実測で選ぶ。** 次の 4 構成を稼働機で比べ、VRAM 予算を満たす構成のうち品質評価が最良のものを採る。
   - 共通設定は次のとおり。
     - モデルとコーデックは bf16
     - `num_candidates=1`
     - デコードは sequential
     - 同時合成数は 1
     - `IRODORI_EMPTY_CACHE_INTERVAL=1`
     - 参照音声の上限は 10 秒
     - サーバー側の自動分割は無効
     - `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`（アロケータの断片化を抑える。計測経過を参照）
   - 構成は `IRODORI_CONFIG=C1..C4` で切り替える。
   - 計測は `irodori-tts/bench/bench_vram_rtf.py` で行い、比較は `compare.py` で行う。

   | 構成 | チェックポイント | 重み | サンプリング |
   |---|---|---|---|
   | C1 | v4.1-Small | bf16 | RF 40 ステップ |
   | C2 | v4.1-Small-MF | bf16 | MeanFlow 4 ステップ |
   | C3 | v4.1-Small-Quantized / int8-weight-only | INT8 重み、bf16 計算 | RF 40 ステップ |
   | C4 | v4.1-Small-MF を INT8 重み化（`quantize_checkpoint.py` を CPU で実行してローカルに作る） | INT8 重み、bf16 計算 | MeanFlow 4 ステップ |

   - 品質が最良と見込まれる C1 を先に測る。FP8 と INT4 は評価しない。
5. **tts-speaker。** FastAPI の薄いゲートウェイとして新設する。旧 Connect-RPC 契約（`alt.tts.v1`）は復元しない。
   - **API：** `POST /v1/synthesize`（`{text, speed}` を受けて `audio/wav` を返す）と `GET /health`。`speed` は省略すると `TTS_DEFAULT_SPEED`（既定 1.25x）になり、指定できる範囲は 0.5〜1.5x である。
   - **認証：** inbound は mTLS で終端する（news-creator と同じ in-process PKI と peer identity の実装を持つ）。`PEER_IDENTITY_STRICT=true` とし、許可する peer は `alt-butterfly-facade` だけにする。`irodori-tts` へは内部ネットワーク上の HTTP と Bearer キーで接続する。
   - **前処理：** NFKC 正規化と、大文字略語・単独のアルファベットを 1 文字ずつカタカナの文字名に展開する処理だけにする。変換表はリポジトリ内に持つ。`alkana` は GPL-2.0 なので使わない。それ以外の英単語はそのまま渡す。数字・日付・単位の読み展開は入れない。受け入れ条件 G4 の結果を見て、読み辞書の ADR で扱う。
   - **分割：** 1 チャンクは `TTS_MAX_CHUNK_CHARS`（既定 60 文字。1.0x で約 12 秒の音声）以下とする。句点・改行で分けて詰め、長い文は読点で、それでも長ければ文字数で切る。上限の目的は 2 つある。チェックポイントのテキスト上限（256 トークン）を超えないことと、VRAM のピークを入力長から予測できるようにすることである。
   - **直列化とリトライ：** 1 リクエストのチャンクはロックの下で直列に合成する。ロックの待ちが長すぎたら 503 を返す。5xx・408・429・接続エラーは指数バックオフで再試行する。読み取りタイムアウトは再試行しない。
   - **設定：** fail-fast とする。`TTS_VOICE_ID` に `none` / `no-ref` / `text-only` を指定すると、起動時に拒否する。
   - **BFF / FE への接続：** 本 ADR の範囲外とする。接続する PR では、Pact CDC を RED で先に入れる。
6. **声の固定。** 本番では必ず参照音声を使う。参照音声は次の手順で作る。
   - VoiceDesign（参照なし＋キャプション）で候補を生成し（`design_voices.py`）、聴感で 1 つ選ぶ。この工程のときだけ `IRODORI_ALLOW_NO_REF_VOICE=true` にし、既定は false にしておく。
   - 選んだ候補を 5〜10 秒に切り出し、`register_voice.sh` で潜在表現（`.pt`）に変換して `voices/` に登録する。変換は `python -m alt_irodori.encode_latent` を CPU で実行する。サービス本体は `/voices` を読み取り専用でマウントするため、登録は書き込み可能な別の `run` で行う。
   - 実在人物の声は使わない。選定手順の詳細は別 ADR で決める。
7. **バージョン固定。**
   - GitHub の commit は上記 2 件で固定する。
   - Hugging Face の revision は次の 4 件で固定する。取得は `fetch_checkpoints.sh` で行う。

     | リポジトリ | revision |
     |---|---|
     | v4.1-Small | `2b28324dc263ed5e6638b3cf3dd94c82ead07b4b` |
     | v4.1-Small-MF | `ccc78f5d480b6e51b69b2d5042a14c4da04fea6e` |
     | v4.1-Small-Quantized | `ef04e6c3ba56138ae23e86a2eabc004f76990e37` |
     | Semantic-DACVAE-Japanese-32dim | `47376ee24834d7a05a48ebabfe3cde29b3c5e214` |

   - ハブへの追従はしない。
8. **透かしとローカル限定。** SilentCipher の透かしは使わない。重みの配布元にライセンス表示がないため取得せず、オフライン運用では上流のサーバーが警告ログを出したうえで透かしなしで出力する。モデルの重み、ローカルで量子化した重み、参照音声とその潜在表現は稼働機のローカルにだけ置き、リポジトリにもそれ以外の場所にも公開しない。
9. **縮退。** TTS が止まっても他の機能には影響しない。[[000943]] の「TTS は Feature-off」の劣化契約に従う。旧経路へのロールバック先はない。

### 検討した代替案

| 案 | 評価 | 不採用の理由・再検討の条件 |
|---|---|---|
| A. 撤去前の tts-speaker（Connect-RPC、Qwen3-TTS / Supertonic、ROCm イメージ）を履歴から復元する | 呼び出し側の契約が過去にあった | 旧エンジン向けの面積が大きく、日本語品質の課題も残る。新しい契約は BFF に接続するときに CDC で決め直す |
| B. Qwen3-TTS（Apache-2.0、多言語） | 日本語対応で、短文は良好との報告がある | 数字・技術語・長文で崩れやすく、実時間より遅いという報告がある。多言語が必要になったら再評価する |
| C. VoxCPM2（Apache-2.0、30 言語） | 内容保持が最良との報告がある | 抑揚に違和感が残り、第三者評価は 1 件だけ。Irodori が受け入れ条件を満たせない場合の代替候補とする |
| D. Fish Audio S2 Pro | 聴感は最も自然との報告がある | 研究用途限定のライセンス。第三者の実測では RTF 124 と遅く、VRAM 予算にも収まらない |
| E. Sarashina2.2-TTS | 日英コードスイッチに対応する | 非商用ライセンスで、日本語品質の第三者比較も足りない |
| F. Style-Bert-VITS2 | 日本語に特化し、話者ごとに学習できる | AGPL-3.0 |
| G. Irodori-TTS v4-Large | 声の設計と話者類似度で v4.1-Small を上回る | 3.29B・約 13GB で VRAM 予算に収まらない。Gemma Terms of Use の適用を受ける |
| H. ホスト型 API（Sonic、Gemini TTS、Eleven など） | 品質は上位 | 継続課金と外部依存が生じる。OpenAI 互換の境界を保っているので、後から第 2 バックエンドとして足せる |
| I. `tts-speaker` を置かず、呼び出し側が Irodori-TTS-Server を直接呼ぶ | 構成が単純 | 認証境界（mTLS）・前処理・分割・リトライの集約点がなくなる |
| J. FP8 / INT4 の量子化版 | メモリを減らせる | FP8 は L4 の測定で最も遅く、削減幅は INT8 と同程度。INT4 は品質への影響が評価されていない |
| K. コーデックを CPU に退避する | VRAM をさらに減らせる | デコードが大幅に遅くなる。C1〜C4 のどれも予算を満たせないときの最終手段とする |
| L. TTS をバッチ時だけ起動し、その間 LLM を止める（時分割） | VRAM 予算の制約が消える | 運用が複雑になり、オンデマンドでの再生成ができない。C1〜C4 のどれも満たせないときに再検討する |
| M. `alkana` で英単語をカタカナ化する | 旧実装と同じ読みが得られる | GPL-2.0 で許可リスト外 |

## Consequences

### Pros

- 日本語の読み上げ品質が上がる見込みがある（G4 で検証する）。
- OpenAI 互換の境界と `tts-speaker` の前段があるので、バックエンドを差し替えやすい。
- 参照音声をモデル自身の生成音声にするので、実在人物の声の調達や同意の管理が要らない。倫理条項に触れるリスクも避けられる。
- opt-in の profile に置くので、実測で予算と品質が確かめられるまで、本番の LLM と他の機能に影響しない。profile 付きのサービスは [[000979]] の OSU 予算の対象外である。

### Cons / Tradeoffs

- **VRAM の余裕がない。** LLM 側の使用量が増えると TTS が OOM になりうるし、逆に TTS の確保が LLM のロードを妨げうる。G7 で確かめる。
- **量子化による品質劣化は評価されていない。** C3・C4 を採るなら G4 で確かめる。
- **英語混じりの読みが弱くなる可能性がある。** 以前の辞書によるカタカナ化をやめ、英単語をそのまま渡すため。G4 で評価し、読み辞書の ADR で補う。
- **直列処理になる。** 同時合成数が 1 なので待ち行列ができる。`tts-speaker` 側で待ち時間の上限を持つ。
- **運用の手作業が増える。** 起動前に、運用者が次の作業をする。
  - secret（`irodori_api_key`、`pki-agent-tts-speaker-jwk`）を作る
  - provisioner を bootstrap する
  - 重みを取得し、C4 を量子化する
  - 参照音声を登録する

  bind 元のディレクトリが無ければ、compose が起動を拒否する。
- **ローカルビルドに時間がかかる。** 約 9GB の CUDA イメージを稼働機でビルドする。
- **上流への依存がある。** 個人プロジェクトで更新が速い（v4.1 が 8 月、MF が 9 月）。バージョン固定とゲートウェイで追随コストを抑える。
- **透かしを付けない。** 生成音声であることを示す技術的な印が付かない。重みと生成物をローカルに閉じる運用で補う。
- **常駐化には OSU 予算の手続きが要る。** 将来 profile を外して常駐させるときは、[[000979]] に従って offset か期限付きの例外を用意する。

### 計測経過（2026-10-01）

稼働機で LLM が常駐した状態のまま、各構成・各条件を 30〜50 件ずつ連続で合成した。速度は `speed` を 1.0x / 1.5x / 2.0x で変えた。値は予算 B に対する割合で記す。

- **G1：** C1〜C4 とも CUDA で起動し、healthcheck が通った。ロードは 15 秒前後で終わる。
- **G8：** MF（C2）と、ローカルで量子化した MF（C4）は、既定の 4 ステップで動いた。
- **ピークは音声の長さで決まる。** MF（CFG の分岐なし）と RF とでピークがほぼ同じで、`speed` を上げて尺が縮むほど下がる。尺に比例する処理（コーデックのデコードと推定）が支配的である。
- **100 文字チャンクは不合格だった。** 1.0x で約 20 秒の音声になり、C1〜C4 のすべてでゲート値が B の 90% を超えた。2.0x にすると C3・C4 だけが合格した。
- **60 文字チャンクと `expandable_segments` を両方使うと合格した。** C3・C4 とも 1.0x で B の約 77% に収まった。どちらか一方だけでは、1.0x で上限付近か超過だった。
- **C1・C2 は未計測である。** この 2 つの対策を入れた状態では、まだ測っていない。
- **G3：** RTF p95 は全構成で 1.0 を大きく下回った。C3 は約 0.23、C4 は約 0.08 で、どちらも 60 文字チャンクと `expandable_segments` を使ったときの値である。MF（C2・C4）は RF の 3〜5 倍速い。
- **起動時に一時的なピークがある。** ロード中は、F32 の重みを bf16 に変換する分だけ一時的に確保量が増え、合成を始める前の予約量は B を上回った。最初の合成でキャッシュが解放されると下がる。G7 の共存試験で、LLM 側への影響を確かめる。
- **G4（構成）：** 試聴で C3 が最も自然と判断し、C3 を採用候補とした。compose の既定構成も C3 にした。
- **声：** VoiceDesign で「20 代の女性アナウンサー」調のキャプションを 2 種類用意し、それぞれ 6 seed で候補を作った。試聴で 1 つを選び、`alt-narrator` として登録した。選定手順の正式な取り決めは別 ADR で行う。
- **G5：** 約 400 文字の要約文を 60 文字以下の 10 チャンクに分けて合成し、つないだ（1.0x で約 77 秒、RTF 約 0.25）。試聴の判定は「最良ではないが妥協できる水準で、Kokoro より確実に良い」だった。G4 の Kokoro との比較も、この試聴で代える。
- **G7（共存）：** TTS を起動・停止しても、その前後で LLM の生成速度は変わらなかった（約 110〜137 tokens/s、エラーなし）。TTS が常駐した状態での LLM の再ロードも成功した。TTS が連続合成している間は、GPU の演算を分け合うため、LLM の生成速度が約 4〜5 割下がった（約 120 → 57〜78 tokens/s）。このとき TTS 側は RTF p95 約 0.25、ゲート値は B の約 69%（1.25x）で、どちらにも OOM は起きなかった。許容範囲は「TTS の合成はバッチ生成時、または要約が終わった後に行い、LLM の要約処理のピークと重ねない運用なら、合成中の低下は許容する」と定めた。ロード中の一時ピークと LLM の推論が重なる瞬間は、今回の計測では捉えていない。
- **通し確認（G6 の補強）：** `tts-speaker` は in-process enrollment で証明書を取得し、strict モードで起動した。平文のリクエストは 401 になった。mTLS 経由では、約 400 文字の要約を 10 チャンクに分けて既定の 1.25x で合成し、200（`audio/wav`、約 62 秒）を返した。
- **速度：** 試聴では 1.25x が最も自然だった。2.0x では文字の読み飛ばしが起きた。`tts-speaker` の既定速度を 1.25x にし、1.5x を超える指定は受け付けないことにした（1.75x は試聴で確認していない）。

## 移行計画（概要）

1. `compose/tts.yaml`、`irodori-tts`、計測ハーネス、`tts-speaker` を追加する（本 ADR と同じ変更）。
2. 運用者が secret と provisioner を用意し、重みを取得して C4 を量子化する（`fetch_checkpoints.sh`、`quantize_mf_int8.sh`）。
3. VoiceDesign で参照音声の候補を作り（`design_voices.py`）、固定する参照を選んで潜在表現を登録する（`register_voice.sh`。選定手順は別 ADR）。
4. C1〜C4 を稼働機で比べて G1〜G3 を測り、構成を絞る。
5. 評価セットを作って G4〜G8 を行い、結果と採用した構成を本 ADR に追記する。
6. BFF / FE への接続を別 PR で行う（Pact CDC を RED で先に入れる）。最初の用途は、モバイルなどの Visual Preview でリアルタイム要約を出したあと、その要約を再生することとする。LLM の要約が終わってから TTS を呼ぶ順序なので、G7 の運用条件（LLM の処理と重ねない）に沿う。再生開始までの待ち時間を短くするため、`tts-speaker` はチャンクごとに音声を返すストリーミング応答を追加する（現状は全チャンクの合成を終えてから返すため、約 400 文字で 18 秒ほどかかる）。常駐化するときは OSU 予算の手続きを取る。
7. 本 ADR を Accepted にする。

## Deploy-model 整合性セルフチェック

- [x] 新設 compose service が `depends_on` で他 service を gate するか？
  - YES：`tts-speaker` → `irodori-tts`（`service_healthy`）。両方とも同じ `tts` profile にあり、運用者が `--profile tts up` で一緒に起動する。rolling deploy の対象外なので、依存先が起動していないのに片方だけ起動される経路はない。
- [x] 新設 compose service に `restart: "no"` の one-shot init container を含むか？
  - NO：証明書ボリュームの chown は、既存の PKI 親サービスと同じ `pre_start` フックで行う。
- [x] 新設名前付き volume を populate する責務はどこにあるか？
  - `tts_speaker_certs` は in-process enrollment が起動時に書く。
  - 重みと参照音声は bind（`create_host_path: false`）で、運用者が `fetch_checkpoints.sh` と参照音声の登録手順で事前に配置する。無ければ compose が起動を拒否する。
- [x] rolling 互換：profile による opt-in のため、既定のデプロイでは起動しない。
