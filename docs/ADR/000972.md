# ADR-000972: 証拠の連鎖を記事原文で終端させ、凍結判別モデルによる含意検証の関所（grounding gate）を経た why だけを Trail branch に許可する

## Status

Superseded by [[000976]]

**Web / code 調査後の判定（2026-08-11）: 条件付き保留。** 原文 grounding と emit 前の
precision gate は Trail 正準と整合するが、MiniCheck の性能主張は英語 LLM-AggreFact 上の条件付き
結果で、日本語性能は著者自身が未評価としている。さらに D4 は現行の
`confidence = corroborated`（共有タグ数）を異なる意味へ破壊的に変更しうる。本 ADR の Decision は
実装根拠にせず、[[000976]] を正とする。CC BY-NC 4.0 の Bespoke-MiniCheck-7B は候補外。

## Date

2026-08-11

## Affected Services

- claim-verifier (Python, 新設) — 含意判定の Connect-RPC サービス
- knowledge-sovereign (Go) — planner の why 生成置換と関所の呼び出し、confidence 算出
- news-creator (Python) — why 生成の LLM ランタイム提供
- alt-data-hub (Go) — 既存原文読み出し RPC の sovereign 向け mTLS 配線
- compose / pki — verifier と sovereign→data-hub の配線、resource policy
- evaluation — 日本語評価セットとモデル・threshold・chunk 規則の版管理
- alt-frontend-sv — 変更なし（既存描画が生成品質向上を反映）

## Context

### 1. 現行の why はメカニズムの開示であり、意味の提示ではない

`knowledge-sovereign/app/usecase/trail_planner/planner.go` の why はテンプレート生成である:

```go
Why: fmt.Sprintf("Because %s %q — joins %s",
    anchor.whyPhrase, anchor.title, strings.Join(c.SharedTags, ", ")),
```

evidence_refs の中身は共有タグと対象記事自身であり、「タグが重なったから出した。根拠はそのタグ」という同語反復になっている。四つ組（relation_kind / why / evidence_refs / confidence）の必須化は "decorated feed" の再発防止として正しいが、構文レベルの scrutability を満たした結果、意味レベルの空洞が露呈している。フロントエンド（`BranchCard.svelte`）は why / evidence / confidence をすべて描画しているため、問題は表示ではなく生成側にある。

### 2. 要約は証拠になれない — 研究的裏付け

要約を根拠として引用・検証する案は棄却する。抽象型要約のハルシネーションは大規模人手評価で
実証されており、Maynez らは評価した全モデルの生成要約にかなりの量のハルシネーションを確認し、
intrinsic（原文と矛盾）/ extrinsic（原文から検証不能）の分類を与えた
（https://arxiv.org/abs/2005.00661 ）。Pagnoni らの FRANK では、注釈対象の XSum 要約の
92% に少なくとも 1 つの事実誤りが含まれた
（正しい一次資料は https://arxiv.org/abs/2104.13346 。従来記載の `2204.13761` は別論文）。
この 92% は XSum 条件の値であり、全要約一般の誤り率ではない。要約は LLM の生成物であり、
要約内スパンの実在検証が証明するのは「別の LLM 出力との一貫性」であって事実との一致ではない。

Alt には原文が存在する。alt-db の `articles` テーブル（migrations-atlas `20240101000700_create_articles_table.sql`）は `content TEXT NOT NULL` を持ち、pre-processor が取得・洗浄した記事本文を保持している。証拠の連鎖はここで終端できる。

### 3. 検証器は「凍結判別モデル」という決定論側の道具として存在する

MiniCheck（EMNLP 2024, https://aclanthology.org/2024.emnlp-main.499/ ）は、LLM 出力の文が
grounding 文書に支持されるかを判定する小型モデル群である。MiniCheck-FT5（770M）の
「GPT-4 accuracy」「約 400 分の 1」「既存特化器比 4〜10 point」は、英語
LLM-AggreFact 上の balanced accuracy と API cost 換算という条件付き結果であり、日本語記事へ
外挿できない。公式 README は multi-sentence claim の文分割を推奨し、長文は chunk 化して
max-support 集約するため、部分一致・複数 hop・引用・時間矛盾への偽陽性を別途評価する必要がある。

RoBERTa / DeBERTa / Flan-T5 系の許容ライセンス候補と Bespoke-MiniCheck-7B を同列に扱わない。
後者の公式モデルカードは CC BY-NC 4.0 で、Alt の MIT / Apache-2.0 only 規則により候補外である。

凍結された非サンプリング判別モデルは生成 LLM より挙動を固定しやすいが、bit-exact な決定論的関数
ではない。判定は確率値と threshold に依存し、model digest・runtime・GPU kernel・浮動小数点・
chunk 境界で結果が変わりうる。「決定論側」は、version と threshold を固定し再実行一致率を監視する
判別器までを含む、という限定付きの意味で用いる。

### 4. 日本語性能は未検証である

MiniCheck は英語データのみで学習され、著者自身が非英語性能を未評価としている。日本語記事
コーパスに対する自前評価は導入後の確認ではなく、モデル選定そのものの前提である。多言語 NLI
ベースラインとして mDeBERTa-v3 系
（https://huggingface.co/MoritzLaurer/mDeBERTa-v3-base-xnli-multilingual-nli-2mil7 ）、
日本語 NLI の比較対象として JNLI / 日本語 DeBERTa 系を使えるが、どちらも文書 grounding
fact-checker としての合格を意味しない。日本語 factual consistency 資源と Alt の実記事 why を
分けて評価し、precision@emit / false-emit rate / supported recall / adversarial category ごとの
閾値を事前固定する。評価の営みには recap-evaluator という既存の前例がある。

### 5. ローカル制約

Alt はゼロクラウド（実行時に外部 API 依存なし）を原則とする。検証・生成ともに単一ホスト上で完結しなければならない。LLM ランタイムは news-creator が既に Ollama + gemma 系 Modelfile（8k〜60k コンテキスト）を保持している。

### 6. 原文 RPC は既存だが sovereign からの配線がない

`alt.datahub.v1` には `GetArticleContent` / `GetArticleContentByID` と data-hub handler が既に存在する。
不足しているのは新 RPC ではなく、knowledge-sovereign の mTLS client、compose / pki 設定、
`DATAHUB_ALLOWED_PEERS` への sovereign 追加、CDC RED、未配線時の fail-fast である。現行 allowlist
に `knowledge-sovereign` は含まれない。claim-verifier を新サービスにする場合も、health / metrics /
model image / GPU・CPU budget / peer policy を同じ配線面として扱う必要がある。

## Decision

**証拠の連鎖を記事原文（articles.content）で終端させることを原則とし、LLM が執筆する why の全事実文が凍結判別モデルの含意検証を通過した branch のみを emit することを採用する。confidence は検証結果から決定論的に算出し、生成 LLM の自己申告を禁止する。**

### D1. 真実の階層

- **原文**（articles.content）: 証拠の終端。唯一の grounding 文書。
- **要約・タグ**: 導出キャッシュ。LLM 段の**選抜の文脈**（どの候補を読むか）には使用してよいが、why 内の事実主張の**根拠**にはなれない。
- **LLM 出力**: 検証を通過するまで「提案」であり、通過しなければ存在しなかったものとして扱う（emit しない）。

### D2. パイプラインは三段構成

1. **候補生成（決定論）**: 既存 planner の候補導出（タグ共起等）を維持・拡張する。
2. **解釈（生成 LLM）**: news-creator の Ollama ランタイムに、候補集合＋対象記事の原文抜粋＋直近の spine 文脈を渡し、少数を選抜して why を意味レベルで執筆させる。生成対象は「この記事を読むことでユーザーの何が進むか」であり、発見メカニズムの再記述を禁止するプロンプト規約を置く。
3. **関所（決定論）**: why を文分割し、各事実文について evidence_refs が指す記事の原文を grounding 文書として claim-verifier に判定させる。1 文でも unsupported があれば branch 全体を emit しない。既存の構文ゲート（四つ組の非空検査）はこの意味ゲートの前段として温存する。

### D3. claim-verifier を新設サービスとして切る

Connect-RPC で `VerifyClaims(claims[], article_refs[]) → verdicts[]` を提供する Python サービスとする。モデルは MiniCheck 系を第一候補とし、**採否は D5 の日本語評価の通過を条件とする**。モデル重みはイメージビルド時に焼き込み、実行時のネットワーク取得を行わない（ゼロクラウド維持、rolling deploy 互換）。

### D4. confidence の決定論的算出

- `corroborated`: 相異なるソースドメインの記事 2 本以上が、それぞれ D2-3 の検証を通過して主張を支持する。
- `plausible`: 検証を通過した支持記事が 1 本。
- 事実主張を含む why が検証を通過しない場合、`speculative` として emit するのではなく **emit しない**（沈黙の権利）。`speculative` は事実主張を含まない純粋な問いかけ型 branch（inquiry）にのみ残す。

生成 LLM に confidence を出力させるインターフェースを設けない。プロンプトにも含めない。

### D5. 日本語評価ゲート（導入の前提条件）

導入前に、自コーパスの記事から LLM-AggreFact 形式（文書・主張・支持ラベル）の日本語評価セットを作成する。合格条件は次の 2 つを事前固定する: (1) 多言語 NLI ベースライン（mDeBERTa-v3 系）を balanced accuracy で上回ること、(2) 検証なし（全通過）のアブレーションに対して、人手確認での偽 emit（幻覚された示唆の通過）を明確に減らすこと。どちらかを満たさない場合、第一候補を mDeBERTa 系に差し替えて再評価する。評価セットと結果は evaluation/ 配下にコミットする。

### D6. 出荷順序: in-app が先

関所を通過した why はまず **in-app（BranchCard）** に出荷する。フロントエンドは変更不要であり、生成品質の向上がそのまま画面に反映される。通知（ロック画面）への露出は [[000973]] が別途決定する。

### 検討した代替案と却下理由

**(a) 保存済み要約からの抽出的引用の実在検証 — 却下。**
Context §2 のとおり、要約は LLM 生成物でありハルシネーションを含む前提で扱うべきである（Maynez et al.、Pagnoni et al.）。要約内スパンの実在確認は事実性の証明にならない。

**(b) 生成 LLM 自身による自己検証（self-critique） — 却下。**
検証者と被検証者が同一の生成系では、confidence 自己申告の禁止（D4）と同じ較正問題を検証段に持ち込むことになる。検証は凍結判別モデルに限定する。

**(c) クラウドの検証 API 利用 — 却下。**
ゼロクラウド原則（Context §5）に反する。

**(d) 原文からの逐語引用の強制（extractive constraint） — 却下。**
引用スパンの実在は主張の正しさを保証せず（文脈切り出しの歪み）、生成の表現自由度を過剰に殺す。含意検証は逐語一致を要求せずに事実性を検査でき、MiniCheck が主張の原子分解なしで機能することが示されている（Context §3）。

**(e) verifier を knowledge-sovereign に同居させる — 却下。**
sovereign は Go であり、Transformers 系モデルの実行は Python ランタイムを要する。責務単位のサービス分割という本リポジトリの構成原則にも、GPU/CPU 資源の独立スケジューリングにも、分離が適合する。

## Consequences

### Pros

- why が「どう見つけたか」から「読むことで何が進むか」に変わり、Trail の scrutability が構文から意味に引き上がる。UI 変更ゼロで着弾する。
- 幻覚された示唆は二重の関所（文単位の含意検証 × confidence の独立ソース勘定）を抜けない限り出荷されない。
- 「決定論側 = 記号コード + 凍結判別モデル」という分業境界の定義が明文化され、以後の LLM 協調機能の判断基準になる。
- 検証は事後付加ではなくパイプラインの構成要素であり、[[000973]] の Beacon はこの関所の上にしか建たない構造になる。

### Cons / Tradeoffs

- 検証器自体が誤り率を持つモデルであり、これはリスクの削減であって消去ではない。最終防衛線は dismiss_reason / dwell の人間信号に残る。
- 現行 `corroborated` は共有タグ数のヒューリスティックであり、D4 の「異なる source domain 2 本」と同じ値ではない。移行を定義せず enum 名だけ再利用すると既存 branch の意味が破壊される。
- 異なる domain でも転載・syndication・同系列メディアなら独立証拠ではない。source independence の判定と、引用虚偽・時間矛盾・prompt injection・multi-hop を含む adversarial set が必要になる。
- 日本語評価（D5）が不合格の場合、導入が遅延する。フォールバックの mDeBERTa 系は MiniCheck より判定性能が低い可能性がある（英語ベンチマーク上では特化モデルが NLI 汎用モデルを上回る）。
- 単一ホストの GPU 時間を LLM 生成と検証で分け合う。夜間バッチ前提であり、リアルタイム性は設計上放棄する。
- 新設サービス 1 つ分の運用面積（イメージビルド、ヘルスチェック、メトリクス）が増える。

## Deploy-model 整合性セルフチェック

- 新設 compose service: **あり（claim-verifier）**

  - one-shot init container → なし。
  - モデル重みの populate 責務 → **イメージビルド時に焼き込む**（named volume を使わない）。実行時ネットワーク取得なし。
- **rolling 互換** と明記して pass。
