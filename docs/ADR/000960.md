# ADR-000960: alt-db に残る孤児テーブルとロールを DROP し宣言スキーマと実 DB を一致させる

## Status

Accepted（決定として確定。**マイグレーションもコード削除もまだ書かれていない**。本 ADR 単体では一切の実装を含まない）

## Date

2026-08-08

## Affected Services

- migrations-atlas（drop マイグレーション + `schema.hcl` 整合）
- db（`db/init/01-create-users.sh`、`compose/db.yaml`）
- pre-processor (Go)（死にコード削除）
- scripts（孤児 SQL 削除）
- compose（`compose.staging.yaml`）
- docs（`docs/services/`、`docs/wiki/decisions/`）
- alt-data-hub (Go)（確認のみ、変更なし）

## Context

### 1. 立てた仮説は否定された — Shared Database アンチパターンは既に解消済みだった

本調査は「alt-db に Shared Database アンチパターンが残っているのではないか」という疑いから始まった。alt-db には pre-processor 由来のジョブキューと acolyte 由来のレポート系テーブルが存在し、マイグレーション履歴には複数サービス向けの `GRANT` が並んでいる。構造だけを見れば、複数サービスが同じ DB を共有している形に見える。

**この仮説は稼働中の DB を直接見た時点で否定された。** [[000241]] → [[000246]] → [[000954]] の 3 段で、alt-db への直結はすでに 1 プロセスに閉じている。残っていたのはアンチパターンではなく、**移行が完了したあと誰も消さなかった死んだスキーマ**である。

現在 alt-db に接続しているのは 3 つだけである。

| 接続元 | 定義位置 | 役割 |
|---|---|---|
| `alt-data-hub` | `compose/core.yaml:519` | [[000954]] D3 で唯一のオーナーに指定されたプロセス |
| `migrate` | `compose/core.yaml:624-632` | Atlas マイグレーション適用の one-shot |
| `pgbouncer` | `compose/pgbouncer.yaml:19` | 接続プール |

[[000954]] D3 は「**alt-data-hub が alt-db を独占する。alt-backend / alt-harvester は読み書きとも Connect-RPC 経由で依存する。**」と定めており、Wave 3 は完了している。この独占はレビュー依存ではなく、`alt-backend/app/di/import_boundary_test.go` のリンカレベルのアサーション（`cmd/backend` / `cmd/harvester` は `alt/shared/driver/alt_db` / `pgx/v5` / `pgxpool` を import できず、`cmd/datahub` は import しなければならない）で機械的に固定されている。

pre-processor 側も同様である。alt-db のデータには mTLS Connect-RPC 経由でしか到達せず（`pre-processor/app/driver/backend_api/client.go:18-23`）、`pre-processor/app/bootstrap/wire.go:100-103` は `BACKEND_API_URL` 未設定時に "BACKEND_API_URL is required; legacy direct-DB mode has been removed" で fail-fast する。acolyte-orchestrator は acolyte-db にしか接続しない（`compose/acolyte.yaml:88-89`）。

### 2. 証拠は `pg_stat_user_tables` の書き込みカウンタであって、`GRANT` の履歴ではない

この誤読は繰り返す価値があるので明記する。**マイグレーション中の `GRANT` 文を grep して得られるのは移行の「履歴」であって、現在の状態ではない。** 過去に権限を付与した事実は、今その主体が接続していることを何ひとつ意味しない。実際 `migrations-atlas/migrations/20260317000001_drop_legacy_service_users.sql` は `tag_generator` / `search_indexer_user` / `pre_processor_user` を既に DROP 済みであり、`GRANT` の grep だけを根拠にすると存在しないロールを現役と読み違える。

そこで 2026-08-08 に、稼働中の `db` コンテナ（database `alt`）へ直接クエリして現在の状態を取った。

**ロール**: `alt_appuser` / `alt_db_user` / `pre_processor_sidecar_user` の 3 つが存在する。テーブル権限を持つのは `alt_appuser`（NOLOGIN の別名ロール）のみ。`pre_processor_sidecar_user` はテーブル権限を**ゼロ**しか持たず、クライアントも存在しない。

**`pg_stat_user_tables` の累積カウンタ**:

| テーブル | rows | reads (seq+idx) | ins | upd | del |
|---|---:|---:|---:|---:|---:|
| `summarize_job_queue` | 235 | 3 | 0 | 0 | 0 |
| `report_jobs` | 0 | 1 | 0 | 0 | 0 |
| `reports` | 0 | 1 | 0 | 0 | 0 |
| `report_runs` | 0 | 1 | 0 | 0 | 0 |
| `report_versions` | 0 | 0 | 0 | 0 | 0 |
| `report_sections` | 0 | 0 | 0 | 0 | 0 |
| `report_section_versions` | 0 | 0 | 0 | 0 | 0 |
| `report_change_items` | 0 | 0 | 0 | 0 | 0 |
| （対照）`outbox_events` | 317 | 375,689 | 1,229 | 17,625 | 34,494 |
| （対照）`articles` | — | 5,227,125 | 2,608 | 260,592 | 105 |

候補 8 テーブルはすべて**書き込み実績ゼロ**である。わずかな read（1〜3 回の seq scan）は調査時のアドホックな参照と整合し、クライアントの存在を意味しない。そして下 2 行の対照は、このカウンタが「リセット直後でゼロに見えているだけ」ではないことを示す — 同一の統計収集期間に `articles` は 522 万回読まれている。**ゼロは、集計されていないことではなく、書かれていないことを意味する。**

### 3. どうやってそこに残ったか

#### 3.1 `summarize_job_queue` — [[000246]] Phase 5 が未完了のまま [[000397]] に取りこぼされた

`summarize_job_queue` は `migrations-atlas/migrations/20251213000000_create_summarize_job_queue.sql` で alt-db に作られ、`migrations-atlas/migrations/20260304000000_add_dead_letter_status_to_summarize_job_queue.sql` で ALTER された。[[000246]]（accepted, 2026-02-15）がこれを pre-processor-db へ移し、現住所は `pre-processor-migration-atlas/migrations/20260215000001_initial.sql` である。

[[000246]] の Cons #3 は当時すでにこう書いている。

> **Phase 5 未完了**: alt-db にテーブルが残存。DROP TABLE マイグレーションは別途実施が必要

その Phase 5 を閉じるはずだったのが [[000397]] である。しかし実際に書かれた `migrations-atlas/migrations/20260317000000_drop_pre_processor_legacy_tables.sql` が DROP するのは `inoreader_articles` / `inoreader_subscriptions` / `sync_state` / `api_usage_tracking` の**ちょうど 4 つ**で、5 つ目の `summarize_job_queue` を落としている。マイグレーション冒頭のコメントは "No service queries these tables from alt-db anymore" と宣言しており、これは名指しされた 4 つについては真、5 つ目については**黙って偽**である。以来 1 年半近く、235 行が誰にも読まれず誰にも書かれずに残った。

#### 3.2 acolyte 7 テーブル — 専用 DB を決めた後も alt-db 側のコピーが消されなかった

acolyte の 7 テーブルは `migrations-atlas/migrations/20260409000000_create_acolyte_tables.sql` で alt-db に作られた。このファイルは `acolyte-migration-atlas/migrations/20260409000000_create_acolyte_tables.sql` と**バイト単位で同一**である。[[000653]]（accepted, 2026-04-09）は同日、acolyte が専用の `acolyte-db` を持つことを既に決めていた。にもかかわらず alt-db 側のコピーに対する drop マイグレーションは一度も書かれなかった。

しかも alt-db 側のコピーは**古い分岐した部分集合**である。`report_briefs`（`acolyte-migration-atlas/migrations/20260410000000_create_report_briefs.sql`）を持たず、`ON DELETE CASCADE` の FK（`acolyte-migration-atlas/migrations/20260413000000_cascade_delete_reports.sql`）も持たない。つまり「同名の 2 つのテーブル群のうち、片方は 4 か月前の形で凍結している」状態である。

### 4. 孤児は受動的ではない — 実際に人を騙した

2026-07-18、コミット `b3535715e` が `migrations-atlas/migrations/20260718000000_add_report_jobs_run_id_index.sql` を追加し、`idx_report_jobs_run_id` を作成した。これは `docs/review/20260706largerepocodereview.md:1599` が指摘した「FK にインデックスが無い」という所見への対応として正しい修正である。**ただし修正されたのは死んだ alt-db 側のコピーであり、実際にクエリが飛ぶ acolyte-db 側ではなかった。** レビュー所見・修正・マージのどの段階でも、そのテーブルが alt-db に存在してはいけないことに誰も気付かなかった。

孤児テーブルのコストは「ディスクを少し食う」ではない。**機械的なレビュー修正掃きが、間違ったデータベースに着地する。** これが本 ADR を今書く直接の動機である。

### 5. 宣言スキーマがすでに信用できない

`migrations-atlas/migrations/schema.hcl` が宣言しているテーブルは 10 個で、実 DB（`pg_tables`, schema `public`）には 27 個ある。リプレイ状態と宣言スキーマは既に乖離しており、`schema.hcl` を読んで alt-db の姿を把握することはできない。まったく同じ乖離を潰した前例が `migrations-atlas/migrations/20260611000002_drop_misplaced_trail_tables.sql` にあり、本 ADR はその手順を踏襲する。

### 6. 同じ由来の隣接した死体

- **ロール `pre_processor_sidecar_user`** — `db/init/01-create-users.sh:147-149` と `compose/db.yaml:27-28,36` がいまも作り続けているが、クライアントは存在しない。sidecar 自身は pre-processor-db を向いている（`pre-processor-sidecar/app/config/config.go:210,213`）。テーブル権限はゼロ。
- **`pre-processor/app/repository/stale_pending_cleanup.go:8-34`** — 死んでいるうえに**壊れている**。`summarize_job_queue` を `article_summaries` と JOIN するが、`article_summaries` は pre-processor-db に存在しない。2 つのメソッドは `SummarizeJobRepository` インタフェース（`pre-processor/app/repository/interfaces.go:50-80`）に載っておらず、呼び出し元もゼロ。そして `stale_pending_cleanup_test.go:12-22` はクエリを実行せず**クエリ文字列にアサートしている**ため、実行すれば必ずエラーになる SQL の上でテストが緑のままになっている。
- **`scripts/pre_processor_cleanup_stale_summarize_jobs.sql`** — 上と同型の SQL で、参照元ゼロ。
- **staging の残骸 env** — `compose/compose.staging.yaml:970-974` と `:1119-1123` が `alt-backend` / `alt-harvester` に `DB_*` を渡しているが、[[000954]] Wave 3 以降この 2 バイナリは DB ドライバをリンクしておらず**読むことができない**。本番 compose と矛盾しており、読む者に「まだ直結している」と誤解させる。

### 7. 旧状態を主張し続けているドキュメント

- `docs/services/pre-processor.md:296` — 「API モードでも summarize_job_queue と inoreader_articles テーブルへの DB 直接アクセスは維持」
- `docs/services/alt-db.md:302` — alt-db の所有テーブルとして `summarize_job_queue` を列挙している
- `docs/wiki/decisions/architecture.md` rule 5 — alt-db のオーナーを `alt-backend:9101` と書いており、[[000954]] 以前の記述のまま
- `docs/plan/knowledge-sovereign-full-separation.md` — `migrations-atlas/migrations/20260323100000_drop_sovereign_tables.sql` と [[000544]] から参照されているが、**git にコミットされたことがない dangling reference**

これらの訂正は本決定に含めるが、訂正そのものは ADR に値する判断ではない（実態に合わせるだけである）。

### 8. 前例からの警告 — drop マイグレーションこそが規律の抜ける場所

このリポジトリの実証された失敗モードは、**drop マイグレーションで検証が省かれる**ことである。`migrations-atlas/migrations/20260323100000_drop_sovereign_tables.sql` は 14 テーブルを無条件に落とした。`docs/review/20260706largerepocodereview.md:1598` の指摘:

> append-only の knowledge_events を含む 14 テーブルを、移行完了検証（例: sovereign 側 max(event_seq) 一致確認の DO ブロック）なしで無条件 DROP。手順書依存の不可逆操作。

本 ADR の Decision は、この指摘を自分自身に適用する。`DROP TABLE IF EXISTS` を素で並べることは、たとえ今日の証拠がどれだけ強くても採らない。

## Decision

**alt-db に残る 8 個の孤児テーブルとその付随オブジェクト、および `pre_processor_sidecar_user` ロールを、書き込み実績ゼロを DB 内で検証する guard 付きの Atlas マイグレーションで DROP し、あわせて `schema.hcl` / 死にコード / staging env / ドキュメントを実態に一致させることを採用する。**

### D1. DROP する対象

| 由来 | テーブル | 現住所 |
|---|---|---|
| [[000246]] Phase 5 の取りこぼし | `summarize_job_queue` | pre-processor-db |
| [[000653]] の alt-db 側コピー | `report_jobs` / `reports` / `report_runs` / `report_versions` / `report_sections` / `report_section_versions` / `report_change_items` | acolyte-db |

付随オブジェクトは `DROP TABLE` で同時に消えるが、消えるものを明示する。

- 所有シーケンス `summarize_job_queue_id_seq`
- `20251213000000` / `20260304000000` / `20260409000000` が作成したインデックス
- `20260718000000_add_report_jobs_run_id_index.sql` が誤って作った `idx_report_jobs_run_id`

**`CASCADE` は使わない。** acolyte 7 テーブルは FK 依存の逆順（`report_change_items` → `report_section_versions` → `report_sections` → `report_versions` → `report_runs` → `reports` → `report_jobs`）で個別に DROP し、想定外の依存が残っていた場合はエラーで止まるようにする。`CASCADE` は「知らない依存を黙って道連れにする」ことであり、本 ADR の趣旨と正反対である。

### D2. guard `DO` ブロックを必須とする

無条件 DROP は採らない。マイグレーションは DROP に先立ち、次を DB 内で検証し、1 つでも破れたら `RAISE EXCEPTION` でトランザクションごと中断する。

```sql
DO $$
DECLARE
  v_tables text[] := ARRAY[
    'summarize_job_queue',
    'report_jobs', 'reports', 'report_runs', 'report_versions',
    'report_sections', 'report_section_versions', 'report_change_items'
  ];
  v_writes bigint;
  v_reset  timestamptz;
BEGIN
  -- (1) 統計が十分な期間を代表していること。リセット直後のゼロは証拠にならない
  SELECT stats_reset INTO v_reset FROM pg_stat_database WHERE datname = current_database();
  IF v_reset IS NULL OR v_reset > wall_clock() - interval '7 days' THEN
    RAISE EXCEPTION 'pg_stat counters too young (reset=%); cannot prove tables are dead', v_reset;
  END IF;

  -- (2) 8 テーブルすべてが書き込み実績ゼロであること
  SELECT coalesce(sum(n_tup_ins + n_tup_upd + n_tup_del), 0) INTO v_writes
    FROM pg_stat_user_tables WHERE relname = ANY(v_tables);
  IF v_writes <> 0 THEN
    RAISE EXCEPTION 'orphan tables still receive writes (%); abort drop', v_writes;
  END IF;

  -- (3) 行数が記録済みの想定（summarize_job_queue=235、他 7 テーブル=0）から増えていないこと
  --     増えていれば「書き込み元がいる」ので、統計より行数が新しい証拠になる
END $$;
```

`wall_clock()` は現在時刻を返す組み込み関数を指す（リテラルを ADR に書かないための表記であり、実装では標準の時刻関数を使う）。

**この guard の限界を正直に書く。** alt-db と pre-processor-db / acolyte-db は別インスタンスであり、単一の `DO` ブロックから移送先の行数を見ることはできない（`postgres_fdw` / `dblink` をこのためだけに導入するのは割に合わない）。したがって「移送先が移送元と同じかそれ以上のデータを持つこと」の確認は **migration 適用前の明示的な pre-condition** として runbook に固定し、その実行結果をリリースの証跡として残す。`DO` ブロックが担保するのは「alt-db 側に生きたクライアントがいないこと」であり、担保していないことは担保しているふりをしない。

### D3. `schema.hcl` を実 DB と一致させる

`migrations-atlas/migrations/schema.hcl` は 10 テーブルしか宣言していないのに実 DB は 27 ある。本 ADR の DROP と同じ PR で、宣言スキーマを実 DB と一致するところまで引き上げる。先行事例は `migrations-atlas/migrations/20260611000002_drop_misplaced_trail_tables.sql` で、同じ手順を踏む。Atlas の宣言スキーマが実態と一致しない限り、以後どの diff も信用できない。

### D4. 死んだうえに壊れているコードを消す

- `pre-processor/app/repository/stale_pending_cleanup.go` を削除する
- `pre-processor/app/repository/stale_pending_cleanup_test.go` を削除する（クエリ文字列アサーションは、実行すれば失敗する SQL を緑に保つ装置であり、移植する価値はない）
- `scripts/pre_processor_cleanup_stale_summarize_jobs.sql` を削除する

これらは「pre-processor-db に存在しないテーブルを JOIN する SQL」であり、修正して残す選択肢はない。stale pending job のクリーンアップが将来必要になったなら、そのときに pre-processor-db の実スキーマに対して書き直す。

### D5. `pre_processor_sidecar_user` ロールとその provisioning を消す

- 上記マイグレーションで `DROP ROLE`（所有オブジェクト・権限がゼロであることを guard で確認したうえで）
- `db/init/01-create-users.sh:147-149` からロール作成を削除
- `compose/db.yaml:27-28,36` から関連する env / secret 参照を削除

### D6. staging env の残骸を消す

`compose/compose.staging.yaml:970-974` と `:1119-1123` の `DB_*` を `alt-backend` / `alt-harvester` から削除し、本番 compose と一致させる。読めない env は設定ではなく誤情報である。

### D7. ドキュメントを実態に合わせる

`docs/services/pre-processor.md:296` / `docs/services/alt-db.md:302` / `docs/wiki/decisions/architecture.md` rule 5 を [[000954]] 以後の実態へ訂正する。`docs/plan/knowledge-sovereign-full-separation.md` については、実在しないファイルを指し続けるより参照側を直す — `20260323100000_drop_sovereign_tables.sql` と [[000544]] の引用を、当該 ADR への wikilink かインラインの経緯記述に置き換える。

### 検討した代替案

| 代替案 | 評価 |
|---|---|
| **(a) 何もせず残す** | **棄却**。「使われていないだけで害はない」は 2026-07-18 に反証された。孤児テーブルは実際に、正しいレビュー所見への修正を間違ったデータベースへ誘導した。放置のコストはゼロではなく、誤った修正の期待値である |
| **(b) 235 行を先にアーカイブする** | **形式的なアーカイブは不要、ただし使い捨ての dump は取る**。この 235 行は 2026-02-15 の移行より前の残滓であり、以後の書き込みはすべて pre-processor-db 側に入っている（live queue はそちら）。さらに中身はジョブキューのエントリ、すなわち完了済みの作業単位であって、再構成不能な業務事実ではない。よって archive テーブルへの退避やリポジトリへの成果物コミットは正当化されない。一方で `pg_dump --data-only -t summarize_job_queue` はコストが実質ゼロなので、マイグレーション適用時に取得しリリース窓の間だけ保持する（恒久保管はしない） |
| **(c) `DROP TABLE IF EXISTS` を無条件で並べる** | **棄却**。`20260323100000_drop_sovereign_tables.sql` がまさにこれをやり、`docs/review/20260706largerepocodereview.md:1598` に「移行完了検証なしの不可逆操作」として記録されている。同じ指摘を受けた直後に同じ形を再生産することはできない。D2 の guard を必須とする |
| **(d) テーブルを残し DataHubService の RPC の背後に置く** | **棄却**。RPC 化は「複数の直結クライアントを 1 オーナーに集約する」ための手段であり、集約すべきクライアントが存在しない。書き込み 0・読み取り 3 のテーブルに対して proto と Pact 契約と handler を書くことは、死んだスキーマを生きたインタフェースに昇格させて維持義務を発生させるだけである。**提供すべき相手がいない** |

## Consequences

### Pros

- **同じテーブルの 2 つのコピーを将来の読者が見なくなる。** `report_jobs` を grep したときに `migrations-atlas` と `acolyte-migration-atlas` の両方が当たり、どちらが本物か判断するコストが消える。`summarize_job_queue` も同様に、居場所が pre-processor-db 一箇所になる。
- **Atlas の宣言スキーマが再び信用できるものになる。** `schema.hcl` が実 DB と一致すれば、以後の diff / lint / drift 検出が意味を持つ。10 対 27 の乖離を抱えたままの宣言スキーマは、機能ではなく飾りである。
- **機械的なレビュー修正掃きが死んだテーブルに着地できなくなる。** 2026-07-18 と同じ事故は、対象が存在しなければ起こらない。これは規律ではなく構造による防止である。
- **[[000246]] が 2026-02-15 に自分で書いた Cons #3 が、ようやく閉じる。** ADR に書かれた未完了事項が 1 件減る。
- **`pre_processor_sidecar_user` が消えることで、alt-db のロール一覧が「実際に使われているもの」だけになる。** 次に権限監査をする者が、権限ゼロのロールの正体を調べる時間を使わずに済む。
- **pre-processor から、実行すれば必ず失敗する SQL と、それを緑に保っていたテストが消える。** テストスイートの緑が、いま少しだけ本当のことを言うようになる。

### Cons / Tradeoffs

- **235 行の削除は不可逆である。** (b) で述べたとおり再構成不能な業務事実ではないと判断したが、判断が誤っていた場合に取り返す手段はリリース窓の間だけ保持する使い捨て dump しかない。恒久的な退避先は作らない。
- **`atlas.sum` の再ハッシュが必要になる（`make migrate-hash`）。** 忘れると migrate コンテナが checksum mismatch で落ち、`service_completed_successfully` を gate している下流が上がらない。
- **`migrations/atlas.hcl` は `destructive.error = true` であり、この DROP は lint に引っかかる。** 明示的な lint 許可（当該マイグレーションに対する destructive 例外）を入れるか、override を実行手順として文書化するかのどちらかが必要で、どちらも「破壊的操作を通す穴」を 1 つ作ることに変わりはない。穴を恒久的に開けっぱなしにしないこと（対象マイグレーション限定にすること）が条件である。
- **`db/init/01-create-users.sh` の編集は新規初期化ボリュームにしか効かない。** 既存ボリュームでは init スクリプトが再実行されないため、`pre_processor_sidecar_user` は D5 の `DROP ROLE` が適用されるまで残る。init スクリプトの修正は「次に作られる DB を汚さない」ためのものであって、今動いている DB を直すものではない。この 2 つを混同すると「消したはずのロールがまだいる」で時間を溶かす。
- **本 ADR は再発防止の仕組みを一切追加しない。** ここで消すのは 2 件の完了済み移行が残した死体であって、「移行完了後に旧スキーマが残り続ける」という**クラス**は塞いでいない。同じことは 3 度目が起こりうる（[[000246]] が 1 度目、[[000653]] が 2 度目である）。この空白は意図的に本 ADR のスコープ外とし、[[000961]] が担う。本 ADR だけを実施して終えると、掃除は済むが再発率は変わらない。
- **実装はまだ存在しない。** マイグレーションファイル・guard `DO` ブロック・コード削除・ドキュメント訂正のいずれもまだ書かれていない。本 ADR は決定の記録であり、完了報告ではない。

## Deploy-model 整合性セルフチェック

- [x] **新設 compose service が `depends_on` で他 service を gate するか？** — **N/A**。本 ADR は compose service を新設しない。既存の `migrate`（`compose/core.yaml:624-632`、`alt-data-hub` が `service_completed_successfully` で gate）に**マイグレーションを 1 本追加するだけ**であり、gate の形は変えない。rolling deploy 下で単独 `up <svc>` したときに `migrate` が起動されない既知の性質も既存どおりで、スキーマ適用はデプロイ tooling 側の責務として既に扱われている。
- [x] **新設 compose service に `restart: "no"` の one-shot init container を含むか？** — **NO**。one-shot コンテナを新設しない。
- [x] **新設名前付き volume を populate する責務はどこにあるか？** — **N/A**。新設 volume はない。`db/init/01-create-users.sh` を編集するが、これは**既存ボリュームでは再実行されない**（Cons に記載）ため、populate 責務の変更ではない。
- [x] **適用順序** — 本 ADR は Atlas マイグレーションを追加するため、**`migrate` → サービス deploy** の順序が必要である。ただし本件に限れば順序に対する感度は低い: 削除対象 8 テーブルにはいかなるバイナリからの参照も存在せず（`import_boundary_test.go` により `cmd/backend` / `cmd/harvester` は alt-db driver を import できず、`cmd/datahub` にも該当テーブルへの参照はない）、`DROP ROLE` の対象ロールにもクライアントがいない。したがって「migrate が先に走らずコードだけ出た」「migrate だけ走ってコードが古い」のどちらの中間状態でも壊れるものがない。
- 結論: **rolling 互換**。
