# ADR-001012: Inoreader 取り込みのサイレント停止検出と ClickHouse ログ上限を現行契約として再確定する

## Status

Accepted

本 ADR は [[000895]] の現行有効な決定を現行契約（binding record）として引き継ぐ。[[000940]] から [[000895]] への `supersedes` 辺はフロントマターの一括修復作業で誤って追加されたものであり、[[000940]] の決定内容を反映していないが、確定済み ADR の append-only 規約によりグラフ上に残置される。

## Date

2026-11-15

## Affected Services

- pre-processor-sidecar (Go) — `repository.RemoteTokenRepository` による 404 / 空トークンの `ErrTokenNotFound` 分類、`service.RemoteTokenService` の `ErrTokenUnavailable` / `IsDegraded()` / `TokenAvailable()` / `Clock` 注入、`service.InoreaderService` の `LastSuccessfulFetch()` / `CircuitBreakerState()`、`handler.HealthHandler` による GET `/admin/health`、`cmd.ingestionHealthAdapter` による統合
- auth-token-manager (Deno) — `/api/token` の HTTP 404（`{"error":"No token data found"}`）セマンティクスが現行のまま維持されており、`pre-processor-sidecar` 側で型付きエラーとして解釈する（`auth-token-manager` 自体への変更なし）
- clickhouse / compose — `compose/db.yaml` の `clickhouse` サービスにおける `logging` 上限（`json-file` `max-size: "10m"` / `max-file: "3"`）および `mem_limit: 4g`

## Context

2026-10-24 のフロントマター・DocDag 意味論の一括修復（commit `7ff28708b`）において、Knowledge Loop を Knowledge Trail へ retire する [[000940]] の `supersedes` リストが本来の 6 件（[[000929]], [[000930]], [[000933]], [[000937]], [[000938]], [[000939]]）から 60 件へ拡大し、54 件の ADR が `accepted` から `superseded` へ反転した。[[000895]] は Inoreader 取り込みのサイレント停止検出および ClickHouse のログ上限を定めた ADR であり Knowledge Loop とは無関係だが、この 54 件に含まれたため `superseded` 扱いとなった。

この結果、[[000895]] は `docdag query --binding` の返却対象から脱落し、実装着手前の pre-edit ADR brief に現れなくなった。一方で CI は `docdag validate --immutable-since` で、確定済み（`accepted` / `superseded`）ADR の書き換えを `immutable_violation` として報告する。vault の規約は、意味を変えない編集を「意図してレビューする例外」として認めているが、通常の PR はこの finding をゼロに保つ。[[000940]] の `supersedes` から `000895` を外す訂正は、[[000895]] の status と本文の Status 節の書き戻しを伴い、訂正の経緯が ADR として残らない。そこで新規 ADR を立てて現行有効な契約を再確定し、[[000895]] を引き継ぐ。

[[000895]] が対処した原インシデント（2026-05-05 からのサイレント停止事案）の背景は次のとおりである。

- ディスク圧迫の副作用で `oauth_token_data` ボリューム上の `oauth2_token.env` が空ファイル化した際、auth-token-manager は `/api/token` で HTTP 404 `{"error":"No token data found"}` を返し続け、pre-processor-sidecar は 16 分ごとの fetch tick でサーキットブレーカーが `OPEN` と `HALF_OPEN` を往復するだけで外部から観測可能な停止信号がなかった。結果として `sync_state.last_sync` が約 3 日間停止したまま検知が遅れた。
- 既存の `pre-processor-sidecar -health-check` CLI は `token_manager_available: true` を返し続け、404 応答は `auth-token-manager returned status: 404` という不透明な文字列エラーとして伝搬するためテスト分岐もアラート判定もできなかった。
- あわせて、ClickHouse の compose 定義に `logging` 設定がなかったため、OOM 再起動ループ（RestartCount=85 を観測）でコンテナログが肥大化しディスクを圧迫する経路が残っていた。

その後、環境変数 `INOREADER_SYNC` による同期ゲートが導入され、`compose/workers.yaml`（および `compose/ai.yaml`、`.env.example`、`.env.template`）では既定値が `INOREADER_SYNC=${INOREADER_SYNC:-disabled}` となっている（この停止設定を単独で定めた ADR は存在しない）。`INOREADER_SYNC=disabled` のあいだ `pre-processor-sidecar` の scheduler は定期 fetch / refresh ループを起動しないが、トークン 404 の型付き分類、degraded 状態管理、`/admin/health` の露出、ClickHouse のログ・メモリ上限というコードおよび compose 上の契約自体は現行コードに維持されている。

## Decision

**[[000895]] で定めた Inoreader 取り込みのサイレント停止検出機構と ClickHouse のディスク流出防止設定を現行契約として再確定する。**

### 現行有効として引き継ぐ契約

1. **auth-token-manager 404 / 空トークンの型付きエラー化**
   - `auth-token-manager/src/handler/oauth_server.ts` の `/api/token` は、トークン不在時に HTTP 404 `{"error":"No token data found"}` を返す（`auth-token-manager` 本体は変更しない）。
   - `pre-processor-sidecar/app/repository/remote_token_repository.go` の `RemoteTokenRepository.GetCurrentToken` は、HTTP 404 および空の `AccessToken` 応答を `repository.ErrTokenNotFound`（`pre-processor-sidecar/app/repository/oauth2_token_repository.go`）に分類する。
   - `pre-processor-sidecar/app/service/remote_token_service.go` の `RemoteTokenService.GetValidToken`（および同メソッドへ委譲する `EnsureValidToken`）は、`errors.Is(err, repository.ErrTokenNotFound)` を sentinel `service.ErrTokenUnavailable` でラップして返す。呼び出し元は `errors.Is(err, service.ErrTokenUnavailable)` によりトークン消失を一意に判定する。

2. **`RemoteTokenService` の degraded 状態判定**
   - `pre-processor-sidecar/app/service/remote_token_service.go` の `RemoteTokenService` は `degradedWindow = 60 * time.Second`、`degradedThreshold = 3` を保持し、60 秒ローリングウィンドウ内に 3 回以上の失敗を記録した場合に `IsDegraded()` が `true`（`TokenAvailable()` が `false`）を返す。
   - 1 回でもトークン取得に成功すると `recordSuccess()` が失敗履歴スライスを破棄してウィンドウをクリアする。
   - 時間依存テストを決定的に実行できるよう `Clock` インターフェース注入（`NewRemoteTokenServiceWithClock`）を維持する。
   - `INOREADER_SYNC=disabled` との整合: 既定値 `disabled` 下では scheduler による定期 fetch / refresh が起動しないため `RemoteTokenService.GetValidToken` は定常的には呼ばれない（`pre-processor-sidecar/app/cmd/main.go` の 30 分定期ログは `tokenRepo.GetCurrentToken` を直接呼ぶ）。本機構は `INOREADER_SYNC=enabled` 時または `RemoteAdminTokenManager.GetValidToken` 経由の呼び出し時に機能する契約として維持する。

3. **`/admin/health` エンドポイントと `InoreaderService` / アダプタの実装契約**
   - `pre-processor-sidecar/app/cmd/main.go` の `:8080` `adminMux` 上に、認証付き `/admin/trigger/*` とは別に unauthenticated な `GET /admin/health`（非 GET は HTTP `405 Method Not Allowed`）を公開する。
   - `pre-processor-sidecar/app/handler/health_handler.go` の `HealthHandler.HandleHealth` は、`degraded` 時も HTTP `200 OK` で JSON スナップショットを返し、ボディ内のフィールドで状態を通知する。返却フィールドは `status`（`"ok"` / `"degraded"`）、`token_available`、`circuit_breaker_state`、`last_successful_fetch_at`（RFC3339 または `""`）、`seconds_since_last_fetch`（未取得時は `-1`）、`ingestion_silent_threshold_seconds`（既定 `1800`）、`ingestion_silent` とする。
   - `last_successful_fetch_at` がゼロ値（起動後未取得）または経過秒数が `1800` 秒以上の場合に `ingestion_silent` が `true` となり、`ingestion_silent || !token_available` の場合に `status` が `"degraded"` となる。
   - `pre-processor-sidecar/app/service/inoreader_service.go` の `InoreaderService` は `FetchStreamContents` 成功時に `fetchMu` 配下で `lastSuccessfulFetch` を更新し、`LastSuccessfulFetch()` と文字列化済みの `CircuitBreakerState() string` を公開して handler を `utils` 型から切り離す。
   - `pre-processor-sidecar/app/cmd/main.go` の `ingestionHealthAdapter` は `TokenProvider` を `*service.RemoteTokenService` へ型アサーションし、該当する場合のみ `TokenAvailable()` を照会する（他の `TokenProvider` 実装にはインタフェース変更を強制せず `true` とみなす）。
   - `INOREADER_SYNC=disabled` との整合: 同期無効時は `FetchStreamContents` が実行されないため `lastSuccessfulFetch` はゼロ値のままとなり、`GET /admin/health` は `last_successful_fetch_at: ""`、`seconds_since_last_fetch: -1`、`ingestion_silent: true`、`status: "degraded"` を返す。これはコードの不具合ではなく未同期状態の実測値であり、`INOREADER_SYNC=enabled` で同期を再開した際に 30 分以内のサイレント停止検出契約としてそのまま機能する。

4. **ClickHouse のディスク流出防止（ログ上限とメモリ上限）**
   - `compose/db.yaml` の `clickhouse` サービスに `logging` ドライバ `json-file` のローテーション上限 `max-size: "10m"` / `max-file: "3"`（最大 30MB）および `mem_limit: 4g` を設定する。OOM 再起動ループ時にもコンテナログがホストディスクを圧迫しない構造を維持する。

### 引き継がない事項

- **「通常時は `/admin/health` が `ok` を返し、異常時のみ 30 分以内に `degraded` へ反転する」という常時同期前提の運用仮定**: `compose/workers.yaml`（および `compose/ai.yaml`、`.env.example`、`.env.template`）で `INOREADER_SYNC=${INOREADER_SYNC:-disabled}` が既定値となり、`pre-processor-sidecar/app/service/scheduler/scheduler.go` の `Scheduler.Start` が ticker を起動せず手動トリガも `ErrSyncDisabled` を返す現状では、既定構成の `/admin/health` は起動直後から常に `ingestion_silent: true` / `status: "degraded"` を返す。無条件に `status == "degraded"` をページング条件とする運用仮定は引き継がない（`INOREADER_SYNC=enabled` 時にのみ有効なアラート条件とする）。
- **Prometheus blackbox / cron curl / 汎用ディスク監視の自動配線済み前提**: [[000895]] の代替案評価や Tradeoffs に言及のあった Prometheus blackbox / cron curl による `/admin/health` ポーリングや汎用ディスク・コンテナログ監視について、現行の `observability/prometheus/prometheus.yml`・`observability/prometheus/rules/`・`observability/alerts/`・`observability/synthetic/probes.yaml` には `pre-processor-sidecar:8080/admin/health` の scrape・probe・alert ルールは配備されていない。未配備の外部監視配線が存在する前提は引き継がない。

### 検討した代替案と却下理由

1. **[[000940]] の `supersedes` を修正し [[000895]] を `accepted` に戻す** — 却下。`docdag validate --immutable-since` が `immutable_violation` を出す。vault の規約は意味を変えない編集を意図してレビューする例外として認めており、この訂正はその例外に当たりうる。それでも例外として通すと、訂正の経緯が ADR として残らず、通常の PR で finding をゼロに保つ運用を一度崩すことになる。訂正そのものを決定として記録できる新規 ADR を選んだ。
2. **現状のまま放置する** — 却下。`/admin/health`、`ErrTokenUnavailable`、`IsDegraded()`、ClickHouse のログ・メモリ上限といった現行有効な契約が `docdag query --binding` から欠落し、変更前ブリーフで参照できなくなる。
3. **[[000877]] と [[000895]] を 1 本の ADR にまとめて再確定する** — 却下。両者は対象ドメイン（CI / マイグレーション不変ルール vs Inoreader 停止検出・ClickHouse ログ上限）も影響サービスも異なるため分離すべきである（[[000877]] は [[001011]] が引き継ぐ）。

## Consequences

### Pros

- [[000895]] の現行有効な契約（`ErrTokenUnavailable`、`RemoteTokenService.IsDegraded()`、`GET /admin/health`、`compose/db.yaml` の ClickHouse ログ・メモリ上限）が再び `docdag query --binding` に復帰し、変更前ブリーフで参照可能になる。
- `INOREADER_SYNC=disabled` 導入後の実態と未配備の監視配線を「引き継がない事項」として明文化したことで、現行の挙動（未同期時の `ingestion_silent: true` / `status: "degraded"`）と運用契約の乖離が解消される。
- `pre-processor-sidecar` 内のテスト（`service/remote_token_service_test.go`、`handler/admin_api_handler_health_test.go`、`repository/remote_token_repository_test.go`、`service/scheduler/scheduler_sync_mode_test.go`）で型付きエラー、60 秒ウィンドウ判定、`/admin/health` 契約、同期無効時ガードが継続検証されている。

### Cons / Tradeoffs

- 誤って追加された `[[000940]] → [[000895]]` の `supersedes` 辺は append-only 規約のためグラフ上に残る。
- `docdag resolve 000895` は `000940` と `001012` の双方を返す。
- 決定本文が [[000895]] と本 ADR の 2 箇所に重複して存在する。
- `/admin/health` は既存の設計どおり unauthenticated のままであり、インターネット非公開ネットワーク前提に依存する。また `1800` 秒閾値によるポーリング検知の遅延上限および ClickHouse `mem_limit: 4g` 下での重いミューテーション制約は [[000895]] からそのまま残る。
