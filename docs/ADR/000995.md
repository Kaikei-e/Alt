# ADR-000995: mTLS接続意図と実効設定・稼働観測を結ぶ設定変更および復旧ゲートを段階導入する

## Status

Proposed（将来設計の提案。本 ADR は未実装の設計案および未検証の所有権整理を含み、実装完了の主張や現行契約の即時置換を行わない）

## Date

2026-11-06

## Affected Services

- pre-processor (Go) — `compose/ai.yaml`（347〜400 行付近）における `news-creator` 向け mTLS クライアント設定（初期検証エッジの caller）
- news-creator (Python) — `compose/ai.yaml`（265〜286 行付近）における inbound mTLS・`MTLS_ALLOWED_PEERS` 設定（初期検証エッジの receiver）
- compose (`compose/ai.yaml`, `compose/compose.yaml`) — 候補環境に対する実効設定レンダリングと環境変数補間の検査対象
- scripts (`scripts/deploy.sh`, `scripts/check-compose-variables.sh`, `scripts/check-env-overrides.py`, `deploy/host-prereqs.yaml`, `deploy/desired-env.lkal`) — 既存デプロイ導線への事前検証・観測・補償復旧ゲートの統合

## Context

本 ADR は [[000743]]（サービス間認証の mTLS 一本化）、[[000826]]（rolling deploy 整合性）、[[000954]]（データプレーン分割と peer 境界）、[[000978]]（subject-scoped in-process PKI enrollment）、[[000979]]（Compose 5.4 以上と host-bind / OSU 監査）を前提とする。

### 1. 現状の証拠（Current Evidence）と既存資産の所有境界

現在、サービス間 mTLS の接続設定とホスト環境変数の制約は以下の既存資産に配置されている。

| 既存ファイル | 現在の役割と所有範囲 | 限界・境界 |
|---|---|---|
| `services.yaml` | 正準のサービス識別子台帳（pacticipant / runtime / compose_files） | サービス間の mTLS 接続エッジ自体は記述しない |
| `compose/ai.yaml` | `news-creator`（265〜286 行）と `pre-processor`（347〜400 行）のコンテナ環境変数・既定値 | `${VAR:-default}` がホスト `.env` や呼び出し元環境変数で上書きされうる |
| `deploy/host-prereqs.yaml` | `host_paths`・`retired_env`・`dead_env_values`・`env_allowlists` の正本（`scripts/check-env-overrides.py` が検査） | 静的な `.env` 検査であり、Compose の実効補間結果や稼働中コンテナの状態は直接検査しない |
| `deploy/desired-env.lkal` | kisage 管理下のホスト環境宣言（`upstreams` / `mtls_allowlists` / `rate_limits` / `feature_flags`） | `mtls_allowlists` サブツリーを `deploy/host-prereqs.yaml` の `env_allowlists` と独立に手編集すると二重権威を生む |
| `scripts/deploy.sh` | `scripts/check-compose-variables.sh` → AppArmor 検査 → Pact gate → leftover sweep → `c2quay deploy`（`c2quay.yml` / `scripts/smoke.sh`） | edge health 4 点（`scripts/smoke.sh`）のみを検査し、内部 mTLS エッジの実効設定とコンテナ反映の一致を直接検証しない |

具体的には、`compose/ai.yaml` において `pre-processor` は `CERT_SUBJECT=pre-processor`・`CERT_SANS=pre-processor,localhost` の証明書（`NEWS_CREATOR_CLIENT_CERT_FILE=/certs/svc-cert.pem`）で `NEWS_CREATOR_HOST=https://news-creator:9443` へ接続し、`news-creator` は `INBOUND_MTLS=true`・`CERT_SANS=news-creator,localhost`・`MTLS_ALLOWED_PEERS=${NEWS_CREATOR_MTLS_ALLOWED_PEERS:-recap-worker,acolyte-orchestrator,rag-orchestrator,recap-evaluator,pre-processor}`・`PEER_IDENTITY_STRICT=${NEWS_CREATOR_PEER_IDENTITY_STRICT:-true}` で検証する。なお、**本 ADR の作成にあたり実ホストに対する変更・デプロイ操作は一切行っていない。**

### 2. 生 `.env` 検査の誤解と構造的ギャップ

事前調査でホスト上の生 `.env` と宣言キーを単純照合した際、管理対象 23 キーが `.env` に未記載と報告されたが、**これは稼働ドリフトの証拠ではない**。`compose/ai.yaml` 等の `${VAR:-default}` により Compose の既定値が適用されるためである。一方で、解決すべき真のギャップは以下の 3 点にある。

1. **本番変更前の候補環境に対する実効補間検証の欠如**: `compose/compose.yaml` は `include:` 集約モデルであり（`scripts/check-compose-variables.sh` 記載のとおり）、各 include ファイルは `compose/.env`、ルート `./.env`、`env_file: ../.env`、およびシェル環境変数を参照する。本番の `.env` や kisage 状態を書き換える**前に**、候補（candidate）環境ファイルに対して実際の Compose レンダリングを通す必要がある。
2. **ホスト収束とロールアウト成功の非同値性（`host converged != rollout succeeded`）**: ホスト上の設定ファイルが収束しても、コンテナが新設定・期待イメージ digest で起動し mTLS 通信が成立するまでは成功ではない。また障害時の復旧では `.env` だけでなく直前の Compose 定義リビジョンと不変イメージ digest を対で戻す必要がある。
3. **秘密情報保護と重複サブツリーのみの保守的な権威整理**: `docker compose config` や `docker inspect` の全文出力は秘密値を含むためログに残せない。また既存の `deploy/host-prereqs.yaml` や [[000979]] の監査所有権を維持しつつ、重複する `mtls_allowlists` サブツリーのみの二重権威を解消する必要がある。

## Decision

**新規の常駐デーモンを設けず既存の `scripts/deploy.sh` / `c2quay` デプロイ入口を再利用し、まず `pre-processor -> news-creator` の単一 mTLS エッジを対象として、「ロールバック用チェックポイント（`previous_artifact_id`）準備 → 本番変更前の候補成果物（`candidate_artifact_id`）の意味論・実効 Compose 検証 → 排他ロック下での世代再確認とホストコミット → 検証済み候補成果物のデプロイ → 実コンテナ・機能通信観測 → 確定または `previous_artifact_id` への補償復旧」の 6 段階ゲートを段階導入する。**

### D1. 対象スコープ（単一エッジ整合性）と保守的な権威・所有権境界

- **単一エッジ整合性の定義**: 初期対象は `pre-processor`（caller）から `news-creator`（receiver, `:9443`）への単一エッジに限定する。整合条件は (1) caller の `CERT_SUBJECT` / `CERT_SANS` とクライアント証明書パス、(2) caller の接続先 URL（`NEWS_CREATOR_HOST`）の scheme（`https`）・ホスト名と receiver の `CERT_SANS`、(3) receiver の `MTLS_ALLOWED_PEERS` への caller 含有ならびに `INBOUND_MTLS=true`・`PEER_IDENTITY_STRICT=true` の一致とする。**これは単一エッジの整合性検査であり、推移的グラフ閉包（transitive graph closure）ではなく、形式証明（formal proof）でもない。**
- **保守的な権威配分（Phase 1 — 重複サブツリーのみ派生化）**:
  - サービス識別子の正本は `services.yaml`、コンテナ配線・既定値の正本は `compose/*.yaml` が維持する。
  - Phase 1 では **`deploy/host-prereqs.yaml` が引き続き `env_allowlists`・`retired_env`・`dead_env_values`・`host_paths` の正準制約権威（canonical constraint authority）を保持**し、OSU 予算およびホストセキュリティ制約も [[000979]] の既存オーナー（`compose-audit` / `scripts/ops-surface-inventory.yaml`）がそのまま所有する。
  - `deploy/desired-env.lkal` のうち、**`deploy/host-prereqs.yaml` の `env_allowlists` と重複する `/mtls_allowlists` サブツリー（および直接対応する制約フィールド）のみを正本から同期・整合検査される派生投影（derived / non-separately-edited subtree）として扱い、当該サブツリーの独自手編集を禁止する**。一方、`deploy/desired-env.lkal` 内の他セクション（`/feature_flags`、`/rate_limits`、および `dead_env_values` / `retired_env` 制約内の `/upstreams`）は引き続きリポジトリ所有の望ましい状態宣言（repo-owned intent）として保持し、すべてを単なる Compose デフォルトへ縮退させない。将来もし `mtls_allowlists` の編集正本を LKAL 側へ切り替える場合は、明示的な移行手順と後続 ADR による更新を必須とする。

### D2. 変更・検証・観測の 6 段階ライフサイクルと環境凍結・機密保護

直前の稼働状態を表す **`previous_artifact_id`**（ロールバック用チェックポイント: 旧 `kstate` + 旧 `.env` + 旧 Compose/config リビジョン + 旧稼働コンテナ Image ID / RepoDigest 群）と、今回適用する **`candidate_artifact_id`**（新 Compose/config リビジョン + 新ターゲットイメージ digest 群 + ステージングされた候補 `.env`）を明確に区別し、以下の 6 段階を実行する。

| 段階 | 処理内容 | 検証・保護・失敗時の扱い |
|---|---|---|
| 1. Prepare Checkpoint (`previous_artifact_id`) & Context | **保護された writer を静止・排他（quiesced/excluded）した状態**で、直前の完全な状態（ベースライン `host_state_generation`、旧 `kstate`、旧 `.env`、稼働中の旧 Compose/config リビジョン、実行中コンテナの Image ID / RepoDigest 一覧）を `previous_artifact_id` として一貫性をもって取得。実行環境を固定 | `DOCKER_HOST` / `DOCKER_CONTEXT` / `DOCKER_CONFIG` / `COMPOSE_PROJECT_NAME=alt` / `PATH` / `HOME` のみを許可リスト方式で通す制御環境を構築し、未申告のシェル変数を遮断しつつ、検証・デプロイ・復旧で**同一の Docker コンテキストとプロジェクト**を使用する（文脈を落とす単純な `env -i` は使わない） |
| 2. Validate Candidate (`candidate_artifact_id`) Pre-Mutation | **本番の `.env` や kisage ストアを一切変更する前**に、非管理値および `/local/*` を保持した候補 `.env` と新 Compose リビジョン（`candidate_artifact_id`）をステージング領域（`include:` と `env_file: ../.env` の相対解決を満たす `./.env` と `compose/.env` 構造）に配置し、実 `docker compose config` で実効設定を検査 | **全文は一切ログ出力・保存せず**、メモリ上で対象エッジのキー整合のみを判定し、キー名と `pass`/`fail` のみ記録。**ここで失敗した場合は本番ファイル未変更のまま即時中断する（ホスト復元不要）** |
| 3. Protected Commit / Reconciliation | Stage 2 合格後、**世代再確認からコミット完了までを単一の writer 排他ロック区間で囲み**（ハッシュ確認＋`rename` 単独では CAS にならないため）、本番の `host_state_generation` と `.env` ダイジェストが Stage 1 時点から不変であることを確認した上で、`candidate_artifact_id` の kisage 調停と本番 `.env`（および `compose/.env`）反映を実行し、書き出し後ダイジェストを再検証 | `kisage Resolve` は**所有権競合の解決認可**でありシークレット解決器ではない（シークレット参照は opaque のまま保持）。複数ファイル更新は非アトミックなため、**コミット途中で部分失敗した場合は排他ロック下で `previous_artifact_id` の `kstate + .env` 完全スナップショット対を即時復元する** |
| 4. Deploy Candidate (`candidate_artifact_id`) | Stage 1 と同一の制御された Docker コンテキスト下で、Stage 2〜3 を通過した **`candidate_artifact_id`（新 Compose/config リビジョンおよび新ターゲットイメージ digest 群）**を `scripts/deploy.sh` / `c2quay` でデプロイ | 旧リビジョン（`previous_artifact_id`）の誤再デプロイや、未検証の可変タグへのすり替わりを禁止 |
| 5. Observe Live Containers & Edge | 稼働中コンテナの Image ID / RepoDigest が `candidate_artifact_id` と一致すること、コンテナ内対象環境変数の反映有無、および `pre-processor -> news-creator` の機能通信（mTLS 疎通）を観測 | `host_converged` と `rollout_succeeded` を分離。未観測（`not_observed`）を成功とみなすことを禁止 |
| 6. Finalize or Compensate (`previous_artifact_id`) | 証跡確定、または Stage 4〜5 失敗時に `previous_artifact_id` を用いた補償復旧を実行 | D3 の補償復旧手順に従い、回復不能時はオペレータ介入のため fail-closed で停止 |

### D3. 排他制御・非アトミック性・補償復旧（Rollback）契約

- **書き込み保護の現実的境界**: ユーザー空間の「ハッシュ確認＋`rename(2)`」は CAS ではない。Stage 1 の一貫したチェックポイント取得と、Stage 3 の「ベースライン世代不変確認＋書き出し＋再検証」を跨ぐ保護された writer の排他ロックを用いるが、**同一 UID の任意の非協調プロセスによる直接書き込みレースの根絶は主張しない**。
- **変更前失敗と変更後失敗の明確な分離**:
  - **Stage 1〜2（本番変更前）での失敗**: 本番の `.env` も kisage 状態も未変更であるため、ホスト復元処理は不要でありそのまま中断する。
  - **Stage 3（部分コミット失敗）**: writer 排他下で、`previous_artifact_id` に記録された直前の完全な `kisage state + .env` スナップショット対を同一ホスト上で復元し、ダイジェスト一致を確認する。
  - **Stage 4〜5（デプロイ・稼働観測失敗）での補償復旧**: Docker Compose の複数コンテナ更新は非アトミックである。失敗時は writer を静止させ、**同一ホスト・同一ツール構成上でのみ**、**`previous_artifact_id`（旧 `kstate + .env` に加え、旧 Compose/config リビジョンおよび旧稼働実績のある正確な Image ID / RepoDigest 群）を一括して復元・再適用する**（可変の `:main` / `:latest` タグや失敗した `candidate_artifact_id` の設定では再収束させない）。復元後、稼働コンテナの image digest が `previous_artifact_id` に戻ったことと `pre-processor -> news-creator` の機能通信回復の双方を検証する。回復しない、または観測不能（`not_observed`）な場合は **`rollout_succeeded: false` を記録してオペレータ向けに停止する**。

### D5. 実装フェーズと具体的受入・中断基準

- **Phase 1（隔離フィクスチャでの失敗注入・補償検証）**: 本番環境に触れず、以下の **6 つの具体的な検証シナリオ（5 つの失敗注入＋切替/補償往復フィクスチャ）**をテストハーネスで検証する。
  1. `stale env override`: 候補 `.env` の上書きが `NEWS_CREATOR_MTLS_ALLOWED_PEERS` から `pre-processor` を欠落させるケース（**候補が現行 `.env` と異なる状態で Stage 2 が失敗し、現行 `.env` と kisage ストアが 1 バイトも変化しないこと**を検証）
  2. `shell override`: 呼び出し元シェルの未許可環境変数が Compose 補間を上書きしようとするケース（Stage 1 の環境固定で遮断されることを検証）
  3. `asymmetric allowlist`: caller の接続先 URL / SAN と receiver の allowlist が非対称に食い違うケース
  4. `stale container image/env`: ホストファイルは収束したがコンテナが旧環境変数・不一致イメージ digest のまま残るケース（Stage 5 で検知し補償復旧が発火することを検証）
  5. `concurrent change`: Stage 1 と Stage 3 の間にベースライン世代が変化したケース、およびコミット途中の中断ケース（排他ロック下の世代検査で遮断され、部分失敗時に `previous_artifact_id` の `kstate + .env` が完全復元されることを検証）
  6. `candidate switch & previous rollback fixture`: `previous_artifact_id` と `candidate_artifact_id` で異なるイメージ digest・Compose 設定を持つ小規模フィクスチャを用い、正常時に `candidate_artifact_id` へ切り替わること、および Stage 5 失敗注入時に `previous_artifact_id` の正確なイメージ digest と設定へロールバックされることを検証
- **受入基準（Acceptance Criteria）**: 上記有限テストにおいて、**見逃し 0 件（0 misses）・正常系の誤遮断 0 件（0 false-stops）・設定値やシークレット値のログ漏洩 0 件（0 value leaks）**を達成すること。ゲート所要時間は実測・記録対象とし、未検証の固定時間保証（例:「3 秒以内保証」）は前提としない。
- **Phase 2（`scripts/deploy.sh` への統合）**: Phase 1 合格後、`scripts/deploy.sh` の導線へ統合する。
- **中断基準（Abort Criteria）**: 証跡への平文値漏洩が 1 件でも発生した場合、Stage 2 失敗時に本番ファイルが書き換わった場合、または補償復旧後に `previous_artifact_id` のイメージ digest と機能通信の回復が確認できない場合は即時中断する。

### D6. 検討した代替案と却下理由

- **(a) 本番 `.env` を先に書き換えてから `docker compose config` を実行する案 — 却下**: 検証失敗時に本番環境がすでに汚染され、不要なロールバックリスクを負うため。
- **(b) `env -i` で全環境変数を無差別に消去してレンダリングする案 — 却下**: `DOCKER_CONTEXT` や `DOCKER_HOST` 等が落ちてデプロイ時と異なるコンテキストを参照する恐れがあるため、Docker 必須変数の明示的許可リストで同一コンテキストを凍結する方式を採る。
- **(c) ロールバック時に `.env` だけ戻して現行の `c2quay` 設定・可変タグで再デプロイする案 — 却下**: コンテナイメージや Compose 定義の変更を伴う障害では `.env` 復元だけでは元の稼働状態に戻らないため、`previous_artifact_id` の Compose リビジョンと正確なイメージ digest を対で復元する。
- **(d) 新規の常駐監視・自動修復デーモンを導入する案 — 却下**: [[000979]] の operational-surface（OSU）予算を増やし、`scripts/deploy.sh` と競合する dual-writer を招くため。

### D7. 残存する未解決事項と解消方法（Open Issues）

1. **`deploy/desired-env.lkal` の `/mtls_allowlists` サブツリーと `deploy/host-prereqs.yaml` の `env_allowlists` の CI 整合チェック実装**: Phase 1 では `deploy/host-prereqs.yaml` を `env_allowlists` の正本に維持し、`deploy/desired-env.lkal` の他セクション（`/feature_flags`・`/rate_limits`・`/upstreams`）の既存所有権を保ったまま、重複する `/mtls_allowlists` サブツリーの一致を検査する lint を `scripts/check-env-overrides.py` のテストスイートに追加して閉じる。
2. **Stage 5 の機能通信観測プローブ方式**: `pre-processor` コンテナ内からの疎通確認と `/health/deep`（[[000980]]）の所要時間・切り分け精度を Phase 1 で実測比較して確定する。

## Consequences

### Pros

- 本番変更前に候補環境の実効 Compose 設定を検証するため、不正な上書きが本番ファイルに到達する前に無傷で遮断できる。
- ロールバック時に `.env`・kisage 状態だけでなく直前の Compose リビジョンと不変イメージ digest を復元するため、再現性のある復旧が可能になる。

### Cons / Tradeoffs

- 候補環境のステージングレンダリングと直前デプロイ成果物のスナップショット保持により、デプロイ前後の処理ステップと所要時間が増加する（Phase 1 で実測管理）。
- 初期対象は `pre-processor -> news-creator` の単一エッジであり、他エッジへの展開は段階的な追補を要する。
