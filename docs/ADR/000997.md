# ADR-000997: kisage所有権プロトコルの競合・委譲・復旧挙動を複数actorの隔離実験で検証する

## Status

Proposed（将来設計の提案。本 ADR は隔離環境における所有権プロトコル検証実験の計画であり、実装完了の主張や本番環境でのマルチ actor 運用採択を宣言するものではない）

## Date

2026-11-06

## Affected Services

- scripts (`scripts/tests/test-kisage-env.py` 等のテスト群) — 単一 actor / MCP 境界の先行検証テスト（`scripts/tests/test-kisage-env.py`）はすでにリポジトリに存在する。本 ADR で新たに提案する複数 actor 競合・委譲・復旧（`E1`〜`E7`）の隔離適合性ハーネスのみが未実装の将来計画である（本番の `.env` や `.kisage` 状態ストアには一切触れない）
- compose (`deploy/desired-env.lkal`) — 宣言構造およびスコープ境界の参照モデル（既存ファイル自体の変更は行わない）

## Context

本 ADR は [[000826]]（デプロイモデル整合性）および [[000979]]（ホスト設定・operational-surface の機械的統制）を前提とする。

### 1. 現状の証拠（Current Evidence）と権限・所有権モデルの前提

現在、`scripts/tests/test-kisage-env.py` において単一 actor での環境宣言検証や MCP ツール境界のパイロットテストが存在する。今後、ワークツリー上の宣言ファイル（例: `deploy/desired-env.lkal`）の編集主体と、ホスト上の実ファイルに対する保護された反映処理を分離し、複数 actor 間の所有権プロトコルを評価するにあたり、判明している事実と未検証の仮説を明確に区別する必要がある。

1. **OS 実行主体（Principal）・`0700` ストア所有・信頼された host-config プロファイル**:
   - パーミッション `0700` の共有状態ストア（`.kisage`）を、異なる複数の OS UID が同時に直接独立所有することは OS 権限モデル上不可能である。したがって、**共有ストアを所有する単一の信頼された実行主体（trusted executor UID）の下で、ホスト側設定ファイルに定義された複数の actor プロファイル（`actorA`, `actorB`）を実行する構成**と、**別個の非特権 UID で動作しストアへの直接書き込みも任意の actor プロファイル選択もできないエージェント（`agy` ワーカー）**を明確に分離する。なお、要求元 OS 主体から許可された host-config actor プロファイルへのマッピング機構自体はゲート付きの未実装課題である。
   - **同一 UID 内で動作するプリフックやラッパースクリプトは OS のセキュリティ境界ではない。** また、kisage における `actor` 識別子は**信頼されたホスト側設定（trusted host config）**から決定されるべきものであり、MCP リクエスト等のトランスポート層から自己申告されたクレームを信頼してはならない。ホスト初期化・管理操作（admin CLI）と MCP 公開ツールの権限も明確に分離される。
2. **Resource・DeclarationFile 束縛・3 つの意味論的リーフ分類とソース版固定（Tool Pinning）**:
   - kisage は `Resource -> DeclarationFile` の固定束縛を持ち、各宣言は対象リソースに対する**完全な望ましい状態（complete desired intent）**を表す。**部分的な差分（partial delta）を「完全宣言」と呼んではならず、本番で複数の部分宣言ファイルを分割運用する前提も置かない。**
   - リーフの起源と所有権は、特定コミットの内部列挙子リテラル（例: 開発ツリーの `OriginNone` / `OriginCreated` / `OriginModified` 等）を決め打ちせず、以下の**バージョン中立な 3 つの意味論的カテゴリ**で定義し、実験実行時に選択・固定した kisage コミット/バイナリの契約（provider contract）に照らして実測値（`observed_raw_origin`）を記録する。
     - **(a) 自己作成来歴を持つ所有リーフ（Creation-provenance ownership）**: 宣言に基づき不在（`absent -> present`）から当該 actor が新規作成したと検証されたリーフであり、作成・削除（明示的 `prune` 時）の来歴を持つ。
     - **(b) 既存値由来の所有リーフ（Existing-value-derived ownership）**: 既存の値に由来して所有権を保持するが、**自動削除権（deletion right）を持たない**カテゴリ。宣言に含まれるキーの既存値が宣言値と**一致（matching）**している場合、固定された kisage リビジョンの仕様によっては通常の `apply` でこの所有権を取得しうる（「あらゆる既存値の所有権取得に必ず明示的 `adopt` が必要」とは仮定しない）。また、既存値との不一致競合に対する明示的な `explain` / `adopt` 解決や、保守的なクラッシュ復旧後の状態もこのカテゴリに属する。
     - **(c) 未宣言・非管理リーフ（Undeclared / unmanaged leaves）**: `/local/*` 等の宣言に含まれない既存リーフであり、所有権ストア外（非所有）としてターゲットファイル上にそのまま保持される。
   - 以前所有していたリーフを宣言から省略した場合、通常の `apply` 単体では削除されず、まず**退役候補・未収束（retirement / non-convergence）として報告されターゲット値は保持される**。その後の明示的な `prune` 操作と前提条件充足を経て初めて、当該 actor の **(a) 自己作成来歴を持つ所有リーフ**のみが削除され、**(b) 既存値由来の所有リーフ**および **(c) 未宣言・非管理リーフ**は保護される。
   - 同一の完全宣言ファイルを、`Scope` が `/feature_flags` のみに制限された actor 設定で適用すると、`/feature_flags` 配下は適格（eligible）である一方、他パスでスコープ違反（例: `K401` 相当のスコープ拒否診断）が発生する。
3. **未検証の事項（Explicit Unknowns）とソース版整合ゲート**:
   - 浮動する開発ブランチ（floating `main`）と Alt 側で固定された kisage バイナリのリビジョン差により、内部 `Origin` 列挙名や診断コードの細部が異なりうる。したがって**実行ごとに kisage / LKAL のコミット SHA・バイナリ digest・プロバイダ契約を 1 つに固定（pin）し、そのリビジョンから期待される `Origin` 値とエラーコードを導出することを `E1`〜`E7` 着手前の必須ゲートとする**（浮動ブランチの仮説と別リビジョンの固定バイナリを混在させない）。
   - 異なる actor 設定が同一のターゲット Resource に対して別々の宣言ファイルをグローバルに束縛し共存できるか否か、および 1 回の `apply` 内で適格リーフと拒否リーフが混在した際に「リソース全体が all-or-nothing でアトミックに不変となるか」は**未検証（UNVERIFIED）**であり、全体トランザクションを前提にしてはならない。

## Decision

**本番環境へのマルチ actor 導入を前提とせず、まず使用する kisage / LKAL のコミットとバイナリ同一性を固定した上で、隔離されたテストフィクスチャ上で「同一の正準 Resource・共有状態ストア・同一の登録済み完全宣言ファイルパス」を用いた複数 actor の競合・委譲・異常復旧実験を実施する。仮説と検証済み保証を厳密に区別し、実験結果によっては「本番は単一 actor 運用を維持する」という結論も正当な採択出口とする。**

### D1. 実験トポロジ・事前ゲート・境界設定（Baseline Isolation Setup）

| 境界要素 | 隔離実験での設定 | 根拠・制約 |
|---|---|---|
| 事前ゲート（Tool & Contract Pin） | 実行対象の kisage / LKAL コミット SHA とバイナリ SHA-256 を固定 | 浮動する開発ツリーと固定バイナリの仕様混同を防ぎ、当該リビジョンから期待 `Origin`・診断コードを導出する |
| Git ワークツリー変更主体 | エージェント（`agy`、別 UID）または開発者 | 宣言ファイル案の編集のみを担い、`0700` ストアの直接書き換えや任意プロファイル選択の権限を持たない |
| ホスト反映主体（Trusted Executor） | 共有 `0700` ストアを所有する単一の信頼された実行 UID | 信頼されたホスト設定上のプロファイル（`actorA`, `actorB`）を切り替えて実行する |
| Actor 識別子の決定源 | 信頼されたホスト側設定ファイル（trusted host config） | トランスポート（MCP ツール引数等）からの自己申告 actor クレームは信頼しない |
| 操作インターフェース分離 | ホスト初期化・管理 CLI と MCP 公開ツールを分離 | リソース登録・初期束縛は管理側で行い、公開ツールからの恣意的な束縛変更を防ぐ |
| 共有宣言ファイルの変更記録 | テストハーネスが宣言の変更前後 SHA-256 と実行ステップ主体を記録 | 同一の正準宣言ファイルを `actorA` 用・`actorB` 用に書き換える際、どのハーネス操作がどの宣言 digest を書いたかを厳密に追跡する |

- **同一 Resource・共有ストア・同一完全宣言パス**: ベースラインの所有権競合テストでは、競合する `actorA` と `actorB` が**同一の正準 Resource、同一の共有状態ストア、および同一の登録済み完全宣言ファイルパス**を参照する。
- **所有権競合とスコープ違反の分離**:
  - 所有権競合テスト（`E2`）では、スコープ違反が先に発火して所有権検査が隠蔽されるのを防ぐため、両 actor に十分な広さの `Scope` を付与する。
  - スコープ制限テスト（`E3`）は別ケースとして切り出し、`/feature_flags` のみに絞った狭小 `Scope` で完全宣言を投入した際に、スコープ外リーフへの変更が拒否されることを検証する。

### D2. 有限フィクスチャ実験マトリクス（仮説 vs 検証対象の分離）

以下の 7 シナリオを有限の実験マトリクスとして定義する。各項目は現時点では**検証対象の仮説（Expected Behavior / Hypothesis）**であり、実験完了前に「検証済み保証（Verified Guarantee）」として扱わない。また、**リソース全体のアトミックな all-or-nothing 適用は前提とせず、リーフ単位の安全性アサーション（per-leaf safety assertions）を基本とする。**

| ケース ID | シナリオ | 検証対象の仮説（Expected Behavior） | 観測オラクル（リーフ単位の遷移証跡・値なし） |
|---|---|---|---|
| `E1` | `ownerA initial acquisition`（初期取得の 3 サブケース分離検証） | 以下の 3 点を別々に検証する: (1) 宣言された `absent -> present` リーフは**自己作成来歴（カテゴリ a）**で所有取得される、(2) 宣言された**既存一致値（existing matching value）**リーフは固定リビジョンの契約に従い通常の `apply` で**削除権を持たない既存値由来所有（カテゴリ b）**を取得しうる、(3) 宣言された**既存不一致値（existing mismatching value）**は競合として停止し、**未宣言リーフ（`/local/*` 等、カテゴリ c）**は所有権ストア外でそのまま保持される | 3 サブケースそれぞれのリーフ別 `observed_raw_origin`・意味論カテゴリ分類、不一致時の競合停止、未宣言キーのストア外保持確認 |
| `E2` | `actorB conflicting change blocked`（広スコープ下の所有権競合） | 同一 Resource・同一完全宣言パス・広スコープ下で、`actorB` が `actorA` 所有リーフを変更しようとすると競合拒否され、**当該競合リーフのターゲット値と所有権（`owner`, `owner_rev`）が不変に保たれる**（全体不変を検証する場合は競合変更のみを含む settled フィクスチャで分離検証する） | 固定ツールの実際の拒否診断コード、競合リーフの `prev == next` 所有権・値ハッシュ（他パスに操作がある場合は別途観測し全体トランザクションを仮定しない） |
| `E3` | `narrow scope rejection`（スコープ違反の分離検証） | `Scope` を `/feature_flags` のみに制限した actor が完全宣言を適用すると、スコープ外のリーフ群がスコープ違反で拒否され、**拒否された各リーフのターゲット値・所有権が不変に保たれる**（適格な `/feature_flags` 側の変更有無とは分離して観測し、ストア全体の世代不変は仮定しない） | スコープ拒否診断コード、スコープ外各リーフの所有権・値ハッシュ不変確認、適格パス側の別観測記録 |
| `E4` | `external drift stopped`（帯域外変更の検知・遮断） | ハーネスがターゲットファイルを直接書き換えた場合、次回調停時に外部ドリフトとして検知・停止し、暗黙の上書きを行わない | ドリフト検知ステータス、対象キー名（値は出力しない）、ターゲット保護確認 |
| `E5` | `explain / release / adopt & stale token`（直接横取り不可・2 段階委譲と失効検査） | **`actorA` 所有リーフに対する `actorB` の直接 `adopt` は `Resolve` 付きでも拒否される（`Resolve` は他 owner 所有権の横取りを許可しない）**。所有権移転は (1) `actorA` が現在有効なトークン・`owner_rev` で明示的に `release` して非所有化し、(2) その後 `actorB` が改めて `explain` を実行して最新条件を取得し、必要 `Scope` 内で**非所有（unowned）状態となったリーフのみを `adopt`**（削除権を持たない既存値由来所有＝カテゴリ b）する 2 段階手順でのみ成立する。いずれの段階でも古いトークンや旧 `owner_rev` の再利用は拒否される | 直接 `adopt` の拒否結果、`release` 後・再 `explain` 後のリーフ別 `owner`・`owner_rev`・実測 `observed_raw_origin`、旧トークン/旧 `owner_rev` 拒否確認 |
| `E6` | `omission vs explicit prune`（宣言省略と明示的 prune の分離） | 宣言からのリーフ省略単独では `apply` は**退役候補・未収束を報告してターゲット値を保持**し、削除しない。その後の**明示的 `prune` 実行時のみ自 actor の自己作成来歴リーフ（カテゴリ a）が削除**され、既存値由来所有リーフ（カテゴリ b）および未宣言・非管理リーフ（カテゴリ c）は削除されず保護される（`release`/disposition の詳細挙動は推測せず実測記録する） | (a) 省略 `apply` 後のターゲット保持と未収束報告、(b) 明示的 `prune` 後のカテゴリ a 削除とカテゴリ b/c 保護の確認 |
| `E7` | `deterministic barrier interruption & recovery`（決定論的バリア中断と静止復旧） | 永続化プロトコル上の境界（durable protocol barriers）での決定論的中断後、アクティブな writer プロセスの静止（quiescence）を確認した上でストアとターゲットが整合状態へ復旧する | 中断バリア識別子、プロセス静止確認結果、復旧後のストア・ターゲット整合と `observed_raw_origin` |

### D3. オラクル設計と非保証事項（Explicit Non-Claims）

- **具体的オラクル（Concrete Oracle）**: 各テストケースは固定したツールのリビジョン情報（`tool_pin`）、ハーネスが書き換えた宣言ファイルの前後ダイジェストと書き換え主体、実行前（`previous`）と実行後（`next`）のターゲットおよび状態ストアのリーフ単位スナップショット（架空のリテラルを決め打ちせず意味論カテゴリと実測 `observed_raw_origin` を記録）、ならびに**テストハーネスの観測結果と既存 CLI / MCP ツールの返却結果（kisage に既存の公開イベントストリーム API が存在するという主張ではない）**を構造化記録する。**秘密値や生の設定値は一切記録しない。**

- **証跡の誠実性と有限性**: 将来この実験を実行した際は、実際のテスト実行 ID（`run_id`）と固定ツールの実測診断コード・実測 `Origin` 値を記録し、未実行の段階で合格ステータスや未検証のエラーコードを捏造しない。また本オラクルは有限フィクスチャに対する検証であり、普遍的証明やリソース全体のアトミックトランザクションを主張しない。
- **明示的な非保証（Non-Claims）**:
  1. **全体アトミック適用・複数ファイルトランザクション・分散コンセンサスの不在**: kisage は複数ファイル間のグローバルトランザクションや分散コンセンサスを提供せず、単一リソース内でも未検証の全体 all-or-nothing アトミック性を前提としない。
  2. **「ロックファイル不在＝静止」ヒューリスティックの禁止**: ロックファイルの存在有無はロック保持状態と同値ではない。したがって「locks ディレクトリが空であること」を汎用的な静止（quiescence）判定に使ってはならず、実験ハーネス自身が起動した全 writer プロセスの終了確認をもって静止と判定する。
  3. **ランダムなプロセス強制終了の限界**: 外部からのランダムな `kill -9` はすべての永続化プロトコル境界（durable barriers）を網羅した証明にはならない。

### D4. 段階的実施フェーズと受入・中断・出口基準

- **Phase 0（ツール・契約リビジョンの固定ゲート）**: 実験で使用する kisage / LKAL のコミット SHA・バイナリ digest・プロバイダ契約を 1 つに固定し、当該リビジョンにおける `Origin` 列挙定義と診断コード体系を確定させる（このゲート完了前に `E1`〜`E7` を実行しない）。
- **Phase 1（適合性ハーネス構築と E1〜E6 の隔離検証）**: `scripts/tests/test-kisage-env.py` の先行知見を踏まえ、一時ディレクトリ上で `E1`〜`E6` を自動実行するリーフ単位オラクル付きテストを作成する。
- **Phase 2（E7 バリア中断検証と運用モデル判定）**: 決定論的バリア中断フック（D6-3 参照）が利用可能な範囲で `E7` を検証し、本番で複数 actor プロファイルを許容するか単一 actor に固定するかを判定する。
- **受入基準（Acceptance Criteria）**:
  - 固定されたツールリビジョンに対する有限フィクスチャ `E1`〜`E6`（およびフック整備後の `E7`）において、拒否対象リーフの未認可上書き（false allow）が 0 件、未宣言リーフ（カテゴリ c）の誤追跡・誤削除が 0 件、省略単体での誤削除が 0 件、既存値由来所有リーフ（カテゴリ b）の `prune` 誤削除が 0 件、生値のログ漏洩が 0 件であること。
- **中断基準（Abort Criteria）**: `E2`（競合リーフ保護）、`E5`（古い `owner_rev` / トークン拒否）、または `E6`（既存値由来所有リーフおよび未宣言リーフの保護）で 1 件でも意図しない状態破壊が観測された場合、マルチ actor 運用の検討を直ちに中断し、本番は単一 actor 構成に固定する。
- **正当な出口としての単一 actor 維持**: 全テストが合格した場合であっても、運用複雑度や `Resource -> DeclarationFile` 束縛の制約が見合わないと判断すれば、**「本番環境は単一の保護された production actor のみで運用する」という決定を本実験の正当な最終結論として採択できる**。

### D5. 検討した代替案と却下理由

- **(a) 隔離実験を省き、本番 `.env` 上で直接複数 actor を競合させる案 — 却下**: スコープ違反や退役候補の扱いが本番設定を破壊するリスクが高いため。
- **(b) MCP リクエストの引数で渡された `actor` 名をそのまま信頼して権限判定する案 — 却下**: 呼び出し側が任意の owner を詐称でき、所有権プロトコルが形骸化するため。
- **(c) 各 actor が変更したい数行だけの部分差分ファイルを「宣言」として渡す案 — 却下**: kisage の完全宣言モデルでは省略された所有リーフが退役候補（未収束）となり、明示的 prune 時に意図しない設定削除を引き起こすため。

### D6. 残存する未解決事項と解消方法（Open Issues）

1. **固定バイナリとソースツリー間の契約整合性および複数宣言ファイル束縛の可否（Gated Open Issue）**: 実行対象として固定する kisage リビジョンの正確な `Origin` 遷移表の確認、および異なる actor 設定が別個の宣言ファイルパスを同一 Resource に登録し共存できるか否か（UNVERIFIED）。解消方法: Phase 0 のツール固定ゲートで対象コミットの遷移表を確定し、Phase 1 の適合性テストで検証するまで複数宣言束縛は採用不可とする。
2. **要求元 OS 主体から信頼された executor の actor プロファイルへの昇格・マッピング機構**: `agy` 等の非特権 UID からの要求を、どのように認可して共有 `0700` ストアを持つ trusted executor UID 上の特定 host-config プロファイルとして起動するか。解消方法: Phase 2 完了後、単一 actor か複数 actor かの結論と合わせて最小権限の起動方式を決定する。
3. **`E7` における永続化プロトコル境界（durable barriers）の特定と決定論的テストフック（Gated Open Issue）**: ランダムなプロセス kill ではなく、ストア書き出しとターゲット反映の各バリア直前・直後で決定論的に中断させるためのテストフックまたは計装の有無。解消方法: 固定した kisage リビジョンの内部バリア箇所とフック提供可否を確認し、フックが確認できるまで `E7` の完全網羅は主張しない。

## Consequences

### Pros

- 自己作成来歴リーフ（カテゴリ a）・削除権を持たない既存値由来所有リーフ（カテゴリ b）・未宣言リーフ（カテゴリ c）の 3 分類と、ツールリビジョン固定（`tool_pin`）により、開発ツリーと固定バイナリの仕様差に惑わされずに競合（`E2`）・スコープ違反（`E3`）・明示的 `prune`（`E6`）を実証できる。
- 「仮説」と「検証済み保証」を分離し、実験結果に基づいて単一 actor 維持という保守的な判断も迷いなく選択できる。

### Cons / Tradeoffs

- 隔離テストハーネスと `previous`/`next` スナップショット比較オラクルを整備する工数がかかる。
- 有限フィクスチャ上の検証であり、OS カーネルやファイルシステム固有のあらゆる異常や別 UID 以外の特権濫用を網羅的に証明するものではない。
