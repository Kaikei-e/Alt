# ADR-000955: フロントエンドが内部 RPC 名を直接発話している構造を論点化し公開契約の表現方法を選択する

## Status

Proposed（**決定ではない**。ユーザから提起された「フロントエンドが RPC 名を知っているのはおかしくないか、BFF が居るのに」という問いを構造的な論点として定式化し、選択肢と評価軸を並べるところまでを本 ADR の責務とする。採否の判断は本 ADR 単体では行わない）

## Date

2026-07-31

## Affected Services

- alt-frontend-sv (SvelteKit / Svelte 5)
- alt-butterfly-facade (Go)
- alt-backend (Go)
- proto（名前空間設計・`buf.gen.*.yaml` の生成ターゲット）

## Context

### 1. 現状の経路と、各層が「知っていること」

ブラウザからバックエンドまでの Connect-RPC 経路は 3 ホップある。実測した各ファイルの内容は次のとおり。

```
ブラウザ (connect-es client)
  → alt-frontend-sv の SvelteKit server route  /api/v2/[...path]
  → alt-butterfly-facade (BFF) :9250
  → alt-backend Connect リスナー :9101
```

`compose/core.yaml` で `alt-frontend-sv` の `BACKEND_CONNECT_URL` は `http://alt-butterfly-facade:9250` を既定値にしており、ブラウザ経路（`/api/v2` プロキシ）も SSR 経路（`src/lib/connect/transport-server.ts`）も同じ変数を使う。つまり **BFF は経路上ちゃんと居る**。問題は居ないことではなく、居ても意味論を持っていないことである。

各層が実際に持っている知識を並べると次のようになる。

| 層 | 知っていること | 知らないこと |
|---|---|---|
| ブラウザ | `alt.feeds.v2.FeedService/GetFeedStats` のような**完全な RPC パス**（connect-es の `GenService` 記述子経由）と、リクエスト／レスポンスの proto 型 | — |
| SvelteKit `/api/v2/[...path]` | 通してよい**サービス名 14 個の文字列集合**（`PROXYABLE_SERVICES`）。プロシージャ名は「1 個存在すること」しか見ない | RPC の意味、引数、副作用 |
| BFF | `mux.Handle` で事前登録した**パス prefix**（`/alt.tts.v1.TTSService/`、`/alt.knowledge_home.v1.KnowledgeHomeAdminService/`、`/alt.admin_monitor.v1.AdminMonitorService/`、`/alt.acolyte.v1.AcolyteService/`、`/v1/`、`/v1/aggregate`）と、catch-all で**拒否する prefix 2 個**（`/services.`、`/alt.datahub.v1.`） | それ以外のすべて。透過プロキシなので body も読まない |
| alt-backend | 実際の RPC 実装 | 呼び出し元がブラウザか worker か（`X-Alt-Backend-Token` の検証はするが、経路の由来は問わない） |

BFF が意味論を持たないのは事故ではなく設計である。[[000082]] は BFF 導入時に「透過型 HTTP プロキシ」を選び、その理由として **proto 依存問題の回避**を挙げている。実際 `proto/buf.gen.yaml` は BFF に対して `protoc-gen-go`（型のみ）は流すが `protoc-gen-connect-go` は意図的に流していない（"NOTE: connect-go plugin not used because BFF uses transparent HTTP proxy pattern"）。BFF は proto の**型**は持つが**サービス定義**を持たない。

### 2. 統制が「肯定形」と「否定形」に分裂している

同じ 1 本の経路に、形の違う 2 つの門が直列に並んでいる。

**フロント側（肯定形 / allowlist）** — `alt-frontend-sv/src/routes/api/v2/[...path]/+server.ts`:

```ts
const PROXYABLE_SERVICES = new Set([
	"alt.acolyte.v1.AcolyteService",
	"alt.articles.v2.ArticleService",
	// … 計 14 サービス
]);
```

パスを `/` で split して `[service, method, ...rest]` に分解し、`rest.length === 0` かつ service が集合に含まれる場合のみ通す。ここで通らなければ 404 を返し、`fetch` を呼ばない。

**BFF 側（否定形 / deny-list）** — `alt-butterfly-facade/internal/server/rest_allowlist.go`:

```go
var serviceToServicePrefixes = []string{
	"/services.",
	"/alt.datahub.v1.",
}
```

catch-all ハンドラでこの prefix に当たれば 404、当たらなければ `mainHandler` へ素通しする。

この非対称は `alt-frontend-sv/.../server.test.ts` のコメントに明記されている（"Note the shape of the guard here differs from the BFF's: this proxy is an allowlist (PROXYABLE_SERVICES), so a new east-west service is denied by construction"）。フロント側は構造的に閉じているが、**BFF 側は新しい東西サービスの proto パッケージが増えるたびに `serviceToServicePrefixes` へ追記しない限り開いたままになる**。deny-list は登録漏れ 1 個で破れる。

なお REST 側（`/v1/`）はさらに弱く、`allowRESTPath` は**警告ログを出すだけでルーティングを一切ゲートしていない**（コード内コメントが明示。[[000729]] Phase 3 が未着手）。

### 3. この統制が必要になった理由（confused deputy）

両方の門は、同じ 1 つの攻撃面に対する後付けの防波堤である。BFF テストのコメントが根拠を最も端的に述べている:

> The BFF holds a legitimate mTLS identity toward alt-backend. Forwarding an arbitrary caller-supplied service path therefore turns it into a confused deputy: a self-registered user with a valid session could reach the service-to-service RPC surface through the product's own /api/v2 proxy.

SvelteKit プロキシも同型である。呼び出し元が選んだ任意のパスに対して、プロキシが**有効な backend token を付けて**転送する。パスが無制限なら、セルフ登録した任意のアカウントが東西 RPC 面への踏み台を手に入れる。この面には end-user JWT の検証が無い（それは南北面の責務だから）。

つまり **「フロントが RPC 名を選べる」という性質が、そのままセキュリティ境界の問題になっている。** 名前を選べる主体が信用できないので、選ばれた名前を後段でフィルタするしかない、という構造である。

### 4. 内部名の変更がフロントに波及する — [[000954]] が実例を作った

[[000954]] は `services.backend.v1.BackendInternalService` の 24 RPC を `alt.datahub.v1.DataHubService` へ移す決定をした。これは **alt-backend 内部の都合による、内部専用サービスの改名**である。ブラウザから到達できないどころか、alt-data-hub は mTLS 専用リスナー 1 本で publish ゼロ、BFF は peer allowlist にすら入っていない。

にもかかわらず、この改名は次の 2 箇所に波及した。

- `alt-butterfly-facade/internal/server/rest_allowlist.go` — `serviceToServicePrefixes` に `/alt.datahub.v1.` を追加（新パッケージは `services.` prefix を共有しないため）
- `alt-frontend-sv/src/routes/api/v2/[...path]/server.test.ts` — deny テーブルに `alt.datahub.v1.DataHubService/*` の 3 行を追加

`rest_allowlist.go` のコメントは、この追加が「上流が今たまたま拒否するから不要」ではないと明言している（"the deny stays at the edge: the point is that a caller-chosen path is never forwarded, not that the upstream happens to refuse it today"）。判断としては正しい。しかし**バックエンド内部のサービス改名 1 件が、フロントエンドのテストファイルの編集を要求した**という事実自体が、境界の位置がおかしいことの徴候である。

この波及は proto の性質に根ざしている。Connect-RPC では proto の `package` 名がそのまま wire path になる。[[000085]] は、`clients.search.v2` と `services.search.v2` の食い違いだけで実行時 404 が出た事例を記録している。**proto パッケージ名は単なる名前ではなく、経路上のすべての層に露出する load-bearing な識別子である。**

### 5. 「フロントは内部名を知らない」は既に部分的に守られている（ただしアドホックに）

`proto/buf.gen.yaml` は `alt/datahub` を `exclude_paths` で TypeScript 生成から外している。コメントの理由は次のとおり。

> DataHubService is reachable only over mutual TLS from a listener with no published port — a browser client for it could not connect and should not be shipped.

これは本 ADR が論点にしている「公開 proto と内部 proto を分ける」判断そのものである。ただし現状は **1 パッケージについて手書きの `exclude_paths` とコメントで表現されているだけ**で、規約でもツールでも CI でもない。

そして分離は完全ではない。`alt-frontend-sv/src/lib/gen/` の実測（全 22 ファイル）には東西パッケージの生成物が残っている。

| パス | 由来 | アプリコードからの import |
|---|---|---|
| `gen/services/sovereign/v1/sovereign_pb.ts` | `services.sovereign.v1` (東西) | 無し |
| `gen/services/search/v2/search_pb.ts` | `services.search.v2` (東西) | 無し |
| `gen/services/preprocessor/v2/preprocessor_pb.ts` | `services.preprocessor.v2` (東西) | 無し |
| `gen/internal/search/v2/search_pb.ts` | `proto/internal/` は**現在存在しない** | 無し |
| `gen/internal/preprocessor/v2/preprocessor_pb.ts` | 同上 | 無し |

現在の `buf.gen.yaml` の `inputs.paths` は `alt` 系のみで、これらを生成する設定はもう無い。**過去の生成設定の遺物がフロントのソースツリーに居座っている**状態である。実害は今のところ小さい（アプリコードが import していないので tree-shaking でバンドルには入らない）が、`KnowledgeSovereignService.ApplyProjectionMutation` のような東西 RPC の完全な記述子がフロントのリポジトリに物理的に存在し、`import` を 1 行書くだけでバンドルに入る状態であることは事実である。しかも `.github/workflows/proto-contract.yaml` は `alt-frontend-sv/src/lib/gen/**` を trigger path に含めているため、この孤児ファイル群は CI の依存グラフにも入っている。

### 6. 一方で、typed end-to-end 契約には実利がある

「RPC 名をフロントから消す」ことだけを目的にすると、connect-es が提供している型安全を捨てることになる。現状 `src/lib/connect/` 配下には 20 以上のラッパモジュールがあり、生成型を使って `alt-backend` のレスポンス構造をコンパイル時に検証している。さらに `alt-frontend-sv/src/test/contracts/` の 9 本の conformance テストは、proto 由来の型を根拠に契約回帰を検出しており、CI の必須チェック "Contract Conformance Tests (FE)" として branch protection に載っている。

これを捨てて BFF に手書き API（GraphQL / REST / tRPC）を切ると、BFF が製品ハンドラを持つ方向、すなわち fat BFF に向かう。[[000954]] は D4 で「独占の対象を拡大解釈すると data-hub を新しいファットサービスに育ててしまう」という論理を明示的に採っており、同じ論理は BFF にも当てはまる。同 ADR は Follow-up で「`orchestrator` の純粋 proxy エンドポイントの BFF 直行化監査」だけをスコープ外の後続作業として残しており、BFF に業務ロジックを移す方向は取っていない。

### 7. 本 ADR の論点は [[000954]] とは別軸である

[[000954]] が扱ったのは **BFF より奥の話**（alt-backend の内部分割と、data-hub が公開する API の形状）である。本 ADR が扱うのは **BFF より手前の話**（フロントエンドと BFF の間の契約が何を明示しているか）である。

| 軸 | [[000954]] | 本 ADR |
|---|---|---|
| 対象境界 | alt-backend ↔ 内部 peer（東西） | ブラウザ ↔ BFF（南北） |
| 問い | DB 状態遷移の所有権をどのプロセスに閉じるか | 公開 API の集合をどこで、肯定形で、機械検証可能に宣言するか |
| 決定物 | プロセス境界・proto 名前空間・mTLS 統制 | フロントが発話する識別子の意味（内部名か公開契約名か） |

両者が交差する点は 1 つだけである — [[000954]] の名前空間移行が、本 ADR の問題を**観測可能にした**こと（§4）。

## Decision

**本 ADR は決定を行わない。** 以下の 3 案を提示し、評価軸を明示するところまでを行う。採否はユーザが判断する。

### 評価軸

1. **統制の形** — 公開面の宣言が肯定形（allowlist）か否定形（deny-list）か。否定形は「新しい内部サービスを足したとき、誰も何もしなければ開く」という失敗モードを持つ
2. **知識の重複** — 「何が公開 API か」の真実が何箇所に手書きされているか（現状 2 箇所：`PROXYABLE_SERVICES` と `serviceToServicePrefixes`。しかも形が違う）
3. **内部改名の波及範囲** — バックエンド内部のサービス改名が、フロントエンドのファイル編集を要求するか
4. **型安全の保持** — connect-es 由来の end-to-end 型と 9 本の FE conformance テストを維持できるか
5. **BFF の肥大** — BFF が製品知識を持つ方向に動くか
6. **「シンプル（率直）」基準** — [[000954]] D3 でユーザが採用した判断基準。「今の形をそのまま持ち上げる（easy）」ではなく「本質を率直に表現している（simple）」ものを選ぶ

### 案 (a): 現状維持 + deny-list 強化

BFF の `serviceToServicePrefixes` を維持し、東西 proto パッケージが増えるたびに追記する。追記漏れを CI で検出する（例: `proto/services/` と `proto/alt/datahub/` 配下のパッケージを列挙し、`serviceToServicePrefixes` に対応 prefix があることを検証するテスト）。

**Pros**
- 変更が最小。プロダクションの経路に一切触れない
- CI ガードを足すだけなので、いつでも他案へ移行できる（他案の前提条件としても有用）
- 既存の型安全・conformance テストに影響ゼロ

**Cons / トレードオフ**
- 統制が否定形のまま。「拒否リストに載っていないものは公開扱い」という既定値は変わらない
- CI ガードは「東西パッケージの命名規約」に依存する。`proto/services/` にも `alt/datahub/` にも属さない第 3 の東西パッケージが将来生まれたら、ガード自体が漏れる
- ユーザの問い（「フロントが RPC 名を知っているのはおかしくないか」）に答えていない。知識の重複（軸 2）と内部改名の波及（軸 3）は残る
- 軸 6 では「easy だが simple ではない」に分類される。症状（漏れる deny-list）に対処し、原因（公開面が宣言されていないこと）に触れない

### 案 (b): 公開サービス allowlist を proto から機械生成し、BFF の既定を拒否にする

「何が公開 API か」を proto 側の 1 箇所で宣言し（ディレクトリ規約、proto の custom option、または明示的な `public_services.yaml` のいずれか）、そこから BFF の Go allowlist とフロントの `PROXYABLE_SERVICES` を**生成**する。BFF の catch-all は deny-list ではなく allowlist で判定し、列挙外は既定で 404。

オプションとして、公開 proto と内部 proto の**名前空間分離を規約化**する（例: 公開は `alt.<domain>.<version>` のみ、東西は別ルート）。これにより「フロントが知っている RPC 名」は**公開契約の名前**になり、内部サービス名ではなくなる。§5 で見た `buf.gen.yaml` の `exclude_paths` は、この規約の 1 パッケージ分の手書き先行実装として自然に吸収される。

フロントは connect-es の typed クライアントを維持する。RPC 名は知り続けるが、それは「公開契約として意図的に安定させた名前」である。

**Pros**
- 統制が肯定形になる（軸 1）。新しい東西サービスは、生成元に載っていない限り**構造的に**通らない。追記漏れという失敗モードが消える
- 真実が 1 箇所になる（軸 2）。BFF とフロントの 2 つの門が同じ生成元から出るので、形の非対称（§2）も解消する
- 名前空間を分離すれば、内部改名がフロントに波及しなくなる（軸 3）。§4 の実例は「そもそもフロントの deny テーブルに東西パッケージが登場しない」形になる
- 型安全と 9 本の conformance テストがそのまま残る（軸 4）
- BFF は依然として透過プロキシであり、製品ハンドラを持たない（軸 5）。[[000082]] の「proto 依存問題の回避」という選定理由とも整合する（BFF が必要なのはサービス名の集合であって、サービス実装ではない）
- 軸 6 では最も simple に近い。「公開 API の集合」という実在する概念に、実在する名前と実在する宣言場所を与える

**Cons / トレードオフ**
- コード生成基盤の追加が要る。`buf.gen.*.yaml` は既に 15 本あり、そこに生成ステップが 1 つ増える
- 名前空間分離まで踏むと、既存の公開パッケージ（`alt.acolyte.v1` / `alt.knowledge_home.v1` など）に対する扱いを決める必要がある。全面リネームは [[000085]] 型の wire path 変更であり、フロント・BFF・backend の同時デプロイか二重 serve 期間を要する。**名前空間分離は必須ではなく、allowlist 生成だけでも軸 1〜3 の大半は取れる**ため、段階を分けられる
- 「公開かどうか」の宣言をどこに置くかの選択が残る（proto の custom option は最も自己記述的だが、buf plugin 側の読み取り実装が要る。ディレクトリ規約は安いが、規約違反を別途検出する必要がある）
- 生成物をコミットするなら、生成漏れを CI で検出する必要がある（`buf generate` 後に `git diff --exit-code`）

### 案 (c): BFF がフロント専用 API を終端し、RPC 名をフロントから完全に消す

BFF に GraphQL / 手書き REST / tRPC のいずれかを実装し、フロントは BFF 固有のスキーマだけを知る。alt-backend の Connect-RPC 名はフロントのバンドルから完全に消える。

**Pros**
- ユーザの問いに最も直接的に答える。フロントは backend の proto 契約を一切知らなくなる（軸 3 が完全に消える）
- BFF が画面単位の集約を持てるようになり、N+1 的な RPC 往復を BFF 側で畳める。既存の `/v1/aggregate` ハンドラと [[000179]] / [[000582]] の BFF キャッシュ路線の延長線上にはある
- 公開面が BFF のスキーマ 1 枚で完全に定義される（軸 1・2 は最も強い形で満たされる）

**Cons / トレードオフ**
- **[[000954]] が採った「独占の拡大解釈でファットサービスを育てない」という論理に正面から衝突する**（軸 5）。BFF は透過プロキシから製品ハンドラの集合になる
- [[000082]] の BFF 選定理由（proto 依存問題の回避、透過プロキシによる実装の単純さ）を覆す。`CLAUDE.md` の BFF Critical Rule 3「Transparent Proxy: Forward requests without modification」も改訂対象になる
- 型安全が「connect-es 生成型」から「BFF スキーマ生成型」に置き換わる（軸 4）。GraphQL / tRPC なら型自体は保てるが、`src/test/contracts/` の 9 本を BFF 契約基準に書き直す必要があり、backend との CDC は BFF ↔ backend 間に移る
- **すべての RPC に BFF 側の手書き対応が要る。** 現在フロントが到達している公開サービスは 14 個、それぞれ複数プロシージャを持つ。新機能のたびに backend と BFF の両方に実装が要る二重実装コストが恒久化する
- 軸 6 では最も easy でない代わりに、「BFF が API 形状を持つ」という新しい責務を導入する点で率直さも増すとは限らない。フロントと backend の間に**もう 1 つの契約**が増える

### 推奨（決定ではない）

**案 (b) 系を推奨する。** 根拠は評価軸に沿って次のとおり。

1. **ユーザの問いの本質は「フロントが名前を知っていること」ではなく「その名前が内部名であること」だと解釈できる。** 公開契約であれば、フロントがその名前を知っているのは正常である（HTTP API のパスをフロントが知っているのと同じ）。異常なのは、`alt.datahub.v1.DataHubService` という**ブラウザから到達不能なサービス**の名前が、フロントのテストファイルに書かれていること（§4）であり、`services.sovereign.v1` の記述子がフロントのソースツリーに置き去りになっていること（§5）である。案 (b) はこの 2 つを直接消す
2. **軸 1（否定形 → 肯定形）が本件の中心的な脆弱性である。** [[000954]] Context が引用した A-1 の教訓、および `rest_allowlist.go` のコメントが述べている「上流が拒否するからではなく、caller-chosen path を転送しないことが要点」という原則は、どちらも「既定を拒否にせよ」と言っている。deny-list はその原則を満たしていない
3. **軸 6（シンプル = 率直）** — [[000954]] D3 でユーザが採った基準に照らすと、案 (a) は「今の形（deny-list）をそのまま補強する」easy な選択であり、案 (c) は「契約層をもう 1 枚足す」ことで率直さを買う代わりに二重実装を恒久化する。案 (b) は「公開 API の集合という既に実在する概念に、宣言場所を 1 つ与える」だけで、新しい概念も新しい層も導入しない。表現していない事実を表現するようにする、という意味で最も率直である
4. **後退可能である。** 案 (b) の第 1 段階（allowlist の機械生成、既定拒否）は案 (c) を排除しない。将来 BFF に集約 API が必要になったとき、公開サービスの列挙は依然として有用な前提になる。逆に案 (c) を先に採ると、透過プロキシへ戻す道は実質閉じる

同時に、推奨に伴うリスクを明示する。案 (b) の名前空間分離部分は [[000085]] 型の wire path 変更を伴うため、**allowlist 生成（軸 1・2 を解決）と名前空間分離（軸 3 を解決）は別々の判断として分けられるべき**である。前者だけを採り、後者は保留するという選択肢が実質的に存在する。

### 決定に必要な追加情報（本 ADR では未取得）

- `proto/services/` と `proto/alt/datahub/` 以外に東西専用パッケージが存在しないことの確認（案 (a) の CI ガード、案 (b) の生成元の網羅性の前提）
- `alt-frontend-sv/src/lib/gen/{services,internal}/` の孤児ファイル群を削除した場合の CI 影響（`proto-contract.yaml` の trigger path に含まれている）
- 公開判定を proto custom option で表現する場合の buf plugin 実装コスト
- BFF の `/v1/` REST 面（[[000729]] Phase 3 未着手、現在は警告ログのみ）を同じ枠組みに載せるか、別 ADR に分けるか

## Consequences

本 ADR は Proposed であり、それ自体はコード・compose・CI のいずれも変更しない。以下は**論点を ADR として明文化したこと**の帰結である。

### Pros

- ユーザの問いが、感覚的な違和感から**測定可能な 6 軸**へ変換された。以後の議論は「おかしいかどうか」ではなく「どの軸で何点か」で進められる
- 現状の統制が肯定形と否定形に分裂していること（§2）、および REST 面はそもそもゲートしていないこと（`allowRESTPath` が警告のみ）が、コードの実測として記録された。これは本 ADR の採否と無関係に有効な事実である
- `alt-frontend-sv/src/lib/gen/{services,internal}/` の孤児生成物（§5）という、どの案を採っても掃除すべき残債が可視化された
- [[000954]] との軸の違い（§7）を明示したことで、「BFF に製品ハンドラを持たせる案は既に棄却済みでは」という混同を防いだ。本 ADR の案 (c) は確かにその棄却と衝突するが、案 (a)/(b) は衝突しない

### Cons / Tradeoffs

- **Proposed のまま放置されると、現状（案 (a) の CI ガードすら無い状態）が既定になる。** deny-list の追記漏れリスクは本 ADR を書いても減らない
- 論点を分割した（allowlist 生成と名前空間分離を別判断にできると述べた）ことで、**部分採用のまま止まる**可能性がある。allowlist 生成だけを採ると軸 3（内部改名の波及）は残り、「フロントが内部 RPC 名を知っている」というユーザの問いへの回答は部分的なものにとどまる
- 案 (b) を採る場合、`buf.gen.*.yaml` は既に 15 本あり、生成テンプレートの増加自体が別種の複雑さになる。生成物の同期漏れを CI で検出する仕組みが同時に要る
- 本 ADR は BFF の `/v1/` REST 面を意図的にスコープ外にした（[[000729]] Phase 3 の未着手分）。Connect 面だけ既定拒否にして REST 面が素通しのままなら、境界としては依然として片肺である

## Deploy-model 整合性セルフチェック

本 ADR は compose service / volume / deploy pattern を一切変更しない（Proposed の論点整理であり、コード変更を伴わない）。

- [ ] 新設 compose service が `depends_on` で他 service を gate するか？ — **N/A**（新設 service 無し）
- [ ] 新設 compose service に `restart: "no"` の one-shot init container を含むか？ — **N/A**（新設 service 無し）
- [ ] 新設名前付き volume を populate する責務はどこにあるか？ — **N/A**（新設 volume 無し）
- 結論: **N/A / rolling 互換**。なお本 ADR の案 (b) を将来採用する場合、追加されるのはコード生成ステップと CI ガードであり、いずれもランタイムのプロセス構成を変えないため rolling deploy model への影響は生じない見込みである。案 (c) を採用する場合は BFF のイメージが実質的に別物になるため、その時点で改めて本チェックを行うこと。
