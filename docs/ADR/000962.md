# ADR-000962: Web Push のために push 専用 service worker を fetch ハンドラなし・Cache Storage 不使用で登録する

## Status

Accepted

本 ADR は [[000898]] を**置換しない**。同 ADR の Decision は現在も完全に有効であり、コードもそのまま生きている。本 ADR が触れるのは、同 ADR の Context に書かれた「取り下げた仮説」一行の**前提**だけである。よって frontmatter に `supersedes` は書かない。

## Date

2026-08-09

## Affected Services

- alt-frontend-sv (TypeScript / Svelte 5) — `src/service-worker.ts`、`src/app.html`、`static/manifest.webmanifest`、`src/lib/push/*`
- nginx — 変更なし（既存 stale chunk 防御の前提確認のみ）

## Context

### 1. iOS の制約が worker の登録を強制する

iOS では **Web Push は Home Screen web app にのみ、かつ service worker 経由でのみ配送される。** 他の機構は存在しない。通常の Safari タブには `PushManager` がそもそも露出しない。したがって「通知を出す」という機能を持つのであれば、service worker の登録は設計上の選択肢ではなく**前提条件**である。

このため manifest は `display: standalone` を宣言し、`app.html` は `apple-mobile-web-app-capable` を併記している。ブラウザ chrome 付きで起動した web app は iOS で PushManager を静かに失うため、standalone 起動そのものが通知の可用性条件になる。インストール状態の判定 (`src/lib/push/install-state.ts`) が `navigator.standalone` / `display-mode: standalone` / `display-mode: fullscreen` の 3 signal を見ているのも同じ事情で、インストール済み iOS web app は WebKit bug 264218 により *fullscreen* を報告する。

つまり設計上の問いは「worker を登録するかどうか」ではない。**stale asset の失敗クラスを買い戻さずに、その代金をどう払うか**である。

### 2. [[000898]] の却下根拠が、この登録によって古びた

[[000898]] は iOS Safari の "Cannot Open the Page" を調査した ADR で、その「取り下げた仮説」節（L69）は次のように書いている。

> Service Worker / Cache Storage 既知 bug: 本リポジトリは Service Worker を登録していない (grep で 0 件)。

**この前提は本変更で偽になった。** 登録それ自体が障害を再導入するわけではない。しかし仮説を却下した**論拠**は、もはやそれ自身の言葉のままでは成立しない。ここが本 ADR を書く理由の核心である。再発をデバッグする将来の読者が、古びた事実から「Cache Storage は無関係」という結論を再導出してはならない。

その前提を置き換えるものは以下である。

- **worker は `fetch` event handler を持たない。** したがって network request に一切介入しない。仕様上、fetch listener を持たない worker は navigation および subresource fetch について**完全に bypass される**。介入しないことは実装上の努力目標ではなく、仕様の帰結である。
- **worker は Cache Storage を使わない。** したがって stale な module map を保持する場所そのものが存在しない。

### 3. 既存の防御層はすべて「network が authoritative」を前提にしている

[[000898]] / [[000902]] が積んだ層は次のとおりで、どれも「最新の真実はサーバにある」ことを前提に組まれている。

- HTML は `no-cache, must-revalidate` で配られる（[[000902]] L4 / [[000412]]）
- `updated.check()` が deploy された version を polling し、差分があれば reload する（[[000898]] / [[000902]] L5）
- `app.html` の inline bootstrap が chunk 404 を capture phase で拾って reload する（[[000902]] L2）
- nginx が `/_app/immutable/*.{js,mjs}` の 404 を 200 の reload stub に倒す（[[000902]] L1）

**caching worker はこのすべての前に座る。** `docs/wiki/operations/ios-safari-defense.md` は Layer 2 の存在理由を説明する箇所で、拾うべき経路として「SW から来た fetch」を明示的に名指ししている。worker が存在しなかった時点で書かれた文章だが、層の設計はもともと service worker 由来の fetch を leak path として想定していた。

失敗の**性質**が変わる点が重要である。現在の失敗は自己治癒する — chunk 404 は reload 1 回で新 HTML → 新 chunk に解決する。precache を持つ worker が前に座ると、その worker 自身が更新されるまで evicted な module map を供給し続けうる。iOS Safari においてそれは「タブが死んだまま戻らない」を意味し、リロードボタンも効かない経路に入る。**自己治癒する失敗を恒久的な失敗に変える**のが、caching worker の実際のコストである。

### 4. Declarative Web Push を使う理由

push payload の wire format は Declarative Web Push (`{ web_push: 8030, notification: … }`) を採る。Safari はこの形を native に描画でき、service worker が通知の表示に失敗した場合でもそれにフォールバックする。これが効く理由は防御的ではなく実利的である — **Safari は何も表示しなかった push に対して、サイトの通知許可そのものを剥奪する。** Chrome / Firefox は envelope を無視して同じ JSON を自前の `push` handler で読むため、単一 payload が全ブラウザに供給される。

同じ理由から `parsePushPayload` は throw せず空 title も返さない。`push` handler 側も payload の読み取り失敗を汎用通知に degrade させる。すべての経路が「表示可能な通知」で終わる必要がある。

## Decision

**Web Push を受け取ることだけを目的とした service worker を登録し、その worker には `fetch` event handler を置かず、Cache Storage も一切使わないことを採用する。**

### D1. worker の構成

`alt-frontend-sv/src/service-worker.ts` が持つ listener は `install` / `activate` / `push` / `notificationclick` の 4 つだけである。`fetch` は無く、`caches` API への参照も無い。

`install` で `skipWaiting()`、`activate` で `clients.claim()` を呼ぶ。**これが安全なのは worker が `fetch` に応答しないからである** — client を claim しても、ページが network から受け取るものは何ひとつ変わらない。「古い worker が古い応答を返し続ける」という service worker の典型的な事故は、応答する経路が存在しない以上、起こりようがない。

`notificationclick` の遷移先は same-origin に閉じる。文字列の prefix 検査では足りず、WHATWG parse 後の origin で判定する（`.claude/rules/security-boundaries.md`）。通知タップはユーザが URL を打っていない navigation であり、payload は暗号化されて届くが「送信者が入れたもの」以上の意味を持たない。

### D2. [[000898]] の却下根拠を差し替える

[[000898]] の Cache Storage 仮説の却下は、今後「本リポジトリは worker を登録していない」ことにではなく、**本 ADR が課す制約（fetch に介入しない / Cache Storage を持たない）**に依拠する。[[000898]] 本文の Decision は改変しない（vault のルール）。再発調査時にはこの ADR を併せて読むこと。

### D3. Declarative Web Push を採る

§4 のとおり。worker が通知を出せない場合に Safari が native に描画する経路を確保することが目的であり、Chrome / Firefox 向けの payload を別に持たないことは副次的な利得である。

### D4. [[000898]] / [[000902]] の層はコード上そのまま温存する

削除も簡素化もしない。本 ADR の変更は追加のみで、8 層のいずれにも触れていない。

### 検討した代替案と却下理由

**(a) app-shell を precache する worker（Workbox 等の precache + runtime cache）— 却下。**
オフライン起動と体感速度という正当な利得がある。しかし precache manifest は build 時点の chunk hash 一式を保持するため、worker が更新されない限り evicted な module map を**無期限に**供給しうる。そしてそれは [[000898]] / [[000902]] の 8 層すべての前に座る — HTML の `no-cache` も、`updated.check()` の polling も、bootstrap の 404 検知も、nginx の 200 stub も、cache hit したリクエストには一度も到達しない。§3 のとおり、これは自己治癒する失敗を恒久的な失敗に変える取引である。得られるオフライン体験の側も小さい: 本アプリの記事本文・要約・Trail はいずれもサーバ側にあり、shell だけをオフラインで出しても中身が無い。

**(b) worker を登録しない — 却下。**
最も安全な選択だが、iOS における Web Push を完全に放棄することになる。そしてそれが今回やろうとしていることそのものである。§1 のとおり iOS には代替の配送機構が存在しないため、これは「通知機能を作らない」と同義であり、決定を回避しているだけで選択にはなっていない。

**(c) すべてを素通しする `fetch` handler を置く（`event.respondWith(fetch(event.request))` あるいは `respondWith` を呼ばない handler）— 却下。**
正直に評価すると、これは実質的にほぼ no-op であり、(a) のような失敗モードを直ちに導入するわけではない。それでも採らない理由が 3 つある。

1. **介入経路が有効になる。** handler を置いた時点で仕様上の bypass 最適化が失われ、navigation / subresource が worker の起動を待つようになる。「介入しない」が仕様の帰結ではなく実装の中身に依存する性質に変わる。
2. **将来の caching 行を誘う。** 素通し handler の中に cache を足すのは 3 行の変更であり、そこに至るまでの摩擦がレビューしかない。空の handler は「ここに書け」という招待状である。
3. **規約としての検査可能性が違う。** 「`fetch` handler を持たない」は grep 一発で機械的に検査できる。「何もしない `fetch` handler」は静的に検査できない — 何もしないことの定義が要る。ルールは検査可能な形で述べるほうが強いという論法は、このリポジトリが [[000961]] や `alt-backend/app/di/import_boundary_test.go` で既に採っているものである。

## Consequences

### Pros

- **当初の目的（iOS で通知を出す）を、stale asset の失敗クラスを買い戻さずに達成する。** worker は代金であって、機能ではない。
- **8 層防御の前提が保たれる。** worker が `fetch` に介入しない以上、HTML の `no-cache` も version polling も bootstrap の 404 検知も nginx の reload stub も、従来どおり同じ条件で効く。
- **「介入しない」が仕様の帰結である。** fetch listener を持たない worker は navigation / subresource について完全に bypass される。実装の注意深さに依存する保証ではない。
- **`skipWaiting()` + `clients.claim()` を副作用なく使える。** 応答する経路が無いので、claim による「古い worker が居座る」事故が構造的に起きない。新しい worker は次の起動を待たずに push を受け取れる。
- **通知許可を失う経路を閉じている。** Declarative Web Push により、worker が `showNotification` に失敗しても Safari が native に描画する。何も表示しない push で許可が剥奪される事故が起きにくい。
- **worker script 自体が cache に固定されない。** `/service-worker.js` は nginx の catch-all `location /`（`Cache-Control: no-cache`）で配られるため、置き換え版が古い cache に阻まれない。
- **検査が安い。** `src/service-worker.ts` に `fetch` が現れないことは、レビューでも CI でも同じコストで確認できる。

### Cons / Tradeoffs

- **[[000898]] の Cache Storage 仮説の却下は、もはや「worker が存在しない」という事実にではなく、本 ADR が課す制約に依存する。** 根拠が「観測された事実」から「維持すべき制約」へ移った。事実は変わらないが、制約は破られうる。この移動そのものがコストである。
- **`fetch` handler の追加を機械的に防ぐものが無い。** 現状あるのは `src/service-worker.ts` の doc comment と `tests/e2e/mobile/pwa/installability.spec.ts` のコメントだけで、後者が assert しているのは worker が activated に到達することであって、`fetch` handler の**不在**ではない。`.claude/rules/` にも該当規約は無い。この空白は意図的に本 ADR のスコープ外に置く。塞ぐなら `import_boundary_test.go` と同型の静的 assertion（build 後の worker bundle に fetch listener が現れないこと）が自然な形である。
- **iOS Safari 自身の Cache Storage 挙動は、このプロジェクトが制御しないプラットフォームリスクとして残る。** 本 ADR が保証するのは「Alt が Cache Storage を使わない」ことだけである。WebKit が worker や storage をどう扱うか（eviction、storage 上限、bfcache との相互作用）は外部要因であり、[[000898]] の当該仮説は「Alt のコードが原因ではない」という形でしか閉じない。
- **worker は deploy より長生きする。** 一度端末に install された worker は、ブラウザの update check で置き換わるまで残る。壊れた worker を出荷した場合の回復は新 worker の activate に依存し、`skipWaiting` / `claim` はその窓を縮めるが消しはしない。
- **登録が暗黙である。** SvelteKit は `src/service-worker.ts` の存在を見て自動登録する（`kit.serviceWorker.register` の default が true）ため、`navigator.serviceWorker.register(` を grep しても 0 件になる。[[000898]] が「grep で 0 件」を根拠に判断したのとちょうど同じ形の落とし穴が、向きを変えて残っている。
- **通知は Home Screen にインストールした利用者にしか届かない。** `isInstalled` の 3 signal はいずれも heuristic であり、WebKit bug 264218 のように仕様と実装がずれれば誤判定しうる。インストールしていない利用者にとって、この worker は何もしないコードとして常駐する。

- [x] 新設 compose service に `restart: "no"` の one-shot init container を含むか？ — **N/A**
- [x] 新設名前付き volume を populate する責務はどこにあるか？ — **N/A**（volume 新設なし）
- [x] いずれも該当しない: **rolling 互換** と明記して pass

本 ADR の変更は `alt-frontend-sv` の application code と static asset に閉じている。rolling deploy 時の挙動:

- `/service-worker.js` は content hash を持たない安定 URL で配られるため、deploy によって 404 になることがない（`/_app/immutable/*` とはこの点が異なる）。nginx の catch-all `location /` 経由で `Cache-Control: no-cache` が付くため、新 worker はブラウザの次回 update check で取得される。
- 旧 worker が動いている端末に新 build が届いても、旧 worker は `fetch` に応答しないので、そのタブが取得する HTML / chunk は常に新しいサーバの応答である。**worker の更新遅延が asset の鮮度に影響しない**ことが、本決定の rolling 互換性の実体である。
- `manifest.webmanifest` と `/icons/*` も同様に安定 URL の static asset であり、rolling 中の中間状態で壊れる組み合わせが無い。
