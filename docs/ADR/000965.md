# ADR-000965: 実 PostgreSQL に対する integration tier を alt-data-hub の driver に導入し、supersede の相互打ち消しを塞ぐ

## Status

Accepted

## Date

2026-08-09

## Affected Services

- alt-data-hub (Go)
- alt-backend (Go)
- release pipeline（self-hosted 側の build / e2e）

## Context

### テストの階層に穴があった

`shared/driver/alt_db` の driver は pgxmock だけで覆われていた。pgxmock は記録した
スクリプトを再生する。発行された SQL 文字列と引数が呼び出し側の意図どおりかは証明できるが、
**サーバがそれをどう扱うかは一切見えない**。ロック、制約、トランザクション可視性、そして
migration 適用後のスキーマそのものが射程外になる。

CI 側も同じ形をしていた。`reusable-test-{go,rust,python,deno}.yaml` に `services:` ブロックは
一つも無く、実 DB を使うテストは CI に存在しない。unit と full-compose E2E の間が空洞で、
実 SQL・migration・トランザクション境界の検証は E2E でしか行われていなかった。

`integration` build tag 自体は以前から存在したが、**どのワークフローからも実行されていなかった**。
`integration_tests/` は書かれて以来一度も走っておらず、現在は bit-rot して落ちる
（backend token を渡さずに Connect handler へ feed を要求し成功を期待している）。
「タグはあるが誰も回さない」状態が、そのまま tier 不在と同義だった。

### 穴に落ちていたもの

tier を作って最初に当てた `tag_set_versions` の supersede が、並行時に不変条件を破っていた。
3/3 で再現し、**非 supersede の版が 0 件**になる。

```
v1 が既存。2 つの再生成が v2 / v3 を INSERT した後、両者が supersede に入る。
A(v2): 自分以外の非 supersede 行を全部 v2 で supersede → v1, v3 が v2 を指す
B(v3): 自分以外の非 supersede 行を全部 v3 で supersede → v2 が v3 を指す
結果: 全行が successor を持ち、superseded_by IS NULL は空
```

`pg_advisory_xact_lock` は 2 つのトランザクションを直列化していた。直列化は必要だったが
十分ではなかった。UPDATE の述語が `superseded_by IS NULL AND <id> != $1` ——「自分以外の全行」
—— だったため、**自分より後に生成された版まで supersede する**。直列化された 2 つの呼び出しが
順番に相手を打ち消し、記事は「要約もタグも生成に成功したのに現在版が無い」状態になる。

この race は `summary_version_repository_test.go` の doc comment が明示的に警告していたもので、
advisory lock はその対策として入っていた。lock は入ったが、集合の意味論は直っていなかった。
そして pgxmock はスクリプトを再生するだけなので、**その期間ずっと緑を報告し続けていた**。

競合ウィンドウは実運用の方が広い。`CreateTagSetVersionUsecase.Execute` は
INSERT → knowledge event の append → supersede の順に進むので、2 つの INSERT が
どちらの supersede よりも先に完了するのは例外ではなく通常の並びになる。

二次的な欠陥も同時に出た。既に新しい版に敗れた版が supersede を呼ぶと、`prev` として
**自分より新しい版**を返す。呼び出し側はそれを根拠に `TagSetSuperseded` /
`SummarySuperseded` を emit するので、起きていない置換が event log に business fact として
残る（append-first 違反）。さらに、敗れた版自身は supersede されないまま残るため、
現在版が 2 件になる。

### CI の image ラウンドトリップ

release pipeline の e2e leg を計測したところ、Ansible 実行時間の 43% が image pull だった。
build job と e2e job は同じ self-hosted runner ラベルの上で、**同一の Docker daemon** を
共有している。にもかかわらず build は buildx の `docker-container` driver で registry へ
push するだけで、daemon の image store には何も残らない。e2e は直後に同じ image を
GHCR から取り直していた。ホストから一度も出ていないバイトを、ネットワーク越しに往復させていた。

pre-pull 側も `force_source: true` で、ローカルに同一 digest があっても必ず registry を叩く。

## Decision

### 1. `shared/driver/alt_db` に integration tier を新設する

`test_utils/pgtest` を追加し、`//go:build integration` の下で実 PostgreSQL に対して driver を回す。

- **テストバイナリごとにコンテナ 1 つ。** migration は 1 回だけ適用し、その DB を template にする。
  `NewDB` は毎回 `CREATE DATABASE ... TEMPLATE` で複製する。PostgreSQL はこれをファイルコピーで
  行うので、100 本超の migration を再生せずに同一スキーマから始められる。テストは行を共有せず、
  並行実行できる。
- **スキーマは committed な Atlas history をそのまま適用する。** 手書きの schema dump ではなく、
  deploy される migrator image と同じ Atlas バージョン・同じ migration ディレクトリを使う。
  「既にデータがある DB でしか通らない migration」はここでも落ちる。
- **role fixture は staging と同じものを使う。** migration history は自身が作らない role
  （`tag_generator`, `search_indexer_user` 等）に GRANT する。deploy されるスタックは
  entrypoint の init ディレクトリでそれを満たしているので、harness も同じ fixture ファイルを
  読む。二つ目のリストを持つと、GRANT が増えた最初の一回で乖離する。
- **image は staging と同じものに pin する。** `postgres:17-alpine` と Atlas のバージョンを
  compose と migrator Dockerfile に合わせる。

検討して採らなかった代替:

- **schema dump を読み込む** — 速いが、migration が空の DB から通るかを検証できない。
  今回 harness が最初に見つけたのは role 不在で migration が止まる差分そのもので、
  dump 方式ならこれを見逃していた。
- **CI の service container（`services:` ブロック）** — GitHub Actions の
  `services:` は job 全体で 1 インスタンス固定になり、per-test の template 複製が使えない。
  また harness をローカルで再現できない（`make test-integration` が CI と別物になる）。
- **Testcontainers の container reuse** — 公式ドキュメントが CI 非推奨と明記しており、
  reuse の意味が言語ごとに違う。多言語 monorepo で依存すべきではない。
- **既存 `integration_tests/` を復活させて相乗り** — bit-rot の修復は別の作業で、
  tier の導入とは独立している。CI job の対象パッケージを明示的に絞り、除外理由を
  ワークフローのコメントに残した（silent skip にはしない）。

### 2. supersede の述語を「自分以外」から「自分より古い」に変える

`MarkSummaryVersionSuperseded` / `MarkTagSetVersionSuperseded` を次の形にする。

- 対象行を `(generated_at, <version_id>) < (新版の generated_at, 新版の id)` で選ぶ。
  id をタイブレークに入れるのは、同一瞬間に stamp された 2 版でも順序が決まるようにするため。
- 新版より**新しい**非 supersede 版が既にある場合は、新版自身がその勝者を指す。
  supersede は行わず、`prev` は nil を返す。呼び出し側は起きていない置換の event を emit しない。
- 新版の id が実在しない場合はエラーにする。silent no-op にすると、記事の要約／タグが
  凍りついたまま何も言わない状態になる（Rule 8）。

advisory lock は残す。lock を外すと SELECT と UPDATE の間に割り込みが入り、`prev` が
実際には supersede しなかった行を指しうる。

検討して採らなかった代替:

- **部分 UNIQUE INDEX（`WHERE superseded_by IS NULL`）で DB に強制させる** —
  新版は `superseded_by = NULL` で INSERT され、その時点で旧版もまだ NULL なので、
  INSERT 自体が通らなくなる。INSERT と supersede を 1 トランザクションに畳む前提が要り、
  RPC 境界の設計（[[000954]] Wave 3 batch 5）を作り直すことになる。
- **到着順で supersede する（現状維持 + lock 強化）** — 遅れて届いた古い版が
  新しい版を上書きする。versioned artifact の「最新」が生成順ではなく到着順で決まり、
  reproject で結果が変わる。

### 3. build した image を daemon にも load し、immutable タグの再 pull を止める

- build job の exporter を `push: true` から `type=registry` + `type=docker` の 2 系統にする。
  後者はローカルの tarball ストリームで、ネットワークを使わない。
- e2e の pre-pull は `sha-<short>` のとき `force_source` を false にする。このタグは
  1 コミットのビルドを指し、動かない。ローカルにあるものが求めているものである。
- `main` は mutable なので force を維持する。regression leg は production が実際に
  serve しているものを試すために存在する。速度と引き換えにここを緩めると、
  古い image で緑になった leg と新しい image で緑になった leg が区別できなくなる。
- pull 後に解決した digest を notice として出す。`main` leg の遅さがタグの移動によるものか、
  ホスト側の GC による layer 破棄によるものかは、外からは同じに見える。digest が
  run 間で安定していれば前者ではないと判る。この切り分けは測定であって判定ではないので、
  値で赤にはしない。

## Consequences

### Pros

- pgxmock では原理的に届かない性質（ロック、制約、トランザクション可視性、適用済みスキーマ）が
  CI で検証されるようになった。導入直後に、本番に入っていた不変条件違反を 1 件、
  その二次影響を 2 件検出している。
- migration history が「空の DB から通る」ことが PR 時点で保証される。今回 harness が
  最初に落ちた 2 箇所は、どちらも staging の環境変数と init fixture に暗黙依存していた箇所だった。
- versioned artifact の不変条件（記事は現在版をちょうど 1 つ持つ）が、
  片方の table だけでなく `summary_versions` / `tag_set_versions` の両方で
  実サーバに対して固定された。
- 起きていない置換の event が emit されなくなり、event log の business fact が
  実際に起きたことだけを表すようになった。
- CI 上の実行時間は container 起動と 118 本の migration 適用を含めて 1 桁秒台に収まる。
  template 複製が効いているため、テストを増やしても migration の再生コストは増えない。
- release pipeline で、その release がビルドしたサービスの image ラウンドトリップが消える。

### Cons / Tradeoffs

- CI job が Docker daemon に依存する。GitHub-hosted runner では利用できるが、
  daemon の無い環境ではこの job は動かない。
- `main` タグの regression leg の pull コストは**手つかず**のまま残る。計測した pull 時間の
  9 割はこちら側で、原因（タグの移動か GC による layer 破棄か）は CI ログからは判別できず、
  runner ホスト側の実測が要る。推測で `force_source` を落とすと stale image で緑になるため、
  今回は digest の記録だけを入れて判断を保留した。
- `integration_tests/` は bit-rot したまま残る。CI job の対象から明示的に外してあるが、
  復旧されるまでこのパッケージのカバレッジは無い。
- supersede が 1 トランザクションあたり SELECT を 1 本増やす。advisory lock 保持中の
  主キー lookup なので実測できる差にはならないが、round trip は増えている。
- pgxmock 側のテストは SQL の形を pin しているため、この種の変更のたびに更新が要る。
  今回は 2 ファイルを書き直した。実セマンティクスが integration tier に移ったので、
  mock 側の役割はトランザクションの構造に絞った。
- tier があるのは alt-data-hub の driver だけで、他サービス（auth-hub, pre-processor,
  search-indexer, mq-hub）は依然 unit と E2E の 2 層のまま。

## Deploy-model 整合性セルフチェック

本 ADR は compose service を新設せず、deploy pattern も変更しない。テストハーネスが起動する
コンテナはテストバイナリのライフサイクル内で完結し、prod スタックには存在しない。
release pipeline の変更は build の exporter と e2e の pre-pull 条件のみで、
サービスの起動順序・依存関係・volume には触れていない。

- rolling 互換（compose / deploy pattern への変更なし）
