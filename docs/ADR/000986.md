# ADR-000986: external_content の membership を「返す前に第三者を待つか」と明文化し ResolveOgImages / RegisterRSSFeed を分類する

## Status

Accepted

## Date

2026-08-28

## Affected Services

- alt-butterfly-facade (Go) — `internal/resilience/dependency_class.go` の分類テーブルとその判定条件

## Context

[[000959]] §2 が `ClassExternalContent` を新設したとき、メンバーは
`ArticleService/FetchArticleContent` の 1 本だけだった。条件そのものは
`dependency_class.go` が自らの doc comment に書いている。

```go
// Membership requires an outbound fetch on the response path — an RPC that
// merely returns a URL pointing at a third party stays non-critical.
```

**条件は書かれたが、全数には適用されていなかった。** この条件を満たすのに未分類のまま
残っていた public Connect RPC が 2 本ある。未分類は `ClassNonCritical` に落ち、
内部依存向けの予算（`CBFailureThreshold: 5` / `CBOpenTimeout: 30s`）が当たっていた。
外部向けの予算は `CBExternalContentFailureThreshold: 20` /
`CBExternalContentOpenTimeout: 5s`（`config/config.go`）である。

### `ResolveOgImages` — 1 RPC の中で最大 10 出版社を待つ

`og_image_resolve_usecase.Execute` は、まだ画像を持たないフィードごとに
`OgImageFetcher.FetchOgImage` を呼ぶ。`og_resolve_gateway` は `WaitForHost` で
per-host の politeness スロットを待ってから robots.txt と出版社のページを取りに行く。
これが **RPC を開いたまま、インラインで**走る。`MaxBatch = 10` なので、1 回の viewport
変更が最大 10 出版社との往復を 1 本の RPC に詰め込む。

失敗の写り方は `FetchArticleContent` と違う。フィード単位の fetch 失敗は usecase が
`unresolved` に畳んで 200 で返すので、出版社の 404 / 403 が 5xx になることはない。
breaker を叩くのは**バッチ全体が BFF のデッドラインを追い越したとき**で、この経路は
`bff_handler.go` の transport error 分岐にあたり、ヘッダによる帰属判定の余地なく
`recordFailure(endpoint)` が無条件に走る。

```go
resp, err := h.backendClient.ForwardRequest(newReq, token)
if err != nil {
    h.recordFailure(endpoint)   // ← 帰属ヘッダを見る前
    return nil, err
}
```

つまり**自分のホストスロットに並んだだけ**で失敗が 1 つ計上され、5 回続けば og:image
解決が 30 秒暗転する。[[000959]] §4 が `FetchArticleContent` の裏で見つけた自己 DoS
ループと同型で、増幅の形は [[000884]] が先読み 10 件に対してクライアント側で見たものと
同じものが 1 RPC の中に入っている。

### `RegisterRSSFeed` — Step 1 が外向き境界

`RegisterFeedsUsecase.Execute` の 1 行目が
`r.validateAndFetchPort.ValidateAndFetch(ctx, link)` で、DB 書き込み
（`RegisterFeedLink`）は Step 2 以降にしかない。登録先の RSS を取り終わるまで
レスポンスは返らない。gateway 自身のコメントが
`This is the external HTTP boundary for feed registration` と名乗り、
`rateLimiter == nil` で panic する（CLAUDE.md rule 2 のゲートが production では必ず
経路上にあることを、起動時に保証している）。この「1 回だけ fetch する」形は
[[000331]] が二重 fetch を排したときに作ったものである。

**これが仮説でないことも確認した。** usecase は fetch 失敗を素の
`errors.New("failed to register RSS feed link")` に潰す。したがって
`HandleUpstreamError` は chain に Connect code を見つけられず
`HandleInternalError` に落ち、`CodeInternal` = HTTP 500 になる。rss ハンドラは
`X-Alt-Failure-Scope` を stamp しない（stamp しているのは articles ハンドラだけ）ため、
BFF 側で `IsDependencyFailure(500) && !IsUpstreamAttributed` が成立する。

**出版社の障害が、いま alt-backend の失敗として記録されている。**

### 外向き境界の全数調査

alt-backend で `HostRateLimiter` を使う gateway は 6 つ。

| gateway | public Connect RPC | 分類 |
|---|---|---|
| `fetch_article_gateway` | `FetchArticleContent` | [[000959]] で分類済み |
| `og_resolve_gateway` | `ResolveOgImages` | **本 ADR** |
| `validate_fetch_rss_gateway` | `RegisterRSSFeed` | **本 ADR** |
| `fetch_feed_gateway/feeds_gateway` | なし（harvester のジョブ経路） | 対象外 |
| `fetch_feed_gateway/single_feed_gateway` | なし（同上） | 対象外 |
| `rate_limiter_gateway` | なし（共有 limiter そのもの） | 対象外 |

public RPC に露出しているのは 3 つで、**この変更で 3 つとも揃った**。

## Decision

### 1. 判定条件を明文化する

`external_content` の membership は「**第三者サイトの画像や URL を扱うか**」ではなく
「**返す前にそれを待つか**」である。この一文を `dependency_class.go` のコメントと
テストの両方に固定する。

near-miss を対照として明記した。3 件とも「第三者の URL を扱う」を満たすが、
「返す前に待つ」を満たさない。

| near-miss | 待たない理由 | 出所 |
|---|---|---|
| `BatchPrefetchImages` | 保持済みの行から署名付き proxy URL を作るだけで、response path で出版社に触れない | [[000959]] §2 が「移さない」と明記 |
| `BatchPrefetchArticleContent` | 受理レシートを返してから detached で fetch する | [[000982]] が telemetry に置いた |
| `RegisterFavoriteFeed` | 同じくフィード URL を受け取るが DB 参照だけ。ハンドラが SSRF チェックを省く理由として自ら "it does not make external requests" と書いている | 本 ADR のテストで固定 |

`RegisterFavoriteFeed` は同一サービス（`RSSService`）の隣にいる分だけ対照として強い。
「フィード URL を受け取る RPC」で括ると一緒に動いてしまうが、条件は括らない。

### 2. `ResolveOgImages` を `external_content` に入れる

返すステータスとレイテンシが報告しているのは第三者の健康状態と自前のレート制限
ゲートで、[[000959]] が alt-backend の failure budget から外したのはまさにその 2 つ
だった。閾値は 5 → 20、open は 30 秒 → 5 秒になる。再プローブが速いことの根拠は
[[000959]] §2 と同じで、次の viewport はたいてい別の出版社である。

### 3. `RegisterRSSFeed` を `external_content` に入れる

頻度が全く違う（読者のスクロールごとに走る経路と、ユーザが 1 URL を登録する低頻度の
操作）ことは反論として正当なので、答えを残す。

**当初の懸念は逆だった。** `FailureThreshold` は `circuit_breaker.go` の
`consecFailures` に対する閾値で、**連続**失敗を数え、成功で 0 にリセットされる。

```go
cb.consecFailures++
if cb.consecFailures >= cb.config.FailureThreshold { /* open */ }
// RecordSuccess 側: cb.consecFailures = 0
```

したがって**低頻度のエンドポイントこそ専用 breaker で過敏になる**。`RegisterRSSFeed`
は現状 `nonCritical.forEndpoint()` が配る閾値 5 / open 30 秒の専用 breaker に載って
おり、カウンタを戻す成功トラフィックがほぼ無い。**1 人が死んだ URL を 5 回リトライ
するだけで、30 秒間すべてのユーザーの登録が 503 になりうる。** 共有 breaker に移せば、
高頻度な og:image 解決 / 記事取得の成功が常時 `consecFailures` を戻すので、登録失敗が
単独で 20 に到達することは実質なくなり、開いたときの拒否も 5 秒で済む。

閾値 20 が「登録の異常検知」として緩すぎるのはその通りだが、検知はこの予算の仕事では
ない（遷移ログとメトリクスの仕事）。この予算の仕事は「第三者の失敗を自分の障害として
数えない」ことである。

### 4. 代償を明記する

`ClassExternalContent` は `nonCritical.forEndpoint()` と違い、**クラス全体で単一の
共有インスタンス**（`bff_handler.go` の `externalContentCB` フィールド）である。
つまりこの変更は「独立 breaker → 共有 breaker」への移動であり、`ResolveOgImages` /
`FetchArticleContent` / `RegisterRSSFeed` が 1 つの breaker を相乗りする。

方向としては両方向に改善する。登録は 20 連続失敗を単独で積むには低頻度すぎて reads を
巻き込みにくく、reads 側が開いたときに登録が拒否される時間は現状の 30 秒から 5 秒に
なる。それでも「相乗り」であることは事実なので Cons に残す。

### 却下した代替案

| 案 | 却下理由 |
|----|----------|
| `RegisterRSSFeed` に第 4 のクラス（専用 breaker）を与える | 低頻度エンドポイントを単独 breaker に置くこと自体が今回の問題。クラスを増やしても `consecFailures` がリセットされない構図は変わらない |
| `RegisterRSSFeed` を breaker 対象外にする（telemetry と同様） | telemetry の免除は「呼び出し側が結果を捨てる」ことに対する免除であって、外向きであることに対する免除ではない（[[000982]]）。ユーザは登録の成否を待っている |
| `ClassNonCritical` のまま閾値だけ上げる | [[000959]] が既に却下した「一律で上げる」と同じ。内部依存の検知が鈍る |
| 先に usecase の `errors.New` を型付けし直す | 正しい方向だが層が違う。**分類は「どの予算に載せるか」、stamp / code は「その予算から外すか」**。分類の適用漏れは分類側で塞ぐ。型付けは別の変更として Cons に残す |
| `RSSService` 全体を移す | `RegisterFavoriteFeed` / `ListRSSFeedLinks` / `DeleteRSSFeedLink` などは alt-db しか触らない。サービス単位の括りは条件ではない |

## Consequences

### Pros

- `dependency_class.go` が doc comment で宣言していた membership 条件が、初めて
  **全数に適用された**。`HostRateLimiter` を持つ gateway のうち public RPC に露出する
  3 経路が同じ予算に揃い、`ExternalContentEndpointCount()` が 3 になって起動ログの
  `external_content` にもそう出る。
- `RegisterRSSFeed` が「連続 5 回 / 30 秒 / 全ユーザー分」の過敏な専用 breaker から
  外れ、1 人の死んだ URL が他のユーザーの登録を止める経路が消えた。
- `ResolveOgImages` が自分のホストスロット待ちで 30 秒暗転する自己 DoS ループが断たれ、
  再プローブが 5 秒になった。
- near-miss 3 件（`BatchPrefetchImages` / `BatchPrefetchArticleContent` /
  `RegisterFavoriteFeed`）がテストに固定され、「第三者 URL を扱う」だけの endpoint が
  次に来ても誤って移されない。分類を外すとテストが落ちることも確認済み
  （`ResolveOgImages` で 4 本、`RegisterRSSFeed` で 5 本）。

### Cons / Tradeoffs

- **`X-Alt-Failure-Scope: host` を stamp しているのは articles ハンドラだけ**で、feeds
  にも rss にも無い。[[000963]] の Cons が「ヘッダは proto にも Connect 標準にも現れない
  ので**新しい producer は stamp を忘れうる**」と予告した状態が、2 箇所で現実に起きて
  いる。分類と stamp は層が違う（どの予算に載せるか／その予算から外すか）ため、
  **今回の分類変更後も出版社起因の 5xx は external_content の予算を消費する**。
  未帰属 = 我々の失敗に倒れるので安全側ではあるが、[[000959]] / [[000963]] の意図が
  完結しているのは 3 経路のうち `FetchArticleContent` の 1 経路だけである。
- 単一共有インスタンスの相乗り。出版社側の広域障害で 20 連続失敗すれば 3 endpoint が
  同時に 5 秒拒否される。[[000959]] が new class 時に受け入れたトレードオフの範囲内だが、
  対象が 1 から 3 に増えた。
- `RegisterFeedsUsecase` が fetch 失敗を素の `errors.New` に潰す構造は本 ADR で直して
  いない。出版社の 404 / 429 が Connect code を失って一律 500 になるため、
  [[000959]] §1 の「4xx は breaker に計上しない」も `RegisterRSSFeed` には効かない。
  stamp を足すより先に、ここを型付けするのが順序として正しい。
- 閾値 20 / open 5 秒は [[000959]] のときと同じく実測に基づく値ではない。登録という
  「1 回のクリック」に対しては明らかに緩く、検知はメトリクス / アラート側の責務のまま
  である（[[000959]] が 4xx について、[[000963]] が scope=host について負ったのと同種）。
- 実スタックでの検証はしていない。[[000963]] が残した「breaker の open / half-open
  遷移が実スタックで未検証」という状態は本 ADR でも解消していない。検証はユニット
  テストの範囲に留まる。

## Deploy-model 整合性セルフチェック

本 ADR は alt-butterfly-facade のアプリケーションコード（分類テーブル 2 行と
そのテスト）のみを変更し、compose / CI / deploy pattern を触らない。

- [x] 新設 compose service が `depends_on` で他 service を gate するか？ — **N/A**
- [x] 新設 compose service に `restart: "no"` の one-shot init container を含むか？ — **N/A**
- [x] 新設名前付き volume を populate する責務はどこにあるか？ — **N/A**
- [x] いずれも該当しない: **rolling 互換**

分類は BFF プロセス内の静的テーブルで、他サービスの deploy 順序に依存しない。
alt-backend が先に出ても BFF が先に出ても、変わるのは BFF がどの breaker に失敗を
計上するかだけである（[[000826]] の per-service rolling deploy と整合）。
