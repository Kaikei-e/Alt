# ADR-000983: og:image の「未解決」を 2 リスト 4 状態のワイヤ契約に開き、遅れて解決したカードを描画する

## Status

Accepted

## Date

2026-08-28

## Affected Services

- **proto** — `proto/alt/feeds/v2/feeds.proto`、`proto/services/datahub/v1/datahub.proto`
- **alt-backend (Go)** — `domain/og_image.go`、`orchestrator/usecase/og_image_resolve_usecase/`、`orchestrator/connect/v2/feeds/og_image_resolve.go`、`shared/driver/alt_db/feed_og_image_driver.go`、`shared/gateway/datahub_gateway/og_image.go`
- **alt-data-hub (Go)** — `dataplane/connect/datahubapi/wave3_handler.go`（alt-backend と同一モジュールの `cmd/datahub`）
- **alt-frontend-sv (TypeScript / Svelte 5)** — `lib/utils/{ogImageResolver,ogImageRetry,proxyImage.svelte,ogImagePrefetch}.ts`、`lib/stores/ogImageOverlay.svelte.ts`、`lib/connect/feeds/ogImages.ts`、`VisualFeedCard` / `MobileGalleryTile` / `ArticleScopeCard`、`src/test/contracts/feed-contract.test.ts`

## Context

### 症状

`/feeds/visual-preview` のカードが "No preview" のまま固定される。裏では og:image の解決が
続いており、**成功しているのにカードは blank のまま**で、リロードすると出る。つまり画像は
再取得 1 回ぶんの距離にあり、更新されていなかったのは UI だけだった。

### 機構 — 死ぬのは読者のリクエストだけで、サーバは仕事を終える

`ResolveOgImages` は per-host スロットの内側で出版社のページを**同期に**取得する
（`og_image_resolve_usecase.Execute`）。1 回の RPC で終わらなかったバッチは**読者側の
リクエストだけが死に**、サーバが到達できたフィードの画像は `feed_og_images` に書かれる。
次に同じことを訊けばストアから答えられ、出版社へのリクエストは 1 本も増えない。

にもかかわらずクライアントは、その死んだリクエストを「オリジンの回答」として読み、
セッションが終わるまで訊き直さなかった。

### 同じ形のバグが 3 層に重なっていた

「サーバが URL をくれなかった」を 1 つの意味に潰す、という同一の誤りが 3 か所にあった。
どれか 1 つを直しても症状は残る。

| 層 | 潰し方 |
|---|---|
| コンポーネント（`createProxyImage`） | 解決を 1 回しか要求しない。1 回で駄目なら `absent` へ落ちる |
| クライアント（`ogImageResolver`） | 答えを `string \| null` の 2 値で持ち、`null` を session 記憶に入れる |
| proto（`ResolveOgImagesResponse`） | `images` に居ないこと以外に、区別するための語彙が無い |

サーバ内部の「未解決」は最初から 4 通りあり、それぞれ retry 方針が違った
（`domain.OgImageRefusal.RetryAfter`）。robots disallow / og タグ無し / 404 は保持窓の内側で
恒久、403 は 24h、fetch_error は 6h、page URL 不正は何も記録せず `NeedsFetch()` は true の
まま。これが全部ワイヤ上で「不在」に潰れていた。

### 使われていなかった `attempts` と、成功を罰していた upsert

`feed_og_images.attempts` は upsert のたびに `attempts + 1` で書かれていながら、
**コードベースのどこからも読まれていなかった**。エスカレーションの材料が DB にあるのに、
domain も usecase もワイヤも参照していない。

さらにその upsert は**成功時も無条件に**インクリメントしていた。1 週間スクロールのたびに
順調に解決し続けていた feed が、初めての一時的な 502 で 2 桁のカウンタを抱えたまま
最大バー（6h）を食らう。エスカレーションが行儀の良い feed を罰し、まったく解決しない
feed を見逃していた。

### 半年前に同じクラスのバグを記録している

[[000269]]（2026-02-26）は「取得結果が UI に反映されない」を主題にした ADR で、主因を
**「`ogImageCache` が非リアクティブ」**と特定している。本件はその半年後に、まったく別の
経路で同じクラスが再発したものである。当時は Svelte のリアクティビティが壊れていた。
今回は反映すべき値そのものが「不在」という単一の意味に潰されていて、リアクティビティは
正しく動いていた。**「結果は出ているのに画面に出ない」という症状は、フロントの
リアクティビティ以外の理由でも成立する** — これが 000269 に足りなかった一般化である。

なお本件で見つかったリアクティビティ側の穴も同じ PR で塞いだ。ページ側の backfill が
フィードオブジェクトへ代入していたが、`await` をまたいで掴んでいた配列は撮った時点の
スナップショットで、SSR 由来のプレーンオブジェクトや `$derived` が作り直したオブジェクトへの
代入は画面に出ない。article キーの overlay（`ogImageOverlay.svelte.ts`）に変えた。

## Decision

**`ResolveOgImages` の「未解決」を、2 本の並列リストのメンバーシップで表現する 4 状態の
ワイヤ契約に作り替える。**

### 1. 2 リスト 4 状態（proto）

`ResolveOgImagesResponse` に `repeated UnresolvedOgImage unresolved = 2` を**純加算**する。
`UnresolvedOgImage` は `feed_id` と `retry_after_seconds` の 2 フィールドだけを持つ。

| 状態 | ワイヤ上の表現 | 意味 | クライアントの振る舞い |
|---|---|---|---|
| 解決 | `images` に居る | proxy URL がある | 描画。記憶する |
| 確定 | `unresolved` にバー 0 | 保持窓の内側で settled | 記憶する。二度と訊かない |
| 一時失敗 | `unresolved` にバー > 0 | 訊いて失敗した。バーが明ければ成功しうる | 記憶しない。バーを ladder の床にして訊き直す |
| 未検討 | **どちらのリストにも居ない** | バッチ上限で切り詰めた / 行が返らなかった | 記憶しない。即座に訊き直してよい |

既存の設計意図「A feed whose origin refused is absent rather than
present-with-an-empty-URL」は覆していない。`unresolved` は**その不在がどの種類かを言うだけ**
である。

**不在の意味は「検討すらしていない」だけに狭めた。** 検討したうえで解決できなかったものは、
理由が我々側の URL 不正 / SSRF 拒否であっても `unresolved` に入る（バー 0）。DB に refusal を
記録しない既存の決定は変えていない — 書くものと答えるものは別の質問で、行は書かないが
この読者のセッションに対しては settled と答える。page URL はこの保持窓の内側で変わらず、
それに対する我々の判断も変わらないので、次に訊いてもまったく同じ場所で失敗する。
検討した結果を沈黙で表すと、絶対に解決しない feed をクライアントが毎ページロード訊き直し
続けることになる（不在は「未検討」を意味するので、クライアントは記憶しない）。

### 2. バーを試行回数に連動させる（domain）

`OgImageRefusal.RetryAfter(attempts)` にする。エスカレートするのは一時的障害
（`fetch_error`）だけで `min(6h, 5s × 2^(attempts-1))`。

- `robots_disallow` / `no_og_tag` / `http_404` は 0 のまま。これらは**オリジンの答え**で
  あって到達途中の障害ではなく、4 回聞いても答えが変わりやすくなるわけではない。
  エスカレートさせるとそれを示唆してしまう。
- `http_403` は 24h 固定のまま。「誤設定 edge を 1 日 1 回拾う」という既存の根拠が、
  まさにエスカレーションで壊れる。保持窓 7 日が総回数を 7 に抑えている。
- `attempts < 1` は 1 に正規化し、`attempts > 13` は即座に ceiling へ落とす（`base << 13`
  は既に 40960s で、int64 ナノ秒のオーバーフローで負のバーになるのを防ぐ）。

**base が 5s なのはワイヤの向こう側の天井による。** クライアントは 10 秒を超えるバーを
待てない（`ogImageRetry.ts` の `OG_RETRY_CEILING_MS`）。5s → 10s → 20s なら 2 回は
セッション内に着地し、3 本目はセッションを超えるが、サーバ側の行は残るので次のページ
ロードが無償で回収する。

### 3. upsert を「refusal だけがカウンタを進める」に是正（driver）

```sql
attempts = CASE WHEN EXCLUDED.state = 'resolved' THEN 1
                ELSE feed_og_images.attempts + 1 END
```

解決は「何が悪かったにせよそれは終わった」という証拠なので、カウンタを 1 段目に戻す。
`FetchFeedOgImageTargets` は `attempts` を**生のまま**返す（行が無い feed は 0）。
+1 を driver に置くと、この driver が報告する数と `attempts` 列が持つ数が 1 ずれ、
以後どちらを見ているのか全員が知っていなければならなくなる。正規化は
`RetryAfter`（0 と 1 を同じに扱う）に寄せた。

### 4. 4 状態を読み分け、サーバのバーを床として待つ（frontend）

`outcomeFor` が 2 本のリストから 4 状態を読み、`OgImageOutcome` を
`resolved` / `absent` / `unavailable` の 3 値で返す。**記憶するのはサーバが答えた前 2 者だけ**
で、「訊けなかった」は誰も記憶しない（RFC 2308 が negative answer と server failure に
別々の TTL を与えるのと同じ線）。

- 両リストに居る異常応答は `resolved` を優先する。
- **天井超えのバーは `absent` に畳む。** 待たないと決めた時間だけ shimmer を出し続けるのは、
  読者にも、実際には何も要求していない出版社にも嘘になる。サーバ側の行は残るので、
  バーを実際に越えた時計を持つ後のセッションが回収する。
- `createProxyImage` に上限つき retry ladder（full jitter、計 3 回、`OG_RETRY_BASE_MS`
  1.2s）。再取得はストアから答えられるので出版社へのリクエストは増えない。届かない
  バックエンドは shimmer ではなく fallback に着地する。

transport failure を分類する `classifyFailure` は**無改変**。あれは「訊けなかった」の軸で、
今回足したのは「訊いたが解決しなかった」の軸であり、2 つは独立している。出版社自身が出した
429（[[000963]] が `X-Alt-Failure-Scope: host` を刻む）は再送しない。

`retry_after_seconds` は protobuf-es が int64 を bigint にするため `ogImages.ts` の
エッジで ms の number に変換する。ここで `if (!retryAfterSeconds)` と書くとバー 0（確定）が
「未検討」（即再試行可）に化けて意味が正反対になるため、テストで固定した。

### 5. モックドリフト検出に `ResolveOgImages` を入れる

`src/test/contracts/*.test.ts` はこのリポジトリが frontend ↔ backend の契約に選んだ守りで、
「when the proto changes, these tests break before the E2E tests silently pass with stale mock
data」を目的として明言している。`ResolveOgImages` だけがこの守りに一度も入っていなかった。
現に今回、`unresolved` を足したことでモックの `{images: []}` の意味が「断られた」から
「検討すらしていない」に変わり、E2E スペックを手で直して初めて気づいた。

- E2E スペックにインラインで散っていたレスポンスを `buildResolveOgImagesResponse()` に
  引き上げた。契約テストは「E2E が実際に使うモック」を検証してこそ意味がある。
- 検証は `create()` ではなく **`fromJson()`** で行う。`create()` は未知プロパティを黙って
  捨て、int64 に生の number を受けて `toBinary` が黙って強制変換するため、今回のドリフト
  2 種のどちらも見えない。`fromJson` は未知キーを拒否し、Playwright が返すこのボディを
  ブラウザの Connect クライアントが実際に通す経路でもある。

守りが効くことは注入で確認済み（確定行を落とすと 3 本、int64 を数値で書くと 1 本落ちる）。

### 検討した代替案と却下理由

| 代替案 | 却下理由 |
|---|---|
| **クライアント側で `absent` に TTL を張る**（proto を触らない） | サーバの 6h / 24h / 恒久という 3 つの方針を、クライアントが選んだ単一の TTL で塗り潰す当て推量になる。サーバは既に正しい数を持っており、それを送らない理由が無い |
| **1 本のリスト + `status` enum** | proto の「拒否は不在で表す」という既存の記述を覆す。そのうえ「サーバが到達しなかった」を表すのに enum 値が 1 つ余分に要り、**バッチ上限で切り詰めた分にまで「何もしなかった」と言うための行を出す義務が生じる**。2 リストのメンバーシップなら、両リスト不在が第 3 の意味を無償で持つ |
| **SSE / Connect server-streaming で解決を push する** | nginx は `listen 80`（http2 なし）で、ブラウザの HTTP/1.1 per-origin 6 socket 制限がそのまま効く。`nginx/conf.d/default.conf` は既に stream / SSE 用 location を 6 本持っており枠を使い切っている。さらに `location /`（= visual-preview 自身）は `proxy_buffering on` なので、そこに載せた streaming はバッファに溜まって届かない |
| **バーの計算を SQL に置く** | 政策が `domain` と SQL に二重化する。`RetryAfter` は refusal ごとの方針そのもので、テストと読解の中心を DB に散らす価値が無い |
| **base を 30s にする** | クライアントの `OG_RETRY_CEILING_MS`（10s）を初回から超え、ladder が一度も回らない。サーバが「あとで訊いてよい」と言っているのにクライアントが構造的に訊けない、という今回のバグの別形になる |
| **`SaveFeedOgImageRequest.retry_after_seconds` の意味を相対秒に変える** | 既存フィールドの意味を書き換えると、ローリングデプロイで新旧が混ざったとき黙って壊れる。絶対バーの意味のまま据え置き、新しい意味は新しいフィールドに載せた |

### [[000935]] との関係 — SUPERSEDE ではなく PARTIAL である

[[000935]] は 4 つの決定を置いた。本 ADR が無効化するのはそのうち 1 つだけなので、
[[000982]] が [[000533]] に対して取った形にならい、**frontmatter に `supersedes` キーは
置かない**。

| [[000935]] の決定 | 現状 |
|---|---|
| §1 読み取りパスで `article_heads` をフォールバック解決（COALESCE + 7 日 age-gate） | **有効**。`fetch_feed_driver.go` の `ogImageSelectExpr` として現役 |
| §2 `ExtractOgImageURL` の抽出候補拡張と相対 URL 絶対化 | **有効**。`og_resolve_gateway` と `fetch_article_usecase` の両方が使っている |
| §3 **能動 backfill（`og-image-backfill` ジョブ、30 分間隔）** | **削除済み**。オンデマンド解決に置換された |
| §4 `og-image-retention` ジョブ（7 日保持窓） | **有効**。`feed_og_images` もこのジョブの purge 対象に加わり、窓は 7 日のまま |

§3 が削除された理由は負荷でも方針転換でもなく、**失敗の記憶を持たなかったこと**である。
`feed_og_images` の migration に記録されているとおり、あのジョブは同じ 16 本の拒否 URL を
30 分ごとに取り直し、生涯で 1 度も成功しなかった。オンデマンド解決は
(a) 出版社への各リクエストが「今そのカードを見ている人がいる」ことに起因し、
(b) feed あたり最大 1 回で、
(c) 拒否を記録して同じカードを見直しても再び訊かない、
という 3 点で置き換えている。加えて §3 は `article_heads.article_id NOT NULL REFERENCES
articles(id)` に縛られ、**articles 行を持つ feed にしか到達できなかった**。記事本文が一度も
取得されていない feed には article 行が無く、画像なし feed の大半がそれに当たる
（`tests/e2e/desktop/feeds/visual-preview-ondemand-og-resolve.spec.ts` が「image-less feeds の
92% が article 行を持たない」と記録している。この 92% の測定手順は vault に残っていないため、
桁の目安として扱う）。`feed_og_images` が feed をキーにするのはこの制約を外すためで、
[[000935]] §3 の設計では原理的に届かなかった側がオンデマンド解決の対象になる。

**この ADR の副次的な目的は、その宙吊りの解消である。** コードは既にジョブを削除し、
`orchestrator/job/registry_test.go` が「`og-image-backfill` が登録されていないこと」を
テストで固定している。一方 [[000935]] は `status: accepted` のまま、そのジョブの追加を
指示し続けていた。本 ADR は §3 のみを無効化し、§1 / §2 / §4 が有効であることを上表で明示する
（[[000935]] の status はグラフ投影に委ね、本文も改変しない）。

## Consequences

### Pros

- **遅れて解決した画像が、リロード無しでカードに出る。** サーバが到達できたフィードの画像は
  既にストアにあり、再問い合わせは出版社へのリクエストを 1 本も増やさずにそれを回収する。
- **「訊き直してよい」とサーバが判断したケースが実際に訊き直される。** 4 状態のうち 3 つ
  （一時失敗 / 未検討 / 天井超えの後続セッション）が blank 固定から救い出される。
- **エスカレーションが行儀の良い feed を罰さなくなった。** `attempts` は refusal でのみ進み、
  解決で 1 に戻る。同時に、DB にあって誰も読んでいなかった列が実際の政策入力になった。
- **不在の意味が 1 つに定まった。** 「サーバが検討すらしていない」だけ。検討した結果は理由を
  問わず `unresolved` に入るので、絶対に解決しない feed を毎ページロード訊き直す経路が閉じた。
- **`ResolveOgImages` が契約テストの守りに入った。** `fromJson` 検証により、proto 変更が
  E2E の stale モックを黙って通すのではなく、契約テストで先に落ちる。
- **すべて純加算で `buf breaking` を通過。** 旧クライアントは今までどおり `images` だけを見る。
- shimmer が無限ループから 3 周に変わり（WCAG 2.2.2）、`prefers-reduced-motion` と
  `aria-busy` が付いた。

### Cons / Tradeoffs

- **4 状態の意味は 3 か所に散っている** — proto コメント、`og_image_resolve_usecase.Execute` の
  doc、`ogImageResolver.outcomeFor` の doc。契約テストが形は守るが、**意味の同期は人手**である。
  bad1276 で直したのはまさにこの食い違い（proto は「page URL 不正は両リスト不在」と書き、
  実装は `unresolved`/0 に入れていた）で、同じ乖離は再発しうる。
- **天井超えのバーはクライアントで捨てられる。** サーバが 6h と言っても、そのセッションの
  カードは fallback に落ちる。回収は次のページロード頼みで、1 セッションしか開かない読者には
  最後まで出ない。
- **`OG_RETRY_CEILING_MS`（10s）と domain の `base`（5s）は暗黙に結合している。** 天井を
  下げるか base を上げると ladder が回らなくなる。この結合は両側のコメントに書いてあるだけで、
  テストでは固定されていない。
- **`unresolved` は `?? []` でガードしている。** フィールドを知らない旧サーバの応答が通る経路の
  ための後方互換だが、形としては CLAUDE.md ルール 8 が禁じる無言フォールバックに似る。
  producer / projector / resolver の配線ではなく**純加算フィールドの読み側**なので範囲外と
  判断したが、`unresolved` が恒久化した後は外すべき負債である。
- **`OgImageBackfillCandidate` と `ListFeedsMissingOgImage` の proto surface が残っている。**
  `Deprecated` コメント付きで、breaking-change baseline が動くまで削除できない。
- 契約テストが検証するのは E2E のモックであり、alt-backend の実レスポンスではない。実
  producer 側は Pact CDC（`alt-backend/pacts/alt-backend-alt-data-hub.json`）が担保する。

## Deploy-model 整合性セルフチェック

本 ADR は compose / CI / deploy pattern を変更しない（proto とアプリコードのみ）。
DB マイグレーションも追加しない（`feed_og_images.attempts` は既存列）。

- [ ] 新設 compose service が `depends_on` で他 service を gate するか？ → **N/A**
- [ ] 新設 compose service に `restart: "no"` の one-shot init container を含むか？ → **N/A**
- [ ] 新設名前付き volume を populate する責務はどこにあるか？ → **N/A**
- [x] いずれも該当しない: **rolling 互換**。proto 変更は純加算で `buf breaking` を通過して
  おり、新旧が混ざった状態でも旧クライアントは `images` のみを読む。alt-backend /
  alt-data-hub / alt-frontend-sv をどの順で入れ替えても壊れない。
