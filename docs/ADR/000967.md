# ADR-000967: projector の checkpoint 前進を compare-and-set にして rebuild との競合を閉じる

## Status

Accepted

## Date

2026-08-09

## Affected Services

- knowledge-sovereign (Go)

## Context

### rebuild は単一トランザクションになったが、競合は閉じていなかった

projection rebuild（`driver/sovereign_db/rebuild_projection.go`）は 1 トランザクション内で checkpoint 行を `FOR UPDATE` でロックし、read model を TRUNCATE し、`last_event_seq` を 0 に戻して commit する。PM-2026-010 は「TRUNCATE と checkpoint reset が別操作だったため、走行中の projector が隙間で checkpoint を進め、326 記事が再 fold されなかった」障害で、この単一トランザクション化はその対策として入った。

しかし `FOR UPDATE` は競合する projector を**待たせる**だけで、**読み直させない**。そして `UpdateProjectionCheckpoint`（`read_infra.go`）は自前のロックを持たない無条件 upsert である。

```sql
INSERT ... ON CONFLICT (projector_name) DO UPDATE SET last_event_seq = $2, updated_at = now()
```

projector は batch 冒頭で checkpoint を読み、events を fold し、最後に書き戻す。したがって次の順序が成立する。

| 時刻 | rebuild | projector |
|---|---|---|
| t0 | | checkpoint = N を読み、N+1..M を fold |
| t1 | `FOR UPDATE` 取得（projector はまだ書きに来ていない） | |
| t2 | TRUNCATE | |
| t3 | checkpoint = 0、commit、ロック解放 | |
| t4 | | `SET last_event_seq = M` を無条件に書く |

**テーブルは空、checkpoint は M。** projector は以降 `> M` しか取得しないので 1..M は永久に再 fold されない。PM-2026-010 の最終状態そのものである。

さらに checkpoint 行が存在しない場合（projector が一度も動いていない）、`SELECT ... FOR UPDATE` はロック対象が無いため完全な no-op になり、窓はさらに広い。

### 見つかった経緯

この欠陥は本番稼働後に、integration tier を新設する過程で発見された。既存の単体テストは pgx をモックしており、ロックが「本物のロック」かどうかも、`pgx.ErrNoRows` 分岐が実行されるかも検証できていなかった。[[000965]] が alt-data-hub について述べた「モックは発行された SQL しか証明できない」がそのまま当てはまる。

## Decision

**in-process の checkpoint 前進を compare-and-set にする。wire RPC は変更しない。**

1. `ProjectionCheckpoint`（`LastEventSeq` / `UpdatedAt` / `Exists`）を read token として導入し、`ReadProjectionCheckpointForAdvance` で取得、`AdvanceProjectionCheckpointIfUnchanged` で「読んだときのまま」であることを条件に前進させる。適用可否は `(applied bool, err error)` で返す。拒否はエラーではなく通常の結果である。
2. home / trail 両 projector は batch 冒頭で読んだ token をそのまま渡す。`applied == false` のときは ERROR で構造化ログ（`*.checkpoint_advance_rejected`、`expected_seq` / `attempted_seq` / `batch_events` 付き）を出して tick を終了する。**ループ内リトライはしない** — 次の tick が読み直せば正しい状態から再開できる。
3. `UpdateProjectionCheckpoint` は署名も SQL も変えない。

### なぜ token であって `last_event_seq` だけの CAS ではないのか

ここが本 ADR の中心的な判断である。seq だけを比較する CAS には **ABA が残る**。

rebuild は checkpoint を 0 にする。0 から fold を始めた batch の途中で **2 回目の rebuild** が走ると、前後とも 0 なので seq は一致し、CAS が通ってしまう。これは仮想的な心配ではない: runbook は「landed したか不安なら再実行せよ」と書いており、`TestRebuildProjection_IsIdempotent` が「オペレータは実際に再実行する」ことを既にコード化している。`updated_at` を witness に含めるとこの経路が閉じる。

また「行が無い」を 0 に潰すと、**fresh projector の穴が CAS でも閉じない**。行なし → 読み手は 0 → rebuild が 0 の行を INSERT → CAS(0→M) が通る。`Exists` を持ち、absent からは `INSERT ... ON CONFLICT DO NOTHING`（決して `DO UPDATE` に落ちない）とすることで、rebuild が作った行を上書きしない。同時に「初回起動の projector が永久に前進できない」退行も防げる。

### 検討して採らなかった代替案

- **wire RPC `UpdateProjectionCheckpoint` の署名に `expected_seq` を足す** — これは共有 proto（`proto/services/sovereign/v1/sovereign.proto`）の RPC で、alt-backend が reproject swap から呼んでいる。proto は alt-backend と rag-orchestrator にも生成されるため、3 サービス同時変更になる。in-process の競合を閉じるのに service 境界を巻き込む理由がない。`AppendKnowledgeEventIfNew` を wire 形の隣に足した先例と同じ形にした。
- **rebuild 側で「行が無い」穴を塞ぐ** — `INSERT ... DO NOTHING` してから `FOR UPDATE` すればロック対象は作れる。だが**ロックは読み直しを強制しない**ので、rebuild 開始前に読み終えた batch には無力である。閉じるのは projector 側の CAS だけであり、rebuild にコードを足すと「守られている」という誤った印象だけが増える。
- **拒否時にリトライする** — 拒否は「前提が変わった」という意味なので、同じ token での再試行は必ず失敗する。読み直しは次の tick の仕事である。

## Consequences

### Pros

- rebuild と projector が競合しても、read model が空のまま checkpoint だけ進む状態が発生しなくなった。PM-2026-010 の再発経路が塞がれている。
- 2 回目の rebuild（ABA）と、projector 未起動時（行なし）という 2 つの周辺経路も同時に閉じた。どちらも `FOR UPDATE` では守れない領域だった。
- 拒否が観測可能になった。従来は無条件上書きなので、競合が起きても何のログも残らなかった。
- 実 PostgreSQL に対する integration tier が knowledge-sovereign にも入った（[[000965]] の alt-data-hub と同じ形）。競合というモックで到達不能な性質を、実サーバに対して固定できるようになった。
- wire 契約を触っていないので、alt-backend / rag-orchestrator への波及がない。

### Cons / Tradeoffs

- **wire RPC は依然として無条件上書きである。** alt-backend の reproject swap が rebuild と競合すれば同種のバグが起こりうる。閉じるには proto 変更が要るため範囲外とし、doc コメントで危険性を明記するに留めた。
- 拒否された tick の分だけ fold が遅れる。次の tick で追いつくが、rebuild 直後の短い間、read model には truncate 後に書かれた高 seq の部分行が残る（idempotent upsert なので収束する）。
- checkpoint 読み取りが 1 往復増える。ロック待ちのない単純な主キー lookup なので実測できる差ではないが、往復は増えている。
- 競合の integration test は、`ListKnowledgeEventsSince` の直後に rebuild を同期的に走らせる seam を使っている。**真の並行実行ではない** — goroutine と sleep では flaky で何も証明できないため、時間軸を取り除いた決定的再現を選んだ。seam は checkpoint メソッドではなくイベント取得側に置いてあるので機構ではなく結果を固定しているが、実運用の並行性そのものを再現しているわけではない。
- integration tier は Docker daemon を要求する。
