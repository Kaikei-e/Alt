# ADR-000959: 外部サイトの応答と自前のレート制限ゲートを alt-backend の failure budget から切り離す

## Status

Accepted

## Date

2026-08-08

## Affected Services

- alt-butterfly-facade (Go)
- alt-backend (Go)
- alt-frontend-sv (TypeScript / SvelteKit)

## Context

Visual Preview を数枚スワイプしただけで、UI に次の文字列が出るようになっていた。

```
[unavailable] Service temporarily unavailable due to circuit breaker
```

[[000950]] で導入した依存クラス別 circuit breaker のうち `non_critical` breaker が開いていた。
連鎖は次の通り。

1. `VisualPreviewCard` は BFF 経由で `ArticleService/FetchArticleContent` を呼ぶ。この RPC は
   alt-backend に**第三者の出版社サイトへの外部 fetch** をさせる。
2. `dependency_class.go` が分類していたのは 5 endpoint のみ（MarkAsRead / MarkAsUnread、
   GetUnreadFeeds / GetUnreadCount / GetAllFeeds）。`FetchArticleContent` は未分類のため
   `ClassNonCritical` に落ち、他の全未分類 endpoint と単一の breaker を共有していた。
3. alt-backend は出版社サイトの結果をそのまま Connect コードへ写していた。出版社の 404 →
   HTTP 404、403/401 → 403、429 や robots.txt Crawl-delay → 429、その他 → 503。
4. BFF の `IsErrorResponse` は `statusCode >= 400`。上記すべてが `recordFailure` を叩いた。
5. `CBFailureThreshold: 5` 連続で OPEN、`CBOpenTimeout: 30s`。以降 30 秒間、未分類 endpoint
   全体が 503 を返した。

つまり**レート制限中またはペイウォールの出版社の記事を 5 本続けて開くと、アプリ全体の
breaker が 30 秒開く**。Visual Preview が自分自身を落としていた。

### 引き金の大半は外部サイトではなく自前のゲートだった

ログを分類すると、breaker を叩いていた失敗の内訳は 4 種類あり、**外に 1 バイトも出ていない
ものが半分を占めていた**。

| ログ | 誰の制限か | リクエストは送信されたか |
|---|---|---|
| `wait for host slot ...: context deadline exceeded` | Alt 自身の politeness gate | いいえ |
| robots.txt Crawl-delay 未経過 | サイトが宣言し Alt が執行 | いいえ |
| `http request failed ...: context deadline exceeded` | 外部サイトが無応答 | はい |
| 外部サイトが HTTP 429 | 外部サイト | はい |

`RATE_LIMIT_EXTERNAL_API_INTERVAL` の既定は**ホストあたり 10 秒**（burst 3）。さらに
[[000954]] のレビュー対応で `HOST_RATE_LIMITER_REDIS_URL` による分散調停が有効になっており、
`cmd/backend` と `cmd/harvester` が namespace `external_api` の**同一ホストスロットを共有**する。
結果として、ユーザーの対話的スワイプが harvester の定期ジョブの後ろに並び、待ちきれずに
BFF の 30 秒デッドラインが切れ、その失敗が「alt-backend の障害」として記録されていた。

直前の修正（swipe の記事取得が数枚で停止する不具合）が Crawl-delay を永続的な 403 から
retryable な `ResourceExhausted`(429) へ改善した結果、**その 429 が breaker をより確実に
開かせる**ようになっていた。正しい修正が、その下にあった次の欠陥を露出させた形である。

### エラーエンベロープが Connect 仕様を満たしていなかった

BFF は circuit-open 時に `{"code":"SERVICE_UNAVAILABLE","is_retryable":true,"retry_after":30,...}`
を返していたが、Connect のエラーコードは小文字 snake_case である。connect-es の
`codeFromString("SERVICE_UNAVAILABLE")` は `undefined` を返し、HTTP status 由来のコードに
フォールバックする。実測でも確認した。

```
codeFromString("SERVICE_UNAVAILABLE") -> undefined
codeFromString("unavailable")         -> 14   (Code.Unavailable)
```

`is_retryable` / `retry_after` / `request_id` は標準フィールドではないため**すべて破棄され、
残るのは `message` だけ**だった。UI に出ていた `[unavailable] ...` はその `message` に
connect-es がコードを前置したものである。BFF が算出した 30 秒の Retry-After はクライアントに
届いておらず、フロントエンドが賢くバックオフする手段が構造的に存在しなかった。

## Decision

**第三者サイトの健全性と Alt 自身の politeness gate を、alt-backend の failure budget から
切り離す。** 3 サービスにまたがって次を採用する。

### 1. クライアントエラーは依存障害ではない (alt-butterfly-facade)

`IsErrorResponse`(>= 400) はエラー正規化用として維持し、breaker 計上には
`IsDependencyFailure`(>= 500) を新設して分離する。`recordOutcome` は 5xx で failure、
2xx/3xx で success、**4xx ではどちらも記録しない**。

4xx を success にしないのが要点である。success にすると `consecFailures` がリセットされ、
実際のバックエンド障害を隠す。failure にすると、ペイウォール 1 サイトでクラス全体が落ちる。
中立が唯一正しい。

### 2. 外部コンテンツ取得に独立した failure budget を与える (alt-butterfly-facade)

`ClassExternalContent`（`FetchArticleContent` のみ）を新設する。予算は内部依存より意図的に
緩く、閾値 20 / open timeout 5 秒とする（内部は 5 / 30 秒）。開いても再プローブが 6 倍速い
のは、次の記事はたいてい別の出版社であり、30 秒の暗転は読書セッション 1 回分に相当するため。

`BatchPrefetchImages` は移さない。署名付き proxy URL を生成するだけで出版社への外向き
fetch を行わないことをコードで確認した。

### 3. 外部サイト無応答を内部エラーとして扱わない (alt-backend)

`domain.UpstreamFetchError` を新設し、gateway（anti-corruption 層）で分類する。判定は
positive allowlist とする — secure client の SSRF チェックが dialer 内で走るため、拒否された
アドレスも `*net.OpError` として現れる。エラーの「形」で判定すると**自分のポリシー判断が
「サイトが遅い」に化ける**。分類済みのものは `CodeUnavailable` + WARN ログとし、
`HandleInternalError` を通さない。未分類のエラーは内部障害のまま loud に残す。

### 4. 自前のゲートは 429、外部無応答は 503 (alt-backend)

host slot の期限切れは `RateLimitedError` → `CodeResourceExhausted`(429) + Retry-After に
写す。これは Crawl-delay が既に使っている経路である。

当初これを `UpstreamFetchError` に畳む実装を試したが**差し戻した**。理由は 3 つ。
(a) クライアントに "the source site did not respond" と返すのは事実に反する。1 パケットも
送っていない。(b) 503 は 5xx なので決定 1 の下でも failure として計上され、**自己 DoS の
ループが影響範囲を狭めただけで生き残る**。(c) スロット待ちは「いつ空くか」を知っているが、
死んだサイトは知らない。畳むとその情報が失われる。

### 5. 対話経路は速く諦める (alt-backend)

`NewInteractiveFetchArticleGateway` に slot 取得のみを包む短い wait budget
（`RATE_LIMIT_INTERACTIVE_SLOT_WAIT`、既定 2 秒）を持たせる。fetch 本体は呼び出し側の
デッドラインをそのまま使う。harvester のジョブと batch fetcher は従来どおりブロックする。

**politeness は 1 ミリも緩めない。** `ExternalAPIInterval` / `ExternalAPIBurst` /
`NamespaceExternalAPI` は変更しない。共有は [[000954]] のレビューで意図的に入れたもので、
分ければ同一 publisher が 1 インターバルに 2 リクエストを受ける。方針は
**「速く諦める、決して多く叩かない」**。`x/time/rate` は予約失敗時にトークンを消費しないため、
早期離脱でホストへのリクエストは増えない。

### 6. Connect 準拠のエンベロープとバックエンド文言の非表示

BFF は circuit-open 時に小文字 `"unavailable"` を返し、リトライ指示は Connect のエラー本文に
枠が無いため `Retry-After` ヘッダに載せる（connect-es は `ConnectError.metadata` として渡す）。
値は**拒否したクラス自身の** open timeout を使う。

フロントエンドは `Code.Unavailable` を**全ホスト一時停止**として扱う（429 のホスト別
cooldown とは別。breaker はグローバルな状態であり、他ホストへ迂回できない）。既存の
"Source content unavailable." フォールバックに繋ぎ、**上流の `message` は描画しない**。

### 却下した代替案

| 案 | 却下理由 |
|----|----------|
| `FetchArticleContent` を breaker 対象外にする | 出版社が本当に総崩れした場合に無防備。予算を分けるのが正しい |
| `CBFailureThreshold` を一律で上げる | 内部依存の検知が鈍る。問題は閾値ではなく「何を失敗と数えるか」 |
| rate limiter の namespace を backend/harvester で分離 | 同一 publisher が 1 インターバルに 2 リクエスト受ける。Rule 2 違反 |
| `ExternalAPIInterval` を短縮 | 同上。politeness の緩和は選択肢に入れない |
| `isTransientError()` に `Code.Unavailable` を追加 | 2 箇所が 500ms 後に再送し、開いた breaker を叩き直す |

## Consequences

### Pros

- 出版社の 404 / 403 / 429 が alt-backend の failure budget を消費しなくなり、
  Visual Preview が自分自身を落とすループが断たれた。
- 自前の politeness gate による待ちが 429 として中立に扱われ、**自己 DoS ループが消えた**。
- 対話的リクエストが最大 30 秒ブロックされたのち失敗する経路が、約 2 秒で retryable な
  応答を返す経路に置き換わった。フロントは既存の要約フォールバックを即座に出せる。
- Retry-After がクライアントに実際に届くようになり、バックオフが推測でなくなった。
- 「サイトが遅い」が ERROR ログを汚さなくなり、本物の内部障害が見えやすくなった。

### Cons / Tradeoffs

- 4xx を中立にしたことで、**バックエンドが 4xx を返し続ける形の障害は breaker で検知
  できない**。この検知はメトリクス / アラート側の責務に移る。
- `external_content` の閾値 20 は、出版社側の広域障害時に内部クラスより検知が遅れる。
  意図的なトレードオフだが、実測に基づく値ではない。
- `tts-speaker` のような外部 pacticipant の扱いは本 ADR では解決していない。
  alt-butterfly-facade が久々にリリース集合へ戻った結果、CI の `can-i-deploy` が
  「本番ホストしか打刻できない参加者の本番実績」を要求してゲートが赤くなる構造的な
  問題が露出した。**別途の決定が必要**。
- [[000946]] が指摘した「open / half-open 遷移が実スタックで未検証」という状態は本 ADR でも
  解消していない。検証はユニットテストと契約テストの範囲に留まる。
