# ADR-001036: ライブ検証の SSE probe が使う news-creator の実行環境を CI で lock から用意し、使えない Python への黙った切り替えをやめる

## Status

Accepted

手元で CI と同じ手順を再現して確かめた。`uv` を PATH から外した状態で、lock から作った環境があればライブ検証の全テストが通り、無ければ環境チェックの時点で D4 のエラーになる。CI 上での実行はまだ確認していない。

## Date

2026-11-27

## Affected Services

- `scripts/altharness`（ライブ検証の Python 選択と環境チェック）
- `.github/workflows/`（ハーネスの CI ジョブ）
- `.claude/skills/verify-alt`（前提条件の記述）

## Context

ハーネスの CI ジョブが、ライブ検証の全 probe を通すテストで必ず失敗している。`main` 自身の実行でも、`main` とのマージ結果に対して走る PR の実行でも同じである。ハーネスのジョブが失敗すると、各ワークフローの結果を集約するチェックも失敗する。ハーネスのジョブはすべての PR で走るので、無関係な PR でも同じである。

失敗するのは SSE probe である。この probe は news-creator の SSE ハンドラを実際の FastAPI / Uvicorn で起動する。CI では起動した子プロセスが `ModuleNotFoundError: No module named 'uvicorn'` で終了する。

### 原因

**CI に実行環境が無い。** ハーネスのジョブが入れる Python パッケージは、検査ツール 3 つ（`pyrefly`、`ast-grep-cli`、`pytest`）だけである。news-creator の依存は入れていない。

**使える Python が無いとき、黙って使えない Python に切り替わる。** probe が使う Python は次の順で選ばれる。

1. news-creator の `.venv` の Python。`import fastapi, uvicorn` が通れば採用する。
2. PATH 上の `python3`。同じ確認が通れば採用する。
3. `uv` があれば、`uv run --offline` 経由の Python。確認はしない。
4. どれも駄目なら、PATH 上の `python3` をそのまま返す。

4 番目は必ず失敗する選択である。それでも環境チェックはこれを「正常」と報告する。CI では毎回 4 番目に落ち、probe の起動時に初めてトレースバックで失敗する。開発機には news-creator の `.venv` があるので、手元では通る。

**環境の確認が、probe が実際に読み込むものと合っていない。** probe のサーバは `news_creator.handler.sse_stream` を読み込む。このとき handler パッケージの初期化がすべてのハンドラを読み込む。実測では、サードパーティのトップレベルモジュールが 28 個読み込まれた。`fastapi` と `uvicorn` のほかに、`aiohttp`、`jinja2`、`json_repair`、`nh3`、`prometheus_client`、`pydantic`、`python_multipart` などが含まれる。

`fastapi` と `uvicorn` だけを入れた環境で確かめると、現在の確認（`import fastapi, uvicorn`）は通り、probe の読み込みは `No module named 'aiohttp'` で失敗した。CI に `fastapi` と `uvicorn` を足すだけでは直らない。

### news-creator の依存の重さ

news-creator の lock から開発用を除いた依存は 88 パッケージで、`torch` と `sentence-transformers` を含む。この 2 つとその先を取り除くと 58 パッケージになる。この 58 パッケージで作った環境は 109 MB で、probe の読み込みは成功した。`torch` は入っていない。SSE ハンドラの読み込み経路は `torch` に届かない。

### `uv` を CI に入れる影響

lock から依存の一覧を取り出すには `uv` が要る。一方、ハーネスには `uv` が PATH にあるかどうかで動作が変わる箇所が複数ある。使える言語だけを検査する canary の言語判定、compose 検査の Python の代替経路、上記の Python 選択の 3 番目である。CI のジョブ全体に `uv` を入れると、これらの動作が変わりうる。

### 既存の決定との関係

[[001028]] は、ハーネスとゲートの実行経路から Python を無くし、単一の Go バイナリに統一した。同じ ADR は、ハーネスが対象サービスのテストランナーを起動する場合、対象サービスの実行環境への依存はサービス側に残ると明記している。SSE probe が起動する Python は、ハーネスの実装ではなく検証対象の news-creator である。本 ADR はこの区別を保つ。ハーネスに Python やシェルの実装を足さない。

## Decision

**ハーネスの CI ジョブで、news-creator の lock から SSE probe に必要な実行環境を作る。あわせて、probe が使えない Python を「正常」として返す経路を無くす。**

### D1. CI で news-creator の `.venv` を lock から作る

- Go のテストを実行する前に、news-creator の lock から開発用を除いた依存を取り出し、`torch` と `sentence-transformers` をその先ごと取り除いて、news-creator の `.venv` に入れる。
- インストールはハッシュの照合を必須にする。
- バージョンの正本は news-creator の lock だけにする。ワークフローにパッケージのバージョンを書かない。
- probe は `.venv` を最優先で使うので、Python の選択に新しい設定は足さない。

### D2. `uv` はその手順の中だけで使う

- `uv` はバージョンを固定し、ジョブの PATH に載らない場所へ入れる。
- 環境を作る手順だけが、その場所の `uv` を直接呼ぶ。後続の手順からは `uv` が見えない。Context に挙げた、`uv` の有無で変わる動作を変えないためである。

### D3. 環境の確認を、probe が実際に読み込むものに合わせる

Python を採用する前の確認を、probe のサーバと同じ読み込み（`uvicorn`、`fastapi`、`news_creator.handler.sse_stream`）に変える。`fastapi` と `uvicorn` だけが入った Python を採用しない。

### D4. 使える Python が無いときはエラーにする

- 必ず失敗する `python3` を返す経路（Context の 4 番目）を削除する。
- 代わりに、どの Python も SSE ハンドラを読み込めなかったことと、直し方（news-creator の依存を入れる）を示すエラーを返す。
- 環境チェックはこの状態を「異常」と報告する。probe は起動を試みる前に、同じエラーで失敗する。

### D5. probe をスキップしない

依存が無い環境で SSE probe を飛ばす動作は入れない。CI で必ず飛ばされる検査は、検査していないのと同じである。

### 検討した代替案

| 案 | 却下理由 |
|---|---|
| CI に `fastapi` と `uvicorn` だけを入れる | 実測のとおり、probe の読み込みは `aiohttp` で失敗する。必要なパッケージを手で列挙すると、lock と別にバージョンと一覧を保守することになる |
| CI で news-creator の依存をすべて入れる | `torch` と `sentence-transformers` が入り、ダウンロードが数 GB になる。すべての PR で走るジョブ（制限時間 10 分）には重すぎる。probe の読み込み経路はこれらに届かない |
| probe のサーバが SSE ハンドラをファイルパスから直接読み込み、handler パッケージの初期化を避ける | 必要な依存は減るが、サービスが実際に行う読み込み方と変わる。バージョンを lock に合わせる手段は結局要る |
| 依存が無いとき SSE probe をスキップする | D5 のとおり |
| 環境を作る手順をシェルスクリプトやハーネスのサブコマンドにする | [[001028]] はハーネスの実行経路を Go のバイナリに統一している。CI の環境構築は、既存の検査ツールの導入と同じくワークフローの手順として置く。手元では news-creator の通常の依存導入がそのまま使える |
| `uv` をジョブ全体に入れる | Context のとおり、`uv` の有無で変わる動作がハーネスに複数あり、今回の修正と無関係な挙動が変わりうる |
| 必ず失敗する `python3` を返す経路を残し、CI の環境だけを直す | 環境チェックが「正常」と報告したまま probe がトレースバックで落ちる状態が、次に環境が欠けたとき再発する |

## Consequences

### Pros

- ハーネスの CI ジョブで SSE probe が実際に走るようになり、`main` とすべての PR で、ハーネスのジョブと集約チェックが通る状態に戻る。
- probe が使うパッケージのバージョンが news-creator の lock と一致する。依存の更新は lock の更新だけで CI に反映される。
- 依存が欠けた環境では、環境チェックの時点で原因と直し方が分かる。
- `fastapi` と `uvicorn` だけが入った Python が採用され、起動時に失敗することが無くなる。
- 後続の手順の PATH は変わらないので、今回の修正と無関係なハーネスの動作は変わらない。

### Cons / Tradeoffs

- 取り除くパッケージ（`torch`、`sentence-transformers`）はワークフローに手で書く。news-creator に別の重い依存が増えると、CI の環境が大きくなる。
- handler パッケージの読み込みが将来 `torch` に届くようになると、CI の SSE probe は読み込みエラーで失敗する。失敗は見えるが、取り除く一覧か読み込み経路の見直しが要る。
- CI の環境は本番の news-creator と同じではない。`torch` を使う経路は、この probe では検証されない。
- ハーネスのジョブが PyPI からのダウンロードに依存する箇所が増え、所要時間が延びる。CI での増分は未計測である。
- `uv` のバージョンはワークフローに直接書くので、依存の自動更新の対象にならない。
- news-creator の依存を入れていない開発環境では、環境チェックが失敗するようになる。これまでは「正常」と報告され、probe の実行時に失敗していた。
- 環境チェックを通すテスト用の合成リポジトリには、news-creator の `.venv` の代役になる実行ファイルを置く必要がある。
- `uv run --offline` 経由の Python（Context の 3 番目）は、採用前の確認をしないまま残る。CI では `uv` が PATH に無いので通らないが、手元でキャッシュが無いと probe の起動時に失敗しうる。
