# ADR-000951: 推論ワークロードを役割別 Ollama インスタンスに分離しローカル完結の RAG トポロジを確立する

## Status

Accepted

## Date

2026-07-25

## Affected Services

- compose (rag.yaml) — knowledge-embedder-local / rerank-local 新設
- rag-orchestrator (Go) — embedding / rerank の宛先 env 変更
- rerank-server (Python) — ONNX int8 CPU バックエンド追加 + コンテナ化
- knowledge-embedder — entrypoint のモデルリスト env 化
- Meilisearch — articles index embedder url 変更（運用 PATCH）
- recap-subworker — embed 宛先 env 変更

## Context

2 つの独立した障害・劣化が同時に顕在化した。

1. **リモート embedder ホストの死亡**: RAG embedding（embeddinggemma, 768-dim）はリモート GPU ホストの Ollama に依存しており、そのホストの停止により (a) 記事インデックスが全停止（outbox `ARTICLE_UPSERT` が 2 日で 4,800+ 件滞留）、(b) Ask Augur の retrieval が BM25-only へ無言劣化した。ADR-000943 が定めた「リモートは Enhancement Tier（Hard Remote Dependency 禁止）」の契約に対し、embedding は実質ハード依存になっていた。
2. **単一 GPU 上のモデル相互 evict（スラッシング）**: 生成モデル gemma4-e4b-12k と Meilisearch hybrid search 用 qwen3-embedding:0.6b が同一 Ollama インスタンス（news-creator-backend）に同居し、独立スケジュールされた 2 つの 5 分周期ジョブ（search-indexer warmup と pre-processor fallback バッチ）が位相ずれで交互にモデルをロードするたび相互 evict が発生。直近 24h の生成リクエストの **COLD_START 率は 100%（1098/1098）**、`/api/v1/summarize` の p99 は **310 秒**（p50 9.3s の 33 倍）に達していた。Ollama 公式 FAQ は「VRAM 不足時は keep_alive に関わらず idle モデルを evict する」ことを明記しており、`OLLAMA_MAX_LOADED_MODELS` は同居保証ではない。さらに VRAM 使用量を最大 2.2 倍過大見積もりする既知バグ（ollama/ollama#10359）が 8GB GPU でこの evict を悪化させる。ADR-000794 が想定した「news-creator-backend 専有 GPU + 1.6GB headroom」という予算前提は、その後のワークロード追加により崩れていた。

rerank（BAAI/bge-reranker-v2-m3, Apache-2.0）もリモートホスト（Apple Silicon / MPS）依存であり、ローカル完結の要件に反していた。

## Decision

**役割別に Ollama インスタンスを分離し、embedding / rerank をすべてローカルの専用サービスに集約する。**

1. **`knowledge-embedder-local`（専用 Ollama インスタンス、単一 GPU 上の別プロセス）** に全 embedding モデルを集約する: embeddinggemma（rag-orchestrator）、mxbai-embed-large（recap-subworker）、qwen3-embedding:0.6b（Meilisearch hybrid search）。`OLLAMA_MAX_LOADED_MODELS=3` で 3 モデル常駐（合計 ~3GB VRAM、生成モデルと合わせ ~6.2/8GB）。**別プロセスであることが本質**: Ollama のスケジューラ evict は自インスタンス内のモデルにしか作用しないため、生成モデルと embedding モデルの相互 evict が構造的に不可能になる。VRAM が満杯の場合は Ollama が自律的に CPU フォールバックするため、生成側を巻き込む障害にはならない。
2. **`rerank-local`（ONNX int8 CPU）**: rerank-server に `RERANK_BACKEND=onnx` モードを追加しコンテナ化。実測ベンチ（15 候補 × ~500 token）で p95 3.8s（fp32 torch は 6.2-6.8s、30 候補では 14-17s でタイムアウト超過）、リモート MPS 比 ~5 倍高速。順位品質はリモートと top1 一致・top5 4/5（相違は同点タイブレークのみ）。既存 torch/MPS パス（Mac デプロイ）は `RERANK_BACKEND=torch` デフォルトで不変。
3. **ベクトル空間互換の実測ゲート**: embeddinggemma は同一 Ollama タグ（BF16）を維持し、既存 pgvector 546k チャンクからの標本再 embedding で cosine 類似度 min 0.9999 を確認してから切替（ADR-000943 の「embedder 代替は同一モデルのみ」を実測で担保）。qwen3-embedding は Meilisearch の設定タスクで全 74,965 docs を再 embedding。

**検討した代替案と却下理由**:

- **同一インスタンスへの同居継続（MAX_LOADED_MODELS 増加や phase offset 調整）**: evict が公式仕様 + VRAM 過大見積もりバグ由来のため、パラメータ調整では構造的に解決しない。ジョブの位相をずらす案は衝突頻度を下げるだけで根絶しない。
- **リモート embedder ホストの復旧**: ローカル完結（ADR-000943 の Primary Host 契約強化）に反する。単一障害点の再導入。
- **embedding の CPU 常駐**: 移行初期に実施し動作したが（~250-300ms/chunk）、53 チャンク記事で 9.7s と大きく、GPU 余剰（当時 ~4-5GB）を使わない理由がなかった。GPU 配置で ~46ms/chunk（p50）。
- **rerank の fp32 CPU / スキップ縮退**: fp32 は 30 候補で 12s タイムアウトを超過。スキップ縮退（RRF スコアのまま返す）は品質を恒常的に落とすため、int8 で品質を保てる以上採らない。

## Consequences

### Pros

- スラッシング解消: 切替後の観測で news-creator-backend のモデルリロード 0 回、gemma4 が 100% GPU 常駐、warmup probe 3-4.6s → 0.6s。COLD_START 常態が解消
- Ask Augur の full retrieval 復旧: vector search ~110ms、rerank 10 候補 ~520ms（リモート時代 4.7s）、BM25-only 縮退フラグ消滅
- ローカル完結: embedding / 生成 / rerank のすべてが単一ホストで完結し、リモートホスト停止が RAG 品質に影響しない（ADR-000943 の Enhancement Tier 契約が実態と一致）
- rerank-server の Mac / Docker 両対応が単一コードベースで成立（backend env 切替）

### Cons / Tradeoffs

- 単一 GPU (8GB) 上のマルチプロセス構成のため、全モデル同時常駐時の VRAM は ~6.2-6.7GB と余裕が薄い。生成モデルのコンテキスト拡大や 4 つ目の embedding モデル追加は VRAM 実測ゲートを必須とする
- Ollama インスタンスが 2 つになり、モデル pull・バージョン pin（0.22.1）・監視の対象が増える
- Meilisearch の embedder 設定は依然 out-of-band（運用 PATCH）であり、コード管理されていない（ADR-000794 から継続する負債。settings 変更のたびに全 docs 再 embedding が走る点も同様）
- rerank-local の初回起動は HF から ~2.3GB ダウンロード + ONNX int8 量子化が必要（volume 永続化で 2 回目以降は数秒。量子化時ピークメモリ >4G のため mem limit 6G）
- ONNX int8 の rerank スコアは fp32 と完全一致ではない（smoke test で相対差 ~0.6%、順位への実害は確認されず）

## Deploy-model 整合性セルフチェック

- [x] 新設 compose service が `depends_on` で他 service を gate するか？
  - `knowledge-embedder-local` は `knowledge-embedder-local-volume-init`（one-shot, `service_completed_successfully`）に依存。rolling deploy（サービス単独 recreate）では init が起動されないが、(a) 対象は名前付き volume の初回 chown のみで、既存ホストでは volume が既に正しい所有権を持つ、(b) knowledge-embedder image の entrypoint は root で起動して gosu で uid 2000 へ降格する構造のため、init 不在でも自己修復可能。新規ホストの初回のみ full `up` が必要（[[PM-2026-037]] パターンの既知の緩和条件に合致）
- [x] `restart: "no"` の one-shot init container: 上記のとおり volume-init のみ。責務は初回 chown に限定
- [x] 新設名前付き volume（`knowledge_embedder_local_models`, `rerank_local_models`）の populate 責務: いずれもサービス自身の entrypoint / 初回起動時ダウンロードが担う（init container 非依存）。rolling 互換
