# ADR-000982: 記事本文の同期取得を warm RPC と background retry ladder で緩和し per-host interval を 7.5s に下げる

## Status

Accepted

## Date

2026-08-22

## Affected Services

- **alt-backend (Go)** — `orchestrator/connect/v2/articles/handler.go`、`di/article_module.go`、`orchestrator/gateway/fetch_article_gateway/`、`config/config.go`、`config/validation.go`、`utils/rate_limiter/`、`shared/driver/redis_slot_store/`
- **alt-butterfly-facade (Go)** — `internal/resilience/dependency_class.go`
- **alt-frontend-sv (TypeScript / SvelteKit)** — `src/lib/utils/{articlePrefetcher,errorClassification,articleContentState}.ts`、`src/lib/api/client/articles.ts`、`src/lib/connect/`、読書サーフェス 6 面（`ArticleDetailPanel` / `FeedDetailModal` / `FeedDetails` / `RenderFeedDetails` / `SwipeFeedCard` / `VisualPreviewCard`）、`routes/(app)/articles/[id]/+page.svelte`
- **proto** — `proto/alt/articles/v2/articles.proto`

## Context

記事を開いた瞬間に、本文欄に次の文字列が出る。

```
Source content is temporarily unavailable. Please try again shortly.
```

「しばらくして再試行」と書いてあるが、その文字列はリクエストがまだ飛んでいる最中にも、
一度も飛ばずに終わった直後にも、同じ顔で出ていた。

### 1. 本文は読み取り経路で同期に取得されている

コードを追うと、この症状に「遅延」も「非同期パイプラインの詰まり」も関与していない。
**記事本文を事前に用意する経路がそもそも存在しない。**

- `knowledge_events` 系のような pending 状態を持つ投影は本文には無い。取得中を表す状態が
  どのレイヤーにも存在せず、UI は「取れた / 取れない」の 2 値しか受け取れない。
- `RegisterHarvesterJobs` が登録する定期ジョブは 7 本（`hourly-feed-collector` /
  `daily-scraping-policy` / `outbox-worker` / `og-image-retention` / `outbox-prune` /
  `today-entrance-notifier` / `ogp-image-warmer`）で、**記事本文を取るジョブは 1 本も無い**。
- したがって本文は `FetchArticleContent` が呼ばれた瞬間に、読者を待たせながら出版社サイトへ
  取りに行く。これは [[000533]] が意図した設計そのものである（後述 §4）。

### 2. 支配的な引き金は外部サイトではなく Alt 自身の politeness gate

[[000959]] が既に分類しているとおり、この失敗の内訳の半分は**外に 1 バイトも出ていない**。
その内訳の中でも支配的なのは Redis 調停された per-host スロット待ちである。

| 設定 | 値（本 ADR 前） | 効果 |
|---|---|---|
| `RATE_LIMIT_EXTERNAL_API_INTERVAL` | 10s | ホストあたり約 1 リクエスト / 10s |
| `RATE_LIMIT_EXTERNAL_API_BURST` | 3 | Redis slot の TTL が interval 全長なので実効的にワイヤへ出ない |
| `HOST_RATE_LIMITER_REDIS_URL` | 設定済み（[[000954]]） | `cmd/backend` と `cmd/harvester` が同一スロットを共有 |
| `RATE_LIMIT_INTERACTIVE_SLOT_WAIT` | 2s（[[000959]] §5） | 対話経路はスロットを 2 秒待って諦める |

**この 2 つの数字の関係が症状の全体である。** 同一出版社の記事を 10 秒以内に 2 本目開くと、
2 秒待って `ResourceExhausted` になる。パケットは 1 つも出ていない。そして RSS リーダーで
人は 1 つのフィードを続けて読む — すなわち **1 ホストを続けて叩く**。この limiter にとって
最悪の使われ方が、このアプリの標準的な使われ方である。

（この因果は設定値とコードからの推論であり、本 ADR の作業では実スタックに対する計測を
行っていない。以降「実測」と書いていない数値はすべて設定由来である。）

### 3. これは同じ症状に対する 5 回目の対処である

| ADR | 日付 | 何をしたか |
|---|---|---|
| [[000883]] | 2026-05-02 | unary RPC に 5s タイムアウト、`VisualPreviewCard` に summary フォールバック |
| [[000884]] | 2026-05-02 | per-host inflight gate と 429 cooldown、`prefetchAhead` を 10 → 4 |
| [[000959]] | 2026-08-08 | 外部サイトと自前ゲートを failure budget から分離、対話経路に 2s の slot wait |
| [[000963]] | 2026-08-09 | `X-Alt-Failure-Scope` で到達範囲を宣言、前景 probe の配給 |

4 本とも出荷済みで、4 本とも**「失敗をどう数え、どう名付け、どこまで波及させるか」**の問題を
解いている。誰が失敗を計上するか、どのコードがどの意味か、どの cooldown を張るか。
どれも正しく、どれも本文の**到着**には触れていない。

本 ADR が初めて別の軸を触る。(a) 本文の供給側に非同期の余地を作る、(b) politeness interval
そのものに手を入れる。前者は [[000533]] の、後者は [[000959]] §5 の領分であり、どちらも
「既に決まっていること」なので、先に両方との関係を明示する。

### 4. [[000533]] との関係 — SUPERSEDE ではなく NARROW である

[[000533]] は `AutoFulltextFetchUsecase` を削除し、Cons に次を明記した。

> RSS 収集直後に全文付き記事が自動生成されなくなるため、ユーザーが初めて記事を開く際に
> オンデマンド取得の待ち時間が発生する

**本 ADR の症状は、この Cons が 5 か月後に読者から見えた姿そのものである。** さらに
[[000533]] は代替案として「非同期キュー化して負荷を分散する案」を**明示的に却下**している。
したがって本 ADR は、素朴に読めば受理済みの決定を反転させているように見える。していない。
[[000954]] が [[000945]] の measurement-first 基準に対して取った形と同じ、**部分的な上書き**である。

[[000533]] が削除したのは「購読を起点に、ユーザーが読むかどうかに関係なく全文を取る」経路で、
その却下理由は「**ユーザーが閲覧しない記事を取得する**問題は解消されない」だった。
本 ADR が足す warm は、その却下理由が当たらない範囲に限定してある。

| [[000533]] が削除した `AutoFulltextFetchUsecase` | 本 ADR の `BatchPrefetchArticleContent` |
|---|---|
| 起点は `CollectFeedsJob`（購読の RSS 収集） | 起点は読者が今スワイプしている lookahead window |
| 対象は購読フィード × 記事 × ユーザーの組み合わせ全体 | 対象は「あと数枚で開かれる」と読者の操作が示した数件のみ |
| harvester 側の定期ジョブとして常時走る | 定期ジョブを 1 本も追加しない。読者がスワイプを止めれば 0 件になる |
| hourly job の 30 分タイムアウトに線形に効く | RPC は即座に返り、warm は 8 本の pool で shed される |
| 1 件の外部障害が `Process()` 全体をブロックする | 各 warm は detached で、失敗は自分 1 件で終わる |

そして「非同期キュー化」でもない。本設計は **shed-not-queue** であり、pool が埋まっていれば
warm は捨てられる。キューが無いので、[[000533]] が懸念した「負荷を後ろに積む」構造は生じない。

**結論: 本 ADR は [[000533]] を supersede しない。** frontmatter に `supersedes` キーを置かない。
[[000533]] の決定 — 購読起点の自動全文取得を持たない — は全面的に有効なままで、本 ADR が
狭めるのは同 ADR の Cons のうち「ユーザーの生きた操作シグナルがある数件」の部分だけである。
[[000533]] の Related ADRs にも本 ADR にも逆辺は DocDag が算出する。

### 5. [[000959]] §5 の改定 — politeness を 1 ミリ緩める

[[000959]] §5 はこう書いてある。

> **politeness は 1 ミリも緩めない。** `ExternalAPIInterval` / `ExternalAPIBurst` /
> `NamespaceExternalAPI` は変更しない。

本 ADR は `ExternalAPIInterval` を 10s から 7.5s に下げる。**これは同 ADR の当該文の改定であり、
その事実を曖昧にしない。** オーナーの判断は次のとおりで、そのまま記録する。

- **5s は短すぎる。** repo rule 2 の床にちょうど等値になり、以後どんな微調整も規約違反になる。
- **10s は長すぎる。** 買っている politeness に対して、読者が払っている待ち時間が見合わない。
- **7.5s は repo 自身の 5 秒ルールの上に留まる。** 下回っていない。
- **publisher が宣言した `robots.txt` Crawl-delay は独立に AND で執行される。**
  `ScrapingPolicyGateway` が自前の状態で持っており、本 ADR は触っていない。したがって実効間隔は
  **max(7.5s, Crawl-delay)** であり、10 秒以上を宣言している publisher にとっては何も変わらない。
- **交換条件として 5s の床をコードで執行する。** それまで validation は 1 秒超を通していた。
  rule 2 は「5 秒」と書いてあるのに、実際にそれを守らせていたのは配布時の設定値だけだった。

[[000959]] 本文は履歴として改変しない。同 ADR の他の決定（§1〜§4、§6）はすべて有効なままであり、
[[000963]] が依存している部分も無傷である。frontmatter の `supersedes` には記載しない
（改定は §5 の 1 文であって、完全置換ではない）。

## Decision

**本文の供給に「まだ来ていない」という状態を初めて作り、warm RPC・background retry ladder・
per-host interval の 3 方向から同期取得の待ちを削る。ただし publisher から見た per-host の
上限は 1 ミリも上げない。**

### 1. background prefetch の失敗を retry する（alt-frontend-sv）

`runFetch` の catch はキャッシュエントリを消し、cooldown を張り、warn を出して `null` を返して
いた。**その項目が再試行されるのは、後続の `triggerPrefetch` がたまたままだ lookahead に
持っていた場合だけ**だった。読書サーフェスではこれが「開いた瞬間に unavailable、以後も自動
復帰しない」として現れる。

- `isRetryableContentError()` を新設し、メッセージ部分一致ではなく **Connect code と
  `X-Alt-Failure-Scope` metadata** で分岐する（[[000963]] の契約をそのまま使う）。
  `host` が刻まれた `ResourceExhausted` は publisher 自身の 429 なので retry しない。
  **無刻印**の `ResourceExhausted` は自前の host-slot queue であり、ワイヤに何も出していないので
  retry する。
- 失敗を ledger に記録して timer を張り直す。遅延は **Full Jitter**
  `random(0, min(30s, 1000 * 2**attempt))` — インシデント中にクライアントが揃って再送しない
  ため。1 項目あたり最大 **2 回**。遅延の**下限は `max(Retry-After, global pause, host cooldown)`**
  で、直前の失敗が閉じたゲートの内側に retry が着弾することはない。`Retry-After` は 60s で
  clamp し、既存 cooldown の上限も同時に押さえる。
- ledger のエントリは、その項目が lookahead window から外れた時点で捨てる。読者が通り過ぎた
  カードのために出版社を叩かない。
- lookahead を **ホストの空き具合で並べ替える**。cooling down でもなく in-flight でもない
  ホストが早い rung を取り、同点は元の lookahead 順。rung カウンタはスキップしたスロットも
  歩くのでペース配分は不変。**`prefetchAhead` は変更しない**（[[000884]] が 10 → 4 に切った値）。

外向きレートは常に neutral-or-lower である。retry は変更していない per-host serialization /
host cooldown / global pause をそのまま通り、着弾した retry は読者がそのカードに到達したときに
出すはずだった前景リクエストを 1 本消す。

### 2. `BatchPrefetchArticleContent` RPC を新設する（alt-backend / proto / BFF）

読者があと数枚で開くと思われる記事の本文を、応答を返してから温める。**順序がこの設計の全体**である。

```
validate → 1 ホスト 1 URL → pool slot を取る   （同期・安価・失う自由がある）
  → store を probe する                        （無料）
    → WaitForHost                              （権威的。拒否のコストは 0）
      → CanFetchArticle → fetch                （窓を消費する。最後に、1 度だけ）
```

**取り消せないゲートを最後に置く。** 逆順にすると、gate に尋ねてから pool やホストが埋まって
いると分かった時点で、パケットを 1 つも出さずに publisher の窓を焼く。そして次にその窓に
拒否されるのは、その記事を今まさに開いた読者自身である。

- **1 コールにつき 1 ホスト 1 URL。** handler 内で、何かを claim する前に dedupe する。残りは
  `skipped_same_host_count` として返す。単一 publisher のバッチは 1 件だけ温めて、残りを
  キューに積まない。
- **pool は 8 本（`maxConcurrentContentWarms`）、満杯なら queue せず shed。**
  `context.WithoutCancel` + 明示的な 30s の budget（`contentWarmBudget`）で、warm が応答より
  長生きしつつ無限には生きない。
- **store probe が先。** 既に保存済み（本文 100 文字以上）の記事は、ホストの順番を 1 度も
  claim しない。
- **rate limiter の namespace も interval も新設しない。** warm は対話 fetch と同じ
  `infra.RateLimiter` / `NamespaceExternalAPI` から、1 レイヤー早くホストの順番を取り、
  `PrefetchSlotWait`（既定 250ms）で諦める。**キューには並ばない。**
- **配線状態は宣言する（rule 8 / [[000928]] / [[000966]]）。**
  `RATE_LIMIT_PREFETCH_SLOT_WAIT` は `string` 型で、`"off"` が unset とは区別される明示的な
  無効化。`0` は「無限に待つ」と読み替えず起動時に拒否する — warm にとってそれは、この設計が
  避けようとしている反転そのものだからである。起動時に `article_prefetch.enabled` /
  `.disabled` を出し、無効時は変数名を名指しした `FAILED_PRECONDITION` を返し、
  **enabled と宣言されているのに配線されていなければ `NewHandler` で panic** する。
- **この RPC は `X-Alt-Failure-Scope` を一度も刻まない。** 返すのは `Unauthenticated` と
  `FailedPrecondition` だけで、どちらも我々の失敗である。publisher 起因の結果は応答より後にしか
  起きないので、[[000963]] が `host` scope に求める「positively 帰属できる失敗」がこの経路には
  存在しない。
- **BFF では `external_content` ではなく telemetry に分類する**
  （`internal/resilience/dependency_class.go`）。warm に並んだデッドリンクが
  `FetchArticleContent` の前の breaker を開けて、warm が速くしようとしている読み取りを
  暗転させないため。
- **CDC を先に RED にした（rule 7）。** provider test は stub ではなく実物の `ArticleService`
  handler を mount し、proto も handler も存在しない状態で 404 / `text/plain` を返して RED に
  なることを確認してから GREEN に進んだ。

### 3. per-host interval を 7.5s にし、5 秒の床をコードで執行する（alt-backend）

```go
// config/validation.go
const MinExternalAPIInterval = 5 * time.Second
```

- `RateLimitConfig.ExternalAPIInterval` の既定を `10s` → **`7.5s`**。
- `MinExternalAPIInterval` 未満は**起動時に非ゼロ終了**。変数名と床を名指ししてエラーを出す。
  **clamp しない** — この値は他人のサーバーに対する約束であり、過少申告は静かに直すものではなく
  エラーである（rule 9）。
- burst は **3 のまま**。配布構成ではワイヤに届かない（ローカルのトークンも結局 Redis スロットを
  取る必要があり、その TTL は interval 全長）。interval を縮めたことで、burst が貸す
  「2 × interval 分の頭金」も絶対値としては小さくなる。
- ホストあたりの持続レートは **6 req/min → 8 req/min**。
- 1 つだけ忠実に表現できない値がある。Connect の `Retry-After` は RFC 9110 の整数 delta-seconds
  なので、`handler.go` は 7.5s を `math.Ceil` で **8** に丸める。丸めは常に切り上げなので、
  クライアントは必要より早く再送するのではなく、必ず遅く再送する。
- 7.5s は struct tag の既定として初めて整数秒でない値になる。token bucket / Redis slot TTL /
  429 backoff / `Retry-After` はすべて `time.Duration` 演算で半秒を保つ。7s への truncation が
  ログに何も残さず rule 2 を破ることを避けるため、`utils/rate_limiter/fractional_interval_test.go`
  と `shared/driver/redis_slot_store/fractional_ttl_test.go` でこれを pin した。

### 4. 読書サーフェスに「まだ来ていない」を持たせる（alt-frontend-sv）

読書サーフェス 3 種が、3 種類のハードコードされた文字列で in-flight を unavailable に畳んで
いた。`SwipeFeedCard` の `onMount` catch に至っては `console.error` だけで、自動取得が失敗しても
画面には RSS の要約が何事もなかったように出ていた。

- `articleContentState.ts` を新設し、**フェーズとその文言を決める唯一の場所**にする。
  `idle` / `pending` / `retrying` / `ready` / `failed`。全サーフェスをここと
  `articleContentErrorMessage` に通し、リテラルの再ハードコードを消した。
- **RSS の description は常に出す。** 本文が来ていようが来ていまいが、読者の手元が空になる瞬間を
  作らない。
- 終端状態は**両方の救済**を出す — `Try again` と、出典サイトで読むリンク。
- **前景の自動再試行は 1 回だけ、1 ケースだけ。** `foregroundRetryDelayMs` が許すのは
  **`X-Alt-Failure-Scope: host` が刻まれていない `ResourceExhausted`** のみ。無刻印は
  alt-backend が自前の host-slot gate に帰属させたということで、パケットは出ておらず、
  下流を叩いてもおらず、`Retry-After` が既にスロットの空く時刻を言っている。待ち時間は
  500ms〜10s に clamp。

### 5. `content: ""` を明示的なエラー値にする（alt-frontend-sv）

空文字を falsy な no-op として扱うのは [[000581]] の無限 `$effect` を生んだ経路そのものである。
`EMPTY_CONTENT_ERROR`（`Code.DataLoss`）を与えて、他の失敗と同じ formatter で終端状態に
到達させる。`DataLoss` は transient 集合に入らないので、これは正しい — 空の本文は 500ms 後に
自分で埋まったりしない。

---

### 最重要: warm と ladder は dedupe されないが crawl-delay gate は共有する

**この ADR で次に触る人が最初に踏むのはここである。**

`di/article_module.go` は prefetch 用に **2 つ目の `ArticleUsecase` インスタンス**を作る。

```go
prefetchArticleUC = fetch_article_usecase.NewArticleUsecaseWithScrapingPolicy(
    fetch_article_gateway.NewPrefetchFetchArticleGateway(),  // ← 別インスタンス（意図的）
    infra.RobotsTxtGateway, articleRepoGw, ragAdapter,
    scrapingPolicyGw,                                        // ← 同一インスタンス（意図的）
)
```

`scrapingPolicyGw` の共有は load-bearing である。crawl-delay の状態（`lastRequestTime`）は
その gateway インスタンスの中にあり、2 つ持てば読者と warmer が 1 つの crawl delay の中で
1 grant ずつ得てしまう — publisher に 1 回と約束した窓で 2 回叩くことになる。

だが `singleflight.Group` は `ArticleUsecase` 構造体のフィールドである。**インスタンスが 2 つある
以上、group も 2 つある。**

> **同じ URL に対する warm と読者の fetch は dedupe されない。**
> **一方で crawl-delay gate は共有している。**

結果、後から来た方が `ErrCrawlDelayNotElapsed` → `ResourceExhausted` を受け取る。クライアントは
それを host cooldown に変換し、カードが目に見えて壊れる。**これは [[000884]] が外から観測した
失敗の形を、内側から自作していることになる。**

現在の設計はこれを**クライアント側の 3 つの取り決め**で回避している（`articlePrefetcher.ts`）。

1. **ladder が window の先頭 2 スロットを所有する**（`LADDER_OWNED_AHEAD = 2`）。読者が実際に
   到達するカードであり、かつクライアントキャッシュを埋められる唯一の経路でもある
   （warm は本文を返さない）。warm の対象になるのはそれより後ろのスロットだけ。
2. **tail スロットは、ladder 所有スロットとホストを共有する場合 / そのホストが cooling down の
   場合 / そのホスト向けの ladder リクエストが in-flight の場合、スキップする。**
3. **`WARM_SETTLE_MS = 10s`** が warm 済みの記事を ladder から遠ざける。この 10 秒は usecase の
   外部 fetch budget（`defaultExternalFetchTimeout = 8s`）より上に取ってある。warm が
   crawl-delay の grant を握っている最中に ladder がそこへ歩いていく順序を閉じるため。
   **前景の `ensureContent` は免除**する — 読者自身のリクエストをブロックするのは、この仕組みが
   避けようとしている劣化そのものだからである。

**3 つとも 1 クライアント内の取り決めにすぎない。** サーバ側にこの衝突を防ぐものは何もない。
2 つ目のタブ、別デバイス、あるいは将来この RPC を呼ぶ別の呼び出し元は、そのまま衝突を再現する。
この RPC に手を入れるときは、まずこの段落に戻ること。

### crawl-delay gate は「問い合わせ」ではない — grant で窓を消費する

`ScrapingPolicyPort.CanFetchArticle` は純粋なクエリではない。grant した瞬間に
`lastRequestTime[domain] = time.Now()` を刻む。実際に fetch したかどうかは見ていない。

作業中、これを「fetch 時に刻む」形へ変更する検討を行い、**正しく見送った**。理由は 2 つある。

- 既存テスト `TestScrapingPolicyGateway_CanFetchArticle_CrawlDelay` が、fetch を挟まない
  2 連続呼び出しに対して grant → deny を pin している。この挙動が契約として固定されている。
- 刻印を fetch まで遅らせると、**並行する 2 つの呼び出し元が両方 gate を通る**。crawl delay の
  意味が消える。

代償として、**パケットを 1 つも出さずに窓（あるいはホストの順番）が焼かれる経路が 3 つ残る**。

| # | 経路 | 焼かれるもの |
|---|---|---|
| 1 | **singleflight collapse** — 同一 URL の 2 番目の呼び出し元が gate を通った後、`fetchGroup.Do` で先行の in-flight に畳まれる。自分のリクエストは発行されない | crawl-delay 窓 |
| 2 | **grant 後の fetch 失敗** — gate は通ったが、dialer の SSRF 拒否や期限切れでワイヤに出ないまま終わる | crawl-delay 窓 |
| 3 | **slot 保持後の gate 拒否** — warm 経路は `WaitForHost` でホストの順番を取ってから gate に尋ねる。gate が crawl-delay で拒否すると、Redis の host slot はその interval ぶん消費済み | host slot |

これを直すには port に **token-guarded / fail-closed な `RetractFetchReservation`** が要る。
token が要るのは、無記名の retract では他人の予約を巻き戻せてしまうため。fail-closed が要るのは、
予約が見つからないときに黙って no-op する retract は「巻き戻せた」と区別が付かず、rule 8 が
禁じる silent fallback そのものになるため。**本 ADR ではこれを実装していない。** 3 経路とも
「publisher を余計に叩く」方向ではなく「自分が 1 回損をする」方向に倒れるため、fail-safe 側の
負債として残す。**明示的な future work とする。**

### 前景と背景で retry の述語が違う理由

`isRetryableContentError`（背景 ladder）は `Code.Unavailable` を**許す**。
`foregroundRetryDelayMs`（読書サーフェス）は**許さない**。この非対称は意図的である。

[[000959]] は「`isTransientError()` に `Code.Unavailable` を追加」を、**2 箇所が 500ms 後に再送し
開いた breaker を叩き直す**という理由で却下した。**その却下は今も有効で、意図的に維持している。**
そして読書サーフェスは、まさにそのインシデントが起きた面である。

背景 ladder が同じコードを許せるのは、そこが同じ形をしていないからである。Full Jitter が入り、
上限 2 回で止まり、遅延の下限が `max(Retry-After, global pause, host cooldown)` に張り付き、
[[000963]] の global pause が `global` 刻印の `Unavailable` に対して ladder ごと停止させる。
**lockstep での再送が構造的に起きない。** 前景は読者の画面であり、jitter も予算も無い即時の
1 発なので、そこには入れない。

### 却下した代替案

| 案 | 却下理由 |
|---|---|
| harvester に記事本文の定期ジョブを足す | [[000533]] を実際に反転させる。「ユーザーが読まない記事を取得する」問題が当時のまま戻る |
| 非同期キューにして負荷を平準化する | [[000533]] が明示的に却下済み。キューは per-host ceiling を上げないので、待ち時間が queue depth に移るだけ |
| interval をちょうど 5s にする | repo rule 2 の床に等値。以後どんな微調整も規約違反になる。余裕を残す |
| interval は据え置き burst を上げる | burst は Redis slot TTL の前で消える。publisher から見た間隔は変わらない |
| 床を超えた値を clamp して起動する | 他人のサーバーへの約束を黙って直すことになる。rule 9 に従い非ゼロ終了 |
| warm 用に rate limiter namespace を分ける | [[000959]] が却下済み。同一 publisher が 1 interval に 2 リクエスト受ける |
| warm を同期化して結果を返す | 読者の待ちが増えるだけで、warm の存在意義が消える |
| `CanFetchArticle` を純粋クエリにして fetch 時に刻む | 既存テストが grant → deny を pin。加えて並行 2 呼び出しが両方通る |
| 前景の auto-retry に `Code.Unavailable` を足す | [[000959]] の却下が有効。開いた breaker を読者の画面から叩き直す |
| `prefetchAhead` を増やして warm の適用範囲を広げる | 上限は変わらないので、増やしても衝突と cooldown が増えるだけ。まず測る（後述） |

## Consequences

### Pros

- **本文の供給に初めて非同期の余地ができた。** [[000533]] 以降、本文を事前に用意する経路は
  1 つも無かった。読者の生きた操作シグナルがある範囲に限って、それが 1 つできた。
- **失敗した background prefetch が自動で戻ってくるようになった。** それまで再試行は
  「後続の `triggerPrefetch` がまだその項目を持っていたら」という偶然に依存していた。
- **読書サーフェスが verdict を先に出さなくなった。** pending / retrying が failed と別の顔を
  持ち、文言は 1 箇所（`articleContentState.ts`）で決まる。3 面 3 リテラルの状態が解消した。
- **どの終端状態でも読者に 2 つの出口がある** — 再試行と、出典サイトで読むリンク。
- **同一ホスト連続の待ちが 10s → 7.5s に縮んだ。** ホストあたり 6 req/min → 8 req/min。
  publisher が `Crawl-delay` を宣言していれば `max(7.5s, Crawl-delay)` なので、10 秒以上を
  宣言している publisher には何の変化もない。
- **rule 2 の 5 秒がコードで執行されるようになった。** それまで validation は 1 秒超を通しており、
  ルールを守らせていたのは配布時の設定値だけだった。設定規律に依存する不変条件が 1 つ減った。
- **`content: ""` が状態として扱われるようになった。** [[000581]] の無限 `$effect` を生んだ
  falsy no-op が、`Code.DataLoss` を持つ明示的なエラー値になった。
- **warm RPC の配線状態が宣言的である。** enabled / disabled が起動ログに出て、
  「enabled と言いながら未配線」は起動時に panic する。オペレータのボタン操作時にではない
  （rule 8 / [[000928]] / [[000966]]）。

### Cons / Tradeoffs

- **publisher から見た上限は 1 ミリも上がっていない — 上げていないことが効果の上限でもある。**
  warm RPC が勝てるのは **異なるホストにまたがるバッチ**だけである。単一 publisher を読み続ける
  セッション、つまり本 ADR の Context §2 が最悪ケースとして挙げたまさにその使われ方では、
  warm はほぼ何もしない。1 コール 1 ホスト 1 URL の dedupe があるため、単一ホストのバッチは
  1 件温めて残りを `skipped_same_host_count` に落とす。
- **既定のスワイプモードでは warm が 1 度も発火しない。** 呼び出しは `prefetchAhead > 2` の
  ときだけで、既定の swipe は 2、visual-preview が 4 である。実質 visual-preview 専用の機能に
  なっている。オーナーはこれを承知の上で受け入れ、**広げる前に測る**ことを選んだ。
- **本 ADR の作業では実スタックに対する計測を一切行っていない。** 効果に関する記述はすべて
  設定値とコードからの推論であり、[[000946]] / [[000959]] / [[000963]] が残した
  「breaker の open / half-open 遷移が実スタックで未検証」という状態も解消していない。
- **crawl-delay 窓 / host slot をパケット無しで焼く経路が 3 つ残っている**（上表）。
  `RetractFetchReservation` は意図的に作らなかった。
- **warm と ladder の非衝突は 1 クライアント内の取り決めでしかない。** サーバ側の防御は無く、
  2 つ目のタブや将来の別呼び出し元は衝突を再現する。踏んだときの症状は [[000884]] と同じ形
  （host cooldown と壊れたカード）で、原因だけが自作である点が違う。
- **[[000959]] を後から読む人は「politeness は 1 ミリも緩めない」を読むことになる。** それは
  出荷中の既定に対しては既に真ではない。履歴として同 ADR は改変しないので、本 ADR が
  改定であることを Related ADRs と本文の両方に書いてある。それでも、両方を読まないと
  誤読する構造は残る。
- **`alt-perf` のスクリプトが陳腐化した。** `alt-perf/scripts/run-sv-connect-composite-test.sh` は
  `RATE_LIMIT_EXTERNAL_API_INTERVAL=10ms` を設定しており、**5s 床の導入で alt-backend が起動時に
  非ゼロ終了するようになった**。同スクリプトと `alt-perf/k6/README-sv-connect-composite-10m.md`
  は併せて `RATE_LIMIT_EXTERNAL_API_UNSAFE_FAST=true` を設定・記載しているが、
  **この環境変数を読む Go コードはリポジトリに 1 行も存在しない**（`--include="*.go"` で全 grep 済み。
  README 自身が「要: alt-backend コード一時変更」と注記している）。負荷試験は mock-rss を
  相手にするので床の対象外にすべきだが、その分岐は存在しない。**別途の対応が要る。**
- **component テストは黙って走らなくなりやすい。** `src/**/*.svelte.{test,spec}.ts` は
  **77 ファイル**（`.svelte.test.ts` 55 + `.svelte.spec.ts` 22）実在するのに、
  `VITEST_BROWSER=true` で起動した browser project が収集したのは **66 ファイル / 517 テスト**
  だった（実測）。差の 11 ファイルがなぜ収集されないかは未解明で、`exclude` の
  `src/lib/server/**` 配下には 1 つも該当しない。**未解決の発見として記録する** —
  収集されないテストは失敗もしないので、CI は緑のままこれを報告しない。
  そもそも `bun run test` は `VITEST_BROWSER=true` が無いと 1 つも収集しない
  （`vitest.config.ts` が警告を出すので silent ではないが、CI のログでは流れる）。さらにこの
  開発サンドボックスでは `@vitest/browser-playwright` が要求する Chromium build が実在しない —
  runner は `chromium_headless_shell-1234` を探すが、`/opt/pw-browsers` に実在するのは `-1194`
  である。この不一致のあいだ browser project は起動すらせず、**本 ADR の作業中も
  当初その状態だった**。`vitest.config.ts:27` の `VITEST_CHROMIUM_EXECUTABLE_PATH` が
  そのための正規の逃げ道で、実在するバイナリを指せば 66 ファイル / 517 テストが走る（実測）。
  リポジトリの設定は変更していない。
- **CI runner には `libpact_ffi` が要る。** 無いと contract テストは実行時ではなく **link 時に
  全滅**する。`.github/workflows/proto-contract.yaml` が v0.4.28 を取得し、
  `docs/runbooks/runner-setup.md` と `docs/testing-strategy.md` が前提として記載しているが、
  self-hosted runner を組み直したときに最初に踏む種類の依存である（[[000589]]）。
- **`Retry-After` は 7.5s を忠実に表現できない。** RFC 9110 の整数 delta-seconds なので 8 に
  切り上がる。切り上げなのでクライアントは常に必要より長く待つ側に倒れるが、half-second は
  ワイヤ上には存在しない。
- **`X-Alt-Failure-Scope` に依存する分岐が 1 つ増えた。** [[000963]] が Cons に挙げた
  「proto にも Connect の標準にも現れない Alt 固有の out-of-band 契約」の利用箇所が、
  背景 ladder と前景 auto-retry の 2 つの述語に広がった。stamp を忘れた producer は
  「無刻印 = 自前ゲート」に倒れ、**retry される方**に落ちる。

## Deploy-model 整合性セルフチェック

本 ADR はアプリケーションコード、proto、設定既定値のみを変更する。compose service の新設も、
`depends_on` の追加も、名前付き volume の追加も無い。

- [x] 新設 compose service が `depends_on` で他 service を gate するか？ — **N/A**（新設なし）
- [x] 新設 compose service に `restart: "no"` の one-shot init container を含むか？ — **N/A**（新設なし）
- [x] 新設名前付き volume を populate する責務はどこにあるか？ — **N/A**（新設なし）
- [x] いずれも該当しない → **rolling 互換**

ただし rolling deploy に関して 2 点、明示しておく。

1. **`MinExternalAPIInterval` は fail-fast である。** `RATE_LIMIT_EXTERNAL_API_INTERVAL` に
   5s 未満を設定しているホストは、この変更を含む image に入れ替えた時点で**起動しなくなる**
   （warn-and-limp はしない。rule 9）。配布既定は 7.5s なので、明示的に上書きしている環境だけが
   対象になる。`alt-perf` の負荷試験構成（10ms）が該当する。deploy 前に当該ホストの `.env` を
   確認すること。
2. **warm RPC は 3 サービスの deploy 順序に依存しない。** フロントが先に出た場合、
   `BatchPrefetchArticleContent` は `Unimplemented` になる。クライアントはこれを
   `FailedPrecondition` の latch 経路には入れず debug ログに落とし、cooldown を張らず、
   URL を ladder へ返す。したがってカバレッジは従来どおりで、5 秒に 1 回の無駄な RPC が
   バックエンドが出るまで続くだけである。バックエンドが先に出た場合は誰も呼ばない。
