# ADR-001025: 購読者のいないフィードの収集を止め、フィード別の流入と読了率を見せて、購読ごとの日次上限を設ける

## Status

Accepted

## Date

2026-11-18

## Affected Services

- alt-harvester — 定期収集ジョブ `hourly-feed-collector` の対象から購読者のいない `feed_links` を外す
- alt-data-hub — 収集対象の購読フィルタ、日次上限列を含む購読データの読み書き、フィード別流入統計の取得 capability を追加する
- alt-backend — `FeedService.GetFeedInflowStats` の実装と、`daily_cap` による未読一覧の絞り込みを行う
- alt-butterfly-facade — 新規 RPC の仲介を通す
- alt-frontend-sv — `routes/(app)/settings/feeds/+page.svelte` にフィード別流入・読了率・並べ替え・日次上限の設定 UI を追加する
- proto — `FeedService.GetFeedInflowStats` と `FeedSource.daily_cap` を追加する
- migrations-atlas — `user_feed_subscriptions.daily_cap` 列を追加する

## Context

持ち主が 2026-11-18 に、製品の目的を「読むこと、読ませること、読んだ情報が血肉になること」と定めた（[[001015]]）。主端末は Android の Chrome であり、日常の面は Gallery と Swipe である。流入の絞り込みも段階 R4 の範囲に含める。

2026-11-17 時点の本番データを読み取り専用で計測したところ、直近 30 日の流入と利用状況は次のとおりだった。

- 直近 30 日の流入は 44,158 件である。内訳は、購読中の 66 本のフィードリンクから 23,676 件、購読者のいない 9 本のフィードリンクから 20,482 件である。
- 要約・タグ付け・埋め込みは `articles` に対して働く。30 日で作られた `articles` 1,314 本のうち 1,312 本は購読中のフィード由来である。購読者のいないリンクからの流入が増やしているのは、収集処理と Recap・Topic Cards の入力だけである。
- 購読中のフィードにおける 30 日の流入と既読の割合（上位）は、最多の配信元が 8,937 件 / 5.1%、2 番目が 2,782 件 / 5.3%、3 番目が 2,035 件 / 9.1%、4 番目が 1,700 件 / 13.9%、5 番目が 1,526 件 / 9.3%、6 番目が 1,031 件 / 4.2%、7 番目が 982 件 / 4.0%、8 番目が 829 件 / 10.0%、9 番目が 605 件 / 2.8% である。

リポジトリのコードを確認したところ、現状の構造は次のとおりである。

- **収集経路と購読解除の挙動**: 定期収集は `alt-harvester` の `hourly-feed-collector`（`alt-backend/app/orchestrator/job/registry.go:22-27`、`job_runner.go:43-90`）が担う（Inoreader 経路は `compose/workers.yaml:57` と `compose/ai.yaml:404` で既定 `INOREADER_SYNC=disabled`）。`alt-backend/app/shared/driver/alt_db/fetch_rss_feed_urls_driver.go:14-17` は `feed_links` と `feed_link_availability` だけを見ており、`user_feed_subscriptions` を参照しない。購読解除時は [[000502]] により `DeleteSubscription`（`alt-backend/app/shared/driver/alt_db/subscription_driver.go:67-87`）が `user_feed_subscriptions` の行だけを消すため、`feed_links` 行が残る。同ファイル `subscription_driver.go:72-78` の `deleteOrphanFeedLinkQuery` は `FeedRepository.DeleteFeedLink`（`feed_link_driver.go:114,122`）から参照されているものの、`alt-backend` / `alt-harvester` に `DeleteFeedLink` を呼ぶ本番経路がなく、購読解除後も収集が続く。
- **未読一覧と Recap・要約の入力**: 未読一覧の SQL（`alt-backend/app/shared/driver/alt_db/feed_sql_builder.go:51-100`）は `user_feed_subscriptions` で絞り、新しい順（`f.created_at DESC, f.id DESC`）に並べるだけである。Swipe と Gallery の未読の山は購読中のフィードだけから作られており、購読者のいないリンクの収集を止めても山の量は減らない。一方、Recap の入力（`alt-backend/app/shared/driver/alt_db/feeds_in_window_driver.go:14-46`）と未要約記事取得（`list_unsummarized_articles_driver.go:25-58`）は購読を見ない。
- **購読テーブルと UI の現状**: `user_feed_subscriptions`（`migrations-atlas/migrations/20260211000002_create_user_feed_subscriptions.sql:2-9`）は `user_id`、`feed_link_id`、`created_at` のみで上限列を持たない。設定画面 `alt-frontend-sv/src/routes/(app)/settings/feeds/+page.svelte`（L414-467）が出すのは URL、健全性バッジ、購読切り替え、削除ボタンだけであり、フィード別の読了率を出す SQL はない。`alt-frontend-sv/src/lib/components/mobile/feeds/swipe/SwipeFilterSortSheet.svelte:42-46` と `SwipeFeedScreen.svelte:68,347-355` の除外フィルタは 1 ドメインのみで保存されない。
- **SQL の業務判断に関する規則**: `docs/wiki/architecture/clean-architecture.md:76` および `.claude/skills/immutable-design-guard/references/alt-invariants.md:136,149`（[[000452]]・[[000558]] 等）で、SQL に業務判断を置かずアプリケーション層で扱う方針が定められている。

## Decision

1. **購読者のいない `feed_links` は収集しない。** `FetchRSSFeedURLs`（`alt-backend/app/shared/driver/alt_db/fetch_rss_feed_urls_driver.go`）の対象取得 SQL に、`user_feed_subscriptions` に購読が 1 件以上あること（`EXISTS`）を条件として足す。`feed_links` の行は消さず、再び購読されたら収集を再開する。なお、この変更では Swipe と Gallery の未読の山の量は減らず、減るのは `alt-harvester` の収集と Recap・Topic Cards の入力だけである。理由は、無用な収集とバッチ入力を止めつつ、再購読時に履歴と健全性状態を保ったまま再開できるようにするためである。
2. **フィード別の流入と読了率を設定画面に出す。** `FeedService.GetFeedInflowStats` を新設し、直近 30 日のフィード別の流入件数、読んだ記事数、読了率を返して `routes/(app)/settings/feeds/+page.svelte` に表示する。読了率の「読んだ」には [[001018]] の定義（末尾到達または本文の長さに見合う滞在による `reading_sources`）を使う。[[001018]] より前の期間は旧規則（`HomeItemOpened` による「開いた」）の値として区別して返し、Swipe で払っただけの既読は読了に数えない。理由は、流入の偏りと実際に読まれた割合を持ち主が事実で確認できるようにするためである。
3. **購読ごとの日次上限を設ける。** `user_feed_subscriptions.daily_cap` 列（`INTEGER NULL`、未設定は上限なし）をマイグレーションで追加する。日次上限は未読の山（Gallery / Swipe の未読一覧）への出し方に効かせるものとし、収集と `feeds` への保存は変えない。検索では上限を超えた記事も見つかる状態を保つ。実装の配置は R4 で決め、その際に「SQL に業務判断を置かない」規則（`docs/wiki/architecture/clean-architecture.md` 等）と整合させる。理由は、多量配信元の記事が未読の山を埋め尽くすのを防ぎつつ、検索可能性と過去の記録を失わないためである。
4. **読了率の低いフィードを設定画面で並べ替えられるようにし、自動解除はしない。** `routes/(app)/settings/feeds/+page.svelte` で流入数や読了率による並べ替えを提供する。読了率が低くてもシステム側で自動的に購読解除しない。理由は、何を読むかは持ち主自身が決めるべきであり、システムは判断材料と上限・解除の操作だけを提供するためである。
5. **Recap と Topic Cards の入力は項目 1 以上の制限を足さない。** 項目 1 で購読者のいないフィードの収集が止まれば Recap と Topic Cards の入力は自然に減るため、それ以上の絞り込みはしない。理由は、購読中フィードの中での話題把握に必要な母集団を狭めすぎないためである。
6. **Swipe の除外フィルタはこの ADR では変えない。** `SwipeFilterSortSheet.svelte` の 1 ドメイン・非永続の仕様は維持する。理由は、永続的な流入調整は `daily_cap` と購読設定で担い、一時除外と責務を混ぜないためである。

### 検討した代替案

- **(a) 購読者のいない `feed_links` を削除する**: 退けた。削除すると再購読時に元の状態へ戻せないためである。
- **(b) 未読の山を順位付け（スコアリング）で並べ替える**: 退けた。並べ替えても未読の総量は減らず、なぜその順番になったのかを持ち主に説明しにくいためである。
- **(c) 読了率の低いフィードを自動で解除する**: 退けた。理由は決定項目 4 のとおり、何を読むかは持ち主が決めるためである。

## Consequences

### Pros

- 購読者のいない 9 本のフィード（計測上 30 日で 20,482 件）の収集と Recap・Topic Cards への無用な入力が止まる。
- [[001018]] の定義に基づく読了率と流入数を設定画面で並べて見られるようになり、持ち主が感覚ではなく数値で購読と上限を決められる。
- 検索対象を減らさずに未読の山の偏りだけを抑えられる。

### Cons / Tradeoffs

- **未解決の点・本 ADR では決めない点**: `daily_cap` 適用の具体的な実装位置（`alt-data-hub` からの取得と `alt-backend` 側での上限判定の分担、SQL に業務判断を置かない規則との整合形）、1 日の区切り時刻（UTC か持ち主のタイムゾーンか）、上限を超えた未読を翌日以降に回すかどうかは R4 実装時に決める。
- **未解決の点・本 ADR では決めない点**: `GetFeedInflowStats` が必要とする流入数（`alt-db`）と読んだ数（`knowledge-sovereign-db` の `reading_sources`）の結合経路は R4 実装時に決める。
- 項目 1 だけでは既存の購読中フィード由来の未読の山の量は減らない。量を減らすには、持ち主による `daily_cap` 設定または購読の見直しが必要である。
- `daily_cap` の既定値は未設定（上限なし）のため、持ち主が値を設定するまで未読一覧の表示は変わらない。
