# ADR-000992: Visual Preview の AI 要約を tts-speaker の Connect ストリーミングで読み上げる

## Status

Proposed

## Date

2026-10-01

## Affected Services

- tts-speaker (Python)
- alt-butterfly-facade (Go)
- alt-frontend-sv (TypeScript/Svelte)
- proto (alt.tts.v1)

## Context

### 需要とスコープ

- 日本語要約文の読み上げ需要がある。
- 最初の対象面は Visual Preview とする。ギャラリー型の `/feeds/visual-preview` で要約を表示する記事詳細モーダル（FeedDetailModal）と、スワイプ型 Visual Preview のカードの両方に置く。リアルタイム AI 要約（`FeedService.StreamSummarize`）の完了後に、ユーザーが再生できるようにする。
- デスクトップ、Recap、Evening Pulse などの他面は現時点では対象外とする（最小スコープ）。

### 現状

- [[000991]] で新設された tts-speaker は REST `POST /v1/synthesize` を公開している。全チャンクの合成を終えてから 1 つの WAV を返す仕様である。
- 約 400 文字の要約文で合成完了までに約 18 秒かかり、再生開始までの待ち時間として長すぎる。
- 現在、このエンドポイントを呼ぶ呼び出し側（caller）はまだ存在しない。

### 経緯と既存知見

- 2026-08-08 に撤去された旧 TTS 実装では、`alt.tts.v1.TTSService.SynthesizeStream`（メッセージごとに 1 つの完全な WAV を返却）を採用していた。
- クライアント側は Web Audio プレイヤーで各チャンクを `decodeAudioData` でデコードし、`AudioBufferSourceNode` の再生開始時刻を隙間なく連続でスケジュール（gapless scheduling）していた。
- 再生は、ユーザーのタップ操作を契機として `AudioContext` をアンロックして開始していた（[[000917]]）。

### 制約

- **公開 API 契約：** フロントエンド向けの API は `VISIBILITY_PUBLIC` を付与した proto サービスとし、生成された allowlist を経由して BFF（alt-butterfly-facade）を通過させる。BFF が独自の公開 API を所有しない（[[000955]]）。
- **劣化契約：** TTS は Feature-off の劣化契約に従う。利用不可時は「利用不可」を表示し、他機能には影響させない（[[000943]]）。
- **無効時の応答：** 無効化された機能は `FAILED_PRECONDITION` を返し、フロントエンドはその状態をラッチして表示を固定する（[[000966]] のパターン）。
- **契約テスト先行：** プロデューサー側の配線前に、契約テストを RED で先行導入する（リポジトリのルール 7。通常は Pact CDC）。
- **ストリーミングと Pact：** このリポジトリの Pact は unary の RPC だけを扱っている。Connect のサーバーストリーミングは、リクエストもレスポンスも長さ付きの封筒形式で、Pact では照合できない。ストリーミング RPC は Playwright の `@contract` テストで封筒形式と content-type を検証するのが前例である（acolyte-orchestrator の `StreamRunProgress`）。
- **デプロイゲート：** BFF → tts-speaker の pact を Broker に公開すると、BFF の can-i-deploy は本番にデプロイ記録のある tts-speaker の検証を求める。tts-speaker は opt-in の profile でパイプラインからデプロイされないので、記録ができず、`all_or_nothing` の本番デプロイ全体が止まる。
- **運用と GPU 競合：** TTS スタックは opt-in の compose profile（`profiles: [tts]`）を維持する。GPU 競合は、LLM 要約の完了後に TTS を実行する順序とすることで許容範囲に収める（[[000991]] G7）。

### 技術調査結果

- Connect for Python は beta 版でライセンスは Apache-2.0 である。ASGI 上の async iterator によるサーバー・ストリーミングに対応している。
- acolyte-orchestrator はすでに Starlette 上に connect-python をマウントして Connect-RPC を提供している実績がある。
- connect-web はブラウザから `fetch` 経由で unary および server-streaming メソッドを呼び出せる。
- `decodeAudioData` は完全なファイルデータに対してのみ機能する。そのため、ストリーミングされる各チャンクはそれぞれ単体で完結した WAV バイナリでなければならない。
- WAV は Media Source Extensions (MSE) のバイトストリーム形式としては非対応である。
- ブラウザの Autoplay Policy により、`AudioContext` の作成や再開（resume）にはユーザージェスチャー（タップ等の操作）が必須である。

## Decision

Visual Preview の AI 要約読み上げに Connect-RPC のサーバー・ストリーミング API を採用し、tts-speaker からブラウザまでチャンク単位で音声を順次配信・再生する。

1. **スコープ（AI 要約ブロック限定）**
   - 記事詳細モーダル（FeedDetailModal）とスワイプ型 Visual Preview カードの AI 要約ブロック内に限定する。FeedDetailModal は `/feeds/visual-preview`・`/feeds`・お気に入り・検索・既読一覧で共有されるため、これらすべてに表示される。
   - 要約ストリーム（`FeedService.StreamSummarize`）の完了後に再生ボタンを表示する。
   - 再生ボタンのタップ操作を `AudioContext` の作成・再開（resume）を行うユーザージェスチャーとする。
   - 停止（Stop）操作を提供する。カードや記事の切り替え、モーダルを閉じたとき、コンポーネントのアンマウント時に再生を即時停止する。
   - 自動再生（autoplay）は行わない。
   - 永続 mini-player は設けない。
   - 話者や速度の変更 UI は提供せず、サーバー既定値（[[000991]] で定めた 1.25x）を使用する。
2. **API 契約（`alt.tts.v1.TTSService`）**
   - `alt.tts.v1.TTSService` を復元する。
   - 提供する RPC は `SynthesizeStream(SynthesizeStreamRequest) returns (stream SynthesizeStreamResponse)` の 1 本のみとし、`VISIBILITY_PUBLIC` を付与する。
   - `SynthesizeStreamRequest`: `text`（文字列）、`speed`（任意指定の浮動小数点数）。
   - `SynthesizeStreamResponse`: `audio_wav`（バイト列）、`sample_rate`（整数）、`duration_seconds`（浮動小数点数）。
   - 1 チャンクにつき 1 メッセージを返す。各 `audio_wav` は単体でデコード可能な 16-bit PCM mono の完全な WAV バイナリとする。
   - 話者（voice）はサーバー側で固定（[[000991]] の `alt-narrator`）とし、API パラメータには含めない。
3. **tts-speaker（connect-python）**
   - connect-python の ASGI アプリケーションを既存アプリケーションの横にマウントして提供する（acolyte-orchestrator と同型の構成）。
   - 各チャンクが合成され次第、即座にクライアントへストリーミング送出する。
   - REST の `POST /v1/synthesize` エンドポイントは削除する（呼び出し側が存在したことはなく、プロトコル面を二重化しないため）。これは [[000991]] の決定 5 の API 部分を変更するものであり、前処理・分割・認証・リトライ等の他の決定は維持する。
   - エラーは Connect エラーコードに写像する。
     - テキストが空または上限文字数超過: `invalid_argument`
     - 上流（Irodori-TTS-Server）利用不可またはキュー待ちタイムアウト: `unavailable`
     - 上流のエラー応答または音声フォーマット変換エラー: `internal`
4. **BFF（alt-butterfly-facade）**
   - catch-all ルートの手前に `/alt.tts.v1.TTSService/` 専用ルートを配置する。
   - tts-speaker URL への mTLS クライアントを構成する。
   - ストリーミングタイムアウトを設定し、`SynthesizeStream` をストリーミング手続きとして登録する。
   - 起動時に配線状態を示すログ `bff.tts_proxy.wiring` を出力し、有効/無効の別と理由を明示する。
   - 明示的な設定で TTS が無効化されている場合、該当ルートは `failed_precondition`（"tts is disabled"）を返す。
   - 有効化されているが tts-speaker が起動していない場合（compose profile が OFF の場合）、呼び出しは `unavailable` として失敗する。
5. **フロントエンド（alt-frontend-sv）**
   - 撤去された実装から Web Audio プレイヤー（`SeamlessTtsPlayer`）を復元する（各チャンクを `decodeAudioData` でデコードし、ギャップレスにスケジュール再生する）。
   - 再生状態は軽量な状態機械（`idle` / `loading` / `playing` / `error` / `unavailable`）で管理する。
   - `failed_precondition` を受信した場合は `unavailable`（利用不可）として状態をラッチし、UI に表示する。他機能の動作には一切影響させない。
6. **テストと契約（ストリーミングの前例に倣う）**
   - Pact は作らない（ルール 7 の例外。理由は Context の「ストリーミングと Pact」「デプロイゲート」）。代わりに、プロデューサー実装より前に次の契約テストを RED で入れる。
   - tts-speaker：Playwright の `@contract` テストで、`SynthesizeStream` が 200・`application/connect+json` を返し、各フレームが `audio_wav`・`sample_rate`・`duration_seconds` を持つメッセージとしてデコードできることを検証する。
   - BFF：Go の httptest で、`/alt.tts.v1.TTSService/SynthesizeStream` がストリーミング手続きとして逐次フラッシュされて中継されること、TTS 無効時に `failed_precondition` を返すことを固定する。
   - 契約の型は proto（`alt.tts.v1`）から両側のコードを生成して共有する。
   - フロントエンドには、プレイヤーおよび再生状態管理のユニットテストを追加する。
   - Connect ストリームをモックし `AudioContext` をスタブ化した Playwright E2E テストを追加する。
7. **運用（Operations）**
   - TTS スタック（`tts-speaker`、`irodori-tts`）は opt-in の compose profile（`profiles: [tts]`）を継続する。
   - BFF には tts-speaker の接続先 URL を設定する。
   - BFF は `TTS_PROXY=enabled` と `https://tts-speaker:9443` を既定とする。BFF から tts-speaker へは、BFF 自身のクライアント証明書を使う HTTP/1.1 の mTLS で接続する（tts-speaker の TLS リスナーは HTTP/2 を話さないため、`MTLS_ENFORCE` とは独立した専用トランスポートを使う）。
   - profile を止めている間に再生しようとすると、再試行可能なエラー（"Couldn't play the summary. Try again."）になる。TTS を長期間使わないときは `TTS_PROXY=disabled` にすると、「Speech unavailable」と固定表示され、無駄なリクエストも送られない。

### 検討した代替案

| 案 | 評価 | 却下理由 |
|---|---|---|
| A. REST のフレーム化バイナリストリーム（BFF 独自ハンドラ配下） | 実装可能 | アドホックなフレーム定義とフロントエンドでの自前パーサーが必要になり、生成された公開 API allowlist モデル（[[000955]]）から外れる |
| B. Server-Sent Events (SSE) | ストリーミング対応 | テキスト形式のためバイナリ音声の base64 エンコードのオーバーヘッドが生じる。またブラウザ標準の EventSource は GET のみでリクエストボディを送れない |
| C. 1 つの WAV を返却する方式の維持（合成完了後に再生） | 既存実装のまま | 約 400 文字で約 18 秒の待機時間が発生し、再生開始までの UX が著しく劣る |
| D. Media Source Extensions (MSE) | ブラウザ標準のストリーミング再生 | WAV 形式は MSE のバイトストリーム形式として仕様上サポートされていない |
| E. 要約生成直後の自動再生（Autoplay） | ユーザー操作不要 | ブラウザの Autoplay Policy によりユーザージェスチャーなしでの AudioContext 開始がブロックされる。また意図しない音声再生は体験を損ねる |
| F. 撤去前の bottom-sheet + mini-player 構成の全面復元 | 過去の実績あり | 今回のスコープ（Visual Preview での要約読み上げ）に対して過剰（minimal scope を逸脱）。TTS を必要とする面が増えた段階で改めて再検討する |

## Consequences

### Pros

- タップ後約 1〜2 秒で最初の音声が再生開始される（体感レイテンシの大幅短縮）。
- BFF からフロントエンド、バックエンドまで Connect-RPC のストリーミング方式に一貫し、統一的なスキーマ・型生成・エラー処理を利用できる。
- 過去に実績のある Web Audio ギャップレス再生方式（`decodeAudioData` + `AudioBufferSourceNode`）を再利用できる。
- Feature-off の劣化契約（[[000943]]、[[000966]]）により、TTS スタックが停止していても Visual Preview の要約表示など他機能に一切影響を与えない。

### Cons / Tradeoffs

- connect-python は beta 版であり、将来的な破壊的変更の追従リスクがある。
- PyPI の配布名は `connect-python` から `connectrpc` に改名され、`connect-python` は 0.9.0 で更新が止まっている（import 名はどちらも `connectrpc`）。tts-speaker は acolyte-orchestrator と同じ `connect-python` 0.9.0 に揃える。`connectrpc` への移行は、両サービスで同時に別途行う。
- tts-speaker から REST エンドポイントを削除するため、プロトコルは Connect-RPC に一本化される（REST 単体での外部テスト等は行えなくなるが、二重管理の負債を解消できる）。
- 要約生成と音声合成が同時に走った場合の GPU 競合リスクがあるが、Visual Preview では要約完了後に再生ボタンを表示・押下する順序とするため実質的に緩和される。
- 非圧縮の WAV をチャンクごとに送るため、転送量が大きい（48 kHz・16-bit・mono で、約 10 秒のチャンク 1 つが約 1MB）。モバイル回線で問題になったら、圧縮形式（Opus など）とブラウザ側のデコード対応を別途検討する。
- 画面遷移（カード移動や unmount）で再生が停止し、ページをまたいだ永続再生はサポートしない。

## Deploy-model 整合性セルフチェック

- [x] 新設 compose service が `depends_on` で他 service を gate するか？
  - NO：新設の compose service はない。tts-speaker と irodori-tts は [[000991]] で導入済みであり、引き続き `profiles: [tts]` の opt-in として維持される。BFF への環境変数追加（tts-speaker URL）のみで、compose 上の起動依存（`depends_on`）は追加しない。
- [x] 新設 compose service に `restart: "no"` の one-shot init container を含むか？
  - NO：新設の one-shot init container はない。
- [x] 新設名前付き volume を populate する責務はどこにあるか？
  - 該当なし：新設の名前付き volume はない。
- [x] いずれも該当しない：
  - rolling 互換：BFF の環境変数追加のみであり、tts-speaker が停止していても BFF は正常に起動し、Feature-off 契約に従って FAILED_PRECONDITION / unavailable を返す。各サービスの独立した rolling deploy と互換である。
