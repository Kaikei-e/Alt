# ADR-000996: LKALによる要約品質実験バンドルの型付き版管理と評価・生成結果への追跡を導入する

## Status

Proposed（将来設計の提案。本 ADR は未実装の実験バンドル設計案であり、実装完了の主張や現行スキーマ・RPC 契約の即時置換を行わない）

## Date

2026-11-06

## Affected Services

- news-creator (Python) — `news-creator/app/news_creator/config/config.py`（188〜240 行付近）および `news-creator/app/news_creator/config/llm_config.py`（48〜66 行付近）の要約・Recap 品質設定の型付き読み込み・受付時ポリシー束縛（初期マイルストーンの対象。DB への直接書き込みは一切行わない）
- recap-evaluator (Python) — ゴールデンデータセットに対するオフライン評価とベースライン比較の実行点
- pre-processor (Go) / alt-data-hub (Go) / recap-worker (Rust) — 将来フェーズにおいて `news-creator` の応答メタデータ（`policy_digest`）を受け取り、それぞれの所有 DB（[[000954]] により `alt-db` の `summary_versions` 等は `alt-data-hub` が唯一のオーナー、Recap 成果物は `recap-worker` がオーナー）へ伝播する呼び出し側・永続化オーナー（初期マイルストーンではスキーマ・配線変更なし。将来の跨ぎ配線時は Pact CDC RED を必須前提とする）

## Context

本 ADR は [[000532]]（所有権マトリクス: `knowledge-sovereign` は `knowledge_events` と投影を所有し、要約生成自体は `news-creator`、Recap 生成は `recap-worker` が所有）、[[000928]]（サービス間配線での Pact CDC RED 先行と silent fallback 禁止）、[[000940]]（append-first / reproject-safe 原則）、[[000954]]（`alt-data-hub` による `alt-db` および `summary_versions` 状態遷移の単独所有）、[[000981]]（Ollama 0.32.14 と Gemma4 E4B 推論基盤）、[[000989]]（Gemma4 Apache-2.0 ベースライン）を前提とする。

### 1. 現状の証拠（Current Evidence）と課題

現在、`news-creator` の記事要約および Recap 要約の生成制御パラメータは、`news-creator/app/news_creator/config/config.py`（188〜240 行）および `news-creator/app/news_creator/config/llm_config.py`（48〜66 行）で環境変数から個別に読み込まれている。下表の値は**現行コード上の設定事実（current evidence）であり、普遍的に最適な既定値であることを意味しない**。

| 分類 | `config.py` / `llm_config.py` の対象属性 | 現行コード上の設定値 | 役割 |
|---|---|---|---|
| トークン・コンテキスト | `num_ctx` / `num_keep` / `summary_num_predict` / `recap_summary_num_predict` / `recap_card_max_new_tokens` | `8192` / `0` / `1000` / `4000` / `700` | コンテキスト窓上限、中間切り詰め保護、生成上限トークン予算 |
| 品質・文字数・言語閾値 | `recap_min_avg_bullet_length` / `recap_ja_ratio_threshold` | `300` / `0.6` | 箇条書き最小平均文字数と日本語文字比率の品質ゲート |
| 入力成立閾値 | `recap_min_source_articles_for_llm` / `recap_min_representative_sentences_for_llm` | `1` / `2` | LLM 要約を実行する最小記事数・最小代表文数 |
| 反復抑制・修復・温度 | `max_repetition_retries` / `repetition_threshold` / `recap_summary_repair_attempts` / `summary_temperature` / `recap_summary_temperature` | `2` / `0.3` / `2` / `0.5` / `0.0` | 反復検知リトライ、構造修復回数、サンプリング温度 |

この構成には以下の構造的課題がある。

1. **サービングポリシー同一性と評価実行同一性の未分離・追跡不能性**: 設定パラメータ・プロンプト・実際に解決されたモデル重み digest が単一の不変ポリシー識別子（`policy_digest`）として束ねられておらず、さらに評価データセットや評価器リビジョンを含む実験識別子（`experiment_digest`）とも区別されていない。
2. **実行途中の設定切り替えによる誤帰属リスク**: キュー待ちや反復リトライ・修復ループの完了後に「その時点のグローバル設定」を参照して結果を記録すると、飛行中（mid-flight）のポリシー切り替え時に生成結果が誤ったポリシーへ帰属される。
3. **平板な環境変数への早期変換と層境界の曖昧さ**: 外部設定フォーマット（LKAL）の型を Domain 層へ直接持ち込むと Clean Architecture の依存規則に反し、逆に最初から文字列の `-plain` に落とすと次元・値域・コンテキスト予算の検査が失われる。

## Decision

**初期マイルストーンを `news-creator` の要約・Recap 品質設定とオフライン評価に限定し、LKAL の型付き AST / 可逆 JSON を Driver / Gateway 層で Alt 所有の Domain 値オブジェクト（`SummarizationPolicySpec`）へ写像する。サービング設定を表す `policy_digest` と評価条件を表す `experiment_digest` / `evaluation_run_id` を明確に分離し、リクエスト受付時に不変ポリシーを束縛してリトライ・永続化境界まで一貫追跡する段階的運用を導入する。**

### D1. スコープ境界と Clean Architecture 配置

- **初期スコープの限定**: `news-creator` の要約・Recap パラメータ群と `recap-evaluator` の評価に閉じる。**Lens ランキング調整や無関係な `knowledge-sovereign` projector の変更は初期マイルストーンに一切混在させない。** また、本 ADR はドキュメント上の設計提案であり、**新規コードの追加は行っていない**。
- **LKAL のネイティブ型と Clean Architecture の層分離**:
  - LKAL のネイティブ数値・単位型は `Int`・`Decimal`・`Quantity`（外部 `lkal` の `lexer.go` 321〜354 行により、`MiB`・`GiB`・`s`・`m`・`h` 等の ASCII 単位識別子を構文上受理）である。時間長（duration）やトークン数・文字数・比率は **Alt ドメイン側の次元・意味論**として扱う。
  - **Driver 層**: LKAL AST / 可逆 JSON の読み込み I/O を実行し、Driver 固有の raw 構造体を返す。
  - **Gateway 層**: Usecase 所有の `PolicyBundlePort` を実装し、LKAL の `Int` / `Decimal` / `Quantity` を検査・変換して Alt 所有の Domain 値オブジェクト（`SummarizationPolicySpec`）へ写像する。`-plain` 形式は外部プロセス起動境界でのみ使用し、内部検証には用いない。
  - **Domain 層**: 標準ライブラリのみに依存し、`SummarizationPolicySpec` の不変条件を強制する。**Domain 層が LKAL SDK / CLI / JSON パーサや I/O を import することは禁止する。**
  - **Composition Root**（`news-creator` の DI コンテナ / 起動配線）: ローダとモデル digest 解決器の配線を所有する。起動時に `policy_bundle_tracking_enabled` / `policy_bundle_tracking_disabled` を明示的にログ出力する。**サービング実行時（`news-creator` で tracking が有効な場合）に resolver が未配線または `resolved_model_digest` が解決不能な場合は fail-fast で起動失敗させる**（`"unknown"` や `nil` への無言フォールバックは [[000928]] に従い禁止する）。一方、モデル重み未取得環境でのローカル構文・制約検査に限っては、後述 D3 のとおりオフライン診断プリフライト（diagnostic preflight report）専用モードのみが `identity_status: "unverified"`（`policy_digest: null`）の出力を許容される。

### D2. コンテキスト予算および品質バリデータの 2 段階検証

- **1. バンドル読込時の静的検証（Domain 層）**:
  - `Decimal` で表される比率（`recap_ja_ratio_threshold`, `repetition_threshold`）は `0.0 < x <= 1.0` の範囲内であること。
  - 出力トークン予算（`output_budget` = `summary_num_predict` 等）単体が `num_ctx` 未満であるだけでなく、`min_prompt_tokens + output_budget + safety_reserve_tokens <= num_ctx` かつ `num_keep == 0`（末尾の生成指示トークン保護）を満たすこと。
  - **品質・安全バリデータ緩和の禁止**: `recap_min_avg_bullet_length`・`recap_ja_ratio_threshold`・`repetition_threshold` 等の品質ゲート閾値をベースラインより緩めて合格率をかさ上げする変更は不適格として弾く。
- **2. リクエスト受付時の動的トークン予算検証（Usecase / PromptBuilder 層）**:
  - LLM 呼び出し前に `tokenized(system_prompt + user_input) + output_budget + safety_reserve_tokens <= actual_num_ctx` を Usecase / PromptBuilder が検証する。超過時はポリシーで定めた中間切り詰め（middle truncation）または受付拒否（fail-fast rejection）を Usecase 側で確定させてから Ollama Gateway へ渡し、下流ランタイムの暗黙的な先頭/末尾切り捨てに委ねない。

### D3. `policy_digest` と `experiment_digest` / `evaluation_run_id` の分離と正規化規則

「同じサービングポリシーを改訂データセットで再評価した場合」と「サービングパラメータを変更した場合」を厳密に区別するため、識別子を 2 階層に分離する。

```yaml
policy_bundle:
  policy_schema_version: 1
  policy_id: "nc-recap-policy-20261106-a"
  policy_digest: "sha256:<canonical-serving-policy-digest>" # unverified 診断時は null
  model:
    configured_tag: "gemma4-e4b-q4km" # 可変タグ単独では同一性証明とみなさない
    resolved_model_digest: "sha256:<actual-ollama-manifest-and-weights-digest>"
    modelfile_digest: "sha256:<modelfile-digest>"
    identity_status: "verified" # 解決不能時は unverified（診断レポートのみ許容、昇格・採択不可）
  prompt:
    template_id: "recap_summary_ja_v3"
    template_digest: "sha256:<prompt-content-digest>"
  spec_digest: "sha256:<canonical-SummarizationPolicySpec-json-digest>"

experiment_record:
  experiment_schema_version: 1
  experiment_digest: "sha256:<policy_digest + dataset_revision + evaluator_revision + protocol_digest>"
  evaluation_run_id: "<uuid-per-execution>"
  policy_digest: "sha256:<canonical-serving-policy-digest>"
  baseline_policy_digest: "sha256:<baseline-serving-policy-digest>"
  dataset_revision: "sha256:<golden-fixture-content-digest>"
  evaluator_revision: "<git-sha>"
  protocol: { seed: 42, repeats: 5 }
  runtime_observation: { ollama_version: "0.32.14", p50_ms: 0, p95_ms: 0 }
```

- **ハッシュ範囲と正規化（Canonicalization）規則**:
  - **JSON 空白除去の厳密な境界**: キーを辞書順ソートし、**JSON 文字列リテラル外の構造的空白のみを除去した UTF-8 正規化 JSON** に対して SHA-256 を計算する。**プロンプト本文や意味を持つ文字列値内部の空白・改行・インデントは一切改変・正規化しない。**
  - **`Decimal` および単位の無損失正規化**: `Decimal` 数値および `Quantity` 単位は 2 進浮動小数点（IEEE-754 float）丸めを介さず、スキーマで定義された正確な 10 進表現と正準基底単位へ決定論的に正規化する。この正規化規則はゴールデンフィクスチャ（**ブロック表記 vs ラベル表記、コメント有無、キー順序の差異では同一の `policy_digest` となり、意味論的値が 1 箇所でも変われば異なる `policy_digest` になること**）でロックする。
  - **`policy_digest`** は `policy_schema_version`・`spec_digest`（正規化された `SummarizationPolicySpec`）・`prompt.template_digest`・実際に解決された `model.resolved_model_digest`・`model.modelfile_digest` のみを入力とする。
  - **`experiment_digest`** は検証済みの `policy_digest`・`dataset_revision`・`evaluator_revision`・評価プロトコル設定（`seed`, `repeats`, `baseline_policy_digest`）を入力とし、実行ごとの観測値やタイムスタンプは **`evaluation_run_id`** に紐づける。
  - **不変性規則**: 同一ポリシーを新しいゴールデンデータセットで評価した場合、`policy_digest` は不変のまま `experiment_digest` のみが変わる。一方、トークン予算・温度・プロンプト・モデル重みのいずれかが 1 つでも変われば `policy_digest` が変化する。
  - **機密・生テキストの除外**: `inference_service_token` や Redis パスワード等のシークレット、およびユーザー記事の生本文はハッシュ入力からも成果物からも完全に除外する。
  - **未解決モデル同一性の扱い（D1 との一貫契約）**: 可変タグ（`gemma4-e4b-q4km`）単独ではモデル同一性の証明にならない。`news-creator` のサービング起動時は未解決を fail-fast で拒否する。オフライン側でも、`resolved_model_digest` が取得できない状態は**構文・制約の事前診断レポート（diagnostic preflight report）の出力のみに限定して `identity_status: "unverified"`（`policy_digest: null`）と記録し、検証済み `policy_digest` の発行、公式評価実行（`experiment_digest` 確定）、ベースライン登録、および shadow / canary への昇格をすべて機械的に遮断する**。
- **受付時スナップショット束縛（Admission-Time Binding）**: `news-creator` はリクエストまたはバッチジョブの受付（admission）時点で不変の `PolicySnapshot`（`policy_digest` を含む）をコンテキストに束縛し、内部の優先度キュー待ち（`SchedulingConfig`）、反復リトライ（`max_repetition_retries`）、修復試行（`recap_summary_repair_attempts`）、および応答返却まで同一スナップショットを引き回す。完了時にグローバルの「現在アクティブなポリシー」を参照して刻印することを禁止し、飛行中のポリシー切り替えによる誤帰属を防ぐ。
- **LLM 非決定論の扱い**: シードや温度を固定しても GPU カーネルや並行スケジューリングによりビット単位の完全決定論は成立しないことを明記し、ベースライン対照での反復実行（`repeats`）による品質・レイテンシ・トークン消費分布で比較判定する。

### D4. 3 つのプレーンの分離とデータ所有権境界（[[000532]] / [[000954]] 準拠）

| プレーン | 所有・実行主体 | 責務と境界制約 |
|---|---|---|
| 1. ポリシー配布・有効化 | リポジトリ / kisage（ホストローカル） | ホスト上の LKAL 設定ファイルの配備のみ。DB には一切触れず、kisage に DB/HTTP プロバイダがあるという前提も置かない |
| 2. 生成・実験実行 | `news-creator` / `recap-evaluator` | 受付時の `PolicySnapshot` 束縛、LLM 推論、オフライン・シャドウ比較。`news-creator` は DB へ直接書き込まない |
| 3. 永続化ビジネス結果 | `alt-data-hub`（`alt-db`）/ `recap-worker`（`recap-db`）/ `knowledge-sovereign`（イベント・投影） | [[000954]] により `summary_versions` を含む `alt-db` の状態遷移は `alt-data-hub` が単独所有する（呼び出し側 `pre-processor` 等が RPC 経由で記録）。[[000532]] により `knowledge-sovereign` は `knowledge_events` と投影のみを所有する |

- **イミュータブル不変条件の遵守**: 生成結果の追跡は `news-creator` の応答メタデータから呼び出し側（`pre-processor` / `recap-worker`）および永続化オーナー（`alt-data-hub`）へ `policy_digest` を渡すことで行い、過去の `summary_versions` や `knowledge_events` の遡及書き換え、およびホスト設定ファイルによるイベントログの代替は一切行わない。

### D5. 段階的導入フェーズ・事前登録制の品質昇格ゲート・受入/中断基準

- **事前登録制の品質昇格ゲート（Preregistered Quality Promotion Gate）**:
  - **候補結果を見る前の事前登録**: 候補ポリシーの評価結果を閲覧する**前**に、(1) ベースラインフィクスチャの対象範囲・除外条件・反復回数（`repeats`）、(2) 主要品質指標と非劣性/改善許容幅（non-inferiority / improvement allowance）、(3) p95 レイテンシ上限、および (4) トークン消費量上限を事前登録する。各上限・基準値は未検証の固定数値を捏造せず、同一ランタイム上のベースライン実測値から導出する（ハードウェア構成の詳細は記載しない）。
  - **昇格ゲート条件**: 事前登録基準の欠落や計測反復数の不足がある場合は昇格を認めない。`Shadow -> Canary` への昇格には、**既存の品質・安全バリデータ（`recap_min_avg_bullet_length`・`recap_ja_ratio_threshold`・`repetition_threshold`）を一切緩和していないこと**に加え、**事前登録した品質・p95 レイテンシ・トークン消費量の全基準を同時に満たすこと**を必須とする。
  - **事後基準変更の禁止**: 候補の結果を見た後に評価基準や許容幅を変更する場合は、既存結果の遡及合格とせず、**新たな `experiment_digest` を採番して再計測（rerun）することを必須とする**。
- **Phase 1（Offline Experiment）**: `news-creator` の Driver/Gateway/Domain ポリシー検証層、受付時スナップショット束縛、および `recap-evaluator` での事前登録基準に基づくオフライン評価（`policy_digest` と `experiment_digest` の分離記録）を実装する。サービス間 RPC・DB スキーマ変更は行わない。
- **Phase 2（Shadow Evaluation）**: シャドウ実行でベースライン対照の品質ゲート通過率・レイテンシ（p50/p95）・トークン消費量を比較し、上記昇格ゲートを判定する。
- **Phase 3（Bounded Canary & CDC-Gated Persistence Wiring）**: `news-creator` から `pre-processor` → `alt-data-hub`（`summary_versions`）や `recap-worker`（および必要時のみ既存のイベント消費契約に沿った `knowledge-sovereign`）へ `policy_digest` を伝播させる前に、**必ず Pact CDC RED テストを先行させ（`CLAUDE.md` Critical Rule 7 / [[000928]]）**、additive な契約拡張として導入する。
- **ロールバック方式**: 品質劣化やレイテンシ超過時は、**過去の DB レコードやイベントを書き換えるのではなく、直前の検証済み `policy_digest` を持つ不変ポリシーバンドルを再有効化（re-activate）する**。また飛行中のリクエストは受付時に束縛された `policy_digest` を維持したまま完了または中断される。
- **受入基準（Acceptance Criteria）**:
  - Domain 層が LKAL パッケージを一切 import せず、不正な単位・範囲外 `Decimal`・コンテキスト予算超過のポリシーを 100% 拒否できること。
  - データセットのみを変更した際に `policy_digest` が不変で `experiment_digest` のみが変化し、サービング設定を変更した際に `policy_digest` が変化すること。
  - 推論中にアクティブポリシーを切り替える並行テストにおいて、完了応答の `policy_digest` が受付時のスナップショットと 100% 一致すること。
- **中断基準（Abort Criteria）**: `identity_status: "unverified"` のモデルが昇格した場合、品質バリデータ閾値の緩和や事前未登録基準での昇格が検出された場合、シークレットや生記事本文がバンドル証跡に含まれた場合、または CDC RED なしにサービス間スキーマが変更された場合は即時中断する。

### D6. 検討した代替案と却下理由

- **(a) サービング設定と評価データセットを単一の `bundle_digest` に混ぜる案 — 却下**: 評価データセットを拡充しただけでサービング上のポリシー識別子まで変わってしまい、本番生成結果の一貫した追跡ができなくなるため。
- **(b) リクエスト完了時にグローバルの現行アクティブポリシーを読んで結果に刻印する案 — 却下**: キュー待ちやリトライ中にポリシーが切り替わった際、旧ポリシーで生成された要約に新ポリシーの digest が誤刻印されるため。
- **(c) `news-creator` から DB（`summary_versions` 等）へ直接メタデータを書き込む案 — 却下**: [[000532]] の生成責務分離および [[000954]] の `alt-data-hub` による `alt-db` 単独所有原則に違反するため。

### D7. 残存する未解決事項と解消方法（Open Issues）

1. **`alt-data-hub`（`summary_versions`）および `recap-worker` への `policy_digest` 伝播フィールド定義**: 既存の Connect-RPC / REST 契約に対する additive フィールド名と型。解消方法: Phase 3 着手前に `pre-processor` ↔ `news-creator` および `pre-processor` ↔ `alt-data-hub` の Pact CDC RED テストを先行作成して確定する。
2. **トークナイザ見積もりの共有方式とベースライン実測による事前登録閾値の確定**: Usecase 層の受付時トークン数検査方式と、Phase 1 ベースライン実測に基づく `repeats`・非劣性許容幅・p95 レイテンシ/トークン上限の確定。解消方法: Phase 1 でベースライン反復計測を実施し、候補評価前に実験定義へ固定登録して閉じる。

## Consequences

### Pros

- `policy_digest`（サービング同一性）と `experiment_digest` / `evaluation_run_id`（評価同一性）の分離により、データセット改訂とポリシー変更を混同せずに追跡できる。
- 受付時スナップショット束縛と Clean Architecture の層分離により、飛行中の設定変更による誤帰属や外部 DSL へのドメイン汚染を防げる。
- [[000532]] と [[000954]] の所有権境界および append-first 原則を守ったまま、旧ポリシーの再有効化による安全なロールバックが行える。

### Cons / Tradeoffs

- Gateway 層での LKAL AST → `SummarizationPolicySpec` 変換と、起動時のモデル重み digest 解決の実装・保守コストが加わる。
- LLM の非決定論に対処するため複数回反復評価（`repeats`）を行う必要があり、オフライン・シャドウ評価の計算時間が増加する。
