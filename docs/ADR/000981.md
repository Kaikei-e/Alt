# ADR-000981: Ollama を 0.32.14 に統一し Gemma4 E4B を公式 QAT + MTP speculative decoding に載せ替える

## Status

Accepted

## Date

2026-08-20

## Affected Services

- **news-creator-backend (Ollama)** — ローカル GPU 上の Gemma4 推論 runtime。image tag / GGUF ソース / Modelfile / KV cache 精度 / entrypoint のすべてを更新。
- **knowledge-embedder / knowledge-embedder-local** — embedding 用 Ollama。image tag のみ更新。
- **knowledge-augur** — koko-aix ノード側の Ollama。image tag のみ更新（当該ノードでのビルドは未実施）。
- **compose/ai.yaml / compose.augur.yaml** — digest pin と KV cache 設定の配線。

消費者サービス（news-creator / pre-processor / rag-orchestrator / recap / acolyte / search-indexer）のモデル名・API 呼び出しは据え置き。

## Context

[[000887]] は 3 つの Ollama 派生 image を `0.22.1` に揃える方針を立て、[[000947]] は news-creator-backend だけを `0.32.1` に上げた。結果として **`0.32.1` と `0.22.1` が混在**し、[[000887]] が防ごうとした挙動 drift が構造として残っていた。

`0.22.1` は 2026-04-28 リリースで、`0.32.14`（2026-08-15）との間に 10 マイナーバージョンの差がある。本 ADR の作業前に、本番 volume を read-only マウントした一時コンテナで互換性を実測した。

- **モデルストア互換**: `0.22.1` が作成した blob を `0.32.14` がそのまま認識。再 pull / 再 import 不要。
- **embedding ベクトル互換**: 同一入力の cosine 類似度が `bge-m3` で 0.999991〜0.999993、`qwen3-embedding:0.6b` で 0.99927〜0.99979。GPU fp16 と CPU の演算精度差の水準であり、**Meilisearch インデックスの再構築は不要**。
- **GBNF structured output 互換**: [[000887]] の根本原因だった `^(lead|top3|what_changed|by_genre:[a-z0-9_-]+)$` を含む schema を `format=` で渡して成功。回帰なし。
- **image サイズ**: 6.3GB → 5.04GB（`/usr/lib/ollama` が 5.5GB → 4.3GB）。CPU バックエンドの variant は 7 → 14 に増加。
- **Vulkan**: バンドル版 `libvulkan.so.1` は `/usr/lib/ollama/vulkan/` から消えたが、システム側の `libvulkan.so.1` と `radeon_icd.json` は image に残存。

更新後、embedder の VRAM 実測が **1.2GB 前提から 0.66GB** に下がり、`common_fit_params: successfully fit params to free device memory` という llama.cpp の自動メモリフィットが動作するようになった。GPU 全体の使用量は 5847 MiB → 4540 MiB に減り、約 1.3GB の余裕が生まれた。

この余裕を何に使えるかを実測で検討した結果が、以降の 3 つの決定（QAT / MTP / KV f16）である。

### 実測: モデルサイズを上げる価値はなかった

Gemma 4 12B への載せ替えを検討した。配布・ライセンス面は問題がなく、Google が QAT 版 GGUF を **Apache 2.0** で直接配布している（`google/gemma-4-12B-it-qat-q4_0-gguf`、6.976 GB）。Gemma 4 世代から従来の Gemma Terms of Use ではなく Apache 2.0 になっており、Alt のライセンス方針にも適合する。

しかし日本語性能の公開実測（JCommonsenseQA）は **12B 94.6% に対し E4B 94.1%** とほぼ差がなく、応答時間は 12B が 2 倍以上かかる。12B の優位は画像と音声であり、Alt の用途（日本語記事要約・Morning Letter・RAG 生成、テキストのみ）では VRAM 2 倍・速度半減の対価に見合わない。

### 実測: コンテキスト長を上げる価値もなかった

Gemma 4 E4B の KV cache は 42 層のうち **最初の 24 層しか確保されず**（残り 18 層は KV 共有）、そのうち `num_ctx` に線形比例するのは global 4 層のみで、残り 20 層は sliding window 512 に対応する 1024 cells に固定される。llama.cpp のソースから導いた式 `n_ctx × 8704 B` は実測と 1 バイト単位で一致した。

```
num_ctx=12288: global 102.00 MiB (4 layers) + SWA 21.25 MiB (20 layers)   [q8_0]
num_ctx=32768: global 272.00 MiB (4 layers) + SWA 21.25 MiB (20 layers)   [q8_0]
```

つまり `num_ctx` を上げるコストは 10.6 KiB/token と極めて安く、E4B の上限である 131072 まで上げても VRAM は足りる。しかし上げる理由がなかった。

- 実プロンプト長は最大 7,548 tokens で、8192 を超えたものは 0%
- 実測トークン比は日本語 2.11 / 英語 5.06 chars/token、実記事で 3.28 chars/token
- 過去 7 日に要約された 506 記事のソース長は avg 7,808 / p50 6,421 / p95 18,015 / p99 34,369 / max 65,718 chars。p99 でも約 10,478 tokens で 12288 に収まる
- 階層要約（`HIERARCHICAL_SINGLE_ARTICLE_THRESHOLD=20000`）に回るのは 21 件 = 4.2%
- **同一記事（7,548 tokens）で `num_ctx` を 32768 にすると生成が 81.5 → 72.9 tok/s と 11% 遅くなる**

同様に `OLLAMA_NUM_PARALLEL` の引き上げも、セマフォのキュー待ちが実測 0.00s であり根拠がなかった。embedder 側の context も 554 サンプルで最大 1156 tokens であり、既定の 4096 が制約になっていない。

## Decision

**Ollama を全 image で `0.32.14` に統一し、Gemma4 E4B を Google 公式 QAT GGUF + MTP speculative decoding に載せ替え、KV cache を f16 に戻す。`num_ctx` とモデルサイズは据え置く。**

### 1. `ollama/ollama:0.32.14` に統一する

3 つの Dockerfile と `compose.augur.yaml` の volume-init を同一タグに揃え、[[000887]] の「3 image を同タグに揃える」方針に戻す。`:latest` は使わない。

### 2. GGUF を Google 公式 QAT に切り替える

```
https://huggingface.co/google/gemma-4-E4B-it-qat-q4_0-gguf
gemma-4-E4B_q4_0-it.gguf   5,154,941,280 bytes
sha256 676c35070db6dbe52f93e9c864ee0fba4eddea94b9c875d9cb10daff453fbaee
```

Quantization-Aware Training は学習中に 4bit 演算をシミュレートするため、[[000947]] が使っていた ggml-org の post-training quantization より品質が bf16 に近い。Google 自身が Apache 2.0 で GGUF を配布しているため、第三者による再量子化の工程が供給経路から消える。

ファイルは 4.59GB → 5.15GB と 12% 大きくなるが、**VRAM は 2851 MiB → 2696 MiB と 155 MiB 減った**（量子化構造の違いによる）。タグ名 `gemma4-e4b-q4km` は消費者互換のため据え置く（[[PM-2026-016]]）。

### 3. MTP draft head を `DRAFT` 命令で導入する

Modelfile に 1 行追加する。

```
DRAFT /tmp/gguf/mtp-gemma-4-E4B-it-Q4_0.gguf
```

Ollama はこれを llama-server へ `--spec-type draft-mtp --spec-draft-n-max <draft_num_predict> --spec-draft-backend-sampling` として渡す。draft head は 59.7MB（`sha256 d19a11e4fd5019967d9296f77f4d3e139c8903909f70c3a9cf009c9af4b9b88d`）で、Google の QAT リポジトリには MTP head がないため ggml-org から取得する。

8k / 12k の variant Modelfile は変更不要である。`FROM gemma4-e4b-q4km` で draft レイヤーが継承されることを実機で確認した（`ollama create` が `using existing layer sha256:d19a11e4...` を出し、生成された manifest に `application/vnd.ollama.image.draft` 59.7MB が含まれる）。

**出力品質は変わらない。** llama.cpp は Leviathan/Chen 型の rejection sampling ではなく、各位置で target 自身のサンプラーからトークンを引き、draft と一致した場合のみ採用して不一致で打ち切る実装になっている。採用されるトークンは常に target が選んだものであり、draft が外れるのは速度の損失にしかならない。

`draft_num_predict` は既定の 4 を維持する。実測では 2 と 4 が分散内（100.7 対 102.8 tok/s）で、8 以降は明確に劣化した（8 → 89.4、12 → 81.4 tok/s）。Ollama は `--spec-draft-p-min` を渡さないため draft が常に n_max まで走り、深くするほど無駄が増える。

### 4. `OLLAMA_KV_CACHE_TYPE` を `q8_0` から `f16` に戻す

同一プロトコルで A/B 計測した結果、**f16 のほうが速い**。

| 指標 | q8_0 | f16 | 差 |
|---|---|---|---|
| 短文生成（200 tok × 5） | 108.1 tok/s (σ 3.6) | **131.0 tok/s** (σ 10.1) | **+21.2%** |
| 長文生成（7,548 tok prompt × 3） | 76.8 tok/s | **94.0 tok/s** | **+22.4%** |
| KV cache 合計 | 151.94 MiB | 286.00 MiB | +134 MiB |
| compute buffer (base + draft) | 104.29 + 76.28 MiB | 114.02 + 33.00 MiB | −33 MiB |
| **GPU 実使用量** | 4598 MiB | 4646 MiB | **+48 MiB** |
| draft acceptance rate | 0.32–0.45 | 0.24–0.42 | 変化なし |

q8_0 が節約していたのは 134 MiB にすぎない。E4B は KV を 24 層しか持たず、うち 20 層を 512 トークンの sliding window で抑えているため、そもそも量子化で削れる絶対量が小さい。一方で CUDA 上では dequantization のコストが帯域削減を上回り、21% の速度を失っていた。compute buffer が逆に減ったため、実際の VRAM 増加は 48 MiB で済んでいる。

副次的に判明した点として、**`q8_0` 設定時は MTP draft の KV cache も 1088 B/cell（q8_0 相当）で確保されていた**。llama.cpp #25725 は draft 側 KV の量子化で acceptance が 80–99% から 0–2% に崩壊する事例を報告している。今回の計測では acceptance に有意差は出なかったが、f16 にすることでこの危険な組み合わせから抜けられる。同様に llama.cpp #24400 が報告する「Gemma 4 E4B が flash attention + draft model + KV 量子化の 3 条件でクラッシュする」構成にも該当しなくなる。

greedy 生成（`temperature=0, top_k=1, seed=42`）の出力は q8_0 と f16 で異なった（sha256 `568ebd9b…` / 195 字 対 `e9e989e3…` / 201 字）。どちらが良いかを判定する基準は持たないが、量子化が出力を変えていた事実は確認できた。

### 5. entrypoint のタグ検出を完全一致にし、作成後に fail-fast する

`create_model()` の存在判定が `grep -q "^${model_name}"` という前方一致で、`gemma4-e4b-12k-mtp` のような派生タグを `gemma4-e4b-12k` として誤検出していた。この作業中に検証用タグを作ったことで実際に踏み、`gemma4-e4b-12k` が存在しないまま「Modelfile が変わっていないのでスキップ」と判定され、消費者が約 10 分間 `model 'gemma4-e4b-12k' not found` で 404 を受けた。preload の `curl -s`（`-f` なし）は HTTP 404 でも終了コード 0 を返すため、「12K model confirmed to be loaded in GPU memory」という誤ったログまで出していた。

3 点を修正する。

```bash
model_exists() {
  ollama list 2>/dev/null | awk -v n="$1" 'NR > 1 && ($1 == n || $1 == n ":latest") { found = 1 } END { exit !found }'
}
```

- 前方一致の 3 箇所（FORCE 削除ループ / base モデル判定 / `create_model` のスキップ条件）を完全一致に置換
- variant 作成後に全タグの実在を検証し、欠けていれば `exit 1`（Rule 9 の fail-fast。warn-and-limp を避ける）
- preload の 2 つの `curl -s` を `curl -fs` に

合わせて、本体と draft の取得・digest 検証を `fetch_gguf()` に括り出した。

### 検討した代替案

- **Gemma 4 12B への移行**: 日本語性能が E4B と 0.5 ポイント差しかなく、速度は半分以下。却下。
- **`num_ctx` を 32768 に拡大**: VRAM は足りるが実プロンプトが最大 7,548 tokens で必要がなく、同一入力で生成が 11% 遅くなった。却下。
- **`OLLAMA_NUM_PARALLEL=2`**: キュー待ちが実測 0.00s で必要性がない。加えて MTP との併用は llama.cpp #26425（リクエスト間の状態リーク）と #27296（ループ出力）が未解決。却下。
- **`draft_num_predict` を 8 以上に**: 実測で劣化。却下。
- **`OLLAMA_GPU_OVERHEAD` で VRAM を予約**: v0.32.14 の CUDA パスでは何も予約せず、ログ行と VRAM tier 判定と macOS MLX runner でしか読まれない。却下。
- **`LLAMA_ARG_FIT_TARGET` を絞る**: 既定 1024 MiB のマージンに対し実測で 3109 MiB 残っており、layer が CPU に落ちる気配がない。触る必要がない。却下。
- **KV の K と V を別精度にする（K を f16、V を q8_0 等）**: Ollama は K/V を 1 変数でしか持たない。llama.cpp でも既定ビルドは対称 4 組み合わせしかカーネルを持たず、非対称指定は無警告で CPU にフォールバックして 25–45 倍遅くなる事例がある。却下。

## Consequences

### Pros

- 3 つの Ollama image が再び同一タグに揃い、[[000887]] の drift 防止方針が構造として回復した。
- 生成スループットが **65.6 → 131.0 tok/s（短文）/ 76.8 → 94.0 tok/s（長文）** に向上した。MTP で 1.56–1.96 倍、KV f16 でさらに 21%。VRAM の増加は合計で 100 MiB 未満。
- モデルの供給元が Google 公式（Apache 2.0）になり、第三者の再量子化が経路から消えた。digest pin で監査可能な状態も維持している。
- image が 6.3GB → 5.04GB に縮み、3 image 分のビルド・pull・ディスクが軽くなった。
- 起動時のタグ欠落が silent failure ではなく `exit 1` になり、[[PM-2026-045]] 系の「DI が繋がっていない状態を正常起動と区別できない」失敗モードが 1 つ減った。
- `num_ctx` / `NUM_PARALLEL` / モデルサイズについて「上げない」根拠が実測で残った。今後同じ検討を繰り返さずに済む。

### Cons / Tradeoffs

- **MTP draft head だけ供給元が ggml-org に分かれる**。Google の QAT リポジトリが MTP head を出せば一本化できるが、現時点では 2 系統を pin することになる。
- **`DRAFT` 命令は Ollama の公式 Modelfile ドキュメントに記載がない**。parser には実装されているが未文書 API であり、仕様変更のリスクを負う。
- **draft acceptance rate が 0.24–0.45 と公開値（Gemma 4 31B で 64%、12B で 70%）より低い**。Ollama が `--spec-draft-p-min` を渡さず draft が常に n_max まで走ることが原因と見られるが、Ollama 側の実装制約であり現時点では手が出せない。
- **`ollama ps` の VRAM 表示が信用できない**。`memoryBufferKey` が llama.cpp の `__func__` プレフィックスをキーにしているため、後から読み込まれる draft の `load_tensors: CUDA0 model buffer size = 41.86 MiB` が target の 2696 MiB を上書きし、モデル全体が 0.19GB と報告される。upstream 未報告。監視でこの値を使う場合は `load_tensors` / `llama_kv_cache` / `sched_reserve` のログを直接読む必要がある。
- **Modelfile を変更するたびに base タグの再作成が必要で、5.2GB の再ダウンロードを伴う**。`FORCE_MODEL_REFRESH=1` の one-shot 実行中は healthcheck の `start_period`（120s）を超え、その間 AI 要約が停止する。今回の作業では、この待ちを完了前に打ち切って再起動したために 10 分間の 404 を発生させた。**「Model created successfully」をログで確認してから次の操作に移る**必要がある。
- **2 つの Ollama インスタンスは互いのモデルを認識しない**。どちらも起動時に live free VRAM を読むだけなので、実ロードのタイミングが重なると race する。`knowledge-embedder-local` は [[000940]] 系の degrade contract のため意図的に `depends_on` を持たない設計であり、この race は残る。
- **`num_ctx` を明示しているため、Ollama の OOM 自動リカバリ（context を 1 段下げて 1 回だけ再試行）が無効**。Modelfile の `PARAMETER num_ctx` がある限り `numCtxAuto` は false になる。
- **knowledge-augur の `0.32.14` 化は koko-aix ノードでのビルドが未実施**。Vulkan バックエンドはシステム側の `libvulkan.so.1` と `radeon_icd.json` が image に残っていることを確認済みだが、実機での起動確認は取れていない。
- **`news-creator` の非ストリーミング `/api/generate` 経路は `think` を送っていない**。[[000614]] の `think=false` は `ollama_stream_driver.py` の `/api/chat` 経路にのみ適用されており、generate 経路では gemma4 が thinking モードに入って `response` が空文字で返ることを検証中に再現した。本 ADR の範囲外だが、別途対応が要る。

## Deploy-model 整合性セルフチェック

本 ADR は compose service を新設せず、`depends_on` も名前付き volume も追加していない。変更は既存サービスの image tag、環境変数、entrypoint、Modelfile に限られる。

- [x] 新設 compose service が `depends_on` で他 service を gate するか？ → **N/A**（新設なし）
- [x] 新設 compose service に `restart: "no"` の one-shot init container を含むか？ → **N/A**（新設なし。`compose.augur.yaml` の既存 volume-init は image tag のみ追随）
- [x] 新設名前付き volume を populate する責務はどこにあるか？ → **N/A**（新設なし。既存の `news_creator_models` は entrypoint が populate する既存経路のまま）
- [x] いずれも該当しない → **rolling 互換**

ただし `FORCE_MODEL_REFRESH=1` を伴う更新は rolling deploy と相性が悪い。既存タグを削除してから 5.2GB を取得する間、当該サービスは要約を返せない。モデル本体を差し替える変更は、単独の `docker compose up` ではなくメンテナンス枠で実施する。
