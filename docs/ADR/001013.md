# ADR-001013: 未要約記事の enqueue sweep を、ガードで弾かれる記事に枠を使い切られないよう 1 回の sweep 内で複数ページ進める

## Status

Accepted

## Date

2026-11-15

## Affected Services

- pre-processor（未要約記事の enqueue sweep のページング、ガードのスキップログの水準）

## Context

pre-processor は定期 sweep で「要約を持たない記事」の一覧を新しい順に 1 ページ（batch サイズ分）取得し、各記事を enqueue ガードに通してから要約ジョブを作る。[[001006]] はこの sweep に、batch が満杯だったときの即時補充を足した。

その後、低品質と判定されて要約を消された記事の再要約に回数上限を設けた。上限に達した記事と、dead-letter 済みのジョブを持つ記事は、ガードが恒久的に弾く。この上限そのものは「リトライを無制限にしない」という意味で妥当だが、次の副作用が出た。

- 恒久的に弾かれる記事は要約を持たないままなので、未要約の一覧に残り続ける。本番ではこの一覧の大半（約 9 割）がそうした記事になった
- sweep は 1 回につき 1 ページしか見ず、弾かれた記事もそのページの枠を消費する。ほぼ毎回「取得した全件がスキップ、enqueue は 0 件」になった
- 一覧は新しい順で、カーソルは末尾に達するまでリセットされない。新着記事は、カーソルが一覧を一周して先頭に戻るまで sweep の視界に入らない

結果として、記事の取り込みから要約完了までの中央値は、数分から 1 時間半前後まで伸びた。コンテナのヘルスチェック、LLM 推論、ジョブキューはすべて正常で、エラーログも出ていなかったため、利用者が「要約が出ない」と気付くまで検知されなかった。

メッセージキューやジョブキューの定石は、リトライ上限に達した項目を候補集合から外すことである（dead-letter queue、ジョブの終端状態、スケジューラの backoff キュー）。ただしこの sweep では、候補の一覧は記事を所有するサービスの DB から RPC で取得し、終端状態は pre-processor 自身の DB にあるため、取得クエリの中で両者を突き合わせることができない。

## Decision

**1 回の enqueue sweep は、次のいずれかに達するまで一覧のページを進める方式を採用する。**

1. enqueue した件数が batch サイズに達した
2. 一覧の末尾に達した
3. コンテキストがキャンセルされた
4. 1 回の sweep で進めるページ数の上限に達した

細部は次のとおりとする。

- 1 回の sweep で作るジョブは従来どおり batch サイズまで。下流（要約キューと LLM）への流量は変えない
- ページ数の上限はコード内の定数とし、上限で止まったときは WARN ログを出す。黙って打ち切らない
- ページの途中で batch が埋まった場合、カーソルはそのページの先頭に留める。次の sweep は同じページを取り直し、enqueue 済みの記事はガードが弾き、未確認の記事から続きが処理される。ガードとジョブ作成が冪等であることに依存する
- 一覧の取得が 2 ページ目以降で失敗したときは、そこまで進めたカーソルを保持したうえでエラーを返す
- 1 ページも取得しないうちにキャンセルされた場合はエラーを返す。「末尾に達した」と誤認してカーソルをリセットしない
- sweep ごとの集計ログに、進めたページ数と理由別のスキップ件数を載せる。記事 1 件ごとのスキップログと、ガード内の恒久的な理由（再要約回数の上限到達、dead-letter 済み）のログは DEBUG に下げる。同じ記事について毎回同じ行が出るだけで、件数は集計ログで追えるため
- 補充の判定（一覧に続きがあり、かつ 1 件以上 enqueue できたときだけ即時補充する）と、末尾到達時のカーソルリセットは [[001006]] のまま変えない

### 検討した代替案

- **恒久的に弾かれる記事を候補の一覧から外す**: 定石どおりで、スキャン量が終端記事の数に依存しなくなる。しかし終端状態を記事側のサービスに持たせるか、一覧取得の RPC に除外条件を渡す必要があり、サービス間の契約変更になる。要約が出ない状態を先に解消するため今回は見送り、別の ADR で扱う
- **sweep の間隔を短くする、または batch サイズを増やす**: 一周にかかる時間は縮むが、終端記事が増えれば同じ遅延が再発する。batch サイズは下流への流量も変えてしまう
- **sweep のたびにカーソルを先頭へ戻して新着を優先する**: 先頭の 1 ページがすべて恒久的に弾かれる記事になった時点で、それより古い未要約記事に永久に届かなくなる
- **恒久的に弾かれる記事の ID をプロセス内に覚えて読み飛ばす**: ガードの DB 参照は減るが、ページの枠を消費する点は変わらない。再起動で失われる状態を増やすことにもなる

## Consequences

### Pros

- 新着記事は、次の sweep か、遅くともその次の sweep で enqueue される。取り込みから要約までの遅延が、終端記事の数に左右されなくなる
- ジョブ作成の上限は batch サイズのままなので、要約キューと LLM への負荷は変わらない
- sweep の集計ログだけで「何ページ見て、何件を、どの理由で弾いたか」が分かる
- ページ数の上限に達したことが WARN で見えるため、終端記事の増加に気付ける

### Cons / Tradeoffs

- 恒久的に弾かれる記事は候補の一覧に残ったままで、sweep のたびに全件を読み直す。スキャン量（一覧取得の RPC 回数と、ガードの DB 参照）は終端記事の数に比例して増える。ページ数の上限を超えるまで増えると、再び一周待ちの遅延が出る。根本的な解決は、上記の見送った代替案（候補の一覧からの除外）である
- ガードの「再要約回数の上限」は、完了済みジョブの行が残っていることに依存している。ジョブ表に保持期限を入れると、上限が効かなくなり、同じ記事の再要約が再開する
- ページの途中で batch が埋まると、次の sweep で同じページをもう一度ガードに通す。無駄は 1 ページ分に限られる
- 恒久的な理由のスキップは既定のログ水準では 1 件ずつ見えなくなる。個別の記事を調べるときは DEBUG に上げるか、ジョブ表を直接見る
- 「取り込みから enqueue までの経過時間」の指標とアラートはまだ無い。今回と同種の遅延は、引き続き利用者の報告か集計ログの確認でしか見つからない
