# ADR-001038: LOOP-01〜07 の運用ループと pstack 準拠スキルを alt-harness へ統合し実運用検証する

## Status

Proposed

## Date

2026-11-28

## Affected Services

- `scripts/altharness`, `scripts/verify`, `scripts/harness/eval`, `scripts/agent-harness` (Go 単一バイナリ運用ループサブコマンド・評価シナリオ・スキーマ/テンプレート)
- `.claude/skills/interrogate`, `.claude/skills/blast-radius`, `.claude/skills/correct`, `.claude/skills/show-me-your-work`, `.claude/skills/loop-eval`, `.agents/skills/`, `.agents/rules/rule-ledger.md`, `.agents/rules/task-packet.md` (pstack 準拠スキル・シンボリックリンク・規則台帳)
- `docs/review/` (LOOP-04 敵対的レビュー実測証拠台帳)

## Context

[[001028]] による純 Go 標準ライブラリ単一バイナリ（`scripts/altharness/alt-harness`）への統一、[[001032]] による ADR 先行起票ゲート、および [[001037]] による層 3 動的検証（`VERIFY-01〜06`）の統合により、静的解析（`ARCH-01〜06`, `CHECK-01〜07`）と動的検証（`VERIFY-01〜06`）の土台が稼働した。一方で、`docs/review/ハーネス追加施策 — poteto 方式の適用.md` の運用ループ系統（`LOOP-01〜07`）には、継続運用を閉じるための以下のギャップが残っていた。

1. **LOOP-01 / LOOP-02 の残差**: `packet verify-handoff` と `packet measure` の基盤は存在するが、`host-final-check.sh` に実行順ランダム化テスト（Go `-shuffle` / Python `pytest-rand`）の明示オプションとシード記録が未統合であり、`measure` にターン上限からの予算導出（例: 上限の 1/5）オプションがなかった。
2. **LOOP-03（判断ログ）の整合検証と衛生**: `harness-run` が `.harness/runs/<branch>/decisions.tsv` を記録するが、既存ログに対する構造検証（6 列ヘッダ・1 行目 `init` 方針と完了定義・ポインタ証拠・追記専用整合性）コマンド、スプレッドシート式インジェクション対策（先頭 `=` / `+` / `@` の無害化）、および独立した `show-me-your-work` スキルが未整備だった。
3. **LOOP-04（敵対的最終レビュー）の未実装**: 重点 7 項目（`errorlint` 条件式・`protogetter` nil ガード・`auth-hub` 設定読込・`altctl` パス封じ込め・`nilerr` 縮退・`news-creator` ゲートウェイ・長大関数分割）を対象に、異系統モデルで「壊す役」レビューを行い、4 分類（`fix` / `investigate` / `note` / `dismiss`）・`fix` への再現証明必須化・`blast-radius` 実行証明・判断ログへの 1 指摘 1 行記録を強制する仕組みとスキルが未実装だった。
4. **LOOP-05（パケット定型 eval）の未実装**: `CORPUS-01` から抽出した 5 件以上の評価シナリオを、観察者効果を避ける中立ディレクトリ名で展開し、`CHECK-01`・特性テスト・`LOOP-01`・トランスクリプトのファイル読込主張検証で決定論的に採点し、前後 3 試行以上の比較結果を判断ログへ残す仕組みが未実装だった。
5. **LOOP-06（信頼に基づく並列数制御）の完了条件未達**: `harness-run status` は推奨並列数を算出するのみで、**並列数の変更を理由つきで `decisions.tsv` に残す**記録経路と前回並列数の継続追跡が欠落していた。
6. **LOOP-07（区切りごとの `/correct`）の未実装**: `decisions.tsv` の `reverted` / `mismatch` 行から 2 回以上発生した失敗クラスを自動抽出し、`ARCH → CHECK → VERIFY → LEDGER` の優先順で対処を決定して「クラス・証拠・選んだ段・上の段を使わなかった理由」を機械検証・記録する仕組みと `/correct` スキルが未実装だった。

## Decision

[[001028]] の純 Go 標準ライブラリ単一バイナリ方針（`scripts/altharness/go.mod` の外部依存ゼロ）および [[001032]]・[[001037]] の整合方針を維持し、`LOOP-01〜07` のすべての運用ループ機構と pstack 準拠スキル群を `scripts/altharness/alt-harness` へ統合する。

1. **LOOP-01 / LOOP-02 補強（`internal/packet`, `internal/lang`）**:
   - `host-final-check.sh`（`alt-harness host-final`）に実行順ランダム化テスト支援（`--random-seed` および Go `-shuffle` / Python `pytest-rand` の統合実行・シード出力）を追加し、既存の `--test-cmd` 契約と完全互換に保つ。
   - `alt-harness packet measure` に `--turn-limit-s`（既定の 1/5 で `max_command_budget_s` を算出・クランプ）および任意 `--log-run` を追加し、未計測・予算超過・コマンド改変を fail-closed で拒否する検証を固定する。
2. **LOOP-03 / LOOP-06 完結（`internal/guards`）**:
   - `alt-harness harness-run validate` を新設し、6 列 TSV ヘッダ・1 行目 `init`（`policy=` と `completion=`）・ISO8601 時刻・ポインタ証拠・正準結果語彙を機械検証する。あわせて TSV セル先頭の式インジェクション文字（`=`, `+`, `@`）を安全化する。
   - `alt-harness harness-run parallelism`（`--apply`, `--current`, `--base-parallelism`, `--format`）を新設し、直近 10 件の終端結果から推奨並列数を算出し、変更時に理由・集計・ポインタ証拠つきで `decisions.tsv`（`phase=parallelism`）および `.harness/runs/<branch>/parallelism.json` へ永続化する。
   - `.claude/skills/show-me-your-work/SKILL.md`（および `.agents/skills/show-me-your-work`）を整備する。
3. **LOOP-04 敵対的レビュー（`internal/loopreview`, `alt-harness loop-review`）**:
   - `brief`（重点 7 項目・`CORPUS-01` 要約・`CHECK-01` 候補・差分統計の構造化出力）、`validate`（異系統モデル強制、`auto_applied: false` 強制、4 分類 `fix`/`investigate`/`note`/`dismiss`、`fix` への再現コマンド/テスト証明必須、`safe` 判定への `blast-radius` 実行証明必須、7 項目網羅検査）、`record`（検証済みレポートを `.harness/runs/<branch>/reviews/` へ保存し 1 指摘 1 行で `decisions.tsv` へ追記）、`check-coverage`（重点 7 項目すべての判断ログ記録確認）を実装する。
   - `.claude/skills/interrogate/SKILL.md` および `.claude/skills/blast-radius/SKILL.md`（および `.agents/skills/` リンク）を整備する。
   - 異系統モデル（Carbon High）による重点 7 項目の実敵対的レビューを実施し、実行可能な証拠とともに検証・記録する。
4. **LOOP-05 パケット定型 eval（`internal/loopeval`, `alt-harness loop-eval`）**:
   - `CORPUS-01` から抽出した 7 シナリオ（`E-01`〜`E-07`: `C-01`, `C-06`, `C-07`, `C-11`, `C-15`, `C-16`, `C-18`）を `scripts/harness/eval/scenarios/` に配置し、観察者効果を防ぐ中立ディレクトリ名（`eval`/`benchmark`/`candidate`/`rubric`/`corpus` 等の語彙を機械禁止）で隔離ワークスペースを生成する `stage` を実装する。
   - `CHECK-01` スクリーナ・特性テスト・`LOOP-01` `verify-handoff`・ツール呼び出しトランスクリプト（JSONL）のファイル読込主張検証を組み合わせた決定論的採点器 `grade` と、前後各 3 試行以上を比較して `decisions.tsv` へ記録する `compare` を実装する。
   - `.claude/skills/loop-eval/SKILL.md`（および `.agents/skills/loop-eval`）を整備し、`loop-eval validate` を `alt-harness gate harness` へ配線する。
5. **LOOP-07 区切りごとの `/correct`（`internal/loopcorrect`, `alt-harness loop-correct`）**:
   - `scan`（`decisions.tsv` の `reverted`/`mismatch` から 2 回以上再発したクラスを抽出し `CORPUS-01` 登録有無を照合）、`record`（`ARCH > CHECK > VERIFY > LEDGER` 階層検証・選択段より上位の段を使わなかった理由の必須検証・実在 `corpus_id` と強制手段参照の検証・Markdown 表保存と `decisions.tsv` 追記）、`scaffold-corpus`（次番号 `C-NN` の雛形生成）を実装する。
   - `.claude/skills/correct/SKILL.md`（および `.agents/skills/correct`）を整備する。
6. **統合配線・メタゲート・規則台帳**:
   - 新規サブコマンド（`loop-review`, `loop-eval`, `loop-correct`）を `main.go`・`selfcheck`（`validAltHarnessSubcommands`）・`meta` ゲート・`corpus`（`ImplementedChecks` へ `LOOP-04..07` 追加）・`.agents/rules/rule-ledger.md` へ統合する。
   - 先行事例帰属: 運用ループの各概念（`show-me-your-work` 6 列 TSV、`interrogate` 4 分類・非自動適用、`blast-radius` 実コード証明、`eval` ブラインド中立環境・トランスクリプト検証、`/correct` 2 回クラス化・上位段優先ラダー）は Alt 自身の失敗記録（`docs/review/lint-rollout-harness-learnings-2026-11-21.md`）を第一の根拠としつつ、`cursor/plugins` の `pstack`（MIT License, primary source: <https://github.com/cursor/plugins/blob/main/pstack/docs/guide/README.md>）を参照したクリーンルーム実装として明記する。

検討して却下した案:
- **LOOP-04/05/07 を Python スクリプトや独立 CLI として実装する案**: [[001028]] の単一 Go バイナリ・外部依存ゼロ方針および CI 並列メタゲート統合に反するため却下した。
- **pstack プラグインを外部から直接導入するだけで Alt 固有の機械検証を持たない案**: Alt の `TaskPacket` / `decisions.tsv` / `CORPUS-01` / `CHECK-01` / `rule-ledger.md` と連動する決定論的検証（fail-closed）ができず、モデル割り当て等も環境依存で崩れるため、Alt の単一 Go バイナリ上で機械検証可能な形へクリーンルーム統合した。

## Consequences

### Pros

- `LOOP-01〜07` のすべての運用ループ項目が、自己申告や文章ルールに頼らない決定論的な Go CLI サブコマンド・テスト・スキルとして完結する。
- 並列数の増減、敵対的レビュー指摘、パケット定型の前後比較、`/correct` のクラス分類と上位段却下理由が、すべて `.harness/runs/<branch>/decisions.tsv` に 1 行 1 判断のポインタ証拠付きで蓄積され、セッション切替をまたいで監査可能になる。
- `loop-eval validate` が `alt-harness gate harness` に常時組み込まれるため、評価シナリオ・中立性制約・コーパス参照の陳腐化を CI で自動防止できる。

### Cons / Tradeoffs

- `alt-harness` バイナリのサブコマンドが増える分、保守対象パッケージが 3 つ（`loopreview`, `loopeval`, `loopcorrect`）増えるが、既存の `guards`・`packet`・`screener`・`corpus` パッケージを直接再利用することで重複を抑える。
- `LOOP-04`（異系統モデルレビュー）や `LOOP-05`（前後 3 試行比較）の実運用には相応のトークン・実行時間を要するが、重点絞り込み（`brief`）とシナリオ数調整によりコストを制御できる。
