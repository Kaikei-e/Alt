# ADR-001000: news-creator の BE 記事要約オフロードを OpenAI 互換 gateway 経由のターゲット宣言方式に置き換える

## Status

Accepted

## Date

2026-11-07

## Affected Services

- news-creator: `DistributingGateway` の transport を Ollama ネイティブ API から OpenAI 互換 API に置き換え、送り先を `(base_url, model, num_ctx)` のターゲット宣言にした。`DistributingGateway` を受け取るのは `SummarizeUsecase` だけになった
- compose / `.env.template` / `.env.example` / `deploy/host-prereqs.yaml`: 新しい env キーへの追従と、旧キーの `retired_env` 登録

## Context

[[000497]] は、BE（バッチ）要約をリモートの Ollama 群へ分散させる仕組みを、Decorator Gateway として導入した。リモートは `/api/generate` に Gemma 4 の raw プロンプトを送り、`/api/tags` でヘルスチェックし、URL 単位で識別していた。必須モデル名は `DISTRIBUTED_BE_REMOTE_MODEL` の 1 つで、[[000575]] で URL ごとの上書き（`DISTRIBUTED_BE_MODEL_OVERRIDES`）が加わっていた。

運用中に次のことがわかった。

- **リモートへの分散が黙って止まっていた。** リモートノードのモデル構成が変わり、必須モデル名を持つノードがなくなっていた。ヘルスチェックは起動直後から全リモートを unhealthy と判定し、BE 要約は全件がローカル GPU に戻されていた（ログは WARNING 1 行だけ）。ローカルでの処理は 1 記事あたり平均約 30 秒だった。
- **運用者側には、複数の推論ノードを束ねる OpenAI 互換 gateway がすでにあった。** gateway が公開する API は `/v1/chat/completions` と `/v1/models` だけで、Ollama ネイティブ API はない。さらに `/api/tags` を叩くと、非 JSON の応答が 200 で返る。URL を差し替えるだけでは、旧ヘルスチェックはこの gateway を「正常」と誤判定する。
- **束ねられたノードのモデルは Gemma ではない。** Gemma 4 のターン記法を埋め込んだ raw プロンプトは送れず、chat messages に変換し、バックエンド側のチャットテンプレートに任せる必要がある。
- **Ollama の OpenAI 互換経路は、コンテキスト長を超えたプロンプトを黙って先頭から切り詰める。** 実測では、約 9 千トークンのプロンプトがコンテキスト 4096 のノードで約 2 千トークン、8192 のノードで約 4 千トークンに切られた。要約指示ごと消え、モデルは「何をすればいいか」を聞き返した。OpenAI 互換経路ではリクエストごとに `num_ctx` を指定できない。BE の記事プロンプトは最大で約 1.2 万トークン（日本語約 2 万字）になる。
- **束ねられたノードはいずれも思考型モデルだった。** 思考を止めないと、思考トークンが `max_tokens` を使い切り、本文が空になる。gateway を通しても効いた止め方は、OpenAI 標準の `reasoning_effort: "none"` だけだった。`chat_template_kwargs` は gateway で落とされた。

## Decision

**BE 記事要約のオフロードを、operator が宣言した OpenAI 互換ターゲットへの dispatch に置き換える。送り先の選択は news-creator が行う。**

1. **ターゲット宣言**
   - `DISTRIBUTED_BE_TARGETS=<base_url>|<model>|<num_ctx>,...` でターゲットを宣言する。
   - `base_url` はオリジンのみとし、パス・認証情報・クエリ・非印字文字を含むものは起動時に拒否する。
   - `DISTRIBUTED_BE_ENABLED=true` なのにターゲットが空、または不正なら、起動時に失敗する（fail-fast）。
   - 旧キー `DISTRIBUTED_BE_REMOTES` / `DISTRIBUTED_BE_REMOTE_MODEL` / `DISTRIBUTED_BE_MODEL_OVERRIDES` は削除し、互換 shim は置かない。代わりに `host-prereqs.yaml` の `retired_env` に登録する。
   - 実値はホスト固有なので、`deploy/desired-env.lkal` には宣言しない。ホストの `/local/*` に置く。
2. **Transport**
   - `POST {base_url}/v1/chat/completions` で送る。Gemma 4 のターン記法のプロンプトは chat messages に変換し、不正な構造は ValueError にする。
   - 送るパラメータは `max_tokens` / `temperature` / `top_p` だけ。
   - 任意の `DISTRIBUTED_BE_REASONING_EFFORT` は、設定されているときだけ送る。
   - Alt 内部の推論トークンは外部 gateway に送らない。
   - リダイレクトは追わず、応答本文の読み込みには上限を設ける。
3. **ヘルスチェック**
   - `GET {base_url}/v1/models` を base_url ごとに 1 回だけ叩き、各ターゲットのモデル ID が一覧に含まれていれば healthy とする。JSON でない 200 は unhealthy にする。
   - dispatch が失敗したら指数バックオフのクールダウンに入れる。これを解除できるのは dispatch の成功だけで、一覧の probe では解除しない。
   - リクエスト単位の拒否（408 / 429 以外の 4xx、空の本文）では健康状態を減点しない。
4. **黙った切り詰めを避けるガード**
   - プロンプト長は UTF-8 のバイト数 ÷ 3 で保守的に見積もる。見積もりに `max_tokens` と余裕分を足した値が宣言 `num_ctx` に収まるターゲットにだけ送る。
   - 収まるターゲットが空いていなければ、他のターゲットへ回し、それもなければローカルで処理する。
5. **劣化契約（[[000943]]）は維持する**
   - リモートが全滅しているか、すべて埋まっているときは、ローカルの BE slot を取得したうえでローカルで生成する。
   - 1 つの BE slot の中でローカルに落ちたら、その slot のリトライ中はローカル slot を 1 つだけ保持し続ける。
   - その slot を他タスクや閉じた後から使った場合は RuntimeError にする。
6. **適用範囲は記事要約だけ**
   - Recap / Recap card / Expand / Plan / Morning letter は、ローカル gateway に直結する。
   - Recap は JSON スキーマ付きの構造化出力を使っている。異なるモデル群でそれが成立するかは検証していないので、今回は対象から外した。

検討した代替案:

- **gateway 側の重み付きルーティングで振り分ける:** news-creator は論理モデル名で同時に N 件投げるだけになる。しかしランダムな振り分けでは、同じノードに 2 件重なると待ちが出る。また、共有 gateway の設定変更と再起動が必要になる。既存の「空いているターゲットを選ぶ」処理、ヘルス、クールダウン、ローカル fallback を活かせないので却下した。
- **旧 Ollama ネイティブ transport を残し、モード切替を追加する:** 2 経路を保守することになるうえ、旧経路はすでに実質機能していなかった。Ollama は OpenAI 互換 API も持っているので、ターゲット宣言方式で直接ノードも指せる。却下した。
- **ノード側のコンテキストを一律に大きくして、ガードを置かない:** ノードごとのメモリ事情でコンテキスト長は揃えられず、Alt 側から実効値を検証する手段もない。宣言値に基づくガードを Alt 側に置くことにした。
- **[[000943]] の「集中インフェレンスルータ新設」との関係:** 本決定は Alt が新たに常駐プロキシを持つものではない。operator が既に運用している外部 gateway を、オフロード先の 1 つとして扱うだけである。劣化状態の判定と遷移は、引き続き news-creator の gateway 層が担う。

## Consequences

### Pros

- 送り先のモデルやノード構成が変わっても、env の宣言を書き換えるだけで済む。必須モデル名の不一致で全リモートが無言で脱落する、という障害様式がなくなる。
- 宣言 `num_ctx` に基づくガードによって、要約指示ごと切り捨てられた要約が保存されることを防げる。
- gateway を経由することで、推論ノード側の可観測性（gateway のログ・同時実行制御）をそのまま使える。
- Recap など構造化出力の経路はローカルに固定され、モデルの異質性の影響を受けない。

### Cons / Tradeoffs

- BE 要約は、ターゲットごとに異なるモデルで生成されるようになる。要約の文体や品質のばらつきは、pre-processor の品質チェックに依存する。
- バイト数 ÷ 3 の見積もりは日本語で約 1.6 倍の過大評価になる。宣言 `num_ctx` が小さいターゲットには、実際は収まる長さの記事も回らない。
- gateway が自前のフォールバックルールを持っていると、指定と別のノードで生成されることがある。応答の `served_model` をログに残すだけで、検知はしていない。
- 宣言 `num_ctx` と実際のノード設定がずれていても、Alt 側では検出できない。ノード側でコンテキストを下げた場合は、宣言も合わせて更新する運用が必要。
- `DISTRIBUTED_BE_ENABLED=true` のホストで旧キーのまま新イメージを起動すると、fail-fast で起動しない。ロールアウト前に、ホストの env を新キーへ移す必要がある。
- 空の本文はリクエスト単位の拒否として扱うので、クールダウンには入らない。思考を止める設定を忘れたターゲットは毎回タイムアウトするまで生成し続け、そのあとで次へ回る。
