# ADR-001021: 「今日読む」キューをイベントから導く read model とし、上限 7 本・期限 48 時間・期限切れは未読に戻す

## Status

Accepted

## Date

2026-11-18

## Affected Services

- proto — `proto/alt/reading/v1/reading.proto` の `ReadingService` にキュー操作 RPC を追加する
- alt-frontend-sv — Swipe 右払いのキュー積載、上限到達時の通知、手動解除 UI を実装する
- alt-butterfly-facade — 追加 RPC の公開許可リスト更新と中継を行う
- alt-backend — キュー操作の Connect-RPC ハンドラ、上限の判定、`expires_at` の確定、起動時の必須設定検証を実装する
- knowledge-sovereign — キュー用イベントの認可設定と `reading_projector` の拡張を行う
- knowledge-sovereign-db — `reading_queue_items` read model テーブルのマイグレーションを新設する

## Context

持ち主が 2026-11-18 に定めた製品目的のうち「読ませる」は、読むと決めた記事が少数だけ手元に残る状態を指す（[[001015]]）。R2 では Swipe の右払いを「今日読む」としてキューに積み（[[001020]]）、起動面 `/today`（[[001022]]）で消化する導線を作る。

現状、あとで読むための列やキューの概念はリポジトリ内に存在しない。既存のお気に入り（`favorite_feeds`）は `alt-db` 側の可変の行であり、上限や期限を持たない。2026-11-17 時点の本番データを読み取り専用で計測したところ、Swipe からのお気に入り追加は直近 90 日で 0 件だった。

`alt-db` の未読一覧 SQL（`alt-backend/app/shared/driver/alt_db/feed_sql_builder.go` の `buildUnreadFeedsCursorQuery`）は、`read_status` に `is_read = TRUE` がない購読フィードを `created_at DESC, id DESC` 順で取得している。

## Decision

1. **「今日読む」キューをイベントから導く read model `reading_queue_items` として `knowledge-sovereign` に新設する。** Swipe で右に払った記事（[[001020]]）を `reading.queued.v1` として追記し、手で外す操作を `reading.unqueued.v1` として追記する。`reading_projector`（[[001018]]）がこれらのイベントから `reading_queue_items` を射影する。可変の行を正にせず、お気に入りの流用もしない。理由は、破棄可能な read model の原則を保ち、消化率と期限切れ率（[[001015]]）をイベントから計測できるようにするためである。
2. **上限は 7 本とし、上限に達しているときは積まずにその場で知らせる。** 古い項目を自動で押し出さない。理由は、持ち主が自分で選んだ記事をシステムが黙って落とさないためであり、同時に手元に残る記事数を少数に保つためである。
3. **期限は積んだ時点から 48 時間とし、`expires_at` と `queue_policy_version` を積む時点で確定してペイロードに書く。** 理由は、イベントから再射影したときに期限判定の結果が変わらないようにするためである。
4. **期限切れはイベントにしない。** 読み出すときに `expires_at` を過ぎた項目を除外して返す。理由は、時間の経過はユーザーの操作という事実ではなく、読み出す時点の時刻で一意に決まる導出結果であるためである。
5. **期限が切れた記事は未読に戻し、キューにある間だけ未読の山から除いて見せる。** 積む操作では `read_status` に既読を書かず、操作のないまま既読を書く処理も作らない。`alt-db` にキューの写しは持たない。未読一覧から除く処理の実装位置は R2 で決める（キューは最大 7 本なので取得側で除ける）。理由は、積載時に既読を書いてしまうと期限切れ時に既読を戻す処理が要り、既読の意味がさらに濁るためである。
6. **「読んだ」（[[001018]]）が成立した記事はキューから外れ、手で外すときは `reading.unqueued.v1` を送る。** 理由は、読み終えた記事と不要になった記事を自動で、または明示の操作でキューから片付けるためである。
7. **「今日は読み終えた」という独立した状態は持たない。** キューが空であることと、その日に読んだ本数から導く。理由は、独立した完了状態を持つと後から積んだ場合や日付変更時の不整合を招くためである。
8. **`ReadingService`（[[001018]]）に `QueueArticle`、`UnqueueArticle`、`GetReadTodayQueue` を追加する。** あわせて `knowledge-sovereign/config/event-auth-policy.json` の許可リスト更新と Pact の失敗テスト（RED）を producer 配線より先に置く。理由は、既存の読書イベント経路とサービス境界および契約テストの規律を揃えるためである。
9. **上限と期限を必須の起動設定（`READING_QUEUE_CAP`、`READING_QUEUE_TTL_HOURS`）とし、未設定なら起動に失敗させる。** 設定は、上限を判定して `expires_at` を確定する `alt-backend` に置く。既存の必須設定検証（`alt-backend/app/config/validation.go`）と同じく fail-fast とする。期限切れの割合を 1 週間見て設定値を調整する。調整しても、すでに積まれた項目の `expires_at` は変えない。理由は、設定漏れを暗黙の既定値で隠さず（[[000928]]）、調整の前後で既存イベントの再射影結果を守り続けるためである。

### 検討した代替案

- **(a) お気に入り（`favorite_feeds`）を流用する**: 退けた。可変の行であり期限がなく、2026-11-17 時点の本番データを読み取り専用で計測した結果、Swipe からの追加は直近 90 日で 0 件だったためである。
- **(b) 期限切れを自動で既読にする**: 退けた。操作のない既読を書く処理が必要になり、既読の意味がさらに濁るためである。
- **(c) 上限を設けない**: 退けた。積んだまま読まない列になるためである。
- **(d) 期限を暦日の終わりにする**: 退けた。夜に積むとすぐに期限が切れてしまうためである。
- **(e) 期限切れをイベントとして書く**: 退けた。理由は決定項目 4 のとおりである。

## Consequences

### Pros

- キューの積載・解除・読了が追記専用イベントとして残り、再射影可能な read model として安全に運用できる。
- キューへ積んでも `read_status` を汚さないため、期限切れ時に追加の巻き戻し処理なしで未読一覧へ戻る。
- 上限 7 本・期限 48 時間という制約により、「今日読む」の一覧が消化可能な大きさに保たれる。

### Cons / Tradeoffs

- 未読一覧の取得時にキュー内の記事（最大 7 本）を除く具体的な実装位置（取得件数の補填方法を含む）は、この ADR では決めておらず R2 で決める。
- キューから記事を外す「読んだ」の具体的な閾値と、R1 の既読仕様変更（[[001019]]）が確定するまで、Swipe・未読一覧・`/today` 間の挙動は段階的に統合する前提となる。
- `READING_QUEUE_CAP` と `READING_QUEUE_TTL_HOURS` を必須設定とするため、デプロイ前に Compose や環境変数定義へ両変数を追加する必要がある。
- 期限切れをイベントにしないため、過去の任意時点の期限切れ履歴を再現するには、積載イベントの `expires_at` と読了・解除イベントの時刻を突合して算出する必要がある。
