# ADR-000980: ユーザ旅程の deep health と synthetic 契約を運用し Prometheus の multi-window burn-rate SLO を正規のページ経路にする

## Status

Accepted

本 ADR はリポジトリ上の契約・計装・promtool / カウンタ / GameDay 台本の GREEN を記録する。外部 synthetic provider の開通も、本番へのルール reload も行っていない。[[000420]] と [[000969]] を置換しない。

## Date

2026-08-19

## Affected Services

- alt-butterfly-facade（旅程カウンタの発行点）
- alt-backend（Knowledge Home `status=` ラベル、ops `/health/deep`）
- news-creator / recap-subworker / knowledge-sovereign / search-indexer（deep health）
- Prometheus / Alertmanager / Grafana Unified Alerting（pause した KH コピー）
- `observability/synthetic/probes.yaml`

## Context

cheap liveness が 200 でも、依存が死んでいる・エッジ旅程が壊れている・エラー予算が燃えている、の三つは別の事実である。これまでそれらは別系統で沈黙できた。

- recap-subworker は `/health` 200 のまま 8 日間分類不能だった（[[PM-2026-036]]）。artefact の `is_file()` は cheap probe ではなく deep の critical check に属する。
- news-creator の cheap `/health` は Ollama ダウンでも 200 を返し得る。summarise 不能は `/health/deep` でなければ見えない。
- Knowledge Home は [[000420]] の MWMBR を持つが、feeds / login / search には旅程カウンタが無く、「プロダクトが死んでいる」報告と page が結びつかなかった。BFF は JWT 401・circuit-breaker 503・upstream 5xx を backend handler より先に見る。
- in-host blackbox が loopback `/health` を叩いても、TLS 終端・IAP・cookie セッション・本文アサーションは見えない。それを P2-11 完了と呼ぶと synthetic が空洞になる。
- [[000969]] で Alertmanager / Pushover は存在する。Grafana Unified Alerting の Knowledge Home 可用性コピーを同時に live にすると二重 page する。

`scripts/observability-validate.sh`（promtool check/test + 構造監査）と `scripts/tests/test-user-journey-slo-counters.py` は GREEN。live 14.4× 点火と外部 provider 開通はオペレータ前提であり、本 ADR の範囲外。

## Decision

**cheap liveness と deep health とエッジ synthetic と Prometheus MWMBR を役割分担して運用する。canonical な page は Prometheus ルールである。synthetic の機械可読契約は provider 非依存とし、ベンダー開通は ops gate に残す。**

### D1. `/health/deep`

- 語彙は `pass` | `warn` | `fail`。cheap 側の `healthy` / `ok` と混ぜない。
- HTTP: 全体 `pass`/`warn` は 200、critical `fail` は 503。
- compose `healthcheck` を `/health/deep` に向けない。依存瞬断で本プロセスを restart-loop させない。
- 並列・check あたり 250ms・全体 <1s・2–5s cache + singleflight。reason に DSN / path / peer / stack を載せない。
- 置く場所はサービスごとのリスナー（正本は [[health-deep-contract]]）。**unpublished PKI ops `:9110` が `/health/deep` を serve するとは限らない。** alt-backend は ops `:9110`（ホストへ publish しない。toolbox から `http://alt-backend:9110/health/deep`）。news-creator は FastAPI `:11434`、recap-subworker は `:8002`、search-indexer は REST `:9300`。この 3 本の PKI ops `:9110` は `/health` と `/metrics` のみ（`/health/deep` は 404）。knowledge-sovereign は ops `:9501`（ホスト `127.0.0.1:9511`、`ADMIN_AUTH` 時は token）。DoS whitelist に載せない。

### D2. synthetic（エッジ旅程）

正本は `observability/synthetic/probes.yaml`。login session / feeds cursor / Knowledge Home / search をエッジから叩き、HTTP 200 だけでなく JSON/body を assert する。連続失敗 3 で page 候補。**in-host blackbox では契約完了にしない。** 本リポジトリは cloud アカウントを作らず、probe 資格情報も本番ホスト名も commit しない。activation はオペレータが provider か out-of-host runner を繋いだとき。

### D3. ユーザ旅程 SLO

カウンタは BFF: `alt_user_journey_requests_total{journey="feeds|login|search",status="ok|error"}`。SLO は Knowledge Home と同じ 99.5% 可用性。

- Page: 14.4× burn on (1h ∧ 5m)、1h に min-events
- Ticket: 6× burn on (6h ∧ 30m)。solo-ops では Pushover Normal。Emergency にしない
- `UserJourneyRequestsAbsent`: シリーズ欠落を 15m で page。**BFF 新イメージで 6 本のシリーズを確認してから** Prometheus を reload する。逆順は空 vector で Emergency する
- login の 401 は「パスワード誤り」ではなく「セッション検証経路の死」を error にする。Kratos の誤パスワードは予算を焼かない
- Recap は比率 SLO にしない。鮮度は既存 heartbeat / `absent()` を使う
- Knowledge Home `alt_home_requests_total` は `status="ok|error"` を付ける。Grafana 側の可用性 burn コピーは `isPaused: true`

### D4. 検証の層

| 層 | 何を証明するか | 本 ADR 時点 |
|---|---|---|
| リポジトリ | ルール構文、promtool ユニット、カウンタが request path にある、probe spec が parse できる、GameDay 台本がある | GREEN |
| ホスト | BFF rebuild、Prometheus reload、Alertmanager→Pushover、deep 実装の稼働 | オペレータ前提。未実施 |
| 外部 | spec を provider に import しエッジから連続失敗で page する | ops gate。未実施 |

### 検討した代替案

| 案 | 却下理由 |
|---|---|
| Grafana Unified Alerting を canonical にする | [[000969]] の Prometheus→Alertmanager と二重 page する。KH コピーは pause |
| compose healthcheck を `/health/deep` にする | 依存の warn/fail でコンテナが restart し、障害を増幅する |
| in-host blackbox で P2-11 完了とする | エッジ / セッション / body を見ない |
| unlabeled `http_requests_total` を旅程 SLO に流用する | feeds/login/search を分離できない |
| Recap にリクエスト比率 SLO を新設する | バッチ鮮度の問題であり、カウンタ発明は偽の予算になる |
| ベンダー SDK をリポジトリに固定する | 資格情報とアカウント作成が docs/CI に漏れる。spec を正本にする |

## Consequences

### Pros

- 「cheap 200」と「仕事ができる」と「ユーザ旅程が生きている」が別シグナルになる。
- 旅程 page が BFF の実カウンタに結びつき、promtool が 14.4× / 回復 / min-events / 欠落を pin する。
- synthetic を後からどの provider に繋いでも、旅程 ID と assert が drift しにくい。
- Alertmanager 導入（[[000969]]）後に「ルールはあるが誰にも届かない」へ戻さない。canonical が一つ。

### Cons / Tradeoffs

- **リポジトリ GREEN ≠ 本番で page が届く。** reload 前の BFF イメージにカウンタが無いと `UserJourneyRequestsAbsent` が誤って Emergency する。Pushover の live drill は GameDay 窓が要る。
- synthetic activation は未完。spec だけの状態を「ユーザ旅程を監視している」と呼んではならない。
- `/health/deep` の実装カバレッジは全サービスではない。未実装サービスを cheap 200 だけで「依存も生きている」と読んではならない。
- BFF がカウンタの単一発行点なので、BFF 自体の scrape 欠落は全旅程の absent page になる（意図した fail-loud）。
- 14.4× の live 点火は共有環境では危険。通常検証は promtool、live は予定された GameDay のみ。

## Deploy-model 整合性セルフチェック

新設 compose service なし。ルールと probe spec は configs / bind で既存 prometheus に載る。deep health は既存 ops リスナー。synthetic provider は compose 外。

- [x] 新設 compose service が `depends_on` で他 service を gate するか？ — 新設なし
- [x] 新設 compose service に `restart: "no"` の one-shot init container を含むか？ — なし
- [x] 新設名前付き volume を populate する責務はどこにあるか？ — なし
