# ADR-000957: 残る 11 サービスの E2E を Playwright へ移行して Hurl を退役させ、共有ハーネスと単一 CI ワークフローに統合する

## Status

Accepted

## Date

2026-08-06

## Affected Services

- **e2e** — `e2e/hurl/`（11 サービス・116 シナリオ）を削除。`e2e/playwright/<service>/` を 11 スイート新設し、既存の alt-backend パイロットと合わせて 12 スイート・1039 テスト
- **CI** — `e2e-hurl.yml`（9 ジョブ手書き）と `e2e-playwright-alt-backend.yml` を `e2e-playwright.yml` に統合
- **compose** — `compose.staging.yaml` の `knowledge-sovereign` に `image:` キーを追加
- **alt-frontend-sv** — `e2e/playwright/alt-frontend-sv/run.sh` のイメージ pin を修正（プロダクションコードは無変更）

いずれもプロダクションコードは無変更。E2E から観測される契約のみが対象。

## Context

[[000956]] が alt-backend 1 サービスを Playwright へ移し、その「失うもの・負債」の筆頭に
こう書いた——**Hurl と Playwright の 2 フレームワークが `e2e/` に並存する**。本 ADR は
その負債を清算する。

移行を「網羅性向上」と同時に行う判断の根拠は、パイロットが見つけた 3 つの構造的欠陥が
alt-backend 固有ではなく、Hurl というツールの表現力に由来していた点にある。

### 1. `jsonpath "$" exists` は何も検証しない

`null` / `[]` / `{}` / `{"error": ...}` のすべてを通す。退役した 116 シナリオはこの形の
アサーションに広く依存していた。1:1 で機械的に移植すれば、**テストがないという事実ごと**
移植することになる。

実害の実例：

- `knowledge-sovereign/03-event-append-happy.hurl` は `event_seq` を
  `matches "^[0-9]+$"` で検証していた。これは `"0"`——driver が「重複、書き込みなし」を
  表す値——も通す。append が何もしなくても green だった。
- 同 `04-event-latest-seq.hurl` は 03 が `[Captures]` した `event_seq` を**一度も比較して
  いなかった**。同じ正規表現を再度当てているだけで、README が謳う「同じ event_seq を返す」は
  実行可能な形では検証されていなかった。
- `mq-hub` の README は `mqhub_errors_total` をカバーすると書いていたが、warmup が
  Publish 1 回だけだったため、そのメトリックファミリは lazy registration により
  scrape 時点で存在しなかった。

### 2. 順序依存が並列化の天井だった

`--jobs 1` は knowledge-sovereign / mq-hub など複数スイートで load-bearing だった。
`12-stream-info.hurl` が `04` と `07` の publish、`10` の consumer group 作成に依存する、
といった形である。Hurl は `[Captures]` でしかシナリオ間の値を渡せず、各シナリオが自分で
seed する書き方に構造的な誘因がない。

### 3. 「このポートは応答してはならない」が表現できない

Hurl では接続失敗は run failure であってアサーション成功ではない。alt-data-hub /
alt-harvester のような **topology が主題**のスイートは、シェル側で極性を反転させる
必要があった（`assert-transport-refused.sh` が Hurl の exit code 3 を要求し、
`HTTP *` を書いた probe ファイルを併用する）。テスト対象の性質がフレームワークの外に
漏れていた。

## Decision

**残る 11 サービスの E2E を Playwright API スイートへ移行し、Hurl を退役させる。**
併せて、12 スイートが共有する 3 層——TypeScript ヘルパ / シェルライフサイクル / CI——を
それぞれ 1 箇所に集約する。

### D1. `_shared/` — 12 スイートが共有する TypeScript ヘルパ

パイロットの `src/http.ts` を昇格し、11 スイートが各自で再発明したであろうものを追加した。

| モジュール | 解く問題 |
|---|---|
| `connect.ts` | Connect-RPC。特に `expectProcedureMounted` は 404（未登録）と業務的 404 を判別する |
| `eventual.ts` | Hurl の `--delay` 固定スリープを収束アサーションに置き換える |
| `net.ts` | 「このポートは閉じている」を通常のアサーションとして書く |
| `ids.ts` | worker/test 単位のユニーク命名（並列安全性の土台） |
| `schemas.ts` | int64-as-string など protojson の事実、エラーエンベロープ |
| `config.ts` | `defineApiSuite` — 唯一の Playwright config |

`expectProcedureMounted` は CLAUDE.md ルール 8 を E2E 境界に持ち出したものである。
DI 依存が nil を返して登録がスキップされたハンドラは、ユニットテストからも
「2xx でない」形のアサーションからも見えない——サービスが単に存在しなくなり、
呼び出し側には行が無いのと区別できない 404 が返る。**パスが解決するかどうか**だけが
両者を分ける。

### D2. `_lib/suite.sh` — 12 本の run.sh が複製していたライフサイクル

slice 描画・network pool 回収・retry 付き `up`・失敗時ログダンプ・秘匿値の redaction・
teardown 順序で約 150 行。複製は必ずドリフトする（1 本がセキュリティ監査後に redaction
規則を得ても 11 本は得ない）。各 run.sh はイメージ・エンドポイント・compose サービスの
**宣言**に縮んだ。

### D3. インストールルートを 1 つにする

12 個の package.json は 12 通りの Playwright バージョンに分岐しうる。1 つなら分岐しない。

**npm workspaces は評価のうえ採用しない。** workspace サブディレクトリからの `npm ci` は
リポジトリルートにインストールし、しかも既存の `node_modules` を先に削除する。
リポジトリを 1 パスに bind mount している以上、並列スイートが互いの木を消し合う。

### D4. 順序依存は持ち越さず、命名で解く

各テストが自分で読むデータを seed する。隔離は teardown ではなく**命名**で行う——
teardown は兄弟 worker の `list` と競合するし、staging stack はどのみち dispatch ごとに
破棄される。順序が本当に不可分な場合（単調増加シーケンス、共有レートリミッタのバケツ）
だけ `workers: 1` プロジェクトに隔離し、**なぜ self-seeding が不可能か**をコメントで
残す。

### D5. CI は suites.yaml から導出する

サービスごとの shard 数は「そのスイートがどれだけ遅いか」という性質であり、スイートの
他の事実の隣に置くべきである。手書きマトリクスは静かにドリフトし、しかも悪い方向に——
誰かが `shards: 4` を `6` に上げても CI は 4 のまま走り、変更したように読める。
`plan` ジョブが `suites.yaml` から 3 つのマトリクスを生成する。

**シャーディングは最後の手段とする。** 12 スイートは既に 12 並列であり、各 shard は
compose slice 起動コストを丸ごと払う。4 分で終わるスイートを分割すれば遅くなる。
現状 `shards:` を持つのは alt-backend のみ。

### D6. Docker 不要の静的ゲートを高コストジョブの前段に置く

`check-suites.sh` は全スイートの typecheck と `playwright test --list` を数秒で走らせる。
`--list` は config をロードし、全 spec を import し、全 fixture を解決して test tree を
返すので、壊れた import・無効な project matcher・存在しない fixture・タイトル重複を
すべて捕らえる。**タイプミスのコストを 20 分から 1 分にする。**

各スイートが必要とする env は、そのスイート自身の `env.ts` の `requiredEnv(...)` 呼び出しを
読んで供給する。エンドポイントが増えたスイートは自動的にカバーされ、これらのヘルパを
経由せずに env を読むスイートはここで落ちる——それ自体が finding である。

### D7. 「配線されているつもり」を機械的に検出する

`audit-suite-wiring.py` は、全テストが green のまま成立する 3 つの配線ミスを検出する。

1. **ビルドされたが誰も使わないイメージ。** knowledge-sovereign の compose エントリには
   `build:` があり `image:` がなかった。CI が buildx とレジストリキャッシュで作った
   GHCR タグ付きイメージは無視され、compose が毎回ゼロからリビルドしていた。
   スイートはずっと green だった。ビルド代を二重に払い、キャッシュを一度も使わずに。
2. **転送されないイメージタグ。** compose は各 GHCR イメージを `<SERVICE>_IMAGE_TAG`
   （既定 `main`）で解決する。`:ci` にビルドしてタグを転送しないスイートは、
   **テスト対象サービスの前回リリース**に対して走る。何も落ちない。単にこのコミットに
   ついてのテストでなくなる。
3. **片側にしか存在しないスイート。** `suites.yaml` になければ CI で走らず、
   ディレクトリがなければマトリクスが落ちる。

2 には正当な逆ケースがある。acolyte-orchestrator の search-indexer は意図的に `:main` の
ままにする——テスト対象ではなく依存であり、acolyte-orchestrator と co-version されて
いないため、pin すると dispatch SHA が作っていないビルドを要求して無関係な green を
`manifest unknown` に変える。これは**判断**なので `unpinnedImages:` として書き下す。
監査は「意図的に main」と「忘れた」を区別する。ルール 8 を CI 配線に適用した形である。

## Consequences

### Pros

- **カバレッジ。** 116 Hurl シナリオ → 1039 Playwright テスト。増加の内訳は、
  (a) Hurl では書けなかったアサーション、(b) どのシナリオも触れていなかった面、
  (c) Hurl が最初の失敗で停止するため 1 ファイルに同居できなかった独立した主張の分割。
- **並列実行。** `--jobs 1` が消え、全スイートが `fullyParallel` で走る。
- **失敗が読める。** アサーション失敗にレスポンスボディが載る。失敗時は trace が残る
  （Hurl の `--report-html` の代替）。
- **ローカル再現。** `build-images.py <service>` で CI と同じビルドが再現する。
  従来ビルドは CI の中にしか無く、ソース変更後に `run.sh` を叩くと**前のイメージ**を
  黙ってテストしていた（ルール 3 が E2E ハーネスに移動した形）。
- **search-indexer がついに CI で走る。** シナリオは存在したが、どのワークフローからも
  呼ばれていなかった。手で `run.sh` を叩いたときだけ実行されていた。

### Cons / Tradeoffs

- **本 PR の時点で、アサーションはライブスタックに対して一度も実行されていない。**
  作業環境に Docker デーモンが無いため、検証は typecheck と `--list` に限られる。
  これは「spec が parse され、config が妥当で、fixture が解決する」ことしか証明しない。
  **最初の実信号は CI 実行である**——パイロット [[000956]] の初回 CI が複数の想定違いを
  暴いたのと同じことが起きる前提で扱う。移行エージェントが報告した「ソースから推論した
  が観測していない」アサーション（axum の JsonRejection ステータス、connect-python の
  未知プロシージャ応答、Playwright `clientCertificates` の mTLS 挙動など）が最初の
  候補である。
- **敵対的パリティレビューは 12 スイート中 4 スイートしか完了していない。**
  完了したのは knowledge-sovereign / auth-hub / alt-data-hub / rag-orchestrator。
  残る 7 スイート（mq-hub, news-creator, acolyte-orchestrator, tag-generator,
  alt-harvester, search-indexer, recap-worker）は移行担当のセルフ検証
  （typecheck + `--list` + 自己申告のパリティ表）までしか受けていない。
  完了した 4 件がいずれも「落ちようがないテスト」を 3 件前後ずつ見つけている以上、
  未レビューの 7 件にも同種のものが残っていると考えるのが妥当である。
  レビューは移行と独立に後追いできる（`e2e/hurl/` は git 履歴に残っている）。
- **`ignoreHTTPSErrors: true` が alt-data-hub スイート全体で有効。** CA が実行ごとに
  発行されるため。server leaf の検証は失われ、mTLS 境界そのもののアサーションで回収して
  いるが、等価ではない。
- **依存インストールが 2 コンテナに割れる**（[[000956]] から継続）。staging network は
  `internal: true` で egress が無いため、`npm ci` は default bridge の別コンテナで走る。
- **1 スイートあたりの記述量は Hurl より多い。** `.hurl` ファイルの密度は失われた。
  代わりに得たのは、型・スキーマ・並列安全性・そして「なぜこのアサーションが正しいか」を
  書ける場所である。

### 移行の途中で見つかった、移行と無関係な欠陥

- `e2e/playwright/alt-frontend-sv/run.sh`——alt-deploy がリリース時に叩く dispatch——が
  Playwright コンテナを `v1.59.1-jammy` に pin していた一方、スイートは
  `@playwright/test@1.62.1` をインストールしていた。ドライバは自分が pin したリビジョンの
  ブラウザバイナリを要求するため、起動しないか実行中に約 400MB を取りに行く。
  タグは package.json から読むようにした。
- `scripts/regen-service-registry.py` が、移行済みの alt-backend に対して
  `e2e/hurl/<name>/` を alt-deploy の SERVICE_PATHS に出力し続けていた。
- `e2e/_lib/reclaim-network-pool.test.sh` の behavioural 半分は、PM-2026-046 Fix 1 が
  `reclaim_network_pool` に `STAGING_PROJECT_NAME` 必須ガードを入れて以来壊れていた
  （テスト側が設定していなかった）。しかもこのファイルは**どのワークフローからも
  呼ばれていなかった**ため誰も気づかなかった。structural 半分は `e2e/hurl/*/run.sh` を
  glob しており、`_lib` の移動でマッチ 0 件になり `nullglob` で黙って通るところだった。
  修正し、0 件スキャンを失敗扱いにし、`check-suites.sh` から呼ぶようにした。

## Deploy-model 整合性セルフチェック

本 ADR は E2E ハーネスと CI ワークフローのみを変更し、production compose
（`compose/compose.yaml` およびその include 群）には触れない。唯一の compose 変更は
`compose.staging.yaml`（ephemeral E2E stack 専用、dispatch ごとに `down -v` される）への
`image:` キー 1 行追加であり、rolling deploy の対象外である。

- [ ] 新設 compose service が `depends_on` で他 service を gate するか？ → **N/A**（新設なし）
- [ ] 新設 compose service に `restart: "no"` の one-shot init container を含むか？ → **N/A**
- [ ] 新設名前付き volume を populate する責務はどこにあるか？ → **N/A**
- [x] いずれも該当しない → **rolling 互換**
