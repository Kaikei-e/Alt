# ADR-000953: alt:events:articles の記事本文をイベントから外し article_id 参照に切り替える

## Status

Accepted

## Date

2026-07-31

## Affected Services

- **alt-backend (Go)** — producer。payload から `content` を外す。前提として `register_feed_usecase` の `ArticleID` 混入バグを修正する
- **search-indexer (Go)** — 唯一の本文 consumer。fat 分岐を削除する
- **mq-hub (Go)** — provider 側 pact generator の修正
- **pre-processor (Go) / tag-generator (Python)** — 実装変更なし。CDC で id-only 依存を固定する

## Context

2026-07-30、`redis-streams` が `maxmemory` 1GB に到達し `XADD` が全拒否された。`alt:events:articles` が
**973 MB / 95,632 entries** を占有していたことが原因である。記事本文 HTML をイベント payload に
埋め込んでいるため、実測で **1 件あたり 17.4 KB** に達する。

同時に、この構成が自己回復できないことも判明した。XADD 時トリムは XADD が成功したときにしか
走らない。`XADD` は denyoom コマンドなので `maxmemory` 到達時点で拒否され、結果としてトリムも
止まる。ストリームは自力で縮まなくなる。この latch 自体は XADD から独立した定期 `XTRIM`
バックストップの導入で別途解消した。本 ADR はその上流、**そもそもなぜ 1 件 17.4 KB なのか**を扱う。

### 埋め込みの出自

fat event は [[000241]] の副産物である。同 ADR は「alt-backend を唯一のデータオーナーにする」ことが
主題で、fat event そのものは決定事項ではなく、変更表の 1 行として現れるだけである。
`docs/services/mq-hub.md` に記録された理由は 1 点のみ:

> Fat Events により search-indexer は alt-backend への API 呼び出しなしでインデックス更新可能

つまり **DB 直アクセスを失った search-indexer の API 往復を省く**、それだけが根拠である。

### サイジング前提の破綻

[[000326]] は `XADD MAXLEN ~` を導入した際、次の見積もりを置いていた:

> デフォルト 10,000 エントリ: … Fat Event (~30KB) x 10,000 = ~300MB であり、1GB の maxmemory に収まる

1 件あたりのサイズ見積もり (~30 KB) はむしろ保守的で、実測 17.4 KB は範囲内だった。破綻したのは
**エントリ数**の前提である。実際には 95,632 件まで伸びた。原因は `Mode: "ACKED"` トリム —
どの consumer group も ack していないエントリは削除されないため、1 つの consumer が滞ると
`MAXLEN 10000` は事実上無効になる。この挙動は ADR に記録されていなかった。

### 調査で判明した決定的な事実

payload の `content` を実際に読んでいる consumer を全 unmarshal 箇所にあたって特定した。

| consumer | `content` を読むか | 実際に使うフィールド |
|---|---|---|
| pre-processor | **読まない**（構造体にフィールドが無い） | `article_id`, `title` |
| search-indexer | **読む**（唯一） | `article_id`, `user_id`, `title`, `content`, `tags`, `published_at` |
| tag-generator | **読まない** | `article_id`, `feed_id`, `title`（ログのみ） |

pre-processor と tag-generator は既に `article_id` で本文を再取得している。tag-generator の
handler には *"The service will fetch content from DB and generate tags"* とコメントまである。
**両者は既に claim-check の consumer であり、使わない 17.4 KB を受け取って捨てているだけ**だった。

さらに、search-indexer の thin 経路は本番コードとして既に存在する。`enqueue` → `flush` →
`ExecuteBatchArticles` → `GetArticleByID` が実装済みで、`ErrArticleNotFound` のスキップまで
書かれている。**取得経路を新規に作る必要はなく、fat 分岐を止めるだけでよい。**

### 参照の意味を制約する事実

`alt-db` の `articles` テーブルには **version / revision / content_hash / updated_at 列が一切無い**。
`created_at` / `published_at` / `deleted_at` のみである。さらに upsert は破壊的で、
`ON CONFLICT DO UPDATE SET content = EXCLUDED.content` に加え「既存 content の方が長ければ
content を更新しない」という長さヒューリスティックを持つ。

したがって **`article_id` 参照は "latest" しか意味できない**。「このイベントを引き起こした
バイト列」を指すことは、現在のスキーマでは不可能である。

### Reproject-safe 不変条件との関係

`docs/wiki/architecture/immutable-data-model.md` は「projector は event payload のみを参照。
latest state クエリ禁止」を掲げる。claim-check は定義上これに反する。ただし:

1. **適用範囲が異なる。** 同文書は knowledge-sovereign の `knowledge_events` を対象とする。
   `alt:events:articles` は `MAXLEN 10000` の一時作業キューであり、生涯 8,216,253 件が
   すべてトリム済みで、そもそも今日時点で reproject 不可能である
2. **ただし精神は該当する。** search-indexer の Meilisearch index は disposable な read model であり、
   claim-check 後はその内容が「いつ fetch したか」の関数になる

なお、この問題に対するプロジェクト自身の解答は既に存在する。summary と tag は
`summary_versions` / `tag_set_versions` を経由し直接上書きしない。**`articles.content` だけが
versioned でない**という非対称がある。

### 外部文献の位置づけ

Azure Architecture Center の claim-check は、適用条件として *"large messages are straining the
messaging system and degrading system performance"* を挙げており、本件と一致する。同時に
*"Implement the pattern conditionally"*（サイズ閾値で分岐）を推奨する。

一方、**文献はこの設計で最も難しい 3 点に答えていない**: replay 時に参照先が消えていた場合の扱い、
参照の version 固定、fat から thin への移行手順。Confluent が触れるのは「外部ストアは独立した
expiry が必要」の 1 点のみである。ここは Alt が明示的に決めるべき領域である。

## Decision

**`alt:events:articles` の payload から `content` と `tags` を外し、`article_id` による参照に
切り替える。参照は "latest" 解決とし、content_hash 等による version 固定は行わない。**

`published_at` はイベントに残す。ただし**それだけでは劣化を防げない**（後述の「published_at の
訂正」を参照）。

### 参照を version 固定しない理由

point-in-time 固定を必要とする consumer が**存在しない**ため。唯一の本文 consumer である
search-indexer は Meilisearch の upsert-by-PK でインデックスを更新しており、検索インデックスは
本来「現在の記事内容」を反映すべきものである。「イベント発生時点のバイト列」を要求する
consumer が現れて初めて、`content_hash` 列の追加と両 upsert driver の変更というコストを
払う価値が生じる。今払うのは投機である。

**ただしこれは semantics の変更である。** 今日 `ArticleUpdated` はそれを引き起こした正確な
バイト列を運ぶ。変更後、後から dereference した consumer が得るのは「その時点の行の内容」であり、
長さヒューリスティックによっては**より古いが長い本文**でありうる。この性質の喪失を明記する。

### 検討した代替案

**案 A: 現状維持 + `MAXLEN` を下げる。** 却下。17.4 KB × N の N を削るだけで、1 件あたりのコストは
変わらない。consumer のラグ耐性（再配信のために保持できる件数）を犠牲にして memory を買う
取引になり、本質的な非対称——3 consumer 中 2 つが使わないデータを全員に配っている——を残す。

**案 B: `content_hash` を追加して version 固定する。** 却下（ただし将来の拡張として保持）。
`articles` への migration と `create_article_driver` / `save_article_driver` 両方の変更が必要で、
**それを必要とする consumer が現時点で存在しない**。プロジェクトの
`summary_versions` / `tag_set_versions` と同じ идиom で後から追加できるため、必要になった時点で
別 ADR とする。

**案 C: サイズ閾値による条件付き適用**（Azure 推奨）。却下。小さい記事だけ本文を同梱すると、
consumer は「content があるかもしれないし無いかもしれない」両分岐を恒久的に保持することになる。
今回はまさにその両分岐（fat/thin）が既に存在し、fat 側だけが使われて thin 側が忘れられた結果、
`ExecuteBatchArticles` が死んだコードとして残っていた。**分岐を 1 本に畳むことが目的**なので、
閾値分岐はそれに逆行する。

**案 D: 本文を Redis の別キーに置いて TTL 管理する**（典型的な claim-check）。却下。記事本文は
`alt-db` に system of record として既に存在する。第 2 の保管先を作れば Confluent が指摘する
「外部ストアの独立した expiry」問題を自ら招き入れることになる。**参照先が既にあるのだから、
それを使う。**

### 前提条件（先行して修正する）

`register_feed_usecase` の producer 経路は `ArticleCreatedEvent.ArticleID` に、実際には
`feeds.id` を入れている。`FeedRegistrationResult.ArticleID` というフィールド名が
`INSERT INTO feeds ... RETURNING id` の戻り値を保持しているためである。現状は本文が
同梱されているため consumer が dereference せず露見しないが、**claim-check 後は確実に
参照解決の失敗になる。** 本 ADR の実装より先に修正する。

### 移行手順（expand-contract）

各段階で Pact CDC を先に RED にする（CLAUDE.md ルール 7）。

1. **前提**: `register_feed_usecase` の `ArticleID` 修正
2. **expand**: search-indexer が thin payload を扱えることを CDC で固定する。producer は
   まだ `content` を送る（consumer は fat 分岐を優先したまま）
3. **switch**: search-indexer の fat 分岐を削除し、常に fetch 経路を通す。この時点で
   producer 側の `content` は無視される
4. **contract**: producer から `content` / `tags` を削除。mq-hub の provider pact generator も
   同時に更新する

段階 3 と 4 を分けるのは、consumer が本当に fetch 経路で動くことを本番で確認してから
producer を変えるためである。「誰も使っていないから消す」で壊すのがこの種の変更の典型的な
失敗であり、実際 pre-processor には `alt:events:articles` の CDC 契約が 1 つも無い——
「使っていない」という前提が契約で守られていない状態にある。

### published_at の訂正（実装中に判明）

本 ADR は当初「`published_at` をイベントに残せば精度劣化を回避できる」と書いたが、**これは誤りだった。**

段階 3 の実装で判明した事実: `payload.PublishedAt` を読んでいたのは fat 分岐**だけ**である。
thin 経路は article id をバッファし、`ExecuteBatchArticles` が `GetArticleByID` の戻り値のみから
document を組み立てる。したがってイベントにフィールドを残しても**誰も読まない**。

結果として、段階 3 の後は全 `ArticleCreated` / `ArticleUpdated` が
`PublishedAt = created_at` になる。今日 fat 経路を通っている母集団（＝ほぼ全件）にとって
これは劣化であり、`SearchWithDateFilter` と Acolyte の weekly_briefing 窓に影響する。

根本原因は `proto/services/backend/v1/internal.proto` の `ArticleWithTags` に `published_at` が
無いことである。`articles.published_at` は DB に存在するのに proto が露出していない。
`search-indexer/app/driver/backend_api/client.go` はそれを承知で `CreatedAt` を代入している。

**段階 3 は、この劣化を解消するまで本番投入しない。** 対処は次のいずれか:

- **(推奨) proto に `published_at` を追加する** — DB にある値を露出していないことが defect であり、
  `GetArticleByID` を使う全 consumer が恩恵を受ける。サービス境界を越えるため CDC を先行させる
- search-indexer 内で `bufferedArticle` にパース済み timestamp を持たせて document 生成時に上書きする —
  proto を触らないが、proto の欠落という本当の問題は残る

### スコープ

**対象は `alt:events:articles` のみ。**

`alt:events:tags` も `content` を埋め込む（実測 ~13.6 KB/件）が、**明示的に対象外とする。**
こちらは同期 request-reply であり、caller が既に本文を保持している。claim-check にすると
tag-generator にレイテンシクリティカルな経路での fetch を強いることになる（cold-miss の
タグ表示は最悪 120 秒との測定がある）。size と latency のトレードオフが articles とは
逆向きであり、同じ判断を機械的に適用してはならない。

DLQ (`alt:events:articles:dlq`) は payload を verbatim コピーするため、本 ADR の効果を自動的に
受け継ぐ。ただし 3 つの writer いずれも `MAXLEN` を設定しておらず、これは別途対処を要する。

## Consequences

### Pros

- **1 件あたり 17.4 KB → 数百バイト規模**になる。`MAXLEN 10000` での定常メモリは実測 174 MB から
  1 桁以上小さくなり、`maxmemory` 到達が現実的な脅威でなくなる
- **entry あたりのサイズが `stream-node-max-bytes` (既定 4096) を下回る**ため、macro node に複数
  エントリが詰まるようになる。現在は 1 entry あたりほぼ 1 node（radix-tree-keys が length の
  ~0.78 倍）で、`~` 近似トリムが本来持つ「node 単位でまとめて解放する」効率を失っている
- **使わないデータを配らなくなる。** 3 consumer 中 2 つは 17.4 KB を unmarshal して捨てていた
- **死んだコードが生き返る。** `ExecuteBatchArticles` は書かれたまま使われていなかった。
  [[000241]] 以前の設計意図がここに残っていた
- **DLQ が自動的に縮む**（payload の verbatim コピーであるため）
- consumer が producer の payload 設計に暗黙依存する面積が減り、将来 consumer が増減しても
  payload を触らずに済む

### Cons / Tradeoffs

- **point-in-time の忠実性を失う。** イベントは「何が起きたか」を運ぶが「その時どうだったか」は
  運ばなくなる。`articles` に version 列が無く upsert が破壊的（かつ長さヒューリスティック付き）
  である以上、dereference 結果が event 時点と異なりうる。これを必要とする consumer が現れたら
  `content_hash` 導入（案 B）に進む
- **producer 可用性への結合が生まれる。** thin event の一般的な代償で、alt-backend が落ちていると
  search-indexer は本文を取得できない。現状の fat event は「alt-backend が落ちていても
  インデックスできる」性質を持っており、それを捨てる
- **fetch が 1 記事 1 RPC になる。** `ExecuteBatchArticles` は Meilisearch への書き込みが batch
  なだけで、取得は id ごとのループである。イベント流量に対して RPC 数が線形に増える。
  measurement を取ってから必要なら batch 取得を足す
- **`published_at` の精度**: `GetArticleByID` が返す proto には `published_at` が無く、
  `created_at` で代用されている。イベントに `published_at` を残すことで回避するが、
  「イベントに残すフィールド」と「fetch で取るフィールド」の境界が生まれる
- **参照解決の失敗が無言のインデックス欠落になる。** `ExecuteBatchArticles` は
  `ErrArticleNotFound` をスキップ扱いにするため、`IndexedCount: 0` かつ `err == nil` で flush が
  「成功」し、メッセージは ACK され再配信も DLQ も起きない。fat event 時代は payload だけで
  index できたので、この失敗モード自体が存在しなかった。transport / backend エラーは
  `RepositoryError` として ACK されず XAUTOCLAIM で回収されるので、reclaim 規律は保たれている。
  **参照解決失敗を無言スキップのままにするか DLQ に送るかは、別途決める必要がある**（Alt の
  サイレントフォールバック禁止の観点では後者が筋）
- **`alt:events:tags` の 13.6 KB/件が残る。** 意図的な先送りであり、負債として認識しておく
- **pre-processor / tag-generator の「本文を使っていない」性質が契約で守られていない。**
  CDC を追加するが、それ自体が本 ADR で増える作業である

payload 形状の変更のみであり、per-service rolling deploy と整合する。ただし移行段階の順序
