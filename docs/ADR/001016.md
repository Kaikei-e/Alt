# ADR-001016: summary_ready の Web Push を、持ち主が自分で頼んだ要約の完了に限って送る

## Status

Accepted

## Date

2026-11-18

## Affected Services

- pre-processor — `summarize_job_queue` への起点列追加、`CreateJob` 引数への起点必須化、完了時の通知送出分岐
- alt-backend — 要約キュー投入経路からの起点明示、契約テスト更新
- proto — サービス間契約で起点を渡す場合の RPC スキーマ更新
- pre-processor-migration-atlas — `summarize_job_queue` に `origin` 列を追加するマイグレーション

## Context

[[001015]] の R0（計測と止血）として、読書体験を損ねている過剰な通知を止める必要がある。2026-11-17 時点の本番データを読み取り専用で計測した結果は次のとおりである。

- `push_deliveries` の `summary_ready` は累計 30,220 件、直近 30 日で 9,224 件、直近 7 日で 1,888 件である。
- 週次件数は 2026-10-26 の週が 1,168 件、11-02 の週が 2,126 件、11-09 の週が 3,472 件である。
- 購読は 2 端末ある。1 台は常に成功（HTTP 201）し、もう 1 台は Apple の push サービス宛てで常に HTTP 400 `BadWebPushTopic` で失敗している。
- 同じ時期に、持ち主が画面から要約を頼んだ回数は 15 日で 10 回である。通知のほぼすべては、収集した記事を裏で要約したジョブの完了通知である。

現状の実装を確かめた結果、原因は要約ジョブに発生源の区別がないことにある。

- `alt-backend/app/domain/push.go` の通知種別は `summary_ready`、`acolyte_report_ready`、`recap_ready`、`today_entrance_ready` の 4 つである。
- `pre-processor/app/service/summarize_queue_worker.go` は、キューから取得したジョブが成功すると、発生源を問わず `jobRepo.CompleteJobWithNotification` を呼ぶ。
- `pre-processor/app/repository/summarize_job_repository.go` の `CompleteJobWithNotification` は、`summarize_job_queue` を完了に更新する同一トランザクションで `notification_outbox`（`pre-processor-db`）に `summary_ready`（payload は `{"kind":"summary_ready","url":"/articles/<article_id>"}`）を挿入する。その後 `pre-processor/app/service/notification_relay.go` が `alt-data-hub`（`alt-backend/app/dataplane/connect/datahubapi/push_handler.go`）へ転送し、`alt-backend/app/shared/driver/alt_db/push_delivery_driver.go` が `push_deliveries` へ展開する。
- 要約ジョブ表は `summarize_job_queue` であり、マイグレーションは `pre-processor-migration-atlas/migrations/`（初期定義は `20260215000001_initial.sql`）にある。現状、このテーブル（`pre-processor/app/domain/job.go`）にも `SummarizeJobRepository.CreateJob`（`pre-processor/app/repository/interfaces.go`）にも起点を区別する列や引数がない。
- `CreateJob` の呼び出し元は本番コードに 4 か所ある。
  1. `pre-processor/app/service/summarize_queue_worker.go`（`EnqueueUnsummarizedBatch`）: `pre-processor/app/handler/job_handler.go` の 5 分定期処理とキュー空時の補充（[[001006]]）から呼ばれる裏の処理である。
  2. `pre-processor/app/consumer/summarize_adapter.go`（`SummarizeServiceAdapter.SummarizeArticle`）: `pre-processor/app/consumer/event_handler.go` が `alt:events:articles` から `ArticleCreated`（記事収集時の裏の処理）と `SummarizeRequested` を受けて呼ぶ。`SummarizeRequested` は現状本番の送信元がなく、payload にも起点の項目がない。
  3. `pre-processor/app/handler/summarize_handler.go`（`HandleSummarizeQueue`、`POST /api/v1/summarize/queue`）: `alt-backend` の `POST /v1/feeds/summarize/queue`（認証・クォータ付き）から呼ばれる持ち主起点の経路である。なお現行の `alt-frontend-sv` は同期ストリーミングの `StreamSummarize` を使っており、この経路は呼んでいない。
  4. `pre-processor/app/connect/v2/preprocessor/handler.go`（`Handler.QueueSummarize`、Connect-RPC `PreProcessorService/QueueSummarize`）: 現状は `alt-backend/app/orchestrator/driver/preprocessor_connect/client.go` と Pact 契約テストがあるのみで本番呼び出し元はない。同 RPC は `pre-processor/app/connect/v2/server.go` で mTLS の許可ピア（`alt-backend`）のみを検査し、`proto/services/preprocessor/v2/preprocessor.proto` の `QueueSummarizeRequest` にも起点や利用者を表す項目がない。したがって、`connect/v2/preprocessor/handler.go` の呼び出しは持ち主の操作だけから来るとは構造的に保証できない。

## Decision

1. **要約ジョブに起点（`origin`）を持たせる。** `summarize_job_queue` テーブルに `origin` 列（値は `user` と `system` の 2 値、`CHECK` 制約付き）を新設する。`pre-processor-migration-atlas/migrations/` のマイグレーションで追加し、既存の行は `system` とする。理由は、完了時に通知を送るべきかをジョブ自身の状態から一意に判定するためである。
2. **`summary_ready` は起点が `user` のジョブが完了したときだけ送る。** `SummarizeQueueWorker` は完了時にジョブの `origin` を参照し、`user` のときだけ `CompleteJobWithNotification` で `notification_outbox` に `summary_ready` を挿入する。`system` のときは `UpdateJobStatus` 相当で完了だけを記録し、通知を送らない。理由は、裏の要約ジョブによる通知を止めて持ち主の読書体験を守るためである。
3. **起点はジョブを作る呼び出し元が明示して渡す。** `CreateJob` とこれにつながる内部 RPC・イベント契約に `origin`（`user` または `system`）の明示指定を必須として追加する。呼び出し経路や認証ヘッダからの推測は行わない。`origin` の指定がない呼び出し（空値や未定義値を含む）はコンパイルエラーまたは入力検証エラーにし、黙って既定値を当てない。理由は、既定値があると新しい呼び出し元が増えたときに通知が再びあふれるためである。
4. **通知種別と購読設定は変えない。** 4 つの通知種別と `push_subscriptions` の設定列はそのまま維持する。Apple の push サービス宛ての HTTP 400 `BadWebPushTopic` 失敗は本 ADR では扱わない。理由は、主端末は Android の Chrome であり、Apple 宛ての失敗は原因が別であるためである。
5. **サービス間の契約が変わる場合は Pact の失敗テストを先に置く。** `QueueSummarizeRequest` や `SummarizeRequested` などサービス間の契約に `origin` を追加する場合は、producer の配線より先に consumer 側の Pact 失敗テストを置く。理由は、契約変更の抜け漏れを配線前に検出するためである。

### 検討した代替案

- **(a) `summary_ready` という通知種別をなくす**: 退けた。持ち主が自分で頼んだ要約の完了は知らせる価値があり、必要なのは全廃ではなく送る条件の修正であるためである。
- **(b) 通知を送る側で件数を制限する**: 退けた。件数制限では裏の要約による意味のない通知が残り、持ち主が自分で頼んだ要約の通知まで制限に巻き込まれるためである。
- **(c) 既定で通知を切る**: 退けた。問題は初期設定ではなく通知を送る条件の誤りであり、設定を切っても `notification_outbox` と `push_deliveries` への不要な記録は止まらないためである。

## Consequences

### Pros

- 裏の要約ジョブによる `summary_ready` の大量送信が止まり、Android 端末の通知騒音と `push_deliveries` の肥大化を防げる。
- `origin` に既定値を置かないため、将来の呼び出し元追加時に通知の要否を強制的に判断できる。
- 既存の通知種別・購読設定・同期ストリーミング要約（`StreamSummarize`）を壊さずに止血できる。

### Cons / Tradeoffs

- `system` のジョブが `pending` または `running` の記事に対して後から `user` が要約を頼んだ場合、既存の重複抑止でスキップするか `user` へ昇格させるかは本 ADR では決めていない。
- `CompleteJobWithNotification` は通知先の `userID` を要求するため、`QueueSummarize` や `SummarizeRequested` で `user` 起点を渡す際の `userID` 受け渡しと検証規則は実装時に詰める必要がある。
- Apple の push サービス宛ての HTTP 400 `BadWebPushTopic` 失敗は未解決のまま残る。
- 現行の `alt-frontend-sv` は `StreamSummarize` を使っているため、非同期キューと `summary_ready` 通知を実際の読書導線で使うかはリーダー統合（[[001019]]）で扱う。
