# ADR-001008: Tag Verse のトピック色分けを共起グラフ上の決定的な Leiden クラスタリングで決め、トピック別インクと共起の細線で描く

## Status

Accepted

## Date

2026-11-12

## Affected Services

- alt-frontend-sv: Tag Verse のシーン（トピック別インク、共起の細線、フォーカスと文脈、ラベルの階層、カメラ挙動、背景の塗り）
- alt-backend: `FetchTagCloudUsecase` のエッジ計算とクラスタリング、`FetchTagCloud` RPC の応答
- alt-data-hub: タグ共起を返す SQL（`FetchTagCooccurrences`）
- alt-butterfly-facade: `FetchTagCloud` の BFF → alt-backend 契約（Pact）

## Context

[[001007]] で Tag Verse を Alt-Paper の WebGL シーンに作り直した。軽くはなったが、本番で次の 3 つの問題が出た。

1. **情報が乏しい。** ノードの色は記事数の 5 段階だけで（[[000362]] のしきい値）、どのタグが同じ話題に属するかが画面から読み取れなかった。
2. **キャンバスが黒い。** `scene.background` と `Fog` をリアクティブな `<T.Color attach>` / `<T.Fog attach>` で与えていたところ、本番ではキャンバスが黒く描かれた。レンダラは `alpha: true` で作られるので、背景が欠けただけなら黒ではなく透明になるはずで、コードを読んでも真因は特定できなかった。
3. **カメラが急に動く。** タグを選ぶたびにカメラが `max(node.radius * 8, R * 0.35)` まで寄るため、画面がガクッと動いた。

1 への対応（PR #308）では、トピックを API で返すようにした。`TagCloudItem.cluster_id` と `FetchTagCloudResponse.edges` を追加し、エッジは Ochiai 係数、クラスタは重み付きラベル伝播で求めた。ところが実データでは、ラベル伝播がほとんどの頻出タグを 1 つのコミュニティにまとめてしまった。code / data / agent / model / api / security など、どの話題とも一緒に出る汎用タグが原因で、いわゆる monster community である。

上位 300 タグの実データでオフライン評価した結果は次のとおり。

- **現行方式（ラベル伝播 + 生の共起数による打ち切り）**: 最大コミュニティが色付き 226 タグ中 118 タグを占め、色が付くタグは 75% にとどまった。
- **共起 SQL の欠陥**: 共起 SQL は `feed_tags` の行 ID で組を作っていた。`feed_tags` はフィードごとに行を持つため、同じタグ名の組が両方向で返り、タグが自分自身と組になる行も混ざっていた。評価時点では 37,155 行のうち、異なる組は 21,989 件だった。両方向に現れる組が 15,166 件、自己ペアが 296 件あった。
- **打ち切りの偏り**: 上位 2,000 組を生の `shared_count` 順で切るので、汎用タグを含む組が枠を占め、規模の小さい話題の内側の組が落ちていた。

## Decision

タグ共起グラフを API で返し、トピックは共起グラフ上の決定的な Leiden クラスタリングで決める。そのうえで、トピック別のインクと共起の細線で描く。`cluster_id` の意味は変えない（0 はトピックなし、1..8 は総記事数の多い順）。

### API と契約（PR #308）

- `TagCloudItem.cluster_id = 6` と、`TagCloudEdge { source_index, target_index, weight }`（`FetchTagCloudResponse.edges = 3`）を追加する。どちらも追加のみで、後方互換を保つ。
- エッジは Ochiai 係数 `c / sqrt(n_a * n_b)` で求める。各タグの上位 3 相手に絞り、重複を除いて最大 600 本とし、最も強い辺を 1 として正規化する（weight は (0, 1]）。同点はタグの順位で決める。
- エッジとクラスタは、レイアウト（[[000351]]）と同じくキャッシュを埋めるときに 1 回だけ計算する。キャッシュは [[001007]] の stale-while-revalidate を使う。
- BFF → alt-backend の Pact には `FetchTagCloud` の interaction を producer 変更の前に追加した（RED 先行）。ゼロ値は protojson が省略するので、契約では常に存在するフィールドだけを固定する（`tagName`、`articleCount`、`edges[].targetIndex`、`edges[].weight`）。

### クラスタリング（PR #310）

- **アルゴリズム**: Reichardt–Bornholdt 型の configuration modularity を最大化する Leiden を、パッケージ内で実装する。局所移動、well-connected を保証する refinement、集約の 3 段からなる。得られた分割から、どの単一ノードの移動も品質を上げなくなるまで、回数を限って繰り返す。
- **決定性**: 入力の並び順によらず同じ結果を返す。同点はタグの固定順位で決め、map の走査結果は必ずソートしてから使う。キャッシュを作り直しても色が入れ替わらないようにするためである。300 タグで約 0.7 ms。
- **重みと解像度**: 重みはエッジと同じ Ochiai 係数を使い、解像度は γ = 2.0 とする。4 タグ未満のコミュニティは 0、残りは総記事数の上位 8 つを 1..8 とする。

### 共起 SQL（PR #310、alt-data-hub で実行）

- 組はタグ名単位で作る（`tt1.tag_name < tt2.tag_name`）。同じ名前が複数の `feed_tags` 行にあっても `COUNT(DISTINCT article_id)` で 1 つにまとめ、自己ペアは作らない。
- 2,000 組の打ち切りは Ochiai 降順とし、同点は `shared_count`、`tag_a`、`tag_b` の順で決める。タグごとの記事数は、tag cloud と同じ数え方で SQL の中で求める。`HAVING >= 2` は維持する。
- `GetTagCooccurrences` の応答の形は変えない。testcontainers を使う `-tags integration` のテストで、名前の重複のマージ、自己ペアの除外、組の向き、Ochiai 順を確認する。

### γ の決め方

上の実データ（新しい SQL と同じく組をマージしたもの）で、重みと γ を振って比べた。

| 設定 | 最大コミュニティ | 色が付くタグ |
|---|---|---|
| ラベル伝播 + 生の共起数による打ち切り（現行） | 118 / 226 | 75% |
| Leiden + Ochiai 打ち切り、γ 1.0〜1.25 | 約 120 / 283 | 約 94% |
| **Leiden + Ochiai 打ち切り、γ 2.0（採用）** | **85 / 272** | **91%** |

γ 2.0 では、「Web・データ・API・サーバー」の塊が「AI エージェント」の塊から分かれ、日本語の技術タグも「開発」と「インフラ・セキュリティ」に分かれる。γ をさらに上げると灰色のタグが急に増える（γ 2.25 で 43、γ 3.0 で 87）。どの γ でも、上位タグのおよそ半分は「AI コーディングエージェント」のトピックに入る。これは記事コーパスそのものの偏りである。

### シーン（PR #308、alt-frontend-sv）

- **背景**: 背景色、霧の色、クリアカラー（`renderer.setClearColor(paper, 1)`）を、パレットから命令的に設定する（`paintPaper`）。黒背景の真因が未確定なので、どの経路でも紙色になるようにした。
- **カメラ**: キャンバスでタグをクリックしてもカメラは動かさない。インデックスから選んだ場合だけ、ノードが隠れているか中心から外れているときに注視点を平行移動する。距離は変えず、移動先は詳細パネルに覆われない領域の中央とし、約 900 ms で移動する。`prefers-reduced-motion` のときは即座に切り替える。詳細パネルはキャンバスの上に重ね、キャンバスの幅は変えない。
- **インク**: トピックごとに 8 色の印刷インクを割り当てる（indigo、oxblood、forest、ochre、plum、teal、sienna、slate）。小さいタグほど淡くするが、どの色も紙色に対して 3:1 以上を保つ。陰影は Lambert で、ライト強度に π を掛けて正面光の面がインク色そのものになるようにする。
- **共起の細線**: 1 本の `LineSegments` に線形 RGBA の頂点色を持たせる。同じトピック内の線はそのトピックのインク、トピックをまたぐ線は中立色にする。
- **フォーカスと文脈**: タグを選択またはホバーしたとき、あるいは Topics key でトピックにフォーカスしたとき、近傍やそのトピックは濃いまま残し、それ以外を薄くする。更新は変化したインスタンスと alpha だけに絞る。
- **ラベル**: 上位 12 タグは Playfair Display、それ以外は Source Sans 3 で描く。クラスタの重心にトピック名を置き、紙の地紋を重ね、キーボードで操作できる Topics key とインデックスの色見本を付ける。

### 検討して却下した案

- **ラベル伝播のまま閾値や反復回数を調整する**: 帰無モデルを持たない手法なので、汎用タグがまとめて一色になる性質は変わらない。
- **association strength で重み付けする**（van Eck & Waltman 2009、VOSviewer の正規化）: 偶然の共起を補正する指標で、合成データでは差が出た。しかし実データでは Ochiai と区別できる差が出なかったので、エッジと同じ重み 1 本にまとめた。
- **γ 1.0〜1.25**: 最大コミュニティが約 120 タグのまま残り、本番の 118 から実質的に縮まない。
- **ハブらしいタグ（participation coefficient の高いタグ）を 0 にする、またはクラスタを凝集度順に並べる**: 前者は最大級のタグがすべて灰色になる。後者は「1..8 は総記事数の多い順」という `cluster_id` の意味を変えてしまう。
- **生の `shared_count` による打ち切りのままにする**: 汎用タグの組が枠を占め、話題の内側の組が落ちる。Leiden に変えても最大コミュニティは 134 タグのままだった。
- **既製のグラフライブラリを使う**: 依存が増え、ライセンス方針（[[000988]]）の確認も要る。300 ノード規模なら、パッケージ内で実装すれば十分に速い。
- **WebGL を実際にマウントするコンポーネントテストで背景を固定する**: CI のブラウザでイベントループが止まり、テストスイートが 20 分の上限に達した。背景の設定は `paintPaper` に切り出し、単体テストで固定する。

## Consequences

### Pros

- 本番の 300 タグで、色が付くタグが 75% から 91% に増える。最大コミュニティは色付き 226 タグ中 118 タグから、272 タグ中 85 タグに縮む。トピックの色と細線から、どのタグが同じ話題に属するかを読み取れる。
- クラスタは決定的で入力の並びに依存しないので、キャッシュの再計算で色が入れ替わらない。
- 共起 SQL がタグ名単位の組を返すようになり、両方向の重複行と自己ペアがなくなった。エッジ（細線）の入力も正しくなった。
- タグを選んでもカメラが急に動かない。

### Cons / Tradeoffs

- γ 2.0 はグラフの規模に依存する。Tag Verse の limit≈300 を前提にした値で、30〜50 タグに絞って呼ぶと、上位のタグが 4 タグ未満のコミュニティに入って灰色になる。今のところクラスタを使う呼び出しは Tag Verse だけである。
- タグが少ない単独のグラフ（孤立したクリークだけなど）は、γ > 1 のもとでは単一ノードに分割され、すべて灰色になる。テストではこれを既知の挙動として記録している。
- どの設定でも、上位タグのおよそ半分は 1 つのトピック（AI コーディングエージェント）に入る。コーパスの偏りなので、色だけでは解消しない。
- 保存済みのノイズタグ（like、time、https など）も 1 つのトピックの一部になっている。tag-generator 側の対処（[[001009]]）は新しいタグにしか効かないため、既存データの是正方法は別途決める必要がある。
- 黒背景の真因は特定していない。命令的に塗ることで回避している。
- 共起 SQL はタグごとの記事数の集計を 1 段追加した。`(feed_tag_id, article_id)` の索引を線形に走査するだけで、組の生成は `at1.feed_tag_id <> at2.feed_tag_id` で早めに絞っている。
