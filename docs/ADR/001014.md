# ADR-001014: 要約ジョブを二度と作らない記事に、版を作らない placeholder 要約を保存して未要約の一覧から外す

## Status

Accepted

## Date

2026-11-15

## Affected Services

- pre-processor（enqueue sweep が終端の記事に placeholder 要約を保存する。placeholder 文面の定義を 1 か所に集約する。要約保存の要求に「版を作らない」指定を載せる）

## Context

[[001013]] は、未要約記事の enqueue sweep が、ガードで恒久的に弾かれる記事にページの枠を使い切られる問題を、1 回の sweep で複数ページ進めることで緩和した。ただし弾かれる記事そのものは未要約の一覧に残り続ける。sweep は 5 分ごとに全件を読み直しており、件数が sweep のページ上限を超えれば同じ遅延が再発する。[[001013]] はこれを未解決の負債として記録していた。

恒久的に弾かれる理由は 2 つある。

- dead-letter 済み: モデルが処理できない本文で、リトライを使い切ったジョブがある
- 再要約の上限到達: 品質チェックで要約を消されることを繰り返し、再要約の回数上限を超えた

どちらの記事も `article_summaries` に行を持たない。上流の「未要約記事」は「要約の行を持たない記事」として定義されているので、要約ジョブを二度と作らない記事が、候補として永久に返り続ける。

本文が短すぎる・長すぎる記事については、[[000551]] が placeholder 要約を保存して候補から外す方式を既に採用している。同じ方式を上記 2 つにも広げるのが自然だが、要約保存の既定の動作をそのまま使うと次の副作用がある。

- 要約の版が 1 つ作られ、要約完了のイベントが追記される
- Knowledge Home の投影はそのイベントを「要約が完成した」ものとして扱い、項目のスコアを上げ、placeholder の文面を抜粋として表示する
- イベントログは追記専用なので、一度書いたものは取り消せない

対象は長期間にわたって溜まった古い記事であり、これらを一斉に「要約完了」として Home に浮上させるのは誤った表示になる。

また、placeholder の文面は 3 か所に同じ文字列として複製され、手で一致させていた。品質チェッカーは既知の placeholder を評価対象から外すが（[[000251]]）、文面が 1 つでも除外の一覧から漏れると、品質チェッカーが placeholder を消し、sweep が保存し直すという繰り返しが止まらなくなる。

## Decision

**enqueue sweep が、ガードの恒久的な理由（dead-letter 済み、再要約の上限到達）で弾かれた記事に出会ったとき、その記事に placeholder 要約を「版を作らない」指定で保存する方式を採用する。**

- 書き手は sweep の 1 か所だけとする。終端に達した瞬間（ジョブが dead-letter になる処理、品質チェックの削除処理）には書かない。次の sweep が拾うので遅れは 1 周期以内に収まり、既に終端になっている記事も同じ経路で解消される。本番データを手で直す作業は要らない
- 保存には、要約保存 RPC に既にある「`article_summaries` の行だけを書き、版もイベントも作らない」指定を使う。placeholder は要約という成果物ではないので、版管理にもイベントログにも載せない
- 保存するのは記事 ID、所有者、タイトル、placeholder 文面だけで、sweep が取得したページの情報から作る。追加の RPC は発行しない
- 保存に失敗したら ERROR ログを出し、その sweep のエラー件数に数えて処理を続ける。記事は一覧に残るので、次の sweep が再試行する
- ジョブは作らない。ジョブ表にも触れない。利用者への要約完了通知も出さない
- placeholder 文面は理由ごとに分ける（モデルが処理できなかった、品質基準を満たす要約を生成できなかった）
- placeholder 文面の定義と「placeholder かどうか」の判定を 1 か所に集約し、保存する側と品質チェッカーが同じ定義を参照する
- ガードが返す 2 つの理由は定数にし、ガードと sweep が同じ定数を使う
- sweep の集計ログに、その回に保存した placeholder の件数を載せる
- pre-processor が「版を作らない」指定を送るのはこれが初めてなので、consumer 側の契約テストにその要求を追加する。provider 側はこの指定を既に実装している
- [[000551]] が定めた、本文が短すぎる・長すぎる場合の placeholder の保存（版を作る既定の動作）は変えない

### 検討した代替案

- **候補の一覧を返す側に終端の印を持たせ、一覧のクエリで除外する**: 版もイベントも placeholder の行も作らず、モデルとして最も素直。しかしスキーマのマイグレーション、新しい RPC、サービス間の呼び出し許可の追加、契約テスト、2 サービスの同時デプロイが要る。「未要約の件数」を数える他のクエリも揃えないと数字が食い違う。効果に対して変更範囲が大きい
- **placeholder を既定の動作（版を作る）で保存する**: [[000551]] と完全に同じ扱いで実装は最小。上記のとおり、溜まった古い記事を一斉に「要約完了」として Home に浮上させ、取り消せないイベントを残すため採らない
- **回数上限に達したら、最後の要約を消さずに残す**: 利用者は placeholder ではなく何らかの要約を読める。しかし品質チェックで基準未満と判定された要約を表示することになり、品質の基準そのものを変える判断になる。既に要約を消された記事にはもう一度要約を作り直す必要もある
- **終端に達した瞬間にも placeholder を書く**: 候補から外れるのが最大 1 周期早くなるだけで、書き手が 3 か所に増える。品質チェックの経路では所有者を得るための追加 RPC も要る

## Consequences

### Pros

- 要約ジョブを二度と作らない記事が未要約の一覧から消える。sweep のスキャン量は、処理待ちの記事の数だけで決まるようになる
- [[001013]] のページ上限に、終端の記事が溜まることで近づくことがなくなる
- 版もイベントも作らないので、Knowledge Home の表示やスコアは変わらない。投影を作り直しても結果は同じになる
- placeholder の行を消せば、その記事は未要約の一覧に戻る。判断を誤っていた場合に元へ戻せる
- placeholder 文面の定義が 1 か所になり、保存する側と品質チェッカーの一覧が食い違う余地がなくなった
- 画面からの明示的な要約の再実行は、placeholder があっても従来どおり動く

### Cons / Tradeoffs

- placeholder は統計上「要約済み」に数えられる（[[000551]] から引き継ぐ負債）。「要約できなかった記事」は独立した区分として見えない
- 記事の詳細画面は、要約として placeholder の文面を表示する。要約の再実行は最初の操作で保存済みの placeholder を返すため、作り直すにはもう一度操作が要る（[[000551]] の placeholder と同じ挙動）
- Knowledge Home の項目は、これらの記事について以前の状態のまま残る。品質チェックで要約を消してもイベントは出ないため、消された要約の抜粋が Home に残っている記事がある。この不整合は本 ADR の前からあり、今回は直していない
- placeholder の種類によって版の扱いが分かれた。本文が短すぎる・長すぎる場合は版とイベントを作り、今回の 2 種は作らない。揃えるなら [[000551]] の決定を改める必要がある
- 再要約の回数上限は「完了済みで要約本文が空になったジョブの行」を数えている。運用上の整理で要約本文を一括で空にした行も同じ形になるため、品質チェックで却下された回数より多く数えられる記事がありうる。その記事には今回、品質理由の placeholder が保存される
- ガードの判定と placeholder の保存のあいだに、利用者が画面から要約を作り終えた場合、保存は同じ行への上書きなので placeholder がその要約を上書きする。ごく短い時間窓だが排除していない
- 品質チェックが何度も却下する記事がなぜ生じるのか（判定基準が厳しすぎるのか、特定の媒体の本文に問題があるのか）は調べていない。placeholder はその結果を固定するだけである
