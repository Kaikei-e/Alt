# ADR-000974: FSRS を明示4択の recall_reviewed イベントで駆動し、期日到来を recall_echo_ready とバッジで配送する

## Status

Proposed

本 ADR は [[000970]] を完全置換する。[[000970]] の Decision（特に Loop `dismiss_state` 依存・mutable memory 単独所有）は実装根拠にしない。

## Date

2026-08-11

## Affected Services

- knowledge-sovereign (Go) — review event / FSRS projection / 期日件数 RPC
- alt-backend (Go) — ReviewRecallCandidate / push kind / proto
- alt-harvester (Go) — recall_echo_notifier
- alt-data-hub (Go) — preference 列・fan-out CASE・datahub proto
- alt-frontend-sv (TypeScript) — 4択 UI・通知設定・Badging

## Context

### 1. [[000970]] が実装不能だった理由

[[000970]] は FSRS を `v3_fsrs` として導入し `recall_echo_ready` で配送する方向を示した。しかし Web / code 調査で次が判明した。

1. **rating 入力が死んでいる。** D3 は `dismiss_state = internalized` 等の Knowledge Loop 状態に依存するが、[[000940]] で Loop projection は DROP 済みである。
2. **organic dwell は計測されない。** Trail 契約は `?trail_proposal=` 後の dwell のみを計り、recall 提示後の再読を Hard に写像できない。
3. **mutable memory だけでは reproject-safe でない。** review の append log なしに `knowledge_recall_memory` を更新すると、再投影で due が再現できない。
4. **現行 `next_suggest_at` は FSRS due ではない。** open + 1h の単純規則であり、課題は「精密な期日が通知されない」ではなく「評価履歴に基づく期日へ刷新して配送する」ことである。

### 2. FSRS は4値が前提である

FSRS は Again / Hard / Good / Easy の4値 rating を要求する（go-fsrs v4、FSRS-6、desired retention 既定 0.9）。proxy signal だけで4値を捏造すると、Optimizer 導入時に適合対象が壊れる。よって評価 UI は明示4択を正とする。

### 3. 通知とバッジは維持する価値がある

recall が Home rail の pull にしか露出しない問題はなお有効である。`today_entrance_notifier` 同型の「RPC 読み → enqueue」と Badging API（`WorkerNavigator` 対応）は、rating 設計を直したうえで再利用できる。

## Decision

**FSRS を `v3_fsrs` として導入する。rating は recall 面の明示4択のみとし、`knowledge.recall_reviewed.v1` を append-first で記録する。`knowledge_recall_memory` と `next_suggest_at` は review event 列だけから再構築する disposable projection とする。期日到来は `recall_echo_ready`（user-local day の朝夕2枠）と Badging で配送する。**

### D1. イベントと projection

- 新イベント: `knowledge.recall_reviewed.v1`
  - payload: `{ item_key, rating: again|hard|good|easy, client_review_id (UUIDv7), occurred_at, fsrs_param_digest, desired_retention, scheduler_version }`
  - business-fact 時刻は client が閾値を超えた瞬間の `occurred_at`（event-time）。server `time.Now()` を due に焼かない。
- `knowledge_recall_memory` は projection であり source of truth ではない。列は stability / difficulty / due / last_reviewed_at / review_count / param_digest 等。
- projector は event payload のみを読み、go-fsrs v4 の純関数遷移で memory を畳み、`recall_candidate_view.next_suggest_at` を due で更新する。
- CHECK / enum: `weight_set_version` に `v3_fsrs` を追加（現行は `v1_fixed` / `v2_heavy_ranker` のみ）。ScoreBreakdown に stability / retrievability 寄与を1行載せる。
- 初回カード: 未レビュー item は default parameters で card を生成し、最初の4択提出で review event が立つ。

### D2. 明示4択 UI（唯一の rating 源）

- Knowledge Home の recall rail（および期日通知の着地）に Again / Hard / Good / Easy を表示する。
- snooze は rating ではない（既存 snooze 経路を維持。review event を出さない）。
- dismiss（対象外）はカードを recall 対象から外す別 action とし、Again と混同しない。
- organic 再読 dwell・Trail act_outcome・retired Loop 状態を rating に写像しない。

### D3. Echo 配送

- alt-harvester に `recall_echo_notifier` を追加する。`today_entrance_notifier` 同型（短い tick + 時刻ゲート、sovereign の期日件数 RPC 読み、data-hub enqueue、producer 側 outbox なし）。
- スロットは **user-local calendar day** の朝・夕2枠。dedupe_key = `recall_echo:<user_id>:<local_date>:<slot>`。
- payload は kind / url / count のみ（トリガー原則を維持）。
- TTL はスロット間隔相当（12h）。予算消費は [[000977]] の global budget（local day 最大3、Echo 最大2）に従う。
- CDC RED: harvester → data-hub `EnqueuePushDelivery`（kind=`recall_echo_ready`）を producer GREEN より先に置く。

### D4. Badging

- SW の `push` handler で `self.navigator.setAppBadge(count)` を呼ぶ。未対応・拒否は catch して no-op。
- クライアント起動時に `clearAppBadge`。
- Declarative Web Push の `app_badge` メンバーは初期採用しない（根拠は crash 断定ではなく、実装差分と検証コスト）。
- Android / Linux 非表示を設定 UI に明記する。

### D5. スキーマ・proto・配線

- `push_subscriptions.recall_echo_ready BOOLEAN NOT NULL DEFAULT TRUE`
- `alt.push.v1.NotificationPreferences` **と** `services.datahub.v1.NotificationPreferences` の両方に field を追加する（field 番号は [[000977]] と事前合意: 5 = recall_echo_ready）。
- data-hub fan-out SQL の CASE に kind を追加する。未知 kind は silent FALSE にせず、契約テストで落とす。
- Optimizer（パラメータ適合）は導入しない。ログ蓄積後の別 ADR。

### D6. 実装 wave（outside-in）

1. **Wave A (CDC RED)**: `knowledge.recall_reviewed.v1` schema + ReviewRecallCandidate Pact。
2. **Wave B**: projector / go-fsrs / `v3_fsrs` migration + unit（reproject 決定性）。
3. **Wave C**: FE 4択 + E2E（提出 → next_suggest_at 更新）。
4. **Wave D**: Echo notifier + prefs/fan-out + Badging（[[000977]] の budget API が先行または同 PR で atomic）。

### 検討した代替案と却下理由

**(a) Loop / Trail 行動からの暗黙 rating — 却下。**  
入力が存在しないか計測ゲート外であり、Again を捏造する。

**(b) 「思い出せた / 忘れていた」2択 — 却下。**  
ユーザは明示4択を選択した。FSRS の4値契約と一致させる。

**(c) memory table を source of truth にする — 却下。**  
append-first / disposable projection に反する。

**(d) Optimizer を初日から入れる — 却下。**  
履歴ゼロでは適合対象がない。

## Consequences

### Pros

- rating・due・通知が現行コードと Trail / Loop 退役後の現実に整合する。
- review event があれば memory を捨てて再投影でき、Optimizer への道も開く。
- Echo / Badging により、画面を開かない日にも再想起の接点が生まれる。

### Cons / Tradeoffs

- 4択は操作コストを増やす。単一ユーザーでも継続率が低い場合、Echo は鳴ってもカード状態が更新されない。
- user-local day の TZ は JWT / profile 由来で固定する必要があり、TZ 欠落時は fail-closed（Echo スキップ + loud log）とする。
- prefs 列と proto 二重定義は [[000977]] と同時に触ると field 番号衝突しやすい。番号計画を先に固定する。
- 初期パラメータは記事再読に未適合で、期日は粗い。
