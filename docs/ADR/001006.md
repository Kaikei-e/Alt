# ADR-001006: news-creator 宛ての呼び出しを外部 API 用の間隔制御から外し、要約キューの即時補充と busy ターゲットに強いヘルスチェックで BE 要約の並列度を回復する

## Status

Accepted

## Date

2026-11-10

## Affected Services

- pre-processor（news-creator 宛ての間隔制御を専用リミッタに分離、要約キューの即時補充）
- news-creator（`RemoteHealthChecker` の probe 失敗の扱い）
- 運用者側の OpenAI 互換 gateway（リポジトリ外。プロバイダごとの並列度を 1 → 2 に変更）

## Context

[[001000]] で BE 記事要約を gateway 経由で 3 つのリモートターゲットへ分散するようにしたが、本番では 3 並列で動いていなかった。3 時間（170 件要約）のログと DB を突き合わせた結果は次のとおり。

- **news-creator は 80% の時間が空いていた。** 同時に 3 件を処理していた時間は全体の 2% だけだった。リモート 3 ターゲットの p50 は 10〜33 秒で、ターゲット側に詰まりはなかった。
- **律速は pre-processor の投入側だった。**
  - 要約ジョブは 5 分ごとに最大 10 件しか enqueue されない。上限は 1 時間あたり 120 件で、実績は約 57 件/時だった。
  - news-creator 宛ての呼び出し（要約の blocking / streaming 両経路と品質チェック）は、すべてプロセス共通の 5 秒間隔リミッタを通っていた。これは [[000723]] の MED-3b で、外部 API 向けの「5 秒ルール」を news-creator にも適用したもの。news-creator は Alt 内部のサービスで、同時実行数は worker 3 本と news-creator 側の 429 で既に抑えている。そこにさらに固定間隔をかけていたため、要約と品質チェックが同じ 5 秒枠を奪い合っていた。
- **リモートへの分散も黙って止まっていた。**
  - 3 時間で 39 件がローカルに回され、うち 38 件はリモートの不調ではなく、ヘルスチェックの誤判定が原因だった。
  - 現在の gateway 実装（Bifrost v2.4.0）は、`/v1/models` の一覧取得を chat と同じプロバイダ別キューに積む。並列度 1 のプロバイダが非 streaming の生成中だと、一覧取得は順番待ちのまま、変更できない 5 秒の期限で打ち切られる。そのプロバイダは一覧から黙って省かれる。
  - news-creator は「一覧に無い = unhealthy」と 1 回で判定していたので、自分のリクエストを処理中のターゲットを自分で外していた。同じ 3 時間に「必須モデルが一覧に無い」WARNING が約 40 件、「recovered」INFO が 47 件出ていた。
- **最も遅いターゲットは調整しても速くならなかった。** prefill / decode の速度を実測したところ、ハードウェアの上限付近だった。バッチサイズを変えても差は出なかった（変更は戻した）。今回は扱わない。

あわせて、内部サービスへの流量制御とヘルスチェックの定石を一次資料で確認した。

- **流量制御。** 固定のレートで絞るより、同時実行数の上限とサーバ側の背圧（429）で抑えるのが定石である（Netflix concurrency-limits、Envoy circuit breaking / adaptive concurrency）。
- **ジョブキューの補充。** 前回の取得が上限まで埋まっていたら、間隔を待たずに次を取りに行く。少なかったときは通常のポーリング間隔に戻る（River の `fetchWhenSlotsAreAvailable`、Que の `last_poll_satisfied`）。
- **ヘルスチェック。** 単発の probe 失敗では外さず、連続 N 回の失敗で外す（Envoy の `unhealthy_threshold`、outlier detection の consecutive 5xx）。

## Decision

次の 4 点を採用する。

1. **news-creator 宛ての間隔制御を専用リミッタに分ける（pre-processor）。**
   - 要約の blocking / streaming 両経路と品質チェックは、`utils.NewsCreatorRateLimiter()` を使う。
   - 間隔は `NEWS_CREATOR_MIN_INTERVAL` で決める。既定は `1s`、`0` は無効化で、負の値は起動時に拒否する。
   - 間隔は起動時に 1 回だけ設定する。リミッタの実際の値を `news_creator_pacing_enabled` / `news_creator_pacing_disabled` として起動ログに出す。
   - 主な制御は、従来どおり worker 3 本の同時実行上限と news-creator の 429 が担う。1 秒の間隔は、補充直後のバーストを均すための保険として残す。
   - 外部ホスト向けの `DefaultHostRateLimiter` と 5 秒ルールは変えない。
2. **要約キューを即時補充する（pre-processor）。**
   - 前回の enqueue が上限まで埋まり（`HasMore` かつ `Enqueued > 0`）、保留ジョブが無くなったら、5 分を待たずに次の enqueue を実行する。
   - 0 件・続きなし・エラーのときは、通常の 5 分間隔に戻る。
   - 補充は `sweepMu` で直列化し、`summarization refill sweep` をログに出す。
3. **busy なターゲットを probe で外さない（news-creator）。**
   - 自プロセスのリクエストを処理中（`in_flight_count > 0` または `busy`）のターゲットでは、probe 失敗を DEBUG ログだけにして健康状態を変えない。
   - 空いているターゲットは、`DISTRIBUTED_BE_UNHEALTHY_THRESHOLD`（既定 2、1 未満は拒否）回連続で probe に失敗したときに unhealthy にする。
   - 外した後の最初の再 probe は、従来どおり `cooldown_seconds`（60 秒）後に行う。その後は指数バックオフになる。
   - dispatch 失敗のクールダウンを解除できるのは dispatch の成功だけ、という [[001000]] の規則は変えない。
4. **gateway のプロバイダ並列度を 2 にする（運用者側、リポジトリ外）。**
   - 生成中でも、もう 1 本の worker が一覧取得を処理できる。
   - 各バックエンドは 1 リクエストずつしか生成しない。2 本目のリクエストは gateway ではなくバックエンド側のキューで待つことになり、スループットは変わらない。

### 検討した代替案

- **gateway の並列度を上げるだけで済ませる。**
  - gateway は他のアプリケーションと共有している。2 本の worker が両方とも生成中なら、一覧取得は同じように省かれる。
  - Alt の健全性判定が gateway の内部キュー構造に依存したままになる。
  - このため、Alt 側の修正を主とし、gateway の変更は補強に留めた。
- **gateway のモデル一覧を静的に宣言する。** 打ち切りは一覧取得の実行経路そのもので起きるので、v2.4.0 のコードでは効果がない。
- **能動 probe をやめ、dispatch の成否だけで判定する。** [[001000]] の発端は、モデル名の変更でリモートが黙って全滅したことだった。一覧による検知は残す必要がある。
- **probe の失敗 1 回で外す方式のまま、成功時に即座に戻す。** 外れている間はローカルに回されるので、取りこぼしは解消しない。「成功で即時復帰」を定石とする一次資料も見つからなかった。
- **間隔制御を完全に外す（既定 0）。** 補充直後に 3 本の worker が同時に投げるバーストを均したいので、1 秒を既定にした。運用で不要と判断したら `0` を明示すればよい。
- **1 回の enqueue 件数を増やす。** 消費の速さと無関係に先積みするので背圧が効かない。消費に合わせて補充する方式を採った。

## Consequences

### Pros

- 要約のスループットの上限が、5 秒間隔と「5 分ごとに 10 件」ではなく、worker 数とリモートのレイテンシで決まるようになる。
- 処理中のターゲットが自分の probe で外されなくなり、誤判定によるローカルへのフォールバックがなくなる。
- 品質チェックと要約が 5 秒枠を奪い合わなくなる。
- 起動ログで、間隔制御と unhealthy 閾値の実際の値を確認できる。

### Cons / Tradeoffs

- **品質チェックによる要約の削除と再生成の循環が速く回る。** 調査した 3 時間では、品質チェックが古い要約 197 件を削除していた（スコアの多くが 1〜3、閾値は 7）。投入が速くなると、削除された記事の再要約に LLM 時間を多く使う。別途調査が必要な未解決の負債である。
- **他アプリのトラフィックは判別できない。** news-creator から見て空いているターゲットでも、他アプリの生成で gateway が詰まっていれば、2 回連続で一覧から省かれた時点で外される。gateway の並列度 2 で緩和しているが、なくなりはしない。
- 補充のたびに pre-processor が DB を問い合わせる回数が増える。
- 外部ホスト向けの `DefaultHostRateLimiter` は、本番コードから呼ばれなくなった。今後、外部ホストへの呼び出しを追加するときの受け皿として残している。
- unhealthy 閾値の検証が、設定読み込みとコンストラクタの 2 か所にある。
- 運用で見る指標は 3 つ: news-creator の空き時間の割合、「必須モデルが一覧に無い」WARNING の件数、`summarization refill sweep` ログの頻度。
