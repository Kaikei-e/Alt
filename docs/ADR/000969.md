# ADR-000969: Alertmanager を新設して評価だけされていた page アラートを Pushover へ配送し、netns 共有 pki-agent の scrape 宛先を親サービス名に訂正する

## Status

Accepted

## Date

2026-08-10

## Affected Services

- observability stack（Prometheus / Grafana / 新設 Alertmanager）
- `observability/prometheus/prometheus.yml` の `pki-agent` job（14 サイドカー全数）

## Context

### 1. アラートは評価されていたが、誰にも届いていなかった

`observability/prometheus/rules/` には 31 本の alerting rule があり、うち 16 本は
`severity: page` または `critical` である。しかし `prometheus.yml` に `alerting:`
ブロックが無く、Alertmanager も存在しなかった。Prometheus は式を評価し、UI 上で
firing 表示まで到達させたうえで、そこから先へは何も送っていなかった。

この構造は [[PM-2026-054]] で顕在化した。mTLS leaf 証明書の失効から検知まで 7 時間
21 分を要し、その間 `page` 相当のルールは 3 本 firing していた。検知の実体は
「ユーザーからの報告」であり、監視は一度も関与していない。**設定されたアラートの
不在ではなく、配送経路の不在**が検知遅延の原因である。ポストモーテムの D1 は
「Alertmanager を導入するか、pki アラートを Grafana alerting に移植する」を
最優先アクションに挙げている。

なお [[PM-2026-042]] の D-1（ディスク使用率アラート）も同じ理由で未着手のまま
残っており、配送先が無いことが前提条件として効いていた。

### 2. `docs/ADR/000910.md` の記述は事実ではなかった

[[000910]] は 3 箇所で Alertmanager がスタックに存在する前提で書かれている。

- 140 行目「新設 compose service なし — observability 既存 stack を流用
  (Prometheus / Grafana / **Alertmanager**)」
- 143 行目「Grafana / **Alertmanager** は config reload で反映」
- 153 行目「**Alertmanager** への rules.yaml の hot-reload は
  `docker compose exec prometheus kill -HUP 1` を runbook に追記済み」

いずれも当時から誤りである。153 行目は `rules.yaml` を Alertmanager が読むかのように
書いているが、alerting rule を読むのは Prometheus であり、Alertmanager が読むのは
route / receiver / inhibit の設定である。この誤記の実害は大きい。ADR に
「Alertmanager がある」と書かれていたため、以降の設計レビューで
「page ルールを足せば通知される」という前提が繰り返し再生産され、
[[PM-2026-054]] まで誰も配送経路を確認しなかった。

### 3. `pki-agent` の scrape target が 14 個中 4 個で解決不能だった

`compose/pki.yaml` は 14 個のサイドカーを定義するが、`prometheus.yml` は 10 個しか
列挙しておらず、しかもそのうち 2 個は解決できない DNS 名を指していた。

サイドカーには 2 つのネットワーク形態がある。

- **パターン A**: `alt-network` に自分で参加する。自分の Docker DNS 名を持つので
  宛先は `pki-agent-<subject>:9510`。
- **パターン B**: `network_mode: "service:<親>"` と `networks: !override []` を宣言し、
  親と netns を共有する。親を :9443 で front する mTLS リバースプロキシを同居させる
  ための構成である。**この形態のサイドカーは自分の DNS 名を持たない。**
  `pki-agent-<subject>` は NXDOMAIN になり、:9510 の listener は親の netns 側に居る。
  したがって正しい宛先は**親サービス名** `<親>:9510` である。

実測（Prometheus コンテナからの到達確認）:

```
pki-agent-tag-generator:9510        → bad address
tag-generator:9510                  → {"state":"fresh"}
pki-agent-acolyte-orchestrator:9510 → bad address
acolyte-orchestrator:9510           → {"state":"fresh"}
```

パターン B は 4 個（tag-generator / acolyte-orchestrator / recap-subworker /
news-creator）あり、うち 2 個が誤った宛先で列挙され、2 個は列挙すらされていなかった。
誤った宛先の 2 個は 2026-08-09 以降 `PkiAgentDown` を出し続けていた。つまり
`PkiAgentCertExpirySoon` / `PkiAgentCertExpired` は**この 2 subject について一度も
機能したことがない**。列挙されていなかった 4 個（alt-notifier / rag-orchestrator /
recap-subworker / news-creator）に至っては、証明書の残り時間を誰も見ていなかった。

`PkiAgentFleetIncomplete`（`count(up{job="pki-agent"}) < 14`）はこの欠落を検出する
ために存在するが、これも配送経路が無かったため沈黙していた。

## Decision

### D1. Alertmanager を独立した compose service として新設する

`compose/observability.yaml` に `alertmanager` を追加し、`prometheus.yml` に
`alerting: alertmanagers:` を追加して両者を接続する。設定は
`observability/alertmanager/alertmanager.yml` に置く。既存の prometheus / grafana /
cadvisor と同じ形（loopback bind / `mem_limit` / healthcheck /
`rask.group=observability` / json-file logging / 名前付き volume）に揃える。

Prometheus に `depends_on: alertmanager` は付けない。Prometheus は alertmanagers
エンドポイントを自力でリトライするため不要であり、付ければ「通知の障害」が
「メトリクス保存の障害」に昇格してしまう。

### D2. Grafana alerting には寄せない

[[PM-2026-054]] D1 は「Alertmanager 導入 **または** Grafana alerting への移植」を
選択肢として並べている。後者を採らない理由は 3 つある。

1. **Grafana は `depends_on: clickhouse` の `service_healthy` で gate されている。**
   ログストアが落ちると Grafana は起動しない。page の配送経路をログストアの
   可用性に従属させると、「ログが壊れた」が「ページが飛ばない」を含意する。
   配送は観測対象の中で最も依存の浅い場所に置くべきである。
2. **Prometheus ルール 31 本の書き直しは promtool テストを捨てることになる。**
   `observability/prometheus/tests/` には rule の unit test がある
   （`pki-agent-alerts_test.yml` / `knowledge-loop-rules_test.yml`）。Grafana
   managed rule に移すと、この検証手段に等価なものが無い。テスト済みのルールを
   テスト不能な形式へ移す取引は割に合わない。
3. **Grafana の alerting provisioning schema には `inhibit_rules` に相当するものが
   無い。** 後述の通り、pki-agent の障害クラスでは 1 つの原因が十数本を同時に
   点灯させる。抑制が書けない配送先は、単一運用者にとって「通知を全部ミュートする」
   という最悪の適応を誘発する。

逆方向、すなわち Grafana 管理の 27 本（大半が ClickHouse 由来で Prometheus では
評価できない）は Alertmanager datasource を provisioning し
`jsonData.handleGrafanaManagedAlerts: true` で同一 Alertmanager に寄せる。
2 つのアラートエンジンに対して route / silence / inhibit を 1 セットに統合する。
メンテナンス時に subject を silence するのに「どちらのエンジンが出した page か」を
思い出す必要が無くなる。

### D3. 配送先は Pushover とする

`pushover_config` は Alertmanager に native に存在する。採用理由は代替と交換不能な
一点にある。**Pushover の Emergency priority (2) は端末のサイレント / おやすみモードを
公式に貫通し、人間が確認するまで再送を続ける。** Alt は単一運用者で運用しており、
深夜にチャットチャンネルへ落ちたアラートは「翌朝読むアラート」である。Slack /
Discord には送信側から通知レベルを昇格させる手段が無く、通知の強さは受信側の
クライアント設定に委ねられる。7 時間 21 分の検知遅延を繰り返さないという目的に対して、
この差は決定的である。

資格情報は `user_key_file` / `token_file` で Docker secret から読む。設定ファイルにも
コンテナの environment にも平文を置かない。

`priority` / `retry` / `expire` は **page 系 receiver では明示しない**。Alertmanager の
既定値が `priority = {{ if eq .Status "firing" }}2{{ else }}0{{ end }}` /
`retry = 1m` / `expire = 1h` であり、これは意図する挙動そのものだからである
（firing 中は Emergency、resolved は Normal に落として「復旧通知自体が
おやすみモードを破る」ことを避ける）。明示的に書き下すと、考え抜いた override の
ように見えながら実際には今日の既定値を pin するだけになる。判断の記録は設定ファイル内の
コメントに残した。一方 ticket 系 receiver では `priority: '0'` を**明示する**。
既定のままでは warning が Emergency に昇格してしまい、それが page と ticket を
分ける唯一の実質的差分を消してしまうためである。

### D4. inhibit_rules を pki-agent の障害クラス向けに定義する

`route.group_by` に `subject` を入れる。pki-agent のアラートは subject 単位であり、
subject こそが通知の実質的な内容だからである（14 subject を 1 group に畳むと
「PkiAgentCertExpirySoon (14)」としか出ず、どの証明書か分からない）。代償として
fleet 全体の事象が 14 通知になるため、以下の抑制を必須とする。

1. `PkiAgentMetricsAbsent` firing 中は、個別 cert アラート
   （`PkiAgentCertExpirySoon` / `PkiAgentCertExpired` / `PkiAgentRenewalFailing` /
   `PkiAgentDown` / `PkiAgentFleetIncomplete`）を抑制する。これらは全て同一 metric
   family 上の式であり、系列が全く無い状態では firing するかどうかが
   「TSDB に何が残っているか」の副産物にすぎない。`PkiAgentMetricsAbsent` は
   `absent_over_time()` 由来で `subject` を持たないため、`equal` は `stack` で取る。
2. `PkiAgentDown{subject=X}` firing 中は、同一 subject の
   `PkiAgentCertExpirySoon` / `PkiAgentCertExpired` を抑制する。scrape が落ちている
   subject の cert gauge は定義上 stale であり、報告しているのは
   「コンテナが消える直前に取得した値」であって現在の証明書の状態ではない。

加えて汎用の severity ladder（page/critical が同一 alertname・stack・subject の
warning/ticket を抑制）を置く。[[PM-2026-054]] の事象を今回の設定に通すと、
5 subject × 2 本 + fleet count の計 11 通知が数本まで畳まれる。

### D5. pki-agent の scrape target を 14 全数にし、パターン B は親名で引く

パターン B の 4 件は宛先を `<親>:9510` とし、**なぜ親名なのかを英語コメントで
prometheus.yml に明記する**。これが無いと将来の読み手には単なる不整合に見え、
`pki-agent-<subject>:9510` へ「修正」されて同じ障害が再発する。`subject` ラベルが
どのエージェントの系列かの正であり、アドレスは到達手段にすぎない旨も併記する。

## Consequences

### Pros

- `severity: page` のアラートが初めて人間に届く。16 本の page/critical ルールが
  評価専用から配送対象に変わる。
- pki-agent の監視が 14 subject 全てで成立する。従来は 10 subject が列挙され、
  そのうち 2 subject は解決不能な宛先を指し、実効カバレッジは 8 subject だった。
- `PkiAgentFleetIncomplete` の閾値 14 と実際の target 数が一致する。今後
  `compose/pki.yaml` にサイドカーを足して `prometheus.yml` を忘れると、
  10 分後に page が飛ぶ。
- 2 つのアラートエンジン（Prometheus 31 本 / Grafana 27 本）が単一の silence /
  inhibit 面を共有する。
- 資格情報が設定ファイルにも environment にも現れない。ローテーションは
  secret ファイルの差し替えと Alertmanager の再作成のみ。

### Cons / Tradeoffs

- **secret の実ファイルが存在しないと compose が起動に失敗する。** 本 ADR では
  `secrets/pushover_user_key.txt` / `secrets/pushover_token.txt` を作成していない
  （値を持たないため）。`docker compose config` は欠落を検出せず正常に render するので、
  失敗は `up` の時点まで遅延する。適用前に両ファイルを用意することが前提条件である。
- **通知疲れのリスクを inhibit_rules に賭けている。** `group_by` に `subject` を
  含める選択は、可読性と通知本数のトレードオフを後者に不利な側で取っている。
  抑制ルールが実地の障害で期待通りに畳まなければ、単一運用者は通知そのものを
  ミュートしうる。次の実障害での実測が必要であり、それまでこの設定は仮説である。
- **Emergency priority は誤検知のコストを引き上げる。** サイレントを貫通して
  1 分ごとに 1 時間再送する挙動は、正しい page に対しては望ましいが、
  flapping するルールに対しては有害である。severity のラベル付けが従来より
  重い意味を持つようになった。
- **Alertmanager 自身の死は無音である。** Prometheus は `alertmanager` への
  送信失敗を `prometheus_notifications_errors_total` に計上するが、それを見る
  アラートは本 ADR の範囲外であり、まだ無い。配送層の自己監視は未着手の課題として
  残る（`ALERTS` の meta-monitoring も同様）。
- **Grafana 側の統合は provisioning だけでは完結しない。** datasource の
  `handleGrafanaManagedAlerts: true` は「この Alertmanager を選択可能にする」までで、
  実際に Grafana managed rule の配送先として使うには Grafana 側で
  Alertmanager を選ぶ操作が要る。
- **`docs/ADR/000910.md` の本文は訂正しない。** ADR の本文は改変しない規約に従い、
  誤りの訂正は本 ADR に置く。したがって 000910 を単独で読んだ人間は依然として
  誤った前提を得る。逆辺（backlink）が唯一の防御である。

## Deploy-model 整合性セルフチェック

- [x] 新設 compose service が `depends_on` で他 service を gate するか？ — **NO**。
  `alertmanager` は `depends_on` を一切持たず、また他の service から `depends_on`
  されもしない（Prometheus に依存を張らない判断は D1 に記載）。rolling deploy で
  `docker compose up alertmanager` 単独起動が成立する。
- [x] 新設 compose service に `restart: "no"` の one-shot init container を含むか？ — **NO**。
- [x] 新設名前付き volume を populate する責務はどこにあるか？ — `alertmanager_data` は
  Alertmanager 自身が silence / nflog を書く。init による populate は不要で、
  空の状態から正常に起動する。
- [x] rolling 互換 — `prometheus.yml` / `alertmanager.yml` はいずれも bind mount で、
  設定変更はコンテナ再作成なしに reload で反映できる。target 追加は Prometheus の
  reload、route 変更は Alertmanager の reload。
- [x] DB migration 不要。
