# ADR-000973: 関所を通過した Trail branch のみを trail_branch_proposed 通知（Beacon）として配送し、沈黙を正常動作とする通知予算を導入する

## Status

Superseded by [[000977]]

本 ADR は [[000972]] の関所（grounding gate）の稼働を配送の前提条件とする、と書いていたが、
正準契約との衝突と予算未決により実装根拠にならない。本 ADR の Decision は実装根拠にせず、
[[000977]]（および前提の [[000976]]）を正とする。

**Web / code 調査後の判定（2026-08-11）: 正準契約の改訂前は実装不可だった。**
`knowledge-trail-core-concept.md` §C5 / §G と Web Push Beacon の衝突、Echo 合算予算の未決、
同一 Tx API / fan-out CASE の実装ギャップが後継で解消される。

## Date

2026-08-11

## Affected Services

- knowledge-sovereign (Go) — event + outbox 同一 Tx API、planner の選抜、relay、data-hub client
- alt-data-hub (Go) — per-kind 列、datahub proto、fan-out CASE、sovereign peer allowlist
- alt-backend (Go) — kind / コピー / alt.push.v1 proto / fan-out capability 拡張
- alt-frontend-sv (TypeScript) — 設定 UI、rich preview トグル、着地画面

## Context

### 1. branch には配送に必要な構造と効果測定ループが既に揃っている

`proto/alt/knowledge_trail/v1` の Branch は relation_kind（continuation / cluster / contradiction / inquiry）・why・evidence_refs・confidence の四つ組を必須で携え、`ResolveBranch`（taken / dismissed、UUIDv7 冪等、dismiss_reason: not_following_topic / already_known / wrong_relation）と `EmitTrailOutcome`（Page Visibility 準拠の dwell_ms、branch ごと first-write-wins）が応答と帰結を記録する。通知経由の taken 率と dwell は、新しい計測基盤なしで測れる。

### 2. producer 起点の通知は三重に前例がある

`push_deliveries` のマイグレーションコメントは「各 producer は自分の DB に notification_outbox を持ち、relay が data-hub に転送する。alt-db 側は下流の配送キューである」と定義しており、pre-processor（Go: `service/notification_relay.go`、batch 50 / tick 15s / lease 2min / full-jitter backoff 10s〜1h / max 8 attempts / TTL 24h / 起動ログ `notification_outbox_relay_enabled` / at-least-once + dedupe_key）と recap-worker（Rust: `src/notification/relay.rs`、`store/dao/notification_outbox.rs`、`clients/datahub.rs`）が同型で実装している。

### 3. reproject 安全性が発火点を規定する

`trail_planner` パッケージは自身を「trail.branch_proposed.v1 の唯一の emitter。producer は現在状態を読んで emit を決めてよく、events を畳む projector は payload-only（reproject-safe）に留まる」と定義している。通知の発火点を projector に置けば、reproject のたびに過去 branch 全件が再発火する。発火点は producer（planner）でなければならない。planner は knowledge-sovereign の main.go で ticker 駆動の RunBatch として稼働しており、起動時に `trail.branch_producer.wiring` を loud に出力する（PM-2026-045 / [[000928]] の規約）。

### 4. 悉皆的な通知は情報量ゼロに退化する

現行テンプレート why の教訓（[[000972]] Context §1）は、全件に付与される説明が説明として機能しないことを示した。通知はさらに厳しい媒体であり、割り込みを正当化できない配送はチャネル自体の信頼（通知許可）を焼く。したがって Beacon は「言うべきことがある日にだけ鳴る」ことを正常動作として設計しなければならない。

### 5. 通知のコンテンツ搭載は原則の明示的変更を要する

現行原則（`push_dispatch_usecase/render.go`）は「通知はトリガーであり、コンテンツを運ばない。運べばロック画面に載る」。RFC 8291 により transit は暗号化されるため、この原則の実質的根拠はロック画面表示に絞られる。原則を黙って侵食するのではなく、変更するなら本 ADR で明示的に決定する。

### 6. 調査で判明した実装ギャップと数値根拠の限界

- 1 日 1 件・`corroborated` 限定は RFC / Apple HIG / Android guide が要求する値ではなく、
  「意味があるときだけ割り込む」という原則を具体化した初期仮説である。数値自体を外部標準で
  正当化しない。
- 現行 planner の `corroborated` は「共有タグが 2 個以上」、relation は cluster / continuation
  であり、[[000972]] の「独立した原文 2 本」や contradiction と同じ意味ではない。関所の green と
  confidence migration 完了を feature-state として観測できなければならない。
- `AppendKnowledgeEventIfNew` は内部で transaction を commit するため、後続で outbox INSERT すると
  dual-write になる。branch event と outbox を 1 transaction に閉じる新 repository capability が必要。
- data-hub の fan-out SQL は未知 kind を `ELSE FALSE` で静かに落とす。列追加だけでなく
  `NotificationPreferences` の二つの proto と fan-out CASE を同じ変更で更新し、CDC RED で固定する。
- 「1 日」は UTC calendar day だと JST 09:00 に境界が来る。rolling 24h / user-local day の
  どちらを global budget に採るかは未決である。

## Decision

**[[000972]] の関所を通過し、かつ選抜条件を満たす Trail branch を、新 kind `trail_branch_proposed` のトリガー通知として 1 日最大 1 件配送することを採用する。ゼロ件の日は正常動作である。**

### D1. 選抜条件（配送ゲート）

- `confidence = corroborated`（[[000972]] D4 の決定論的算出による）
- `relation_kind ∈ { contradiction, continuation }`
- 1 日（UTC）あたり最大 1 branch。複数候補がある日は contradiction を優先し、同種内は planner のスコア順とする。
- 条件を満たす branch が無い日は enqueue しない。この沈黙は監視上の異常ではない（D6 参照）。

### D2. 発火点は planner、outbox は sovereign DB

knowledge-sovereign の migrations に `notification_outbox` を新設する（pre-processor / recap-worker と同形の自 DB outbox。[[000961]] の Atlas 同名テーブルゲートに対しては「複数サービス DB が同形の notification_outbox を持つのは正」という既存整理の範囲内であり、alt-db 側の配送キューは `push_deliveries` という別名で既に区別されている）。planner は D1 の選抜を通った branch について、branch emit と同一トランザクションで outbox 行を書く。

relay は pre-processor の定数体系（batch 50 / lease / full-jitter backoff / max attempts / TTL）を踏襲して sovereign 内の goroutine として追加し、起動時に配線状態を loud ログで宣言する。TTL は 24h とする（branch の鮮度が価値であり、pre-processor の `notificationTTL = 24h` と同じ判断）。

### D3. dedupe_key と冪等性

`dedupe_key = "trail_branch:" + branch_key` とし、送信時ではなく業務事実から導出する（`push_deliveries` の設計原則）。これにより relay の at-least-once 再送も、万一 planner が同一 branch を再 emit する経路が生じた場合も、`UNIQUE (dedupe_key, subscription_id)` が二重配送を潰す。`occurred_at` は branch の提案時刻を producer が供給する。

### D4. payload はトリガーのみ、rich preview はオプトイン（既定 OFF）

既定の通知は既存原則どおりコンテンツを運ばない: payload は kind / url（該当記事の patch-exit 面へ navigate）/ count のみ、表示コピーは notificationCopy の定型文（例:「知識の分岐が 1 件あります」）とする。

そのうえで、per-kind 設定に **rich preview トグル（既定 OFF）** を新設する。ON の場合に限り、payload に対象記事タイトルと why の第一文を含め、ロック画面に表示する。これは Context §5 の原則の**明示的な部分変更**であり、適用範囲は本 kind のみ、既定値は原則側（OFF）に置く。単一ユーザー・自己ホストという本システムの脅威モデルにおける、表示リスクと価値の交換をユーザー自身が選ぶ形にする。

### D5. スキーマ・proto・UI

[[000970]] D5 と同形の反復: `push_subscriptions` に `trail_branch_proposed BOOLEAN NOT NULL DEFAULT FALSE` を追加（**本 kind のみ既定 FALSE** — 生成系を含む新機能の通知は明示オプトインとする）、`NotificationPreferences` に field 追加、`preferences.ts` / notificationCopy 拡張。notificationclick の着地は該当記事の記事末尾（`GetItemBranches` が描画する patch-exit 面）とし、taken / dismissed の応答導線に直結させる。

### D6. 監視は「配送の沈黙」と「選抜の沈黙」を区別する

Web Push 配送系の既存メトリクス（push_send_total 等）は流用する。追加で planner 側に「本日の選抜候補数」「選抜結果（emit / 予算超過 / 関所不通過 / 候補なし）」のカウンタを置き、**ゼロ配送の日が『候補なし・関所不通過』に分類されている限り正常**と定義する。配送経路の故障とゼロ選抜が同じ「鳴らない」に見える問題は、push_dispatcher が既に持つ「沈黙の検知」設計と同じ手法（分類付きカウンタ）で区別する。

### D7. 誤差信号の還流

通知経由で開かれた branch の dismiss_reason / dwell を、LLM 段（[[000972]] D2-2）のプロンプト文脈に反例・正例として注入する。`already_known` は新規性閾値の、`wrong_relation` は関係判定の誤差信号として扱う。評価器の新造は行わない。

### 検討した代替案と却下理由

**(a) 全 branch を通知する — 却下。**
Context §4 のとおり悉皆性は情報量をゼロにする。"decorated feed" の通知版であり、本機能群の存在理由に反する。

**(b) projector / 通知専用スキャナを発火点にする — 却下。**
projector 起点は reproject で全件再発火する（Context §3）。定期スキャナ（outbox なし）は「業務事実に紐づく通知は producer の自 DB outbox」という既存整理に反し、branch emit と通知決定の原子性も失う。[[000970]] の Echo が outbox を持たないのはビュー導出・日付 dedupe で自己修復するからであり、branch はその条件を満たさない。

**(c) 生成 LLM に配送可否・confidence を判断させる — 却下。**
[[000972]] D4 で禁止済み。配送ゲートは決定論側の専権とする。

**(d) 予算をハードコードせず macro state による動的予算にする — 初期は却下。**
1 日 1 件の固定上限から開始する。動的化は Echo（朝夕）との合算予算が実運用で問題になった時点で、[[000909]] の macroState を持つ knowledge_loop 側の設計として別 ADR で扱う。初手から動的化する根拠となる観測データが存在しない。

**(e) rich preview を最初から ON にする — 却下。**
既存原則の既定を反転させる根拠がない。原則の変更は明示的・限定的・オプトイン（D4）に留める。

## Consequences

### Pros

- 「Alt が学んだことを Alt の側から話しかける」体験が、関所（[[000972]]）と予算（D1）という二重の品質保証の上で初めて成立する。
- 効果測定は既存 RPC（ResolveBranch / EmitTrailOutcome）がそのまま担い、通知の価値が taken 率と dwell で観測可能になる。
- 発火点・outbox・relay・dedupe のすべてが三重の既存前例の反復であり、新規の設計リスクは選抜条件（D1）に局所化される。
- ゼロ配送日を正常と定義した監視（D6)により、「鳴らない」ことが機能不全と混同されない。

### Cons / Tradeoffs

- 価値が [[000972]] の生成・検証品質に完全に従属する。関所が厳しすぎれば沈黙が続き、緩すぎれば通知許可を焼く。閾値調整は D7 の誤差信号を見ながらの継続作業になる。
- 1 日 1 件・corroborated 限定は、立ち上がり期には「ほぼ鳴らない機能」になりうる。これは仕様であるが、体感的な「作ったのに動かない」と区別するために D6 の分類カウンタが必須になる。
- 1 日 1 件は Beacon の業務事実 1 件を意味し、複数端末 subscription への fan-out は端末数分届く。通知通数の global cap ではない。
- Echo との合算予算は未決であり、[[000970]] の「本 ADR で一元管理する」という期待を満たしていない。
- UTC 日境界はユーザーの生活日と一致しない。日次 dedupe と fatigue budget を同じ clock で扱う根拠がない。
- rich preview トグルは per-kind 設定の複雑性を一段上げる（boolean 列 + 表示モードの二軸）。kind 増加時の JSONB 化検討（[[000970]] Cons）を早める要因になる。
- sovereign に relay という常駐責務が増え、プロセスの責務が「状態の所有」から一歩はみ出す。将来 notifier 系を独立プロセスに切り出す場合の分割線として明記しておく。
