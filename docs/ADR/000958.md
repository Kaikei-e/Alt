# ADR-000958: リリースパイプラインの出荷判定を per-service artifact の AND に統一し部分ロールアウトを既定にする

## Status

Accepted

## Date

2026-08-06

## Affected Services

- alt-deploy (private repo) — `release-deploy.yaml` の構造変更（本 ADR の Phase 0–4）
- c2quay — 部分デプロイ機構 `--withhold` / `partial_rollout` の本体実装
- alt-backend / alt-harvester / alt-data-hub — deploy-atomic family 宣言の対象
- 全 compose デプロイ対象サービス — 出荷単位が「リリース全体」から「qualified なサービス集合」に変わる

## Context

### 問題: 1 サービスの CI 失敗が全サービスのデプロイを止める

[[PM-2026-053-adr954-split-release-pipeline-and-dataplane-outage]] で、リリースパイプラインが約 17 時間閉塞した（6 回中 5 回失敗）。調査の結果、`release-deploy.yaml` は「per-service artifact による分離」（gate の per-pacticipant 実行、deploy filter、roll-services の per-service reconcile）と「job-level result による一括ブロック」が混在しており、後者の 3 本のエッジが前者の分離設計を全て無効化していることが判明した。

| # | エッジ | 効果 |
|---|--------|------|
| (A) | `deploy.if` が `needs.e2e.result == 'success'` を要求 | e2e matrix は未変更サービス含む全 18 leg。どれか 1 本の赤で全デプロイ停止 |
| (B) | `pact-publish-consumer` の `needs: [resolve, build]` に `always()` がない | build 1 leg の失敗（例: base image pull のレート制限）で publish → gate → deploy が全段 skip |
| (C) | resolve 時点の co-release 一括 pin | 1 サービスの pact publish 失敗が、同時リリース全員の gate を未解決 selector で赤にする |

さらに精査で未報告の構造欠陥 3 件が見つかった。

| # | 欠陥 | 効果 |
|---|------|------|
| (D) | deploy filter が build 成否を見ておらず、非 pacticipant は無条件通過 | build 失敗サービスが一括 `docker compose pull` に入り manifest 不在で deploy job ごと途中死。(A)(B) を直すとここが新たな単一障害点になる |
| (E) | [[000954]] の 3 バイナリ family（alt-backend / alt-harvester / alt-data-hub）が filter 上アトミックでない | alt-backend が gate 赤で withheld されても harvester / data-hub は素通り。新 data-hub × 旧 backend の split roll は PM-2026-053 のデータプレーン停止と同型 |
| (F) | deploy job の `always()` はキャンセル時も true | オペレータの実行キャンセル後も本番ロールが続行しうる（PM-2026-053 のタイムラインに実操作あり） |

### e2e ゲートの実効カバレッジ

e2e matrix（`services_all`）の実測: `e2e/hurl/` に実在するスイートは 18 件中 12 件。各スライスは focal service のタグしか上げないため、**未変更サービスの regression leg はスライス全体が `:main`（= 本番と同一イメージ）で走っており、リリース対象の新コードを一度も実行していない**。その赤が意味するのは「本番が既に赤」か「共有ハーネス（`e2e/hurl/_lib/`）のドリフト」であり、リリースを止めても直らない。典型リリースでは 12 本中 9–11 本がこの pure regression leg で、それぞれが全デプロイへの拒否権を持っている。

### 外部ベストプラクティスとの突き合わせ

2026-08-06 に公式ドキュメント優先の調査を実施した。要点:

- **Independent deployability はマイクロサービスの定義的性質**（Fowler / Newman / Richardson / DORA で完全なコンセンサス）。「全部一緒に出す」は distributed monolith であり、共有 release train を正しい目標状態として支持する権威的ソースは存在しない。デプロイ列車では任意のインシデントの MTTR が「無関係サービスも含め全パイプラインを緑にする時間」で下限が決まる
- **クロスサービス E2E をデプロイゲートにすることが、N サービスを 1 つのデプロイ単位に変換する装置**（Richardson）。定石は三層: smoke（blocking + rollback）/ 変更サービス限定 E2E（blocking）/ フリート E2E（post-deploy・非ブロッキング・インシデント起票）
- **Pact のモデルはもともと per-service**。`can-i-deploy` は 1 pacticipant 単位の質問で fleet-wide モードは存在しない。公式の推奨形は「サービス X の gate / deploy / record-deployment を 1 ジョブに閉じる」。未変更サービスは古い record のまま残すのが matrix 的にも正しい
- **GitHub Actions では matrix job を `needs` で受けると結果が 1 値に潰れる**のが仕様であり、per-service 判定は artifact でしか下流に運べない。gate が既に採用している `gate-<svc>` artifact の idiom が唯一の一貫した解。あわせて公式は `always()` ではなく `!cancelled()` を推奨している

## Decision

**「あるサービスをこのリリースで出荷してよいか」の判定を、job-level の `needs.*.result` から per-service artifact の AND に統一する。** 適用後、job-level 依存は `needs.resolve.result == 'success'`（matrix 展開の前提となる唯一の不可避エッジ）だけになる。

出荷判定 = 以下 4 artifact の AND ＋ 宣言的 family 制約:

| artifact | 生成元 | 意味 |
|---|---|---|
| `build-ok-<svc>`（新設） | build leg | この SHA のイメージが GHCR に存在する |
| `pact-status-<role>-<svc>`（既存） | pact-publish | この SHA の pact / verification が Broker に届いた |
| `gate-<svc>`（既存） | gate leg | `can-i-deploy` が production に対して green |
| `e2e-status-<svc>`（新設） | e2e leg | この SHA の Hurl スイートが green |

### 適用順序（各段は独立に commit / 検証可能、前段が次段の安全性の前提）

1. **Phase 0（安全性強化のみ）**: 全ジョブの `always()` を `!cancelled() && needs.resolve.result == 'success'` に統一 (F)。deploy filter に deploy-atomic family（`alt-backend,alt-harvester,alt-data-hub`）を追加 (E)。部分ロール発生を `.c2quay/partial-rollout` に記録し、rollout composition を `$GITHUB_STEP_SUMMARY` に出力
2. **Phase 1（build の per-service 化, (D)）**: build に `build-ok-<svc>` artifact を追加し、deploy filter の第 1 判定にする。一括 pull はリトライ化（per-service 分割はしない — family atomicity を壊すため）
3. **Phase 2（(B) の解消）**: `pact-publish-consumer` を `!cancelled()` 化。pact publish はイメージ非依存（`scripts/pact-check.sh` はチェックアウト上で走る）なので build 失敗サービスの publish は無害であり、むしろ現状の skip が provider verify を旧 consumer pact に対して走らせる race を作っている
4. **Phase 3（(C) の解消）**: co-release pin を gate 実行時評価に変える。publish 済みメンバーだけ SHA で pin し、publish 失敗メンバーは pin から外して production 現行版に解決させる。問いが「実際に出荷される集合＋本番現行版と一緒に出せるか」になり、真に breaking なら証拠に基づいて赤、無関係なら通る
5. **Phase 4（(A) の解消・最大の構造変更）**: e2e leg に `e2e-status-<svc>` artifact を追加し、deploy の `if` から `needs.e2e.result` を除去。touched サービスの赤はそのサービス（と family）のみ withhold。**未変更サービスの regression 赤は advisory（warning + summary）に降格**し、デプロイを止めない

### c2quay 側の決定

- **`all_or_nothing: false` への設定変更は解として却下する。** このフラグは gate クエリ形状（集約 matrix ↔ per-service）の切替のみで、「最初の赤で全体中断」のロジックは値に関わらず無条件。false は c2quay ADR-0009 が修正した per-service gate の誤セマンティクス（2026-04-17 インシデント）を再発させ、悪化させる
- **c2quay 本体に `--withhold <svc>` を追加する**: 候補集合から withheld を除外して Plan を再構成し、**縮小集合で gate を再実行**、withheld サービスのイメージを pre-snapshot 値に pin した override で compose up、record-deployment は縮小集合のみ、専用 exit code で部分ロールを明示する。無人（systemd timer）経路には `partial_rollout: withhold-failing` + deploy-atomic `groups` 設定を用意する
- **c2quay ADR-0012（`--skip-gate` 拒否）との区別**: withhold は gate をバイパスしない。候補集合を変えて gate を**再実行**する。また PM-2026-053 の「co-release は全量固定が唯一の表現」という教訓とも矛盾しない — あちらが禁じたのは「一部を SHA 固定し残りを stale な状態と未固定比較」であり、withhold は外したサービスを「実際に動き続ける現行バージョン」という事実に固定する
- **二重系統（GH Actions 自動経路 / c2quay 手動・timer 経路）は短期維持**。中期的には c2quay に withhold + 変更検知 + リモート実行が揃った時点で gate セマンティクスを c2quay に一本化する方向とする

### 検討した代替案と却下理由

| 代替案 | 却下理由 |
|---|---|
| e2e の blast-radius withhold（未変更サービス Y の赤で、Y と Pact 統合を持つ touched サービスも withhold） | regression leg は構造的に新コードを実行していないため、blast radius を計算する土台が存在しない。依存グラフの新規レジストリも必要になる |
| e2e フリートゲートの現状維持 | 得ている安全性（共有ハーネスのドリフト検出のみ）に対して支払うブロック力が過大。ゲートで止めても対象の欠陥は直らない |
| `all_or_nothing: false` | 上記の通り。中断ロジックに影響せず、gate セマンティクスだけ退行する |
| build → test → deploy を 1 つの matrix leg（reusable workflow）に閉じる縦割り再編 | GHA セマンティクス上の最終形として正しいが、1900 行の workflow の全面書き換えになる。per-service artifact 化で同じ分離特性を段階的・可逆的に得られるため、今回は採らない（将来の選択肢としては残す） |
| c2quay 経路の廃止（alt-deploy 一本化） | GH Actions / GHCR / ネットワーク障害時のローカル手動デプロイ手段が消える。PM-2026-031 起点の「デプロイ実行パスは Pact ゲート必須」の合意にも反する |

## Consequences

### Pros

- 1 サービスの build / gate / e2e 失敗が、そのサービス（と宣言された family）だけの withhold になり、他サービスのデプロイと**インシデント修正の投入**が止まらない
- 未解決 selector による「情報量ゼロの全員赤」（PM-2026-053 問題 3 の一形態）が、「非互換なら証拠に基づいて赤」に置き換わる
- (D)(E)(F) という顕在化前の構造欠陥（deploy job 途中死・トリオ split roll・キャンセル時続行）が先回りで塞がる
- 部分ロールが記録・可視化され（summary / `.c2quay/partial-rollout`）、rollback 判断の前提情報が残る

### Cons / Tradeoffs

- **部分デプロイが常態化する**。Pact が張られていない結合（alt-frontend-sv ↔ alt-butterfly-facade）は family 宣言か明示的許容かの判断が別途必要
- family atomicity は Pact ではなく**宣言**でしか守れない（harvester / data-hub は Broker 上の gate leg を持たない）。宣言の保守を怠ると (E) が再発する
- withheld サービスの migration は適用される（expand-migrate-contract 上は schema-first が正しいため意図的に維持）。「新スキーマ＋旧バイナリ」の中間状態が増えるので、view 列末尾追加・UPSERT COALESCE などの既存規律への依存が強まる
- regression e2e の赤が非ブロッキングになるため、共有ハーネスのドリフトの検出が「デプロイ停止」から「warning の監視」に弱まる
- pacticipant allowlist が alt-deploy 側に手書きで 3 箇所以上残っている問題は本 ADR では解消しない（`services.yaml` からの生成への統合は別作業）
- [[000931]] Phase B の「全 pacticipant 常時全走」は維持するが、**その結果をデプロイゲートに使う部分だけを advisory に降格**する（完全置換ではないため supersedes にはしない）
