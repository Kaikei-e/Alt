# ADR-000970: FSRS を recall_weight_set v3 として導入し、期日到来の再想起を recall_echo_ready 通知とアプリバッジで配送する

## Status

Superseded by [[000974]]

**Web / code 調査後の判定（2026-08-11）: 実装着手不可。** D3 が [[000940]] で retire / DROP
済みの Knowledge Loop projection（`dismiss_state` / `internalized`）を現行 rating 入力として扱い、
organic な再読 dwell も Trail 正準契約では計測されない。さらに D1 は review の append log を定義せず
可変 memory table だけを置くため、そのまま実装すると append-first / reproject-safe を破る余地がある。
本 ADR の Decision は実装根拠にせず、[[000974]] を正とする。

## Date

2026-08-11

## Affected Services

- knowledge-sovereign (Go) — FSRS 記憶状態の保持と期日計算、期日件数 RPC
- alt-harvester (Go) — `recall_echo_notifier` job（朝夕の時刻ゲート付き enqueue）
- alt-data-hub (Go) — `push_subscriptions.recall_echo_ready` 列の追加
- alt-backend (Go) — kind 定数 / 描画コピー / proto の拡張
- alt-frontend-sv (TypeScript) — 通知設定 UI と service worker のバッジ処理

## Context

### 1. recall 基盤は存在するが、pull 型サーフェスにしか露出していない

`recall_candidate` は `next_suggest_at` / `snoozed_until` を持つ。sovereign RPC
（`proto/services/sovereign/v1`）は候補と期日を返し、explainable scoring の
`weight_set_version` = `v1_fixed` / `v2_heavy_ranker` と `ScoreBreakdown` は
`proto/alt/knowledge_home/v1` および [[000922]] が正本である（従来ここで参照していた
[[000913]] は Loop の act outcome であり、scoring の実装根拠ではない）。

現行 projector の `next_suggest_at` は event-time の open から 1 時間後を置く単純規則で、FSRS due
ではない。この状態を消費するのは Knowledge Home 画面内の recall rail のみであり、ユーザーが画面を
開かない限り到来は何も引き起こさない。したがって課題は「既存の精密な期日が通知されない」ではなく、
**単純な再提示時刻しかない recall を、評価履歴に基づく期日へ刷新して配送するか**である。

### 2. 既存の通知 kind はすべて完了通知である

`domain/push.go` の kind は `summary_ready` / `acolyte_report_ready` / `recap_ready` / `today_entrance_ready` の 4 つで、いずれも「依頼したジョブが終わった」「入口が開いた」という完了・合図の通知である。ナレッジの定着（再想起）を目的とする通知は存在しない。

### 3. 再想起のスケジューリングには確立されたアルゴリズムが存在する

FSRS（Free Spaced Repetition Scheduler）は open-spaced-repetition コミュニティが開発する間隔反復アルゴリズムで、MaiMemo 系研究（KDD 2022 / IEEE TKDE 2023）を背景に持つ
（https://github.com/open-spaced-repetition/free-spaced-repetition-scheduler ）。
レビュー評価は Again / Hard / Good / Easy の 4 値で、desired retention とカード状態から次回期日を
計算する。レジストリ実査（2026-08-11）では crates.io `fsrs` v6.6.1、npm `ts-fsrs`
v5.4.1、Go `github.com/open-spaced-repetition/go-fsrs/v4` v4.0.0（MIT）が公開されている。
go-fsrs の optimizer は開発中であり、初期導入の安定した前提には置かない。

先行製品として Readwise の Daily Review があり、想起確率が 50% 以下に減衰したハイライトを再浮上候補とし、初期半減期を 7 / 14 / 28 日に置く設計を公開している（https://docs.readwise.io/readwise/docs/faqs/reviewing-highlights ）。「読んだものを適切な間隔で再浮上させる」体験そのものに確立した前例がある。

### 4. Loop 時代の評価入力は履歴であり、現行入力としては使えない

FSRS は各レビューに Again / Hard / Good / Easy の rating を必要とする。Loop 時代には
`dismiss_state = internalized` と macroState が存在したが、[[000940]] により Loop read path と
projection は retire され、migration `00028_drop_knowledge_loop_projections.sql` で型・表も DROP
済みである。過去イベントは履歴として残るが、新規 rating の producer にはならない。

現行で観測できるのは recall の snooze / dismiss、Home の open、Trail の
`trail.branch_resolved.v1` / `trail.act_outcome.v1` である。ただし Trail dwell は branch taken 後の
`?trail_proposal=` 経路だけを計測し、organic な再読を計測しない。よって D3 の写像は
「既存の日常操作を読み替えるだけ」では実装できず、Again を含む review event と計測可能な発火点を
後継 ADR で定義する必要がある。

### 5. 通知を増やさない告知チャネル（バッジ）が同時に必要である

通知は割り込みであり、総量を増やす施策には抑制チャネルを対にする必要がある。Badging API は
W3C Working Draft で `Navigator` と `WorkerNavigator` の両方に定義され、service worker の push
handler から利用できる（https://www.w3.org/TR/badging/ ）。ただし表示可否は UA / OS に依存し、
iOS Home Screen web app では通知許可が必要である。Android Chrome は API を露出せず通知ドットが
OS 管理、Linux は API が存在してもバッジを表示しない実装があり、ChromeOS も公式文書上の提供状況を
一律に断定できない。したがって「許可プロンプト不要」「Chromium desktop なら全 OS で表示」という
前提は置かず、feature detection と失敗時 no-op を契約にする。

Declarative Web Push の payload には `app_badge` が定義されている。一方、従来引用していた
Modern Web Weekly #54 の Safari 18.5 crash は公開一次資料で再確認できず、WebKit の公式資料は
`app_badge` を正規機能として説明している。D6 の payload 非採用は保守的な選択として維持できるが、
クラッシュを確定事実として根拠にしない。

## Decision

**FSRS を recall_weight_set の第3世代 `v3_fsrs` として knowledge-sovereign に導入し、期日到来の再想起を新 kind `recall_echo_ready` のトリガー通知（朝夕・件数のみ）とアプリバッジで配送することを採用する。**

### D1. FSRS 記憶状態は sovereign DB に置く

記憶状態（stability / difficulty / due / 最終レビュー時刻）は「ユーザーの記憶の減衰モデル」というナレッジそのものであり、[[000954]] の境界規則に従い knowledge-sovereign の DB に置く。`knowledge_recall_memory` テーブルを新設し（item_key ごと 1 行）、`recall_candidate` の `next_suggest_at` を FSRS の due で駆動する。`weight_set_version` に `v3_fsrs` を追加し、[[000913]] の ScoreBreakdown に FSRS 由来の寄与（stability / retrievability）を 1 行として載せる。既存 v1 / v2 の行は温存する。

### D2. スケジューラは go-fsrs、Optimizer は導入しない（初期）

knowledge-sovereign は Go であり、期日計算は純関数なので新サービスを切らず go-fsrs をライブラリとして組み込む。パラメータ最適化（Optimizer）はレビューログの蓄積を前提とするため初期導入せず、デフォルトパラメータで開始する。将来ログが蓄積した時点で fsrs-rs（crates.io `fsrs` v6.6.1、Optimizer 込み）によるバッチ最適化を別 ADR で検討する。

### D3. rating は knowledge_loop の状態遷移から導出する

明示的な採点 UI は作らない。写像は以下に固定する。

| loop 側の事実 | FSRS rating |
|---|---|
| `dismiss_state = 'internalized'` への遷移 | Good（読み直しなしで卒業した場合は Easy） |
| recall 提示後に該当記事を再読した（dwell 発生） | Hard |
| snooze | rating なし（レビュー延期） |
| `dismissed`（already_known 以外） | カードを recall 対象から除外 |

この写像自体が本 ADR の決定事項であり、変更する場合は supersede する。

### D4. producer は today_entrance_notifier と同型の「outbox なし」パターン

`recall_echo_ready` の enqueue は alt-harvester の新 job `recall_echo_notifier` が行う。`today_entrance_notifier` と同じく、(1) 短い tick と時刻ゲートで朝夕 2 スロットに着地させ、(2) sovereign に新設する RPC（期日到来件数の取得）を読み、(3) `datahub_gateway.PushDeliveryGateway` 経由で enqueue する。ビュー導出かつ日付スロットで dedupe（`recall_echo:<user_id>:<date>:<slot>`）できるため、producer 側 outbox は不要である — これは `push_deliveries` マイグレーションが定義した「業務事実に紐づく producer は自 DB に outbox を持つ / ビュー導出の日次トリガーは dedupe で自己修復する」の後者に該当する。payload は kind / url / count のみとし、既存原則（通知はトリガーでありコンテンツを運ばない）を維持する。TTL はスロット間隔（12 時間）とする。

### D5. スキーマ・proto・UI の拡張

- alt-db: `push_subscriptions` に `recall_echo_ready BOOLEAN NOT NULL DEFAULT TRUE` を追加（既存 4 列と同形）。`push_deliveries.kind` は非制約 TEXT のため変更不要。
- proto: `alt.push.v1.NotificationPreferences` に `bool recall_echo_ready = 5` を追加。
- alt-backend: `domain/push.go` に kind 定数、`render.go` の notificationCopy にコピーを追加（表示不能 payload は汎用コピーに degrade する既存規約に従う）。
- alt-frontend-sv: `preferences.ts` の NOTIFICATION_KINDS / KIND_LABELS / KIND_DESCRIPTIONS に追加。`decideAction` のロジックは kind 非依存のため変更不要。

### D6. バッジは service worker 側の Badging API で設定し、payload の app_badge は使わない

`src/service-worker.ts` の `push` handler（[[000962]] の 4 listener 構成は維持）で、payload の count を `navigator.setAppBadge` に渡す。アプリ起動時（クライアント側）に `clearAppBadge` する。Declarative Web Push envelope への `app_badge` メンバー追加は、Safari 18.5 のクラッシュ報告（Context §5）が実機で解消確認されるまで採用しない。Android Chrome では API 非対応のため、設定画面にその旨を明記する。

### 検討した代替案と却下理由

**(a) Periodic Background Sync による画面内バッジ更新 — 却下。**
Chromium 系限定で Safari / Firefox が非対応、同期タイミングは開発者が制御できずサイトエンゲージメントスコアに依存する（https://developer.chrome.com/docs/capabilities/periodic-background-sync 、https://github.com/web-platform-dx/developer-signals/issues/380 ）。デスクトップと iOS の両方に届ける本件の要件を満たさない。配送は既存の Web Push 経路一本に集約する。

**(b) FSRS Optimizer を初日から導入 — 却下。**
Optimizer はユーザー自身のレビュー履歴への適合であり、履歴ゼロの時点では適合対象が存在しない。デフォルトパラメータで開始し、ログ蓄積後に再検討する（D2）。

**(c) 通知本文に対象記事タイトルを載せる — 却下。**
「通知はトリガーでありコンテンツを運ばない」という現行原則（`push_dispatch_usecase/render.go` の producerPayload 設計）を、本 ADR は変更しない。コンテンツ搭載の是非は [[000973]] の rich preview 節で明示的に扱う。

**(d) 明示的な 4 択採点 UI（Anki 型）の新設 — 却下。**
単一ユーザーの日常操作に採点作業を追加するのは継続コストが高く、knowledge_loop の状態遷移という既存の暗黙的信号で代替できる（D3）。写像の粗さは Optimizer 導入時に再評価する。

## Consequences

### Pros

- recall 基盤の `next_suggest_at` が初めて push 型の意味を持ち、画面を開かない日にも再想起の接点が生まれる。
- 生成 LLM に依存しない完全決定論の機能であり、Knowledge Home / Trail の生成品質の議論（[[000972]] / [[000973]]）と独立に価値が立つ。
- バッジという「通知ゼロ件でも知らせる」チャネルが整備され、以後の kind 追加（[[000973]]）の通知圧を吸収する土台になる。
- 変更はすべて既存パターンの反復（kind 追加・列追加・notifier job 追加）で、新サービス・新プロセスを増やさない。

### Cons / Tradeoffs

- FSRS デフォルトパラメータは Alt の記事再読という題材に最適化されておらず、初期の期日は粗い。D3 の rating 写像も近似であり、精度は Optimizer 導入まで頭打ちになる。
- D3 の入力は現行コードに存在せず、Again 経路もない。後継 ADR なしに実装するとカード状態が更新されないか、観測不能な proxy signal を rating と誤認する。
- `knowledge_recall_memory` を append log から再構築できる projection として定義しない限り、reproject 後の due が再現できず immutable data model を破る。
- `push_subscriptions` の per-kind boolean 列は 5 列目となる。kind がさらに増える場合、列追加方式の限界（マイグレーション頻発）が顕在化する。JSONB 化の検討は kind が 7 を超えた時点の課題として明記しておく。
- Android Chrome ではバッジが機能せず、プラットフォーム間で体験が非対称になる。
- 朝夕 2 スロットの通知は、[[000973]] の Beacon と合算した 1 日の通知総量に予算圧力をかける。予算の一元管理は [[000973]] で扱う。
