# ADR-000968: ディスク掃除を無差別 prune から保護集合方式に変え、到達不能な目標を実行可能な不足報告に置き換える

## Status

Accepted

## Date

2026-08-09

## Affected Services

- `scripts/docker-cleanup.sh`（スタックを動かすホスト上で systemd timer から 30 分ごとに実行）

## Context

### 起きた障害

ある日の稼働中、`knowledge-sovereign` が何らかの理由で停止した。次の掃除が走ったとき、以下の順で復帰不能になった。

1. `docker container prune -f` が停止済みコンテナを削除
2. コンテナが消えたことでその image が未参照になる
3. `docker image prune -a -f` が **`until` フィルタ無し**で走り、その image を削除
4. `restart: unless-stopped` は image が無いので何もできない

サービスは約 70 分停止し、人手で image を再取得するまで戻らなかった。当日そのサービスは変更セットに入っておらず、デプロイによる自動復旧の機会も無かった。

停止の一次原因は特定できていない。ログ転送を持たないサービスだったため、コンテナごと prune された時点で証拠も消えた。**しかし「一瞬の停止」を「70 分の停止」に変換したのは掃除スクリプトである。**

### なぜ prune では表現できないのか

`docker image prune` の語彙は「参照されているか」しかない。「停止中のサービスの image」を除外する述語を持たない。これは設定の誤りではなく、道具の選択の誤りだった。

`docker volume prune -f` も同じ形をしている。停止中コンテナの named volume はアプリケーションのデータであり、ゴミではない。実測では、コンテナを持たない volume の中に別プロジェクトのデータベース volume が含まれていた — 従来の経路はそれを 30 分ごとに削除候補にしていた。

### 目標そのものが到達不能だった

計測すると、上限 100GB に対して使用量は約 114GiB、`RECLAIMABLE` は 0%。内訳は概ね次のとおり。

| 区分 | 規模 |
|---|---|
| 未参照 image + build cache（削除してもデータ損失なし） | 約 260MB |
| コンテナを持たない volume（＝落ちているサービスのデータ） | 約 74MiB |
| 稼働中サービスのデータ volume | 約 45GiB |
| コンテナの writable layer | 約 4.4GiB |
| docker の会計に現れない領域 | 約 37GiB |

**不足 14GiB に対し、安全に解放できるのは 2% 未満。** 旧スクリプトが 30 分ごとに暴れていたのは、到達不能な目標に対して唯一残った刈り取り対象——つまり稼働しているサービスの image——を狙い続けていたからである。「Manual intervention may be required」と出力して exit 1 していたが、何を消せばよいかは何も言っていなかった。

最後の行「docker の会計に現れない約 37GiB」も重要である。`du --apparent-size` はスパースファイルを実使用量より大きく数える。ファイルシステム全体の使用率はこの計測が示唆するほど逼迫していない。**予算メトリクスの定義自体が疑わしい。**

## Decision

**無差別 prune を全廃し、削除前に構築した保護集合に基づく狙い撃ち削除に変える。到達できない目標は、実行可能な不足報告に変える。**

1. `docker image prune -a` / `docker volume prune` / `docker container prune` を使わない。削除は `docker rmi`（`-f` なし）と `docker rm` を対象ごとに呼ぶ形にする。`-f` を付けないのは、こちらの列挙に漏れがあったとき daemon 側が拒否してくれる二重の網を残すため。
2. **削除を始める前に保護集合をスナップショットする。** 状態を問わず全コンテナの image 参照を解決したものを主とし、compose が解決できる image 一覧を補助として加算する。障害の因果が「コンテナを消したから image が未参照になった」だった以上、削除前に確定させれば同一実行内でコンテナを消しても image は対象にならない。
3. **compose が管理するコンテナは状態を問わず削除しない。** 停止中の compose サービスはゴミではなく再起動待ちであり、そのライフサイクルは compose の持ち物である。ラベルを持たない一時コンテナのみ、age フロアを超えた場合に対象とする。
4. **volume の削除は buildx の孤児 state volume に限る。** 名前一致かつ参照コンテナ無しの二条件。それ以外の volume は報告するだけで削除しない。
5. **age フロアをゼロにしない。** 通常 24 時間、超過時 6 時間。pull 直後でまだコンテナの無い image は「進行中のデプロイ」であってゴミではない。
6. 目標未達のときは、到達に必要な削除候補を「データ損失なし → 落ちているサービスのデータ → 稼働中のデータ → コンテナ再作成で戻るもの → docker の会計外」の順位で、累計付きで出力する。30 分ごとの全文出力はログを肥大させるため間隔を空け、通常は 1 行サマリに留める。
7. exit 1 は維持する。未達は未達として鳴らし続ける。

### 検討して採らなかった代替案

- **`docker image prune -a --filter until=N` で妥協する** — age は「使われているか」の代理変数として不正確である。長期間更新されていない安定サービスの image ほど古く、真っ先に消える。障害を起こしたのはまさにその種の image だった。
- **上限を引き上げて済ませる** — 実際に予算メトリクスは疑わしく、引き上げは妥当な選択肢でありうる。しかしそれは掃除の安全性とは独立した判断であり、閾値を動かしても「一瞬止まったサービスの image を消す」経路は残る。閾値の意味を変える判断は運用者のものとして、計測方法には手を触れていない。
- **停止中コンテナを一律で保護する** — compose 管理でない使い捨てコンテナ（テスト用 reaper 等）まで永久に溜まる。compose プロジェクトのラベルで区別できるので、そこで線を引いた。

## Consequences

### Pros

- 一瞬停止したサービスが image を失わなくなった。障害を 70 分に引き伸ばした経路が塞がっている。
- アプリケーションのデータ volume が削除候補に入らなくなった。別プロジェクトのデータベース volume が毎回対象になっていた状態が解消した。
- 未達時の出力が「何を消せば届くか」を答えるようになった。実測では「データ損失のない候補だけでは届かない。閉じるにはデータを消すか上限を上げるしかない」と明示される — これは旧スクリプトが 30 分ごとに隠していた結論である。
- 保護集合を構築できない異常時（コンテナがあるのに集合が空）は image 掃除自体を中止する。無言で全部消しに行かない。
- compose が解決できない場合も、その旨を明示的にログへ出して続行する。無言フォールバックにしない。
- シェルテスト 7 本を追加した。旧実装に対しては 7 本すべて RED になる。

### Cons / Tradeoffs

- **回収量は激減する。** 実測で削除されたのは未参照の補助 image 2 つのみ。これは正しい挙動だが、「掃除が効いている」感覚は失われる。
- **予算未達は解消しない。** exit 1 が続くため systemd 上は失敗表示のままである。鳴らし続けるのが正しいと判断したが、慣れによる無視のリスクはある。
- コンテナも無く compose にも現れない image は削除される。現状では migrator のベース image などが該当し、いずれも再取得で復旧する。
- `docker ps -a` の列挙と `docker rmi` の間に理論上のレースが残る。`-f` を付けないことが最終防衛線である。
- デプロイが「先に image を取得し、数時間後にコンテナを作成する」形に変わると、age フロアを超えた未参照 image が消えうる。現行のデプロイ経路では該当しない。
- **計測方法の疑いは未解決のまま残した。** `du --apparent-size` と docker 自身の会計に大きな乖離があり、スパースファイルが原因である可能性が高いが、確認には特権が要る。上限値の妥当性はこの決着を待つ。

### 運用上の注意

インストール済みの systemd unit は、リポジトリにチェックアウトされたスクリプトを直接指している（リポジトリ内に置かれている unit ファイルの写しは別のパスを指しており、実体と食い違っている）。したがって**このスクリプトへの変更は、コミットやデプロイを経ずに次回の発火から有効になる**。編集した時点で本番の挙動が変わる。unit ファイルの写しと実体の不一致は、いずれ揃えるべき別の課題である。
