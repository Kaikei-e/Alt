# ADR-001001: recap-worker から recap-subworker への認証をクライアント構築時に一元化し、Authorization ヘッダを CDC 契約で固定する

## Status

Proposed

## Date

2026-11-09

## Affected Services

- recap-worker (Rust): `SubworkerClient` の HTTP クライアント構築、401/403 の扱い、Pact consumer テスト
- recap-subworker (Python): provider verification を認証有効の状態で回す

## Context

2026-10-31 のコミット `714e80996` で、recap-subworker の classification / preprocessing / classification_runs / evaluation の各ルーターに `Depends(require_admin_token)` が追加された。embed / story_clustering / verify は以前から認証付きだったので、これで `/v1/*` 配下はすべて認証必須になった。FastAPI では `include_router(..., dependencies=[...])` に渡した依存は、そのルーターの全 path operation に適用される（FastAPI 公式ドキュメント "Bigger Applications" の記述どおり）。

一方 recap-worker の `SubworkerClient` は、リクエストを組み立てる箇所ごとに `authorize(...)` で Authorization ヘッダを付ける方式だった。付けていたのは `admin.rs` と `clustering.rs` だけで、次の呼び出しは無認証のまま送られていた。

- `classification.rs`: coarse 分類の POST、classify-runs の POST、classify-runs の完了待ち GET
- `utils.rs`: 本文抽出（extract）
- `evaluation.rs`: 評価呼び出し

reqwest の `RequestBuilder::header` はそのリクエストにだけ効き、全リクエストに付けるには `ClientBuilder::default_headers` を使う（docs.rs の reqwest リファレンス）。呼び出し箇所ごとに付ける方式では、付け忘れを型やテストで検出できない。認証ヘルパーも、`SubworkerClient` の `authorize`（`subworker.rs`）と `SubworkerCardsClient` の `apply_auth`（`cards.rs`）の 2 つに分かれていた。

provider 側の変更が本番に反映された後、2026-11-04 02:00 (JST) 以降の日次 3 日 Recap バッチ 6 本と Topic Cards 24 試行がすべて 401 で失敗した。この失敗は次の理由で表に出なかった。

- 3 日 Recap では、classify-runs の 401 がジョブ履歴に `classification job … completed with 1 failed chunk(s)` として残り、401 という事実はログの `failed to parse classify-runs response` の文脈にしか出なかった（Topic Cards の履歴には `classify_coarse endpoint error 401 Unauthorized` が残っていた）
- extract の 401 は「ローカル清掃にフォールバック」する WARN だけで処理が続いた（1 回のバッチで約 200 件）
- coarse 分類の失敗はジャンル `other` へのフォールバックとして扱われた
- recap-worker → recap-subworker の Pact consumer テストは、runs・embed・cluster-stories・verify などの interaction では Authorization を要求していた。しかし classify-runs（POST と完了待ち GET）と coarse 分類の interaction では要求しておらず、extract と evaluation には interaction 自体がなかった。provider verification は `require_admin_token` を配線済みだったが、契約に載っていない呼び出しの付け忘れは検出できなかった

認証方式の変更に参照側が追随していなかった、という構図は [[PM-2026-052]] の寄与要因にも挙がっていた。

## Decision

recap-worker から recap-subworker への全リクエストに、クライアント構築時の既定ヘッダとして Authorization を付けることを採用する。あわせて、認証の有無を CDC 契約で固定する。

1. `SubworkerClient` と `SubworkerCardsClient` は、`reqwest::ClientBuilder::default_headers` に Authorization（`HeaderValue::set_sensitive(true)`）を設定してクライアントを作る。呼び出し箇所ごとの `authorize` / `apply_auth` は削除し、ヘルパーを 1 つも残さない
2. トークンの起動時検証は既存のものを維持する（トークンファイルは必須、認証の無効化は `RECAP_ADMIN_AUTH=disabled` の明示値のみ）。そのうえで、subworker 呼び出しの認証状態を起動ログに `subworker_auth_enabled` / `subworker_auth_disabled` として出す
3. recap-worker → recap-subworker の全 Pact interaction で、Authorization ヘッダの存在を matcher で要求する。具体的には、classify-runs（POST と完了待ち GET）と coarse 分類の interaction に要求を加え、extract と evaluation の interaction を新設する。この RED テストを実装より先に入れる。provider verification は引き続き `require_admin_token` が有効な状態で回す
4. recap-subworker からの 401 / 403 は再試行しない致命エラーとしてジョブを失敗させる。本文抽出のローカル清掃フォールバック、coarse 分類の `other` フォールバックは、認証エラーでは発動させない。ジョブ履歴にはエラーの原因チェーン全体（`{:#}`）を残す

### 検討した代替案

- **不足している呼び出し箇所に `authorize` を足すだけ**: 差分は最小だが、今回 3 か所目の取りこぼし（完了待ち GET）を調査中に見つけたように、同じ漏れを繰り返す構造が残る。却下
- **recap-subworker の `/v1/*` 認証を元に戻す**: 内部 API を無認証に戻すことになり、セキュリティ上の後退になる。却下
- **mTLS のピア識別だけで認可し、トークンをやめる**: 認可方式の変更であり、今回の範囲を超える。トークン方式のまま一元化する

## Consequences

### Pros

- 新しいエンドポイントを追加しても、自動的に認証付きで呼ばれる。付け忘れという失敗の形がなくなる
- provider 側の認証変更が、Pact の検証段階で consumer の失敗として表に出る
- 401 がフォールバックに吸収されず、ジョブの失敗理由として残る

### Cons / Tradeoffs

- ヘルスチェックなど認証不要のエンドポイントにも Authorization が付く（害はないが、ヘッダは sensitive 指定で扱う）
- トークンをローテーションするにはクライアントの再構築（プロセス再起動）が要る
- 認証エラーで本文抽出がジョブごと失敗するようになり、部分的な成果物は出なくなる。部分出力より、失敗が見えることを優先する
- Pact interaction の更新が必要になり、contract の content hash が変わる
