# ADR-001028: ハーネスの残存 Python 経路を撤去し単一 Go バイナリとインプロセス並列ゲートへ統一する

## Status

Accepted

## Date

2026-11-24

## Affected Services

- `scripts/altharness` (Go バイナリ・並列メタゲート・フック・検証ツール群)
- `scripts/lint`, `scripts/agent-harness`, `scripts/verify` (ハーネス入口・ラッパ)
- `.codex/hooks.json`, `.agents/hooks.json`, `.claude/hooks/`, `.claude/skills/` (エージェントフックおよびスキル定義)
- `.github/workflows/` (CI 品質ゲートおよび sparse checkout 配線)

## Context

[[001027]] でハーネス検査器を `scripts/altharness`（Go）へ移行した際、移行期互換のため「既存パスに薄い Python ラッパを残す」方針を採った。しかし実運用と監査により、この二層構成が以下の構造的欠陥を生むことが確認された。

1. **二重正本と死蔵テスト（FP-07 / FP-14）**: `scripts/agent-harness/*.py` や `scripts/lint/*.py` に旧 Python 実装と `os.execv` 転送が共存した結果、CI の Python ユニットテストが本番フックでは実行されない死蔵 Python 実装を `import` して通過する一方、実際に本番実行される Go パッケージ 15 個の `go test -race` がゲートに含まれていなかった。
2. **未配線パッケージと残存 Python 経路**: `internal/pyver`・`internal/pki`・`internal/workflow` が移植済みでありながら未配線のまま Python 側が動き続け、さらに `adr_preflight.py`・`run_pytest_randomized.py`・`internal/packet` の関数数計測に `python3` サブプロセス依存が残っていた。
3. **コールドワークツリーと sparse checkout での失敗**: 外部モジュール依存が残る `go.mod` や、`scripts/altharness` を含まない sparse checkout CI ジョブでは、ネットワーク遮断下の独立ワークツリーや CI ランナーで `alt-harness` のビルド・起動が失敗し、Bash フォールバックや `FileNotFoundError` を引き起こした。
4. **サブプロセス多重起動オーバーヘッド**: `meta` ゲートが同一 Go バイナリ内のステップであっても外部プロセスとして起動し直しており、並列化の効果が削がれていた。

以上より、[[001027]] の「既存 `*.py` パスを薄いラッパとして残す」決定を完全に置換し、ハーネス・フック・メタゲート全体から Python 実行経路を撤去する。

## Decision

[[001027]] を置き換え、Alt のエージェントハーネスおよびリポジトリ品質ゲートの実行経路を単一の標準ライブラリ専用 Go バイナリ（`scripts/altharness/alt-harness`）へ完全統一する。

1. **残存 Python ハーネスツールの純 Go 移植と旧 `.py` の削除**:
   - `.claude/skills/adr-preflight/scripts/adr_preflight.py` を `scripts/altharness/internal/preflight`（`alt-harness preflight`）へ、`scripts/verify/run_pytest_randomized.py` を `scripts/altharness/internal/pytestrand`（`alt-harness pytest-rand`）へ 100% 移植する。`preflight --hook` は Claude/Codex の snake_case ペイロードと Antigravity の camelCase ペイロードの双方を受理し、セッション受領証・ワークツリー独立・`docdag` 検証・6000 文字上限トランケーション・終了コード（0 / 1 / 2）を保持する。
   - `internal/packet` の Python 変更関数計測から `python3` サブプロセスを撤去し、純 Go 構造解析へ統一する。
   - 移植済みの旧 Python スクリプト（`scripts/agent-harness/*.py`、`scripts/lint/*.py`、`scripts/verify/run_pytest_randomized.py`、`.claude/skills/adr-preflight/scripts/adr_preflight.py`）および対応する旧 Python テストを削除し、二重正本を構造的に根絶する。
2. **外部依存ゼロの Go モジュールと全パッケージ `-race` テスト**:
   - `scripts/altharness/go.mod` は Go 標準ライブラリのみに依存し、ネットワーク遮断下のコールドワークツリーでも外部ダウンロードなしで確実にビルドできることを不変条件とする。
   - 削除した Python テストの全ケースを `t.Parallel()` 付きの Go テストへ移植し、`go -C scripts/altharness test -race -count=1 ./...` をゲートおよび CI の必須検証とする。
3. **フック・メタゲート・スキルの直接 Go 配線とインプロセス並列実行**:
   - `.codex/hooks.json`、`.agents/hooks.json`、`.claude/hooks/deny-unsafe-commands.sh`、`.agents/rules/rule-ledger.md`、および各スキル・ドキュメントの参照をすべて `./scripts/altharness/alt-harness <subcommand>` へ統一する。
   - `meta` ゲート（`repo` / `harness`）は Go 実装ステップを外部プロセスではなくインプロセス goroutine ワーカープールで並列実行し、決定論的なカタログ順出力と成功キャッシュを維持する。
   - CI の sparse checkout 対象へ `scripts/altharness` を含め、ローカルと CI の実行経路の乖離（FP-07）を解消する。
4. **規則台帳と捕捉率の不変条件維持**:
   - 規則台帳の `max_judgment_rules` ラチェット（現行 6）と失敗コーパス `C-01`..`C-22` の 100% 捕捉率を維持する。
   - `scripts/altharness/bin/` は引き続き生成物として git 管理外に置く。

検討して却下した案:
- **[[001027]] の Python シムラッパを延命する案**: シムとテストの二重正本（FP-14）が残り、`python3` 起動コストとテスト乖離が再発するため却下した。
- **一部ツール（`adr-preflight` 等）のみ Python に残す案**: フック経路に `python3` 依存が残り、単一バイナリ化とインプロセス呼び出しの利点が崩れるため却下した。

## Consequences

### Pros

- フック・`repo` ゲート・`harness` ゲートの実行経路から `python3` 依存がゼロになり、単一 Go バイナリとインプロセス並列実行により起動・検証レイテンシが大幅に短縮される。
- 旧 Python 実装と旧 Python テストを削除することで二重正本（FP-07 / FP-14）が解消され、`go test -race ./...` が本番実行コードそのものを直接検証する。
- `go.mod` の標準ライブラリ専用化と sparse checkout 配線修正により、独立ワークツリー・サンドボックス・CI ランナーのコールドスタート失敗が解消される。

### Cons / Tradeoffs

- 既存の外部手順や手元メモで旧 `python3 scripts/.../*.py` パスを直接叩いていた利用者は `./scripts/altharness/alt-harness <subcommand>` へ切り替える必要がある（ドキュメント・スキル・`CLAUDE.md`・`AGENTS.md` は本変更で一括更新する）。
- `alt-harness pytest-rand` 自体は対象 Python サービスの `pytest` ランナーを起動する責務を持つため、テスト対象サービスの実行環境（`uv` / `pytest`）への依存は引き続き対象サービス側に残る。
