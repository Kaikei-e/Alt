# ADR-000954: alt-backend を alt-backend / alt-harvester / alt-data-hub の3プロセスへ分割し alt-db 所有を data-hub に閉じる

## Status

Accepted（設計決定として確定。実装は Wave 0〜4 として後続。本 ADR 単体ではコード・compose の変更を含まない）

## Date

2026-07-31

## Affected Services

- alt-backend (Go)
- alt-harvester (Go, 新設)
- alt-data-hub (Go, 新設)
- proto (`alt.datahub.v1` 新設)
- pre-processor (Go) / search-indexer (Go) / tag-generator (Python) / rag-orchestrator (Go) / recap-worker (Rust) / alt-butterfly-facade (Go) / auth-hub (Go) — Wave 2 の peer 付け替え対象
- altctl (Go) — オペレータリスナー / data-hub peer allowlist の対象
- compose (core.yaml / pki.yaml / logging.yaml / base.yaml)、step-ca (pki)、observability (prometheus)

## Context

### 1. 認証境界が「到達可能性」1 枚に依存している

2026-07-29 に実施した alt-backend 周辺の敵対的レビューが、次の 2 点を指摘した。

- **A-1**: 内部リスナー（`BackendInternalService` / `KnowledgeHomeAdminService` / `AdminMonitorService` / `/v1/internal/*` を同居させている平文リスナー）は、アプリケーション層の認証を一切持たない。実運用で閉じているのは compose 側の loopback バインド 1 行だけであり、これは「構成でしか閉じていない」状態である。
- **A-3**: 同じ内部リスナーが mTLS リスナーにも多重化されて serve されている（`buildMTLSHandler` が REST / Connect / internal の全ハンドラを 1 本の mTLS リスナーに束ねる）。つまり境界の実体は「どのネットワークから届くか」だけで決まり、ハンドラ側は呼び出し元を区別していない。

この構造には前科がある。[[000717]] は「network policy に頼るアプローチは defense-in-depth の観点で不十分」と明記して `/v1/internal/*` にアプリ層認証を付けたが、[[000743]] の mTLS 一本化でその層は撤去され、内部リスナーは再び「到達できたら通る」状態に戻った。[[000743]] の判断自体は正しい（shared secret の二元管理は [[PM-2026-025]] 型のサイレント degradation を生む）が、結果として **同じ欠陥クラスが 2 度発生している**。

さらに A-5 が指摘したのは、mTLS があっても解決していない部分である。mTLS のチェーン検証は「この証明書は自分の CA が出したものか」までしか言わない。それは**認証であって認可ではない**。誰が呼んでよいかは peer allowlist が決めるはずだが、allowlist が実質死蔵（未設定でも起動が続行し、loud log は出るが exit しない）であれば、CA が発行した任意の leaf 証明書を持つコンテナが内部 API に到達できる。

構成ミス 1 個（`ports:` の 1 行、env の 1 行）で開く境界は、境界とは呼べない。**プロセス + ネットワーク + mTLS の三重で、構成ミスでは開かない構造的境界へ格上げする**必要がある。

### 2. ファットバックエンドの実測

[[000945]] で `app/{shared,dataplane,orchestrator}` へ package 分割した後の非テスト Go ファイル数は次のとおり。

| package | 非テスト Go ファイル数 |
|---|---|
| `orchestrator/` | 304 |
| `shared/` | 107 |
| `dataplane/` | 13 |

`orchestrator/` の中には、ユーザ向け API のオーケストレーションと、`job/registry.go` の 8 本の定期ジョブ（`hourly-feed-collector` 1h / `daily-scraping-policy` 24h / `outbox-worker` 5s / `ogp-image-warmer` 1h / `og-image-retention` 6h / `og-image-backfill` 30m / `tag-cloud-cache-warmer` 24m / `outbox-prune` 24h）という、**トラフィック特性もスケーリング要求も障害耐性の要求も違うもの**が同居している。5 秒間隔の outbox-worker とユーザリクエストが同じ goroutine スケジューラ・同じ DB コネクションプールを共有している。

### 3. [[000945]] の「measurement-first」基準との関係

[[000945]] は「プロセス分離はスコープ外。今後判断する際は障害相関 / リソース競合 / デプロイ頻度乖離 / スケーリング非対称性を**計測してから**決める（憶測での先行分離はしない）」と明文化した。本 ADR はこの基準を満たしていない — 上記 4 指標の計測データはまだ無い。

しかしここで持ち込むのは**別軸の新事実**である。[[000945]] の 4 指標はすべて「性能・可用性のための分離」を測るものであり、**セキュリティ境界のための分離**を測る指標を含んでいなかった。そして [[000717]] → [[000743]] の回帰実績は、「同一プロセス内で境界をリスナー単位に分けても、次の設計変更で融合し直される」ことの実証である。境界を維持するコストが構成 1 行に依存している限り、回帰は再発する。

## Decision

**alt-backend を、単一 Go モジュール（`module alt`）のまま 3 バイナリ・3 コンテナへ物理分割し、alt-db の所有を `alt-data-hub` 1 プロセスに閉じる。**

### D1. 3 バイナリの分割

| compose service | エントリポイント | 責務 | リスナー |
|---|---|---|---|
| `alt-backend` | `cmd/backend` | ユーザ向け API・BFF が叩く面 | REST `:9000` / Connect `:9101` / loopback オペレータリスナー |
| `alt-harvester` | `cmd/harvester` | `orchestrator/job/` の 8 定期ジョブ | 業務リスナーなし（loopback オペレータリスナーのみ） |
| `alt-data-hub` | `cmd/datahub` | alt-db の唯一のオーナー | **mTLS 専用リスナー 1 本のみ。平文の業務リスナーなし。compose では publish ゼロ** |

root `main.go` は削除し、`cmd/<binary>/main.go` の 3 本に置き換える。共通の起動処理（config ロード・logger・OTel・シグナルハンドリング・supervisor）は `internal/bootstrap` に抽出して 3 バイナリで共有する。

### D2. パッケージ名は据え置き、compose 名との対応表を持つ

[[000945]] が導入した `app/{shared,dataplane,orchestrator}` という**語彙は変更しない**。ディレクトリの一括リネームは 649 ファイル規模の移動を再度発生させる一方、得られるのは名前の一致だけである。代わりに対応表を ADR とサービス README に置く。

| package（[[000945]] の語彙） | 主な移動先バイナリ | 備考 |
|---|---|---|
| `app/dataplane/` | `alt-data-hub` | `connect/internalapi`・`driver/kratos_client`・`gateway/{recap_articles,tag_set_version,fetch_recent_articles}`・`usecase/{recap_articles,create_tag_set_version}` がほぼそのまま data-hub のスライスになる |
| `app/orchestrator/job/` | `alt-harvester` | 8 ジョブ |
| `app/orchestrator/`（job 以外） | `alt-backend` | REST / Connect ハンドラ、worker への fan-out usecase |
| `app/shared/` | 3 バイナリ全部 | Wave 3 完了後、DB に触る部分は data-hub 側にのみ残る |

注意点として、`InternalArticleGateway` は data-hub 側へ移る `BackendInternalService` だけでなく、alt-backend 側の `RecallRailUsecase` からも read port として使われている。「internal と名の付くものは全部 data-hub」という単純化は backend を壊す。

### D3. DB 契約 — ケイパビリティ型 Connect-RPC を採用し、ポートミラー型を棄却する

**alt-data-hub が alt-db を独占する。alt-backend / alt-harvester は読み書きとも Connect-RPC 経由で依存する。**

- 新名前空間 `alt.datahub.v1`
- consumer = `alt-backend` / `alt-harvester`（および Wave 2 で既存 7 peer）
- provider = `alt-data-hub`
- 契約は Pact CDC で固定する（Rule 7: producer 側 GREEN の前に CDC RED）

検討した 2 案:

- **案 1（棄却）: ポートミラー型** — 既存の `port` インタフェースのメソッドを 1:1 で RPC に写す。機械的で移行が速い。しかし棚卸しの結果、alt-db 操作 113 件のうち **28 件（25%）が複文トランザクションまたは不変条件を持つ**。内訳は明示的 `Begin/Commit` が 12 件（うち `FOR UPDATE SKIP LOCKED` 1 件 = `ClaimOutboxBatch`、`pg_advisory_xact_lock` 2 件 = summary/tag-set version の supersede）、単文 UPSERT が 9 件、versioning 契約が 5 件、コード上の状態機械が 2 件。port メソッドを 1:1 で RPC 化すると、`Begin` と `Commit` の間が RPC 境界で分断され、これらの不変条件がすべて壊れる。
- **案 2（採用）: ケイパビリティ型** — 「1 RPC = 1 完結した業務操作 = 1 トランザクション境界」で切る。`ClaimOutboxBatch` / `RegisterFeedLink` / `MarkSummaryVersionSuperseded` のように、ロックとコミットが RPC の内側に閉じる。

判断基準はユーザの言葉で **「安易(easy)ではなく、シンプル(simple = 率直)」**。ポートミラー型は「今の形をそのまま持ち上げる」という意味で easy だが、トランザクション境界という本質を破壊する点で simple ではない。

この決定により、[[000241]]（「alt-backend を唯一のデータオーナーに」）は読み替え不要で**完全遵守**になる。[[000241]] が排除したかったのは「複数サービスが同じ DB に直接つなぐ」構造であり、本 ADR はそのオーナー役を alt-backend という名前のプロセスから alt-data-hub という名前のプロセスへ移すだけで、原則自体は強化される（従来 alt-backend 本体は自分では DB に直接つないでいた。Wave 3 完了後はそれも無くなる）。

### D4. 居住規則

> **DB 状態遷移とその不変条件は data-hub へ。外界との対話（外部 HTTP fetch、worker RPC、sovereign / mq-hub クライアント）とフロー編成は呼び出し側に残る。**

| 判定 | data-hub に移す | 呼び出し側に残す |
|---|---|---|
| SQL を発行する | ○ | — |
| `Begin`/`Commit` の境界を決める | ○ | — |
| `ON CONFLICT` / advisory lock / `FOR UPDATE` の不変条件を持つ | ○ | — |
| 外部 HTTP（RSS 取得、og:image スクレイプ、robots.txt） | — | ○ |
| sovereign / mq-hub / rag-orchestrator / search-indexer への RPC | — | ○ |
| キャッシュ TTL / rate limiter / リトライのフロー編成 | — | ○ |
| ページング上限・入力バリデーション（純粋関数） | — | ○（薄い層は両側可） |

**data-hub が独占するのは alt-db だけである。** knowledge-sovereign と mq-hub は既に RPC サービスなので、3 プロセスとも直接呼んでよい。これらを data-hub 経由に押し込めるのは、独占の対象を「DB」から「他サービスへの一切の接続」へ拡大解釈することになり、data-hub を新しいファットサービスに育ててしまう。

### D5. 認証 — data-hub は mTLS 専用リスナー 1 本

3 層で守り、どの 1 層も単独では最後の砦にしない。

| 層 | 実現方法 |
|---|---|
| L1: ホスト到達不能 | compose に `ports:` キーを書かない（**publish ゼロ**）。`scripts/compose-port-audit.py` に「publish 自体が禁止されるサービス」の集合を追加し、CI の門にする |
| L2: ネットワーク上は mTLS のみ | 業務リスナーは in-process mTLS 終端の 1 本のみ。平文リスナーを持たない |
| L3: peer allowlist | `MTLS_CLIENT_AUTH=require_and_verify` 相当を**必須 config 化**し、プロセス内 fail-closed allowlist で peer CN を検証 |

Rule 9（fail-fast startup config）の適用として、`MTLS_CLIENT_AUTH` 相当 / TLS 証明書パス / allowlist が未設定または空なら **exit 1**。現行 alt-backend は未設定時に loud log を出しつつ起動を続行するが、data-hub ではこれを起動失敗に格上げする。「TLS だが peer 検証なし」で立ち上がった data-hub は、mTLS を名乗る平文リスナーと同じである。

allowlist の初期値は 10 主体（既存 7 worker + `alt-backend` + `alt-harvester` + `altctl`）。Rule 8 に従い、allowlist の適用状態は起動時に loud log で出す（何件・どの主体を許可したか）。A-5 の教訓は「chain 検証は認証であって認可ではない」であり、allowlist が実質無効のまま気付かれない状態を構造的に潰す。

mTLS 終端は **cert-only サイドカー + in-process 終端（パターン A）** とする。pki-agent の proxy mode（netns 共有）は、平文アップストリームが同一 netns に必要になり、それが `0.0.0.0` バインドなら同一ネットワークから直接到達できるため、A-1/A-3 と同型の穴を再生産する。加えて [[000782]] の orphan 障害クラスを持ち込む。data-hub は Go なので自前で終端できる。

`X-Service-Token` 復活案は棄却する。[[000743]] が撤去した理由（二元管理の歪み、caller 識別の不整合、Pact 負債）は依然として有効であり、その決定を覆す新事実は本検討で出ていない。今回の問題は「shared secret が無いこと」ではなく「境界がプロセスをまたいでいないこと」である。

### D6. admin サーフェス

- `KnowledgeHomeAdminService`（sovereign 管理オペ）と `AdminMonitorService`（Prometheus 読み）は **alt_db に依存しない**ため alt-backend に残す。loopback バインドのオペレータリスナーに載せ、altctl から到達する。
- これは「到達可能性のみ」の統制が残ることを意味する。ただし**同じリスナーの隣にデータプレーンはもう居ない**。仮にこの面が開いても、漏れるのは運用オペと Prometheus クエリであって、記事本文・ユーザ識別子・全文データではない。admin token の追加は follow-up として明示的に残す（本 ADR では実施しない）。
- `/v1/internal` の REST 2 エンドポイントは data-hub の Connect capability へ吸収し、REST グループごと削除する。これは [[000945]] が「`rest` package 内の非公開ヘルパー共有のため抽出コストが見合わない」として `orchestrator/rest/` に**意図的に残置した残債**の解消にあたる。実呼び出し元は `articles/recent` = rag-orchestrator（capability 化対象）、`system-user` = pre-processor（Kratos 参照のみで alt-db に触らないため capability 化しない）。
- `/metrics` は 3 サービス共通のオペレータリスナーへ移し、Prometheus の scrape job を 3 本化する。

### D7. 契約名前空間は `alt.datahub.v1` へ一本化

3 案（(a) `services.backend.v1` を維持 / (b) `alt.datahub.v1` へ一本化 / (c) 既存維持 + 新規のみ新名前空間）のうち **(b)** を採る。(c) は「どちらに追加すべきか」を capability 追加のたびに判断させる恒久的な分岐を残す。

移行手順:

1. 既存 `services.backend.v1.BackendInternalService` の 24 RPC は、移行期間限定で**新旧両方の名前空間で serve** する
2. **1 peer = 1 PR** で 7 peer を付け替える（Rule 7 に従い各 PR で CDC RED が先）
3. 全 peer 完了後に旧名前空間を削除する

Pact の pacticipant 名は Wave 1 では**据え置く**。pacticipant をリネームすると `can-i-deploy` の検証履歴が断絶し、「初めて検証する組み合わせ」として全部が未検証扱いになる。Wave 2 で二重 publish を挟んで段階的にリネームする。

### D8. 移行順序（5 Wave）

| Wave | 内容 | 終了条件 |
|---|---|---|
| **0** | 本 ADR + step-ca の `pki-agent` provisioner の allowedNames に `alt-harvester` / `alt-data-hub` を追加 | 2 サービス名で leaf 証明書が発行できる（これが無いと sidecar が unhealthy になり depends_on でスタック全体が上がらない） |
| **1** | プロセス分割。`internal/bootstrap` 抽出 → composition root を 3 分割 → `cmd/*` 切り出し → Dockerfile / compose 3 サービス化。**過渡的に 3 プロセスとも alt-db 直結**、`DB_MAX_CONNS` を per-process 再配分 | フルスタック起動 + 3 サービスの health |
| **2** | 7 peer の接続先を `alt.datahub.v1` / alt-data-hub へ付け替え（1 peer = 1 PR、CDC RED first） | 全 peer が data-hub 経由。旧名前空間の serve 停止 |
| **3** | capability 移住（全 113、うち Wave 3 の新規移住 89） | **alt-backend / alt-harvester の env から DB DSN を削除**し、かつ「`alt_db` driver は datahub 以外から import 禁止」の CI ガードが green |
| **4** | ドキュメント・監視整合（Prometheus job 3 本化、Grafana、runbook、サービス README、`docs/services/MICROSERVICES.md`） | 監視ダッシュボードとアラートが 3 サービスを前提に読める |

**Wave 1〜3 の期間、3 プロセスが alt-db に直結する状態はユーザが明示的に承認した過渡状態である。** これは Shared DB アンチパターンの再導入ではなく、strangler パターンの足場である。区別する条件を明文化する:

1. 期限が Wave 3 の終了条件として**機械検証可能な形**で定義されている（env から DSN が消え、CI ガードが import を禁止する）
2. 過渡期に**新しい直結呼び出しを増やさない**（新規 capability は最初から data-hub 側に置く）
3. 直結しているのは alt-backend 由来の 3 プロセスのみで、他サービスは Wave 2 で先に RPC 化される

各 Wave はアウトサイドイン（E2E → CDC → Unit）で進める。

### 依存起動順序

`alt-data-hub` の `depends_on` は `migrate` / `pgbouncer` / `pki-agent-alt-data-hub` の 3 つに限定する。search-indexer / knowledge-sovereign / mq-hub への依存は alt-backend 側に残す。data-hub はスタックの下から支える層であり、上を待たせると `data-hub → search-indexer → (runtime) → data-hub` の起動デッドロックを招く。harvester は最後に立てる（5 秒間隔の outbox-worker が最も攻撃的なリトライャであるため）。

## Consequences

### Pros

- **認証境界が構造になる。** data-hub にはホストへの口が無く、平文の業務リスナーが無く、peer allowlist 未設定では起動しない。[[000717]] → [[000743]] で 2 度発生した「構成 1 行に依存する境界」という欠陥クラスが、compose の 1 行を消した程度では再現しなくなる。
- **fault domain が 3 つに割れる。** [[000945]] が「未達成」と明記した点が解消される。5 秒間隔の outbox-worker が DB プールを枯渇させても、ユーザ向け API と worker 向けデータプレーンは別プロセス・別プールで生き残る。
- **[[000241]] の原則が強化される。** 「唯一のデータオーナー」が、名目上の 1 サービスから、DB DSN を持つ唯一のプロセスという物理的事実になる。Wave 3 の CI ガード（`alt_db` driver の import 禁止）により、原則の遵守がレビュー依存でなくなる。
- **トランザクション境界が契約に現れる。** ケイパビリティ型を採ったことで、`FOR UPDATE SKIP LOCKED` や `pg_advisory_xact_lock` を含む 28 件の不変条件が RPC 1 回の内側に閉じ、proto を読むだけで「ここが 1 トランザクション」と分かる。
- **[[000945]] の意図的残債が 1 件解消する。** `/v1/internal` REST グループが Connect capability へ吸収され、data-plane の入口が `BackendInternalService` 系に一本化される。
- **デプロイ単位が責務に一致する。** 定期ジョブの変更でユーザ向け API を再起動しなくてよくなる。

### Cons / Tradeoffs

- **[[000945]] が定めた measurement-first の基準を、計測ではなくセキュリティ回帰実績で置き換えている。** 障害相関・リソース競合・デプロイ頻度乖離・スケーリング非対称性の 4 指標は依然として未計測である。本 ADR は [[000945]] の package 分割の決定は一切覆さず、**プロセス分離判断の基準のみを差し替える**部分的な上書きであるため、frontmatter の `supersedes` には記載しない（完全置換ではない）。
- **Wave 1〜3 の間、3 プロセスが alt-db に直結する。** 期限と機械検証可能な終了条件を持つ承認済みの過渡状態だが、Wave 3 が長期化すれば実質的な Shared DB に退化しうる。
- **`tag-cloud-cache-warmer` は Wave 1 で一旦廃止する。** このジョブはプロセス内キャッシュを温める前提であり、harvester に移すとキャッシュ先が違うプロセスになって効果がゼロになる。Wave 1 では遅延ウォーム（初回リクエスト時に温める）へ切り替え、Wave 3 で `GetTagCloud` が data-hub に移った時点で RPC 経由ウォームとして復活を検討する。ジョブは 8 本から 7 本になる。
- **`HostRateLimiter` がプロセスローカルのため、外部 API への実効レートが最悪 2 倍になる。** backend と harvester が同一ホストへ独立してリクエストを出しうる。これは Rule 2（5 秒最小間隔）との緊張であり、外部 fetch を harvester に集約する（backend 側は外部 HTTP を持たない）ことを follow-up とする。
- **プロセス数が +2、pki-agent サイドカーが +2、rask log forwarder が +2 で、常駐コンテナが 6 個増える。** 単一マシン前提の制約下でのメモリ・コネクション予算の再配分が必要（`DB_MAX_CONNS` の合計が pgbouncer 上限を超えないこと）。
- **Prometheus / Grafana / アラートの `job="alt-backend"` 前提が壊れる。** Wave 4 で 3 本化するまで、メトリクスが部分的に欠ける期間が生じる。
- **alt-backend のオペレータリスナーは依然として「到達可能性のみ」の統制である。** 露出面は運用オペと Prometheus 読みに縮小したが、admin token の追加は follow-up に残る。
- **Pact pacticipant のリネームを Wave 2 に先送りしたため、Wave 1 の間は「compose 名 = alt-data-hub、pacticipant 名 = alt-backend」というズレが残る。**
- **dev 環境も 3 分割する。** 開発時のコンテナ数が増えるが、dev だけ単一バイナリにすると「dev と prod でプロセス境界が違う」状態になり、Rule 8 が禁じている silent-fallback と同じ罠（ローカルで通ったものが本番で通らない）を作るため採らない。

### Follow-up（本 ADR では実施しない）

- alt-backend オペレータリスナーへの admin token 追加
- 外部 HTTP fetch の harvester 集約（`HostRateLimiter` の実効レート 2 倍問題）
- `tag-cloud-cache-warmer` の RPC 経由ウォームとしての復活（Wave 3 以降）
- `orchestrator` の純粋 proxy エンドポイントの BFF 直行化監査（本プロジェクトのスコープから明示的に除外した後続作業）
- `tenant_repository.go`（351 行、呼び出し元ゼロの死にコード）の削除 — capability 移住の前に済ませる
- `recap-worker` がユーザ向け REST を叩いている経路の調査（分割の観点では異物）

## Deploy-model 整合性セルフチェック

- [x] **新設 compose service が `depends_on` で他 service を gate するか？** — YES。`alt-data-hub` は `migrate`(`service_completed_successfully`) / `pgbouncer`(`service_healthy`) / `pki-agent-alt-data-hub`(`service_healthy`) を gate し、`alt-backend` / `alt-harvester` は `alt-data-hub`(`service_healthy`) を gate する。
  - `service_healthy` 条件（pgbouncer / pki-agent / alt-data-hub）: 依存先が既に running であれば rolling deploy 下でも成立する。ただし **`alt-data-hub` に healthcheck を付け忘れると、`alt-backend` 単体の `up -d --wait --no-deps` が本番でだけ exit 1 する**（`compose-audit.yaml` 冒頭に記録された既知の罠と同型）。`compose-audit.yaml` の healthcheck-invariant job が、新設される `service_healthy` エッジの target に healthcheck が存在することを検証すること。
  - `service_completed_successfully` 条件（`migrate`）: **既存の `alt-backend` と同じ形を踏襲するだけであり、本 ADR は新たな one-shot gate を導入しない**。rolling deploy で単独 `up` する場合に `migrate` が起動されない点は既存と同じ挙動で、スキーマ適用はデプロイ tooling 側の責務として既に扱われている。
- [x] **新設 compose service に `restart: "no"` の one-shot init container を含むか？** — NO。`alt-harvester` / `alt-data-hub` はいずれも常駐サービスであり、両者に付く `pki-agent-*` サイドカーも既存アンカー `x-pki-agent` を継承した常駐プロセス（証明書更新ループ）である。
- [x] **新設名前付き volume を populate する責務はどこにあるか？** — `alt_harvester_certs` / `alt_data_hub_certs` を新設する。populate 責務は常駐サイドカー `pki-agent-alt-harvester` / `pki-agent-alt-data-hub`（既存の `alt_backend_certs` と完全に同じパターン）であり、one-shot init container ではないため rolling 非互換問題には当たらない。読み取り専用でマウントする `pki_trust_bundle` は既存 volume で、その populate 責務（`step-ca-bootstrap`）は本 ADR で変更しない。
- [x] **前提条件（compose 外）**: step-ca の `pki-agent` provisioner の allowedNames に `alt-harvester` / `alt-data-hub` を追加する作業は compose では完結せず、**Wave 0 の先行必須**である。未実施のまま Wave 1 を回すと leaf 証明書が発行できず、サイドカーが unhealthy → `depends_on` でスタック全体が起動しない。この手順は runbook に明文化し、prod host の pre-condition として確認できるようにする。
- 結論: **rolling 互換**（上記 healthcheck 必須の条件付き）。
