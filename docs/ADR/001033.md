# ADR-001033: Acolyte の critic に task-fulfillment gate を入れず、仕様適合の検査は独立した供給経路ができるまで見送る

## Status

Accepted

本 ADR は「実装しない」という決定の記録である。判断の根拠にした下書き実装はマージしていない。

## Date

2026-11-27

## Affected Services

- acolyte-orchestrator（`ReportBrief` と CriticNode。変更しない）

## Context

Acolyte のパイプライン計画には、レポートが依頼の仕様を満たしているかを critic で検査する構想があった。内容は次の 3 点である。

1. `ReportBrief` に `required_sections` / `entity_coverage_threshold` / `title` を足す。
2. CriticNode で、必須セクションの充足、entity の網羅率、title と本文の類似度を検査する。
3. 不合格なら、満たしていない要件を添えて writer に差し戻す。

この構想を下書きとして実装し、実コードに当てて評価した。結果、3 つの検査のうち 2 つは本番で何も検査せず、残る 1 つは正常なレポートを不合格にすることが分かった。

**必須セクションの検査は既存の検査と同じ条件でしか発火しない。** セクションの骨組みは Planner の固定 skeleton が決める（[[000681]]）。`required_sections` を供給できるのはこの skeleton だけで、writer も同じ skeleton の全キーを書く。したがって欠落として検出されるのは「skeleton のどこかの本文が空」の場合だけであり、これは既存の空本文検出（[[000685]] の heuristic、blocking）と同じ条件である。それでも結果には「必須セクションを検査した」と記録されるため、検査したという誤った安心を与える。

**entity の検査は本番で常に skip される。** 新規作成画面が送る scope は topic だけである。entity を指定する呼び出し元が無いので、検査対象が常に空になる。

**title は検査対象の仕様ではなく表示ラベルである。** title は新規作成画面の必須の自由入力で、入力例は「Weekly AI Briefing — April 2026」のような形である。writer が見るのは topic だけで、title は渡されない。本文は日本語で書くよう固定されている。title が主題として使われるのは topic が未入力のときだけで、その場合の主題との関連性は既存の LLM critic が検査している。

**title の検査は正常なレポートを不合格にする。** 下書きの判定関数（title の語彙のうち本文に現れる割合、閾値 0.3）を直接呼んで測った。

- 入力例の title は 0.20 で不合格だった。一致したのは「AI」だけである。
- 評価用データセットにある実在の title 9 件について、主題に沿った合成本文で測ると、5 件が不合格だった。原因は語彙の違い（title は「電気自動車」「サプライチェーン」、本文は「EV」「供給網」）と、本文に現れない語（「分析レポート」「まとめ」、日付）である。
- 「週報」「Report 1」のようなラベル型の title はすべて 0.0 だった。

本文は合成であり、本番レポートの実分布は測っていない。ただし title が writer に渡らない以上、この不一致は構造的に生じる。

**不合格は writer には直せず、コストだけが増える。** 実際の WriterNode と CriticNode を使い、入力と LLM の出力を同一にして、title の閾値だけを変えて比べた。

| | 検査なし | 検査あり（閾値 0.3） |
|---|---|---|
| writer の LLM 呼び出し | 7 回 | 17 回 |
| critic の LLM 呼び出し | 1 回 | 0 回 |
| 結果 | 受理 | 上限まで差し戻した末の強制受理 |

下書きは、検査で不合格になると LLM critic を呼ばずに差し戻す作りだった（既存の heuristic blocking と同じ扱い。[[000673]]）。[[000685]] は LLM critic を補助的な最終手段と位置づけており、heuristic が blocking を出した回に LLM を呼ばないこと自体は既存の設計である。ただし既存の blocking は再生成で直る欠陥（空本文、重複）を対象にしているが、title の不一致や evidence に無い entity の欠落は再生成では直らない。そのため差し戻しは `MAX_REVISIONS`（3）まで回り、関連性と根拠を見る LLM critic が一度も走らないまま、強制受理の印が付いて保存される。

**本番で止める手段も無かった。** 下書きは閾値を設定値にしたが、acolyte-orchestrator の compose 定義は環境変数を個別に列挙しており、新しい設定値は compose を変えない限りコンテナに届かない。

## Decision

**CriticNode に task-fulfillment gate を入れない。`ReportBrief` に `required_sections` / `entity_coverage_threshold` / `title` を足さない。下書き実装はマージしない。**

仕様適合の検査を再び検討するのは、次の条件がすべて満たせるときとする。

1. **検査対象に、Planner と独立した供給元がある。** 利用者が明示的に指定した値（例: 新規作成画面で入力した entity）であり、パイプライン自身が導出した値ではないこと。
2. **比較相手が、writer が実際に見ている情報である。** writer に渡っていない値との一致を要求しない。
3. **差し戻すのは writer が直せる欠落だけである。** 収集済みの evidence にあるのに本文に無いものに限る。直せない欠落は判定に影響させず、記録にとどめる。
4. **LLM critic を省略しない。** 仕様適合の不合格を理由に、内容品質の検査を飛ばさない。
5. **判定に使う閾値は、実レポートで計測した分布から決める。** 設定値として持つなら、compose 経由でコンテナに届くことをテストで確かめる。
6. **検査を適用しなかった場合に、合格として記録しない。**

### 検討した代替案

| 案 | 却下理由 |
|---|---|
| 下書きのまま、既定で有効な blocking の検査として入れる | 上記の計測のとおり。正常なレポートで差し戻しが上限まで回り、LLM critic が走らない |
| 判定に影響させず、title と entity の一致率をログに記録するだけにする | entity は誰も指定しないので値が出ない。title は表示ラベルなので、分布が分かっても次の判断につながらない。使われない計測コードが残る |
| title ではなく topic と本文を比べる | 主題との関連性は LLM critic が既に検査している。語彙ベースの比較は日本語と英語の言い換えを扱えず、同じ誤判定が起きる |
| `required_sections` を skeleton から導出して入れる | 既存の空本文検出と同語反復になる |
| 新規作成画面に entity の入力欄を足し、網羅を検査する | 再検討の条件 1〜3 を満たしうる筋の良い形だが、フロントエンドにまたがる機能追加であり、利用者からの要望や計測に基づく必要性がまだ無い。必要になった時点で別の ADR で決める |

## Consequences

### Pros

- 正常なレポートが誤って差し戻され、LLM 呼び出しと所要時間が増える退行を本番に入れない。
- LLM critic による関連性と根拠の検査が、すべてのレポートで走り続ける。
- 何も検査しないのに「検査済み」と記録される項目を作らない。
- 再検討の条件を明記したので、同じ構想が出たときに同じ失敗を繰り返さずに済む。

### Cons / Tradeoffs

- 「レポートが依頼の仕様を満たしているか」を決定的に検査する仕組みは、引き続き無い。利用者が特定の entity の網羅を期待しても、それを伝える入力も、欠落を検出する手段も無い。
- title と本文の内容が食い違うレポート（例: title は「週報」だが topic は別の主題）は検出されない。現状では title を表示ラベルとして扱う。
- 計測は合成本文と、差し替えた LLM 出力によるものである。本番レポートの実分布と、実 LLM での所要時間の増分は測っていない。
- 評価の過程で、今回の決定とは別の既存の問題が 2 件見つかった。本 ADR では直さない。
  - critic がセクション単位で返す feedback のうち、段落に対応しないものは writer 側で照合に失敗して使われない。既存段落が無いセクションは writer がどのみち全段落を生成するので、失われるのは指示文だけである。
  - 型検査の lint 段は、リポジトリの除外設定にかかる場所に置いた作業ツリーでは対象ファイルが 0 件になり、何も検査しない。
