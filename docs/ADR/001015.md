# ADR-001015: 読書を製品の中心に据え、モバイルから「読む・読ませる・つなげて残す」の順に作り直す

## Status

Accepted

## Date

2026-11-18

## Affected Services

- alt-frontend-sv — モバイル導線の再編、単一記事リーダーの統合、`/today` の新設
- alt-backend — 読書イベントと「今日読む」キューのユースケース追加
- alt-butterfly-facade — 新規読書・キュー関連 RPC の仲介
- knowledge-sovereign — 追記型読書イベントと導出 read model の保持
- alt-harvester — 通知遷移先と取り込み・索引連携の調整
- rag-orchestrator — 索引登録の復旧と記事末つながり提示の支援

## Context

持ち主が 2026-11-18 に定めた製品の目的は「とにかく読むこと、読ませること、読んだ情報が血肉になること」である。「血肉になる」とは、過去に読んだ記事とつながり、情報が構造化・結晶化されることを指す。

2026-11-17 時点の本番データを読み取り専用で計測した結果（直近 15 日の RPC 呼び出し回数）、毎日使われている面は Gallery (`/feeds/visual-preview`) と Swipe (`/feeds/swipe/visual-preview`) だけである。他の面の呼び出し回数は、`GetKnowledgeHome` が 13 回、`GetTrail` が 7 回、`GetThreeDayRecap` が 9 回、`GetTopicCards` が 3 回、`GetLatestLetter` が 4 回、`GetSevenDayRecap` と `GetEveningPulse` が 0 回、Augur の `StreamChat` が 0 回である。

既読操作の間隔は中央値 1.31 秒であり、日常の利用は「読む」ではなく「さばく」になっている。開いた記事は 523〜667 本（数え方で変わる）である。[[000993]] で `/feeds` 起点への整理を進めたものの、現状はリーダーが面ごとに分散し、読了の計測と後続の知識蓄積につながっていない。

## Decision

1. **製品の目的を 3 つに定める。** 「読む」は本文を最後まで読める 1 本のリーダーを整えることとする。「読ませる」は読むと決めた記事が少数だけ手元に残ることとする。「血肉にする」は読んだ記事が過去に読んだ記事とつながり、テーマごとにまとまって残ることとする。今後の機能追加と優先順位はこの 3 つで測る。理由は、目的を固定しないと派生機能が増え続け、日常の読書に戻らないためである。
2. **まずモバイルから形にする。** 主端末は Android の Chrome とする。iOS 固有の欠陥は優先順位の根拠にしない。ただし、iOS Safari 向けの既存の防御（[[000898]]・[[000902]]・[[000962]]）は外さない。理由は、毎日使われている環境へ最短で届けつつ、既存の安定性を維持するためである。
3. **日常の面を整理する。** 日常の面は Gallery と Swipe に置く。Knowledge Home、Knowledge Trail、Augur、Morning Letter、Recap は削除せず、主導線から外して Menu から入る面にする（[[001022]]）。Evening Pulse は廃止する（[[001026]]）。理由は、ほとんど開かれていない面を主導線から外し、日常の動線を集中させるためである。
4. **派生機能の扱いを制限する。** 要約、ダイジェスト、チャットなどの派生機能は、読書を助けるのか読書を置き換えるのかを確かめてから扱う。理由は、本文を読む行為の代替となる出力を増やすと目的から外れるためである。
5. **段階 R0〜R4 に分け、各段階を単独で出せる単位にする。** 各段階と姉妹 ADR の対応は次のとおり定める。R0（計測と止血）は [[001016]]・[[001017]]・[[001018]] とする。R1（リーダーの一本化）は [[001019]] とする。R2（Swipe の左右と「今日読む」）は [[001020]]・[[001021]]・[[001022]] とする。R3（つながりとテーマページ）は [[001023]]・[[001024]] とする。R4（流入の絞り込みと不要な面の削除）は [[001025]]・[[001026]] とする。理由は、段階ごとに検証しながら安全に出荷するためである。
6. **計測を先に置く。** R0 で読書イベントを記録する基盤を新設し（[[001018]]）、7 日以上の基準値を取ってから R1 以降の効果を同じ指標で比べる。指標は、1 日に末尾まで読んだ記事数、開いた記事のうち末尾まで読んだ割合、「今日読む」の消化率と期限切れ率、つながりの判定のうち「つながる」の割合の 4 点とする。理由は、変更の前後で読書行動が改善したかを事実で確かめるためである。
7. **既存の不変条件と開発規律を守る。** イベントは追記のみとし、read model はイベントから再構築できる形にする。フロントエンドは BFF（`alt-butterfly-facade`）経由で通信する。サービス間の producer 配線の前に Pact の失敗テストを置く。テストは外側（E2E）から書く。理由は、データ整合性とサービス間の契約を保ったまま作り直すためである。
8. **正準契約との食い違いはこの ADR 群を正とする。** Knowledge Trail や Knowledge Home の計画文書が定める「日々の入口」「ナビ」「位置づけ」と食い違う箇所は、この ADR 群を正とし、該当する段階の実装時に契約文書を改める。理由は、旧来の設計文書との二重基準で実装判断が揺れるのを防ぐためである。

### 検討した代替案

- **(a) ナビの付け替えだけにとどめる**: 退けた。リーダーが面ごとに別実装のままでは、記事を最後まで読んだかどうかを統一して測れないためである。
- **(b) Knowledge Home を育て続ける**: 退けた。2026-11-17 時点の本番データ計測で 15 日間に 13 回しか呼ばれておらず、日常の読書入口として使われていないためである。
- **(c) 想起クイズや自分の言葉でのメモを先に作る**: 退けた。持ち主の定義する「血肉になる」は「つながり・結晶化」であり、毎回の入力を求める仕組みは 1.31 秒間隔でさばく現状の利用から遠いためである。

## Consequences

### Pros

- すべての設計判断と優先順位を「読む・読ませる・血肉にする」の 3 軸で評価できる。
- R0 で 7 日以上の基準値を先に取るため、R1〜R4 の改善効果を同一指標で比較できる。
- 使われていない既存面を即座に削除せず Menu へ移すため、既存機能への逃げ道を残しつつ主導線を整理できる。

### Cons / Tradeoffs

- 既存の Knowledge Home / Trail の計画文書と方針が一時的に食い違うため、各段階の実装にあわせて契約文書の改訂作業が発生する。
- 7 日以上の基準値収集を待つため、R0 完了から R1 効果判定までに時間差が生じる。
- 各機能の具体的なテーブル定義・RPC 契約・UI 詳細は、この ADR では決めず R0〜R4 の個別 ADR（[[001016]]〜[[001026]]）に委ねる。
- 各計測指標の具体的な合格目標値と、Evening Pulse（[[001026]]）以外の面を将来廃止するかどうかの基準は、この ADR では決めていない。
