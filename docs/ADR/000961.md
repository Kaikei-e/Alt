# ADR-000961: サービス抽出後に旧 DB へ残る孤児テーブルとロールを CI の schema ownership ゲートで検出する

## Status

Accepted

本 ADR は**再発防止機構の決定**である。既知の 8 孤児テーブルの実際の掃除は [[000960]] が扱う。本 ADR はその欠陥クラスを機械検出可能にすることだけを決める。

**実装はまだ存在しない。** 以下に述べるワークフロー・スクリプト・生成物はいずれも本 ADR 時点で 1 行も書かれていない。本 ADR は「何を作るか」を確定させる文書であり、「何が動いているか」を記録する文書ではない。

## Date

2026-08-08

## Affected Services

- migrations-atlas / acolyte-migration-atlas / pre-processor-migration-atlas / knowledge-sovereign / recap-migration-atlas / rag-migration-atlas（Atlas マイグレーションディレクトリ群）
- CI（`.github/workflows/` に新設するゲート）
- db/init/01-create-users.sh, compose/db.yaml（ロール棚卸しの入力）
- pre-processor (Go)（検出できない sub-case の所在として）

## Context

### 1. 欠陥クラス

**サービス抽出でテーブルの居住地を移したあと、旧 DB 側を落とす工程が抜ける。**

新しい DB とその Atlas ディレクトリを作り、サービスを新 DB へ向け、動作確認まで済ませると、その時点で機能的には完成している。旧 DB 側の `DROP TABLE` は誰も待っていない後始末であり、抜けても誰も気づかない。テストは通る。ヘルスチェックは緑になる。旧テーブルはただ静かに残る。

### 2. 既に 2 回起きている

**1 回目: pre-processor 抽出（[[000246]]、accepted 2026-02-15）。** 5 テーブルが alt-db から pre-processor-db へ移った。後追いの drop マイグレーション `migrations-atlas/migrations/20260317000000_drop_pre_processor_legacy_tables.sql` が落としたのは **5 件中 4 件** — `inoreader_articles` / `inoreader_subscriptions` / `sync_state` / `api_usage_tracking` — で、`summarize_job_queue` だけが黙って漏れた。同ファイルのヘッダコメントは "No service queries these tables from alt-db anymore" と述べており、これは列挙された 4 件については真である。そして [[000246]] の Cons #3 は、このリスクを事前に文章で警告していた:

> **Phase 5 未完了**: alt-db にテーブルが残存。DROP TABLE マイグレーションは別途実施が必要

**2 回目: acolyte 抽出（[[000653]]、accepted 2026-04-09）。** `migrations-atlas/migrations/20260409000000_create_acolyte_tables.sql` は `acolyte-migration-atlas/migrations/20260409000000_create_acolyte_tables.sql` と**バイト単位で同一**である。alt-db 側のコピーは一度も落とされていない — **7 件中 0 件**。そしてやはり [[000653]] 自身の Cons が、原因になった道具立ての欠落を書き残していた:

> **Atlas マイグレーションの管理** — acolyte-db は専用 DB だが、Atlas の env 設定に追加する必要がある（今回未実施）

つまり **2 回とも、当事者は問題を認識し、ADR に書き残し、そのうえで実施しなかった。** これは注意力の問題ではない。「後で人がやる」という機構の失敗率が、観測できる範囲で 2/2 だということである。

### 3. 人間のレビューは検出していない — 2026-07-18 の実証

2026-07-18、commit `b3535715e` が `migrations-atlas/migrations/20260718000000_add_report_jobs_run_id_index.sql` を適用し、alt-db の**死んだ** `report_jobs` テーブルに `idx_report_jobs_run_id` を追加した。出自は `docs/review/20260706largerepocodereview.md:1599` に対する機械的な LOW severity 一括対応である。

テーブルが死んでから 3 か月後に、**レビュアも、作成者も、マージも、そのテーブルがそもそもこの DB に存在すべきでないことに気づかなかった。** インデックスの内容自体は正しく、SQL としても正しく、Atlas も正常に適用した。誤っていたのは「どの DB を触っているか」だけであり、そこはレビューの視野に入っていなかった。

これが機械検査を要求する load-bearing な論拠である。文章で警告する機構は 2 回失敗し、コードレビューという機構も 1 回失敗している。

### 4. 実測した現在の状態

2026-08-08 に稼働中の `db` コンテナ（database `alt`）に対して `pg_stat_user_tables` を照会した結果、次の 8 テーブルが **INSERT ゼロ / UPDATE ゼロ / DELETE ゼロ**である。

| テーブル | 由来 | 残存行数 |
|---|---|---|
| `summarize_job_queue` | pre-processor 抽出の漏れ（[[000246]]） | 235 |
| `report_jobs` | acolyte 抽出の漏れ（[[000653]]） | 0 |
| `reports` | 同上 | 0 |
| `report_runs` | 同上 | 0 |
| `report_versions` | 同上 | 0 |
| `report_sections` | 同上 | 0 |
| `report_section_versions` | 同上 | 0 |
| `report_change_items` | 同上 | 0 |

カウンタが生きていることは対照行が証明している — `outbox_events` は 1,229 ins / 17,625 upd / 34,494 del、`articles` は 2,608 ins / 260,592 upd / 105 del。ゼロは「計測されていない」ではなく「書かれていない」である。`summarize_job_queue` の 235 行はマイグレーション前の残渣であり、以後 1 行も動いていない。

### 5. Atlas は現在この問いに答えられない

`migrations-atlas/migrations/schema.hcl` が宣言しているのは **10 テーブル**（`article_summaries` / `article_tags` / `articles` / `favorite_feeds` / `feed_links` / `feed_tags` / `feeds` / `read_status` / `schema_migrations` / `scraping_domains`）だけで、実 DB（`pg_tables`, schema `public`）には **27** ある。宣言スキーマは実態から大きく乖離しており、**「何が存在すべきか」の oracle として現状使えない**。これ自体が直すべき対象の一部である。

したがって `atlas migrate diff` を素直に使う道は、本 ADR の出発点では塞がっている（後述の代替案 (b)）。

### 6. 第 3 の、隣接する孤児クラス — cross-database dead code

`pre-processor/app/repository/stale_pending_cleanup.go:8-34` は `summarize_job_queue` を `article_summaries` と JOIN している。`article_summaries` は **alt-db にしか存在しない**。[[000246]] 以降、このクエリは実行されれば `relation "article_summaries" does not exist` で失敗する。

生き残っている理由は 2 つある。第一に、この 2 メソッドは `SummarizeJobRepository` インターフェース（`pre-processor/app/repository/interfaces.go:50-80`）に載っておらず、呼び出し元が 1 つも無い。第二に、`stale_pending_cleanup_test.go:12-22` がクエリを**実行せず文字列として** assert しているため、テストは永久に緑である。

**DB を覗くだけのゲートはこれを検出しない。** 別種の欠陥として本 ADR に明記しておく。

### 7. さらに漂流しているもの

- ロール `pre_processor_sidecar_user` は `db/init/01-create-users.sh:147-149` と `compose/db.yaml:27-28,36` で今も provisioning されているが、テーブル権限はゼロで、クライアントも存在しない。
- `compose/compose.staging.yaml:970-974` と `:1119-1123` は `alt-backend` / `alt-harvester` に `DB_*` env を渡し続けている。この 2 バイナリには DB ドライバがリンクされていないため読むことができない（[[000954]] / `alt-backend/app/di/import_boundary_test.go`）。本番 compose と矛盾する dead config である。

抽出は「テーブルを移す」だけの操作ではなく、ロール・compose env・コードの三方に残渣を残す。

### 8. このリポジトリが既に信頼しているガードの形

新しい形を発明する必要はない。同型のガードが 3 つ既にあり、いずれも運用されている。

- **`alt-backend/app/di/import_boundary_test.go`** — `go list -deps` に対して `cmd/backend` / `cmd/harvester` が `alt/shared/driver/alt_db` / `pgx/v5` / `pgxpool` を含まないこと、`cmd/datahub` が含むことを assert する。同ファイルの理由付けは本 ADR にそのまま効く:

  > Every softer form of this check has a hole. A grep for `alt_db` misses an import added under an alias. […] What has no hole is the transitive dependency graph of the binary.

  つまり **道具自身の答えを採り、それを再導出しない。** リンカが決める。
- **`.github/workflows/proto-contract.yaml`** の protovis allowlist drift gate — CI で生成物を作り直し、drift で落とす。判定に `git diff --exit-code` ではなく `git status --porcelain` を使うのは、新しく宣言されたサービスが**追跡されていない**ファイルを生み、diff が clean と報告してしまうからである（同ファイルのコメントが明記）。
- **`.github/workflows/services-registry-lint.yaml`** — `services.yaml` に対する同じ形の drift gate。`scripts/regen-service-registry.py --check` を叩くだけ。

Atlas 側の既存インフラも揃っている: `Makefile` の `migrate-hash` / `migrate-status` / `migrate-validate`、および `migrations-atlas/migrations/atlas.hcl` の `destructive.error = true` / `data_depend.error = true`。

## Decision

**各 Atlas マイグレーションディレクトリを CI 内の使い捨て Postgres に replay して得たテーブル集合を「その DB が所有すべきテーブル」の定義とし、ディレクトリ間で同名テーブルが重複したら CI を落とす schema ownership drift gate を採用する。**

### 何を検査するか

新設する `scripts/derive-db-ownership.py`（仮）が、6 つの Atlas ディレクトリ（`migrations-atlas` = `alt_db` / `pre-processor-migration-atlas` = `pre_processor_db` / `acolyte-migration-atlas` = `acolyte_db` / `recap-migration-atlas` / `rag-migration-atlas` / `knowledge-sovereign`）それぞれについて次を行う。

1. **ephemeral Postgres に全マイグレーションを適用し、適用後のテーブル一覧を取得する。** これがその DB の inventory である。
2. **assertion 1（disjointness）** — inventory が互いに素であること。同じテーブル名が 2 つ以上のディレクトリに現れたら、DB 名・テーブル名・両方のディレクトリ名を挙げて exit 非ゼロ。
3. **assertion 2（role）** — `db/init/01-create-users.sh` が作成する各ロールに、`compose/` 配下のいずれかのサービスから利用者が居ること。居ないロールを名指しで落とす。
4. **assertion 3（compose env）** — `import_boundary_test.go` が DB 依存を禁止しているバイナリの compose service に `DB_*` env が渡っていないこと。純粋な静的テキスト照合。
5. 導出した inventory を `.github/generated/db-ownership.yaml` に書き出す。CI は `--check` モードで再生成し、`git status --porcelain` が非空なら落とす（protovis ゲートと同じ理由 — 新規 DB を足したとき生成物が**未追跡**になり、`git diff` は clean を返す）。

### 「期待されるテーブル」はどこから来るか — schema.hcl は使わない

**`schema.hcl` を入力に使わない。** §5 のとおり 10 対 30 で乖離しており oracle として機能しない。代わりに **Atlas 自身の答え、すなわちマイグレーション履歴を適用した結果**を採る。`import_boundary_test.go` が「grep でも DI 検査でもなくリンカが決める」と言うのと同じ構図で、ここでは **Atlas が決める**。

したがって**ブートストラップは不要である。** マイグレーション履歴は既に完全であり、意図の記述としては正しい。それは実測で確かめられる。

6 ディレクトリの `CREATE TABLE` を素朴に grep すると **29 件の名前衝突**が出る。そのうち:

- **16 件**（`knowledge_*` / `recall_*` / `today_digest_view` 系）は knowledge-sovereign 抽出時に `migrations-atlas` 側で正しく `DROP TABLE` されている — **偽陽性**。
- **4 件**（`inoreader_articles` / `inoreader_subscriptions` / `sync_state` / `api_usage_tracking`）は §2 の drop マイグレーションで落ちている — **偽陽性**。
- **1 件**（`for`）はコメント文 "Create table for tracking …" の parse artifact — **偽陽性**。
- 残る **8 件** は `summarize_job_queue` + `report_*` 7 件。

つまり **replay 後の inventory で見ると衝突はちょうど 8 件で、§4 で本番 DB の `pg_stat_user_tables` から独立に得た 8 テーブルと完全に一致する。** 本番 DB に一切触れない静的な oracle が、書き込み実績から得た答えを再現する。これが要件「CI に本番 DB を要求しない」を満たす根拠であり、同時に replay が必須である根拠でもある（grep 版の偽陽性率は 29 件中 21 件）。

副産物として、knowledge-sovereign 抽出は 16 テーブルすべてを drop まで完了しており、**この工程は正しく実施可能である**ことも確かめられた。欠けているのは能力ではなく強制である。

### 実行場所

`.github/workflows/db-ownership-lint.yaml`（新設）。trigger path は `*-migration-atlas/**` / `migrations-atlas/**` / `knowledge-sovereign/migrations/**` / `db/init/**` / `compose/**` / 自分自身。`services-registry-lint.yaml` と同じ形にする。ephemeral Postgres は GitHub Actions の service container で、本番はもちろんステージングにも接続しない。

### `pg_stat_user_tables` は CI に入れない

**書き込み実績シグナルは CI のゲートには入れず、運用レポートとして分離する。** 理由:

1. CI に本番 DB は無く、与えるべきでもない。CI runner に本番 DB 資格情報を渡すのは信頼方向の反転であり、ゲートの可用性を本番 DB の可用性に結びつける。
2. **検出力の観点で不要である。** §「schema.hcl は使わない」で示したとおり、静的 oracle は同じ 8 件を再現した。今回の欠陥クラスに対して `pg_stat` が追加する検出力はゼロだった。
3. `pg_stat_user_tables` のカウンタは統計リセットや再起動で消える。ゲートの入力としては非決定的である。

その代わり `pg_stat` が唯一検出できるものがある — **他 DB に対応物を持たない単独の死蔵テーブル**（衝突が起きないので静的ゲートには見えない）。これは定期的な運用レポートとして扱い、人間が読んで判断する材料にする。**マージゲートには決してしない。**

### 検討した代替案

**(a) 定期的な手動監査 / runbook エントリ — 棄却。** §2 が示すとおり、この機構は既に 2 回失敗している。しかも 2 回とも「ADR の Cons に書き残す」という、手動監査より強い形（永続する文書に、当事者自身が、リスクを明記した）で失敗した。§3 の 2026-07-18 のインデックスは、コードレビューという第 2 の人間機構も同じ穴を通り抜けることを示している。人間の注意を増やす方向の対策は、この欠陥クラスに対して 0/3 である。

**(b) 実 DB に対する `atlas migrate diff` — 棄却（ただし正当な魅力はある）。** 宣言と実態を突き合わせるという意味では最も権威ある方法であり、`migrations-atlas/migrations/atlas.hcl` の lint 設定（`destructive.error = true` / `data_depend.error = true`）とも噛み合う。棄却理由は 2 つ。第一に CI から実 DB への到達性と資格情報を要求し、上記 1. と同じ問題に当たる。第二に、より致命的なことに、**現状 `schema.hcl` は 10 テーブルしか宣言していないので、`migrate diff` は残り 17 テーブルすべてを削除する巨大な destructive diff を出す**。`destructive.error = true` の下ではただエラーになり、孤児 8 件と正常な 9 件を区別しない。`schema.hcl` の実態への再収束は別途行う価値があり、本ゲートが生成する `db-ownership.yaml` はその作業の自然な入力になる。

**(c) 他サービスの Atlas ディレクトリに属するテーブル名を `migrations-atlas/` の新規マイグレーションが名指しすることを禁じる静的 lint — 棄却ではなく、強化して採用。** 発想は正しく、安く、authoring 時点で効き、acolyte ケースも 7 月のインデックスも捕まえる。問題は実装形式である。素朴な文字列照合版は §「schema.hcl は使わない」の実測どおり **29 件中 21 件が偽陽性**（既に drop 済みのテーブルとコメント文）になり、除外リストを人手で持つ羽目になる。除外リストを持つガードは腐る。replay 版は同じ性質を、除外リストなしで、Atlas 自身の答えとして得る。よって (c) は棄却ではなく **replay によって置き換えられた**。

**(d) 何もせず [[000960]] の掃除だけに頼る — 棄却。** [[000960]] は**インスタンス**を直すが**クラス**を直さない。[[000246]] は既に一度、掃除の必要性を明文化したうえで再発を許している。掃除だけを繰り返す戦略の再発率は、観測範囲で 1/1 である。

## Consequences

### Pros

- **2026-07-18 の誤 DB インデックスは authoring 時点で落ちる。** [[000960]] が `report_jobs` を `alt_db` から落とした後、`migrations-atlas` の replay に `report_jobs` は存在しない。`CREATE INDEX idx_report_jobs_run_id ON report_jobs (...)` を含むマイグレーションは replay 段階で `relation "report_jobs" does not exist` として失敗し、PR は緑にならない。これは衝突検出よりも強い形の失敗である（Atlas が適用そのものを拒む）。
- **既知の 2 事例をどちらも捕まえる。** `summarize_job_queue` は `migrations-atlas` と `pre-processor-migration-atlas` の衝突として、`report_*` 7 件は `migrations-atlas` と `acolyte-migration-atlas` の衝突として検出される。後者は 2 ファイルがバイト同一であるため、検出は構造的に保証される。
- **第 2 の真実を作らない。** inventory は生成物であり、手書きの期待値リストではない。`import_boundary_test.go` が「リンカが決める」ことで grep より強くなったのと同じ理由で、このゲートは「Atlas が決める」ことで手書きレジストリより強い。腐る手書き資産が増えない。
- **本番 DB も資格情報も要らない。** CI は ephemeral Postgres だけで完結し、実測でその答えは本番の書き込み実績と一致した。
- **ロールと compose env の残渣も同じ PR で見える。** `pre_processor_sidecar_user`（§7）と staging の `DB_*`（§7）は assertion 2 / 3 に該当する。抽出の残渣を 1 か所で棚卸しできる。
- **`schema.hcl` 再収束の入力ができる。** §5 の 10 対 27 の乖離を直す作業に、機械が導出した DB → テーブル対応表が使える。
- **既存の CI 形状の再利用で済む。** `services-registry-lint.yaml` の `--check` + `git status --porcelain` を写すだけで、新しい CI 概念を導入しない。

### Cons / Tradeoffs

- **cross-database dead code は見えない。** §6 の `pre-processor/app/repository/stale_pending_cleanup.go` はスキーマ上の異常を一切起こさない。参照先 `article_summaries` は alt-db 側に**正しく**存在し、参照元は pre-processor のコードである。しかも `stale_pending_cleanup_test.go` はクエリを文字列として assert するため、テストも緑のままである。**クエリ文字列を assert するテストは、この種のゲートを構造的に無効化する。** 本ゲートはこの sub-case に対して無力であり、別の対策（実際にクエリを実行する統合テスト、または dead メソッドの削除）を要する。
- **単独の死蔵テーブルは見えない。** 対応物が他ディレクトリに無い孤児は衝突を起こさない。これは設計上の盲点であり、それを見る唯一の道具（`pg_stat_user_tables`）を意図的に CI から外した以上、当面は運用レポート経由の人間判断に委ねられる。**盲点を持つことを承知で採る決定である。**
- **Atlas 管理外の DB には届かない。** kratos-db（Kratos 自身のマイグレーション）や ClickHouse（`clickhouse/migrations`）は 6 ディレクトリの外にあり、同じ保証を受けない。
- **除外リストは持たざるを得ないかもしれず、その 1 行 1 行が穴になる。** Atlas 自身の revision テーブルのような bookkeeping が全 DB に現れる場合、除外が要る。現時点の実測では実質的な除外候補はほぼ無いが、将来 2 つの DB が正当に同名テーブルを持つ日が来たら、除外リストが伸び始める。**除外リストが伸びたゲートは、人が読まずに追記する対象になり、やがて迂回される。** 各エントリに個別の理由コメントを強制する以外に、この腐食への安い対策は無い。
- **生成レジストリの drift ゲートは、正当なテーブル追加のたびに発火する。** これは意図した挙動だが、意図したノイズもノイズである。`make` して commit するだけの儀式に堕す危険があり、レビュー時に `db-ownership.yaml` の差分そのものを読むことが実質的な検出契機になる。
- **CI コストが増える。** マイグレーションに触る PR ごとに ephemeral Postgres を起動し、6 ディレクトリ分のマイグレーションを適用する。有界ではあるが無料ではない。
- **[[000960]] が先に入らないとゲートは緑にならない。** 現時点で 8 件の衝突が実在するため、本ゲートを main に入れた瞬間にすべての PR が落ちる。順序は **[[000960]] の掃除 → 本ゲートの追加**で固定する。「暫定的に既知の 8 件を除外リストに入れて先にゲートを入れる」案は採らない — 上記のとおり除外リストは恒久化する性質があり、掃除の動機を奪う。
- **ゲートは drop の是非を判断しない。** 「2 つのディレクトリが同じ名前を主張している」としか言わない。どちらが正しい所有者で、残っているデータをどう扱うかは常に人間の判断である。
- **まだ誰も所有していないテーブルを誤った Atlas ディレクトリに作る**ケースは検出できない。衝突相手が存在しないためである。抽出の**開始時点**ではなく**完了時点**でのみ効くゲートである。

## Deploy-model 整合性セルフチェック

本 ADR が追加するのは CI ワークフロー 1 本、スクリプト 1 本、生成ファイル 1 本のみである。ランタイムのプロセス構成・compose service・volume のいずれも変更しない。CI 内の ephemeral Postgres は GitHub Actions の service container であり、compose service ではない。

- [ ] 新設 compose service が `depends_on` で他 service を gate するか？ — **N/A**（新設 compose service 無し）
- [ ] 新設 compose service に `restart: "no"` の one-shot init container を含むか？ — **N/A**（新設 compose service 無し）
- [ ] 新設名前付き volume を populate する責務はどこにあるか？ — **N/A**（新設 volume 無し）
- 結論: **rolling 互換**。CI のみのゲートであり、per-service rolling deploy model に対する影響はゼロである。なお [[000960]] 側の `DROP TABLE` マイグレーションは実 DB を変更するため、rolling 整合性の検討は同 ADR の責務である。
