# ADR-001004: GitHub Actions を docs-only スキップとツールチェーン固定で高速化し ci-gate を唯一の必須チェックにして失敗の握りつぶしを除去する

## Status

Accepted

## Date

2026-11-10

## Affected Services

- `.github/workflows/` のほぼ全ワークフロー（Go / Python / Rust / Deno / フロントエンドの各サービス CI、reusable workflow、`e2e-playwright.yml`、`proto-contract.yaml`、`docker-build.yaml`、`dispatch-deploy.yaml`、CodeQL）
- `.github/workflows/scripts/`（新設 `ci-gate.py`、`workflow-safety-check.py` とその複製 `scripts/workflow-safety-check.py`）
- `e2e/playwright/`（suite のシャーディング、blob レポート、アプリコンテナログ）
- `alt-frontend-sv/tests/e2e/`（E2E モックバックエンドと flaky spec）
- `scripts/ci/pact-artifacts.py`
- `alt-perf/tests/`（本番ランタイムでの型チェック修正）

## Context

Alt リポジトリの GitHub Actions に、速度・堅牢性・安定性の 3 面で次の問題があった。2026-11-09 に run 履歴とワークフロー定義を調べて確認した。

### 速度

- **docs だけの PR でも全 E2E が走っていた**: `docs/` 配下だけを変える PR でも、`e2e-playwright.yml` が PR と main への push の 2 回走り、1 回あたり約 430〜500 秒かかっていた。`docker-build.yaml` と `dispatch-deploy.yaml` も起動していた。`e2e-playwright.yml` に paths フィルタが無いのは、サービス単位で絞ると共有配線の回帰を見逃すという理由による意図的なものだった。
- **必要のないディスク掃除**: `jlumbroso/free-disk-space` などのディスク掃除が、`proto-contract.yaml` の provider 検証ジョブ（掃除 119〜144 秒に対し検証本体は 6〜32 秒）、`recap-worker.yml`（84〜123 秒）、CodeQL 3 本（35〜91 秒）で毎回走っていた。GitHub-hosted runner は掃除前の時点で 145G 中 86G が空いていた。
- **Rust のカバレッジ**: main への push のたびに `cargo-tarpaulin` をソースからビルドして実行し、300〜420 秒を足していた。Codecov へのアップロードは毎回 `Token required - not valid tokenless upload` で失敗しており、トークンも未登録で、カバレッジは誰にも届いていなかった。
- **キャッシュが効いていない**:
  - Go は `actions/setup-go` に `cache-dependency-path` が無く、リポジトリ直下に `go.sum` が無いため一度もキャッシュが保存されていなかった（`go test -race` 282 秒）。
  - Python の lint / security ジョブは、1〜3 秒の ruff / bandit のために ML 依存の巨大な uv キャッシュを 48〜80 秒かけて復元していた。
- **E2E のクリティカルパス**: 型チェックジョブ（約 61 秒）がマトリクス計画の前に直列で入り、alt-frontend-sv スイートが分割されずに約 398 秒かかっていた。

### 堅牢性

- **main の必須チェックが 0 件**: main 向け ruleset の必須チェックは存在しないチェック名 `completed` を要求したまま無効化されており、ブランチ保護も無かった。`dispatch-deploy.yaml` は CI を待たずに main への push で起動する。
- **govulncheck が全 Go サービスで実質停止していた**: Go ツール（gosec / govulncheck）のキャッシュキーに Go のバージョンが無かった。そのため go1.26 でビルドしたバイナリが go1.27 のモジュールで復元され、`package requires newer Go version go1.27 (application built with go1.26)` でパッケージを読めずに失敗していた。この失敗は `|| true` とダミーの空 SARIF で「検出 0」に化けていた。
- **ツールチェーンが本番と食い違っていた**:
  - Bun は CI で 1.2.14 と `latest` が混在していた（本番イメージは 1.3.12）。
  - Deno は `v2.x` で浮動していた。alt-perf のテストは本番イメージの Deno 2.4.0 では `Buffer` 未 import で型チェックに失敗し、CI だけが 2.9.8 で green になっていた。
  - Python は既定が 3.13 で、全 `pyproject.toml` の `requires-python >=3.14` と食い違っていた。
- **イメージとシークレット**: `pactfoundation/pact-broker:latest` のような未固定のサービスイメージと、読み取りもしない `secrets: inherit` / `id-token: write` が残っていた。
- **何も検査していないワークフロー**:
  - `performance-smoke.yaml`: 起動していないバックエンドに k6 を当て、失敗を `|| echo` で握りつぶしていた。
  - `helm-validation.yml`: 削除済みの k8s パスを監視していた。
  - `codeql.yml`: スタブだった。
  - `frontend-tests.yml`: deprecated だった。
- **自身の変更で起動しないワークフロー**: 多くのサービスワークフローが、自分自身のファイルや呼び出す reusable workflow を paths に含めていなかった。そのため CI の変更そのものが、その PR の CI で検証されていなかった。

### 安定性

- **テストが全部通っても赤になっていた**: E2E の Merge reports ジョブで blob のダウンロードが失敗すると、全スイートが通った run でも赤になっていた（再実行しても再発）。
- **alt-frontend-sv の flaky テスト**: `tag-trail.spec.ts` / `knowledge-trail.spec.ts` が、本番イメージ（Bun）での E2E で断続的に失敗していた。アプリのログはスイートが最終的に失敗したときしか残らず、リトライで通った回の証拠が無かった。
  - 本番イメージで 30 回ずつ（780 テスト、リトライなし）実行して 2 件を再現し、その回のアプリのログに `[internal] HTTP 400` を確認した。
  - 仕組みは次のとおり。`/api/v2` プロキシがブラウザ発の Connect-RPC の本文を chunked のまま E2E モックバックエンドへ流し、モックは本文の到着前に応答していた。Bun の fetch は本文を送り終える前に keep-alive の接続を再利用するため、次の SSR リクエストが Node の HTTP パーサにチャンクとして解釈され、ハンドラに届く前に 400 で拒否されていた。

## Decision

次の変更を採用する。

### 1. ci-gate を唯一の必須チェックにする

`ci-gate.yaml` を追加する。すべての pull_request で走り、PR の head SHA に紐づく他の全 workflow run の完了を待つ。いずれかが failure / timed_out / cancelled / action_required / startup_failure / stale なら fail する。そのうえで、main 向け ruleset の必須チェックを `ci-gate` だけにして有効化する。

- **監視の対象**: check run ではなく workflow run（`GET /repos/{repo}/actions/runs?head_sha=`）を見る。起動に失敗したワークフローは job も check run も作らないため、check run を見ていると `startup_failure` を検出できない。
- **評価の範囲**:
  - 同じワークフロー・同じイベントの run は、最新の 1 本だけを評価する（PR の reopen や手動の再実行で置き換わった古い run を数えない）。
  - ci-gate 自身のワークフローの run はすべて除外する。
  - ほかの run が 1 本も無いうちは PENDING とする。
  - 完了した集合が 2 回連続で同じになるまで SUCCESS を返さない。
- **API の扱い**: ポーリングは 60 秒間隔。レート制限（403 / 429）ではリセット時刻まで待つ。一時的な通信エラーは PENDING として扱い、締め切りまで再試行する。
- **ruleset の設定**:
  - ブランチを最新に保つこと（strict）は要求しない。
  - PR の承認数も要求しない。
  - リポジトリ管理者はバイパスできるようにして、main への直接 push の運用を残す。
  - 必須チェックは GitHub Actions のアプリに紐付け、他のアプリが同名のチェックを出しても満たされないようにする。

### 2. docs-only の変更では重いワークフローを起動しない

`docs/**`、`.claude/**`、`.agents/**`、`**/CLAUDE.md`、`**/AGENTS.md`、`**/README.md` だけの変更では、次のものを起動しない。

- **重いワークフロー**: `e2e-playwright.yml`、`docker-build.yaml`、`dispatch-deploy.yaml` は `paths-ignore` で起動しない。
- **各サービスのワークフロー**: `!**/CLAUDE.md` などの否定パターンで除外する。ただし `README.md` がビルド入力になっている recap-subworker（`pyproject.toml` の `readme` と Dockerfile の COPY）は除外しない。

`e2e-playwright.yml` のサービス単位の paths フィルタ無しは維持する。docs-only の例外は、イメージ・fixture・テストのどれにも入らないファイルに限る。

### 3. 失敗の握りつぶしと誰にも届かない処理を除去する

- **govulncheck**: ツールのエラーや空の SARIF で job を失敗させる。検出結果はこれまでどおり code scanning へ送り、ブロックはしない。ツールキャッシュのキーには、解決済みの Go バージョンを含める。
- **Rust のカバレッジ**: tarpaulin と Codecov アップロードを削除する。
- **何も検査していないワークフロー 4 本**: `performance-smoke.yaml`、`helm-validation.yml`、`codeql.yml`、`frontend-tests.yml` を削除する。
- **E2E のレポート統合**: blob のダウンロードを `gh run download` で行い、ダウンロードや統合が失敗しても警告とジョブサマリーに留める。テストの成否は新設の verdict ジョブで判定し、どれか 1 つでも失敗・キャンセルなら run を赤にする。

### 4. ツールチェーンとイメージを本番に揃えて固定する

- **言語ランタイム**:
  - Bun は本番イメージと同じ 1.3.12。
  - Rust は各 crate の `rust-toolchain.toml` を読む。
  - Python は 3.14。
  - Deno は各サービスの Dockerfile の版を caller が明示し、input を必須にする。
  - Go は `go.mod` から読む。
- **イメージ**: サービスコンテナ・ジョブコンテナ（pact-broker、postgres、Playwright）と actionlint を digest で固定する。
- **権限**: 使っていない `secrets: inherit` / `id-token: write` を外す。

### 5. 根拠の無いディスク掃除を外す

provider 検証ジョブ、recap-worker、CodeQL 3 本の `free-disk-space` 系ステップを削除する。

これは [[000762]] の Decision のうち、ディスク枯渇対策の一部を改める変更になる。[[000762]] が対処したディスク枯渇は、分割前の単一ジョブで 4 つの Python サービスが CUDA wheel を順に同期していたことで起きた。現在の分割後のジョブは CPU 版 torch を使っており、runner は掃除前の時点で 86G 空いている。

### 6. キャッシュを効かせる

- **Go**:
  - `setup-go` にモジュールの `go.sum` を `cache-dependency-path` として渡す。
  - `reusable-test-go.yaml` の `-race` テストは、`setup-go` の組み込みキャッシュをやめる（同じキーを quality ジョブが先に保存してしまうため）。代わりに GOCACHE / GOMODCACHE を独自キーで restore し、main への push のときだけ save する。
- **Python**: lint / security ジョブは、lockfile に固定された dev グループだけを入れ、`uv run --no-sync` で実行する。

### 7. E2E のクリティカルパスを短くする

- マトリクス計画と各スイートを、型チェックの完了を待たずに開始する。型チェックの失敗は verdict ジョブで run を赤にする。
- alt-frontend-sv スイートを 3 分割し、blob レポートを出して統合レポートに含める。

### 8. ワークフロー自体の不変条件を機械的に検査する

`workflow-safety-check.py` に次のルールを追加する。

| ルール | 内容 |
| --- | --- |
| 9 | job コンテナとサービスコンテナのイメージを digest 固定にする |
| 10 | reusable workflow の呼び出し以外の全 job に `timeout-minutes` を付ける |
| 11 | paths フィルタを持つワークフローは、自身のファイルと呼び出す reusable workflow を必ず含める |

あわせて、`workflow-safety-lint.yaml` を全 PR で実行し、ルールの単体テストと actionlint（shellcheck 連携なし）も回す。

### 9. alt-frontend-sv E2E のモックの keep-alive 競合を直し、証拠を常に残す

- **モックの修正**: E2E モックバックエンドは、リクエスト本文を読み切ってから応答する。ハンドラの例外はログに出して 500 を返し、unhandled rejection にしない。
- **本番コードは変えない**: 本番プロキシは変更しない。モック側の修正だけで 780 テスト中 0 件失敗になった。本番の上流である Go の `net/http` は、本文を読み残した応答の前に読み捨てるか接続を閉じるため、同じ競合は起きない。
- **証拠を残す**: E2E の各 suite / shard で、アプリコンテナのログを毎回 artifact として残す。

### 却下した代替案

- **各ワークフローを必須チェックにする**: paths フィルタで起動しなかったワークフローは結果を返さない。そのため、関係のない PR が永久に「待機中」で止まる。
- **単一のオーケストレータワークフローに全サービス CI を集約し、変更検出で reusable workflow を呼び分ける**: 必須チェックの問題は解けるが、40 本超のワークフローの構造変更になり、影響範囲が大きい。ci-gate は既存ワークフローを変えずに同じ保証を得られる。
- **ci-gate で check run を監視する**: 起動失敗のワークフローを見落とす（Decision 1）。
- **E2E にサービス単位の paths フィルタを入れる**: 共有配線（compose、fixture、上流パッケージ、proto）の回帰が、どのサービスのパスにも当たらずに green で入る。docs-only の除外に留める。
- **カバレッジを維持して Codecov トークンを登録する**: 現状、誰もカバレッジを参照していない。必要になった時点で、Go と揃えて再導入する。
- **flaky テストを Playwright のリトライやタイムアウト延長で吸収する**: 実際にテストが SSR の失敗を見ている以上、吸収すると検出すべき失敗まで隠す。

## Consequences

### Pros

- **docs-only の PR**: `e2e-playwright.yml`・`docker-build.yaml`・`dispatch-deploy.yaml` が走らなくなった。
- **計測値**:
  - E2E は PR #299（キャッシュなしの初回）で 388 秒、PR #300 で 282 秒になった（従来は 430〜500 秒）。
  - Python の lint / security ジョブは 9〜13 秒になった（従来は 48〜80 秒）。
  - alt-frontend-sv の各シャードは 2〜2.5 分。
- **govulncheck**: 実際に全 Go モジュールのパッケージを読み込んで走るようになった（go1.27 で読み込みエラーなし）。
- **安定性**: PR #300 の E2E は 1549 テスト全通過で、flaky は 0 件だった（#299 では tag-trail が 1 件 flaky）。リトライで通った回もアプリのログが残るので、今後の flaky は証拠つきで調べられる。
- **main への入口**: PR 経由で main に入る変更は、起動失敗を含むすべてのワークフローの成功を経ないとマージできない。
- **静的検査**: ワークフロー変更の誤り（イメージの未固定、タイムアウトの欠落、自己トリガーの欠落、構文エラー）は、workflow-safety-lint が PR ごとに検出する。

### Cons / Tradeoffs

- **ci-gate の待ち時間**: PR ごとに runner を 1 台、最長約 85 分占有する。完了は一番遅いワークフローで決まる（CodeQL Go が約 10 分）。
- **ci-gate の再実行**: 失敗した job を再実行したときは、ci-gate も手動で再実行する必要がある。
- **管理者のバイパス**: 管理者は ruleset をバイパスできる。そのため、main への直接 push は ci-gate を経ない。
- **digest の更新**: digest で固定したコンテナイメージは Dependabot（github-actions）では更新されないので、タグと一緒に手で更新する。
- **バージョンの二重管理**: Bun の版は Dockerfile とワークフロー 3 本に重複しており、ずれを検出する仕組みはまだない。
- **docs-only 除外の前提**: `README.md` などがビルド入力にならないことを前提にしている。前提が崩れるファイルは除外から外す（現状は recap-subworker のみ）。ビルド入力の README を削除する変更は、次にそのサービスをビルドするまで検出されない。
- **ディスク掃除の撤去**: CUDA 版の wheel が依存に戻ると、ディスク枯渇が再発しうる（[[000762]] の当初の状況）。
- **キャッシュ使用量**: リポジトリのキャッシュ使用量は約 23GB ある。Go の `-race` キャッシュは main 保存に限定したが、上限に近づくと他のキャッシュが追い出される。
- **保持期間**: artifact とログはリポジトリ上限の 3 日で消える。flaky の証拠もそれまでに回収する必要がある。
