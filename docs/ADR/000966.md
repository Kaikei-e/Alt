# ADR-000966: reproject / backfill の executor 不在を起動ログと FAILED_PRECONDITION で露出させる

## Status

Accepted

## Date

2026-08-09

## Affected Services

- alt-backend (Go)

## Context

### 観測された症状

operator が Knowledge Home の admin UI から reproject を dry-run で起動した。UI はエラーを出さず、`knowledge_reproject_runs` に行が入り、`status='pending'` / `started_at=NULL` / `stats_json='{}'` のまま 30 分以上動かなかった。UI は `pending` を正直にグレー表示し続けるが、`Compare` / `Swap` は `swappable` でないと押せないため、そこから先へ進む手段が無い。

CLI（`altctl home reproject start`）も同じ RPC を叩くので同じ結果になる。分岐点は BFF の手前だけで、`StartReproject` 以降の経路は完全に共通だった。

### 原因

**run 行を作る control plane は残っているが、それを進める executor が存在しない。**

- [[000421]]（2026-03-18、accepted、leaf）が reproject の実行機構を決めている: 「`StartReproject` → `pending` で INSERT → **background job が pending を拾い `running` に遷移しイベントを投影** → `swappable`」。`knowledge-reproject` ジョブを 30 秒間隔で JobScheduler に登録する、と明記している。
- [[000944]]（2026-07-15、accepted、leaf）が projector を knowledge-sovereign へ re-own する際、`job/registry.go` から 5 ジョブ登録（`knowledge-backfill` / `summary-narrative-backfill` / `knowledge-reproject` / `recall-projector` / `digest-availability-reconcile`）を削除した。§Decision 2 で sovereign に新設したのは `knowledge_home_projector` usecase **のみ**で、**reproject / backfill executor の移管先を一切規定していない**。

結果として、拘束力のある ADR 2 本が矛盾したまま両立している。000421 は executor の存在を前提とし、000944 はそれを削除して行き先を書かなかった。

re-own 自体は部分的に成功している。常駐 projector（home / trail）は sovereign へ移り、現に稼働している。移らなかったのは管理系の one-shot executor だけである。

### 状態機械の穴

`domain.ReprojectStatus*` は `pending → running → validating → swappable → swapped` を定義するが、現在のコードでは:

- `pending` を書くのは `StartReproject` のみ
- `running` を書くコードは**本番に 1 箇所も無い**
- `validating` を書くのは**ユニットテストのみ**（executor が実装された 2026-03 当初から本番 writer が存在しない dead state）
- `CompareReproject` は `validating` / `swappable` 以外を拒否する

つまり `pending` から先へ進む経路が無く、runbook `docs/runbooks/knowledge-home-reproject-operations.md` の Step 2「wait for Swappable」以降は現在のコードでは到達不能である。

### 実害の範囲

同じ形が backfill にもある。`StartBackfill` も `pending` 行を作って返すだけで、`knowledge_backfill_jobs` は 2026-03-17 の `completed` 1 件を最後に増えていない。`PauseBackfill` / `ResumeBackfill` は「動いていない仕事」を操作する。

過去の成功例は executor が生きていた時期のものである。`knowledge_reproject_runs` の 9 件の完了 run（2026-03-18 〜 2026-04-30）はすべて `created_at` → `started_at` のラグが 4〜27 秒で、30 秒 tick のポーラーが次の tick で拾った挙動と一致する。現在 active な projection version は v7（2026-04-30 に activate）で、v8 は今回の `StartReproject` が作った inactive 行として残っている。

### なぜ気付けなかったか

`StartReproject` は成功を返し、行も作られる。observability 側にも痕跡が無い: admin RPC は 1 行もログを出さず（同時間帯に alt-backend は 91 行ログしている）、`http_logs` テーブルは全期間 0 行である。operator から見て「何も起きていない」ことを知る手段が無かった。

これは Critical Rule 8 / [[000928]] が対象とする失敗そのものである。sovereign の `main.go` は home projector・trail projector・branch planner のそれぞれに `*.wiring` 起動ログを出しており、コメントには「missing projector が意図的な無効化と区別できなくならないように」とある。reproject executor の不在は、まさにその防御が適用されていなかった箇所だった。

## Decision

**executor の再実装は本 ADR のスコープ外とし、能力の欠落を沈黙から明示に変える。**

1. `knowledge_reproject_usecase.Usecase` / `knowledge_backfill_usecase.Usecase` に **executor の宣言**を導入する。`WithExecutor(name string)` で明示的に宣言し、未宣言なら `StartReproject` / `StartBackfill` は **行を作らずに** `ErrNoReprojectExecutor` / `ErrNoBackfillExecutor` を返す。
2. executor の有無は **port の nil 判定から推論しない**。port はすべて生きており、その存在は「仕事が実際に行われるか」について何も語らないためである。Rule 9 の「無効は明示的な設定値であって、未設定からの推論ではない」に従う。
3. executor 判定を**引数バリデーションより先**に置く。mode が不正だと言われた operator は mode を直しに行き、executor が消えていることを学ばない。
4. admin handler は `ErrNo*Executor` を **`FAILED_PRECONDITION`** に写像する。`INTERNAL` は一過性の障害と読めてしまい、成功し得ない再試行を誘う。
5. composition root が起動時に `knowledge.reproject.executor.wiring` / `knowledge.backfill.executor.wiring` を **`enabled=false` と理由付きで**出す。operator がボタンを押す前に状態が見える。

### 検討した代替案

- **executor を knowledge-sovereign に実装する（re-own の完遂）** — 000944 の commit message は「reproject … now run inside knowledge-sovereign」と主張しているが、ADR 本文にもコードにも裏付けが無い。加えて sovereign の `knowledge_home_projector.RunBatch` は常に active version で fold し、target/shadow version へ fold する経路が存在しない（コード中のコメントが「reproject/backfill caller may instead pass an explicit target version」と書いているが、その caller は無い）。executor を戻すには shadow version fold の新設が要り、これは独立した設計判断である。能力を沈黙のまま放置するより先に、欠落を可視化する方が小さく確実である。
- **versioned reproject 機構ごと退役する** — より新しい `docs/runbooks/knowledge-trail-reproject.md`（2026-07-18）は `TRUNCATE` + checkpoint 巻き戻しで常駐 projector に再 fold させる方式を採っており、現に機能している。versioned swap 機構は 2026-04-30 以降使われていない。退役は妥当な選択肢だが、`knowledge_reproject_runs` / CLI / UI / 6 つの RPC の撤去を伴い、000421 を supersede する判断になる。本 ADR では選ばない。
- **`panic` する** — `.claude/rules/di-wiring.md` は未配線分岐に panic を求めるが、それは producer / projector / resolver の business code を対象とする。operator が押すボタンで panic するとサービスが落ち、押した者が全体を止められることになる。境界での明示的エラーの方が適切と判断した。
- **現状維持のまま runbook に注記** — prose は advisory であり、実行時には何も強制しない。同じ operator が同じボタンを押す。

## Consequences

### Pros

- reproject / backfill を要求した瞬間に、能力が無いことが名前付きで返る。`pending` を眺めて待つ時間が無くなる。
- 進まない run 行・job 行がこれ以上増えない。今回の v8 のような孤児 version 行も作られない。
- 起動ログが「executor 未配線」を宣言するので、ボタンを押す前に状態が分かる。sovereign の projector 群と同じ Rule 8 の作法に揃った。
- executor を再実装する側は `WithExecutor` を呼ぶだけで有効化でき、宣言が明示的なので「配線したつもり」が起こらない。
- [[000421]] と [[000944]] の矛盾が記録として残り、次に触る人が両方読まずに片方だけで判断する事故を防げる。

### Cons / Tradeoffs

- **reproject / backfill は依然として実行できない。** 本 ADR は能力を回復しない。正直な失敗に変えるだけである。回復するには上記の代替案 1 か 2 を選ぶ判断が要る。
- `dry_run` を含むすべての mode が拒否される。プレビューだけしたい operator にも回避策が無い。
- UI と CLI は `FAILED_PRECONDITION` を受け取るが、文言をそのまま出すだけで、操作者向けの導線（「この機能は現在無効です」の説明）は整備していない。
- 既存の `pending` 行（v8 の run と、対応する inactive な projection version 行）は残る。掃除は運用側の判断であり、本変更は触れない。
- runbook `knowledge-home-reproject-operations.md` は到達不能な手順を書いたまま現役扱いで残る。superseded マークも注記も本 ADR では入れていない。
- `validating` は依然として writer の無い dead state のままである。
