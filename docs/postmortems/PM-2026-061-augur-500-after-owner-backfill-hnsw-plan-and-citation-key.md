## サマリー

2026-11-07、PM-2026-060 の対策として本番の `rag_documents` に所有者（`user_id`）を埋める一回限りの owner backfill を実行した。その直後から、Ask Augur の 1 ターンが約 3 分かかり、ブラウザには「500」が表示されるようになった。原因は、同じデータ分布の変化で表に出た 2 つの潜在欠陥である。

1. **サーバ:** 所有者で絞るベクトル検索の 2 キー結合をプランナが 1 行と誤推定し、HNSW index を使わずに全 chunk との距離を計算していた。1 回約 50 秒の検索が 1 ターンに 3 回走った。
2. **クライアント:** CitationRail が `{#each}` の key を `cite.RefID || cite.URL` で作っていた。同じ記事の複数 chunk を引用した回答で key が衝突し、Svelte の `each_key_duplicate` を SvelteKit が status 500 として描画した。

サーバ側は PR #287 で 17:52 に解消し、ターンは約 12 秒に戻った。クライアント側の修正は commit 済みだが未デプロイで、500 は継続している。サーバの全層が成功ログを出しており、クライアントのエラーはブラウザの console にしか出ないため、2 つ目の原因の特定はサーバ修正のデプロイ後まで遅れた。

## 影響

- **影響を受けたサービス:** rag-orchestrator（ベクトル検索 3 経路）、rag-db（plan のみ。スキーマ・データは無傷）、alt-frontend-sv（Augur の回答画面）
- **影響を受けたユーザー数/割合:** backfill 後に Augur を使った全ユーザー。backfill 後の Augur ターンは、確認できた範囲ですべて両方の影響を受けた
- **機能への影響:**
  - **レイテンシ（15:36〜17:52）:** 1 ターンが約 3 分（15:36:13 → 15:39:11）。内訳は、元クエリのベクトル検索 51.7 s、展開クエリの並列ベクトル検索 56.3 s、回答後の related citations の近傍検索 53.3 s。修正後は同じ並列検索が 0.7 s、retrieval 全体が 6.5 s、ターン全体が約 12 s
  - **回答画面の 500（15:38〜継続中）:** 引用（または related citations）に同じ記事の chunk が複数含まれる回答で、CitationRail の描画が `each_key_duplicate` で落ち、SvelteKit のエラー画面（status 500）になる。backfill 後の回答はいずれもこの条件に該当した。会話を開き直しても、同じ引用で CitationRail を描画するため再びクラッシュする（推定）
  - **影響を受けなかった機能:** 記事取り込み、要約、検索インデックス、Knowledge Home などの Augur 以外の機能
- **データ損失:** なし。回答は `augur_messages` に保存されており、サーバ側のストリームも正常完了していた
- **SLO/SLA違反:** 判定不能。Augur のターン所要時間と、クライアント側の描画エラーに対する SLI/アラートが存在しない

## 検知

- **検知方法:** ユーザー報告（サーバ側）、ユーザーによるブラウザ console の共有（クライアント側）
- **検知までの時間 (TTD):** 約 7 分（15:36 の最初の影響ターン → 15:43 の報告）。クライアント側の原因は、最初のクラッシュ（15:38 推定）から特定（17:57 頃）まで約 2 時間 20 分
- **検知の評価:**
  - 3 分かかるターンにも、ベクトル検索 1 回 50 秒にも、アラートは無かった。`AugurDocumentOwnerCoverageLow` は所有者カバレッジだけを見ており、レイテンシは監視対象外だった
  - `handleClientError` はエラーを `console.error` に JSON で出すだけで、サーバ側のログ・ClickHouse・アラートには届かない。ブラウザで「500」と表示されても、サーバ側では全層が成功ログになる。このため、最初の調査は「レイテンシが 500 を起こした」という仮説から抜けられず、500 を出した層は未確認のまま残った
  - 同じ key 重複を含む回答は 2026-08〜10 にも保存されており、同じクラッシュはそれ以前から潜在的に起きていたと推定される。クライアント側のエラーが観測できないため、その時点では誰も気付けなかった

## 根本原因分析

### 直接原因

- **サーバ:** 旧 SQL `rag_chunks JOIN rag_document_versions JOIN rag_documents WHERE d.current_version_id = v.id AND d.user_id = $owner ORDER BY c.embedding <=> $q LIMIT n` で、プランナが 2 キー結合の行数を 1 行と推定し、HNSW index（`rag_chunks_embedding_idx`）を使わない plan を選んだ。所有者の付いた文書が大半になった時点で、全 chunk の距離計算になった
- **クライアント:** `CitationRail.svelte` の `{#each citations as cite, i (cite.RefID || cite.URL || ...)}`（related citations も同形）。同じ記事の複数 chunk は `RefID` も URL も同じなので key が重複する

### Five Whys

**サーバ（レイテンシ）**

1. **なぜ 1 ターンが約 3 分かかったか？** → 1 ターンで 3 回走るベクトル検索が、それぞれ約 50 秒かかったから
2. **なぜ検索が 50 秒かかったか？** → HNSW index を使わず、所有者条件を満たす全 chunk との距離を計算して並べる plan だったから
3. **なぜその plan になったか？** → `v.document_id = d.id` と `d.current_version_id = v.id` という相関した 2 キー結合の行数を、プランナが 1 行と見積もったから。拡張統計はテーブルをまたぐ相関を扱えない
4. **なぜ backfill の前は問題にならなかったか？** → 所有者付きの文書がほとんどなく、同じ plan でも結合の段階で候補が尽きて速かったから。SQL は変わらず、データ分布だけが変わって plan のコストが爆発した
5. **なぜデプロイ前・backfill 後に気付けなかったか？** → SQL のテストは文字列の形しか見ず、plan をデータ分布に対して検証する仕組みがなかった。backfill の完了確認はカバレッジの数値だけで、Augur を実際に 1 ターン流して所要時間を見る手順がなかった

**クライアント（500）**

1. **なぜ画面が 500 になったか？** → CitationRail の描画中に Svelte が `each_key_duplicate` を投げ、SvelteKit の `handleClientError` がエラー画面（status 500）を出したから
2. **なぜ key が重複したか？** → key が `RefID || URL` で、同じ記事の複数 chunk を引用した回答では両方とも同じ値になるから
3. **なぜ同じ記事が複数回引用されるのか？** → 引用は chunk 単位で、回答本文の `[n]` 番号と 1 対 1 に対応する設計だから。一方 key は「1 記事 1 引用」を暗黙の前提にしていた。2026-07 の修正（`f3ae0af5d`）は空の `RefID` の衝突だけを直し、テストも異なる `RefID` だけを扱っていた
4. **なぜ backfill の後に頻発したか？** → 所有者で可視になった文書が増え、同じ記事の複数 chunk が上位に並ぶようになったから（推定）。PM-2026-060 の期間中は多くのターンが fallback で終わり、引用付きの回答が少なかった
5. **なぜ長く気付けなかったか？** → クライアントの例外がブラウザの console にしか出ず、サーバ側から観測できなかったから。同条件の回答は 2026-08〜10 にも存在した

### 根本原因

- **サーバ:** 所有者で絞るベクトル検索が、プランナの推定に依存する相関結合の形をしていた。データ分布が変わると HNSW を使わない plan に倒れる SQL だった
- **クライアント:** CitationRail が、一意性の保証されない外部データ（記事 ID / URL）を `{#each}` の key に使っていた。位置で意味を持つリストなのに、記事単位の一意性を前提にしていた
- **共通:** 大きなデータ分布の変更（backfill）の後に、実際のユーザー経路（サーバのレイテンシとブラウザ側の描画）を確かめる手順と監視がなかった

### 寄与要因

- `hnsw.iterative_scan = relaxed_order`（ADR-000987）の下では index scan が距離順を厳密に保証しない。PostgreSQL 17 以降は CTE / subquery のソート順を外側で再利用するため、最初の修正版では外側の並べ直しが消えた。修正に `AS MATERIALIZED` と `distance + 0` が追加で必要になった
- owner backfill の初回実行が pgbouncer 越しの prepared statement 衝突（`42P05`）で失敗し、ツール側の修正と再実行が必要だった
- 調査はサーバ側のログと DB から始めた。サーバの全層が成功を記録していたため、500 を出した層は未確認のまま、レイテンシ対策の完了をもって復旧と見なしかけた
- 対応中、「回答は保存されているので再読み込みすれば表示される」と暫定的に案内した。実際には、会話を開き直しても同じ引用で CitationRail が再クラッシュするため、この案内は不正確だった（推定）

## 対応の評価

### うまくいったこと

- ClickHouse のログでステージごとの所要時間を追い、3 回の検索がボトルネックであることを数分で特定できた
- 本番 rag-db では読み取り専用の `EXPLAIN ANALYZE` だけで plan の誤りと修正後の効果（Search 37 ms / SearchNeighbors 16 ms）を確かめ、書き込みなしで修正を検証できた
- 修正は TDD（RED / GREEN を別 commit）で行い、SQL の形を単体テストで固定した。Opus のレビューと CI 全件通過のあと、デプロイパイプラインで 27 分後に本番へ入った
- ブラウザ console の共有から数分で、DB 上の引用の重複（`ref_id` をハッシュ化して比較、読み取り専用）を確認し、クライアント側の原因を確定できた
- PM-2026-060 の修正により回答が `augur_messages` に保存されていたため、データ損失はなかった

### うまくいかなかったこと

- 「500」の発生源を確認しないまま、サーバのレイテンシを原因と見なした。サーバ修正のデプロイ後も 500 が残り、クライアント側の原因の発見が約 2 時間遅れた
- backfill の完了判定がカバレッジ指標だけで、Augur を実際に 1 ターン流す確認がなかった
- クライアントの例外がサーバ側から見えず、調査がユーザーのブラウザ console 共有に依存した
- 暫定案内（再読み込みで表示される）が不正確だった

### 運が良かったこと

- BFF のストリーミング上限（40 分）とストリームの heartbeat（5 秒間隔）により、3 分のターンでもサーバ側のタイムアウトは起きず、回答は保存された
- ユーザーがブラウザ console のログを共有したことで、クライアント側の原因に辿り着けた。これがなければ、サーバ修正をもって復旧と判断していた可能性が高い

## 教訓

- **SQL を変えなくても plan は壊れる。** プランナの推定に依存する相関結合は、データ分布が変わった瞬間に別の plan へ倒れる。HNSW のような index 依存の経路では、推定に左右されにくい形（半結合で候補を先に絞る）を選び、plan そのものを本番相当データで確かめる必要がある
- **大きなデータ変更は、デプロイと同じくらい危険な変更として扱う。** backfill はコードを一行も変えずに、2 つの潜在欠陥を同時に表に出した。完了判定は指標の数値ではなく、実際のユーザー経路で行う
- **「500」はサーバのステータスとは限らない。** SvelteKit はクライアント側の例外も status 500 の画面として描画する。サーバ全層が成功している 500 は、まずブラウザ側を疑う。そのためにも、クライアントの例外をサーバ側から観測できるようにしておく
- **`{#each}` の key は、意味の上で一意なものだけを使う。** 位置で意味を持つリスト（引用番号と対応する引用欄）では、位置が正しい key である。外部データの ID は「たまたま一意だった」だけのことがある
