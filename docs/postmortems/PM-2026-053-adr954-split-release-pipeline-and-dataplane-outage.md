## サマリー

ADR-000954 で alt-backend を 3 バイナリ（alt-backend / alt-harvester / alt-data-hub）に分割する大規模変更（400 ファイル超）を main に merge したところ、リリースパイプラインが多層的に失敗し、約17時間にわたり本番反映がブロックされた。第一の原因は、デプロイ側への dispatch が GitHub Compare API の files 上限（300件）で変更リストを**無警告で切り捨て**、移行対象の consumer 群（recap-worker / search-indexer / tag-generator / rag-orchestrator ほか）がリリース対象から欠落したことである。その修復過程で、デプロイ側パイプラインの 3 バイナリ未対応、廃止済み内部 API を指す配備済み Pact によるゲートのデッドロック、can-i-deploy の部分的バージョン固定という構造的不備、新規 GHCR パッケージへの書き込み権限漏れ、step-ca の CN 許可リスト未更新（文書化済みオペレータ手順の未実施）、production compose のみに存在した設定漏れ 2 件、外部レジストリのレート制限という**7つの独立した問題**が順に顕在化した。途中のロールで新旧サービスが混在した約40分間、データプレーン（alt-data-hub）が起動不能となり、バックグラウンドのデータ処理が全面失敗した。最終的に全サービスは新構成で healthy となり、Broker への配備記録は手動で完了した。

## 影響

- **影響を受けたサービス:** alt-data-hub（起動不能）、alt-harvester（起動不能）、tag-generator（unhealthy）、alt-backend / pre-processor / search-indexer / recap-worker（データプレーン停止中は内部 RPC が全滅）、リリースパイプライン全体
- **影響を受けたユーザー数/割合:** 単一運用プロジェクトのため、実質的な影響はオーナー本人。ユーザー向け読み取り面（フィード閲覧等）は概ね応答を継続
- **機能への影響:** 約40分間、記事の取り込み・要約・タグ付け・recap などデータプレーン経由の全バックグラウンド処理が失敗（`GetSystemUser: 404` 等）。リリースパイプラインは約17時間新規デプロイ不能
- **データ損失:** なし。失敗したジョブは復旧後のサイクルで再処理された
- **SLO/SLA違反:** 明示的な SLO は未定義
- **定量データ:**
  - dispatch の変更リスト: 実変更 400+ ファイルに対しちょうど 300 件で切り捨て（API 上限値）。リリース対象 18 サービス中 7 サービスが欠落
  - リリース実行: 計 6 回中 5 回失敗（原因はすべて異なる層）
  - 配備済み consumer の旧 Pact: 2 サービス（recap-worker / search-indexer）× 計 5 interaction が廃止パスを参照し provider 検証を恒常的に失敗させた

## 検知

- **検知方法:** オペレータがリリースパイプラインの失敗を目視で発見。自動アラートなし
- **検知までの時間 (TTD):** 最初の失敗実行から数時間以内（パイプライン失敗自体は GitHub 上で可視）。ただし「変更リストが切り捨てられ 7 サービスがリリースから欠落していた」ことはパイプラインのどこにも警告が出ず、失敗調査の副産物として発見された
- **検知の評価:** パイプラインの失敗は目立つが、**silent truncation は成功時にも起こり得た**点が重大。仮にビルドが偶然通っていれば、「provider だけ更新され consumer が旧版のまま」という部分リリースが本番に到達し得た（実際には Pact ゲートと e2e が多重に阻止した）。切り捨てに対する tripwire が存在しなかったことが本質的な検知の穴

## 根本原因分析

### 直接原因

ADR-000954 の 400 ファイル超の変更に対し、デプロイ側への dispatch が変更リストを 300 件で無警告に切り捨て、大規模 breaking migration が部分リリースとして実行された。これを起点に、平常時には露出しない 6 つの潜在的不整合（下表）が連鎖的に顕在化した。

| # | 層 | 問題 |
|---|----|------|
| 1 | dispatch | Compare API の files 上限 300 件による silent truncation |
| 2 | デプロイ側ビルド | 3 バイナリ分割（`BINARY` build-arg / 2 新イメージ）への未追随 |
| 3 | Pact ゲート | 廃止 API を参照する配備済み Pact × record-deployment はデプロイ成功後のみ、という鶏卵デッドロック。および can-i-deploy の部分的バージョン固定が固定対象の全 integration を production 旧版と突き合わせる構造問題 |
| 4 | レジストリ権限 | 本体リポジトリの CI が先に作成した新規 GHCR パッケージに、デプロイ側の書き込み権限が無い |
| 5 | PKI | step-ca CN 許可リスト更新という文書化済みオペレータ前提手順が未実施のままリリースが進行可能 |
| 6 | compose 実態差分 | staging スライスにのみ適用された設定（`IMAGE_PROXY_ENABLED=false`）と証明書所有者 UID が production compose で欠落 |
| 7 | 外部依存 | base image pull の未認証レート制限が連続リリース時にビルドを間欠死させる |

### Five Whys

1. **なぜ本番データプレーンが約40分停止したか？**
   → 新構成のロール中、alt-data-hub が設定 fail-fast でクラッシュループし、既にロール済みの他サービスが依存する内部 API が不在になったから。

2. **なぜ alt-data-hub は本番でだけ起動できなかったか？**
   → 起動可否を左右する設定（image proxy 無効化）と PKI 前提（CN 許可リスト・鍵所有者）が staging スライスでは修正済み・本番系では未適用という**環境間パリティの欠如**があったから。CI は staging スライスしか検証しない。

3. **なぜ環境間の不整合がリリース前に検出されなかったか？**
   → 「新サービス追加時の本番側前提条件」（CN 許可リスト、GHCR 権限、production compose の設定パリティ、証明書所有者）がドキュメント上の知識として散在し、リリースパイプラインが機械的に検証する仕組みがなかったから。

4. **なぜ Pact ゲートは移行リリースを一発で通せなかったか？**
   → (a) 配備済み consumer の旧 Pact 検証と record-deployment の順序が鶏卵構造であること、(b) co-release の互換性を「手選りのペア固定」で表現しており、固定した pacticipant の全 integration が行列に入るという can-i-deploy の実セマンティクスと不一致だったから。どちらも小規模リリースでは露出せず、**全サービス同時 breaking migration という初のケース**で初めて実行された。

5. **なぜ初のケースで多数の潜在欠陥が同時に露出したか？**
   → リリースの正しさが「公開リポジトリの CI」「デプロイ側パイプライン」「オペレータ管理のホスト状態（CA・レジストリ権限・canonical .env）」の 3 面に分散しているのに、**面をまたぐ breaking migration のための単一のリリース手順（checklist / choreography）が存在しなかった**から。各面はそれぞれ fail-fast に作られており個別には正しく失敗したが、事前に整合を取る仕組みがなかった。

### 根本原因

**多面（公開 repo / デプロイ側 / ホスト状態）にまたがる breaking migration に対して、変更セットの完全性保証と事前前提条件の機械的検証が存在しなかったこと。** silent truncation はその最初のドミノに過ぎず、以降の各層の失敗はいずれも「初めて踏まれた経路に埋まっていた、検証されていない前提」だった。

### 寄与要因

- Pact の provider 検証ハーネスはスタブであり、実装との一致は保証しない（`GetSystemUser` 未実装なら検証 green のまま本番 404 になり得る構造。今回は実装が存在したため顕在化せず）
- ビルド 1 件の失敗が consumer Pact 公開→ゲート→e2e→デプロイの全段を skip させる needs 構造のため、無関係な一時障害（レジストリのレート制限）でもリリース全体が失敗する
- 本番 canonical .env に `APP_ENV` が未設定で全サービスが `development` 扱いとなっており、環境別の fail-fast 検証が弱まっている（今回の直接原因ではないが調査中に発見）
- record-deployment と last-good-tag 更新がデプロイジョブ最終盤に集中しており、後段失敗時に「実態は配備済みだが記録は旧版」という乖離が残る

## 対応の評価

### うまくいったこと

- **ゲートと e2e は 5 回とも正しく部分デプロイを阻止した。** 誤配備は一度も本番に到達していない。fail-fast 設計（BINARY 必須、設定検証での起動拒否、CN 許可リストの deny-by-default）はすべて意図通り「大声で」失敗した
- 旧 Pact 互換の transitional shim は、同ファイル内に前例（撤去条件コメント付きスタブ）があり、その規約に沿って最小スコープで追加できた
- step-ca 許可リスト更新は冪等スクリプト＋20項目の検証付きで、無停止（SIGHUP のみ）で完了した
- Broker への record-deployment はデプロイジョブと同一コマンドで手動完了でき、パイプライン復旧を待たずに整合を回復できた

### うまくいかなかったこと

- 変更リストの切り捨てが**数ヶ月間誰にも知られず存在**し、大規模リリースで初めて露出した
- 「新 east-west サービス追加の前提手順」（CN 許可リスト・GHCR 権限・compose パリティ・鍵所有者）が 4 つとも漏れた。ドキュメントには存在したが、実施を強制する仕組みがなかった
- リリース実行 6 回・約17時間という復旧コスト。各層の失敗が直列にしか発見できなかった
- 本番ロール途中でデータプレーンが停止する順序（依存される側の起動失敗を、依存する側のロール後に発見）を許した

### 運が良かったこと

- データプレーン停止が深夜帯かつ単一運用であり、実ユーザー影響が最小だった
- 配備済み consumer の旧 Pact がちょうど 2 サービスに収まり、shim の範囲が小さく済んだ
- 外部レジストリのレート制限が「最後の 1 実行」でのみ致命傷となり、本番ロール自体は完了済みだった

## 教訓

- **切り捨ては失敗より危険である。** 外部 API の上限（Compare API の files 300 件）に依存する箇所は、上限到達を「そのまま続行」ではなく「明示的な失敗」に変えておく。上限値ちょうどの結果は疑ってかかる
- **fail-fast は前提条件の事前検証を代替しない。** 各コンポーネントが起動時に大声で死ぬ設計は今回すべて機能したが、「死ぬこと」が分かるのはロール後である。面をまたぐ前提（CA 許可リスト、レジストリ権限、環境パリティ）は、ロール前に機械的に検証する層が別途必要
- **can-i-deploy の部分固定は「固定した相手の全 integration」を行列に引き込む。** co-release の互換性主張は、同時に出すもの全部を一括で固定するのが Pact のセマンティクスに合った唯一の表現である
- **「ドキュメントに書いてあるオペレータ手順」は、初めて必要になった日に実施されない。** 手順はチェックリスト化し、可能なら実行可能な検証スクリプト（今回の許可リスト bootstrap + verify のような）と対にする
- スタブベースの provider 検証は契約の形を守るが実装の存在は守らない。契約追加時は実装側の 404 テスト（今回の datahub handler_test のような）を必ず対にする
