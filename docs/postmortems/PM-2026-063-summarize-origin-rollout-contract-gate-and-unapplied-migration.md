## サマリー

2026-11-18、要約ジョブに起点（`origin`）を必須で持たせる変更（PR #359、[[001016]]）を本番に出したところ、2 つの問題が続けて起きた。

1. **契約ゲートでの部分反映（12:06〜）**: 新しい pre-processor は起点のない要約依頼を 400 で返す。リリースの契約検証は本番で稼働中の alt-backend の契約（起点なし）でも pre-processor を検証するため失敗した。パイプラインは pre-processor だけを据え置いて他を反映し、部分反映のロックを残した。直後にマージされた PR #360 の自動リリースは、このロックのため最初の段階で止まった
2. **マイグレーションの空振りによる要約キューの停止（12:31〜12:40）**: 手動で全対象を出し直したリリースは成功と報告されたが、`summarize_job_queue` に `origin` 列を足すマイグレーションは適用されていなかった。pre-processor のマイグレーション用イメージだけがマイグレーションファイルをイメージに焼き込んでおり、再ビルドされないまま 5 日前のイメージが実行されたためである。新しい pre-processor は `column "origin" does not exist` で、キューの取り出しとジョブの登録に 8 分 20 秒失敗し続けた

マイグレーション用イメージを再ビルドして適用し、12:40 に復旧した。どちらの問題も、変更の PR 上の検査はすべて緑だった。

- **機能への影響:** 部分的劣化

  - PR #360（読書イベント）は、自動リリースがロックで止まり手動での出し直しになった（マージ 12:10、反映完了 12:34）
- **データ損失:** なし。登録に失敗した 8 件はキューに残っていない。内訳（利用者の依頼か、システム起点か）と、イベント経由の分が再配信で回収されたかは未確認（アクションアイテム #9）
- **SLO/SLA違反:** なし（要約キューに SLO は定義されていない）

## 根本原因分析

### 直接原因

- **契約ゲートでの停止**: pre-processor が要求する項目（起点）を必須にする変更を、送る側の alt-backend の変更と同じリリースで出した。リリースの契約検証は、同じリリースの alt-backend だけでなく本番で稼働中の alt-backend の契約でも pre-processor を検証する。稼働中の契約は起点を送らないので、検証は 400 で失敗した
- **要約キューの停止**: `pre-processor-db-migrator` のイメージが 2026-11-13 にビルドされたもので、`20261118000100_add_origin_to_summarize_job_queue.sql` を含んでいなかった。反映段階はこのイメージを再ビルドせずに実行し、Atlas は「未適用のマイグレーションなし」で正常終了した。その後に反映された pre-processor は、存在しない `origin` 列を読み書きして失敗した

### Five Whys

**要約キューの停止**

1. **なぜ要約キューが止まったか？** → 新しい pre-processor が `summarize_job_queue.origin` を読み書きするが、本番 DB にその列が無かったから
2. **なぜ列が無かったか？** → マイグレーション用コンテナが、新しいマイグレーションファイルを含まない古いイメージで実行されたから
3. **なぜ古いイメージが実行されたか？** → `pre-processor-db-migrator` は `build:` だけを持ち、マイグレーションファイルは Dockerfile の `COPY migrations/ ./` でイメージに入る。反映段階は既存のローカルイメージがあれば再ビルドしないので、ファイルを足してもイメージに届かない
4. **なぜこの 1 本だけがそうなっていたか？** → 他のマイグレーション用サービス（`migrate`、`rag-db-migrator`、`recap-db-migrator`、`knowledge-sovereign-db-migrator`、`acolyte-db-migrator`）は、リリースの作業ツリーの `migrations/` を読み取り専用でマウントしている。`acolyte-db-migrator` には 2026-08-09 の `a56c5fe97` で同じ欠陥への対処としてマウントが足され、compose のコメントに「マウントが無いと新しい .sql の適用にイメージの再ビルドが要る」と書かれた。この修正は pre-processor 用には及ばなかった
5. **なぜ誰も気付かなかったか？** → 未適用が失敗として現れないから。マイグレーションの段階は Atlas の正常終了だけを見ており、リリースが含む最新のマイグレーションと DB の適用履歴を突き合わせない。直前の `20261017000100`（索引の最適化）は 2026-10-17 にコミットされたが、適用されたのは全マイグレーション用イメージが作り直された 2026-11-13 で、26 日間未適用だった。この変更はコードが必須としない内容だったため、未適用でも何も壊れず、欠陥は隠れたままだった

**契約ゲートでの停止**

1. **なぜ契約検証が失敗したか？** → 新しい pre-processor が、本番で稼働中の alt-backend の契約（起点なしの依頼）に 400 を返したから
2. **なぜ稼働中の契約で検証されたか？** → provider の検証は、稼働中の consumer を壊さないことを確かめるために、稼働中の契約も対象にする。これは意図した保護で、今回も正しく働いた
3. **なぜ保護に掛かる変更がそのまま出たか？** → [[001016]] は「起点の指定がない呼び出しは入力検証エラーにし、既定値を当てない」と決めたが、送る側と受ける側をどの順で出すかは決めていなかった。実装は 1 つの PR で両側を同時に変えた
4. **なぜ PR の段階で分からなかったか？** → PR 上の契約検証は、同じ PR の consumer の契約に対してだけ走る。稼働中の契約との非互換は、本番リリースの段階で初めて検証される
5. **なぜ同時リリースの仕組みで通せなかったか？** → 同時に出す consumer を名指しして稼働中の契約の検証を外す指定（`PACT_LOCKSTEP_CONSUMERS`）は、alt-backend と search-indexer の provider 検証にしか実装されていなかった。pre-processor の provider 検証は対応しておらず、指定しても検証は落ちる。また、マージ前の確認では非互換を「切り替え中の数分間の失敗」と見積もり、ゲートで止まることとマイグレーションの運び方を確かめなかった

### 根本原因

**「成功」と報告される段階が、目的の状態に達したことを確かめていないこと。** マイグレーションの段階は、適用すべきファイルを運ぶ手段（イメージ）が古くても正常終了する。運ぶ手段がサービスごとに違い（焼き込みかマウントか）、1 本だけ焼き込みのまま残っていたことが、その穴を実際の停止に変えた。

契約ゲートでの停止は、保護が正しく働いた結果である。ただし、必須項目を足す変更の出し方（2 段階で出すか、同時リリースを宣言するか）を、PR の段階で判定する手段が無い。

### 寄与要因

- **部分反映が既定の動作である**: 契約検証に落ちたサービスだけを据え置いて残りを反映するため、失敗したリリースが本番を「一部だけ新しい」状態にし、ロックを残す。今回は結果的に安全な順序（送る側が先）になったが、逆の組み合わせなら据え置きが非互換を作る
- **自動リリースが連続した**: 先行のリリースが失敗している最中に次の PR がマージされ、2 本目はロックで止まった。失敗中のリリースがあることは、マージの操作からは見えない
- **反映後の確認が手順になっていない**: 今回はログを読んで 4 分で気付いたが、決まった手順ではない
- **マイグレーションの既定値が旧バイナリを守っていた**: `origin` 列は `NOT NULL DEFAULT 'system'` で、旧バイナリの INSERT は通る設計だった。この配慮は「マイグレーションが先に適用される」前提に立っており、前提そのものは検査されていなかった

## 失敗の型と再発

- 失敗の型: FP-12, FP-01, FP-14, FP-02, FP-07, FP-16, FP-19
- 再発: PM-2026-058, PM-2026-053
- 持ち越し: PM-2026-058 #6（consumer と provider を同一コミットで変える lockstep 変更を検出し、安全な順序を機械的に示す。期限 2026-10-19 超過）、PM-2026-053 #12（面をまたぐ breaking migration は全サービス指定の手動リリースを標準手順にする。期限 2026-08-08 超過）。どちらも契約ゲートでの停止の再演にあたり、2 度目以降の持ち越しなので本書の #4 に統合して優先度を上げる
- 止められたはずの検査: (1) マイグレーションファイルを `COPY` で焼き込むマイグレーション用サービスが、同じディレクトリを compose でマウントしていない場合に落とす compose の静的検査。(2) マイグレーション実行後に、リリースが含む最新のマイグレーションと DB の適用履歴を突き合わせ、遅れていれば反映を止める検査。(3) 契約の必須項目を足す PR で、稼働中の consumer の契約に対する provider 検証を PR の段階で走らせる検査

## 対応の評価

### うまくいったこと

- 契約ゲートは、稼働中の consumer と非互換な provider を本番に出さなかった
- 部分反映のロックは、状況を確認しないままの次のリリースを止めた
- マイグレーションの列定義が旧バイナリの INSERT を許す形（既定値つき）だったので、適用そのものは瞬時で、追加の停止を生まなかった
- 復旧は Atlas 経由で行い、適用履歴に正しく記録された。DB に直接 SQL を流していない
- 原因の特定は、DB の適用履歴とイメージの中身という 2 つの事実で確定させた

### うまくいかなかったこと

- マージ可否の確認で、非互換の影響を「切り替え中の数分間」と見積もった。契約ゲートが稼働中の契約で検証して止めること、マイグレーションが反映前に適用される前提が成り立っているかは確かめなかった
- リリースが成功と表示された時点では、要約キューは止まっていた。成功の表示が状態の確認になっていない
- 部分反映で終わったリリースの後、次に何を指定して出し直すかは、過去の障害の記憶に頼って組み立てた。手順として引ける形になっていない
- 調査の途中で「他のマイグレーション用サービスも同じ作りに見える」と報告したが、確認すると焼き込みだけに頼るのは pre-processor 用の 1 本だった

### 運が良かったこと

- 部分反映の結果が「送る側が新しく、受ける側が旧い」という無害な組み合わせになった。据え置かれたのが alt-backend だったら、新しい pre-processor が旧 alt-backend の依頼をすべて 400 で拒否していた
- 1 本目のリリースが alt-backend の新版を本番稼働として記録したので、2 本目の手動リリースでは pre-processor の検証が何の指定もなく通った
- 直前の 26 日間未適用だったマイグレーションは索引の最適化で、未適用でも機能は壊れなかった
- 反映直後にログを読んだ。読まなければ、要約が増えないことに利用者が気付くまで続いていた

## 教訓

- **「適用するものが無かった」は成功ではなく、確かめるべき状態である。** マイグレーションの段階が正常終了しても、適用すべきファイルが届いていなければ何も起きていない。成功の判定は、手段の終了コードではなく、到達した状態（適用履歴）で行う
- **同じ役割の部品は、同じ方法で運ぶ。** 6 本のマイグレーション用サービスのうち 5 本はマウント、1 本だけ焼き込みだった。1 本を直したときに兄弟を確かめる検査が無ければ、残りはそのまま残る
- **壊れない変更は、欠陥を隠す。** 直前のマイグレーションは 26 日間未適用だったが、索引の最適化だったので誰も困らなかった。必須の列を足す変更が来て初めて表に出た
- **必須項目を足す変更は、コードの変更ではなくリリースの設計である。** 受ける側が拒否を始める変更は、送る側が先に出ている必要がある。1 つの PR にまとめることと、1 回のリリースで出せることは別の話である
- **保護が働いて止まったときは、止まった後の状態を確かめる。** 契約ゲートは正しく止めたが、部分反映で本番は混在状態になり、ロックが次のリリースを止めた。今回の混在は無害な向きだったが、それは設計ではなく偶然だった
- **過去の障害で分かっていたことが、実行可能な形になっていなかった。** 同時リリースの難しさは [[PM-2026-053]] と [[PM-2026-058]] で記録済みで、対応するアクションアイテムは期限を過ぎて開いたままだった
