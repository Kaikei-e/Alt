## サマリー

2026-08-10 05:46:31 JST に `alt-data-hub` の mTLS サーバー証明書（step-ca 発行の 24h leaf）が期限切れを迎えた。`alt-data-hub` は alt-db の唯一のオーナーであるため、`alt-backend` から DB に到達する全経路が `tls: failed to verify certificate: x509: certificate has expired` で失敗し、BFF (`alt-butterfly-facade`) のサーキットブレーカーが `FeedService` 系エンドポイントで OPEN となった。ユーザーには Visual Preview / フィード一覧に `Service temporarily unavailable due to circuit breaker` が表示された。

直接の原因は、証明書を自動更新する `pki-agent` サイドカー 14 個のうち 5 個（alt-backend / alt-data-hub / alt-butterfly-facade / auth-hub / search-indexer）が docker から消失していたことである。消失させたのは 30 分ごとに実行されるディスク掃除スクリプトの無差別 prune で、この障害機構自体は前日 2026-08-09 に [[ADR-000968]] として記録され修正済みだったが、**修正は予防のみで、既に削除されたサイドカーを復元するアクションを含んでいなかった**。

復旧は (1) prune に剥がされた image タグを、生存コンテナが参照していた同一 image 層に貼り直す、(2) サイドカー 5 個を再作成する、の 2 手で約 2 分。親サービスの再起動は不要だった。

これは [[PM-2026-028]]（2026-04-15）とシグネチャがほぼ一致する 2 度目の発生である。

  - モバイル swipe / desktop の Visual Preview — サーバー load 失敗でエラー表示
  - バックグラウンドジョブ — alt-harvester の feed failure reset / outbox claim が 06:18 JST 頃から失敗

- **データ損失:** なし。read 経路の失敗と、書き込み経路のリトライ可能な失敗のみ
- **未遂に終わった影響:** 復旧の約 1 時間 38 分後（14:45〜14:47 JST）に alt-backend / alt-butterfly-facade / auth-hub の証明書が失効予定だった。auth-hub が失効していればログインとセッション検証が落ち、SEV-1 の全面停止に悪化していた

## 検知

- **検知方法:** ユーザーの目視（読書面がエラー表示になっているのを発見して通報）
- **検知までの時間 (TTD):** 失効到達から約 7 時間 4 分、ユーザー可視の影響開始から約 1 時間 24 分
- **検知の評価:** 機能していない。以下の理由による。

  1. **Alertmanager がスタックに存在しない。** `observability/prometheus/rules/pki-agent-alerts.yml` に 4 本のアラート（`PkiAgentCertExpirySoon` / `PkiAgentCertExpired` / `PkiAgentRenewalFailing` / `PkiAgentDown`）が定義され、うち 3 本は severity `page` である。しかし `prometheus.yml` に `alerting:` ブロックがなく、compose にも alertmanager サービスがない。Grafana 側の provisioning にも pki 関連ルールはない。**4 本すべて、評価はされるが誰にも配送されない。**
  2. **page 系 2 本は、この障害モードでは原理的に発火しない。** `PkiAgentCertExpirySoon` と `PkiAgentCertExpired` はいずれも `pki_agent_cert_remaining_seconds` / `pki_agent_healthy` という**時系列の存在を前提とした式**である。コンテナが削除されると時系列そのものが消えるため、条件が成立しない。`absent()` / `absent_over_time()` を使ったルールはリポジトリ全体に 1 本もない。
  3. **唯一発火しうる `PkiAgentDown`（`up == 0`）の severity が `ticket`。** 全社機能停止を招く事象が ticket 扱いになっている。
  4. **scrape target が compose 定義に追随していない。** `prometheus.yml` の pki-agent job は static_configs で 10 ターゲット、compose 定義は 14 サイドカー。今回消えた 5 個は登録済みだったため 2. と 3. の問題だけが効いたが、未登録の 4 個で同じことが起きれば `PkiAgentDown` すら鳴らない。

  これらの検知策は [[PM-2026-028]] の Detect アクションアイテムとして 2026-04-16 に「完了」とチェックされたものである。

## 根本原因分析

### 直接原因

`alt-data-hub` の mTLS サーバー証明書を更新する `pki-agent-alt-data-hub` コンテナが存在せず、24 時間の leaf が更新されないまま期限切れに到達した。

### Five Whys

1. **なぜ Visual Preview がエラーになったのか？**
   → BFF のサーキットブレーカーが `FeedService` 系エンドポイントで OPEN になり、リクエストを即時拒否していたため。

2. **なぜサーキットブレーカーが開いたのか？**
   → 上流の `alt-backend` → `alt-data-hub` の mTLS 通信が連続失敗し、失敗閾値 5 に到達したため。`alt-data-hub` は alt-db の唯一のオーナーなので、DB に触る全 RPC が巻き添えになった。

3. **なぜ mTLS が失敗したのか？**
   → `alt-data-hub` のサーバー leaf が期限切れだったため。更新を担う `pki-agent-alt-data-hub` が稼働していなかった。

4. **なぜサイドカーが稼働していなかったのか？**
   → コンテナが**削除されていた**ため。停止していたのではない。`restart: unless-stopped` は削除されたコンテナには作用しない。さらに、手動で `up` しようとしても image の `:main` タグが同じ prune に剥がされており、`.env` に `IMAGE_TAG` の指定がないため compose が解決できない状態だった。**削除と再作成不能の両方が同時に成立していた。**

5. **なぜ削除されたのか？**
   → ディスク掃除スクリプトの逼迫時経路が `docker container prune -f` と `docker image prune -a -f`（`until` フィルタなし）を 30 分ごとに実行していたため。prune の語彙は「参照されているか」しかなく、「単に停止しているだけの compose サービスに属する」という述語を表現できない。

6. **なぜ逼迫時経路が常時発火していたのか？**
   → ディスク使用量が上限に対して恒常的に超過しており、かつ安全に解放できる領域が全体の 2% 未満しかなかったため。到達不能な目標に対して、スクリプトは残った唯一の刈り取り対象——稼働中サービスの image とコンテナ——を狙い続けていた。

7. **なぜそれが 7 時間気付かれなかったのか？**
   → 監視が構造的に配送されないため（「検知」セクション参照）。証明書更新のような「いなくなっても当面は動く」系のコンポーネントは、欠損が即座に症状として現れない。今回は欠損から症状発現まで最大 24 時間の猶予があり、その間の無音を検知する手段がなかった。

### 寄与要因

- **[[PM-2026-028]] のアクションアイテムが未完了だった。** 同一シグネチャの障害が 2026-04-15 に発生しており、そのとき「なぜサイドカーが消えたのか」は特定できずに終わっていた。未実施のまま残っていたアクションアイテムのうち、四半期ごとの pki-agent 演習（証明書を volume から消して観測がどの段階で page するかを測定する）を実施していれば、Alertmanager 不在は 5 月時点で判明していた。
- **[[ADR-000968]] の修正が予防のみだった。** 掃除スクリプトの障害機構は前日に正しく特定・修正されているが、ADR が名指しした被害サービスは 1 つだけで、**同じ prune が他に何を削除したかの棚卸しが行われなかった**。「この掃除は過去に何を消したか」を確認するアクションが修正とセットになっていれば、失効前に発見できた。
- **24h という短い leaf 寿命が増幅要因になった。** 更新役の不在が最短 24 時間で障害に転化する。[[PM-2026-028]] の教訓「short-lived は必ず観測とセット。lifetime を短くするほど renewer と観測の信頼性要件が跳ね上がる」がそのまま再現した。leaf TTL の 48h 延長検討も [[PM-2026-028]] の未完アクションアイテムである。
- **runbook が実態から乖離していた。** `docs/runbooks/pki-agent-recovery.md` は 13 subject 前提で書かれており、後から allowlist に追加された 1 subject が一括復旧の volume リストから抜けている。今回は該当しなかったが、別の組み合わせでは復旧漏れを生む。
- **`.env` に `IMAGE_TAG` が指定されておらず、compose の既定値 `:main` に依存していた。** 可変タグへの依存が、image prune に対する耐性を下げていた。

## 対応の評価

### うまくいったこと

- **サーキットブレーカーが設計どおり働いた。** 上流の恒久的失敗を、リクエストの滞留ではなく高速で境界の明確な拒否に変換した。ブレーカーの遷移ログ（`from` / `to` / `consecutive_failures` / `endpoint`）が構造化されていたため、障害の開始時刻を秒単位で特定でき、復旧の確認も同じログで即座にできた。
- **エラーが上流の一次情報を保持したまま伝播していた。** alt-backend のログに `x509: certificate has expired ... current time <now> is after <notAfter>` がそのまま残っていたため、原因特定が 1 コマンドで済んだ。`NotAfter` の値が step-ca の発行記録と完全一致したことで、仮説の裏取りも即座にできた。
- **[[ADR-000968]] の修正が既に有効だった。** 障害対応中に掃除スクリプトが追加の破壊を行わなかった。修正が「commit した時点で次回発火から有効」という性質だったことが、この場面では有利に働いた。
- **image 層が生存していたため、ネットワーク pull なしで正確に復旧できた。** タグを貼り直すだけで、他の稼働中 pki-agent とビット単位で同一の image を使えた。ghcr の rate limit / 認証に依存する経路を踏まずに済んだ。
- **Go の certReloader が mtime で新しい証明書を拾い、親サービスの再起動が不要だった。** 復旧に追加のダウンタイムが発生しなかった。runbook が安全側で指示している「期限切れ leaf の手動削除」と「消費側の restart」は、いずれも今回は不要だった。
- **原因特定から復旧まで約 7 分。** 復旧手順自体は 2 コマンドだった。

### うまくいかなかったこと

- **検知がユーザー報告だった。** 3 本の `page` severity アラートが定義されているにもかかわらず、1 通も配送されていない。定義の存在が「検知策は完了している」という誤った安心を生んでいた。
- **ユーザーに upstream の生メッセージが露出した。** 読書面に `[unavailable] Service temporarily unavailable due to circuit breaker` がそのまま表示された。これを防ぐための分類器 `errorClassification.ts` は存在するが、記事本文取得の経路にしか配線されておらず、一覧取得の経路（`FeedGrid.svelte` / `FeedsClient.svelte` / `ViewedFeedsClient.svelte`）は `{error.message}` を生描画していた。当該コンポーネントにはレンダリングを伴うテストが 1 本もなく、分類器の単体テストは通り続けていた。
- **サイドカーの一次停止原因が特定できなかった。** コンテナごと削除されたため、なぜ最初に停止したのかの証拠が残っていない。[[ADR-000968]] が記録した先行事例とまったく同じ状況であり、同じ理由で 2 度目も分析が打ち切られた。
- **8 月の作業記録（daily note）が存在しない。** 障害当日を含む 8 月の全作業について daily note がなく、サイドカー消失の窓に何が行われていたかを再構成する材料が git 履歴とシステムログしかなかった。
- **compose 定義と実稼働の乖離を検知する仕組みがなかった。** 「定義 14 個 / 実在 9 個」という状態が数時間から数日続いていたが、これを見る仕組みは存在しない。

### 運が良かったこと

- **第二波の 1 時間 38 分前に復旧できた。** alt-backend / alt-butterfly-facade / auth-hub の証明書が 14:45〜14:47 JST に失効予定だった。auth-hub が落ちればログインごと停止し、SEV-1 に悪化していた。ユーザーの通報がこれより遅ければ、あるいは調査が長引いていれば、被害は質的に変わっていた。
- **pki-agent 14 個のうち 2 個が生き残っていたため、image 層が garbage collect されなかった。** もし 14 個すべてが削除されていれば image 層も未参照になり、prune に消されていた。その場合、復旧にはレジストリからの pull が必須となり、既知の rate limit 問題を踏むリスクがあった。
- **同時に消えた 5 個がすべて cert-only パターンだった。** `network_mode: service:<parent>` で親とネットワーク名前空間を共有するパターンであれば、[[ADR-000782]] 系の netns 孤立が重なり、親の force-recreate を伴うより重い復旧になっていた。

## 教訓

### 技術的な教訓

- **prune は運用意図を表現できない道具である。** `docker image prune` / `container prune` の語彙は「参照されているか」だけで、「単に停止しているだけの、再起動を待っている compose サービス」という状態を除外できない。これは設定の誤りではなく道具選択の誤りであり、フィルタの調整では解決しない。
- **「削除されたコンテナ」は「停止したコンテナ」より一段危険である。** `restart: unless-stopped` は削除には作用しない。監視も、時系列の値を見るルールは時系列そのものの消失を捉えられない。**存在しないものを検知するには、不在を明示的に問うルール（`absent`）が要る。**
- **アラートの定義と配送は別の問題である。** 4 本の正しいルールが 4 か月間、誰にも届かないまま評価され続けていた。ルールファイルの存在は検知能力の証拠にならない。
- **証明書更新のような「いなくなっても当面動く」コンポーネントは、欠損と症状の間に時間差がある。** 今回は最大 24 時間の猶予があり、その猶予がそのまま「気付けない時間」になった。この種のコンポーネントは、症状ではなく**存在そのもの**を監視しなければならない。
- **可変タグへの依存は、image 削除に対する耐性を下げる。** `:main` への暗黙依存がなければ、コンテナ削除だけの被害で済み、復旧はもう一段単純だった。
- **エラーメッセージの分類は、経路ごとではなく境界ごとに配線する。** 分類器は存在したが、記事本文取得の経路にしか繋がっていなかった。「どの経路から来た失敗か」ではなく「ユーザーに見せる境界か」で配線すべきだった。

### 組織的な教訓

- **同じ障害の 2 度目は、1 度目の分析が途中で止まった場所から起きる。** [[PM-2026-028]] は「サイドカーが消えた原因は特定できず」で分析を終えており、その未解決部分がそのまま 2 度目の原因になった。特定できなかった項目は、閉じるのではなくアクションアイテムとして残すべきである。
- **障害の修正は「これから起きないようにする」だけでは半分である。** [[ADR-000968]] は機構を正確に特定し正しく修正したが、「すでに壊したものを直す」を含んでいなかった。破壊的なプロセスを修正するときは、その修正とセットで**過去の被害の棚卸し**を行う必要がある。
- **アクションアイテムの「完了」は、成果物の存在ではなく効果で判定する。** 演習（R1）は、定義したものが実際に機能するかを確かめる唯一の手段であり、それが未実施だったために 4 か月間ギャップが温存された。演習は他のアクションアイテムの検証手段でもある。
- **作業記録の欠落は、事後分析のコストを直接押し上げる。** 8 月の daily note が存在しないため、サイドカー消失の窓に何が行われていたかを git 履歴とシステムログだけで再構成することになり、一次停止原因の特定を諦める一因になった。
