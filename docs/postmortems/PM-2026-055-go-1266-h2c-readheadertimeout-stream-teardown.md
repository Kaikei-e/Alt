## サマリー

2026-08-15 22:00 JST のリリースで、alt-backend のビルド toolchain が Go 1.26.5 から 1.26.6 に上がった（依存ライブラリの変更はゼロ、`go.sum` はバイト一致）。Go 1.26.6 は `net/http` の `ReadHeaderTimeout` デッドラインを h2c preface 判定より前に設置するよう変更しており、HTTP/2 サーバ側はそのデッドラインを `ReadTimeout > 0` のときにしか解除しない。alt-backend のユーザー向け Connect-RPC リスナーはストリーミングのために意図的に `ReadTimeout: 0` としていたため、**h2c 接続が確立からちょうど 10.0 秒（`ReadHeaderTimeout` の値）で破壊され、その接続に多重化された全ストリームが `context canceled` で道連れになる**状態が生まれた。

この h2c 接続の実クライアントは BFF（alt-butterfly-facade）であり、ブラウザ → エッジ → frontend → BFF → alt-backend の経路上で唯一の多重化ホップだった。結果として、10 秒を超えるオンザフライ要約ストリーム（記事の約半数に相当する長さ）は全て途中切断され、Knowledge Home の更新ストリームも約 10 秒ごとの再接続ループに陥った（クライアントの自動再接続がこれを覆い隠した）。さらに news-creator 側の潜在バグ（最終トークン後も heartbeat の仕組みが SSE の EOF を最大 10 秒遅らせる）により、10 秒以内に生成が完了したケースですら要約の永続化に到達できず、観測した 2 時間でストリーミング経路の要約保存は 0 件だった。

修正（4 コミットを含むイメージ）は 2026-08-16 09:11 JST にデプロイされ、対象サービスは正常に再起動した。トランスポート層の検証では、Connect リスナーへの受動 HTTP/2 プローブがアクティブなストリームを **40 秒間保持**（障害時はちょうど 10.0 秒で切断）し、障害シグネチャのログはインシデント時間帯以降再発していない。ただし実ユーザーによるオンザフライ要約の end-to-end 完走（表示完了と要約の永続化）はデプロイ後まだ発生しておらず、完全復旧の最終確認はこの 1 点を残している。

## 影響

- **影響を受けたサービス:** alt-backend（Connect-RPC ストリーミング全般）、news-creator（要約永続化）、alt-frontend-sv（要約 UI）
- **影響を受けたユーザー:** 当該時間帯にオンザフライ要約・Knowledge Home を利用した全ユーザー
- **機能への影響:** 部分的停止
  - オンザフライ要約: リクエスト開始から 10 秒で切断。再現試行 **12/12 が 9.99〜10.00 秒**で切断。要約の中央値 ≈ 645 文字は 10 秒で届く限界（≈ 640 文字）とほぼ同値のため、**約半数の記事で尻切れ、長文記事は全滅**
  - 記事詳細ページは部分テキストがあるとエラーを表示しない実装だったため、尻切れの多くは**エラー表示なしの静かな欠損**として現れた（ユーザー体感は「たまに End が切れる」）
  - Knowledge Home 更新ストリーム: 約 10 秒ごとの切断・再接続ループ（自動再接続によりユーザー可視の症状はほぼ無し）
  - unary RPC: 10 秒以内に完了するため影響なし
- **データ損失:** あり（限定的・再生成可能）。観測 2 時間でストリーミング経路の要約保存 **0 件**。生成自体が完了していたケースも寄与バグにより保存に到達できなかった。バッチ要約経路は独立して健全だったため、恒久的な損失はない
- **SLO/SLA違反:** ストリーミング系の SLI は未整備のため判定不能（それ自体が本障害の教訓）

- **検知の評価:** 不十分。Knowledge Home ストリームは**リリース直後から 10 秒ごとに全滅と再接続を繰り返していた**が、クライアントの自動再接続が症状を吸収し、ストリーム寿命を測る指標が存在しないため、監視上は完全に無音だった。ストリーミングの p50 寿命が桁で崩壊しても現行の監視は何も言わない。

## 根本原因分析

### 直接原因

Go 1.26.6 の `net/http` は `ReadHeaderTimeout` のデッドラインを `(*conn).serve` 冒頭（h2c preface 判定の前）で接続に設置する。HTTP/2 サーバはこのデッドラインを `ReadTimeout > 0` のガード内でのみ解除するため、`Protocols` による h2c + `ReadHeaderTimeout: 10s` + `ReadTimeout: 0` の組み合わせ（alt-backend の Connect リスナーがまさにこれ）では、確立済み h2c 接続が **10 秒後に接続ごと破壊**される。

### Five Whys

1. **なぜ要約ストリームが途中で切れた？** → alt-backend の Connect リスナー（h2c）への接続が確立 10.0 秒ちょうどで破壊され、多重化された全ストリーム（要約・Home 更新）が `context canceled` で終了したため。
2. **なぜ接続が 10 秒で破壊された？** → Go 1.26.6 が `ReadHeaderTimeout` のデッドライン設置を h2c preface 判定の前に移し、HTTP/2 側の解除は `ReadTimeout > 0` に限られる仕様変更があったため。当該リスナーはストリーミング応答を無制限にする意図で `ReadTimeout: 0` としており、解除条件を満たさなかった。
3. **なぜ Go 1.26.6 が検証なく本番に入った？** → セキュリティ修正の一環で go.mod が 1.26.6 を要求し、CI を通すために builder digest も 1.26.6 へ更新された。toolchain のパッチリリースは「低リスク」と暗黙に見なされ、リリースゲートに「長時間ストリームを実際に保持する」検証が存在しなかった。
4. **なぜ既存のテスト・E2E は捕捉できなかった？** → E2E はストリーム応答の成立と内容を検証するが、**10 秒を超えて生存すること**は検証しない。ユニット/CDC テストはストリーム寿命という属性自体を扱っていない。壊れたのは「時間」であり、既存ゲートはどれも時間軸を持っていなかった。
5. **なぜ原因特定に 1.5 時間を要した（初動で経路を誤認した）？** → (a) frontend→backend の実経路が compose の環境変数（BFF 経由）とコード内デフォルト（backend 直結）で食い違い、**h2c ホップの存在が文書化されていなかった**。(b) そのため再現ハーネスが HTTP/1.1 で組まれ、h2c のみで発症する本欠陥を素通しして「内部は健全」という誤結論を一度出した。(c) エッジプロキシのアクセスログは応答ヘッダ時刻のみでストリーム終了を記録せず、(d) 同時刻に別障害のアラートが鳴っており、初動の仮説空間を外側（CDN・エッジ）へ誤誘導した。

### 根本原因

**h2c リスナーにおける「`ReadTimeout: 0` はストリーミングに安全」という設定上の前提が、Go のパッチリリースで暗黙に破られた。** upstream の変更自体は Slowloris 対策の妥当な hardening であり、確立済み h2c 接続の長寿命ストリームというケースが upstream のテストにも当該リスナーの回帰テストにも存在しなかったことが、両者の間隙を生んだ。

### 寄与要因

- **news-creator の EOF 遅延（独立した潜在バグ）:** 最終トークン後も heartbeat 機構の二重 sentinel 待ちにより SSE の EOF が最大 10 秒遅延。要約の永続化は EOF 読了後のため、10 秒の切断に**常に**敗北し、生成完了分まで全て失われた。
- **Home ストリームの自動再接続**が接続破壊を無症状化し、被害の全体像（ストリーミング全滅）を隠した。
- **frontend の表示ロジック**（部分テキストがあるとエラー非表示・typewriter バックログのエラー時破棄）が、尻切れを「短い正常な要約」に見せた。
- **未適用の構成コミット**（エッジプロキシの新バージョンがコミット済み・未デプロイ）が「今回のリリースでエッジが変わった」という誤った容疑を成立させた。
- 同時刻に発火した**既存の別障害のアラート**（Web Push dead-letter）が red herring となった。

## 対応の評価

### うまくいったこと

- 実物コンポーネント（本番と同一イメージ）を使った隔離再現環境の構築により、ホップ単位の消去法を安全に実施できた（read-only 規律を通期維持、本番への変更ゼロで原因特定）
- 並列・独立の複数調査（ログ相関 / エッジ深掘り / リリース差分の敵対監査 / UI 症状分析）が**互いに独立に同一の根本原因へ収束**し、確度の高い結論になった
- ユーザーのライブ再現協力と 3 点同時ログ観測により、「複数ストリームの同一ミリ秒同時死」という決定的証拠を短時間で確保できた
- 修正は全て failing test 先行（時間スケールした回帰テストで 10 秒切断を 0.5 秒に縮めて再現）で実装され、再発時はテストが先に落ちる

### うまくいかなかったこと

- 「リリースでエッジプロキシが更新された」という**未検証の仮定**に初動の調査時間を投じた（実際には未適用だった）。デプロイ内容の事実確認（実際に再作成されたコンテナの列挙）を最初に行うべきだった
- 実経路のトポロジ（BFF 経由の h2c）を確認せず HTTP/1.1 で再現ハーネスを組み、「内部は健全」という誤った中間結論を一度確定させた
- 検知がユーザー報告に完全依存。ストリーム寿命の崩壊はリリース直後から観測可能だったのに、それを見る指標がなかった

### 運が良かったこと

- ユーザーが発生直後に利用・報告し、再現にも即応できた（利用がなければ長期潜伏していた）
- unary RPC が無傷で、サービス全面停止には至らなかった
- バッチ要約経路が独立していたため、要約データの恒久損失を免れた
- Go 1.26.5 の toolchain がローカルに残っており、パッチ間の差分再現が即座にできた

## 教訓

- **「時間」はテストされない限り壊れても見えない。** 機能・内容・契約はゲートで守られていたが、「ストリームが N 秒生きる」という時間属性はどのテストも保持していなかった。ストリーミングを持つシステムは寿命を第一級のテスト対象・監視対象にする必要がある。
- **toolchain のパッチリリースは「小さい変更」ではなく「全コードパスの再コンパイル」である。** 依存が 1 行も変わらなくても挙動は変わり得る。今回の upstream 変更自体は正当な hardening であり、「リスクが小さいはず」という直感はゲートの代わりにならない。
- **実経路と文書化された経路の乖離は、障害時に最も高くつく。** compose の環境変数がコード内デフォルトを上書きして BFF 経由 h2c になっていた事実が共有されておらず、再現ハーネスの設計を誤らせた。構成の上書きは「動く」だけでなく「知られている」必要がある。
- **クライアントの自動リトライ・再接続は可用性を上げると同時に障害を隠す。** リトライで症状が消える箇所ほど、サーバ側の一次指標（寿命・切断理由）が必要になる。
- **調査は「何が変わったか」の事実確認から始める。** コミットログではなく、実際に再作成されたコンテナ・実際に動いているイメージを最初に列挙していれば、エッジプロキシへの誤誘導は避けられた。
