## サマリー

2026-09-21 のテナント分離で、rag-orchestrator のベクトル検索は `rag_documents.user_id = $owner` で文書を絞るようになった。同じリリースの migration は `user_id` を nullable 列として足しただけで、既存行を埋める `rag_owner_backfill` は手動の一回限りコマンドとして用意されたまま、本番では一度も実行されなかった。

その結果、テナント分離より前に索引した文書の大半が、エラーを一切出さずにベクトル検索から見えなくなった。この状態が約 47 日続いた。ベクトル検索は毎回「成功」し、テナント分離以降に索引された文書だけを返していた。

2026-11-06 の質問では関連記事のほぼすべてが見えなかった。さらに、タグ展開クエリのスコアが原クエリのヒットを rerank 候補枠から押し出し、回答は RelevanceGate に拒否された。空回答の fallback は保存されない実装だったため、会話を開き直すと質問だけが残っていた。

検知はユーザー報告によるもので、同日中に修正（PR #286）と owner backfill で復旧した。ただし backfill は別の退行（検索の HNSW 不使用による応答停止）を引き起こした。これは [[PM-2026-061-augur-500-after-owner-backfill-hnsw-plan-and-citation-key]] で扱う。

## 影響

- **影響を受けたサービス:** rag-orchestrator（Ask Augur の retrieval 全経路と、関連記事の citation）
- **影響を受けたユーザー数/割合:** テナント分離より前に記事を索引していた Augur 利用者の全員
- **機能への影響:**
  - **ベクトル検索:** テナント分離より前に索引された文書の大半が不可視になった。見えていたのは、テナント分離以降に所有者付きで索引された一部の文書だけだった
  - **回答品質:** 不可視文書に答えがある質問では、関連記事が rerank 候補にほぼ入らなかった。その結果、無関係な記事を根拠にした浅い回答か、RelevanceGate による fallback（「十分な情報が見つかりません」系）になった。報告された質問では、関連する記事のほぼすべてが不可視だった
  - **鮮度の偏り:** 引用がテナント分離以降に索引された記事に偏った（[[PM-2026-057-rag-embedding-wipe-silent-bm25-degradation]] と同じ体感パターン）
  - **会話履歴:** 空回答の fallback で終わった会話は、開き直すと質問だけが残った。全期間の会話のうち無視できない割合がこの状態だった
- **影響を受けなかった機能:** 記事取り込み、要約、タグ付け、検索インデックス、Augur 以外の機能。テナント分離以降に索引された文書の検索
- **データ損失:** なし。所有者は alt-db 側の記事の所有情報から全量復元できた。元記事が削除済みの旧バージョン文書（孤児）は復元対象外だが、これは本障害以前から検索対象外のバージョンである
- **SLO/SLA違反:** 判定不能。retrieval の可視範囲を表す SLI が存在しなかった。fallback 率のアラートはあったが、最小件数条件のため発火条件を満たさなかった（「検知」参照）

## 検知

- **検知方法:** ユーザー報告（アラートではない）
- **検知までの時間 (TTD):** 約 46 日 21 時間
- **検知の評価:** 機能していない。以下が独立に検知を妨げていた。
  1. **無音に縮退する失敗モード。** 所有者フィルタは NULL 行をエラーなく除外するだけだった。ベクトル検索は「0 件」ですらなく、新しい文書だけが並ぶ「成功」として観測された。
  2. **カバレッジ監視が可視性を見ていなかった。** [[PM-2026-057-rag-embedding-wipe-silent-bm25-degradation]] の対策で入れた embedding カバレッジ監視（`AugurEmbeddingCoverageLow`）は、バージョンごとの embedding の有無だけを数えていた。検索側のもう 1 つのフィルタ条件（所有者）は分母にも分子にも入っていなかった。そのため可視範囲が大きく縮んでも緑のままだった。
  3. **fallback 率アラートの最小件数条件。** `AugurFallbackRateHigh` / `AugurFallbackRateCritical` は 30 分で 10 件以上、`AugurEmptyFallbacksRising` は 1 時間で 10 件超を発火の前提にしている。静かな時間帯の誤報を避けるための条件だが、この環境の実際の利用量はこれを下回ることが多い。そのため、fallback が続いても条件を満たしにくかった。
  4. **品質履歴の楽観バイアスの再発。** 空回答の fallback は `assistant_turn_not_persisted` を ERROR ログに出したうえで保存をスキップしていた。最悪の回答ほど会話履歴から消える構造は PM-2026-057 で指摘され、fallback 保存は「DONE」とされていた。しかし実際に保存されていたのは本文のある fallback だけで、RelevanceGate の拒否のように本文が空になる経路は残っていた。

## 根本原因分析

### 直接原因

テナント分離の migration が `rag_documents.user_id` を nullable 列として追加し、検索側は同じリリースで `user_id = $owner` の等値フィルタを有効にした。一方、既存行を埋める `rag_owner_backfill` は本番で実行されなかった。

### Five Whys

1. **なぜ 11-06 の質問は fallback で終わったか？** — rerank 後の最高スコアが RelevanceGate の閾値（0.25）を下回ったため。関連する記事が rerank 候補に入っていなかった。
2. **なぜ関連記事が rerank 候補に入らなかったか？** — 理由は 2 つあった。(a) 関連記事のほぼすべてが `user_id` NULL でベクトル検索から不可視だった。(b) 残った原クエリのヒットも、タグ展開で生まれた数十本のクエリぶん合算された RRF スコアと生スコアのまま比べられ、上位 40 件の rerank 候補枠から押し出された。1 本のリストの RRF は最大でも約 0.033 にしかならず、合算側に必ず負ける構造だった。
3. **なぜ既存文書の `user_id` が NULL のままだったか？** — migration は列の追加だけで、埋め戻しは別コマンド `rag_owner_backfill` の手動実行に委ねられていた。所有者フィルタはリリースとともに自動で有効になったが、埋め戻しには実行のトリガーも担当も完了判定もなかった。
4. **なぜ埋め戻しは実行されないまま放置され、実行もできなくなっていたか？** — 一回限りのコマンドは、書かれた時点の接続形態でしか動作確認されていなかった。その後の内部 RPC の mTLS 必須化と pgbouncer 経由の DB 接続にコマンドが追随しておらず、実行しようとしても失敗する状態だった。実際 11-07 の実行には、mTLS 対応と simple protocol 対応の 2 回の修正が必要だった。
5. **なぜ同じ型の障害が繰り返されたか？** — [[PM-2026-057-rag-embedding-wipe-silent-bm25-degradation]] と同じ構造だから。「検索に効く変更（破壊側）は自動で有効になり、既存データの整合（復旧側）は手動の一回限り手順に依存する」という非対称が、今度は embedding ではなく所有者で再演された。PM-2026-057 の教訓は embedding の再充填については仕組み化されたが、「検索のフィルタ条件を増やす変更一般」には一般化されていなかった。

### 根本原因

検索の可視範囲を狭める変更（nullable 列 + 等値フィルタ）が、既存データの埋め戻しと同じ運用強度で対になっていなかった。フィルタはリリースで自動的に有効になり、埋め戻しは実行の保証がない手動コマンドに置かれた。さらに、可視範囲を測る監視は既存のフィルタ条件（embedding の有無）しか見ておらず、新しいフィルタ条件を監視に足す手順がなかった。

### 寄与要因

- **rerank 候補枠のスコア空間の混在。** タグ展開クエリの合算 RRF と原クエリの単一リスト RRF を生スコアで比べて上位を切っていた。タグ展開には件数の上限がなく、数字や短い英字のような汎用語のタグもクエリになっていた。
- **空回答 fallback の非保存。** 会話を開き直すと質問だけが残り、ユーザー側でも「何が返ったか」を後から確認できなかった。品質の振り返りが楽観側に歪んだ。
- **テナント分離が複数サービスの認証強化と同じコミット群で着地した。** このリリースは契約ゲートで停滞した（[[PM-2026-058-lockstep-auth-hardening-contract-gate-deadlock]]）。rag 側の既存データ移行は別の手動手順として扱われ、リリース完了の判定に含まれていなかった。
- **一回限りコマンドの検証範囲。** `rag_owner_backfill` の単体テストは、本番と同じ接続経路（mTLS、pgbouncer）を通していなかった。

## 対応の評価

### うまくいったこと

- 報告から約 20 分で、read-only の並列調査（ログ集計 / rag-db・alt-db の分布確認）が 3 要因と証拠を確定した。
- 修正はすべて失敗テストを先にコミットしてから実装し、レビューを経て同日中にマージまで到達した。
- 本番 backfill は dry-run で対象を確認してから実行した。更新対象は `user_id IS NULL` の行だけで、再実行しても安全だった。1 回目の失敗は最初のページで止まり、部分更新を残さなかった。
- 本番への書き込みは、エージェントの自律実行ではなく運用者の明示的な実行に限られていた。
- 新設の所有者カバレッジアラートは、backfill で埋められない孤児文書を対象から外した。鳴り続けて無視されるアラートにしないためである。

### うまくいかなかったこと

- 1 回目の本番 backfill が pgbouncer 越しの prepared statement 衝突で失敗し、修正と再ビルドが必要になった。
- backfill によるデータ分布の大きな変化の前後で、検索の実行計画とレイテンシを確認しなかった。その結果、派生障害（[[PM-2026-061-augur-500-after-owner-backfill-hnsw-plan-and-citation-key]]）を本番で踏んだ。
- PM-2026-057 で「DONE」とされた fallback 保存が、空回答の経路をカバーしていなかった。DONE の判定が、全経路で結果が成り立つことの確認を伴っていなかった。

### 運が良かったこと

- 所有者情報は alt-db 側に正しく残っており、埋め戻しは純粋な再計算で済んだ。
- テナント分離以降に索引された文書は所有者付きだったため、全面停止ではなく品質劣化にとどまった。

## 教訓

- **フィルタ条件を足す変更は、既存データを不可視化する変更でもある。** nullable 列を追加して等値で絞れば、既存行は全部消える。この種の変更は、埋め戻しと同じ運用強度で対にしなければならない。
- **一回限りのコマンドは、書いた時点の環境でしか動かない。** 実行されないまま置かれたコマンドは、周囲の接続形態の変化（mTLS、pgbouncer）で黙って実行不能になる。「コマンドがある」は「移行できる」ではない。
- **可視範囲の監視は、検索の全フィルタ条件を分母に含めて初めて意味を持つ。** embedding カバレッジだけを見る監視は、所有者で見えなくなった文書を数えられない。フィルタ条件を増やすたびに、監視も更新する必要がある。
- **最小件数条件付きのアラートは、低トラフィック環境では沈黙する。** 誤報を避ける条件が、本物の劣化も隠していないかを利用量の実態と照らして確かめる。
- **DONE は「全経路で成り立つ」ことの確認までを含む。** PM-2026-057 の fallback 保存は、本文のある経路だけで DONE とされていた。
