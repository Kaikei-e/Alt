## サマリー

[[PM-2026-048]] のアクションアイテム#1として、本番デプロイが参照する secrets/.env を「対話用チェックアウト」と「デプロイランナー用チェックアウト」の2系統から、ホスト上の正準設定ディレクトリ（固定パス）へ集約する移行が実施された（Docker公式ドキュメントの env_file/secrets 絶対パス対応に基づく設計自体は妥当だった）。2026-07-24 09:49、この移行用の一回きりセットアップスクリプトが、鮮度比較なしに移送元の優先順位を「デプロイランナー側の残置コピー優先」に固定していたために4月末日付の古い設定ファイルを正準として昇格させ、加えて対話用チェックアウト側の .env バックアップを取らない非対称設計、およびコンテナ内非rootユーザーの読み取りを考慮しない権限設定（0640）という3つの欠陥を抱えていたため、新設のfail-fastステージングガードによる防御を挟みながらも、レポート生成サービスの誤ルーティング再発、その後の修復波でのDBマイグレータExit(1)・search-indexerの403クラッシュループ・依存待ちCreated滞留という多段障害を引き起こした。オペレータは稼働中コンテナの実効値を単一の真実源として正準設定を段階的に修復し、途中で1件の誤診断（distrolessコンテナへの `docker exec printenv` がOCIエラー文字列を鍵値と誤認）を経つつも、2026-07-24 11:25に全70コンテナの健全化をもって収束した。この過程で、無関係に潜伏していたログ収集系イメージのビルダー/ランタイムglibc不整合が偶発的に発火し、[[PM-2026-051]] として独立に記録している。

## 影響

- **影響を受けたサービス:** レポート生成サービス、DBマイグレータ群、search-indexer、ログ収集（aggregator/forwarder）、依存待ちで起動できなかった複数サービス
- **影響を受けたユーザー数/割合:** 定量化できず。本番環境の利用者は単一オペレータ（社内運用者）であり、一般エンドユーザーへの直接影響は本PM作成時点で確認されていない
- **機能への影響:** レポート生成機能が誤ルーティングenvによる再作成2回で約1時間不能。DBマイグレータ・search-indexer等が10:44の再作成波以降、約20分間断続ダウン（Exit(1)・403クラッシュループ・Created滞留）。ログ転送（可観測性）が[[PM-2026-051]]の発火により約40分停止
- **データ損失:** なし
- **SLO/SLA違反:** 移行作業に関する明示的なSLOは定義されていない
- **定量データ:** 全70コンテナが対象。多段障害発火時点（10:44）で複数サービスがExit(1)/クラッシュループ/Created滞留。正準secretsの欠落3点が判明し稼働系からの実効値回収を2系統（検索キー/マスターキー、および欠落secrets一式）で実施

## 検知

- **検知方法:** 新設のfail-fastステージングガードが「正準ディレクトリ読取不可」を検知しデプロイを阻止したことが最初の自動検知（09:55）。多段障害の全貌（DBマイグレータExit(1)・search-indexer 403クラッシュループ等）は10:44の再作成波で発生した症状からオペレータが把握した
- **検知までの時間 (TTD):** ガード自体は数分以内に「読み取り不可」の異常を検知したが、根本原因（正準の中身が古い＝「読めるが古い」状態）はガードの守備範囲外であり、実際の多段障害発生（10:44）とその原因特定はほぼ同時並行で進んだ
- **検知の評価:** fail-fastガードは「読めない」ことは検知できたが、「読めるが古い」ことは検知できなかった。これは今回導入されたガードのスコープ設計上の限界であり、設定の鮮度検証は別レイヤーの責務として残されている

## 根本原因分析

### 直接原因

正準設定移行用の一回きりセットアップスクリプトが、鮮度比較を行わずに移送元の優先順位を固定（デプロイランナー側残置コピー優先）としていたため、対話用チェックアウト側の最新 .env ではなく4月末日付の古いファイルを正準として昇格させた。

### Five Whys（系統A: 設定の鮮度）

1. **なぜ正準設定ディレクトリに古い .env が昇格したか？** → セットアップスクリプトの移送元優先順位が「デプロイランナー側の残置コピー優先」に固定されており、実際に新しい方を選ぶ鮮度比較（更新日時・内容diff等）を行わなかったため。
2. **なぜ移送元優先順位が鮮度比較なしに固定されていたか？** → スクリプト設計時に「デプロイランナー側が正、対話用は補助」という暗黙の前提が置かれ、両者が食い違いうる（対話用チェックアウト側でオペレータが直接 .env を更新していた）という運用実態が設計に反映されなかったため。
3. **なぜこの暗黙の前提を検証する仕組み（dry-run diff・承認ゲート）が移行スクリプトになかったか？** → 一回きりの移行スクリプトは通常の本番変更と同等のテスト対象・レビュー対象として扱われない文化があり、移行系スクリプトに対するstaging検証やdiff確認を必須とするプロセスが未整備だったため。
4. **なぜこの文化・プロセスの欠如がこれまで露呈しなかったか？** → [[PM-2026-048]] で発覚した「2系統チェックアウトの分岐」自体が今回の移行の直接の動機であり、これまで一回きりの移行作業自体を経験する機会が少なかったため、テスト省略の代償が可視化されていなかった。
5. **(根本)** → 「移行系の一回きりスクリプトはテスト対象外」という文化的な例外が、まさにその移行が解消しようとしていた設定分岐と同種の「片方が正しいという暗黙仮定」を、スクリプト自体の中に再導入してしまった。

### Five Whys（系統B: 権限設計）

1. **なぜDBマイグレータ群がsecrets読取不可でExit(1)したか？** → 正準secretsのファイル権限が0640で設定されており、コンテナ内で稼働する非rootユーザーに読み取り権限がなかったため。
2. **なぜ権限が0640で設定されたか？** → 「グループ外からの秘匿性向上」という意図でファイル単位の権限を絞る設計判断がなされたが、実際にファイルを読む必要があるコンテナ内消費者のuid/gidがどのグループに属しているかの分析が行われなかったため。
3. **なぜこのuid分析が移行手順に含まれていなかったか？** → 従来運用（0644）からの権限変更が「セキュリティ強化」という単一の目的から発想され、設定変更の影響範囲検証（staging再現によるコンテナ起動確認）を移行手順のステップとして明示的に要求するプロセスが存在しなかったため。
4. **なぜディレクトリ側の権限（0750で遮蔽）とファイル側の権限（0644でコンテナ可読）という最終的な組み合わせに、事前ではなく事後の障害対応でしか到達できなかったか？** → 権限設計の検証が「本番での実際のコンテナ起動」でしか行われておらず、事前にstagingで同一権限構成を再現して検証する手順がなかったため。
5. **(根本)** → セキュリティ強化の意図（0640）と可用性要件（コンテナ内非rootユーザーからの読み取り）が、移行設計の段階でトレードオフとして明示的に検討されず、本番での実障害を通じてはじめて正しい組み合わせ（ディレクトリで遮蔽・ファイルで可読）が発見された。

### 根本原因

正準設定移行という構造的に正しい設計判断（[[PM-2026-048]] アクションアイテム#1）を実装するにあたり、一回きりの移行スクリプトが通常の本番変更と同等の検証（鮮度比較、diff確認、dry-run、staging再現、承認ゲート）の対象外として扱われる文化的な例外があった。この結果、スクリプトは(1)鮮度比較なしの移送元優先順位固定、(2)非対称バックアップ設計、(3)コンテナ内消費者のuid分析を欠いた権限設定という3つの独立した欠陥を抱えたまま本番へ適用され、新設のfail-fastガードが1回検知に成功したにもかかわらず、ガードの守備範囲外だった「読めるが古い」状態と権限起因の複数サービス同時停止という多段障害を引き起こした。

### 寄与要因

- 前夜のデプロイ再実行によるレポート生成2連続失敗（[[PM-2026-048]] 再発）が同日朝に発生しており、対応リソースが分散した状態で移行作業が行われた
- 「Created滞留コンテナは作成時点のenvを凍結する」というcompose挙動が一般に知られておらず、誤診断（distrolessコンテナへの `exec printenv` をOCIエラーと誤認）を招く一因になった
- 無関係に潜伏していたログ収集系イメージのglibc不整合（[[PM-2026-051]]）が本件の再作成波で偶発的に発火し、事象を多段階に見せる一因となった（独立した根本原因であり、本件の直接原因ではない）

## 対応の評価

### うまくいったこと

- fail-fastステージングガードが古い正準設定でのデプロイを2回とも大声で（loudに）阻止した。CLAUDE.md Rule 8/9が求める「サイレントフォールバック禁止・fail-fast起動」原則が実際に機能した具体例
- finalize_guard的な仕組み（[[PM-2026-049]] の教訓を受けた品質ゲート改修）がここでも空洞レポート版の永続化を阻止した
- 修復後の正準設定は「1箇所の編集が全参照者に即座に伝播する」という当初の設計意図を実証した
- 復旧の真実源を常に稼働系（実効キー・実効値）に置くという判断が一貫しており、稼働中コンテナからの無表示回収・書き戻しによって最終的に正しい値へ収束できた

### うまくいかなかったこと

- 一回きりの移行スクリプトが本番相当のレビュー・テストを経ずに投入され、3つの独立した欠陥を同時に抱えたまま実行された
- 権限設計（0640）がコンテナ内消費者のuid分析を欠いたまま決定され、事前のstaging検証なしに本番へ適用された
- 誤診断（`docker exec printenv` のOCIエラー文字列を鍵値と誤認）により不要な再作成が発生した。実害はなかったが、正しい検査手順（`docker inspect` 経由）が浸透していなかったことを示すツーリングギャップ

### 運が良かったこと

- オペレータ側のsecretsバックアップが、正準secretsの欠落3点（対象外サービスsecret・ssh鍵ディレクトリ）の補充に使える状態で残っていた
- 旧良品のログ収集系イメージがローカルキャッシュに残存しており、[[PM-2026-051]] の緊急修正時にロールバック手段として機能した

## 教訓

- fail-fastガードは「読めるか」を検証できても「正しいか（鮮度）」までは検証できない。ガードのスコープ設計は、防ぎたい失敗モードを明示的に列挙してから決める必要がある。
- 一回きりの移行スクリプトほど、通常の本番変更より低い検証水準で投入されがちだが、実際には複数サービスを同時に巻き込む変更であり、むしろ高い検証水準（dry-run diff、staging再現）が必要。
- 権限設計は「絞る側」の意図だけでなく「実際に読む側（コンテナ内消費者のuid/gid）」を必ず分析対象に含める。
- 復旧時の真実源は「稼働中の実効値」に置くのが最も信頼できる。ドキュメントや過去のバックアップよりも「今動いているものが正しい」という原則が今回も有効だった。
- 誤診断の一因は「正しい検査手段が周知されていない」ことにある。distrolessコンテナはshellを持たずexecの挙動が通常と異なるため、専用の検査手順（inspect経由）をrunbook化しておく必要がある。
