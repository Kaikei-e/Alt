## サマリー

2026-11-19 夜から 2026-11-20 未明にかけて、リリースパイプラインの契約ゲート（`can-i-deploy --to-environment production`）が依存する Pact Broker 上の状態が数週間にわたり無音でドリフトしていたことに起因し、同一日のリリースが 2 度停止した。1 度目（18:59〜20:14、遅延 75 分）は、PR #373 で `alt-backend` が `recap-worker` との契約から不要な interaction を削除した際、本番稼働版の `recap-worker` をオンデマンド検証する Broker の webhook が期限切れ認証情報で HTTP 401 となり不発に終わった（途中、手動再実行の `e2e (alt-backend)` も `npm ci` の `ETIMEDOUT` 3 回で失敗し、原因は未計測）。2 度目（23:49〜00:16、遅延 26 分）は、`rag-orchestrator` のみの PR #379 のリリースで、独自ゲートを持たない `alt-data-hub`（[[000954]]）のデプロイ記録が毎回スキップされていた結果、Broker 上の本番記録が 2026-09-21 の `863ee8c` のまま更新されていなかったため契約ゲートに拒否された。いずれも運用者による Broker 側の手動操作（`recap-worker` 本番版の手動検証実行、および実稼働中の `alt-data-hub` `c33d88e` の手動デプロイ記録）で復旧し、ユーザー向けサービスの停止やデータ損失は発生していない。

- **影響を受けたユーザー数/割合:** 0 人 / 0%（本番環境は各停止中も前バージョンで稼働を継続）
- **機能への影響:** 本番機能への影響なし（リリースの反映遅延のみ）
  - 停止 1: PR #372 および PR #373（18:58〜18:59 マージ）の反映が、契約ゲート失敗および続く手動再実行時の `e2e (alt-backend)` 失敗（`npm ci` の `ETIMEDOUT` 3 回）により、20:14:03 完了のリリース（`6b5e5a6`）まで 75 分遅延した。並行して 19:22:37 開始の PR #374 自動リリースも 19:41 に契約ゲートで失敗した

- **データ損失:** なし
- **SLO/SLA違反:** なし（リリースパイプラインの反映遅延に対する SLO は未定義。ユーザー向け稼働面に影響なし）

## 検知

- **検知方法:** 停止 1・停止 2 ともに、契約ゲートの失敗によるリリースパイプラインの赤を運用者が確認した（独立した監視アラートによる検知ではない）
- **検知までの時間 (TTD):** 契約ゲートで止まったこと自体はパイプライン失敗時点で可視化された（停止 1: 19:33 失敗・運用者の認知時刻は未計測、停止 2: 23:57:18 失敗 → 00:03 共有）。ただし、Broker 側の状態ドリフト自体は停止 1 で webhook の最終起動（2026-10-27）以降の未計測の時点から、停止 2 で 2026-09-21 以降、それぞれ無検知のまま潜伏していた
- **検知の評価:**
  - 契約ゲートは両回とも fail-closed で動作し、未検証の組み合わせを本番に流さなかった
  - Pact Broker の webhook 配信失敗（HTTP 401）に対するアラートは存在せず、さらに Broker の webhook ステータス API が HTTP レスポンスコードを隠すため、コンテナログを直接見るまで 401 に気付けなかった
  - Broker 上の本番デプロイ記録と、本番ホストで実際に稼働しているコンテナバージョンを比較する定期検査・アラートが存在しなかった
  - デプロイ記録スキップ時のログ文言が「the broker has no such version」と実態に反する説明を出しており（実際には `c33d88e` も検証結果も Broker に存在していた）、異常の発見を遅らせた
  - 停止 1 の手動再実行で起きた `e2e (alt-backend)` の `npm ci` `ETIMEDOUT`（3 回連続）は、別ホストであるビルドランナー側の原因が未計測である（開発ホストからはレジストリ応答 3/3 成功）

## 根本原因分析

### 直接原因

- **停止 1**: `alt-backend` が consumer 契約を変更した際（PR #373）、本番稼働版の `recap-worker`（`e8c09f5`）に新契約を再検証させる Pact Broker の `contract_requiring_verification_published` webhook が期限切れ認証情報によりコードホストから HTTP 401 を返されて失敗し、検証結果が Broker に届かず契約ゲートが失敗した
- **停止 2**: Pact Broker 上の `alt-data-hub` の本番記録が 2026-09-21 の `863ee8c` のまま更新されておらず、PR #379 の契約ゲートが実稼働中の `c33d88e`（`rag-orchestrator` `5a94641` を検証済み）ではなく旧版 `863ee8c` を参照して「検証済み pact が存在しない」と判定した

### Five Whys

**停止 1（webhook によるオンデマンド provider 検証の不発）**

1. **なぜ契約ゲートが失敗したか？** → consumer 側（`alt-backend`）のみが契約を変更した際、本番稼働中の provider（`recap-worker` `e8c09f5`）に対する新しい契約の検証結果が Broker に存在せず、リトライ窓内にも届かなかったから
2. **なぜオンデマンドの provider 検証が起動されなかったか？** → 契約公開時にパイプラインへ通知する Broker の `contract_requiring_verification_published` webhook（12 件）が、期限切れ認証情報によりコードホストから HTTP 401 で拒否されていたから
3. **なぜ 2026-10-27 の最終起動後に発生した認証失敗に気付かなかったか？** → 認証情報がいつから拒否され始めたかが未計測であるうえ、webhook 配信失敗のアラートが無く、Broker の webhook ステータス API も HTTP ステータスを返さないため、失敗がコンテナログの中だけに留まっていたから
4. **なぜ数週間後の特定リリースまで顕在化しなかったか？** → 通常のリリースでは consumer と provider が一緒に出るか契約ファイル変更がなく、パイプライン内の検証だけで完結していたため、webhook 経路に依存する「consumer 単独の契約変更」が起きるまで露出しなかったから
5. **なぜシステム全体としてこの状態を許容していたか？（両停止に共通のシステム原因）** → **契約ゲートが依存する Pact Broker の状態（webhook の認証・疎通健全性と本番デプロイ記録）を他処理の副作用として受動的に維持するだけで、その鮮度と実態との一致を継続的に検査・保証する仕組みが存在しなかったから**

**停止 2（`alt-data-hub` 本番デプロイ記録の陳腐化）**

1. **なぜ契約ゲートが `rag-orchestrator` `5a94641` を拒否したか？** → ゲートが本番稼働中の `alt-data-hub` として 2026-09-21 の `863ee8c` を参照し、検証済み pact が無いと判定したから（実際のコンテナは `c33d88e` で、`5a94641` との検証も 22:31:34 に成功済みだった）
2. **なぜ `alt-data-hub` の本番記録が `863ee8c` のまま止まっていたか？** → パイプラインのデプロイ記録ステップが、自身のゲートアーティファクトを持たない pacticipant を一律スキップする実装になっていたから
3. **なぜ `alt-data-hub` には自身のゲートアーティファクトが無かったか？** → [[000954]] の分割により `alt-data-hub` は独自ゲートを持たず同一コミットの `alt-backend` 契約ジョブから検証結果を公開する構成になっている一方、未公開サービスの 404 回避用に追加されたスキップガードが「親サービスに代理公開される pacticipant」を考慮していなかったから
4. **なぜ約 2 か月間（2026-09-21〜11-19）スキップされ続けても気付かなかったか？** → スキップログが「the broker has no such version」と誤った理由を出して正常終了し、かつ過去のリリースでは `rag-orchestrator` と `alt-backend` が同時に出されていたためゲートがリリースコミットに固定し本番ポインタを参照しなかったから（PR #379 が契約変更後初の単独リリースだった）
5. **なぜシステム全体としてこの状態を許容していたか？（両停止に共通のシステム原因）** → **契約ゲートが依存する Pact Broker の状態（webhook の認証・疎通健全性と本番デプロイ記録）を他処理の副作用として受動的に維持するだけで、その鮮度と実態との一致を継続的に検査・保証する仕組みが存在しなかったから**（あわせて [[PM-2026-058]] で同構造と乖離検査の必要性が記録済みだったが、未実施のまま持ち越されていた）

### 根本原因

**契約ゲート（`can-i-deploy --to-environment production`）が正しさの前提とする Pact Broker の状態（webhook 認証の有効性、および本番環境デプロイ記録）が副作用任せで維持されており、状態の鮮度や実稼働コンテナとの一致を能動的に検査・通知する仕組みが無かったこと。**

どちらのドリフトも平常のリリース形状（両側同時更新や契約変更なし）では踏まれず、前者は webhook による最終起動（2026-10-27）以降の未計測の期間、後者は約 2 か月（2026-09-21 以降）のあいだ無検知で潜伏し、条件が揃った 2 度のリリースで連続して表面化した。

### 寄与要因

- **特定のリリース形状でのみ踏まれる潜在欠陥だった**: 停止 1 は「consumer のみが契約変更し provider がリリース対象外」、停止 2 は「契約変更後の `rag-orchestrator` が `alt-backend` を伴わずに単独リリース」という条件で初めて顕在化した
- **Broker API とスキップログの不透明さ**: webhook の HTTP 401 は API レスポンスに出ずコンテナログでしか確認できなかった。また `record-deployment` のスキップログは「the broker has no such version」と実態と異なるメッセージを出していた
- **`recap-worker` verifier のディスク再生設計と調査中に見つかった偽陽性リスク**: `recap-worker/recap-worker/tests/provider_verification.rs` はチェックアウト先のディスク上の契約ファイル（`load_pact("../../pacts/<consumer>-recap-worker.json")`）を再生し、その結果が Broker 上の該当ペアの全契約版に紐付く。そのため旧コミットで再検証すると、後から追加された interaction まで検証済み（false green）扱いになり得る構造だった（本件では削除のみだったため結果自体は正しかった）
- **[[PM-2026-058]] のアクション未実施**: `alt-data-hub` が独自ゲートを持たず `record-deployment` でスキップされる構造および本番稼働版との乖離監視は [[PM-2026-058]] で既に記録されていたが、期限超過のまま残っていた
- **ビルドランナー側の `npm ci` タイムアウト（原因未計測）**: 停止 1 の手動再実行時に `e2e (alt-backend)` が `ETIMEDOUT` 3 回で失敗し、復旧時間を押し上げた

## 対応の評価

### うまくいったこと

- 契約ゲートが両回とも fail-closed で機能し、未検証の組み合わせを本番に出さなかった
- 原因の特定を、Broker の記録・ログと実稼働コンテナのバージョンを照合する読み取り専用の確認で行い、安全に事実関係を確定できた
- 両停止とも、運用者による単一かつ可逆的な Broker 側操作（`recap-worker` 本番版の手動検証実行、および実稼働と一致する `alt-data-hub` `c33d88e` の手動デプロイ記録）で復旧できた
- 停止 2 では復旧前の読み取り専用 matrix 照会で全 6 相手先との整合を確かめ、復旧後の `rag-orchestrator` `5a94641` も再起動 0 回・error ログ 0 行で稼働を確認できた

### うまくいかなかったこと

- webhook による最終起動（2026-10-27）以降の未計測な時点からの認証失効と、`alt-data-hub` 本番記録の停止（2026-09-21 以降）のいずれも、表面化するまで無検知で放置された
- 停止 1 の手動再実行時に `e2e (alt-backend)` が `npm ci` の `ETIMEDOUT` 3 回で失敗し、ビルドランナー側の原因は未計測のまま次の自動リリースまで反映が延びた
- `record-deployment` のスキップログが「the broker has no such version」と事実に反する文言を出力し、記録が追従していない異常を隠した
- 停止 1 のパイプライン側事前検証は未だ実リリース条件で発火しておらず、また失効した webhook 認証情報（12 件）の更新自体と、`alt-backend` を伴わない `alt-data-hub` 単独リリースの記録ギャップは本件時点で残課題として残っている

### 運が良かったこと

- 停止 1（PR #373）は interaction の削除のみであり、追加を含まなかったため、`recap-worker` のディスク契約ファイル再生による偽陽性（false green）が起きず検証結果が正確だった
- 停止 2 が `rag-orchestrator` のみの小さな単一サービスリリース（PR #379）で発生したため、調査開始（00:03）から手動記録（00:09:24）まで約 6 分で復旧できた
- 両回とも本番環境のサービス提供は無停止で継続し、ユーザー影響は発生しなかった

## 教訓

- **副作用で維持される前提状態は、検査が無ければ必ずドリフトする。** webhook の認証鮮度も Broker の本番デプロイ記録も、通常のリリースが通っているだけでは異常が見えず、条件を満たすリリースが来た日に突然ゲートを止める
- **「存在すること」と「最新・有効であること」は別である。** webhook が 12 件登録されていること（パイプライン起動の最終実績は 2026-10-27、認証情報が拒否され始めた時点は未計測）や、Broker に本番記録が存在すること（2026-09-21 の `863ee8c`）は、現在有効である証明にはならない。実稼働状態との突合が必要である
- **不正確なスキップログと隠蔽されたエラーは調査と検知を遅らせる。** 「the broker has no such version」という実態と違う通知や、API レスポンスに出ない HTTP 401 は、異常を正常の陰に隠す
- **代理公開されるサービスは記録経路でも明示的に扱う必要がある。** `alt-data-hub` のように [[000954]] で分離され検証を親サービスが担う pacticipant は、ゲート有無で一律スキップする仮定と衝突する
- **過去の障害で特定した監視・予防アクションを持ち越すと、次の境界変更で同じ形で再発する。** [[PM-2026-058]] で特定されていた乖離検査が未実施のまま残ったことが、2 か月後の停止 2 をそのまま引き起こした
