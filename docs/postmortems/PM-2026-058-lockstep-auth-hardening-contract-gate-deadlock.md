## サマリー

2026-09-21、`863ee8c46` のリリースで契約ゲートが 8 ジョブ失敗した。原因は、**4 つの provider（knowledge-sovereign / recap-subworker / search-indexer / alt-backend）が同一コミット群で inbound 認証とテナント分離を同時に強化した**ことにある。契約ゲートは「本番稼働中の consumer が新しい provider の要求する資格情報を持っていない」を正しく検出していたが、**本番デプロイ記録を進めるのはリリース完走時の最終段だけで、契約検証はその手前で旧 consumer を相手に走る**ため、lockstep な破壊的変更は構造上どの順序でも自力では通れなかった。

この鶏卵構造は [[PM-2026-053]] で既に特定・文書化されていたが、是正アクションが未着手のまま次の lockstep リリースを迎えた。解決にはロール順序を 5 wave に分割し、実在しない非互換 2 件を force-override、残りは順序で解消した。途中、オペレータ前提条件の未実施（secret の欠落・権限・未設定の環境変数）が 3 回連続でデプロイを止め、そのうち 1 回で acolyte-orchestrator が起動ゲートに阻まれ約 14 分クラッシュループした。

## 影響

- **影響を受けたサービス:** acolyte-orchestrator（完全停止 約 14 分）、alt-butterfly-facade / recap-worker / alt-data-hub（ロール時の瞬断のみ）
- **影響を受けたユーザー数/割合:** 単一ユーザー構成のため 1 / 1。Acolyte 機能が約 14 分利用不可
- **機能への影響:** 部分的停止（Acolyte のみ）。フィード購読・記事閲覧・検索・Knowledge Trail は無停止
- **データ損失:** なし。acolyte の legacy report 10 件に所有者 UUID を付与したが、これは設計どおりの移行であり損失ではない
- **SLO/SLA違反:** なし（個人運用のため SLO 未定義）
- **エンジニアリングコスト:** release-deploy 12 回（成功 5 / 失敗 7）、on-demand 契約検証 6 回以上。実作業 約 5 時間

## 検知

- **検知方法:** 契約ゲート（Pact can-i-deploy）の失敗。アラートでもユーザー報告でもなく、リリースパイプラインが自ら止まった
- **検知までの時間 (TTD):** 0 分（変更を出そうとした瞬間に検出）
- **検知の評価:** **理想的**。ゲートは本来の目的どおり、デプロイ窓で実際に壊れる非互換を本番到達前に止めた。8 件の失敗に偽陽性は 1 件も無く、うち 4 件は実在の非互換、4 件はテストフィクスチャが本番と食い違っていた事実の露呈だった。

一方で acolyte-orchestrator の crash-loop は**パイプラインの deploy ジョブ失敗としてしか観測できなかった**。コンテナの crash-loop 自体を検知するアラートは存在せず、手動でコンテナ状態を確認して初めて判明した。

## 根本原因分析

### 直接原因

4 つの provider が同一コミット群で inbound 認証とテナント分離を同時に強化したため、本番稼働中の consumer（前回リリース版）がいずれも新しい資格情報を送れず、契約ゲートが全面的に赤になった。

| provider | 強化コミット | 影響 consumer | 検証の相手 | 分類 |
|---|---|---|---|---|
| knowledge-sovereign | `a19597d6c` | alt-backend / rag-orchestrator | 実サーバ | 実在の非互換 |
| recap-subworker | `3dda95fd2` | recap-worker | 実アプリ router | 実在の非互換 |
| search-indexer | `1332fe974` | rag-orchestrator / acolyte-orchestrator | 実サーバ | 実在の非互換 |
| search-indexer | `1332fe974` | alt-backend | 実サーバ | フィクスチャの虚構 |
| alt-backend | `13673a3fa` | alt-butterfly-facade | スタブ | フィクスチャの虚構 |

### Five Whys

1. **なぜリリースが約 12 時間停滞したか？**
   → 契約ゲートが「本番稼働中の consumer が新 provider の要求する資格情報を持っていない」を検出し続け、どの dispatch 順序でも通らなかったから。

2. **なぜどの順序でも通らなかったか？**
   → 本番デプロイ記録を進めるのはリリース完走時の最終段だけで、契約検証はその手前で旧 consumer を相手に走る。lockstep な破壊的変更では、デプロイしないと記録が進まず、記録が進まないとデプロイできない鶏卵構造になるから。

3. **なぜ lockstep な破壊的変更が 4 サービス分まとめて出たか？**
   → 認証・テナント分離の強化（[[000954]] の follow-up を含む）が単一の変更セットに集約され、consumer 側の対応と provider 側の強制が同一コミット群に同居したから。個々の変更はいずれも正しく、単体では問題にならない。

4. **なぜ同居が問題になると事前に分からなかったか？**
   → この鶏卵構造は [[PM-2026-053]] の根本原因表 #3 で既に特定され、アクションアイテム #10（手動 record-deployment の手順化）と #11（新サービス追加チェックリスト）として記録されていたが、**いずれも未着手のまま**で、知識が文書の中だけに留まり運用に組み込まれていなかったから。

5. **なぜ未着手のまま次の lockstep リリースを迎えたか？**
   → ポストモーテムのアクションアイテムに担当と期限はあったが、**実施を強制する仕組み（リリース前チェック・CI ゲート・起動時検証）が無く**、「次に同じ穴を踏むまで思い出さない」状態だったから。文書化は再発防止ではなく、再発時の復旧時間短縮にしか効いていなかった。

### 根本原因

**[[PM-2026-053]] で特定済みの構造的欠陥に対する是正が、文書化とアクションアイテム化に留まり、機械的な強制力を持たなかったこと。** 鶏卵構造そのものは既知であり、復旧手順も概念としては分かっていた。欠けていたのは「リリース前にこの状況を検出し、正しい wave 順序を提示し、前提条件の未実施を拒否する」層である。

### 寄与要因

- **オペレータ前提条件が手作業依存だった。** 新規 secret `rag_api_token.txt` がホストに存在せず、手動作成された 5 件の secret が `0600` のまま runner から読めず、acolyte の起動ゲートに必要な環境変数が canonical .env に無かった。いずれも 3 回連続でデプロイを止めた
- **手で維持されたリストが drift していた。** on-demand 契約検証の pacticipant 許可リストから alt-data-hub が漏れていた。このリストは別の定義と一致させる前提でコメントされているが、**その参照先は既に存在しない**
- **gate leg を持たない pacticipant が自己記録できない構造だった。** alt-data-hub は [[000954]] の分割により独自の gate leg を持たず、単独 dispatch では record-deployment が必ず skip される。デプロイ側のコメントはこの drift の症状を逐語で予言していたが、検出する仕組みは無かった
- **調査中の自傷が 1 件あった。** 契約テストの interaction 名を実在 RPC に張り替えた結果、**デプロイ済みのどの provider からも満たせない pact** を publish し、新たな失敗軸を作って 1 run を消費した。pact の interaction 追加・改名それ自体が lockstep 変更であるという性質が認識されていなかった
- **secret 監査の抽出が 2 回とも不正確だった。** 1 回目は正規表現がハイフンを含む名前を除外して 14 件を取りこぼし、その欠けた一覧を根拠に「必須 secret が存在しない」という**誤った BLOCKED 判定**を生んだ。検証スクリプト自体が検証対象になっていなかった

## 対応の評価

### うまくいったこと

- **契約ゲートが設計どおりに機能した。** 8 件の失敗すべてが本物の検出で、偽陽性ゼロ。実在の非互換（4 件）を本番到達前に止めた。もしゲートが無ければ、`/trail` の描画・Trail 検索・記事取り込みのイベント追記・outbox worker・日次 recap のクラスタリングがデプロイ窓で静かに壊れていた
- **fail-fast 設計が期待どおり大声で失敗した。** acolyte の legacy owner ゲート、secret の preflight、いずれも「warn して limp する」のではなく即座に停止し、原因を自己説明的なメッセージで示した（Critical Rule 9 の効果）
- **失敗を「実在の非互換」と「フィクスチャの虚構」に分類したことで、force-override を 2 件に限定できた。** 分類せずに全件 override していれば、実在の非互換 4 件を本番に持ち込んでいた
- **最終的な wave 順序でランタイム障害ゼロ。** consumer を先に出す原則が全ケースで成立し（旧 provider は余分な資格情報を無視する）、逆順による 401/400 は一度も発生しなかった
- **override の証跡が gitignore 下に残された。** 公開リポジトリに broker 内部 ID を持ち込まずに監査可能性を確保できた

### うまくいかなかったこと

- **wave 設計を 3 回作り直した。** rag-orchestrator が「search-indexer / knowledge-sovereign の consumer」かつ「alt-backend / alt-harvester に対する RAG API の provider」という二重の役割を持つこと、alt-data-hub が gate leg を持たないことを、いずれも事前に織り込めず実行中に発見した
- **契約テストの改名を単独で出し、新たな失敗軸を作った。** 実装に近づける方向の正しい修正であっても、consumer 単独で出してはいけなかった
- **secret 監査を 2 回とも不正確に実施し、うち 1 回は誤った BLOCKED 判定に直結した。** 権限確認も 1 回目は実行ユーザーの読み取り可否を見ており、runner から読めるかを見ていなかった
- **オペレータ前提条件の未実施が 3 回連続でデプロイを止めた。** 1 回目で全件を洗い出せていれば 2 回分の試行を節約できた

### 運が良かったこと

- **alt-data-hub が PKI enrollment parent の展開で既に新版にロールされていた。** このリリースで最もリスクの高いロール（alt_db の唯一のオーナー・mTLS 専用・1 ヶ月分の差分）を、改めて実施せずに済んだ。本番ポインタを手で合わせるだけで解決した
- **acolyte-orchestrator の crash-loop が副次機能で、単一ユーザー構成だった。** 主要導線を巻き込まず、約 14 分で復旧した
- **legacy report の所有者候補が一意だった。** identity が 1 件しか存在しなかったため、10 件の帰属先に判断の余地が無く、即座に決定できた。複数ユーザー環境であればマッピングファイルの作成が必要で、停止時間は大幅に伸びていた

## 教訓

- **ゲートが赤いことと、ランタイムが壊れていることは別である。** 今回 8 件の失敗のうち 4 件はテストフィクスチャが本番と食い違っていた事実の露呈で、本番は最初から正しかった。分類を先にやらずに一括 override していれば、実在の非互換 4 件を本番に持ち込んでいた。**provider 検証が実サーバを立てているのかスタブなのかを最初に確認する**ことが、この分類の決定的な分かれ目になる
- **「文書に書いた」は「実施される」ではない。** 本件は [[PM-2026-053]] の再演であり、鶏卵構造も復旧手順も既に文書化されていた。それでも 12 時間かかったのは、文書が運用に組み込まれず、実施を強制する層が無かったからである。**アクションアイテムは実行可能なスクリプトか CI ゲートになって初めて再発防止になる**
- **手で維持されるリストは必ず drift し、参照先が消えても気づかない。** 今回 drift していた許可リストは「別ファイルと一致させる」とコメントされていたが、その別ファイルは既に存在しなかった。同期を人間の注意力に依存させた時点で、drift は時間の問題である
- **契約の interaction を追加・改名することは、それ自体が lockstep 変更である。** 新しい契約はデプロイ済みのどの provider からも満たせないため、provider を先に出す choreography が要る。「実装に近づける正しい修正」であることは免罪符にならない
- **検証スクリプト自体が検証対象である。** secret 一覧の抽出正規表現がハイフン 1 文字を除外していたために 14 件が消え、その欠けた一覧が誤った BLOCKED 判定を生んだ。**一覧を突き合わせるときは、まず一覧の件数が期待と合うかを疑う**
- **単一ユーザー構成は、復旧の選択肢を狭める代わりに判断を速くした。** legacy report の帰属先に候補が 1 つしか無かったことが、停止時間を 14 分に抑えた最大の要因である。多ユーザー環境では同じゲートがはるかに長い停止を招く
